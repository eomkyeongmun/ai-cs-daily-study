# CPU - CPU Architecture and Pipeline

## 핵심 개념

## CPU Architecture and Pipeline 핵심 개념

CPU 아키텍처는 프로그램의 명령어를 해석하고 실행하기 위해 CPU가 어떤 구조와 원리로 설계되어 있는지를 설명하는 개념이다. 넓게는 ISA(Instruction Set Architecture), 레지스터 구조, ALU, 제어 장치, 캐시, 메모리 계층, 인터럽트 처리, 파이프라인, 분기 예측, 명령어 수준 병렬성 등을 포함한다. 그중 CPU 파이프라인은 하나의 명령어 실행 과정을 여러 단계로 나누고, 각 단계를 서로 다른 명령어가 동시에 사용하도록 하여 전체 처리량을 높이는 기법이다.

예를 들어 명령어 하나를 실행하려면 보통 명령어 가져오기, 해석, 실행, 메모리 접근, 결과 저장 같은 과정이 필요하다. 파이프라인이 없다면 CPU는 한 명령어가 모든 단계를 끝낼 때까지 다음 명령어를 시작하지 못한다. 반면 파이프라인 구조에서는 첫 번째 명령어가 실행 단계로 넘어간 동안 두 번째 명령어는 해석 단계에 있고, 세 번째 명령어는 가져오기 단계에 있을 수 있다. 즉, 개별 명령어의 지연 시간 자체가 반드시 줄어드는 것은 아니지만, 일정 시간이 지난 뒤 단위 시간당 완료되는 명령어 수가 증가한다.

CPU 파이프라인이 중요한 이유는 현대 컴퓨터 성능의 핵심이 단순히 클럭 속도만으로 결정되지 않기 때문이다. 파이프라인, 캐시, 분기 예측, 슈퍼스칼라 실행, 비순차 실행 같은 구조적 최적화가 결합되어 실제 프로그램 성능을 결정한다. 운영체제, 컴파일러, 런타임, 데이터베이스, 웹 서버, 클라우드 워크로드 모두 CPU 아키텍처의 영향을 받는다. 특히 분기문이 많은 코드, 메모리 접근이 불규칙한 코드, 캐시 미스가 잦은 코드, 동기화가 많은 멀티스레드 코드는 파이프라인 효율이 떨어질 수 있다. 따라서 CPU Architecture and Pipeline은 단순 하드웨어 지식이 아니라 성능 최적화, 시스템 설계, 보안 취약점 이해에 필수적인 기반 개념이다.

## CPU 내부 구성 요소

CPU는 일반적으로 다음 요소들로 구성된다.

- **명령어 집합 구조, ISA**
  - 소프트웨어가 CPU에게 제공하는 명령어의 규칙이다.
  - 예: x86-64, Arm AArch64, RISC-V 등.
  - ISA는 프로그래머와 컴파일러가 보는 추상적인 CPU 인터페이스이다.

- **레지스터**
  - CPU 내부의 매우 빠른 저장 공간이다.
  - 연산 대상, 주소, 상태값, 함수 호출 정보 등을 저장한다.
  - 일반 목적 레지스터, 프로그램 카운터, 스택 포인터, 상태 레지스터 등이 있다.

- **ALU, Arithmetic Logic Unit**
  - 정수 산술 연산과 논리 연산을 수행한다.
  - 예: 덧셈, 뺄셈, AND, OR, XOR, 비교 연산.

- **FPU, Floating Point Unit**
  - 부동소수점 연산을 담당한다.
  - 과학 계산, 그래픽, 머신러닝, 데이터 분석 등에서 중요하다.

- **제어 장치**
  - 명령어를 해석하고 CPU 내부 신호를 제어한다.
  - 파이프라인 단계 간 데이터 흐름과 실행 순서를 관리한다.

- **캐시**
  - CPU와 메인 메모리 사이의 속도 차이를 줄이기 위한 고속 메모리이다.
  - 일반적으로 L1, L2, L3 캐시 계층을 가진다.
  - CPU 성능은 캐시 적중률에 크게 영향을 받는다.

- **버스와 인터커넥트**
  - CPU 내부 또는 CPU와 메모리, I/O 장치 간 데이터를 이동시키는 통로이다.

## 기본 명령어 실행 흐름

전통적인 단순 RISC 스타일 파이프라인은 설명 목적으로 보통 5단계로 표현된다.

```text
1. IF  : Instruction Fetch
        명령어 메모리 또는 명령어 캐시에서 명령어를 가져온다.

2. ID  : Instruction Decode
        명령어를 해석하고 필요한 레지스터를 읽는다.

3. EX  : Execute
        ALU 연산, 주소 계산, 분기 조건 평가 등을 수행한다.

4. MEM : Memory Access
        load/store 명령어가 데이터 캐시 또는 메모리에 접근한다.

5. WB  : Write Back
        연산 결과를 레지스터에 기록한다.
```

파이프라인이 없는 경우:

```text
시간 →
명령어1: IF ID EX MEM WB
명령어2:                IF ID EX MEM WB
명령어3:                               IF ID EX MEM WB
```

파이프라인이 있는 경우:

```text
시간 →
Cycle 1:  I1 IF
Cycle 2:  I1 ID   I2 IF
Cycle 3:  I1 EX   I2 ID   I3 IF
Cycle 4:  I1 MEM  I2 EX   I3 ID   I4 IF
Cycle 5:  I1 WB   I2 MEM  I3 EX   I4 ID   I5 IF
Cycle 6:          I2 WB   I3 MEM  I4 EX   I5 ID
```

이 구조에서는 파이프라인이 충분히 채워진 후 이상적으로는 매 사이클마다 명령어 하나가 완료될 수 있다. 하지만 실제 CPU에서는 데이터 의존성, 분기, 캐시 미스, 예외 처리, 자원 충돌 때문에 항상 이상적으로 동작하지 않는다.

## 파이프라인 해저드

파이프라인의 성능을 떨어뜨리는 대표적인 문제를 **해저드, hazard**라고 한다.

### 1. 구조적 해저드

동일한 하드웨어 자원을 여러 파이프라인 단계가 동시에 필요로 할 때 발생한다.

예:

```text
IF 단계: 명령어 메모리 접근 필요
MEM 단계: 데이터 메모리 접근 필요
```

명령어와 데이터가 같은 메모리 포트를 공유한다면 충돌이 발생할 수 있다. 이를 줄이기 위해 명령어 캐시와 데이터 캐시를 분리하는 구조가 사용된다. 이를 하버드 구조적 특성이라고 설명하기도 한다.

---

### 2. 데이터 해저드

이전 명령어의 결과가 아직 준비되지 않았는데 다음 명령어가 그 값을 필요로 할 때 발생한다.

예:

```assembly
ADD R1, R2, R3   ; R1 = R2 + R3
SUB R4, R1, R5   ; R4 = R1 - R5
```

두 번째 명령어는 첫 번째 명령어의 결과인 R1이 필요하다. 하지만 ADD의 결과가 WB 단계까지 가기 전에는 레지스터에 기록되지 않았을 수 있다.

해결 방법:

- **스톨, stall**
  - 파이프라인을 잠시 멈춘다.
  - 단순하지만 성능 손실이 있다.

- **포워딩, forwarding 또는 bypassing**
  - 결과가 레지스터에 기록되기 전에 내부 경로를 통해 다음 명령어로 직접 전달한다.

```text
ADD 결과
   │
   ├── 원래 경로: EX → MEM → WB → Register
   │
   └── 포워딩: EX 결과를 다음 명령어 EX 입력으로 직접 전달
```

- **컴파일러 스케줄링**
  - 컴파일러가 의존성이 적은 명령어 순서로 재배치한다.
  - ISA와 CPU 구현에 따라 효과가 달라진다.

---

### 3. 제어 해저드

분기 명령어 때문에 다음에 실행할 명령어 주소가 확정되지 않을 때 발생한다.

예:

```c
if (x > 0) {
    a = b + c;
} else {
    a = b - c;
}
```

CPU는 `x > 0` 조건이 확정되기 전까지 다음에 어느 경로의 명령어를 가져와야 할지 모를 수 있다. 이를 해결하기 위해 현대 CPU는 **분기 예측, branch prediction**을 사용한다.

```text
분기 명령어 도달
     │
     ├─ CPU가 taken 또는 not taken 예측
     │
     ├─ 예측 경로의 명령어를 미리 가져와 실행
     │
     └─ 예측 실패 시 잘못 가져온 명령어를 폐기하고 올바른 경로로 재시작
```

분기 예측이 실패하면 파이프라인을 비우거나 되돌리는 비용이 발생한다. 파이프라인이 깊을수록 일반적으로 예측 실패 비용이 커질 수 있다.

## 슈퍼스칼라와 비순차 실행

현대 고성능 CPU는 단순히 5단계 파이프라인만 사용하는 것이 아니라 여러 명령어를 동시에 발행하고 실행하는 구조를 사용한다.

### 슈퍼스칼라, Superscalar

한 사이클에 여러 명령어를 발행하고 여러 실행 유닛에서 동시에 처리하는 구조이다.

```text
Cycle N:
  Decode:  I1, I2, I3, I4
  Execute:
    ALU0 ← I1
    ALU1 ← I2
    Load/Store Unit ← I3
    Branch Unit ← I4
```

이를 통해 명령어 수준 병렬성, ILP를 활용한다.

---

### 비순차 실행, Out-of-Order Execution

프로그램 순서대로 명령어를 가져오더라도, 의존성이 없는 명령어는 먼저 실행할 수 있다.

예:

```assembly
LOAD R1, [A]      ; 메모리 접근으로 오래 걸릴 수 있음
ADD  R2, R3, R4   ; LOAD 결과와 무관
SUB  R5, R6, R7   ; LOAD 결과와 무관
MUL  R8, R1, R9   ; LOAD 결과 필요
```

비순차 실행 CPU는 LOAD가 지연되는 동안 ADD, SUB를 먼저 실행할 수 있다. 단, 최종적으로 프로그램이 관찰하는 결과는 원래 명령어 순서와 일치해야 한다. 이를 위해 reorder buffer 같은 구조가 사용된다.

---

## 명령어 실행의 고수준 흐름

```text
프로그램 코드
   │
   ▼
컴파일러가 ISA 명령어로 변환
   │
   ▼
CPU 명령어 캐시에서 fetch
   │
   ▼
decode 및 micro-operation 변환
   │
   ▼
레지스터 renaming 및 스케줄링
   │
   ▼
실행 유닛에서 연산
   │
   ├─ ALU
   ├─ FPU
   ├─ SIMD unit
   ├─ Load/Store unit
   └─ Branch unit
   │
   ▼
결과 write-back
   │
   ▼
commit 또는 retire
```

일부 복잡한 ISA에서는 명령어가 내부적으로 더 작은 마이크로 연산, micro-ops로 변환되어 실행될 수 있다. x86 계열 CPU는 일반적으로 복잡한 명령어를 내부 micro-op으로 변환해 실행하는 구조를 사용한다.

## 실제 시스템 연결

## Linux에서 CPU 아키텍처와 파이프라인의 연결

Linux는 CPU 아키텍처별로 다른 커널 코드를 포함한다. 예를 들어 x86-64, Arm64, RISC-V 등은 예외 처리, 시스템 콜 진입, 인터럽트 처리, 컨텍스트 스위칭, 메모리 관리 방식에서 아키텍처별 구현이 존재한다.

확인 명령 예:

```bash
uname -m
```

예상 출력 예:

```text
x86_64
aarch64
riscv64
```

CPU 정보 확인:

```bash
lscpu
```

`lscpu`는 CPU 아키텍처, 코어 수, 스레드 수, 캐시 정보, 가상화 지원 기능 등을 보여준다. 출력 항목은 배포판, 커널, 하드웨어에 따라 달라질 수 있다.

## Linux 성능 분석과 파이프라인

CPU 파이프라인 효율은 애플리케이션 성능에 직접 연결된다. Linux에서는 `perf`를 사용해 CPU 이벤트를 측정할 수 있다.

예:

```bash
perf stat ./my_program
```

측정 가능한 대표 지표:

- cycles
- instructions
- branches
- branch-misses
- cache-references
- cache-misses

예를 들어 `branch-misses`가 많다면 분기 예측 실패로 인해 파이프라인 flush 비용이 증가했을 가능성이 있다. `cache-misses`가 많다면 CPU가 메모리 데이터를 기다리느라 파이프라인이 충분히 활용되지 못할 수 있다.

IPC, Instructions Per Cycle도 중요한 지표다.

```text
IPC = 실행된 명령어 수 / CPU cycle 수
```

IPC가 높다는 것은 같은 cycle 동안 더 많은 명령어를 처리했다는 의미다. 다만 IPC는 CPU 구조, 워크로드, 컴파일러 옵션, 메모리 접근 패턴에 따라 달라진다.

## Nginx와 CPU 파이프라인

Nginx 같은 고성능 웹 서버는 이벤트 기반 구조를 사용해 많은 연결을 처리한다. CPU 관점에서 보면 다음 요소가 성능에 영향을 줄 수 있다.

- TLS 암호화 연산
- HTTP 요청 파싱
- 커널 네트워크 스택 처리
- 메모리 복사
- 캐시 적중률
- 분기 예측 효율
- 시스템 콜 비용

예를 들어 HTTPS 트래픽이 많은 경우 CPU는 대량의 암호화 연산을 수행한다. 이때 AES-NI 같은 CPU 명령어 확장이 지원되면 암호화 성능이 크게 향상될 수 있다. AES-NI는 x86 계열에서 AES 암호화를 가속하기 위한 명령어 집합 확장이다.

확인 예:

```bash
grep -m1 aes /proc/cpuinfo
```

출력이 있다면 해당 CPU가 AES 관련 플래그를 노출하고 있음을 의미한다.

## 데이터베이스와 CPU 파이프라인

데이터베이스 시스템은 CPU 파이프라인과 캐시의 영향을 크게 받는다.

예:

- 인덱스 탐색은 포인터 추적이 많아 캐시 미스가 발생할 수 있다.
- 정렬, 해시 조인, 압축, 벡터화 실행은 CPU 연산량이 많다.
- 분기문이 많은 조건 평가 코드는 분기 예측 실패를 일으킬 수 있다.
- 컬럼 지향 DB는 연속적인 메모리 접근과 SIMD 활용에 유리할 수 있다.

따라서 데이터베이스 성능 최적화에서는 디스크 I/O뿐 아니라 CPU 캐시 친화성, 분기 예측, SIMD 활용도 중요하다.

## AWS와 실제 CPU 선택

AWS EC2 인스턴스는 다양한 CPU 아키텍처와 세대를 제공한다. 예를 들어 AWS Graviton 계열은 Arm 기반 프로세서이고, 다른 EC2 인스턴스는 Intel 또는 AMD x86-64 프로세서를 사용하는 경우가 많다. 워크로드에 따라 x86-64와 Arm64의 성능, 비용, 소프트웨어 호환성이 달라질 수 있다.

실제 선택 시 고려할 점:

- 애플리케이션이 해당 아키텍처용 바이너리를 지원하는가?
- Docker 이미지가 multi-arch를 지원하는가?
- JIT 런타임이 해당 CPU에서 잘 최적화되는가?
- 암호화, 압축, 머신러닝 등 특정 명령어 확장을 활용하는가?
- 라이선스 또는 상용 소프트웨어가 해당 아키텍처를 지원하는가?

## Docker와 CPU 아키텍처

Docker 이미지는 CPU 아키텍처에 의존한다. x86-64용으로 빌드된 바이너리는 일반적으로 Arm64 환경에서 그대로 실행되지 않는다. 이를 해결하기 위해 multi-architecture image를 사용할 수 있다.

예:

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:latest .
```

이미지 매니페스트는 여러 아키텍처용 이미지를 가리킬 수 있고, 런타임은 현재 플랫폼에 맞는 이미지를 가져온다.

확인:

```bash
docker image inspect myapp:latest
```

또는 원격 이미지의 아키텍처 확인:

```bash
docker buildx imagetools inspect nginx:latest
```

CPU 파이프라인 자체는 컨테이너가 직접 제어하지 못하지만, 컨테이너 내부 애플리케이션의 바이너리, 컴파일 옵션, 런타임 최적화는 실제 CPU 성능에 영향을 준다.

## Kubernetes와 CPU 리소스

Kubernetes에서 CPU는 요청량과 제한량으로 관리된다.

```yaml
resources:
  requests:
    cpu: "500m"
  limits:
    cpu: "1"
```

- `500m`은 CPU 0.5개에 해당하는 요청량이다.
- CPU limit이 설정되면 컨테이너가 일정 수준 이상 CPU를 사용하려 할 때 스로틀링될 수 있다.
- CPU 스로틀링은 애플리케이션 지연 시간 증가로 이어질 수 있다.

CPU 파이프라인 관점에서는 컨테이너가 실제 코어에서 얼마나 안정적으로 실행되는지가 중요하다. 잦은 스케줄링 이동, CPU contention, 캐시 오염은 성능에 영향을 줄 수 있다. 지연 시간이 중요한 워크로드에서는 CPU pinning, NUMA-aware scheduling, dedicated node pool 같은 전략을 검토한다.

## AWS에서 CPU 아키텍처 선택

AWS에서는 워크로드에 따라 인스턴스 패밀리를 선택한다.

- 범용 워크로드: 웹 서버, API 서버, 마이크로서비스
- 컴퓨팅 최적화: CPU 집약적 배치 작업, 고성능 웹 서버
- 메모리 최적화: 인메모리 DB, 캐시 서버
- 가속 컴퓨팅: GPU, FPGA, 전용 가속기 활용 워크로드

CPU 아키텍처와 파이프라인 관점에서 중요한 점:

- 같은 vCPU 수라도 실제 성능은 CPU 세대, 클럭, 캐시, 메모리 대역폭, 가상화 오버헤드에 따라 다르다.
- Arm64 기반 인스턴스는 소프트웨어 호환성을 확인해야 한다.
- x86-64 전용 바이너리 또는 특정 SIMD 명령어 의존 코드가 있다면 인스턴스 선택에 제약이 생길 수 있다.
- Java, Go, Rust, C/C++ 등 언어별 컴파일 및 런타임 최적화가 아키텍처별로 다를 수 있다.

## GCP와 CPU 플랫폼

GCP Compute Engine도 다양한 CPU 플랫폼을 제공한다. 인스턴스 머신 타입과 리전에 따라 사용할 수 있는 CPU 플랫폼이 다르다. CPU 집약적 워크로드에서는 머신 타입뿐 아니라 실제 CPU 플랫폼, 메모리 대역폭, 캐시 특성, 가상화 환경을 함께 고려해야 한다.

GCP에서 성능 테스트를 할 때는 다음을 확인한다.

```bash
lscpu
cat /proc/cpuinfo
```

그리고 실제 애플리케이션 기준으로 benchmark를 수행해야 한다. CPU 파이프라인 특성은 마이크로벤치마크와 실제 운영 워크로드에서 다르게 나타날 수 있다.

## 서버리스와 CPU

AWS Lambda, Google Cloud Functions 같은 서버리스 환경에서는 사용자가 물리 CPU를 직접 선택하거나 파이프라인 구조를 제어하지 않는다. 그러나 다음 요소는 여전히 영향을 준다.

- 런타임 언어의 CPU 효율
- 콜드 스타트 시 초기화 비용

- 네이티브 바이너리의 아키텍처 호환성

서버리스 함수에서도 CPU 집약적 작업은 비용과 지연 시간에 큰 영향을 줄 수 있다.

## 보안 연결

## CPU 파이프라인과 보안

CPU 파이프라인, 분기 예측, 비순차 실행, 캐시는 성능 향상을 위한 기능이지만 보안 측면에서는 부채널 공격의 기반이 될 수 있다. 특히 현대 CPU의 추측 실행, speculative execution은 분기 결과가 확정되기 전에 예측된 경로의 명령어를 미리 실행한다. 잘못 예측된 명령어의 결과는 architectural state에는 반영되지 않지만, 캐시 상태 같은 microarchitectural state에는 흔적을 남길 수 있다. 공격자는 이 흔적을 시간 측정으로 관찰할 수 있다.

---

## Spectre

Spectre는 분기 예측 및 추측 실행을 악용해 다른 보안 경계의 데이터를 간접적으로 추론할 수 있는 취약점 계열로 알려져 있다. 핵심은 CPU가 잘못된 경로를 추측 실행하는 동안 접근하면 안 되는 데이터가 캐시에 영향을 줄 수 있고, 공격자가 캐시 접근 시간을 측정해 정보를 유출할 수 있다는 점이다.

단순화된 흐름:

```text
1. 공격자가 분기 예측기를 특정 방향으로 학습시킨다.
2. CPU가 잘못된 분기 경로를 추측 실행한다.
3. 추측 실행 중 비밀 데이터에 따라 특정 캐시 라인이 접근된다.
4. 추측 실행 결과는 폐기된다.
5. 그러나 캐시 상태 변화는 남을 수 있다.
6. 공격자가 캐시 접근 시간 차이를 측정해 정보를 추론한다.
```

완화 방법:

- 브라우저, 컴파일러, 운영체제, CPU 마이크로코드 업데이트 적용
- 민감 코드에 speculation barrier 사용
- 커널과 사용자 공간 간 격리 강화
- 고해상도 타이머 제한
- JIT 엔진 보안 강화

---

## Meltdown

Meltdown은 일부 CPU에서 권한 검사가 완료되기 전에 추측 실행이 진행되면서 커널 메모리의 데이터가 부채널로 노출될 수 있었던 취약점으로 알려져 있다. 이 취약점에 대응하기 위해 운영체제는 커널 페이지 테이블 격리, KPTI 같은 완화 기법을 도입했다.

KPTI의 핵심은 사용자 모드 실행 중 커널 주소 공간 매핑을 분리하여, 사용자 프로세스가 커널 메모리를 부채널로 관찰할 가능성을 줄이는 것이다. 다만 KPTI는 시스템 콜이나 인터럽트처럼 사용자 모드와 커널 모드를 자주 전환하는 워크로드에서 오버헤드를 만들 수 있다.

---

## 캐시 부채널 공격

CPU 캐시는 성능 최적화를 위해 사용되지만, 접근 시간 차이가 정보 유출 경로가 될 수 있다.

대표적인 공격 방식:

- **Flush+Reload**
  - 특정 캐시 라인을 flush한 뒤, victim 실행 후 reload 시간을 측정한다.
  - 공유 메모리 페이지가 있는 환경에서 강력할 수 있다.

- **Prime+Probe**
  - 공격자가 캐시 세트를 자신의 데이터로 채운 뒤 victim 실행 후 다시 접근 시간을 측정한다.
  - 공유 메모리가 없어도 가능한 경우가 있다.

보안적으로 중요한 이유는 클라우드 환경에서 여러 테넌트가 물리 자원을 공유할 수 있기 때문이다. 현대 클라우드는 하이퍼바이저 격리, 마이크로코드 업데이트, 스케줄링 정책, 전용 호스트 옵션 등을 통해 위험을 줄인다.

## 컨테이너와 CPU 보안

컨테이너는 프로세스 격리 기술이며, CPU 마이크로아키텍처 자체를 강하게 분리하지 않는다. 같은 호스트에서 실행되는 컨테이너들은 CPU 캐시, 분기 예측기, 메모리 대역폭 같은 하드웨어 자원을 공유할 수 있다. 따라서 컨테이너 보안은 커널 격리뿐 아니라 하드웨어 부채널 가능성까지 고려해야 한다.

모범 사례:

- 호스트 OS와 CPU 마이크로코드 업데이트 유지
- 민감 워크로드는 전용 노드 또는 전용 호스트 사용
- 서로 다른 신뢰 수준의 워크로드를 같은 노드에 혼합하지 않기
- Kubernetes node pool 분리
- seccomp, AppArmor, SELinux 같은 커널 보안 기능 사용
- 불필요한 권한, privileged container 사용 금지

---

## 암호화 구현과 파이프라인

암호화 알고리즘 구현은 CPU 파이프라인과 캐시에 민감하다. 비밀 값에 따라 분기하거나 비밀 값에 따라 메모리 접근 위치가 달라지면 timing side-channel이 발생할 수 있다. 따라서 암호화 라이브러리는 constant-time 구현을 사용하는 것이 중요하다.

모범 사례:

- 직접 암호화 알고리즘을 구현하지 않기
- 검증된 라이브러리 사용
  - 예: OpenSSL, BoringSSL, libsodium 등
- 비밀 값에 따라 분기하지 않는 constant-time 구현 사용
- CPU 명령어 가속 사용 시에도 보안 업데이트 유지
- 취약한 구버전 라이브러리 사용 금지

## 면접 질문

**Q1. CPU 파이프라인이란 무엇이며 왜 사용하는가?**  
> 핵심 답변: 명령어 실행 과정을 여러 단계로 나누고 서로 다른 명령어가 각 단계를 동시에 사용하게 하는 구조이다. 개별 명령어의 지연 시간이 반드시 줄어드는 것은 아니지만, 파이프라인이 채워진 후 전체 처리량을 높일 수 있다. 대표 단계는 IF, ID, EX, MEM, WB이다.

**Q2. 파이프라인 해저드의 종류와 해결 방법을 설명하라.**  
> 핵심 답변: 구조적 해저드는 하드웨어 자원 충돌이며 자원 분리나 추가로 해결한다. 데이터 해저드는 이전 명령어 결과가 필요한 경우이며 스톨, 포워딩, 컴파일러 스케줄링으로 완화한다. 제어 해저드는 분기 때문에 다음 명령어 주소가 불확실한 경우이며 분기 예측과 추측 실행으로 완화한다.

**Q3. 분기 예측 실패가 성능에 미치는 영향은 무엇인가?**  
> 핵심 답변: CPU가 잘못된 경로의 명령어를 가져와 실행했다면 해당 작업을 폐기하고 올바른 경로로 파이프라인을 다시 채워야 한다. 이 과정에서 cycle 낭비가 발생한다. 파이프라인이 깊거나 비순차 실행 폭이 넓은 CPU에서는 예측 실패 비용이 클 수 있다.

**Q4. Out-of-Order Execution은 무엇이며 왜 필요한가?**  
> 핵심 답변: 프로그램 순서대로 명령어를 가져오더라도 의존성이 없는 명령어를 먼저 실행하는 기법이다. 메모리 접근 지연이나 특정 연산 지연 동안 독립적인 명령어를 실행해 실행 유닛 활용률과 IPC를 높인다. 단, 최종 결과는 프로그램 순서와 일치해야 하므로 reorder buffer 같은 구조가 필요하다.

**Q5. CPU 파이프라인과 보안 취약점은 어떤 관계가 있는가?**  
> 핵심 답변: 분기 예측, 추측 실행, 캐시 같은 성능 최적화 기능은 microarchitectural state에 흔적을 남길 수 있다. Spectre와 Meltdown 같은 취약점은 이러한 흔적을 timing side-channel로 관찰해 민감 정보를 추론하는 방식과 관련이 있다. 완화에는 OS 패치, 마이크로코드 업데이트, speculation barrier, KPTI, constant-time 구현 등이 있다.

## 관련 개념

- [[Instruction Set Architecture]] - CPU가 실행할 수 있는 명령어와 레지스터, 메모리 모델을 정의하는 소프트웨어와 하드웨어의 경계이다.
- [[CPU Pipeline]] - 명령어 실행 단계를 나누어 처리량을 높이는 핵심 구조이다.
- [[Pipeline Hazard]] - 파이프라인 성능을 저하시키는 구조적, 데이터, 제어 충돌을 설명하는 개념이다.
- [[Branch Prediction]] - 분기 결과를 미리 예측해 파이프라인 공백을 줄이는 기법이다.
- [[Speculative Execution]] - 예측된 경로의 명령어를 미리 실행해 성능을 높이는 방식이며 보안 이슈와도 관련된다.
- [[Out-of-Order Execution]] - 의존성이 없는 명령어를 먼저 실행하여 CPU 실행 유닛 활용률을 높이는 기법이다.
- [[Cache Memory]] - CPU와 메인 메모리 사이의 속도 차이를 줄이며 파이프라인 효율에 큰 영향을 준다.
- [[Memory Hierarchy]] - 레지스터, 캐시, 메모리, 스토리지로 이어지는 계층 구조이며 CPU 성능 분석의 핵심이다.
- [[Superscalar Architecture]] - 한 사이클에 여러 명령어를 발행하고 실행하는 CPU 구조이다.
- [[SIMD]] - 하나의 명령어로 여러 데이터에 같은 연산을 적용하여 데이터 병렬성을 활용한다.
- [[Context Switch]] - 운영체제가 실행 중인 프로세스나 스레드를 전환하는 과정이며 CPU 레지스터와 캐시 상태에 영향을 준다.
- [[Spectre]] - 추측 실행과 캐시 부채널을 악용할 수 있는 CPU 취약점 계열이다.
- [[Meltdown]] - 일부 CPU의 추측 실행과 권한 검사 동작과 관련된 부채널 취약점으로 알려져 있다.
- [[KPTI]] - 커널 페이지 테이블 격리를 통해 Meltdown류 취약점 완화에 사용된 운영체제 기법이다.
- [[perf]] - Linux에서 CPU cycle, instruction, cache miss, branch miss 등을 측정하는 성능 분석 도구이다.
