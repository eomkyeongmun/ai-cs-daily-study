# 선형 자료구조 - 배열 vs 연결 리스트, 스택, 큐(Queue, Deque)

## 핵심 개념

선형 자료구조는 데이터가 논리적으로 “앞과 뒤”의 순서를 가지며 일렬로 배치되는 자료구조를 말한다. 대표적으로 배열(Array), 연결 리스트(Linked List), 스택(Stack), 큐(Queue), 덱(Deque)이 있다. 이들은 데이터를 저장하고 탐색, 삽입, 삭제하는 방식이 서로 다르기 때문에 프로그램의 성능과 메모리 사용량에 직접적인 영향을 준다.

배열은 같은 타입의 데이터를 연속된 메모리 공간에 저장하는 구조다. 인덱스를 통해 임의 접근(Random Access)이 가능하므로 특정 위치의 원소를 `O(1)`에 조회할 수 있다. 하지만 중간 삽입이나 삭제 시 뒤쪽 원소들을 이동해야 하므로 일반적으로 `O(n)` 시간이 걸린다. 반면 연결 리스트는 각 노드가 데이터와 다음 노드의 주소를 함께 가지는 구조다. 메모리상 연속될 필요가 없고, 특정 노드를 알고 있다면 삽입과 삭제가 비교적 효율적이다. 다만 인덱스 기반 임의 접근이 불가능하여 원하는 위치까지 순차적으로 이동해야 하므로 탐색은 `O(n)`이다.

스택은 후입선출(LIFO, Last-In First-Out) 구조로, 가장 나중에 들어간 데이터가 가장 먼저 나온다. 함수 호출 관리, 되돌리기 기능, 괄호 검사, DFS 등에 사용된다. 큐는 선입선출(FIFO, First-In First-Out) 구조로, 먼저 들어간 데이터가 먼저 나온다. 작업 대기열, 메시지 처리, BFS, 운영체제 스케줄링 등에 활용된다. 덱(Deque, Double-Ended Queue)은 양쪽 끝에서 삽입과 삭제가 모두 가능한 큐의 확장 형태로, 슬라이딩 윈도우, 캐시, 작업 스케줄링 등에서 유용하다.

이 주제가 중요한 이유는 단순히 자료를 저장하는 방법을 넘어서, 실제 시스템의 성능 병목, 메모리 효율, 응답 지연, 동시성 처리 방식에 큰 영향을 주기 때문이다. 예를 들어 대량의 로그를 순차적으로 처리할 때는 큐가 적합하고, 빠른 인덱스 조회가 필요하면 배열이 유리하며, 잦은 삽입과 삭제가 필요한 구조에서는 연결 리스트나 덱이 더 적합할 수 있다.

## 내부 동작 원리

## 1. 배열(Array)

배열은 메모리상 연속된 공간에 원소를 배치한다. 각 원소의 크기가 동일하다고 가정하면, 인덱스 `i`의 주소는 다음과 같이 계산할 수 있다.

```text
주소 = 시작 주소 + (인덱스 × 원소 크기)
```

예시:

```text
index:   0    1    2    3    4
array: [10] [20] [30] [40] [50]
addr: 1000 1004 1008 1012 1016
```

이 구조 덕분에 `array[3]` 같은 접근은 바로 주소를 계산할 수 있어 `O(1)`이다. 그러나 중간에 값을 삽입하려면 뒤 원소들을 한 칸씩 밀어야 한다.

```text
삽입 전:
[10] [20] [30] [40] [50]

index 2에 25 삽입:
[10] [20] [25] [30] [40] [50]
             ↑ 뒤 원소 이동 필요
```

삭제도 마찬가지로 빈 공간을 메우기 위해 뒤 원소를 앞으로 이동해야 한다.

### 배열의 주요 시간 복잡도

| 연산 | 시간 복잡도 |
|---|---|
| 인덱스 접근 | `O(1)` |
| 탐색 | `O(n)` |
| 끝에 삽입 | 정적 배열은 공간이 있을 때 `O(1)`, 동적 배열은 보통 amortized `O(1)` |
| 중간 삽입 | `O(n)` |
| 중간 삭제 | `O(n)` |

동적 배열은 내부 용량이 부족해지면 더 큰 배열을 새로 만들고 기존 데이터를 복사한다. 이 재할당 순간에는 `O(n)`이 걸리지만, 여러 번의 삽입을 평균적으로 보면 끝 삽입은 amortized `O(1)`로 설명된다.

---

## 2. 연결 리스트(Linked List)

연결 리스트는 노드(Node) 단위로 데이터를 저장한다. 각 노드는 데이터와 다음 노드를 가리키는 참조 또는 포인터를 가진다.

```text
[10 | next] -> [20 | next] -> [30 | next] -> null
```

단일 연결 리스트(Singly Linked List)는 다음 노드만 알 수 있다. 이중 연결 리스트(Doubly Linked List)는 이전 노드와 다음 노드를 모두 가진다.

```text
null <- [prev | 10 | next] <-> [prev | 20 | next] <-> [prev | 30 | next] -> null
```

연결 리스트의 장점은 메모리상 연속 공간이 필요 없고, 노드 연결만 바꾸면 삽입과 삭제가 가능하다는 점이다.

예를 들어 `20` 뒤에 `25`를 삽입하는 경우:

```text
삽입 전:
[10] -> [20] -> [30]

삽입 후:
[10] -> [20] -> [25] -> [30]
```

포인터 변경 과정:

```text
newNode.next = node20.next
node20.next = newNode
```

하지만 특정 인덱스의 원소를 찾으려면 헤드부터 순차적으로 따라가야 한다.

```text
head -> node0 -> node1 -> node2 -> node3
```

따라서 임의 접근은 배열보다 느리다.

### 연결 리스트의 주요 시간 복잡도

| 연산 | 시간 복잡도 |
|---|---|
| 첫 노드 접근 | `O(1)` |
| 특정 값 탐색 | `O(n)` |
| 특정 위치 탐색 | `O(n)` |
| 알고 있는 노드 뒤 삽입 | `O(1)` |
| 알고 있는 노드 삭제 | 단일 연결 리스트는 이전 노드 필요, 이중 연결 리스트는 보통 `O(1)` |
| 맨 앞 삽입 | `O(1)` |

## 3. 스택(Stack)

스택은 한쪽 끝에서만 삽입과 삭제가 일어나는 구조다. 삽입 연산을 `push`, 삭제 연산을 `pop`, 맨 위 값을 확인하는 연산을 `peek` 또는 `top`이라고 한다.

```text
push(10)
push(20)
push(30)

top
 ↓
[30]
[20]
[10]
```

`pop()`을 하면 가장 위의 `30`이 먼저 제거된다.

```text
pop() -> 30

top
 ↓
[20]
[10]
```

스택은 배열로도 구현할 수 있고 연결 리스트로도 구현할 수 있다.

배열 기반 스택:

```text
array: [10] [20] [30] [  ] [  ]
top index = 2
```

연결 리스트 기반 스택:

```text
top -> [30] -> [20] -> [10] -> null
```

일반적인 스택 연산의 시간 복잡도는 다음과 같다.

| 연산 | 시간 복잡도 |
|---|---|
| push | `O(1)` |
| pop | `O(1)` |
| peek/top | `O(1)` |
| search | `O(n)` |

---

## 4. 큐(Queue)

큐는 먼저 들어온 데이터가 먼저 나가는 FIFO 구조다. 삽입 연산은 `enqueue`, 삭제 연산은 `dequeue`라고 한다.

```text
front                         rear
 ↓                             ↓
[10] -> [20] -> [30] -> [40]
```

`dequeue()`를 수행하면 `front`에 있는 `10`이 제거된다.

```text
front                  rear
 ↓                      ↓
[20] -> [30] -> [40]
```

배열로 큐를 구현할 때 단순히 앞 원소를 제거하고 나머지를 앞으로 당기면 매번 `O(n)`이 된다. 이를 피하기 위해 보통 `front`와 `rear` 인덱스를 사용한다.

```text
index:  0    1    2    3    4
data:  [ ]  [20] [30] [40] [ ]
       front      rear
```

하지만 배열 끝까지 사용한 뒤 앞쪽 빈 공간을 재사용하려면 원형 큐(Circular Queue)를 사용한다.

```text
원형 큐 개념도:

        [0]
     [4]   [1]
     [3]   [2]

rear와 front가 배열 끝을 넘으면 다시 0번 인덱스로 이동
```

일반적인 큐 연산의 시간 복잡도는 다음과 같다.

| 연산 | 시간 복잡도 |
|---|---|
| enqueue | `O(1)` |
| dequeue | `O(1)` |
| front 확인 | `O(1)` |
| search | `O(n)` |

---

## 5. 덱(Deque)

덱은 Double-Ended Queue의 약자로, 양쪽 끝에서 삽입과 삭제가 모두 가능하다.

```text
front                         rear
 ↓                             ↓
[10] <-> [20] <-> [30] <-> [40]
```

지원 연산:

```text
push_front()
push_back()
pop_front()
pop_back()
```

예시:

```text
초기:
[20] [30]

push_front(10):
[10] [20] [30]

push_back(40):
[10] [20] [30] [40]

pop_front() -> 10
[20] [30] [40]

pop_back() -> 40
[20] [30]
```

덱은 이중 연결 리스트 또는 원형 배열 기반으로 구현할 수 있다. 양쪽 끝에서 빠르게 삽입과 삭제해야 하는 경우 유용하다.

| 연산 | 시간 복잡도 |
|---|---|
| push_front | `O(1)` |
| push_back | `O(1)` |
| pop_front | `O(1)` |
| pop_back | `O(1)` |
| search | `O(n)` |

## 실제 시스템 연결

## 1. Linux 커널과 연결 리스트

Linux 커널은 다양한 내부 자료구조에서 연결 리스트 개념을 사용한다. 대표적으로 커널 내부에는 `list_head`라는 이중 연결 리스트 기반 구조가 존재한다. 프로세스, 장치, 파일 시스템 캐시 등 다양한 커널 객체를 리스트로 연결해 관리하는 데 활용된다.

연결 리스트가 커널에서 유용한 이유는 다음과 같다.

- 객체의 개수가 실행 중 동적으로 변할 수 있다.
- 중간 삽입과 삭제가 자주 발생한다.
- 메모리상 연속 공간을 요구하지 않는다.
- 특정 객체를 리스트에서 빠르게 제거할 수 있다.

개념적으로는 다음과 같은 구조다.

```text
task A <-> task B <-> task C <-> task D
```

프로세스나 커널 객체가 생성되면 리스트에 추가되고, 종료되거나 해제되면 리스트에서 제거된다.

---

## 2. 함수 호출 스택

대부분의 실행 환경에서 함수 호출은 스택 구조로 관리된다. 함수가 호출되면 해당 함수의 지역 변수, 복귀 주소, 이전 프레임 정보 등이 스택 프레임(Stack Frame) 형태로 쌓인다. 함수가 종료되면 가장 최근에 호출된 함수의 스택 프레임부터 제거된다.

예시:

```text
main() 호출
 └─ foo() 호출
     └─ bar() 호출
```

스택 상태:

```text
top
 ↓
[bar frame]
[foo frame]
[main frame]
```

`bar()`가 종료되면 `bar frame`이 먼저 제거된다. 이는 LIFO 구조와 정확히 일치한다.

---

## 3. Nginx와 이벤트 큐

Nginx는 이벤트 기반 아키텍처를 사용한다. 네트워크 연결, 읽기 가능 이벤트, 쓰기 가능 이벤트 등을 이벤트 루프에서 처리한다. 내부 구현은 단순 큐 하나로만 설명할 수는 없지만, 이벤트를 대기열에 넣고 순차적으로 처리한다는 점에서 큐 개념과 연결된다.

```text
[client event 1] -> [client event 2] -> [timer event] -> 처리
```

이벤트 기반 서버에서 큐는 요청을 순서대로 관리하고, 작업이 몰릴 때 지연을 제어하는 핵심 개념이다.

---

## 4. 운영체제 스케줄링과 큐

운영체제는 실행 가능한 프로세스나 스레드를 관리하기 위해 실행 큐(run queue) 개념을 사용한다. 준비 상태의 작업들은 큐 형태로 관리되며, 스케줄러는 정책에 따라 다음 실행 대상을 선택한다.

단순 FIFO 스케줄링은 큐 개념을 직접적으로 사용한다. 실제 운영체제 스케줄러는 우선순위, 시간 할당량, CPU 코어별 큐 등 더 복잡한 구조를 사용하지만, 기본적으로 “대기 중인 작업을 모아두는 선형 구조”라는 큐 개념이 중요하다.

---

## 5. 메시지 브로커와 큐

AWS SQS, Google Cloud Pub/Sub, Apache Kafka, RabbitMQ 같은 메시징 시스템은 큐 또는 로그 기반 메시지 전달 개념을 제공한다. 생산자(Producer)가 메시지를 넣고, 소비자(Consumer)가 메시지를 가져가 처리한다.

```text
Producer -> [Message Queue] -> Consumer
```

큐의 목적은 다음과 같다.

- 서비스 간 결합도 감소
- 트래픽 급증 완충
- 비동기 처리
- 재시도와 장애 격리
- 소비자 처리 속도 조절

단, Kafka는 전통적인 큐라기보다 파티션된 append-only 로그에 가까운 구조이며, 소비자 그룹을 통해 큐처럼 동작할 수 있다.

## 클라우드 연결

## 1. Docker와 큐 개념

Docker 컨테이너 환경에서는 애플리케이션이 직접 큐 자료구조를 사용하기도 하고, 외부 메시지 큐 서비스와 연결되기도 한다. 예를 들어 웹 컨테이너가 요청을 바로 처리하지 않고 Redis, RabbitMQ, AWS SQS 같은 큐에 작업을 넣으면, 별도의 worker 컨테이너가 이를 비동기적으로 처리할 수 있다.

```text
[Web Container] -> [Queue] -> [Worker Container]
```

이 구조는 다음 장점이 있다.

- 요청 처리 지연 감소
- 작업 재시도 가능
- worker 수평 확장 가능
- 장애 격리

예를 들어 이미지 리사이징, 이메일 발송, 로그 처리 같은 작업은 큐 기반 비동기 처리가 자주 사용된다.

---

## 2. Kubernetes와 작업 큐

Kubernetes 환경에서는 컨트롤러가 클러스터 상태를 감시하고 원하는 상태와 실제 상태를 맞추기 위해 작업 큐(workqueue) 개념을 사용한다. 컨트롤러는 리소스 변경 이벤트를 감지하고, 처리할 객체를 큐에 넣은 뒤 reconcile 루프에서 하나씩 처리한다.

```text
API Server Event -> Controller Queue -> Reconcile
```

예시:

```text
Pod 생성 이벤트
  -> 컨트롤러 큐에 추가
  -> 컨트롤러가 처리
  -> 필요한 리소스 생성 또는 상태 갱신
```

이는 큐가 클라우드 네이티브 시스템에서 이벤트 처리, 재시도, 상태 동기화의 핵심 패턴으로 사용된다는 것을 보여준다.

---

## 3. AWS SQS와 Queue

AWS SQS(Simple Queue Service)는 관리형 메시지 큐 서비스다. 애플리케이션은 메시지를 큐에 보내고, 소비자는 큐에서 메시지를 가져가 처리한다. SQS는 표준 큐와 FIFO 큐를 제공한다. 표준 큐는 높은 처리량을 목표로 하고, FIFO 큐는 메시지 순서와 중복 처리 제어를 더 강하게 제공하는 유형이다.

```text
Producer -> AWS SQS -> Consumer
```

SQS 같은 관리형 큐 서비스는 직접 큐 시스템을 운영하지 않아도 되게 해주며, 분산 시스템에서 비동기 처리와 장애 격리에 유용하다.

---

## 4. AWS Lambda와 큐

AWS Lambda는 SQS, Kinesis, DynamoDB Streams 등 이벤트 소스와 연결될 수 있다. SQS와 연결하면 큐에 메시지가 쌓이고 Lambda가 메시지를 가져와 처리한다.

```text
SQS Queue -> Lambda Function -> Database
```

이 구조에서 큐는 트래픽 급증을 흡수하는 버퍼 역할을 한다. Lambda가 처리할 수 있는 속도보다 메시지가 빠르게 들어오면 큐에 메시지가 쌓이고, 처리량이 회복되면 순차적으로 소비된다.

---

## 5. 클라우드 로드밸런싱과 대기열

클라우드 환경에서 로드밸런서는 들어오는 요청을 여러 인스턴스나 파드로 분산한다. 로드밸런서 자체가 애플리케이션 레벨의 큐 자료구조를 제공하는 것은 아니지만, 요청 처리 과정에서는 네트워크 버퍼, 커넥션 큐, 백로그 큐 같은 대기 구조가 관여한다.

예를 들어 서버가 동시에 처리할 수 있는 연결 수보다 요청이 많이 들어오면 일부 연결은 커널의 대기 큐에 머물거나, 제한을 넘으면 거부될 수 있다. 따라서 큐의 크기와 처리 속도는 클라우드 서비스의 지연 시간과 장애 전파에 영향을 준다.

## 보안 연결

## 1. 배열과 버퍼 오버플로우

배열은 연속된 메모리 공간을 사용하기 때문에 경계 검사를 제대로 하지 않으면 버퍼 오버플로우가 발생할 수 있다. C/C++처럼 메모리 접근을 직접 제어하는 언어에서는 배열 범위를 벗어난 쓰기가 인접 메모리를 덮어쓸 수 있다.

```c
char buf[8];
strcpy(buf, user_input); // user_input 길이가 8 이상이면 위험
```

위와 같은 코드는 입력 길이를 검증하지 않으면 스택 메모리나 다른 데이터를 손상시킬 수 있다. 심각한 경우 제어 흐름 탈취로 이어질 수 있다.

모범 사례:

- 배열 접근 전 인덱스 검증
- 안전한 문자열 처리 함수 사용
- 입력 길이 제한
- ASLR, stack canary, NX bit 등 방어 기법 활용
- 가능하면 경계 검사를 제공하는 언어 또는 라이브러리 사용

---

## 2. 연결 리스트와 Use-After-Free

연결 리스트는 노드의 생성과 삭제가 빈번하다. 노드를 해제한 뒤에도 다른 포인터가 해당 노드를 참조하면 Use-After-Free 취약점이 발생할 수 있다.

```text
A -> B -> C

B 삭제 후:
A -> C

하지만 어떤 포인터가 여전히 B를 참조하면 위험
```

위험한 상황:

- 삭제된 노드 포인터 재사용
- 이중 해제(double free)
- 리스트 연결 해제 순서 오류
- 동시성 환경에서 lock 없이 리스트 수정

모범 사례:

- 노드 삭제 시 모든 참조 정리
- 해제 후 포인터를 `NULL`로 설정
- 동시 접근 시 락 또는 lock-free 알고리즘의 안전한 메모리 회수 기법 사용
- 반복 중 삭제 시 안전한 순회 패턴 사용

---

## 3. 스택과 스택 오버플로우

스택은 함수 호출과 지역 변수 저장에 사용된다. 재귀 호출이 너무 깊거나 큰 지역 배열을 할당하면 스택 오버플로우가 발생할 수 있다.

```text
recursive()
 -> recursive()
   -> recursive()
     -> ...
```

위와 같은 무한 또는 과도한 재귀는 스택 프레임을 계속 쌓아 결국 스택 공간을 초과할 수 있다.

모범 사례:

- 재귀 깊이 제한
- 반복문으로 변환 가능한 경우 반복문 사용
- 큰 데이터는 스택이 아닌 힙에 할당
- 입력 기반 재귀 알고리즘은 최악의 깊이 분석
- 웹 요청 처리 시 사용자 입력으로 재귀 깊이가 결정되지 않도록 제한

---

## 4. 큐와 서비스 거부 공격

큐는 트래픽을 완충하는 데 유용하지만, 무제한 큐는 서비스 거부(DoS) 위험을 키울 수 있다. 공격자가 대량의 요청이나 메시지를 큐에 넣으면 메모리, 디스크, CPU가 고갈될 수 있다.

```text
Attacker -> 많은 요청 -> Queue 폭증 -> Worker 처리 지연 -> 장애
```

위험 요소:

- 큐 길이 제한 없음
- 메시지 크기 제한 없음
- 소비자 처리 속도 부족
- 재시도 폭주
- Dead Letter Queue 미구성

모범 사례:

- 큐 최대 길이 설정
- 메시지 크기 제한
- 생산자 인증과 권한 검증
- rate limiting 적용
- backpressure 설계
- Dead Letter Queue 구성
- 재시도 횟수와 지수 백오프 설정

---

## 5. 덱과 캐시 보안

덱은 LRU 캐시 구현에 사용될 수 있다. LRU 캐시는 최근 사용된 데이터를 앞쪽으로 이동시키고 오래된 데이터를 뒤쪽에서 제거하는 방식으로 구현된다.

```text
front: 최근 사용
[Page C] [Page A] [Page B]
                  rear: 오래됨
```

캐시는 성능에 유리하지만 민감 데이터가 캐시에 오래 남으면 보안 위험이 될 수 있다.

모범 사례:

- 민감 정보 캐싱 최소화
- 캐시 만료 시간 설정
- 사용자별 캐시 키 분리
- 권한 변경 시 캐시 무효화
- 로그, 큐, 캐시에 토큰이나 비밀번호 저장 금지
- 멀티테넌트 환경에서 캐시 격리

## 면접 질문

**Q1. 배열과 연결 리스트의 차이를 설명하세요.**  
> 핵심 답변: 배열은 연속된 메모리에 데이터를 저장하며 인덱스 기반 `O(1)` 접근이 가능하다. 대신 중간 삽입과 삭제는 원소 이동 때문에 `O(n)`이다. 연결 리스트는 노드가 포인터로 연결되어 메모리상 연속될 필요가 없고, 특정 노드를 알고 있으면 삽입과 삭제가 빠르다. 하지만 임의 접근이 불가능해 탐색은 `O(n)`이다.

**Q2. 동적 배열에서 append가 왜 amortized O(1)인가요?**  
> 핵심 답변: 동적 배열은 용량이 부족할 때 더 큰 배열을 할당하고 기존 원소를 복사하므로 그 순간은 `O(n)`이다. 하지만 매번 재할당이 발생하지 않고, 여러 번의 append 비용을 평균 내면 원소 하나당 평균 비용이 상수에 가까워져 amortized `O(1)`로 본다.

**Q3. 스택은 어떤 상황에서 사용되나요?**  
> 핵심 답변: 스택은 LIFO 구조가 필요한 상황에서 사용된다. 대표적으로 함수 호출 스택, 괄호 유효성 검사, DFS, undo 기능, 후위 표기식 계산, 백트래킹 등에 사용된다. 가장 최근 상태를 먼저 되돌려야 할 때 적합하다.

**Q4. 큐와 스택의 차이는 무엇인가요?**  
> 핵심 답변: 스택은 후입선출(LIFO) 구조로 가장 나중에 들어간 데이터가 먼저 나온다. 큐는 선입선출(FIFO) 구조로 가장 먼저 들어간 데이터가 먼저 나온다. 스택은 함수 호출, DFS에 적합하고 큐는 작업 대기열, BFS, 메시지 처리, 스케줄링 등에 적합하다.

**Q5. 덱은 큐와 무엇이 다르며 어디에 사용되나요?**  
> 핵심 답변: 큐는 일반적으로 한쪽 끝에서 삽입하고 반대쪽 끝에서 삭제하지만, 덱은 양쪽 끝에서 삽입과 삭제가 모두 가능하다. 슬라이딩 윈도우 최댓값, LRU 캐시, 양방향 작업 큐, 팰린드롬 검사 등에 사용할 수 있다.

## 관련 개념

- [[동적 배열]] - 배열의 크기 제한을 완화하고 append를 효율적으로 처리하는 구조와 관련된다.
- [[단일 연결 리스트]] - 각 노드가 다음 노드만 가리키는 가장 기본적인 연결 리스트 구조다.
- [[이중 연결 리스트]] - 이전 노드와 다음 노드를 모두 참조하여 양방향 순회와 삭제가 쉬운 구조다.
- [[원형 큐]] - 고정 크기 배열에서 front와 rear를 순환시켜 공간을 재사용하는 큐 구현 방식이다.
- [[스택 프레임]] - 함수 호출 시 스택에 저장되는 실행 문맥으로 스택 자료구조와 직접 관련된다.
- [[BFS]] - 너비 우선 탐색은 큐를 사용해 가까운 정점부터 순차적으로 탐색한다.
- [[DFS]] - 깊이 우선 탐색은 재귀 호출 스택 또는 명시적 스택으로 구현할 수 있다.
- [[LRU 캐시]] - 해시 맵과 이중 연결 리스트 또는 덱 개념을 함께 사용해 오래된 항목을 제거한다.
- [[시간 복잡도]] - 자료구조 선택 시 접근, 삽입, 삭제 비용을 분석하는 핵심 기준이다.
- [[메모리 지역성]] - 배열은 연속 메모리 배치로 캐시 친화적인 특성을 가지며 성능에 영향을 준다.
