# Big-O 표기법 - 시간 복잡도와 공간 복잡도 계산 방법

## 핵심 개념

Big-O 표기법은 알고리즘의 입력 크기 `n`이 커질 때 실행 시간이나 메모리 사용량이 어떤 비율로 증가하는지 표현하는 점근적 표기법입니다. 정확한 실행 시간(예: 3ms, 10초)을 측정하는 것이 아니라, 입력 크기에 따른 증가 추세를 추상화합니다. 예를 들어 배열에서 특정 값을 처음부터 끝까지 찾는 선형 탐색은 최악의 경우 모든 원소를 확인해야 하므로 시간 복잡도는 `O(n)`입니다. 반면 정렬된 배열에서 이진 탐색을 사용하면 매 단계마다 탐색 범위를 절반으로 줄이므로 `O(log n)`입니다.

Big-O의 목적은 하드웨어, 언어, 컴파일러, 런타임 환경에 따라 달라지는 실제 실행 시간을 배제하고 알고리즘 자체의 확장성을 비교하는 것입니다. 작은 입력에서는 `O(n^2)` 알고리즘이 빠르게 보일 수 있지만, 입력 크기가 커질수록 `O(n log n)`이나 `O(n)` 알고리즘이 훨씬 유리해지는 경우가 많습니다. 따라서 Big-O는 대규모 데이터 처리, 서버 성능 최적화, 클라우드 비용 절감, 보안상 서비스 거부 공격(DoS) 방어 등에서 매우 중요합니다.

복잡도는 크게 시간 복잡도와 공간 복잡도로 나뉩니다. 시간 복잡도는 입력 크기에 따라 연산 횟수가 얼마나 증가하는지를 나타내고, 공간 복잡도는 입력 크기에 따라 추가로 필요한 메모리 양이 얼마나 증가하는지를 나타냅니다. 일반적으로 Big-O 계산에서는 상수 계수와 낮은 차수 항을 제거합니다. 예를 들어 `3n + 10`은 `O(n)`, `n^2 + n`은 `O(n^2)`로 표현합니다. 이는 입력 크기가 충분히 커지면 가장 빠르게 증가하는 항이 전체 성능을 지배하기 때문입니다.

## 내부 동작 원리

Big-O 계산은 “입력 크기 `n`이 증가할 때 반복 횟수, 재귀 호출 수, 추가 메모리 사용량이 어떻게 변하는가”를 분석하는 과정입니다. 핵심은 실제 초 단위 시간이 아니라 연산의 증가율을 세는 것입니다.

## 1. 시간 복잡도 계산 방법

### 1) 단순 명령문

```python
x = 10
y = x + 1
print(y)
```

입력 크기와 무관하게 일정한 횟수만 실행됩니다.

```text
입력 크기 n 증가 → 실행 횟수 변화 없음
시간 복잡도: O(1)
```

### 2) 단일 반복문

```python
for i in range(n):
    print(i)
```

반복문이 `n`번 실행됩니다.

```text
n = 10  → 10번
n = 100 → 100번
n = 1000 → 1000번

시간 복잡도: O(n)
```

### 3) 중첩 반복문

```python
for i in range(n):
    for j in range(n):
        print(i, j)
```

바깥 반복문이 `n`번, 안쪽 반복문도 매번 `n`번 실행됩니다.

```text
전체 실행 횟수 = n * n = n²
시간 복잡도: O(n²)
```

다이어그램으로 표현하면 다음과 같습니다.

```text
n = 4인 경우

        j
      0 1 2 3
i 0   ■ ■ ■ ■
  1   ■ ■ ■ ■
  2   ■ ■ ■ ■
  3   ■ ■ ■ ■

총 칸 수 = 4 * 4 = 16
일반화하면 n * n = n²
```

### 4) 서로 다른 크기의 반복문

```python
for i in range(n):
    print(i)

for j in range(m):
    print(j)
```

입력이 두 개라면 각각의 크기를 구분해서 표현할 수 있습니다.

```text
시간 복잡도: O(n + m)
```

만약 `m`이 항상 `n`과 같은 규모라고 가정할 수 있다면 `O(n)`으로 단순화할 수 있지만, 독립적인 입력이라면 `O(n + m)`이라고 쓰는 것이 더 정확합니다.

### 5) 절반씩 줄어드는 반복문

```python
while n > 1:
    n = n // 2
```

매 반복마다 입력 크기가 절반으로 줄어듭니다.

```text
n → n/2 → n/4 → n/8 → ... → 1
```

반복 횟수는 대략 `log₂ n`입니다.

```text
시간 복잡도: O(log n)
```

Big-O에서는 로그의 밑을 일반적으로 생략합니다. 로그의 밑이 달라도 상수 배 차이이기 때문입니다.

### 6) 선형 반복 안에서 로그 연산

```python
for i in range(n):
    binary_search(arr, target)
```

반복문은 `n`번 실행되고, 각 반복에서 이진 탐색이 `O(log n)`이라면 전체 시간 복잡도는 다음과 같습니다.

```text
O(n * log n) = O(n log n)
```

### 7) 재귀 알고리즘

재귀 알고리즘은 호출 횟수와 각 호출에서 수행하는 작업량을 함께 봐야 합니다.

예: 팩토리얼

```python
def factorial(n):
    if n == 1:
        return 1
    return n * factorial(n - 1)
```

호출 구조:

```text
factorial(n)
 └─ factorial(n-1)
     └─ factorial(n-2)
         └─ ...
             └─ factorial(1)
```

호출이 `n`번 발생하고 각 호출의 작업이 상수 시간이므로:

```text
시간 복잡도: O(n)
공간 복잡도: O(n)  # 재귀 호출 스택
```

예: 병합 정렬

```text
배열을 절반으로 나눔 → 각각 정렬 → 병합
```

호출 구조:

```text
크기 n
├─ 크기 n/2
│  ├─ 크기 n/4
│  └─ 크기 n/4
└─ 크기 n/2
   ├─ 크기 n/4
   └─ 크기 n/4
```

각 레벨에서 전체 병합 비용은 `O(n)`이고, 레벨 수는 `O(log n)`입니다.

```text
시간 복잡도: O(n log n)
공간 복잡도: 일반적인 구현에서 O(n) 추가 배열 사용
```

## 2. 공간 복잡도 계산 방법

공간 복잡도는 알고리즘이 입력 외에 추가로 사용하는 메모리 양을 분석합니다. 여기서 “추가 공간”은 보통 보조 배열, 해시 테이블, 재귀 호출 스택 등을 의미합니다.

### 1) 상수 공간

```python
def sum_array(arr):
    total = 0
    for x in arr:
        total += x
    return total
```

입력 배열 크기가 커져도 추가 변수는 `total`, `x` 정도로 일정합니다.

```text
공간 복잡도: O(1)
```

### 2) 선형 공간

```python
def copy_array(arr):
    result = []
    for x in arr:
        result.append(x)
    return result
```

입력 크기 `n`만큼 새 배열을 만듭니다.

```text
공간 복잡도: O(n)
```

### 3) 해시 테이블 사용

```python
def count_frequency(arr):
    freq = {}
    for x in arr:
        freq[x] = freq.get(x, 0) + 1
    return freq
```

최악의 경우 모든 원소가 서로 다르면 해시 테이블에 `n`개의 키가 저장됩니다.

```text
공간 복잡도: O(n)
```

### 4) 재귀 호출 스택

```python
def recurse(n):
    if n == 0:
        return
    recurse(n - 1)
```

재귀 호출이 끝나기 전까지 스택 프레임이 쌓입니다.

```text
호출 깊이: n
공간 복잡도: O(n)
```

반면 이진 탐색 재귀 구현은 호출 깊이가 `log n`입니다.

```text
공간 복잡도: O(log n)
```

단, 반복문으로 구현한 이진 탐색은 추가 공간이 상수이므로 `O(1)`입니다.

## 3. Big-O 계산 규칙 요약

```text
1. 상수는 제거한다.
   O(3n) → O(n)

2. 낮은 차수 항은 제거한다.
   O(n² + n + 1) → O(n²)

3. 독립된 순차 작업은 더한다.
   O(n) + O(m) → O(n + m)

4. 중첩 작업은 곱한다.
   O(n) 안에서 O(m) 실행 → O(nm)

5. 조건문은 보통 최악의 경우를 기준으로 본다.
   if 분기 중 O(n²)이 있다면 최악 시간은 O(n²)

6. 재귀는 호출 수, 호출 깊이, 각 호출 비용을 함께 분석한다.
```

## 4. 주요 복잡도 증가 순서

```text
O(1)
  ↓
O(log n)
  ↓
O(n)
  ↓
O(n log n)
  ↓
O(n²)
  ↓
O(n³)
  ↓
O(2ⁿ)
  ↓
O(n!)
```

일반적으로 아래로 갈수록 입력 크기 증가에 더 민감합니다. 다만 실제 성능은 상수 계수, 캐시 효율, I/O 비용, 구현 방식, 데이터 분포 등에 의해 영향을 받을 수 있습니다.

## 실제 시스템 연결

Big-O는 실제 시스템의 성능 문제를 이해하는 데 직접적으로 연결됩니다. 서버, 운영체제, 데이터베이스, 웹 서버, 클라우드 인프라에서는 입력 크기가 곧 요청 수, 파일 수, 로그 크기, 네트워크 연결 수, 컨테이너 수, 사용자 수로 나타나기 때문입니다.

## 1. Linux 파일 시스템과 디렉터리 탐색

Linux에서 특정 디렉터리 안의 파일 목록을 순회하는 작업은 디렉터리 내 항목 수에 비례하는 경우가 많습니다. 예를 들어 애플리케이션이 로그 디렉터리의 모든 파일을 확인한다면 파일 수를 `n`이라고 할 때 순회 자체는 일반적으로 `O(n)`으로 볼 수 있습니다.

```text
파일 10개    → 10개 확인
파일 10,000개 → 10,000개 확인
```

따라서 로그 파일을 한 디렉터리에 과도하게 많이 쌓아두면 백업, 압축, 검색, 삭제 작업이 느려질 수 있습니다. 이 경우 날짜별 디렉터리 분리, 로그 로테이션, 인덱싱된 검색 시스템 사용 등이 도움이 됩니다.

## 2. Linux 프로세스와 스케줄링

운영체제 스케줄러는 실행 가능한 작업들을 관리해야 합니다. 실제 Linux 스케줄러는 복잡한 자료구조와 정책을 사용하지만, 핵심 관점은 “작업 수가 증가해도 스케줄링 비용을 통제해야 한다”는 것입니다. 실행 가능한 프로세스나 스레드 수가 많아지면 스케줄링, 컨텍스트 스위칭, 캐시 미스 등으로 시스템 처리량이 떨어질 수 있습니다.

Big-O 관점에서는 작업 목록을 단순 선형 탐색으로 관리하면 `O(n)` 비용이 발생할 수 있고, 균형 트리나 우선순위 큐 계열 자료구조를 사용하면 특정 연산을 `O(log n)` 수준으로 관리할 수 있습니다.

⚠️ 확인 필요: 특정 Linux 커널 버전의 스케줄러 내부 자료구조와 연산 복잡도는 버전 및 설정에 따라 달라질 수 있으므로 정확한 분석 시 해당 커널 문서를 확인해야 합니다.

## 3. Nginx 요청 처리와 연결 수

Nginx 같은 웹 서버는 많은 클라이언트 연결을 효율적으로 처리해야 합니다. 요청 처리 로직이 연결 수 `n`에 대해 매번 전체 연결을 순회하는 `O(n)` 구조라면 동시 연결이 많아질수록 처리 지연이 커질 수 있습니다. 그래서 이벤트 기반 I/O, 효율적인 이벤트 알림 메커니즘, 비동기 처리 구조가 중요합니다.

예를 들어 요청 라우팅이나 캐시 키 조회에서 해시 테이블을 사용하면 평균적으로 빠른 조회가 가능합니다. 하지만 해시 충돌이 많거나 키 설계가 좋지 않으면 성능이 나빠질 수 있습니다.

```text
좋은 캐시 키 조회: 평균 O(1)에 가까움
나쁜 선형 검색: O(n)
```

## 4. 데이터베이스 쿼리

데이터베이스에서 인덱스가 없는 컬럼으로 검색하면 많은 경우 테이블 전체를 스캔해야 하며, 데이터 수를 `n`이라고 할 때 `O(n)`에 가깝게 생각할 수 있습니다. 반면 B-Tree 계열 인덱스를 사용하면 검색 범위를 단계적으로 줄일 수 있어 일반적으로 훨씬 효율적입니다.

```text
인덱스 없음: 전체 스캔 → O(n) 관점
인덱스 있음: 트리 기반 탐색 → O(log n) 관점
```

실제 데이터베이스 성능은 디스크 I/O, 캐시 히트율, 쿼리 플래너, 통계 정보, 조인 방식 등에 영향을 받기 때문에 Big-O만으로 전체 성능을 설명할 수는 없습니다. 그러나 인덱스의 중요성을 이해하는 데 Big-O는 매우 유용합니다.

## 5. AWS, GCP에서의 로그 분석

AWS CloudWatch Logs, Amazon S3, GCP Cloud Logging, BigQuery 같은 시스템에서는 로그 데이터 크기가 커질수록 검색, 필터링, 집계 비용이 증가합니다. 로그 전체를 매번 스캔하면 데이터 양에 비례하는 비용이 발생할 수 있습니다. 따라서 파티셔닝, 인덱싱, 시간 범위 제한, 적절한 보존 정책이 중요합니다.

예를 들어 S3에 저장된 로그를 Athena로 조회할 때 파티션을 잘 설계하면 불필요한 데이터 스캔을 줄일 수 있습니다. 이는 알고리즘 관점에서 검색 대상 `n` 자체를 줄이는 최적화라고 볼 수 있습니다.

## 클라우드 연결

Big-O는 클라우드 환경에서 성능뿐 아니라 비용과 안정성에 직접 연결됩니다. 클라우드는 사용량 기반 과금이 일반적이므로, 비효율적인 `O(n²)` 처리 로직은 입력 데이터가 증가할 때 CPU 시간, 메모리, 네트워크, 스토리지 I/O 비용을 빠르게 증가시킬 수 있습니다.

## 1. Docker 컨테이너와 메모리 사용량

Docker 컨테이너 안에서 실행되는 애플리케이션도 결국 호스트의 CPU와 메모리를 사용합니다. 공간 복잡도가 `O(n)`인 작업은 입력 데이터가 커질수록 메모리 사용량도 증가합니다. 만약 컨테이너에 설정된 메모리 제한을 초과하면 애플리케이션이 종료될 수 있습니다.

예를 들어 대용량 JSON 파일을 한 번에 메모리에 올려 파싱하는 방식은 공간 복잡도 관점에서 위험할 수 있습니다.

```text
전체 파일 로딩:
입력 크기 n → 메모리 O(n)

스트리밍 처리:
한 번에 일부만 처리 → 추가 메모리 O(1) 또는 제한된 크기
```

따라서 컨테이너 환경에서는 스트리밍 처리, 배치 크기 제한, 메모리 상한 설정, 백프레셔(backpressure) 적용이 중요합니다.

## 2. Kubernetes와 오토스케일링

Kubernetes 환경에서 애플리케이션의 시간 복잡도가 나쁘면 트래픽이 증가할 때 CPU 사용률이 급격히 상승할 수 있습니다. Horizontal Pod Autoscaler(HPA)는 CPU, 메모리 또는 커스텀 메트릭 기반으로 Pod 수를 늘릴 수 있지만, 알고리즘 자체가 `O(n²)`이면 단순히 Pod 수를 늘리는 방식만으로는 비용 효율적인 해결이 되기 어렵습니다.

예를 들어 요청 하나가 내부적으로 사용자 목록 전체를 매번 중첩 순회한다면 사용자 수가 증가할수록 응답 시간이 급격히 늘어날 수 있습니다.

```text
요청 수 증가 + 데이터 크기 증가 + O(n²) 로직
→ CPU 사용량 증가
→ 응답 지연
→ Pod 증가
→ 클라우드 비용 증가
```

따라서 클라우드 네이티브 환경에서도 기본적인 알고리즘 개선이 우선입니다.

## 3. AWS Lambda와 실행 시간

AWS Lambda 같은 서버리스 환경에서는 함수 실행 시간과 메모리 설정이 비용 및 성능에 영향을 줍니다. 시간 복잡도가 큰 코드는 입력 데이터가 증가할수록 실행 시간이 늘어나고, 제한 시간에 도달할 수 있습니다.

예를 들어 S3 이벤트로 업로드된 파일을 처리하는 Lambda가 파일 전체를 중첩 반복으로 비교한다면 파일 크기가 커질 때 실행 시간이 급격히 증가할 수 있습니다. 이 경우 해시 기반 중복 검사, 정렬 후 비교, 스트리밍 처리 등을 고려할 수 있습니다.

⚠️ 확인 필요: AWS Lambda의 최대 실행 시간, 메모리 범위 등 구체적 제한값은 AWS 정책에 따라 변경될 수 있으므로 최신 공식 문서를 확인해야 합니다.

## 4. AWS S3, Athena, BigQuery와 데이터 스캔

클라우드 분석 서비스에서는 “얼마나 많은 데이터를 읽는가”가 성능과 비용에 큰 영향을 줍니다. 전체 데이터 스캔은 입력 크기 `n`에 비례하는 비용으로 볼 수 있습니다. 파티션 프루닝, 컬럼형 포맷, 압축, 조건절 최적화는 실제로 처리해야 하는 `n`을 줄이는 방식입니다.

```text
나쁜 방식:
전체 로그 n개 스캔 → O(n)

개선 방식:
날짜 파티션으로 대상 축소 → O(k), k << n
```

## 5. AWS DynamoDB, Redis와 자료구조 선택

DynamoDB, Redis 같은 시스템을 사용할 때도 자료구조 선택은 복잡도와 관련됩니다. Redis는 문자열, 리스트, 셋, 정렬된 셋, 해시 등 다양한 자료구조를 제공하며, 명령별 시간 복잡도는 공식 문서에 명시되어 있습니다. 잘못된 명령을 큰 데이터에 반복 실행하면 지연이 발생할 수 있습니다.

예를 들어 많은 원소를 가진 컬렉션을 매 요청마다 전체 조회하는 방식은 `O(n)` 비용을 반복적으로 발생시킬 수 있습니다. 반면 필요한 키로 직접 접근하거나, 적절한 인덱스 구조를 설계하면 더 효율적입니다.

## 보안 연결

Big-O는 보안과도 밀접하게 연결됩니다. 공격자는 입력 크기나 입력 형태를 조작해 알고리즘의 최악 시간 복잡도 또는 최악 공간 복잡도를 유발할 수 있습니다. 이를 알고리즘 복잡도 공격(Algorithmic Complexity Attack) 또는 복잡도 기반 서비스 거부 공격의 관점에서 볼 수 있습니다.

## 1. 서비스 거부 공격과 시간 복잡도

서버가 요청 하나를 처리하는 데 `O(n²)` 이상의 비용을 사용한다면, 공격자는 큰 입력을 보내 CPU 사용량을 급격히 증가시킬 수 있습니다.

예를 들어 다음과 같은 로직은 위험할 수 있습니다.

```python
for a in user_input:
    for b in user_input:
        compare(a, b)
```

입력 길이가 증가하면 비교 횟수는 제곱으로 증가합니다.

```text
입력 길이 n → O(n²)
```

공격자가 매우 긴 입력을 반복적으로 보내면 정상 사용자 요청이 지연될 수 있습니다.

## 2. 해시 충돌 공격

해시 테이블은 평균적으로 삽입, 검색, 삭제가 `O(1)`에 가깝다고 설명되지만, 모든 키가 같은 버킷으로 충돌하면 최악의 경우 성능이 저하될 수 있습니다. 많은 언어와 프레임워크는 해시 충돌 공격을 완화하기 위해 해시 랜덤화 또는 충돌 시 보조 자료구조 사용 등의 방어 기법을 도입해 왔습니다.

⚠️ 확인 필요: 특정 언어, 런타임, 프레임워크의 해시 충돌 방어 방식은 버전별로 다르므로 정확한 내용은 해당 공식 문서를 확인해야 합니다.

보안 관점의 모범 사례는 다음과 같습니다.

```text
- 사용자 입력 크기 제한
- 요청 본문 크기 제한
- 파라미터 개수 제한
- 해시 기반 자료구조 사용 시 런타임의 충돌 방어 기능 확인
- 비정상적으로 큰 요청에 대한 rate limiting
```

## 3. 정규표현식 ReDoS

일부 정규표현식은 특정 입력에서 백트래킹이 폭발적으로 증가할 수 있습니다. 이를 ReDoS(Regular Expression Denial of Service)라고 합니다. 취약한 정규표현식은 입력 길이가 조금만 증가해도 매칭 시간이 급격히 늘어날 수 있습니다.

예시 형태:

```text
중첩 반복, 애매한 선택 조건이 있는 정규식
→ 특정 실패 입력에서 과도한 백트래킹 발생 가능
```

방어 방법:

```text
- 정규표현식을 단순하게 작성
- 중첩된 반복 패턴 주의
- 입력 길이 제한
- 타임아웃 설정
- 안전한 정규식 엔진 또는 정적 분석 도구 사용
```

## 4. 공간 복잡도와 메모리 고갈 공격

공간 복잡도가 큰 알고리즘은 메모리 고갈 공격에 취약할 수 있습니다. 예를 들어 요청 본문 전체를 메모리에 저장하거나, 사용자 입력 크기만큼 거대한 배열이나 맵을 생성하면 공격자가 큰 입력을 보내 메모리를 소모시킬 수 있습니다.

```text
입력 크기 n
→ 요청마다 O(n) 메모리 할당
→ 동시 요청 증가
→ 메모리 압박
→ 프로세스 종료 또는 성능 저하
```

방어 방법:

```text
- 요청 크기 제한
- 스트리밍 파서 사용
- 업로드 파일 크기 제한
- 동시 처리 수 제한
- 큐와 백프레셔 적용
- 메모리 사용량 모니터링
```

## 5. 인증/인가 로직의 복잡도

권한 검사를 매 요청마다 전체 사용자, 전체 그룹, 전체 정책을 선형 또는 중첩 탐색으로 처리하면 사용자가 늘어날수록 인증/인가 지연이 커질 수 있습니다. 보안 로직은 모든 요청에서 자주 실행되므로, 복잡도가 나쁘면 성능 병목이 되기 쉽습니다.

개선 방법:

```text
- 권한 인덱싱
- 캐시 사용
- 토큰에 필요한 클레임 포함
- 정책 평가 범위 최소화
- 캐시 만료와 권한 변경 반영 정책 설계
```

단, 보안 캐시는 권한 변경이 즉시 반영되지 않을 수 있는 문제가 있으므로 TTL, 무효화 전략, 감사 로그를 함께 고려해야 합니다.

## 면접 질문

**Q1. Big-O 표기법이 무엇이며 왜 사용하는가?**  
> 핵심 답변: Big-O는 입력 크기 증가에 따른 알고리즘의 시간 또는 공간 사용량 증가율을 나타내는 점근적 표기법이다. 실제 실행 시간보다 확장성을 비교하는 데 목적이 있다. 하드웨어나 언어 차이를 배제하고 알고리즘의 성장률을 분석할 수 있기 때문에 대규모 데이터 처리와 성능 최적화에서 중요하다.

**Q2. 시간 복잡도와 공간 복잡도의 차이는 무엇인가?**  
> 핵심 답변: 시간 복잡도는 입력 크기에 따라 실행 연산 수가 얼마나 증가하는지를 나타내고, 공간 복잡도는 입력 크기에 따라 추가 메모리 사용량이 얼마나 증가하는지를 나타낸다. 예를 들어 배열 합계를 구하는 알고리즘은 시간은 `O(n)`이지만 추가 변수만 사용하면 공간은 `O(1)`이다.

**Q3. 중첩 반복문의 시간 복잡도는 어떻게 계산하는가?**  
> 핵심 답변: 각 반복문의 반복 횟수를 곱한다. 바깥 반복문이 `n`번, 안쪽 반복문이 매번 `n`번 실행되면 총 `n²`번 실행되므로 `O(n²)`이다. 만약 바깥이 `n`, 안쪽이 `m`이면 `O(nm)`으로 표현한다.

**Q4. 재귀 함수의 공간 복잡도를 계산할 때 무엇을 고려해야 하는가?**  
> 핵심 답변: 재귀 호출 스택의 깊이를 고려해야 한다. 팩토리얼처럼 `n`단계 깊이로 호출되면 공간 복잡도는 `O(n)`이다. 재귀 이진 탐색은 호출 깊이가 `O(log n)`이므로 공간 복잡도도 `O(log n)`이다. 반복문으로 바꾸면 호출 스택이 없어져 `O(1)`이 될 수 있다.

**Q5. 해시 테이블의 조회가 항상 O(1)인가?**  
> 핵심 답변: 평균적으로는 `O(1)`에 가깝게 설명하지만 항상 그런 것은 아니다. 해시 충돌이 많으면 최악의 경우 성능이 저하될 수 있다. 실제 런타임이나 라이브러리는 충돌 완화 기법을 제공할 수 있지만, 키 분포, 해시 함수, 구현 방식에 따라 성능이 달라진다.
