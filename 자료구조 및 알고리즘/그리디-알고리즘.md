# 그리디 알고리즘 - 매 순간 최적의 해를 찾는 전략

## 핵심 개념

그리디 알고리즘(Greedy Algorithm)은 **문제를 여러 단계로 나누고, 각 단계에서 현재 기준으로 가장 좋아 보이는 선택을 반복하여 해를 구성하는 설계 패러다임**이다. 핵심 아이디어는 “지금 당장 최선의 선택이 전체적으로도 최적해로 이어진다”는 가정에 있다. 예를 들어 최소 신장 트리를 구하는 Kruskal 알고리즘은 매 순간 가장 작은 가중치의 간선을 선택하고, Dijkstra 알고리즘은 현재까지의 최단 거리가 가장 짧은 정점을 확정한다.

그리디 알고리즘의 목적은 **복잡한 탐색 공간을 줄이고 빠르게 해를 구하는 것**이다. 모든 경우를 탐색하는 완전 탐색이나, 부분 문제를 저장하며 푸는 동적 계획법에 비해 구현이 단순하고 시간 복잡도가 낮은 경우가 많다. 하지만 모든 문제에 적용할 수 있는 것은 아니다. 그리디가 항상 정답을 보장하려면 일반적으로 **탐욕적 선택 속성(Greedy Choice Property)** 과 **최적 부분 구조(Optimal Substructure)** 가 성립해야 한다.

이 개념이 중요한 이유는 알고리즘 문제 해결뿐 아니라 실제 시스템 설계에서도 자주 등장하기 때문이다. 네트워크 라우팅, 작업 스케줄링, 압축, 캐시 정책, 로드 밸런싱 등 많은 시스템은 제한된 시간과 자원 안에서 “현재 가장 합리적인 선택”을 반복한다. 다만 그리디는 지역 최적해(Local Optimum)에 빠질 위험이 있으므로, 문제 조건을 엄밀히 분석하고 정당성 증명이 필요하다.

## 내부 동작 원리

그리디 알고리즘은 보통 다음과 같은 절차로 동작한다.

1. **후보 집합 정의**
   - 선택 가능한 원소나 행동의 집합을 정의한다.
   - 예: 간선 목록, 작업 목록, 동전 종류, 정점 집합

2. **선택 기준 정의**
   - 현재 상태에서 가장 좋아 보이는 기준을 정한다.
   - 예: 가장 작은 가중치, 가장 빠른 종료 시간, 가장 큰 가치 대비 무게 비율

3. **현재 최선 선택 수행**
   - 기준에 따라 하나의 선택을 한다.
   - 이 선택은 이후에 되돌리지 않는 경우가 많다.

4. **해의 가능성 검사**
   - 선택한 원소가 조건을 위반하지 않는지 확인한다.
   - 예: 사이클이 생기지 않는가, 용량을 초과하지 않는가

5. **해 완성 여부 확인**
   - 목표 조건을 만족할 때까지 반복한다.

일반적인 흐름은 다음과 같이 표현할 수 있다.

```text
[문제 상태]
    ↓
[후보 선택지 생성]
    ↓
[현재 기준에서 가장 좋은 선택]
    ↓
[조건 위반 여부 검사]
    ├── 위반함 → 선택 폐기
    └── 위반하지 않음 → 해에 포함
    ↓
[목표 달성 여부 확인]
    ├── 미달성 → 반복
    └── 달성 → 결과 반환
```

예를 들어 **활동 선택 문제(Activity Selection Problem)** 는 그리디 알고리즘의 대표적인 예다. 여러 활동이 시작 시간과 종료 시간을 가지고 있을 때, 서로 겹치지 않게 최대한 많은 활동을 선택하는 문제다. 이 경우 “가장 빨리 끝나는 활동을 먼저 선택한다”는 전략이 최적해를 보장한다.

```text
활동 목록:
A: 1시 시작, 4시 종료
B: 3시 시작, 5시 종료
C: 0시 시작, 6시 종료
D: 5시 시작, 7시 종료
E: 8시 시작, 9시 종료

종료 시간이 빠른 순서로 정렬:
A → B → C → D → E

선택 과정:
A 선택
B는 A와 겹침 → 제외
C는 A와 겹침 → 제외
D는 A 이후 시작 → 선택
E는 D 이후 시작 → 선택

결과:
A, D, E
```

이 알고리즘이 성립하는 이유는 가장 빨리 끝나는 활동을 선택하면 이후에 남는 시간 구간이 최대화되기 때문이다. 즉, 현재 선택이 미래 선택의 가능성을 최대한 열어준다.

그리디 알고리즘의 정당성을 보일 때는 주로 다음을 증명한다.

- **탐욕적 선택 속성**
  - 현재의 최선 선택을 포함하는 최적해가 존재함을 보인다.
- **최적 부분 구조**
  - 한 번 선택한 뒤 남은 부분 문제도 같은 방식으로 최적으로 풀 수 있음을 보인다.
- **교환 논증**
  - 어떤 최적해가 그리디 선택을 포함하지 않더라도, 그 선택을 그리디 선택으로 바꿔도 최적성이 유지됨을 보인다.

대표적인 그리디 알고리즘은 다음과 같다.

| 알고리즘 | 그리디 선택 기준 | 적용 조건 |
|---|---|---|
| Kruskal 알고리즘 | 가장 작은 가중치 간선 선택 | 무방향 가중 그래프의 최소 신장 트리 |
| Prim 알고리즘 | 현재 트리와 연결되는 최소 가중치 간선 선택 | 무방향 가중 그래프의 최소 신장 트리 |
| Dijkstra 알고리즘 | 현재까지 최단 거리가 가장 작은 정점 확정 | 간선 가중치가 음수가 아닌 그래프 |
| Huffman Coding | 빈도가 가장 낮은 두 노드 병합 | 접두어 코드 기반 압축 |
| 활동 선택 문제 | 가장 빨리 끝나는 활동 선택 | 종료 시간 기준 정렬 가능 |

주의할 점은 “현재 가장 좋아 보이는 선택”이 항상 전체 최적해를 의미하지는 않는다는 것이다. 예를 들어 일반적인 동전 거스름돈 문제에서 큰 동전부터 고르는 전략은 특정 동전 체계에서는 최적이 아닐 수 있다.

## 실제 시스템 연결

그리디 알고리즘은 실제 시스템에서 “전체 최적화를 정확히 계산하기 어렵거나 비용이 큰 경우”에 자주 사용된다. 특히 운영체제, 네트워크, 압축, 로드 밸런싱, 스케줄링 영역에서 그리디적 의사결정이 나타난다.

### 1. 네트워크 라우팅과 최단 경로

Dijkstra 알고리즘은 간선 가중치가 음수가 아닌 그래프에서 최단 경로를 구하는 대표적인 그리디 알고리즘이다. 네트워크에서는 라우터 간 경로 비용을 기반으로 최적 경로를 계산하는 데 최단 경로 알고리즘이 사용된다.

예를 들어 링크 비용이 모두 음수가 아닌 경우, 현재까지 알려진 최단 거리가 가장 작은 노드를 확정하고 이웃 노드의 거리를 갱신한다.

```text
시작 노드
  ↓
현재 최단 거리 최소 노드 선택
  ↓
해당 노드의 거리 확정
  ↓
인접 노드 거리 갱신
  ↓
모든 노드 확정까지 반복
```

다만 실제 네트워크 프로토콜은 단순한 알고리즘 하나만으로 동작하지 않고, 프로토콜 규칙, 장애 감지, 수렴 시간, 정책 라우팅 등 다양한 요소와 결합된다.

### 2. 압축 시스템과 Huffman Coding

Huffman Coding은 파일 압축과 데이터 인코딩에서 중요한 개념이다. 이 알고리즘은 등장 빈도가 낮은 두 문자를 반복적으로 병합하여 이진 트리를 만든다. 빈도가 높은 문자는 짧은 코드, 빈도가 낮은 문자는 긴 코드를 갖게 되어 전체 비트 수를 줄일 수 있다.

```text
빈도 낮은 두 노드 선택
  ↓
두 노드를 병합
  ↓
새 노드를 후보 집합에 추가
  ↓
노드가 하나 남을 때까지 반복
```

이 과정은 매 단계에서 가장 빈도가 낮은 두 항목을 선택하는 그리디 전략이다.

### 3. Nginx 로드 밸런싱

Nginx는 여러 업스트림 서버로 요청을 분산할 수 있다. 그중 `least_conn` 방식은 현재 활성 연결 수가 가장 적은 서버를 선택한다. 이는 “현재 가장 덜 바쁜 서버를 고른다”는 점에서 그리디한 선택 방식으로 볼 수 있다.

```nginx
upstream backend {
    least_conn;
    server app1.example.com;
    server app2.example.com;
}
```

이 방식은 현재 연결 수를 기준으로 빠르게 결정을 내릴 수 있지만, 요청의 실제 처리 비용이나 서버의 성능 차이를 완전히 반영하지 못할 수 있다. 따라서 가중치 설정, 헬스 체크, 타임아웃 설정 등과 함께 사용해야 한다.

### 4. Linux와 작업 스케줄링

운영체제 스케줄러는 제한된 CPU 시간을 여러 프로세스나 스레드에 분배한다. 모든 작업의 미래 실행 시간을 정확히 알 수 없기 때문에, 실제 스케줄러는 현재 상태를 바탕으로 우선순위를 계산하고 다음 실행 대상을 선택한다. 이 관점에서 스케줄링 문제는 그리디적 선택과 밀접하다.

다만 Linux의 실제 스케줄러는 단순한 그리디 알고리즘 하나로 설명하기 어렵다. 정책, 우선순위, 가상 실행 시간, 실시간 스케줄링 클래스 등 다양한 요소가 결합되어 있다.

### 5. 캐시와 자원 관리

캐시 교체 정책 중 일부는 현재 관찰 가능한 정보를 기준으로 항목을 제거한다. 예를 들어 LRU(Least Recently Used)는 가장 오랫동안 사용되지 않은 항목을 제거한다. 이는 “가까운 미래에도 쓰이지 않을 가능성이 높다”는 휴리스틱에 기반한다.

LRU 자체는 전형적인 그리디 최적화 알고리즘이라기보다는 캐시 관리 휴리스틱이지만, 현재 상태에서 하나의 항목을 선택해 제거한다는 점에서 그리디적 사고방식과 연결된다.

## 클라우드 연결

클라우드 환경에서는 자원 배치, 스케일링, 로드 밸런싱, 스케줄링 등에서 그리디적 의사결정이 자주 등장한다. 클라우드 시스템은 수많은 서버, 컨테이너, 요청, 네트워크 경로를 다뤄야 하므로 전체 최적해를 매번 계산하는 것은 현실적으로 어렵다. 따라서 현재 상태를 기반으로 빠르게 좋은 결정을 내리는 전략이 중요하다.

### 1. Kubernetes 스케줄링

Kubernetes 스케줄러는 새로 생성된 Pod를 어느 Node에 배치할지 결정한다. 일반적으로 필터링 단계를 통해 배치 가능한 노드를 찾고, 스코어링 단계를 통해 더 적합한 노드를 선택한다.

```text
새 Pod 생성
  ↓
배치 가능한 Node 필터링
  ↓
Node별 점수 계산
  ↓
점수가 높은 Node 선택
  ↓
Pod 바인딩
```

이 과정은 “현재 Pod 하나에 대해 가장 적합한 Node를 선택한다”는 점에서 그리디적이다. 다만 Kubernetes 스케줄링은 전체 클러스터의 장기적 최적 배치를 항상 보장하는 방식은 아니다. 그래서 Pod affinity, anti-affinity, taint/toleration, resource request/limit, topology spread constraints 등을 함께 사용해 배치 품질을 높인다.

### 2. Docker와 컨테이너 자원 배치

Docker 자체는 단일 호스트에서 컨테이너를 실행하지만, 여러 컨테이너가 CPU와 메모리를 공유할 때 자원 제한 설정이 중요하다. 컨테이너 오케스트레이션 환경에서는 현재 남은 자원, 이미지 위치, 노드 상태 등을 기준으로 배치 결정을 내릴 수 있다.

예를 들어 컨테이너를 배치할 때 다음과 같은 기준이 사용될 수 있다.

- CPU 요청량을 만족하는 노드
- 메모리 요청량을 만족하는 노드
- 네트워크 지연이 낮은 노드
- 이미 필요한 이미지가 있는 노드
- 장애 도메인이 다른 노드

이러한 기준 중 하나 또는 여러 개를 점수화해 가장 적합한 노드를 선택하는 방식은 그리디 전략과 유사하다.

### 3. AWS Elastic Load Balancing

AWS Elastic Load Balancing은 여러 대상에 트래픽을 분산한다. 로드 밸런서는 현재 대상 상태, 헬스 체크 결과, 리스너 규칙, 대상 그룹 설정 등을 기반으로 요청을 전달한다. 로드 밸런싱은 전체 미래 트래픽을 알 수 없기 때문에 현재 상태에서 합리적인 분산 결정을 내리는 문제와 연결된다.

특히 서버 측 로드 밸런싱에서는 다음과 같은 선택 기준이 사용될 수 있다.

- 연결 수
- 대상의 상태
- 가중치
- 지연 시간
- 라우팅 규칙

이러한 방식은 매 요청 또는 연결 단위에서 “현재 적절한 대상”을 선택한다는 점에서 그리디적 사고와 관련된다.

### 4. 오토스케일링과 그리디적 의사결정

클라우드 오토스케일링은 CPU 사용률, 메모리 사용량, 요청 수, 큐 길이 같은 현재 또는 최근 지표를 보고 인스턴스나 컨테이너 수를 늘리거나 줄인다. 이는 미래 부하를 완벽하게 예측하기보다는 현재 관측된 상태를 기반으로 즉각적인 조치를 취하는 방식이다.

```text
메트릭 수집
  ↓
임계값 또는 정책 평가
  ↓
확장 또는 축소 결정
  ↓
새 자원 반영
```

다만 오토스케일링은 단순 그리디 전략만으로 운영하면 진동 현상, 과잉 확장, 지연 대응 문제가 발생할 수 있다. 그래서 쿨다운, 안정화 윈도우, 예측 기반 스케일링, 최소/최대 용량 제한 등을 함께 사용한다.

### 5. 비용 최적화

클라우드 비용 최적화에서도 그리디 접근이 사용될 수 있다. 예를 들어 비용이 높은 리소스부터 줄이거나, 사용률이 낮은 인스턴스를 먼저 종료하는 방식은 그리디 전략이다. 그러나 이러한 방식은 서비스 의존성, 장애 허용성, 예약 인스턴스, 네트워크 비용, 데이터 전송 비용 등을 충분히 고려하지 않으면 전체 비용 최적화에 실패할 수 있다.

## 보안 연결

그리디 알고리즘 자체가 특정 보안 취약점은 아니지만, 보안 시스템이나 인프라 운영에서 그리디적 의사결정을 잘못 적용하면 취약한 설계가 될 수 있다.

### 1. 지역 최적화로 인한 보안 정책 우회

그리디 전략은 현재 기준에서 최선으로 보이는 결정을 내린다. 하지만 공격자는 시스템의 선택 기준을 분석해 이를 역이용할 수 있다. 예를 들어 로드 밸런서가 단순히 현재 연결 수가 적은 서버를 선택한다면, 공격자는 특정 서버의 연결 상태를 조작하거나 불균형을 유도할 수 있다.

보안 모범 사례:

- 단일 지표에 의존하지 않는다.
- 헬스 체크와 이상 탐지를 함께 사용한다.
- 요청 비용, 인증 상태, IP 평판, 속도 제한 등을 함께 고려한다.
- 장애 격리와 서킷 브레이커를 적용한다.

### 2. 스케줄링과 자원 고갈 공격

클라우드나 컨테이너 환경에서 스케줄러가 현재 여유 자원만 보고 워크로드를 배치하면, 공격성 워크로드가 특정 노드의 CPU, 메모리, I/O를 과도하게 점유할 수 있다. 이 경우 정상 서비스의 성능 저하나 장애가 발생할 수 있다.

대응 방법:

- 컨테이너별 CPU, 메모리 request/limit 설정
- Kubernetes ResourceQuota와 LimitRange 사용
- Pod Security Admission 및 최소 권한 정책 적용
- 노드 격리, 네임스페이스 격리
- 런타임 모니터링과 이상 징후 탐지

### 3. 최단 경로 기반 시스템의 가정 위반

Dijkstra 알고리즘은 음수 가중치가 없는 그래프에서 올바르게 동작한다. 시스템 설계에서 알고리즘의 전제 조건을 무시하면 잘못된 결과가 나올 수 있다. 보안 관점에서는 입력 데이터가 신뢰할 수 없을 때, 공격자가 비용 값이나 우선순위 값을 조작해 잘못된 경로 선택이나 정책 결정을 유도할 수 있다.

대응 방법:

- 입력값 검증
- 가중치 범위 제한
- 정책 변경 감사 로그 기록
- 신뢰할 수 없는 데이터와 신뢰 가능한 데이터 분리
- 실패 시 안전한 기본값 사용

### 4. 압축과 부채널 위험

Huffman Coding 같은 압축 알고리즘은 데이터 빈도에 따라 출력 길이가 달라진다. 압축된 크기나 응답 길이가 민감 정보와 상관관계를 가질 수 있는 상황에서는 정보 노출 가능성이 생길 수 있다. 실제 웹 보안에서는 압축과 암호화가 결합될 때 길이 기반 부채널 공격이 논의되어 왔다.

모범 사례:

- 민감 정보와 사용자 입력을 같은 압축 컨텍스트에 두지 않는다.
- 민감 응답에 압축을 비활성화하는 방안을 검토한다.
- 토큰, 세션 값, CSRF 값 등은 충분히 무작위화한다.
- 응답 길이에 민감한 정보가 반영되지 않도록 설계한다.

### 5. 탐욕적 차단 정책의 오탐 문제

보안 시스템이 “현재 가장 위험해 보이는 요청부터 차단”하는 방식만 사용하면 정상 사용자를 차단하는 오탐이 발생할 수 있다. 예를 들어 짧은 시간에 많은 요청을 보내는 사용자가 항상 공격자는 아니다. 배치 작업, 모바일 네트워크 재시도, 프록시 환경 등 정상적인 이유가 있을 수 있다.

대응 방법:

- 단순 임계값보다 다중 신호 기반 판단 사용
- 사용자 평판, 인증 여부, 행동 패턴 고려
- 차단 전 단계적 제한 적용
- 로깅과 사후 분석 체계 마련
- 관리자가 정책을 검토하고 조정할 수 있도록 설계

## 면접 질문

**Q1. 그리디 알고리즘이란 무엇이며, 언제 사용할 수 있나요?**  
> 핵심 답변: 각 단계에서 현재 가장 좋아 보이는 선택을 반복해 해를 구성하는 알고리즘이다. 항상 정답을 보장하지는 않으며, 탐욕적 선택 속성과 최적 부분 구조가 성립해야 한다. 대표 예시는 Kruskal, Prim, Dijkstra, Huffman Coding, 활동 선택 문제다.

**Q2. 그리디 알고리즘과 동적 계획법의 차이는 무엇인가요?**  
> 핵심 답변: 그리디는 현재 선택을 확정하고 보통 되돌리지 않는다. 동적 계획법은 부분 문제의 결과를 저장하고 여러 선택지를 비교해 최적해를 구한다. 그리디는 빠르고 단순하지만 적용 조건이 엄격하고, DP는 더 넓은 문제에 적용 가능하지만 메모리와 시간이 더 들 수 있다.

**Q3. Dijkstra 알고리즘이 그리디 알고리즘인 이유는 무엇인가요?**  
> 핵심 답변: 매 단계에서 아직 확정되지 않은 정점 중 현재까지의 최단 거리가 가장 작은 정점을 선택해 확정하기 때문이다. 이 선택이 안전한 이유는 간선 가중치가 음수가 아닐 때, 나중에 더 짧은 경로가 발견될 수 없기 때문이다.

**Q4. 그리디 알고리즘의 정당성을 어떻게 증명하나요?**  
> 핵심 답변: 보통 탐욕적 선택 속성과 최적 부분 구조를 증명한다. 자주 쓰는 방법은 교환 논증이다. 어떤 최적해가 그리디 선택을 포함하지 않더라도, 그 선택을 그리디 선택으로 바꿔도 해의 품질이 나빠지지 않음을 보이면 된다.

**Q5. 그리디 알고리즘이 실패하는 예시는 무엇인가요?**  
> 핵심 답변: 일반적인 동전 거스름돈 문제가 대표적이다. 큰 동전부터 선택하는 방식은 일부 동전 체계에서는 최소 동전 개수를 보장하지 않는다. 또한 0/1 배낭 문제에서 가치 대비 무게 비율이 큰 물건부터 고르는 전략은 항상 최적해를 만들지 못한다.

## 관련 개념

- [[동적 계획법]] - 그리디와 자주 비교되는 최적화 문제 해결 패러다임이다.
- [[탐욕적 선택 속성]] - 그리디 알고리즘이 최적해를 보장하기 위한 핵심 조건이다.
- [[최적 부분 구조]] - 전체 문제의 최적해가 부분 문제의 최적해로 구성되는 성질이다.
- [[교환 논증]] - 그리디 선택의 정당성을 증명할 때 자주 사용하는 방법이다.
- [[Dijkstra 알고리즘]] - 음수 가중치가 없는 그래프에서 최단 경로를 구하는 대표적인 그리디 알고리즘이다.
- [[Kruskal 알고리즘]] - 가장 작은 간선을 선택해 최소 신장 트리를 만드는 그리디 알고리즘이다.
- [[Prim 알고리즘]] - 현재 트리에서 가장 가까운 정점을 확장하는 최소 신장 트리 알고리즘이다.
- [[Huffman Coding]] - 빈도가 낮은 노드를 반복 병합해 최적 접두어 코드를 만드는 그리디 알고리즘이다.
- [[활동 선택 문제]] - 종료 시간이 빠른 활동을 선택하는 전략으로 최적해를 구할 수 있는 대표 문제다.
- [[최소 신장 트리]] - Kruskal과 Prim 알고리즘의 대상이 되는 그래프 최적화 문제다.
