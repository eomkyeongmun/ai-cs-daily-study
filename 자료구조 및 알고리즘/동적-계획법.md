# 동적 계획법 - 메모이제이션, 타뷸레이션, 배낭 문제(Knapsack)

## 핵심 개념

동적 계획법(Dynamic Programming, DP)은 큰 문제를 여러 개의 작은 부분 문제로 나누어 풀되, **같은 부분 문제가 반복해서 등장할 때 그 결과를 저장해 재사용**하는 알고리즘 설계 패러다임이다. DP가 성립하려면 일반적으로 두 가지 성질이 필요하다. 첫째, **최적 부분 구조(Optimal Substructure)**, 즉 전체 문제의 최적해가 부분 문제의 최적해로부터 구성될 수 있어야 한다. 둘째, **중복 부분 문제(Overlapping Subproblems)**, 즉 재귀적으로 문제를 풀 때 동일한 부분 문제가 여러 번 계산되어야 한다.

DP의 목적은 단순 재귀나 완전 탐색에서 발생하는 지수적 중복 계산을 줄이는 것이다. 예를 들어 피보나치 수를 단순 재귀로 계산하면 같은 `fib(k)`가 반복 호출되지만, DP를 적용하면 한 번 계산한 값을 저장하여 재사용할 수 있다. 이때 대표적인 구현 방식이 **메모이제이션(Memoization)**과 **타뷸레이션(Tabulation)**이다. 메모이제이션은 재귀 기반의 하향식 방식이고, 타뷸레이션은 반복문 기반의 상향식 방식이다.

배낭 문제(Knapsack)는 DP의 대표적인 예제이다. 제한된 용량을 가진 배낭에 여러 물건을 넣어 가치의 합을 최대화하는 문제로, 특히 **0/1 배낭 문제**는 각 물건을 “넣거나 넣지 않거나” 한 번만 선택할 수 있다. 이 문제는 최적 부분 구조와 중복 부분 문제를 모두 가지므로 DP로 효율적으로 해결할 수 있다. DP는 알고리즘 면접, 최적화 문제, 데이터베이스 쿼리 최적화, 문자열 비교, 생물정보학 등 다양한 분야에서 핵심적인 사고 도구로 사용된다.

## 내부 동작 원리

동적 계획법은 보통 다음 절차로 설계한다.

1. **상태 정의**
   - 문제를 표현할 수 있는 부분 문제의 의미를 정한다.
   - 예: `dp[i][w]` = 첫 `i`개의 물건만 고려하고 배낭 용량이 `w`일 때 얻을 수 있는 최대 가치

2. **점화식 정의**
   - 현재 상태를 더 작은 상태들로 표현한다.
   - 0/1 배낭 문제의 경우:
     ```text
     물건 i의 무게 = weight[i]
     물건 i의 가치 = value[i]

     dp[i][w] =
       dp[i-1][w]                                      // i번째 물건을 넣지 않음
       max(dp[i-1][w], dp[i-1][w-weight[i]] + value[i]) // 넣을 수 있다면 선택 비교
     ```

3. **초기값 설정**
   - 물건이 없거나 용량이 0이면 얻을 수 있는 가치는 0이다.
   - `dp[0][w] = 0`
   - `dp[i][0] = 0`

4. **계산 순서 결정**
   - 메모이제이션: 필요한 상태를 재귀적으로 계산한다.
   - 타뷸레이션: 작은 상태부터 순서대로 테이블을 채운다.

5. **정답 추출**
   - 보통 최종 상태가 답이다.
   - 0/1 배낭 문제에서는 `dp[n][W]`

---

### 1. 메모이제이션

메모이제이션은 **하향식 DP**이다. 큰 문제에서 시작해 필요한 부분 문제를 재귀 호출로 계산하고, 계산 결과를 캐시에 저장한다.

예를 들어 피보나치 수열을 단순 재귀로 계산하면 다음과 같은 중복 호출이 발생한다.

```text
fib(5)
├─ fib(4)
│  ├─ fib(3)
│  │  ├─ fib(2)
│  │  └─ fib(1)
│  └─ fib(2)
└─ fib(3)
   ├─ fib(2)
   └─ fib(1)
```

여기서 `fib(3)`, `fib(2)`가 여러 번 계산된다. 메모이제이션을 사용하면 한 번 계산한 값을 저장한다.

```text
memo[3] = fib(3)
memo[2] = fib(2)

이후 fib(3), fib(2)가 다시 필요하면 재계산하지 않고 memo에서 반환
```

0/1 배낭 문제의 메모이제이션 의사코드는 다음과 같다.

```text
solve(i, w):
    if i == 0 or w == 0:
        return 0

    if memo[i][w] exists:
        return memo[i][w]

    if weight[i] > w:
        memo[i][w] = solve(i-1, w)
    else:
        memo[i][w] = max(
            solve(i-1, w),
            solve(i-1, w-weight[i]) + value[i]
        )

    return memo[i][w]
```

장점은 실제로 필요한 상태만 계산한다는 점이다. 반면 재귀 호출을 사용하므로 호출 스택이 깊어질 수 있고, 언어 또는 실행 환경에 따라 스택 오버플로우 문제가 발생할 수 있다.

### 2. 타뷸레이션

타뷸레이션은 **상향식 DP**이다. 작은 부분 문제부터 순서대로 테이블을 채워 나간다.

0/1 배낭 문제에서는 다음과 같은 2차원 테이블을 만든다.

```text
행 i: 고려한 물건 개수
열 w: 현재 배낭 용량

        w=0  w=1  w=2  w=3  ...  w=W
i=0      0    0    0    0        0
i=1      0   ...
i=2      0   ...
...
i=n      0   ...              정답
```

각 칸 `dp[i][w]`는 다음 두 선택 중 큰 값을 가진다.

```text
1. i번째 물건을 넣지 않는다.
   dp[i-1][w]

2. i번째 물건을 넣는다.
   dp[i-1][w-weight[i]] + value[i]
```

단, 두 번째 선택은 `weight[i] <= w`일 때만 가능하다.

의사코드는 다음과 같다.

```text
for i from 1 to n:
    for w from 0 to W:
        if weight[i] > w:
            dp[i][w] = dp[i-1][w]
        else:
            dp[i][w] = max(
                dp[i-1][w],
                dp[i-1][w-weight[i]] + value[i]
            )
```

시간 복잡도는 `O(nW)`, 공간 복잡도는 기본적으로 `O(nW)`이다. 여기서 `n`은 물건 수, `W`는 배낭 용량이다. 다만 `W`가 입력 크기의 숫자 값 자체이므로, 0/1 배낭 DP는 보통 **의사 다항 시간(pseudo-polynomial time)** 알고리즘으로 분류된다.

공간은 1차원 배열로 최적화할 수 있다.

```text
for i from 1 to n:
    for w from W down to weight[i]:
        dp[w] = max(dp[w], dp[w-weight[i]] + value[i])
```

0/1 배낭에서 용량 `w`를 큰 값에서 작은 값으로 순회하는 이유는 같은 물건이 한 번만 선택되도록 하기 위해서다. 만약 작은 용량에서 큰 용량으로 순회하면 현재 물건을 같은 반복에서 여러 번 사용하는 효과가 생길 수 있다. 이는 0/1 배낭이 아니라 무한 배낭 문제의 동작에 가까워진다.

---

### 3. 메모이제이션과 타뷸레이션 비교

| 구분 | 메모이제이션 | 타뷸레이션 |
|---|---|---|
| 방향 | Top-down | Bottom-up |
| 구현 방식 | 재귀 + 캐시 | 반복문 + 테이블 |
| 계산 상태 | 필요한 상태만 계산 | 정의한 범위 대부분 계산 |
| 장점 | 점화식을 자연스럽게 표현 | 스택 오버플로우 위험이 적음 |
| 단점 | 재귀 깊이 문제 가능 | 불필요한 상태도 계산할 수 있음 |
| 대표 사용 | DFS형 문제, 상태 공간이 희소한 문제 | 순서가 명확한 최적화 문제 |

## 실제 시스템 연결

동적 계획법은 특정 운영체제나 웹 서버에서 항상 명시적으로 드러나는 기능이라기보다는, **최적화 알고리즘, 문자열 처리, 데이터베이스 쿼리 계획, 리소스 할당 도구** 내부에서 자주 사용되는 설계 방식이다.

1. **데이터베이스 쿼리 최적화**
   - 관계형 데이터베이스의 조인 순서 최적화는 DP와 밀접하다.
   - 여러 테이블을 조인할 때 가능한 조인 순서가 매우 많기 때문에, 옵티마이저는 부분 집합에 대한 최적 조인 계획을 계산하고 이를 조합한다.
   - PostgreSQL은 조인 수가 일정 범위 안에 있을 때 동적 계획법 기반의 탐색을 사용하고, 조인 수가 많아지면 유전 알고리즘 기반 탐색을 사용할 수 있다.
   - AWS RDS for PostgreSQL, Google Cloud SQL for PostgreSQL처럼 관리형 PostgreSQL 서비스를 사용할 때도 이러한 쿼리 옵티마이저 개념이 적용된다.

2. **문자열 비교와 편집 거리**
   - Levenshtein distance 같은 편집 거리 알고리즘은 대표적인 DP 사례이다.
   - 오타 교정, 유사 문자열 검색, 데이터 정제, 중복 레코드 탐지 등에 활용된다.
   - 예를 들어 두 문자열 `kitten`, `sitting`의 차이를 삽입, 삭제, 치환 연산으로 계산하는 문제는 2차원 DP 테이블로 해결할 수 있다.

3. **생물정보학**
   - DNA, RNA, 단백질 서열 정렬에는 DP가 많이 사용된다.
   - Needleman-Wunsch 알고리즘은 전역 정렬, Smith-Waterman 알고리즘은 지역 정렬에 사용되는 대표적인 DP 기반 알고리즘이다.
   - 대규모 서열 분석 시스템에서는 DP의 계산량이 크기 때문에 병렬화, SIMD, GPU 가속 등이 함께 고려된다.

4. **리소스 선택과 예산 최적화**
   - 제한된 예산, CPU, 메모리, 저장소 용량 안에서 최대 효용을 얻는 문제는 배낭 문제와 유사하게 모델링할 수 있다.
   - 예: 제한된 비용 안에서 어떤 작업을 실행할지 선택, 제한된 캐시 공간에 어떤 데이터를 유지할지 결정, 제한된 광고 예산을 어떤 캠페인에 배분할지 결정.
   - 단, 실제 대규모 시스템에서는 입력 크기와 실시간 제약 때문에 순수 DP 대신 휴리스틱, 근사 알고리즘, 선형계획법, 정수계획법 등이 함께 사용될 수 있다.

5. **Nginx, Linux와의 관계**
   - Nginx 자체의 핵심 구조는 이벤트 기반 비동기 I/O와 워커 프로세스 모델에 가깝고, 동적 계획법이 주요 설계 원리라고 보기는 어렵다.
   - Linux 커널의 스케줄러나 메모리 관리 역시 일반적으로 온라인 환경에서 빠른 결정을 내려야 하므로 전형적인 DP 테이블을 직접 구성하는 방식과는 다르다.
   - 다만 Linux 환경에서 실행되는 데이터베이스, 최적화 도구, 생물정보학 도구, 문자열 분석 도구 내부에서는 DP가 널리 사용될 수 있다.

## 클라우드 연결

클라우드 환경에서 동적 계획법은 주로 **배치 계산, 최적화 작업, 비용 최적화, 리소스 선택 문제**와 연결된다.

1. **Docker 컨테이너에서 DP 작업 실행**
   - DP 알고리즘은 상태 테이블을 많이 사용하므로 메모리 사용량이 커질 수 있다.
   - Docker 컨테이너에서 실행할 때는 메모리 제한을 명확히 설정해야 한다.
   - 예를 들어 `O(nW)` 크기의 배낭 DP 테이블은 `n`과 `W`가 커질수록 컨테이너 메모리를 빠르게 소모할 수 있다.
   - 컨테이너가 메모리 제한을 초과하면 프로세스가 종료될 수 있으므로, 1차원 DP 최적화나 입력 제한이 중요하다.

2. **Kubernetes와 배치 작업**
   - Kubernetes에서 DP 알고리즘은 `Job` 또는 `CronJob` 형태로 실행할 수 있다.
   - 예: 매일 새벽 비용 최적화 계산, 재고 배분 계산, 추천 후보 조합 계산 등을 컨테이너로 실행.
   - DP 작업은 CPU와 메모리 사용량이 예측 가능한 경우가 많으므로 `resources.requests`와 `resources.limits`를 적절히 지정하는 것이 중요하다.
   - Kubernetes 스케줄러 자체는 일반적으로 실시간 클러스터 상태를 바탕으로 휴리스틱과 점수화 방식을 사용하며, 전형적인 배낭 DP를 그대로 수행한다고 보기는 어렵다.

3. **AWS와의 연관성**
   - AWS Batch, ECS, EKS에서는 대규모 DP 기반 최적화 작업을 컨테이너 단위로 실행할 수 있다.
   - S3에 입력 데이터를 저장하고, Batch 또는 EKS에서 계산한 뒤 결과를 다시 S3나 데이터베이스에 저장하는 구조가 가능하다.
   - AWS Lambda에서도 작은 규모의 DP 계산은 가능하지만, 실행 시간, 메모리, 패키지 크기 등 서버리스 환경의 제약을 고려해야 한다.

4. **GCP와의 연관성**
   - Google Kubernetes Engine, Cloud Run, Batch 등의 환경에서 DP 기반 계산 작업을 실행할 수 있다.
   - Google OR-Tools는 조합 최적화 문제를 해결하기 위한 도구이며, 배낭 문제와 같은 최적화 문제를 다룰 수 있다.
   - OR-Tools 기반 최적화 애플리케이션을 컨테이너화하여 GKE나 Cloud Run에서 실행하는 방식은 실무적으로 자연스럽다.

5. **클라우드 비용 최적화와 배낭 문제**
   - 제한된 예산 안에서 어떤 인스턴스, 스토리지, 작업, 기능을 선택할지 결정하는 문제는 배낭 문제와 유사하게 모델링할 수 있다.
   - 예:
     ```text
     용량 W = 월간 예산
     물건 = 실행 가능한 작업 또는 서비스 옵션
     무게 = 비용
     가치 = 기대 효과, 처리량, 비즈니스 가치
     목표 = 예산 안에서 가치 최대화
     ```
   - 다만 실제 클라우드 비용 최적화는 할인 정책, 예약 인스턴스, 스팟 인스턴스, 네트워크 비용, 가용성 요구사항 등 복잡한 제약이 많으므로 단순 0/1 배낭 모델만으로 충분하지 않을 수 있다.

## 보안 연결

동적 계획법은 보안 알고리즘 자체라기보다는 계산 패턴이지만, 실제 시스템에 적용할 때 여러 보안 이슈와 연결된다.

1. **알고리즘 복잡도 기반 DoS**
   - DP 테이블 크기는 입력 크기에 따라 급격히 커질 수 있다.
   - 예를 들어 0/1 배낭의 `O(nW)` 알고리즘에서 사용자가 매우 큰 `W`를 입력할 수 있다면 서버 메모리와 CPU를 과도하게 사용하게 만들 수 있다.
   - 문자열 편집 거리 DP도 두 문자열 길이가 각각 `m`, `n`이면 `O(mn)` 메모리 또는 시간이 필요할 수 있다.
   - 공격자가 매우 긴 문자열을 보내면 API 서버가 과도한 계산을 수행할 수 있다.

   모범 사례:
   - 입력 크기 제한
   - 요청당 시간 제한
   - 메모리 제한
   - 비동기 배치 처리
   - 근사 알고리즘 또는 조기 종료 조건 사용

2. **메모이제이션 캐시의 메모리 고갈**
   - 메모이제이션은 계산 결과를 캐시에 저장한다.
   - 사용자 입력이 다양한 상태를 무한히 생성할 수 있다면 캐시가 계속 커질 수 있다.
   - 특히 웹 서버나 API 서버에서 전역 캐시에 메모이제이션 결과를 저장하면 메모리 누수와 유사한 문제가 발생할 수 있다.

   모범 사례:
   - LRU 캐시 사용
   - TTL 설정
   - 사용자별 캐시 격리
   - 최대 캐시 크기 제한
   - 요청 범위 내 캐시 사용

3. **멀티테넌트 환경의 데이터 누출**
   - 클라우드 환경에서 여러 사용자 또는 테넌트가 같은 애플리케이션을 사용할 때, 메모이제이션 캐시 키 설계가 부정확하면 다른 사용자의 계산 결과가 노출될 수 있다.
   - 예를 들어 캐시 키에 사용자 ID, 권한 범위, 입력 파라미터가 충분히 포함되지 않으면 잘못된 결과가 반환될 수 있다.

   모범 사례:
   - 캐시 키에 보안 경계 포함
   - 사용자별 네임스페이스 분리
   - 민감 정보 캐싱 금지 또는 암호화
   - 권한 검사를 캐시 조회 전후에 수행

4. **정수 오버플로우**
   - 배낭 문제에서 가치 합계가 커질 경우 정수 오버플로우가 발생할 수 있다.
   - C/C++ 같은 언어에서는 정수 오버플로우가 치명적인 버그로 이어질 수 있다.
   - 비용, 가치, 점수, 경로 수를 계산하는 DP에서는 자료형 범위를 신중히 선택해야 한다.

   모범 사례:
   - 충분히 큰 정수 타입 사용
   - 오버플로우 검사
   - 입력 값 검증
   - 언어별 안전 연산 활용

5. **타이밍 및 사이드 채널 가능성**
   - DP 알고리즘이 입력 값에 따라 계산 경로, 캐시 적중률, 실행 시간이 달라질 수 있다.
   - 일반적인 최적화 문제에서는 큰 문제가 아닐 수 있지만, 암호학적 비밀 값과 연결된 계산이라면 실행 시간 차이가 정보 누출로 이어질 수 있다.

   모범 사례:
   - 비밀 값 기반 분기 최소화
   - 상수 시간 알고리즘 고려
   - 민감 데이터에 대한 캐시 사용 신중화

## 면접 질문

**Q1. 동적 계획법이 적용되기 위한 조건은 무엇인가요?**  
> 핵심 답변: 최적 부분 구조와 중복 부분 문제가 필요하다. 최적 부분 구조는 전체 최적해가 부분 문제의 최적해로 구성되는 성질이고, 중복 부분 문제는 같은 부분 문제가 반복 계산되는 성질이다.

**Q2. 메모이제이션과 타뷸레이션의 차이는 무엇인가요?**  
> 핵심 답변: 메모이제이션은 재귀 기반 Top-down 방식으로 필요한 상태만 계산하고 캐시에 저장한다. 타뷸레이션은 반복문 기반 Bottom-up 방식으로 작은 상태부터 테이블을 채운다. 메모이제이션은 재귀 스택 문제가 있을 수 있고, 타뷸레이션은 불필요한 상태도 계산할 수 있다.

**Q3. 0/1 배낭 문제의 DP 상태와 점화식을 설명해보세요.**  
> 핵심 답변: `dp[i][w]`를 첫 `i`개 물건을 고려하고 용량이 `w`일 때의 최대 가치로 정의한다. `i`번째 물건을 넣지 않으면 `dp[i-1][w]`, 넣으면 `dp[i-1][w-weight[i]] + value[i]`이다. 둘 중 큰 값을 선택한다.

**Q4. 0/1 배낭 문제에서 1차원 DP를 사용할 때 용량을 큰 값에서 작은 값으로 순회하는 이유는 무엇인가요?**  
> 핵심 답변: 같은 물건을 한 번만 사용하기 위해서다. 작은 용량에서 큰 용량으로 순회하면 현재 물건으로 갱신된 값을 다시 참조하여 같은 물건을 여러 번 선택하는 결과가 될 수 있다.

**Q5. 배낭 문제 DP의 시간 복잡도 `O(nW)`가 완전한 다항 시간 알고리즘이라고 보기 어려운 이유는 무엇인가요?**  
> 핵심 답변: `W`는 입력 길이가 아니라 입력 값 자체이다. `W`가 매우 큰 숫자이면 입력을 표현하는 비트 수에 비해 실행 시간이 매우 커질 수 있다. 따라서 0/1 배낭의 기본 DP는 의사 다항 시간 알고리즘으로 분류된다.
