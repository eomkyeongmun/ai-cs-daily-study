# 그래프 - 인접 행렬 vs 인접 리스트, 방향/무방향 그래프

## 핵심 개념

그래프(Graph)는 정점(Vertex, Node)과 간선(Edge)으로 구성된 자료구조로, 객체들 사이의 관계를 표현하는 데 사용된다. 예를 들어 컴퓨터 네트워크의 장비 연결, SNS의 친구 관계, 지도에서 도시와 도로, Kubernetes 리소스 간 의존성, 패키지 의존성 그래프 등이 모두 그래프로 모델링될 수 있다. 그래프는 간선의 방향성에 따라 **방향 그래프(Directed Graph)** 와 **무방향 그래프(Undirected Graph)** 로 나뉜다. 방향 그래프는 `A → B`처럼 관계의 방향이 존재하며, 웹 페이지 링크, 작업 의존성, 팔로우 관계처럼 한쪽 방향의 의미가 중요한 경우에 사용된다. 무방향 그래프는 `A — B`처럼 양방향 관계를 나타내며, LAN 연결, 친구 관계, 도로망 일부처럼 상호 연결성을 표현할 때 적합하다.

그래프를 메모리에 저장하는 대표적인 방식은 **인접 행렬(Adjacency Matrix)** 과 **인접 리스트(Adjacency List)** 이다. 인접 행렬은 `V x V` 크기의 2차원 배열을 사용하여 정점 간 연결 여부를 저장한다. 두 정점이 연결되어 있는지 확인하는 연산이 빠르다는 장점이 있지만, 간선 수가 적은 희소 그래프에서는 메모리 낭비가 크다. 반면 인접 리스트는 각 정점마다 연결된 정점 목록을 저장하므로 간선 수에 비례해 공간을 사용한다. 따라서 실제 시스템에서 등장하는 대규모 네트워크, 의존성 그래프, 소셜 그래프처럼 정점 수는 많지만 모든 정점이 서로 연결되어 있지는 않은 경우에는 인접 리스트가 자주 사용된다.

그래프 표현 방식의 선택은 알고리즘 성능에 직접적인 영향을 준다. BFS, DFS, 최단 경로, 위상 정렬, 최소 신장 트리 같은 알고리즘은 그래프 저장 방식에 따라 시간·공간 복잡도가 달라질 수 있다. 따라서 그래프의 밀도, 정점 수, 간선 수, 간선 존재 여부 조회 빈도, 모든 이웃 순회 빈도 등을 고려해 적절한 표현을 선택하는 것이 중요하다.

## 내부 동작 원리

## 1. 방향 그래프와 무방향 그래프

그래프 `G = (V, E)`에서 `V`는 정점 집합, `E`는 간선 집합이다.

### 방향 그래프

방향 그래프에서는 간선이 순서쌍으로 표현된다.

```text
A → B
```

이는 `A`에서 `B`로 갈 수 있음을 의미하지만, 반드시 `B`에서 `A`로 갈 수 있다는 뜻은 아니다.

예시:

```text
A → B → C
↑       ↓
└────── D
```

간선 집합은 다음처럼 표현할 수 있다.

```text
E = {(A, B), (B, C), (C, D), (D, A)}
```

방향 그래프에서는 각 정점에 대해 다음 개념이 중요하다.

- **진출 차수(out-degree)**: 해당 정점에서 나가는 간선 수
- **진입 차수(in-degree)**: 해당 정점으로 들어오는 간선 수

예를 들어 `A → B`에서는 `A`의 out-degree가 1 증가하고, `B`의 in-degree가 1 증가한다.

### 무방향 그래프

무방향 그래프에서는 간선에 방향이 없다.

```text
A — B
```

이는 `A`와 `B`가 서로 연결되어 있음을 의미한다.

예시:

```text
A — B
|   |
D — C
```

간선 집합은 다음처럼 표현할 수 있다.

```text
E = {{A, B}, {B, C}, {C, D}, {D, A}}
```

무방향 그래프에서는 `A — B`가 곧 `A → B`와 `B → A` 양쪽 연결처럼 동작한다고 볼 수 있다. 따라서 자료구조에 저장할 때도 양쪽 정점에 모두 정보를 저장하는 경우가 많다.

## 2. 인접 행렬

인접 행렬은 정점 수가 `V`개일 때 `V x V` 크기의 2차원 배열을 사용한다.

예를 들어 정점이 `A, B, C, D`이고 다음과 같은 무방향 그래프가 있다고 하자.

```text
A — B
|   |
D — C
```

정점 순서를 `[A, B, C, D]`로 두면 인접 행렬은 다음과 같다.

```text
    A B C D
A [ 0 1 0 1 ]
B [ 1 0 1 0 ]
C [ 0 1 0 1 ]
D [ 1 0 1 0 ]
```

`matrix[A][B] = 1`은 `A`와 `B`가 연결되어 있음을 의미한다. 무방향 그래프에서는 `matrix[A][B]`와 `matrix[B][A]`가 대칭이다.

방향 그래프 예시는 다음과 같다.

```text
A → B
B → C
D → A
```

인접 행렬:

```text
    A B C D
A [ 0 1 0 0 ]
B [ 0 0 1 0 ]
C [ 0 0 0 0 ]
D [ 1 0 0 0 ]
```

방향 그래프에서는 `matrix[A][B] = 1`이어도 `matrix[B][A] = 1`이라고 할 수 없다.

### 인접 행렬 특징

| 연산 | 시간 복잡도 |
|---|---|
| 두 정점 `u, v`의 연결 여부 확인 | `O(1)` |
| 한 정점의 모든 이웃 탐색 | `O(V)` |
| 모든 간선 순회 | `O(V^2)` |
| 공간 복잡도 | `O(V^2)` |

인접 행렬은 간선 존재 여부를 자주 확인해야 하는 경우 유리하다. 예를 들어 `u`와 `v`가 연결되어 있는지 매우 빈번하게 질의하는 문제에서는 `O(1)` 조회가 강점이다. 그러나 정점 수가 커지면 실제 간선 수와 관계없이 항상 `V^2` 공간이 필요하므로 대규모 희소 그래프에는 부적합할 수 있다.

---

## 3. 인접 리스트

인접 리스트는 각 정점마다 연결된 이웃 정점 목록을 저장한다.

무방향 그래프:

```text
A — B
|   |
D — C
```

인접 리스트 표현:

```text
A: B, D
B: A, C
C: B, D
D: A, C
```

방향 그래프:

```text
A → B
B → C
D → A
```

인접 리스트 표현:

```text
A: B
B: C
C:
D: A
```

방향 그래프에서는 나가는 간선을 기준으로 리스트를 구성하는 경우가 일반적이다. 필요하다면 들어오는 간선을 빠르게 찾기 위해 역방향 인접 리스트를 별도로 유지할 수도 있다.

### 인접 리스트 특징

| 연산 | 시간 복잡도 |
|---|---|
| 두 정점 `u, v`의 연결 여부 확인 | 일반적으로 `O(deg(u))` |
| 한 정점의 모든 이웃 탐색 | `O(deg(u))` |
| 모든 간선 순회 | `O(V + E)` |
| 공간 복잡도 | `O(V + E)` |

여기서 `deg(u)`는 정점 `u`의 차수이다. 방향 그래프에서는 보통 out-degree를 의미한다.

인접 리스트는 간선 수가 정점 수의 제곱보다 훨씬 작은 희소 그래프에 적합하다. BFS와 DFS처럼 “현재 정점의 이웃을 순회”하는 알고리즘에서는 인접 리스트가 효율적이다.

## 4. 가중치 그래프 표현

간선에 비용, 거리, 지연 시간 같은 값이 붙으면 가중치 그래프가 된다.

예시:

```text
A --5-- B
A --2-- C
B --1-- C
```

인접 행렬에서는 연결이 없음을 `0`, `INF`, `null` 등으로 표현하고, 연결이 있으면 가중치를 저장한다.

```text
    A B C
A [ 0 5 2 ]
B [ 5 0 1 ]
C [ 2 1 0 ]
```

인접 리스트에서는 `(이웃 정점, 가중치)` 쌍을 저장한다.

```text
A: (B, 5), (C, 2)
B: (A, 5), (C, 1)
C: (A, 2), (B, 1)
```

최단 경로 알고리즘인 Dijkstra, Bellman-Ford, Floyd-Warshall 등은 그래프 표현 방식에 따라 구현과 성능 특성이 달라질 수 있다.

## 실제 시스템 연결

## 1. Linux와 그래프

Linux 시스템에서는 여러 구조가 그래프로 해석될 수 있다.

### 파일 시스템 디렉터리 구조

일반적인 디렉터리 구조는 트리처럼 보이지만, 심볼릭 링크를 포함하면 그래프 형태가 될 수 있다.

```text
/home/user/project → /var/www/project
```

심볼릭 링크가 순환 구조를 만들 수도 있기 때문에 파일 탐색 도구나 백업 도구는 순환 참조를 주의해야 한다. 이때 방문한 경로 또는 inode를 기록하는 방식은 그래프 탐색의 방문 배열과 유사하다.

### 프로세스 관계

Linux 프로세스는 부모-자식 관계를 가진다. 기본적으로는 트리 구조로 볼 수 있지만, 프로세스 간 통신, 소켓 연결, 파일 디스크립터 공유 등을 포함하면 더 복잡한 그래프 모델로 해석할 수 있다.

예를 들어 `pstree`는 부모-자식 프로세스 관계를 트리 형태로 보여준다. 반면 네트워크 연결까지 포함하면 프로세스와 포트, 소켓, 원격 호스트 사이의 관계 그래프를 생각할 수 있다.

---

## 2. Nginx와 그래프

Nginx의 설정은 요청 라우팅 그래프로 해석할 수 있다.

예를 들어 다음 흐름을 생각할 수 있다.

```text
Client
  ↓
Nginx server block
  ↓
location /api
  ↓
upstream backend
  ↓
Application Server
```

여기서 각 구성 요소를 정점으로 보고 요청 전달 관계를 방향 간선으로 볼 수 있다. 특히 리버스 프록시 환경에서는 요청이 `Client → Nginx → Backend` 방향으로 흐르며, 장애 분석 시 어느 정점에서 병목이나 오류가 발생했는지 추적하는 것이 중요하다.

로드 밸런싱 대상 서버 목록은 인접 리스트와 유사하게 볼 수 있다.

```text
upstream api_backend:
  - app1
  - app2
  - app3
```

Nginx는 실제로 그래프 자료구조만으로 동작한다고 단정할 수는 없지만, 요청 경로와 의존성을 그래프로 모델링하면 시스템 구조를 이해하고 장애 전파를 분석하는 데 도움이 된다.

---

## 3. AWS와 그래프

AWS 환경에서는 리소스 간 관계를 그래프로 이해하는 경우가 많다.

예를 들어 VPC 네트워크는 다음과 같은 구성 요소 관계를 가진다.

```text
VPC
 ├─ Subnet
 │   ├─ EC2
 │   └─ NAT Gateway
 ├─ Internet Gateway
 └─ Route Table
```

라우팅 관점에서는 다음과 같은 방향 그래프로 볼 수 있다.

```text
EC2 → Route Table → NAT Gateway → Internet
EC2 → Route Table → Internet Gateway → Internet
```

보안 그룹(Security Group) 규칙도 그래프적으로 해석할 수 있다. 예를 들어 `web-sg`가 `app-sg`로 8080 포트 접근을 허용하고, `app-sg`가 `db-sg`로 3306 포트 접근을 허용한다면 다음과 같은 방향 그래프가 된다.

```text
web-sg → app-sg → db-sg
```

이러한 그래프 모델은 네트워크 접근 경로 분석, 최소 권한 원칙 검토, 의도하지 않은 외부 노출 탐지에 유용하다.

---

## 4. GCP와 그래프

GCP에서도 VPC, 서브넷, 방화벽 규칙, Compute Engine 인스턴스, Cloud Load Balancing, GKE 클러스터 간 관계를 그래프로 볼 수 있다.

예시:

```text
Client
  ↓
Cloud Load Balancer
  ↓
Backend Service
  ↓
Instance Group or NEG
  ↓
Compute Engine / GKE Pod
```

방화벽 규칙은 특정 소스에서 특정 대상 태그 또는 서비스 계정으로의 접근 허용·차단 관계를 나타낸다. 따라서 보안 분석에서는 “어떤 노드가 어떤 노드에 접근 가능한가?”라는 그래프 탐색 문제가 된다.

## 클라우드 연결

## 1. Docker 네트워크와 그래프

Docker에서 컨테이너, 브리지 네트워크, 호스트 네트워크 인터페이스는 그래프 형태로 모델링할 수 있다.

```text
container-a
     |
docker bridge network
     |
container-b
```

동일한 Docker bridge 네트워크에 연결된 컨테이너들은 네트워크 설정에 따라 서로 통신할 수 있다. 이때 컨테이너를 정점, 네트워크 연결을 간선으로 보면 컨테이너 간 연결성을 분석할 수 있다.

Docker Compose 환경에서는 서비스 간 의존성도 방향 그래프로 표현할 수 있다.

```text
web → api → db
```

다만 `depends_on`은 컨테이너 시작 순서와 관련된 기능이며, 애플리케이션이 실제로 준비되었는지를 보장하는 것은 아니다. 준비 상태까지 고려하려면 healthcheck 같은 메커니즘이 필요하다.

---

## 2. Kubernetes와 그래프

Kubernetes는 그래프 개념과 매우 밀접하다. Pod, Service, EndpointSlice, Deployment, ReplicaSet, Node, ConfigMap, Secret 등 다양한 리소스가 서로 관계를 가진다.

예시:

```text
Deployment
   ↓ owns
ReplicaSet
   ↓ owns
Pod
   ↓ selected by
Service
   ↓ routes to
EndpointSlice
```

Kubernetes의 OwnerReference는 리소스 간 소유 관계를 표현한다. 이 관계는 방향 그래프로 볼 수 있으며, Garbage Collection 동작에 영향을 준다. 예를 들어 Deployment가 ReplicaSet을 소유하고, ReplicaSet이 Pod를 소유하는 구조에서는 상위 리소스 삭제 시 하위 리소스 정리 정책과 연결된다.

또한 Kubernetes 네트워크 정책(NetworkPolicy)은 Pod 간 통신 허용 관계를 방향 그래프로 표현할 수 있다.

```text
frontend Pod → backend Pod → database Pod
```

기본적으로 어떤 Pod가 어떤 Pod에 접근할 수 있는지 판단하는 문제는 그래프의 도달 가능성 문제와 유사하다.

---

## 3. AWS 서비스와 그래프

AWS에서는 다음과 같은 서비스들이 그래프 모델과 연결된다.

### VPC Reachability Analyzer

AWS VPC Reachability Analyzer는 VPC 내 네트워크 경로의 도달 가능성을 분석하는 기능이다. 소스와 대상 사이의 경로를 분석한다는 점에서 그래프 탐색과 유사한 개념으로 이해할 수 있다.

```text
EC2 → Security Group → Route Table → NAT Gateway → Internet Gateway
```

### IAM 정책 관계

IAM 사용자, 역할, 정책, 리소스 간 관계도 방향 그래프로 볼 수 있다.

```text
User → assumes Role → has Policy → allows Action → Resource
```

권한 분석은 “이 주체가 이 리소스에 특정 작업을 수행할 수 있는가?”라는 그래프 기반 추론 문제로 볼 수 있다.

### AWS Step Functions

AWS Step Functions의 상태 머신은 상태와 전이를 가진 방향 그래프다.

```text
Start → Validate → Process → Success
                  ↘ Failure
```

각 상태는 정점, 상태 전이는 방향 간선으로 볼 수 있다. 순환 구조, 분기, 병렬 처리, 실패 처리 등을 명시적으로 모델링할 수 있다.

---

## 4. 클라우드 운영에서 인접 행렬과 인접 리스트 선택

클라우드 리소스 관계는 보통 매우 큰 희소 그래프인 경우가 많다. 예를 들어 수많은 리소스가 존재해도 모든 리소스가 서로 연결되어 있지는 않다. 따라서 리소스 의존성, 네트워크 연결, 권한 관계를 저장하고 분석할 때는 인접 리스트 방식이 메모리 효율적이다.

반면 다음과 같은 경우에는 인접 행렬 또는 비트셋 기반 표현이 유리할 수 있다.

- 특정 두 리소스 간 연결 여부를 매우 빠르게 확인해야 하는 경우
- 정점 수가 비교적 작고 그래프가 조밀한 경우
- 접근 가능성 행렬이나 전이 폐쇄를 계산하는 경우
- Floyd-Warshall처럼 행렬 기반 알고리즘을 사용하는 경우

## 보안 연결

## 1. 공격 경로 분석

보안에서 그래프는 공격 경로를 분석하는 데 자주 사용된다. 시스템, 계정, 권한, 네트워크 연결, 취약점을 정점과 간선으로 표현하면 공격자가 어떤 경로로 중요 자산에 도달할 수 있는지 분석할 수 있다.

예시:

```text
Internet
  ↓
Public Web Server
  ↓
App Server
  ↓
Database
```

만약 Web Server가 외부에 노출되어 있고, App Server로 접근 가능하며, App Server가 Database에 과도한 권한을 가진다면 공격자는 단계적으로 내부 자산에 접근할 수 있다. 이 구조는 방향 그래프의 도달 가능성 문제로 볼 수 있다.

---

## 2. 권한 그래프와 최소 권한 원칙

IAM, RBAC, ACL 같은 권한 시스템은 그래프로 모델링할 수 있다.

```text
User → Role → Permission → Resource
```

보안 모범 사례는 다음과 같다.

- 불필요한 간선을 제거한다.
- 즉, 불필요한 권한 부여를 제거한다.
- 외부에서 내부 중요 자산으로 이어지는 경로를 최소화한다.
- 관리자 권한으로 이어지는 우회 경로를 점검한다.
- 역할 간 신뢰 관계를 주기적으로 검토한다.

특히 클라우드 IAM에서는 직접 권한뿐 아니라 역할 위임, 리소스 기반 정책, 그룹 멤버십 등을 함께 고려해야 한다. 단순히 한 정책만 보는 것이 아니라 전체 권한 그래프를 분석해야 실제 접근 가능성을 이해할 수 있다.

---

## 3. 네트워크 세그멘테이션

네트워크 보안에서는 서비스 간 연결을 제한하는 것이 중요하다. 모든 서비스가 서로 통신 가능한 완전 그래프에 가까운 구조는 침해 발생 시 횡적 이동(lateral movement)을 쉽게 만든다.

안전한 구조는 필요한 방향의 간선만 허용하는 방식이다.

```text
frontend → backend → database
```

반대로 다음과 같은 구조는 위험할 수 있다.

```text
frontend ↔ backend ↔ database
frontend ↔ database
```

특히 데이터베이스는 일반적으로 프론트엔드에서 직접 접근하지 못하도록 제한하는 것이 권장된다. Kubernetes NetworkPolicy, AWS Security Group, GCP Firewall Rule 등을 사용해 필요한 통신만 허용하는 것이 좋다.

---

## 4. 순환 의존성과 장애 전파

그래프에서 순환(cycle)은 보안과 운영 안정성 측면에서 문제를 만들 수 있다.

예시:

```text
Service A → Service B → Service C → Service A
```

이런 순환 의존성은 장애 전파, 배포 순서 문제, 인증 토큰 발급 의존성 문제를 유발할 수 있다. 보안 시스템에서도 인증 서비스, 정책 엔진, 로깅 시스템이 서로 강하게 의존하면 장애 발생 시 복구가 어려워질 수 있다.

의존성 그래프를 분석해 순환을 줄이고, 핵심 보안 컴포넌트는 단일 장애점이 되지 않도록 설계하는 것이 중요하다.

---

## 5. 그래프 탐색 기반 취약점

그래프 탐색을 사용하는 시스템에서는 다음과 같은 문제가 발생할 수 있다.

- 방문 처리 누락으로 인한 무한 루프
- 악의적으로 큰 그래프 입력으로 인한 자원 고갈
- 깊은 재귀 DFS로 인한 스택 오버플로우
- 순환 참조를 이용한 파서 또는 크롤러 공격
- 권한 그래프 해석 오류로 인한 과도한 접근 허용

모범 사례:

- 방문 집합을 명확히 관리한다.
- 입력 그래프의 크기 제한을 둔다.
- 재귀 대신 반복 기반 DFS/BFS를 고려한다.
- 권한 그래프는 deny/allow 우선순위를 명확히 정의한다.
- 보안 그룹, 방화벽 규칙, IAM 정책의 실제 도달 가능성을 주기적으로 검증한다.

## 면접 질문

**Q1. 인접 행렬과 인접 리스트의 차이는 무엇인가요?**  
> 핵심 답변: 인접 행렬은 `V x V` 배열로 간선 존재 여부를 저장하며 연결 여부 확인이 `O(1)`로 빠르지만 공간 복잡도가 `O(V^2)`이다. 인접 리스트는 각 정점의 이웃 목록을 저장하며 공간 복잡도가 `O(V + E)`로 희소 그래프에 효율적이고, 이웃 순회가 빠르다.

**Q2. 무방향 그래프를 인접 리스트로 저장할 때 주의할 점은 무엇인가요?**  
> 핵심 답변: 간선 `u — v`가 있으면 `u`의 리스트에 `v`를 추가하고, `v`의 리스트에도 `u`를 추가해야 한다. 즉 하나의 무방향 간선이 저장 구조에서는 양쪽에 반영된다. 간선 개수를 셀 때 중복 계산하지 않도록 주의해야 한다.

**Q3. 방향 그래프에서 in-degree와 out-degree는 무엇인가요?**  
> 핵심 답변: out-degree는 특정 정점에서 나가는 간선 수이고, in-degree는 해당 정점으로 들어오는 간선 수이다. 위상 정렬, 의존성 분석, 웹 링크 분석, 작업 스케줄링 등에서 중요하게 사용된다.

**Q4. 정점 수가 매우 많고 간선 수가 상대적으로 적은 그래프에서는 어떤 표현이 적합한가요?**  
> 핵심 답변: 인접 리스트가 적합하다. 희소 그래프에서는 인접 행렬이 실제 간선이 거의 없어도 `O(V^2)` 공간을 사용하므로 비효율적이다. 인접 리스트는 실제 정점과 간선 수에 비례하는 `O(V + E)` 공간을 사용한다.

**Q5. BFS나 DFS를 구현할 때 인접 행렬과 인접 리스트의 시간 복잡도 차이는 어떻게 되나요?**  
> 핵심 답변: 인접 리스트를 사용하면 모든 정점과 간선을 한 번씩 탐색하므로 일반적으로 `O(V + E)`이다. 인접 행렬을 사용하면 각 정점에서 모든 정점에 대해 연결 여부를 확인해야 하므로 `O(V^2)`가 된다. 그래프가 조밀하면 차이가 작을 수 있지만, 희소 그래프에서는 인접 리스트가 훨씬 효율적이다.

## 관련 개념

- [[BFS]] - 그래프에서 가까운 정점부터 탐색하는 대표적인 너비 우선 탐색 알고리즘이다.
- [[DFS]] - 그래프의 경로를 깊게 따라가며 탐색하는 깊이 우선 탐색 알고리즘이다.
- [[위상 정렬]] - 방향 비순환 그래프에서 의존성 순서를 구하는 알고리즘이다.
- [[DAG]] - 사이클이 없는 방향 그래프로 작업 스케줄링과 빌드 의존성 분석에 사용된다.
- [[최단 경로 알고리즘]] - 그래프에서 두 정점 사이의 최소 비용 경로를 찾는 알고리즘 집합이다.
- [[Dijkstra 알고리즘]] - 음수가 아닌 가중치를 가진 그래프에서 단일 시작점 최단 경로를 구하는 알고리즘이다.
- [[Floyd-Warshall 알고리즘]] - 모든 정점 쌍 사이의 최단 경로를 구하는 행렬 기반 알고리즘이다.
- [[Union-Find]] - 무방향 그래프의 연결 요소나 사이클 판별에 자주 사용되는 자료구조이다.
- [[최소 신장 트리]] - 무방향 가중치 그래프에서 모든 정점을 최소 비용으로 연결하는 트리이다.
- [[그래프 순환 탐지]] - 방향/무방향 그래프에서 사이클 존재 여부를 확인하는 기법이다.
