# 정렬 - 버블, 선택, 삽입, 병합, 퀵, 힙 정렬의 원리와 복잡도 비교

## 핵심 개념

정렬(Sorting)은 주어진 데이터 집합을 특정 기준, 예를 들어 숫자 오름차순, 문자열 사전순, 시간순, 우선순위순 등으로 재배열하는 알고리즘 문제이다. 정렬은 자료구조 및 알고리즘에서 가장 기본적이면서도 중요한 주제 중 하나다. 그 이유는 정렬된 데이터가 탐색, 중복 제거, 병합, 순위 계산, 범위 질의, 인덱싱, 로그 분석, 데이터베이스 질의 처리 등 수많은 작업의 기반이 되기 때문이다.

대표적인 정렬 알고리즘에는 버블 정렬, 선택 정렬, 삽입 정렬, 병합 정렬, 퀵 정렬, 힙 정렬이 있다. 이들은 모두 같은 목표, 즉 데이터를 정해진 순서로 재배치하는 것을 목표로 하지만 내부 동작 방식과 시간 복잡도, 공간 복잡도, 안정성, 실제 성능 특성이 크게 다르다.

정렬 알고리즘을 학습할 때 중요한 기준은 다음과 같다.

- **시간 복잡도**: 입력 크기 `n`에 대해 비교와 이동이 얼마나 발생하는가
- **공간 복잡도**: 추가 메모리를 얼마나 사용하는가
- **안정 정렬 여부**: 같은 값을 가진 원소들의 기존 상대 순서가 유지되는가
- **제자리 정렬 여부**: 입력 배열 외에 큰 추가 메모리 없이 정렬하는가
- **입력 상태에 대한 민감도**: 이미 거의 정렬된 데이터에서 더 빠르게 동작하는가
- **최악의 경우 보장 여부**: 어떤 입력에서도 일정한 성능 상한을 보장하는가

대표 알고리즘의 복잡도 비교는 다음과 같다.

| 정렬 알고리즘 | 평균 시간 복잡도 | 최악 시간 복잡도 | 최선 시간 복잡도 | 공간 복잡도 | 안정 정렬 | 제자리 정렬 |
|---|---:|---:|---:|---:|---|---|
| 버블 정렬 | O(n²) | O(n²) | O(n) 가능 | O(1) | 예 | 예 |
| 선택 정렬 | O(n²) | O(n²) | O(n²) | O(1) | 일반 구현은 아니오 | 예 |
| 삽입 정렬 | O(n²) | O(n²) | O(n) | O(1) | 예 | 예 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | O(n) | 예 | 일반 배열 구현은 아니오 |
| 퀵 정렬 | O(n log n) | O(n²) | O(n log n) | 평균 O(log n) | 일반 구현은 아니오 | 예 |
| 힙 정렬 | O(n log n) | O(n log n) | O(n log n) | O(1) | 아니오 | 예 |

정렬 알고리즘의 목적은 단순히 배열을 예쁘게 나열하는 데 있지 않다. 정렬은 더 빠른 탐색을 가능하게 하고, 대량 데이터 처리에서 그룹화와 집계를 쉽게 하며, 분산 시스템에서 데이터 파티셔닝과 병합을 효율적으로 만든다. 또한 알고리즘 면접에서는 시간 복잡도 분석, 재귀, 분할 정복, 힙 자료구조, 안정성, 메모리 사용량 등 다양한 CS 개념을 함께 평가하는 핵심 주제이다.

## 내부 동작 원리

## 1. 버블 정렬 Bubble Sort

버블 정렬은 인접한 두 원소를 비교하여 순서가 잘못되어 있으면 교환하는 과정을 반복하는 정렬이다. 큰 값이 배열의 끝으로 “거품처럼 떠오른다”는 의미에서 버블 정렬이라고 부른다.

예를 들어 `[5, 1, 4, 2]`를 오름차순 정렬한다고 하자.

```text
초기 상태
[5, 1, 4, 2]

1회전:
5와 1 비교 → 교환
[1, 5, 4, 2]

5와 4 비교 → 교환
[1, 4, 5, 2]

5와 2 비교 → 교환
[1, 4, 2, 5]
가장 큰 5가 맨 뒤로 이동

2회전:
1과 4 비교 → 유지
[1, 4, 2, 5]

4와 2 비교 → 교환
[1, 2, 4, 5]
```

다이어그램으로 보면 다음과 같다.

```text
[5] [1] [4] [2]
 ↑   ↑
 비교 후 교환

[1] [5] [4] [2]
     ↑   ↑
     비교 후 교환

[1] [4] [5] [2]
         ↑   ↑
         비교 후 교환

[1] [4] [2] [5]
              ↑
       가장 큰 값 확정
```

버블 정렬은 구현이 매우 쉽지만, 평균 및 최악 시간 복잡도가 `O(n²)`이므로 큰 데이터에는 적합하지 않다. 다만 한 번의 순회에서 교환이 발생하지 않으면 이미 정렬된 상태라고 판단해 종료할 수 있다. 이 최적화를 적용하면 이미 정렬된 입력에 대해 `O(n)`까지 개선될 수 있다.

## 2. 선택 정렬 Selection Sort

선택 정렬은 아직 정렬되지 않은 구간에서 가장 작은 값을 찾아 현재 위치와 교환하는 방식이다. 매 단계마다 “이번 위치에 들어갈 값을 선택한다”는 점이 특징이다.

예: `[5, 1, 4, 2]`

```text
초기 상태
[5, 1, 4, 2]

1단계:
전체에서 최솟값 1 선택
5와 1 교환
[1, 5, 4, 2]

2단계:
미정렬 구간 [5, 4, 2]에서 최솟값 2 선택
5와 2 교환
[1, 2, 4, 5]

3단계:
미정렬 구간 [4, 5]에서 최솟값 4 선택
유지
[1, 2, 4, 5]
```

다이어그램:

```text
정렬 구간 | 미정렬 구간

[] | [5, 1, 4, 2]
      ↓ 최솟값 1 선택

[1] | [5, 4, 2]
       ↓ 최솟값 2 선택

[1, 2] | [4, 5]
          ↓ 최솟값 4 선택

[1, 2, 4] | [5]
```

선택 정렬의 비교 횟수는 입력 상태와 관계없이 거의 일정하게 많다. 따라서 최선, 평균, 최악 모두 `O(n²)`이다. 대신 교환 횟수는 상대적으로 적다. 배열의 각 위치마다 많아야 한 번 정도만 교환하므로, 쓰기 비용이 비싼 환경에서는 단순 정렬 중에서 의미가 있을 수 있다. 하지만 일반적인 대규모 데이터 처리에는 잘 사용되지 않는다.

## 3. 삽입 정렬 Insertion Sort

삽입 정렬은 배열을 왼쪽부터 보면서 현재 원소를 이미 정렬된 왼쪽 구간의 적절한 위치에 삽입하는 방식이다. 사람이 카드를 손에 들고 정렬할 때와 유사하다.

예: `[5, 1, 4, 2]`

```text
초기 상태
[5, 1, 4, 2]

첫 번째 원소 5는 정렬된 구간으로 간주
[5 | 1, 4, 2]

1을 정렬 구간 [5]에 삽입
[1, 5 | 4, 2]

4를 정렬 구간 [1, 5]에 삽입
[1, 4, 5 | 2]

2를 정렬 구간 [1, 4, 5]에 삽입
[1, 2, 4, 5]
```

다이어그램:

```text
정렬된 구간 | 미정렬 구간

[5] | [1, 4, 2]
       ↑
       1을 왼쪽 정렬 구간에 삽입

[1, 5] | [4, 2]
          ↑
          4를 1과 5 사이에 삽입

[1, 4, 5] | [2]
             ↑
             2를 1과 4 사이에 삽입
```

삽입 정렬은 최악의 경우, 예를 들어 역순 배열에서는 각 원소를 앞쪽까지 계속 이동해야 하므로 `O(n²)`이다. 그러나 이미 정렬되어 있거나 거의 정렬된 데이터에서는 이동이 적어 `O(n)`에 가까운 성능을 낼 수 있다. 이 특성 때문에 실제 고성능 정렬 구현에서는 작은 부분 배열을 정렬할 때 삽입 정렬을 보조적으로 사용하는 경우가 많다.

## 4. 병합 정렬 Merge Sort

병합 정렬은 분할 정복 알고리즘의 대표적인 예다. 배열을 절반씩 나누어 각각 정렬한 뒤, 두 정렬된 배열을 병합하여 전체를 정렬한다.

핵심 절차는 다음과 같다.

1. 배열을 절반으로 나눈다.
2. 왼쪽 절반을 재귀적으로 정렬한다.
3. 오른쪽 절반을 재귀적으로 정렬한다.
4. 정렬된 두 배열을 하나로 병합한다.

예: `[5, 1, 4, 2]`

```text
분할 단계

[5, 1, 4, 2]
      ↓
[5, 1]      [4, 2]
  ↓            ↓
[5] [1]     [4] [2]

병합 단계

[5] + [1] → [1, 5]
[4] + [2] → [2, 4]

[1, 5] + [2, 4] → [1, 2, 4, 5]
```

다이어그램:

```text
                [5, 1, 4, 2]
                  /       \
             [5, 1]       [4, 2]
             /   \         /   \
           [5]   [1]     [4]   [2]
             \   /         \   /
            [1, 5]        [2, 4]
                  \       /
               [1, 2, 4, 5]
```

병합 과정은 두 정렬된 배열의 앞 원소를 비교하면서 더 작은 값을 결과 배열에 넣는 방식이다.

```text
왼쪽: [1, 5]
오른쪽: [2, 4]

1과 2 비교 → 1 선택
5와 2 비교 → 2 선택
5와 4 비교 → 4 선택
남은 5 추가

결과: [1, 2, 4, 5]
```

병합 정렬은 항상 배열을 절반씩 나누므로 시간 복잡도가 안정적으로 `O(n log n)`이다. 또한 병합 시 같은 값에 대해 왼쪽 원소를 먼저 선택하면 안정 정렬이 된다. 단점은 일반적인 배열 구현에서 병합을 위해 추가 배열이 필요하므로 `O(n)`의 추가 공간이 든다는 점이다.

## 5. 퀵 정렬 Quick Sort

퀵 정렬 역시 분할 정복 알고리즘이다. 하나의 기준값인 피벗 pivot을 선택하고, 피벗보다 작은 값은 왼쪽, 큰 값은 오른쪽으로 분할한 뒤 각 부분 배열을 재귀적으로 정렬한다.

핵심 절차는 다음과 같다.

1. 피벗을 선택한다.
2. 피벗보다 작은 원소와 큰 원소를 기준으로 배열을 분할한다.
3. 왼쪽 부분 배열을 재귀적으로 정렬한다.
4. 오른쪽 부분 배열을 재귀적으로 정렬한다.

예: `[5, 1, 4, 2]`, 피벗을 `2`라고 하자.

```text
초기 배열
[5, 1, 4, 2]

피벗: 2

2보다 작은 값: [1]
피벗: [2]
2보다 큰 값: [5, 4]

결과 구조:
[1] + [2] + [5, 4]

오른쪽 [5, 4] 정렬:
피벗 4
작은 값: []
피벗: [4]
큰 값: [5]

최종:
[1, 2, 4, 5]
```

다이어그램:

```text
               [5, 1, 4, 2]
                    pivot=2
                 /     |     \
              [1]     [2]   [5, 4]
                              pivot=4
                            /   |   \
                          []   [4]  [5]

결과: [1, 2, 4, 5]
```

실제 배열 기반 퀵 정렬은 보통 별도 배열을 만들지 않고 인덱스를 움직여 제자리 분할을 수행한다.

```text
피벗 기준 분할 개념

[작은 값들 | pivot | 큰 값들]
```

퀵 정렬의 평균 시간 복잡도는 `O(n log n)`이다. 피벗이 매번 배열을 균형 있게 나누면 매우 빠르게 동작한다. 그러나 피벗 선택이 나빠서 한쪽 부분 배열만 계속 커지는 경우, 예를 들어 이미 정렬된 배열에서 항상 첫 원소를 피벗으로 고르는 단순 구현은 최악 `O(n²)`이 될 수 있다.

퀵 정렬은 캐시 지역성이 좋고 추가 메모리를 적게 쓰는 장점이 있어 실제 시스템에서 널리 활용되는 정렬 방식이다. 다만 최악의 경우를 완화하기 위해 무작위 피벗, 중앙값 기반 피벗, 재귀 깊이 제한, 작은 구간에 삽입 정렬 사용 등의 최적화가 함께 사용된다.

## 6. 힙 정렬 Heap Sort

힙 정렬은 힙 자료구조를 이용한 정렬이다. 오름차순 정렬에서는 보통 최대 힙 max heap을 만든 뒤, 최댓값을 하나씩 배열 뒤로 보내면서 정렬한다.

최대 힙은 부모 노드가 자식 노드보다 크거나 같은 완전 이진 트리이다.

```text
배열 표현:
[5, 2, 4, 1]

힙 구조:
        5
       / \
      2   4
     /
    1
```

힙 정렬 절차는 다음과 같다.

1. 배열을 최대 힙으로 만든다.
2. 루트에 있는 최댓값을 배열의 마지막 원소와 교환한다.
3. 마지막 원소는 정렬 완료 구간으로 본다.
4. 남은 힙 구간에서 다시 heapify를 수행한다.
5. 위 과정을 반복한다.

예: `[5, 1, 4, 2]`

```text
초기 배열
[5, 1, 4, 2]

최대 힙 구성
[5, 2, 4, 1]

루트 5와 마지막 1 교환
[1, 2, 4, 5]
          ↑
          5 확정

남은 [1, 2, 4] heapify
[4, 2, 1, 5]

루트 4와 힙 마지막 1 교환
[1, 2, 4, 5]
       ↑
       4 확정

남은 [1, 2] heapify
[2, 1, 4, 5]

루트 2와 1 교환
[1, 2, 4, 5]
```

다이어그램:

```text
최대 힙:
        5
       / \
      2   4
     /
    1

최댓값 5를 끝으로 이동:
        1
       / \
      2   4        | 5 확정

다시 heapify:
        4
       / \
      2   1        | 5 확정
```

힙 정렬은 최선, 평균, 최악 모두 `O(n log n)`을 보장한다. 추가 배열이 필요 없으므로 공간 복잡도는 `O(1)`이다. 하지만 일반적인 구현은 안정 정렬이 아니며, 퀵 정렬에 비해 캐시 지역성이 떨어질 수 있어 실제 평균 성능이 항상 더 좋지는 않다. 그럼에도 최악 시간 복잡도 보장이 필요하고 추가 메모리를 아끼고 싶을 때 유용하다.

## 실제 시스템 연결

정렬은 실제 시스템에서 매우 광범위하게 사용된다. 운영체제, 데이터베이스, 검색 엔진, 로그 분석 시스템, 클라우드 데이터 처리 플랫폼, 네트워크 서버 등 거의 모든 영역에서 정렬이 등장한다.

## 1. Linux 및 유닉스 계열 시스템

Linux 환경에서 사용되는 `sort` 명령은 텍스트 파일의 행을 정렬하는 대표적인 도구다. 작은 파일은 메모리에서 처리할 수 있지만, 큰 파일은 메모리에 모두 올릴 수 없으므로 임시 파일을 만들고 여러 정렬된 조각을 병합하는 외부 정렬 external sort 방식이 사용된다. 이때 핵심 개념은 병합 정렬과 연결된다.

```bash
sort access.log
sort -k 2 users.txt
sort -n numbers.txt
```

예를 들어 대용량 로그 파일을 시간순, IP순, 상태 코드순으로 정렬할 때 `sort` 명령을 사용할 수 있다. 이 경우 내부적으로는 데이터 크기, 메모리 제한, 임시 디렉터리 설정에 따라 메모리 정렬과 디스크 기반 병합이 조합될 수 있다.

⚠️ 확인 필요: 특정 Linux 배포판 또는 특정 `sort` 구현이 내부적으로 어떤 정렬 알고리즘을 사용하는지는 구현체와 버전에 따라 달라질 수 있다.

## 2. 데이터베이스 시스템

SQL의 `ORDER BY`, `GROUP BY`, `DISTINCT`, 인덱스 생성, 조인 처리 과정에서는 정렬이 자주 사용된다.

```sql
SELECT *
FROM orders
ORDER BY created_at DESC;
```

데이터베이스는 정렬 비용을 줄이기 위해 다음과 같은 전략을 사용한다.

- 이미 정렬된 인덱스를 활용
- 메모리 내 정렬 수행
- 메모리가 부족하면 디스크 기반 외부 정렬 수행
- 병렬 정렬 수행
- 정렬 후 병합 조인 merge join 수행

병합 정렬의 “정렬된 두 집합을 선형 시간에 합치는” 특성은 데이터베이스의 병합 조인과 밀접하다.

## 3. 검색 엔진 및 로그 분석

검색 시스템은 문서 점수, 최신순, 클릭 수, 랭킹 점수 등을 기준으로 결과를 정렬한다. 로그 분석 시스템에서는 시간순 정렬, 사용자별 정렬, 이벤트 종류별 정렬이 자주 필요하다.

예를 들어 웹 서버 로그를 분석할 때 다음 작업이 가능하다.

```text
원본 로그:
timestamp, user_id, path, status

분석 목적:
- timestamp 기준 정렬
- user_id 기준 그룹화
- status code 기준 집계
```

정렬은 단순 출력 순서를 맞추는 작업을 넘어, 이후 집계와 탐색의 전처리 역할을 한다.

## 4. 분산 데이터 처리 시스템

Apache Spark, Hadoop MapReduce 같은 분산 처리 시스템에서는 정렬이 핵심 연산 중 하나다. MapReduce의 shuffle/sort 단계는 같은 key를 가진 데이터를 reducer로 모으기 전에 key 기준으로 정렬하는 개념과 연결된다.

```text
Map 출력:
(user1, eventA)
(user3, eventB)
(user1, eventC)

Shuffle/Sort:
user1 → [eventA, eventC]
user3 → [eventB]
```

이 과정에서 각 노드는 부분 정렬을 수행하고, 이후 병합 과정을 통해 전체 결과를 구성할 수 있다. 병합 정렬의 아이디어가 대규모 데이터 처리에 자연스럽게 확장되는 대표적인 사례다.

## 5. Nginx 및 서버 시스템과의 연결

Nginx 같은 웹 서버 자체의 핵심 동작이 정렬 알고리즘에 직접 의존한다고 단정하기는 어렵다. 그러나 실제 운영 환경에서는 Nginx access log를 정렬하고 분석하는 일이 매우 흔하다.

예:

```bash
# 상태 코드 기준 정렬
sort -k 9 access.log

# IP 기준 정렬 후 빈도 계산
awk '{print $1}' access.log | sort | uniq -c | sort -nr
```

이런 로그 분석 파이프라인에서 정렬은 공격 IP 식별, 트래픽 패턴 분석, 장애 시점 추적 등에 사용된다.

## 클라우드 연결

정렬은 클라우드 환경에서도 핵심적인 데이터 처리 연산이다. 특히 컨테이너, Kubernetes, AWS, GCP 같은 환경에서는 대규모 로그, 메트릭, 이벤트, 객체 목록, 쿼리 결과를 정렬하는 일이 빈번하다.

## 1. Docker 환경

Docker 컨테이너에서 애플리케이션 로그를 수집하면 로그는 시간순, 컨테이너 ID순, 서비스명순으로 정렬되어야 할 때가 많다.

```bash
docker logs my-container | sort
```

다만 컨테이너 로그는 보통 stdout/stderr 스트림으로 수집되기 때문에, 단일 컨테이너 내부에서는 출력 순서가 시간 순서와 대체로 관련이 있다. 하지만 여러 컨테이너에서 수집한 로그를 중앙 시스템으로 모으면 네트워크 지연, 수집 지연, 버퍼링 때문에 전역 시간순 정렬이 필요할 수 있다.

```text
container-a: 10:00:01 event1
container-b: 10:00:00 event2
container-a: 10:00:03 event3

중앙 로그 시스템:
timestamp 기준 재정렬 필요
```

이때 정렬은 분산 로그 분석의 기본 전처리 단계가 된다.

## 2. Kubernetes 환경

Kubernetes에서는 Pod, Node, Event, Metric 같은 리소스를 조회할 때 특정 기준으로 정렬하는 요구가 있다.

예:

```bash
kubectl get pods --sort-by=.metadata.creationTimestamp
kubectl get events --sort-by=.lastTimestamp
```

정렬 기준은 생성 시간, 이름, 리소스 사용량, 상태 등 다양할 수 있다. 운영자는 이를 통해 최근 생성된 Pod, 오래된 이벤트, 장애가 발생한 순서 등을 쉽게 파악할 수 있다.

또한 Kubernetes 스케줄링 과정에서는 노드 필터링과 점수화가 이루어진다. 점수화된 후보 노드 중 적절한 노드를 선택하는 과정은 우선순위 계산 및 비교와 관련이 있다. 다만 이것을 특정 정렬 알고리즘 하나와 직접 연결하는 것은 조심해야 한다.

⚠️ 확인 필요: Kubernetes 스케줄러 내부의 특정 단계가 어떤 정렬 알고리즘을 사용하는지는 버전과 구현 세부 사항에 따라 달라질 수 있다.

## 3. AWS와 정렬

AWS 환경에서 정렬은 여러 서비스에서 간접적으로 등장한다.

### Amazon Athena / Amazon Redshift

SQL 질의에서 `ORDER BY`를 사용하면 결과 정렬이 수행된다.

```sql
SELECT user_id, count(*)
FROM logs
GROUP BY user_id
ORDER BY count(*) DESC;
```

이런 작업은 내부적으로 분산 정렬, 부분 정렬, 병합, 메모리 및 디스크 사용 최적화와 관련된다.

### Amazon S3 로그 및 객체 처리

S3에 저장된 로그 파일을 Athena, Glue, EMR, Spark 등을 통해 분석할 때 정렬이 사용된다.

```text
S3 로그 데이터
→ Glue Catalog로 테이블화
→ Athena SQL 실행
→ timestamp 기준 ORDER BY
```

대용량 데이터에서는 단일 머신 정렬이 아니라 여러 노드에서 부분 정렬 후 병합하는 방식이 필요하다. 이는 병합 정렬의 아이디어와 연결된다.

### Amazon EMR

Amazon EMR에서 Hadoop, Spark 작업을 수행할 때 key 기준 정렬은 shuffle 단계에서 중요한 역할을 한다. 예를 들어 사용자별 이벤트를 시간순으로 분석하려면 다음과 같은 흐름이 가능하다.

```text
S3 원본 데이터
→ EMR Spark 작업
→ user_id 기준 파티셔닝
→ timestamp 기준 정렬
→ 사용자 세션 분석
```

## 4. GCP와 정렬

GCP의 BigQuery에서도 `ORDER BY`는 대규모 데이터 정렬을 유발하는 연산이다.

```sql
SELECT *
FROM `project.dataset.table`
ORDER BY event_time DESC;
```

BigQuery 같은 분산 쿼리 엔진은 데이터를 여러 슬롯이나 작업 단위로 나누어 처리하고, 최종 결과를 정렬하기 위해 병합 및 재분배 과정을 수행할 수 있다.

⚠️ 확인 필요: BigQuery 내부의 구체적인 정렬 알고리즘과 실행 계획은 쿼리, 데이터 크기, 파티셔닝, 클러스터링, 엔진 최적화에 따라 달라질 수 있다.

## 5. 클라우드에서 정렬 비용이 중요한 이유

클라우드에서는 정렬이 비용과 성능에 직접 영향을 준다.

- 대용량 정렬은 CPU 사용량 증가
- 메모리 부족 시 디스크 spill 발생 가능
- 분산 정렬은 네트워크 shuffle 비용 증가
- `ORDER BY`는 결과 전체를 정렬해야 하므로 비싼 연산이 될 수 있음
- 적절한 파티셔닝, 인덱싱, 클러스터링이 정렬 비용을 줄일 수 있음

따라서 클라우드 환경에서는 정렬 알고리즘 자체뿐 아니라 데이터 배치, 파티션 설계, 메모리 설정, 병렬 처리 전략까지 함께 고려해야 한다.

## 보안 연결

정렬 알고리즘은 보안과도 연결된다. 정렬 자체가 암호화 알고리즘처럼 보안 기능을 제공하는 것은 아니지만, 잘못된 정렬 구현이나 정렬 비용을 악용한 입력은 서비스 거부, 정보 노출, 무결성 오류로 이어질 수 있다.

## 1. 알고리즘 복잡도 공격 Algorithmic Complexity Attack

퀵 정렬은 평균적으로 `O(n log n)`이지만, 피벗 선택이 나쁘면 최악 `O(n²)`이 된다. 공격자가 서버가 사용하는 정렬 구현의 특성을 알고, 최악의 입력을 대량으로 보내면 CPU 사용량을 급증시켜 서비스 거부 DoS를 유발할 수 있다.

```text
정상 입력:
분할이 균형적 → O(n log n)

공격 입력:
피벗이 계속 최솟값 또는 최댓값 → O(n²)
```

모범 사례:

- 무작위 피벗 사용
- 중앙값 기반 피벗 사용
- 재귀 깊이 제한
- 최악 `O(n log n)`을 보장하는 힙 정렬 또는 introsort 계열 전략 사용
- 입력 크기 제한
- 요청당 CPU 시간 제한

⚠️ 확인 필요: 특정 언어 런타임이나 표준 라이브러리의 정렬 구현이 어떤 공격에 취약한지는 버전과 구현에 따라 다르다.

## 2. 메모리 고갈 문제

병합 정렬은 일반적인 배열 구현에서 `O(n)` 추가 메모리를 사용한다. 사용자가 매우 큰 데이터를 업로드하고 서버가 이를 메모리에서 정렬하려고 하면 메모리 부족이 발생할 수 있다.

```text
사용자 입력 대량 업로드
→ 서버 메모리 내 정렬 시도
→ 메모리 사용량 급증
→ OOM 또는 성능 저하
```

모범 사례:

- 입력 크기 제한
- 스트리밍 처리
- 외부 정렬 사용
- 임시 파일 디렉터리 용량 제한
- 메모리 제한 설정
- 컨테이너 cgroup memory limit 설정

## 3. 임시 파일 보안

대용량 정렬에서 외부 정렬을 사용할 경우 임시 파일이 생성될 수 있다. 이때 임시 파일 경로, 권한, 삭제 정책이 부적절하면 민감한 데이터가 노출될 수 있다.

위험 요소:

- `/tmp`에 민감 데이터 평문 저장
- 다른 사용자에게 읽기 가능한 파일 권한
- 임시 파일 삭제 실패
- 디스크 가득 참으로 인한 장애

모범 사례:

- 안전한 임시 디렉터리 사용
- 최소 권한 파일 권한 설정
- 암호화된 스토리지 사용
- 작업 완료 후 임시 파일 삭제
- 디스크 사용량 모니터링

## 4. 비교 함수 Comparator 오류

정렬에서 비교 함수가 일관성을 만족하지 않으면 결과가 예측 불가능해질 수 있다. 비교 함수는 일반적으로 다음 성질을 만족해야 한다.

- 반사성 또는 자기 비교 일관성
- 반대칭성
- 추이성
- 동일 값 처리 일관성

잘못된 예:

```text
A < B
B < C
그런데 C < A 라고 판단
```

이런 비교 함수는 정렬 결과를 불안정하게 만들고, 일부 구현에서는 무한 루프나 예외, 잘못된 권한 우선순위 계산으로 이어질 수 있다.

보안적으로는 접근 제어 규칙, 방화벽 규칙, 정책 우선순위 등을 정렬할 때 comparator 오류가 치명적일 수 있다.

예:

```text
규칙 A: 관리자 허용
규칙 B: 특정 IP 차단
규칙 C: 전체 차단

잘못된 정렬로 우선순위가 바뀌면 의도하지 않은 접근 허용 가능
```

## 5. 안정 정렬과 보안 정책

안정 정렬은 같은 키를 가진 원소들의 기존 순서를 유지한다. 보안 정책 처리에서 같은 우선순위의 규칙들이 입력 순서대로 적용되어야 한다면 안정 정렬 여부가 중요할 수 있다.

```text
입력 순서:
1. user=alice 허용
2. user=alice 특정 리소스 차단

같은 priority라면 입력 순서가 의미를 가질 수 있음
```

불안정 정렬을 사용하면 같은 우선순위의 규칙 순서가 바뀔 수 있다. 따라서 보안 정책, 라우팅 규칙, 방화벽 규칙 등에서는 정렬 안정성과 tie-breaker 조건을 명확히 정의해야 한다.

## 6. 타이밍 및 부채널 정보

일반적인 정렬 알고리즘은 입력 데이터의 순서나 값에 따라 실행 시간이 달라질 수 있다. 민감한 데이터를 정렬하는 특수한 환경에서는 실행 시간 차이가 정보 유출의 단서가 될 수 있다.

예:

```text
이미 정렬된 데이터 → 빠름
역순 데이터 → 느림
랜덤 데이터 → 중간
```

## 면접 질문

**Q1. 버블 정렬, 선택 정렬, 삽입 정렬의 차이를 설명하세요.**  
> 핵심 답변: 세 알고리즘 모두 단순 정렬이며 평균적으로 `O(n²)`이다. 버블 정렬은 인접 원소를 반복 교환하여 큰 값을 뒤로 보낸다. 선택 정렬은 미정렬 구간에서 최솟값을 선택해 현재 위치와 교환한다. 삽입 정렬은 현재 원소를 이미 정렬된 왼쪽 구간의 적절한 위치에 삽입한다. 삽입 정렬은 거의 정렬된 데이터에서 `O(n)`에 가까워질 수 있다는 점이 중요하다.

**Q2. 병합 정렬의 시간 복잡도가 항상 O(n log n)인 이유는 무엇인가요?**  
> 핵심 답변: 병합 정렬은 배열을 매번 절반으로 나누므로 분할 깊이가 `log n`이다. 각 깊이에서 모든 원소가 병합 과정에 한 번씩 참여하므로 한 레벨당 `O(n)`이 걸린다. 따라서 전체 시간 복잡도는 `O(n log n)`이다. 입력 상태와 관계없이 비슷한 구조로 동작하므로 최선, 평균, 최악이 모두 `O(n log n)`이다.

**Q3. 퀵 정렬의 평균 성능은 좋은데 최악의 경우 O(n²)이 되는 이유는 무엇인가요?**
