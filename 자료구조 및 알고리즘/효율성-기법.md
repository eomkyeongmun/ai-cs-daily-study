# 효율성 기법 - 투 포인터, 슬라이딩 윈도우, 누적 합(Prefix Sum)

## 핵심 개념

## 효율성 기법: 투 포인터, 슬라이딩 윈도우, 누적 합

투 포인터(Two Pointers), 슬라이딩 윈도우(Sliding Window), 누적 합(Prefix Sum)은 배열, 문자열, 리스트 같은 선형 자료구조에서 반복 탐색 비용을 줄이기 위해 자주 사용되는 알고리즘 설계 기법이다. 이들의 공통 목적은 **불필요한 중복 계산을 제거하여 시간 복잡도를 낮추는 것**이다. 단순히 모든 구간이나 모든 쌍을 검사하면 `O(N^2)` 또는 그 이상이 될 수 있지만, 문제의 구조를 이용하면 `O(N)` 또는 `O(N log N)` 수준으로 개선할 수 있다.

투 포인터는 보통 두 개의 인덱스를 사용해 배열의 양끝 또는 같은 방향으로 이동하면서 조건을 만족하는 쌍이나 구간을 찾는다. 정렬된 배열에서 특정 합을 찾거나, 중복 제거, 부분 구간 탐색 등에 적합하다. 슬라이딩 윈도우는 연속된 구간을 하나의 “창(window)”으로 보고, 창의 시작과 끝을 이동시키며 현재 구간 정보를 갱신한다. 고정 길이 구간의 최대합, 특정 조건을 만족하는 최소 길이 부분 배열, 문자열 패턴 탐색 등에 널리 사용된다. 누적 합은 배열의 앞에서부터 합을 미리 저장해 두고, 임의 구간의 합을 `O(1)`에 계산하는 기법이다.

이 세 기법은 코딩 테스트뿐 아니라 실제 시스템에서도 중요하다. 로그 분석, 네트워크 트래픽 집계, 모니터링 지표 계산, 스트림 데이터 처리, 요청 제한(rate limiting), 시계열 데이터 분석 등에서 “최근 N초”, “특정 구간”, “연속된 이벤트”를 빠르게 계산해야 하는 경우가 많기 때문이다. 즉, 이들은 단순한 알고리즘 풀이용 도구가 아니라 대규모 데이터 처리와 성능 최적화의 기본 사고방식이다.

## 1. 투 포인터 핵심 개념

투 포인터는 두 개의 위치 변수, 보통 `left`, `right` 또는 `start`, `end`를 사용하여 탐색 범위를 효율적으로 줄이는 기법이다. 대표적으로 정렬된 배열에서 두 수의 합이 특정 값이 되는지 찾을 때 사용한다. 왼쪽 포인터는 작은 값을 가리키고, 오른쪽 포인터는 큰 값을 가리킨다. 두 값의 합이 목표보다 작으면 왼쪽 포인터를 오른쪽으로 이동해 합을 키우고, 목표보다 크면 오른쪽 포인터를 왼쪽으로 이동해 합을 줄인다.

```text
정렬 배열: [1, 2, 4, 7, 11, 15]
목표 합: 15

left                         right
  ↓                            ↓
[1, 2, 4, 7, 11, 15]

1 + 15 = 16 > 15 → right 이동
```

이 방식은 모든 쌍을 검사하는 `O(N^2)` 접근보다 효율적이며, 정렬되어 있다는 조건이 있으면 `O(N)`에 해결 가능하다.

## 2. 슬라이딩 윈도우 핵심 개념

슬라이딩 윈도우는 연속된 구간을 유지하면서 구간의 시작과 끝을 이동시키는 기법이다. 고정 크기 윈도우와 가변 크기 윈도우로 나뉜다.

고정 크기 윈도우에서는 예를 들어 길이 `K`인 부분 배열의 최대 합을 구할 때, 첫 구간의 합을 구한 뒤 다음 칸으로 이동할 때 빠지는 값은 빼고 새로 들어오는 값은 더한다.

```text
배열: [2, 1, 5, 1, 3, 2], K = 3

초기 윈도우:
[2, 1, 5] 1  3  2  → 합 = 8

한 칸 이동:
 2 [1, 5, 1] 3  2  → 합 = 8 - 2 + 1 = 7
```

가변 크기 윈도우는 조건을 만족할 때까지 `right`를 확장하고, 조건을 유지하거나 최적화하기 위해 `left`를 이동한다. 예를 들어 “합이 S 이상인 가장 짧은 연속 부분 배열” 문제에서 많이 사용된다.

---

## 3. 누적 합 핵심 개념

누적 합은 배열의 각 위치까지의 합을 미리 계산해 저장하는 기법이다. 원본 배열 `arr`에 대해 `prefix[i]`를 `arr[0]`부터 `arr[i-1]`까지의 합으로 정의하면, 구간 `[l, r]`의 합은 다음과 같이 계산할 수 있다.

```text
sum(l, r) = prefix[r + 1] - prefix[l]
```

예시:

```text
arr     = [3, 1, 4, 1, 5]
prefix  = [0, 3, 4, 8, 9, 14]

구간 [1, 3]의 합 = arr[1] + arr[2] + arr[3]
                 = 1 + 4 + 1
                 = prefix[4] - prefix[1]
                 = 9 - 3 = 6
```

누적 합의 장점은 구간 질의가 많을 때 특히 크다. 매번 구간을 순회하면 한 번의 질의가 `O(N)`이지만, 누적 합을 만들면 전처리 `O(N)` 이후 각 구간 합 질의는 `O(1)`에 처리할 수 있다.

## 내부 동작 원리

### 1. 투 포인터의 동작 과정

투 포인터는 두 포인터의 이동 규칙이 명확해야 한다. 특히 정렬 배열에서 두 수의 합을 찾는 문제는 다음과 같이 동작한다.

```text
arr = [1, 2, 4, 7, 11, 15]
target = 13

left = 0, right = 5
arr[left] + arr[right] = 1 + 15 = 16
16 > 13 → right 감소

left = 0, right = 4
arr[left] + arr[right] = 1 + 11 = 12
12 < 13 → left 증가

left = 1, right = 4
arr[left] + arr[right] = 2 + 11 = 13
정답 발견
```

다이어그램으로 보면 다음과 같다.

```text
초기:
 left                            right
  ↓                                ↓
[ 1,   2,   4,   7,   11,   15 ]

합이 너무 큼 → right 왼쪽 이동

 left                      right
  ↓                          ↓
[ 1,   2,   4,   7,   11,   15 ]

합이 너무 작음 → left 오른쪽 이동

      left                 right
       ↓                     ↓
[ 1,   2,   4,   7,   11,   15 ]
```

핵심은 각 포인터가 한 방향으로만 움직이는 경우 전체 이동 횟수가 최대 `N` 또는 `2N` 수준이라는 점이다. 따라서 중첩 반복문처럼 보이더라도 실제 시간 복잡도는 `O(N)`이 될 수 있다.

대표 의사코드:

```text
left = 0
right = n - 1

while left < right:
    current = arr[left] + arr[right]

    if current == target:
        return true
    elif current < target:
        left += 1
    else:
        right -= 1

return false
```

주의할 점은 이 방식이 일반적으로 **정렬 상태 또는 단조성**을 필요로 한다는 것이다. 정렬되지 않은 배열에서 같은 방식으로 포인터를 움직이면 합이 증가하거나 감소한다는 보장이 없기 때문에 올바른 결과를 보장하지 못한다.

### 2. 슬라이딩 윈도우의 동작 과정

슬라이딩 윈도우는 현재 구간의 정보를 유지하면서 이동한다. 핵심은 “전체를 다시 계산하지 않고, 빠지는 원소와 들어오는 원소만 반영한다”는 것이다.

#### 고정 크기 윈도우

길이 `K`인 부분 배열의 최대 합:

```text
arr = [2, 1, 5, 1, 3, 2]
K = 3
```

초기 상태:

```text
window_sum = 2 + 1 + 5 = 8

[2, 1, 5] 1  3  2
 ↑     ↑
 L     R
```

한 칸 이동:

```text
빠지는 값: 2
들어오는 값: 1

window_sum = 8 - 2 + 1 = 7

 2 [1, 5, 1] 3  2
    ↑     ↑
    L     R
```

다음 이동:

```text
빠지는 값: 1
들어오는 값: 3

window_sum = 7 - 1 + 3 = 9

 2  1 [5, 1, 3] 2
       ↑     ↑
       L     R
```

의사코드:

```text
window_sum = sum(arr[0:K])
answer = window_sum

for right in range(K, n):
    window_sum += arr[right]
    window_sum -= arr[right - K]
    answer = max(answer, window_sum)
```

시간 복잡도는 초기 합 계산 `O(K)`와 이후 이동 `O(N-K)`를 합쳐 `O(N)`이다.

---

#### 가변 크기 윈도우

조건에 따라 윈도우 크기가 변하는 경우이다. 예를 들어 양수 배열에서 “합이 `S` 이상인 가장 짧은 연속 부분 배열 길이”를 구한다고 하자.

```text
arr = [2, 3, 1, 2, 4, 3]
S = 7
```

동작 방식:

```text
1. right를 이동하며 합을 증가시킨다.
2. 합이 S 이상이 되면 answer를 갱신한다.
3. left를 이동하며 구간을 줄인다.
4. 조건이 깨지면 다시 right를 확장한다.
```

다이어그램:

```text
[2, 3, 1, 2, 4, 3]
 L        R
현재 합 = 2 + 3 + 1 + 2 = 8
조건 만족 → 길이 4 기록

left 이동:
 2 [3, 1, 2, 4, 3]
    L     R
현재 합 = 6
조건 불만족 → right 확장
```

의사코드:

```text
left = 0
current_sum = 0
answer = INF

for right in range(n):
    current_sum += arr[right]

    while current_sum >= S:
        answer = min(answer, right - left + 1)
        current_sum -= arr[left]
        left += 1
```

중요한 조건은 배열 원소가 음수가 아닌 경우, `right`를 확장하면 합이 감소하지 않고 `left`를 이동하면 합이 증가하지 않는다는 단조성이 있다는 점이다. 음수가 포함되면 이 단순한 가변 윈도우 방식은 일반적으로 올바르지 않을 수 있다.

### 3. 누적 합의 동작 과정

누적 합은 전처리 배열을 만든 뒤, 구간 질의를 빠르게 처리한다.

원본 배열:

```text
index:  0  1  2  3  4
arr:   [3, 1, 4, 1, 5]
```

누적 합 배열:

```text
prefix[0] = 0
prefix[1] = prefix[0] + arr[0] = 3
prefix[2] = prefix[1] + arr[1] = 4
prefix[3] = prefix[2] + arr[2] = 8
prefix[4] = prefix[3] + arr[3] = 9
prefix[5] = prefix[4] + arr[4] = 14
```

다이어그램:

```text
arr:     [ 3,  1,  4,  1,  5 ]
prefix: [ 0,  3,  4,  8,  9, 14 ]
          ↑   ↑   ↑   ↑   ↑   ↑
         빈합 0~0 0~1 0~2 0~3 0~4
```

구간 `[l, r]`의 합:

```text
arr[l] + arr[l+1] + ... + arr[r]
= prefix[r + 1] - prefix[l]
```

예시:

```text
구간 [2, 4]의 합
= arr[2] + arr[3] + arr[4]
= 4 + 1 + 5
= prefix[5] - prefix[2]
= 14 - 4
= 10
```

의사코드:

```text
prefix = [0] * (n + 1)

for i in range(n):
    prefix[i + 1] = prefix[i] + arr[i]

def range_sum(l, r):
    return prefix[r + 1] - prefix[l]
```

누적 합은 2차원 배열에도 확장된다. 이미지 처리, 지도 데이터, 격자 기반 통계에서 직사각형 영역 합을 빠르게 구할 때 사용한다.

2차원 누적 합의 기본 형태:

```text
prefix[y][x] =
    grid[0][0]부터 grid[y-1][x-1]까지의 직사각형 합
```

직사각형 구간 합:

```text
sum(y1, x1, y2, x2)
= prefix[y2][x2]
- prefix[y1][x2]
- prefix[y2][x1]
+ prefix[y1][x1]
```

여기서 마지막 `+ prefix[y1][x1]`는 두 번 빠진 영역을 다시 더하는 포함-배제 원리이다.

### 1. Linux와 로그 처리

Linux 시스템에서는 `/var/log` 아래에 다양한 로그 파일이 저장된다. 예를 들어 인증 로그, 커널 로그, 시스템 서비스 로그 등이 운영 환경 분석에 사용된다. 로그 파일에서 특정 시간 구간의 이벤트 수, 에러 발생 횟수, IP별 요청 빈도 등을 계산할 때 슬라이딩 윈도우와 누적 합 사고방식이 유용하다.

예를 들어 “최근 5분 동안 특정 에러가 몇 번 발생했는가”를 계산할 때 매번 전체 로그를 다시 읽으면 비효율적이다. 로그가 시간순으로 정렬되어 있다면 두 포인터를 사용해 현재 시간 구간에 포함되는 로그만 유지할 수 있다.

```text
로그 시간순 배열:
[t1, t2, t3, t4, t5, t6, ...]

윈도우: 최근 5분
left  = 윈도우에서 제외될 가장 오래된 로그 위치
right = 새로 들어온 로그 위치
```

새 로그가 들어오면 `right`를 증가시키고, 윈도우 범위를 벗어난 로그는 `left`를 증가시켜 제거한다. 이 구조는 실시간 모니터링에서 흔히 필요한 “최근 구간 집계”와 직접 연결된다.

### 2. Nginx와 요청 제한

Nginx에는 요청 처리율을 제한하는 기능이 있다. Nginx의 `ngx_http_limit_req_module`은 요청 처리율을 제한하는 데 사용되며, 공식 문서상 leaky bucket 방식에 기반한 동작으로 설명된다. 이 기능 자체가 단순한 슬라이딩 윈도우 구현이라고 단정할 수는 없지만, “최근 시간 구간 동안 요청 빈도를 관리한다”는 점에서 슬라이딩 윈도우 기반 rate limiting 문제와 개념적으로 연결된다.

예를 들어 애플리케이션 레벨에서 다음과 같은 정책을 구현한다고 하자.

```text
정책: 사용자별 최근 60초 요청 수가 100개를 넘으면 차단
```

이 경우 각 사용자별 요청 타임스탬프를 큐에 저장하고, 현재 시각 기준 60초보다 오래된 요청을 제거한다.

```text
user A 요청 시각 큐:
[10s, 20s, 35s, 59s, 61s, 62s]

현재 시각 = 70s
60초 이전, 즉 10s보다 오래된 항목 제거
```

이는 전형적인 슬라이딩 윈도우 로직이다.

### 3. 데이터베이스와 분석 쿼리

많은 데이터베이스 시스템은 누적 합과 유사한 개념을 윈도우 함수(window function)로 제공한다. SQL의 `SUM(...) OVER (...)` 구문은 행의 순서나 파티션을 기준으로 누적 합, 이동 평균, 랭킹 등을 계산할 수 있다.

예시:

```sql
SELECT
  event_time,
  value,
  SUM(value) OVER (ORDER BY event_time) AS running_total
FROM events;
```

이 쿼리는 시간순으로 누적 합을 계산한다. 내부 구현은 데이터베이스 엔진마다 다르지만, 사용자가 보는 개념은 prefix sum과 매우 유사하다. 또한 최근 N개 행의 이동 합이나 이동 평균은 슬라이딩 윈도우 개념과 연결된다.

---

### 4. 시계열 모니터링 시스템

Prometheus, Grafana 같은 모니터링 도구에서는 일정 시간 범위의 메트릭을 조회하고 시각화한다. 예를 들어 CPU 사용률, HTTP 요청 수, 에러율 같은 데이터는 시간 축을 따라 저장된다. 사용자는 “최근 5분 평균”, “1시간 동안의 요청 증가량”, “분당 에러율” 같은 질의를 자주 수행한다.

이때 내부 저장 방식과 쿼리 엔진의 세부 구현은 시스템마다 다르지만, 개념적으로는 다음과 같은 알고리즘 문제가 등장한다.

```text
- 특정 시간 범위에 포함되는 샘플 선택 → 투 포인터 / 이진 탐색
- 이동 평균 계산 → 슬라이딩 윈도우
- 누적 카운터 차이 계산 → 누적 합 또는 prefix difference 사고방식
```

⚠️ 확인 필요: 특정 버전의 Prometheus 내부 구현이 위 세 기법을 정확히 어떤 자료구조로 사용하는지는 버전과 저장 엔진 구현에 따라 달라질 수 있다.

---

### 5. 이미지 처리와 2차원 누적 합

이미지 처리에서는 특정 영역의 픽셀 합, 평균 밝기, 사각형 영역 통계를 빠르게 구해야 할 때가 있다. 이때 2차원 누적 합과 같은 구조가 사용될 수 있다. 컴퓨터 비전 분야에서는 integral image 또는 summed-area table이라는 개념이 알려져 있으며, 이는 2차원 prefix sum과 같은 아이디어다.

예를 들어 흑백 이미지의 특정 사각형 영역 평균 밝기를 빠르게 계산하려면, 매번 모든 픽셀을 순회하는 대신 2차원 누적 합을 만들고 네 꼭짓점 값을 조합해 영역 합을 계산할 수 있다.

```text
직사각형 영역 합 =
오른쪽 아래 누적값
- 위쪽 영역 누적값
- 왼쪽 영역 누적값
+ 중복 제거된 왼쪽 위 누적값
```

## 클라우드 연결

## 클라우드 연결

### 1. Docker 컨테이너 로그 처리

Docker 컨테이너는 표준 출력과 표준 에러를 통해 로그를 남기는 경우가 많고, Docker는 이를 로그 드라이버를 통해 처리한다. 운영 환경에서는 컨테이너 로그를 수집해 최근 오류율, 요청 수, 특정 패턴 발생 빈도 등을 계산한다. 이때 슬라이딩 윈도우는 “최근 N분” 기준의 집계에 적합하다.

예시:

```text
최근 1분간 ERROR 로그가 100건 이상이면 알림 발생
```

구현 개념:

```text
1. 로그 이벤트를 시간순으로 수집한다.
2. ERROR 이벤트의 타임스탬프를 큐에 넣는다.
3. 현재 시각에서 1분보다 오래된 이벤트를 큐에서 제거한다.
4. 큐 크기가 임계값을 넘으면 알림을 발생시킨다.
```

이는 클라우드 네이티브 환경의 관측 가능성(observability)에서 자주 등장하는 패턴이다.

---

### 2. Kubernetes와 오토스케일링 메트릭

Kubernetes의 Horizontal Pod Autoscaler(HPA)는 CPU 사용률이나 사용자 정의 메트릭을 기반으로 Pod 수를 조정할 수 있다. HPA 자체의 내부 알고리즘은 Kubernetes 문서와 버전에 따라 세부 사항이 정의되어 있으며, 단순한 슬라이딩 윈도우라고 표현하는 것은 정확하지 않다. 하지만 운영자가 메트릭을 수집하고 안정적인 스케일링 판단을 하기 위해 최근 구간의 평균, 이동 평균, 피크 값 등을 계산하는 과정은 슬라이딩 윈도우 개념과 연결된다.

예시:

```text
- 최근 5분 평균 CPU 사용률
- 최근 10분 요청 수 증가 추세
- 특정 기간 동안의 에러율
```

이러한 지표를 계산할 때는 윈도우 기반 집계가 필요하다. Prometheus와 같은 모니터링 시스템에서 시간 범위 쿼리를 사용해 최근 구간 데이터를 분석하는 것도 같은 맥락이다.

---

### 3. AWS CloudWatch Metrics와 Logs

AWS CloudWatch는 메트릭과 로그를 수집하고 알람을 설정하는 데 사용된다. CloudWatch Alarm은 지정한 기간과 평가 조건을 기반으로 알람 상태를 판단한다. 이 개념은 알고리즘 관점에서 보면 일정 시간 구간의 데이터 포인트를 평가하는 윈도우 기반 판단과 연결된다.

예시:

```text
- 최근 몇 개의 평가 기간 동안 CPUUtilization이 임계값 초과
- 특정 기간 내 5XX 에러 수가 기준 이상
- 로그 필터 패턴에 매칭되는 이벤트 수 집계
```

누적 합 관점에서는 기간별 카운터를 누적해 두고 특정 시간 구간의 차이를 계산하면 빠르게 증가량을 구할 수 있다. 예를 들어 요청 수 카운터가 단조 증가 형태로 저장된다면, 특정 구간의 요청 수는 끝 시점 값에서 시작 시점 값을 빼는 방식으로 계산할 수 있다.

⚠️ 확인 필요: CloudWatch 내부 저장 엔진이 prefix sum을 직접 사용하는지는 공개 문서만으로 일반화하기 어렵다. 여기서는 사용자가 지표를 해석하는 알고리즘적 관점의 연결로 이해하는 것이 안전하다.

---

### 4. AWS Kinesis, Google Cloud Pub/Sub와 스트림 처리

AWS Kinesis, Google Cloud Pub/Sub 같은 서비스는 이벤트 스트리밍 또는 메시징 시스템으로 사용된다. 이들 자체가 투 포인터나 누적 합을 직접 제공한다고 말하기보다는, 이 서비스를 통해 들어오는 스트림 데이터를 처리하는 애플리케이션에서 윈도우 기반 집계가 자주 필요하다고 보는 것이 정확하다.

예시:

```text
- 최근 1분 동안 사용자별 클릭 수
- 최근 5분 동안 결제 실패율
- 최근 10초 동안 특정 API 호출 수
```

스트림 처리에서는 이벤트 시간(event time), 처리 시간(processing time), 지연 도착 데이터, 중복 이벤트 같은 문제가 함께 등장한다. 단순 배열 기반 슬라이딩 윈도우보다 복잡하지만, 기본 사고방식은 “시간 구간을 유지하며 집계한다”는 점에서 동일하다.

---

### 5. AWS WAF와 Rate-based Rule

AWS WAF는 웹 요청을 필터링하는 서비스이며, rate-based rule을 통해 일정 시간 동안 특정 기준으로 요청 수가 임계값을 초과할 때 요청을 제한할 수 있다. AWS WAF의 rate-based rule은 일정 평가 기간 동안 요청 비율을 추적한다는 점에서 슬라이딩 윈도우 기반 rate limiting과 개념적으로 연결된다.

⚠️ 확인 필요: AWS WAF의 rate-based rule이 내부적으로 정확히 어떤 윈도우 알고리즘을 사용하는지는 공개 문서와 서비스 구현 세부 사항에 의존하므로, 단정적으로 “슬라이딩 윈도우로 구현된다”고 표현해서는 안 된다.

## 보안 연결

## 보안 연결

### 1. Rate Limiting과 DoS 완화

슬라이딩 윈도우는 API rate limiting에서 자주 사용되는 개념이다. 특정 사용자, IP, API 키가 짧은 시간에 과도한 요청을 보내는 경우 이를 제한하면 무차별 대입 공격, 크리덴셜 스터핑, 스크래핑, 단순 DoS 공격의 영향을 줄일 수 있다.

예시 정책:

```text
- IP별 최근 60초 요청 수 100개 제한
- 사용자 계정별 로그인 실패 최근 5분 5회 제한
- API 키별 분당 요청 수 제한
```

구현 시에는 고정 윈도우 방식과 슬라이딩 윈도우 방식의 차이를 이해해야 한다. 고정 윈도우는 경계 시점에 요청이 몰리면 제한을 우회하는 버스트 문제가 발생할 수 있다.

```text
고정 윈도우 예:
00:59에 100회 요청
01:00에 100회 요청
실제로는 2초 동안 200회 요청 가능
```

슬라이딩 윈도우 방식은 최근 기간을 계속 이동시키기 때문에 이런 경계 문제를 줄일 수 있다.

---

### 2. 인증 실패 탐지

로그인 실패 이벤트를 시간순으로 저장하면 슬라이딩 윈도우를 사용해 최근 일정 시간 내 실패 횟수를 계산할 수 있다.

```text
계정 userA:
실패 시각 [10:00, 10:01, 10:02, 10:04, 10:05]

정책:
최근 5분 내 5회 실패 시 계정 잠금 또는 추가 인증 요구
```

이런 방식은 무차별 대입 공격 방어에 도움이 된다. 다만 IP만 기준으로 제한하면 프록시나 봇넷을 사용하는 공격에 약할 수 있고, 계정만 기준으로 제한하면 특정 계정에 대한 잠금 유도 공격이 가능할 수 있다. 따라서 IP, 계정, 디바이스, ASN, 사용자 행동 패턴 등 여러 기준을 조합하는 것이 보안상 더 안전하다.

---

### 3. 누적 합과 이상 탐지

보안 로그에서 특정 기간의 이벤트 수를 빠르게 계산하려면 누적 합이 유용하다. 예를 들어 분 단위로 실패 로그인 수를 저장해 두고, 특정 1시간 구간의 총 실패 횟수를 빠르게 계산할 수 있다.

```text
minute_count:
[2, 0, 1, 5, 3, 0, 4, ...]

prefix:
[0, 2, 2, 3, 8, 11, 11, 15, ...]

10분~20분 실패 횟수 =
prefix[21] - prefix[10]
```

이 방식은 대시보드, SIEM(Security Information and Event Management), 로그 분석 시스템에서 구간 통계를 빠르게 계산하는 사고방식과 연결된다.

⚠️ 확인 필요: 특정 SIEM 제품이 내부적으로 prefix sum을 사용하는지는 제품과 버전에 따라 다르므로 일반화하기 어렵다.

---

### 4. 메모리 사용량과 공격 가능성

슬라이딩 윈도우 기반 rate limiter를 구현할 때 사용자별로 모든 요청 타임스탬프를 저장하면, 공격자가 많은 사용자 ID, API 키, IP 주소를 생성해 메모리 사용량을 급증시킬 수 있다. 이는 애플리케이션 레벨의 자원 고갈 공격으로 이어질 수 있다.

대응 방법:

```text
- 오래된 키를 주기적으로 삭제한다.
- 사용자별 저장 가능한 이벤트 수에 상한을 둔다.
- Redis 같은 외부 저장소 사용 시 TTL을 설정한다.
- 고정 크기 카운터 또는 근사 알고리즘을 고려한다.
- 인증되지 않은 사용자와 인증된 사용자 정책을 분리한다.
```

특히 분산 환경에서는 여러 서버가 동일한 제한 정책을 공유해야 하므로, 로컬 메모리만 사용하는 rate limiter는 우회될 수 있다. 여러 인스턴스가 있는 경우 중앙 저장소나 API Gateway, WAF, 서비스 메시 등에서 일관된 제한을 적용하는 방식을 고려해야 한다.

---

### 5. 정수 오버플로와 경계 조건

누적 합을 사용할 때 값의 범위가 크면 정수 오버플로가 발생할 수 있다. 예를 들어 많은 요청 수, 큰 파일 크기, 대량 트래픽 바이트 수를 합산하는 경우 32비트 정수 범위를 넘을 수 있다. 보안적으로도 오버플로는 잘못된 검증, 제한 우회, 비정상 동작의 원인이 될 수 있다.

모범 사례:

```text
- 합산 값의 최대 범위를 사전에 추정한다.
- 충분히 큰 정수 타입을 사용한다.
- 언어별 오버플로 동작을 이해한다.
- 입력 인덱스의 범위를 검증한다.
- prefix[r + 1], prefix[l] 접근 시 배열 경계를 확인한다.
```

예를 들어 C/C++에서는 정수 오버플로와 배열 경계 오류가 심각한 취약점으로 이어질 수 있으므로 특히 주의해야 한다. Java, Python, Go 등 언어마다 정수 처리 방식과 배열 접근 오류 처리 방식이 다르기 때문에 사용하는 언어의 특성을 이해해야 한다.

## 면접 질문

**Q1. 투 포인터와 슬라이딩 윈도우의 차이는 무엇인가요?**  
> 핵심 답변: 투 포인터는 두 인덱스를 사용해 탐색 범위를 줄이는 일반적인 기법이고, 슬라이딩 윈도우는 연속 구간을 유지하며 이동하는 특화된 형태로 볼 수 있다. 투 포인터는 양끝에서 좁혀오는 방식과 같은 방향 이동 방식 모두 가능하며, 슬라이딩 윈도우는 보통 `left`, `right`가 같은 방향으로 이동하면서 현재 구간 상태를 갱신한다.

**Q2. 정렬 배열에서 두 수의 합이 target인지 찾을 때 투 포인터가 왜 O(N)인가요?**  
> 핵심 답변: `left`와 `right`가 각각 한 방향으로만 이동하기 때문이다. 각 포인터는 최대 `N`번 이하로 이동하므로 전체 이동 횟수는 선형적이다. 정렬되어 있기 때문에 현재 합이 작으면 `left`를 이동해 합을 키우고, 크면 `right`를 이동해 합을 줄이는 판단이 가능하다.

**Q3. 슬라이딩 윈도우가 음수가 포함된 배열에서 항상 동작하지 않는 이유는 무엇인가요?**  
> 핵심 답변: 가변 크기 슬라이딩 윈도우는 보통 `right`를 확장하면 합이 증가하고 `left`를 이동하면 합이 감소한다는 단조성을 이용한다. 하지만 음수가 포함되면 원소를 추가해도 합이 줄거나, 제거해도 합이 늘 수 있다. 따라서 “합이 S 이상인 최소 길이” 같은 문제에서 단순 윈도우 로직이 틀릴 수 있다.

**Q4. 누적 합을 사용하면 어떤 경우에 시간 복잡도가 개선되나요?**  
> 핵심 답변: 동일한 배열에 대해 구간 합 질의가 여러 번 들어오는 경우에 유리하다. 전처리로 prefix 배열을 `O(N)`에 만들고, 각 구간 합을 `O(1)`에 계산할 수 있다. 질의 수가 많을수록 매번 구간을 순회하는 `O(N)` 방식보다 큰 성능 이점이 있다.

**Q5. Rate Limiting을 구현할 때 슬라이딩 윈도우를 사용하면 어떤 장점과 주의점이 있나요?**  
> 핵심 답변: 장점은 최근 시간 구간을 기준으로 요청 수를 더 정확히 제한할 수 있어 고정 윈도우의 경계 버스트 문제를 줄일 수 있다는 점이다. 주의점은 사용자별 요청 타임스탬프 저장으로 메모리 사용량이 증가할 수 있고, 분산 서버 환경에서는 인스턴스 간 상태 공유가 필요하다는 점이다. TTL, 저장 크기 제한, 중앙 저장소, API Gateway 또는 WAF 활용을 고려해야 한다.

## 관련 개념

- [[시간 복잡도]] - 투 포인터, 슬라이딩 윈도우, 누적 합은 주로 `O(N^2)` 탐색을 `O(N)` 또는 `O(1)` 질의로 줄이기 위해 사용된다.
- [[공간 복잡도]] - 누적 합은 추가 배열을 사용해 시간 비용을 줄이는 대표적인 시간-공간 트레이드오프 사례다.
- [[배열]] - 세 기법 모두 배열 같은 인덱스 기반 선형 자료구조에서 가장 자주 사용된다.
- [[문자열 알고리즘]] - 부분 문자열 탐색, 중복 없는 최장 부분 문자열, 애너그램 검색 등에 슬라이딩 윈도우가 활용된다.
- [[정렬]] - 정렬된 배열에서는 투 포인터로 합, 차이, 중복 제거 문제를 효율적으로 해결할 수 있다.
- [[큐]] - 슬라이딩 윈도우에서 오래된 이벤트를 제거하고 새 이벤트를 추가할 때 큐 자료구조가 자주 사용된다.
- [[해시 테이블]] - 슬라이딩 윈도우에서 문자 빈도, 사용자별 요청 수, 이벤트 카운트를 관리할 때 사용된다.
- [[이진 탐색]] - 정렬된 데이터에서 구간의 시작과 끝을 찾는 데 사용할 수 있으며, 누적 합과 결합해 최적화 문제를 풀 수 있다.
- [[차분 배열]] - 누적 합의 반대 방향 아이디어로, 구간 업데이트를 효율적으로 처리할 때 사용된다.
- [[펜윅 트리]] - 값 변경이 있는 배열에서 prefix sum 질의를 효율적으로 처리하기 위한 자료구조다.
- [[세그먼트 트리]] - 구간 합, 구간 최댓값, 구간 최솟값 등 다양한 구간 질의를 처리하는 자료구조다.
- [[Rate Limiting]] - 슬라이딩 윈도우가 실제 보안 및 API 제어에서 자주 연결되는 대표적인 응용 개념이다.
- [[시계열 데이터]] - 시간 구간 기반 집계, 이동 평균, 최근 구간 분석에서 슬라이딩 윈도우와 누적 합이 중요하다.
- [[포함-배제 원리]] - 2차원 누적 합에서 직사각형 영역 합을 계산할 때 중복 제거를 위해 사용된다.
