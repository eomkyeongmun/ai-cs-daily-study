# 고급 자료구조 - 트라이(Trie), 분리 집합(Disjoint Set / Union-Find)

## 핵심 개념

## 트라이(Trie)

트라이(Trie)는 문자열 집합을 저장하고 탐색하기 위한 트리 기반 자료구조이다. 핵심 아이디어는 문자열 전체를 하나의 키로 비교하지 않고, 문자를 하나씩 따라가며 경로로 표현하는 것이다. 예를 들어 `cat`, `car`, `care`를 저장하면 `c -> a -> t`, `c -> a -> r -> e`처럼 공통 접두사 `ca`를 공유한다. 이 때문에 트라이는 **접두사 검색**, **자동완성**, **사전 검색**, **IP 라우팅**, **금칙어 필터링**, **문자열 집합 membership 검사**에 강하다.

트라이의 탐색 시간은 일반적으로 저장된 문자열 개수 `N`보다 문자열 길이 `L`에 더 직접적으로 의존한다. 즉, 어떤 단어가 있는지 확인할 때 전체 단어 목록을 훑는 대신 문자의 길이만큼 노드를 따라가면 된다. 해시 테이블도 평균적으로 빠른 검색을 제공하지만, 트라이는 “`app`으로 시작하는 모든 단어 찾기” 같은 접두사 기반 연산에서 특히 유리하다. 반면 각 노드가 자식 포인터 또는 맵을 가져야 하므로 메모리 사용량이 커질 수 있다. 이를 줄이기 위해 압축 트라이, Radix Tree, Patricia Trie 같은 변형이 사용된다.

## 분리 집합(Disjoint Set / Union-Find)

분리 집합은 여러 원소가 서로 겹치지 않는 집합들로 나뉘어 있을 때, 두 원소가 같은 집합에 속하는지 빠르게 확인하고, 두 집합을 합치는 자료구조이다. 대표 연산은 `find(x)`와 `union(a, b)`이다. `find(x)`는 원소 `x`가 속한 집합의 대표자를 찾고, `union(a, b)`는 두 원소가 속한 집합을 하나로 합친다.

분리 집합은 그래프 알고리즘에서 매우 중요하다. 예를 들어 크루스칼 알고리즘은 간선을 가중치 순으로 정렬한 뒤, 간선을 추가할 때 사이클이 생기는지 Union-Find로 검사한다. 또한 네트워크 연결성 판정, 동적 연결 컴포넌트 관리, 이미지의 연결 요소 라벨링, 계정 병합 문제 등에도 사용된다. 경로 압축과 union by rank 또는 union by size를 함께 사용하면 실제 사용에서 매우 빠르게 동작하며, 이론적으로도 거의 상수 시간에 가까운 성능을 보인다.

## 내부 동작 원리

## 트라이의 내부 동작 원리

트라이의 각 노드는 보통 다음 정보를 가진다.

```text
TrieNode
- children: 문자 -> TrieNode
- isEnd: 이 노드가 어떤 문자열의 끝인지 여부
- value: 선택 사항, 단어에 연결된 값
```

예를 들어 `to`, `tea`, `ten`, `in`, `inn`을 저장하면 구조는 다음과 같다.

```text
(root)
 ├── t
 │   ├── o  [end: to]
 │   └── e
 │       ├── a [end: tea]
 │       └── n [end: ten]
 └── i
     └── n [end: in]
         └── n [end: inn]
```

### 삽입 과정

문자열 `tea`를 삽입한다고 하자.

1. 루트에서 시작한다.
2. 문자 `t`가 자식에 없으면 새 노드를 만든다.
3. 다음 문자 `e`로 이동한다.
4. 다음 문자 `a`로 이동한다.
5. 마지막 문자에 도달하면 `isEnd = true`로 표시한다.

의사코드:

```text
insert(word):
    node = root
    for ch in word:
        if ch not in node.children:
            node.children[ch] = new TrieNode()
        node = node.children[ch]
    node.isEnd = true
```

### 검색 과정

단어 `ten`을 찾을 때는 `t -> e -> n` 경로가 존재하는지 확인한다. 경로가 존재하더라도 마지막 노드의 `isEnd`가 `true`여야 완전한 단어로 존재한다고 판단한다. 예를 들어 `te` 경로가 있어도 `isEnd`가 아니라면 `te`는 저장된 단어가 아니다.

```text
search(word):
    node = root
    for ch in word:
        if ch not in node.children:
            return false
        node = node.children[ch]
    return node.isEnd
```

### 접두사 검색

`te`로 시작하는 단어를 찾으려면 먼저 `t -> e` 노드까지 이동한다. 그 노드 아래의 모든 하위 노드를 DFS 또는 BFS로 순회하면 `tea`, `ten` 같은 단어를 얻을 수 있다.

```text
startsWith(prefix):
    node = root
    for ch in prefix:
        if ch not in node.children:
            return []
        node = node.children[ch]
    return collectAllWordsBelow(node)
```

### 시간 복잡도

- 삽입: `O(L)`
- 검색: `O(L)`
- 접두사 탐색: `O(P + K)`
  - `P`: 접두사 길이
  - `K`: 접두사 아래에서 실제로 수집하는 결과 크기

단, 자식 저장 방식에 따라 상수항이 달라진다. 알파벳 소문자만 다룬다면 길이 26 배열을 사용할 수 있고, 유니코드나 다양한 문자 집합을 다룬다면 해시맵을 사용하는 경우가 많다.

## 압축 트라이 / Radix Tree

일반 트라이는 한 문자마다 노드를 만들기 때문에 긴 문자열이 많으면 노드 수가 커진다. 압축 트라이는 자식이 하나뿐인 연속 노드를 하나의 간선 라벨로 압축한다.

일반 트라이:

```text
root
 └── c
     └── o
         └── m
             └── p
                 └── u
                     └── t
                         └── e
```

압축 트라이:

```text
root
 └── "compute"
```

Radix Tree 또는 Patricia Trie는 이런 압축 방식을 활용해 메모리 사용을 줄이고 탐색 단계를 줄이는 데 사용된다. IP 라우팅처럼 비트 단위 prefix matching이 중요한 영역에서도 계열 자료구조가 활용된다.

## 분리 집합의 내부 동작 원리

분리 집합은 보통 배열 두 개로 구현한다.

```text
parent[x]: x의 부모 노드
rank[x] 또는 size[x]: 트리 높이 또는 집합 크기 추정값
```

초기 상태에서 각 원소는 자기 자신을 대표자로 가진다.

```text
원소:    1  2  3  4  5
parent: 1  2  3  4  5
```

각 원소가 하나의 독립 집합이다.

```text
{1}, {2}, {3}, {4}, {5}
```

### find 연산

`find(x)`는 `x`가 속한 집합의 대표자를 찾는다.

```text
find(x):
    if parent[x] != x:
        parent[x] = find(parent[x])  // 경로 압축
    return parent[x]
```

경로 압축 전:

```text
1 -> 2 -> 3 -> 4
          대표자: 4
```

`find(1)` 호출 후:

```text
1 ─┐
2 ─┼──> 4
3 ─┘
4 ───> 4
```

중간 노드들이 직접 대표자를 가리키도록 바뀌므로 이후 탐색이 빨라진다.

### union 연산

`union(a, b)`는 `a`와 `b`의 대표자를 찾은 뒤, 서로 다르면 한쪽을 다른 쪽 아래에 붙인다.

```text
union(a, b):
    rootA = find(a)
    rootB = find(b)

    if rootA == rootB:
        return

    if rank[rootA] < rank[rootB]:
        parent[rootA] = rootB
    else if rank[rootA] > rank[rootB]:
        parent[rootB] = rootA
    else:
        parent[rootB] = rootA
        rank[rootA] += 1
```

### union by size 예시

초기:

```text
{1}, {2}, {3}, {4}, {5}
```

`union(1, 2)`:

```text
{1, 2}, {3}, {4}, {5}
```

`union(3, 4)`:

```text
{1, 2}, {3, 4}, {5}
```

`union(2, 3)`:

```text
{1, 2, 3, 4}, {5}
```

`find(1) == find(4)`이면 1과 4는 같은 집합에 속한다.

### 시간 복잡도

경로 압축과 union by rank 또는 union by size를 함께 사용하면 연산의 amortized 시간 복잡도는 `O(α(N))`로 알려져 있다. 여기서 `α(N)`은 inverse Ackermann function이며, 실제 입력 크기에서는 매우 작게 증가한다. 실무적으로는 거의 상수 시간처럼 취급되는 경우가 많다.

## 실제 시스템 연결

## 트라이와 실제 시스템

### 1. Linux 커널의 IP 라우팅

Linux 커널의 IPv4 라우팅 테이블 구현에는 `fib_trie`라는 트라이 계열 구조가 사용되는 것으로 알려져 있다. IP 라우팅에서는 목적지 IP 주소에 대해 가장 긴 prefix가 일치하는 라우트를 찾는 **Longest Prefix Match**가 핵심이다.

예를 들어 라우팅 규칙이 다음과 같다고 하자.

```text
10.0.0.0/8      -> gateway A
10.1.0.0/16     -> gateway B
10.1.2.0/24     -> gateway C
```

목적지 IP가 `10.1.2.33`이면 `/8`, `/16`, `/24`가 모두 일치하지만 가장 구체적인 `/24` 경로가 선택된다. 이런 prefix 기반 검색은 트라이 계열 자료구조와 잘 맞는다.

### 2. Nginx의 Radix Tree

Nginx 소스 코드에는 radix tree 관련 구현이 존재하며, IP 주소 범위나 prefix 기반 매칭에 사용될 수 있다. 예를 들어 특정 IP 대역에 따라 설정을 달리하거나 접근 제어를 수행하는 기능은 prefix tree 계열 구조와 연결된다.

⚠️ 확인 필요: Nginx의 특정 모듈이나 버전에 따라 radix tree가 사용되는 위치와 방식은 달라질 수 있으므로, 정확한 내부 구현은 해당 버전의 소스 코드 확인이 필요하다.

### 3. 검색 엔진과 자동완성

검색창 자동완성은 사용자가 입력한 접두사를 기반으로 후보 단어를 빠르게 보여줘야 한다. 이때 트라이, 압축 트라이, FST(Finite State Transducer) 등 접두사 기반 구조가 활용될 수 있다. 다만 대규모 검색 엔진은 단순 트라이만으로 구성되지 않고, 랭킹 모델, 빈도 통계, 개인화, 캐시, 역색인 등과 함께 동작한다.

⚠️ 확인 필요: Google, AWS, GCP 등 특정 상용 검색 서비스가 내부적으로 어떤 자료구조를 사용하는지는 공개되지 않은 부분이 많으므로 단정하기 어렵다.

## 분리 집합과 실제 시스템

### 1. 네트워크 연결성 분석 도구

분리 집합은 “현재 두 노드가 같은 연결 컴포넌트에 있는가?”를 빠르게 확인하는 데 적합하다. 예를 들어 네트워크 토폴로지 분석 도구에서 서버, 스위치, 라우터를 정점으로 보고 연결 링크를 간선으로 보면, Union-Find로 연결 컴포넌트를 빠르게 계산할 수 있다.

```text
서버 A ─ 스위치 1 ─ 서버 B

서버 C ─ 스위치 2
```

위 구조에서 A와 B는 같은 집합, C는 다른 집합으로 분류된다.

### 2. 크루스칼 알고리즘 기반 최소 신장 트리

분리 집합은 최소 신장 트리 알고리즘인 Kruskal 알고리즘의 핵심 구성 요소다. 네트워크 설계, 케이블링 비용 최소화, 그래프 기반 최적화 문제에서 “간선을 추가해도 사이클이 생기지 않는가?”를 검사하는 데 사용된다.

```text
간선 후보:
A-B 비용 1
B-C 비용 2
A-C 비용 3

A-B 선택
B-C 선택
A-C는 사이클 생성 → 제외
```

이때 `find(A) == find(C)`이면 이미 같은 컴포넌트이므로 해당 간선은 제외한다.

### 3. 이미지 처리의 연결 요소 라벨링

이미지에서 인접한 픽셀들이 같은 객체에 속하는지 판정하는 연결 요소 라벨링 알고리즘에서 Union-Find가 사용될 수 있다. 예를 들어 흑백 이미지에서 이어진 검은 픽셀 영역을 하나의 객체로 묶을 때, 인접 픽셀들을 union하고 최종적으로 대표자를 기준으로 라벨을 부여한다.

⚠️ 확인 필요: 특정 이미지 처리 라이브러리의 내부 구현은 버전과 알고리즘 선택에 따라 달라질 수 있으므로, 특정 라이브러리가 항상 Union-Find를 사용한다고 일반화하면 안 된다.

## 클라우드 연결

## 트라이와 클라우드

### 1. API Gateway, Ingress, Reverse Proxy의 경로 매칭

클라우드 환경에서는 HTTP 요청 경로를 기준으로 서비스를 라우팅하는 일이 많다.

```text
/api/users      -> user-service
/api/orders     -> order-service
/static         -> static-service
```

이런 prefix 기반 경로 매칭은 트라이 또는 radix tree와 잘 맞는다. 예를 들어 Kubernetes Ingress Controller, API Gateway, Reverse Proxy는 요청 경로, 호스트명, 헤더 조건을 바탕으로 백엔드 서비스를 선택한다. 실제 구현은 제품마다 다르지만, prefix matching 문제 자체는 트라이 계열 자료구조로 모델링할 수 있다.

⚠️ 확인 필요: AWS API Gateway, GCP Cloud Load Balancing, Kubernetes Ingress Controller의 특정 구현체가 내부적으로 트라이를 사용하는지는 공개 문서만으로 단정하기 어렵다.

### 2. DNS, 서비스 디스커버리, 접두사 기반 탐색

DNS 이름이나 서비스 이름은 계층 구조를 가진다.

```text
api.prod.example.com
db.prod.example.com
api.dev.example.com
```

문자열 prefix 또는 suffix 기반 탐색이 필요한 시스템에서는 트라이류 구조가 응용될 수 있다. 다만 DNS는 일반적인 문자열 트라이와 완전히 같은 방식으로만 동작하는 것은 아니며, 캐시, zone file, 해시 테이블, 트리 구조 등 여러 구현 방식이 가능하다.

### 3. 컨테이너 이미지 레지스트리 검색

컨테이너 이미지 이름은 다음처럼 계층적인 문자열 구조를 가진다.

```text
registry.example.com/team/service:tag
```

이미지 이름 검색, namespace 자동완성, prefix 기반 필터링을 구현할 때 트라이를 사용할 수 있다. 이는 Docker Registry나 사내 이미지 레지스트리 검색 기능을 구현할 때 응용 가능한 설계이다.

⚠️ 확인 필요: Docker Hub, Amazon ECR, Google Artifact Registry가 내부적으로 트라이를 사용한다고 공개적으로 확정된 것은 아니다.

## 분리 집합과 클라우드

### 1. Kubernetes 리소스 관계 분석

Kubernetes에서는 Pod, Service, Endpoint, Node, NetworkPolicy 등 다양한 리소스가 관계를 가진다. 운영 도구를 만들 때 이 관계를 그래프로 모델링하고, 서로 연결된 리소스 집합을 찾는 데 Union-Find를 사용할 수 있다.

예시:

```text
Service A -> Pod 1
Service A -> Pod 2
Pod 1 -> Node X
Pod 2 -> Node X
```

이 경우 `Service A`, `Pod 1`, `Pod 2`, `Node X`를 하나의 연결 컴포넌트로 묶어 장애 영향 범위를 분석할 수 있다.

### 2. VPC 네트워크 연결성 검증

AWS VPC, GCP VPC, Azure Virtual Network 같은 클라우드 네트워크에서는 서브넷, 라우팅 테이블, 피어링, VPN, Transit Gateway 등으로 연결성이 결정된다. 이를 단순화한 그래프로 만들면 Union-Find로 연결된 네트워크 그룹을 빠르게 계산할 수 있다.

```text
VPC A -- Peering -- VPC B
VPC C -- VPN ----- On-prem
```

여기서 A와 B는 같은 연결 그룹으로 묶을 수 있다. 다만 실제 네트워크 도달성은 보안 그룹, NACL, 방화벽, 라우트 우선순위, NAT, 비대칭 라우팅 등도 고려해야 하므로 Union-Find만으로 완전한 판단은 어렵다.

### 3. IaC 검증 도구

Terraform, Pulumi, CloudFormation 같은 IaC 설정을 분석할 때 리소스 간 의존성을 그래프로 만들 수 있다. Union-Find는 “어떤 리소스들이 같은 연결 그룹에 속하는가?”를 찾는 데 활용할 수 있다. 예를 들어 특정 데이터베이스에 도달 가능한 애플리케이션 그룹을 정적으로 분석하는 보조 도구를 만들 수 있다.

⚠️ 확인 필요: Terraform, Pulumi, CloudFormation 자체가 내부적으로 Union-Find를 사용한다고 단정할 수는 없다. 여기서는 IaC 분석 도구를 구현할 때의 응용 가능성을 설명한 것이다.

## 보안 연결

## 트라이와 보안

### 1. 금칙어 필터링과 악성 URL 탐지

트라이는 금칙어, 악성 도메인, 악성 URL prefix를 빠르게 탐색하는 데 활용될 수 있다. 예를 들어 URL 블랙리스트가 다음과 같다면:

```text
malware.example.com
phishing.example.net/login
bad-domain.org
```

입력 URL이 특정 prefix나 도메인 패턴과 일치하는지 빠르게 검사할 수 있다. 보안 장비나 웹 필터링 시스템에서 유사한 prefix matching 문제가 자주 등장한다.

단, 실제 악성 URL 탐지는 단순 문자열 매칭만으로 충분하지 않다. URL 인코딩, 유니코드 동형 문자, 대소문자 정규화, punycode, 경로 정규화, 리다이렉션, 짧은 URL 등을 고려해야 한다.

### 2. 입력 정규화 문제

트라이 기반 필터링에서 가장 흔한 실수는 저장된 패턴과 입력 문자열의 정규화 방식이 다르다는 것이다.

예:

```text
차단 목록: /admin
입력: /%61dmin
```

`%61`은 ASCII 문자 `a`를 의미하므로 실제 경로는 `/admin`일 수 있다. 정규화를 하지 않으면 우회가 가능하다.

모범 사례:

- URL 디코딩 순서를 명확히 한다.
- 중복 슬래시, `.` 및 `..` 경로를 정규화한다.
- 대소문자 구분 정책을 명확히 한다.
- 유니코드 정규화 방식을 통일한다.
- 필터링 전후의 문자열 표현이 일관되는지 테스트한다.

### 3. 메모리 고갈 공격

트라이는 많은 노드를 생성할 수 있기 때문에, 공격자가 매우 긴 문자열이나 공통 prefix가 거의 없는 대량의 입력을 삽입하게 하면 메모리 사용량이 급증할 수 있다. 특히 사용자 입력을 동적으로 트라이에 저장하는 시스템에서는 제한이 필요하다.

방어 방법:

- 최대 문자열 길이 제한
- 전체 노드 수 제한
- 입력 rate limit 적용
- 만료 정책 또는 LRU 캐시 적용
- 압축 트라이 또는 해시 기반 구조와의 혼합 사용

## 분리 집합과 보안

### 1. 권한 그룹 병합 오류

Union-Find를 권한, 계정, 조직, 리소스 그룹 병합에 사용할 때는 `union` 연산이 비가역적이라는 점에 주의해야 한다. 한 번 두 집합을 합치면 일반적인 Union-Find는 효율적인 분할 연산을 제공하지 않는다.

예를 들어 다음 상황을 생각할 수 있다.

```text
사용자 A와 B가 같은 조직으로 병합됨
B는 관리자 권한을 가짐
A도 같은 집합으로 간주되어 권한 상승 발생 가능
```

권한 체계에서는 “같은 연결 컴포넌트”가 곧 “같은 권한”을 의미하지 않도록 설계해야 한다.

### 2. 계정 병합과 신원 확인

이메일, 전화번호, OAuth 계정 등을 기준으로 사용자 계정을 병합할 때 Union-Find를 사용할 수 있다. 그러나 신원 확인이 충분하지 않은 상태에서 계정을 병합하면 계정 탈취나 개인정보 노출로 이어질 수 있다.

모범 사례:

- 병합 기준의 신뢰도를 구분한다.
- 이메일 소유권 검증을 수행한다.
- 전화번호 재사용 가능성을 고려한다.
- OAuth provider의 subject identifier를 정확히 사용한다.
- 자동 병합 전에 사용자 확인 절차를 둔다.

### 3. DoS와 비정상 입력

Union-Find 자체는 효율적이지만, 구현이 잘못되면 최악의 경우 성능 문제가 발생할 수 있다. 예를 들어 경로 압축이나 union by rank 없이 한쪽으로만 연결하면 긴 체인이 생긴다.

비효율적 구조:

```text
1 -> 2 -> 3 -> 4 -> 5 -> ... -> N
```

이 상태에서 반복적으로 `find(1)`을 호출하면 비용이 커진다. 공격자가 입력 순서를 조작할 수 있는 환경에서는 경로 압축과 union by size/rank를 반드시 적용하는 것이 좋다.

### 4. 동시성 문제

멀티스레드 환경에서 여러 스레드가 동시에 `union`과 `find`를 수행하면 parent 배열이 일관되지 않을 수 있다. 이는 잘못된 연결성 판단이나 무한 루프 같은 문제로 이어질 수 있다.

모범 사례:

- 락을 사용해 동기화한다.
- 병렬 Union-Find 알고리즘을 신중히 사용한다.
- 읽기 전용 단계와 병합 단계를 분리한다.
- 불변 스냅샷 기반으로 분석한다.

## 면접 질문

**Q1. 트라이와 해시 테이블의 차이는 무엇인가요?**  
> 핵심 답변: 해시 테이블은 전체 키에 대한 평균 `O(1)` 검색이 강점이고, 트라이는 문자열 길이 `L`에 비례해 탐색한다. 트라이는 접두사 검색, 자동완성, 사전순 순회에 유리하지만 메모리 사용량이 커질 수 있다.

**Q2. 트라이에서 `search("app")`와 `startsWith("app")`는 어떻게 다른가요?**  
> 핵심 답변: `search`는 경로가 존재하고 마지막 노드의 `isEnd`가 true여야 한다. `startsWith`는 해당 prefix 경로만 존재하면 true가 될 수 있다. 예를 들어 `apple`만 저장되어 있으면 `startsWith("app")`는 true지만 `search("app")`는 false일 수 있다.

**Q3. Union-Find에서 경로 압축은 왜 필요한가요?**  
> 핵심 답변: `find` 과정에서 지나간 노드들이 직접 대표자를 가리키도록 만들어 이후 탐색을 빠르게 한다. 경로 압축이 없으면 트리가 한쪽으로 길어져 `find`가 느려질 수 있다.

**Q4. Union-Find로 사이클을 어떻게 판별하나요?**  
> 핵심 답변: 간선 `(u, v)`를 추가하기 전에 `find(u)`와 `find(v)`를 비교한다. 두 대표자가 같으면 이미 같은 컴포넌트에 있으므로 간선을 추가하면 사이클이 생긴다. 다르면 `union(u, v)`를 수행한다.

**Q5. 트라이의 메모리 사용량을 줄이는 방법은 무엇인가요?**  
> 핵심 답변: 자식 포인터 배열 대신 해시맵을 사용하거나, 압축 트라이/Radix Tree/Patricia Trie를 사용해 단일 자식 경로를 압축할 수 있다. 또한 문자열 집합이 정적인 경우 DAWG나 FST 같은 구조를 고려할 수 있다.

## 관련 개념

- [[Radix Tree]] - 트라이에서 단일 자식 경로를 압축한 형태로, prefix matching과 메모리 절약에 사용된다.
- [[Patricia Trie]] - 비트 또는 문자열 prefix를 압축해 저장하는 트라이 계열 자료구조이다.
- [[Finite State Transducer]] - 대규모 사전, 자동완성, 검색 시스템에서 문자열 매핑을 압축 표현하는 데 활용될 수 있다.
- [[Hash Table]] - 문자열 검색에서 트라이와 자주 비교되는 자료구조이며, 전체 키 기반 조회에 강하다.
- [[Kruskal Algorithm]] - 최소 신장 트리를 구할 때 Union-Find를 핵심적으로 사용하는 그래프 알고리즘이다.
- [[Minimum Spanning Tree]] - 그래프의 모든 정점을 최소 비용으로 연결하는 문제이며, 분리 집합과 밀접하다.
- [[Connected Components]] - 그래프에서 서로 연결된 정점 집합을 의미하며, Union-Find로 효율적으로 관리할 수 있다.
- [[Path Compression]] - Union-Find의 `find` 성능을 개선하는 핵심 최적화 기법이다.
- [[Union by Rank]] - 작은 높이의 트리를 큰 높이의 트리에 붙여 Union-Find의 트리 높이를 줄이는 기법이다.
- [[Longest Prefix Match]] - IP 라우팅에서 가장 구체적인 prefix를 찾는 문제로, 트라이 계열 구조와 관련이 깊다.
