# 탐색 - 선형 탐색, 이진 탐색, Lower/Upper Bound

## 핵심 개념

탐색(Search)은 주어진 데이터 집합에서 원하는 값을 찾거나, 특정 조건을 만족하는 위치를 찾는 알고리즘적 작업이다. 자료구조 및 알고리즘에서 탐색은 매우 기본적이지만, 실제 성능에 큰 영향을 주는 핵심 개념이다. 대표적인 탐색 방법으로는 **선형 탐색(Linear Search)**, **이진 탐색(Binary Search)**, 그리고 정렬된 구간에서 경계 위치를 찾는 **Lower Bound / Upper Bound**가 있다.

**선형 탐색**은 배열이나 리스트의 처음부터 끝까지 순서대로 확인하며 원하는 값을 찾는 방식이다. 데이터가 정렬되어 있지 않아도 사용할 수 있고 구현이 매우 단순하지만, 최악의 경우 모든 원소를 확인해야 하므로 시간 복잡도는 `O(n)`이다. 작은 데이터나 정렬되지 않은 데이터에서는 실용적이다.

**이진 탐색**은 정렬된 데이터에서 중간 값을 기준으로 탐색 범위를 절반씩 줄여 나가는 방식이다. 매 단계마다 탐색 공간이 절반으로 줄어들기 때문에 시간 복잡도는 `O(log n)`이다. 단, 반드시 데이터가 정렬되어 있어야 하며, 인덱스를 통한 임의 접근이 효율적인 배열과 잘 맞는다.

**Lower Bound**와 **Upper Bound**는 이진 탐색의 응용이다. Lower Bound는 정렬된 배열에서 `target` 이상이 처음 나타나는 위치를 찾고, Upper Bound는 `target`보다 큰 값이 처음 나타나는 위치를 찾는다. 이 개념은 중복 원소가 있는 배열에서 특정 값의 개수를 구하거나, 삽입 위치를 결정하거나, 범위 질의를 처리할 때 매우 중요하다.

탐색 알고리즘은 단순히 “값을 찾는 방법”을 넘어, 데이터베이스 인덱스, 파일 시스템 검색, 클라우드 리소스 조회, 보안 로그 분석, 대규모 분산 시스템의 라우팅 및 스케줄링 등 다양한 시스템에서 성능과 확장성을 좌우하는 기반 기술이다.

## 내부 동작 원리

## 1. 선형 탐색

선형 탐색은 가장 단순한 탐색 방식이다. 배열의 첫 번째 원소부터 마지막 원소까지 차례대로 비교한다.

예시 배열:

```text
index:  0   1   2   3   4
value: 10  25  30  42  55
target = 42
```

동작 과정:

```text
10 == 42 ? 아니오
25 == 42 ? 아니오
30 == 42 ? 아니오
42 == 42 ? 예 → index 3 반환
```

의사코드:

```text
linear_search(arr, target):
    for i from 0 to length(arr) - 1:
        if arr[i] == target:
            return i
    return -1
```

시간 복잡도:

| 경우 | 시간 복잡도 |
|---|---|
| 최선 | `O(1)` |
| 평균 | `O(n)` |
| 최악 | `O(n)` |

공간 복잡도는 추가 메모리를 거의 사용하지 않으므로 일반적으로 `O(1)`이다.

선형 탐색은 정렬이 필요 없다는 장점이 있다. 하지만 데이터가 커질수록 비효율적이다. 예를 들어 원소가 1,000,000개인 배열에서 찾는 값이 마지막에 있거나 존재하지 않으면 최대 1,000,000번 비교해야 한다.

## 2. 이진 탐색

이진 탐색은 정렬된 배열에서만 사용할 수 있다. 핵심 아이디어는 현재 탐색 범위의 중간 값을 확인한 뒤, 찾는 값이 중간 값보다 작으면 왼쪽 절반만, 크면 오른쪽 절반만 탐색하는 것이다.

예시 배열:

```text
index:  0   1   2   3   4   5   6
value:  3   7  11  18  25  31  40
target = 25
```

초기 상태:

```text
left = 0, right = 6
mid = (0 + 6) / 2 = 3
arr[mid] = 18
```

다이어그램:

```text
[ 3, 7, 11, 18, 25, 31, 40 ]
 L          M              R

target 25 > arr[M] 18
→ 왼쪽 구간 제거, 오른쪽 탐색
```

다음 단계:

```text
left = 4, right = 6
mid = (4 + 6) / 2 = 5
arr[mid] = 31
```

```text
[ 3, 7, 11, 18, 25, 31, 40 ]
              L   M       R

target 25 < arr[M] 31
→ 오른쪽 구간 제거, 왼쪽 탐색
```

다음 단계:

```text
left = 4, right = 4
mid = 4
arr[mid] = 25
→ 찾음
```

의사코드:

```text
binary_search(arr, target):
    left = 0
    right = length(arr) - 1

    while left <= right:
        mid = left + (right - left) / 2

        if arr[mid] == target:
            return mid
        else if arr[mid] < target:
            left = mid + 1
        else:
            right = mid - 1

    return -1
```

`mid = left + (right - left) / 2` 형태를 사용하는 이유는 `left + right`가 매우 큰 정수일 때 오버플로우를 피하기 위해서다. 일부 언어나 환경에서는 정수 오버플로우가 실제 버그로 이어질 수 있다.

시간 복잡도:

| 경우 | 시간 복잡도 |
|---|---|
| 최선 | `O(1)` |
| 평균 | `O(log n)` |
| 최악 | `O(log n)` |

공간 복잡도:

| 구현 방식 | 공간 복잡도 |
|---|---|
| 반복문 기반 | `O(1)` |
| 재귀 기반 | 호출 스택 때문에 `O(log n)` |

## 3. Lower Bound

Lower Bound는 정렬된 배열에서 `target` 이상인 값이 처음 등장하는 위치를 찾는다.

즉, 다음 조건을 만족하는 가장 작은 인덱스 `i`를 찾는다.

```text
arr[i] >= target
```

예시:

```text
index:  0   1   2   3   4   5
value:  1   2   4   4   4   7
target = 4
```

Lower Bound 결과:

```text
index 2
```

왜냐하면 `4` 이상인 첫 번째 위치가 index 2이기 때문이다.

의사코드:

```text
lower_bound(arr, target):
    left = 0
    right = length(arr)

    while left < right:
        mid = left + (right - left) / 2

        if arr[mid] < target:
            left = mid + 1
        else:
            right = mid

    return left
```

여기서 `right = length(arr)`로 두는 이유는 정답이 배열의 끝 다음 위치일 수도 있기 때문이다. 예를 들어 모든 원소가 `target`보다 작다면 삽입 위치는 `length(arr)`가 된다.

예시:

```text
arr = [1, 2, 4, 4, 4, 7]
target = 5

lower_bound = 5
```

`5` 이상인 첫 번째 값은 `7`이고, 그 위치는 index 5다.

---

## 4. Upper Bound

Upper Bound는 정렬된 배열에서 `target`보다 큰 값이 처음 등장하는 위치를 찾는다.

즉, 다음 조건을 만족하는 가장 작은 인덱스 `i`를 찾는다.

```text
arr[i] > target
```

예시:

```text
index:  0   1   2   3   4   5
value:  1   2   4   4   4   7
target = 4
```

Upper Bound 결과:

```text
index 5
```

왜냐하면 `4`보다 큰 값이 처음 등장하는 위치는 값 `7`이 있는 index 5이기 때문이다.

의사코드:

```text
upper_bound(arr, target):
    left = 0
    right = length(arr)

    while left < right:
        mid = left + (right - left) / 2

        if arr[mid] <= target:
            left = mid + 1
        else:
            right = mid

    return left
```

Lower Bound와 Upper Bound의 차이는 비교 조건이다.

| 알고리즘 | 찾는 위치 | 조건 |
|---|---|---|
| Lower Bound | `target` 이상 첫 위치 | `arr[i] >= target` |
| Upper Bound | `target` 초과 첫 위치 | `arr[i] > target` |

---

## 5. 중복 원소 개수 구하기

정렬된 배열에서 특정 값의 개수는 다음과 같이 구할 수 있다.

```text
count(target) = upper_bound(target) - lower_bound(target)
```

예시:

```text
arr = [1, 2, 4, 4, 4, 7]
target = 4

lower_bound(4) = 2
upper_bound(4) = 5

count = 5 - 2 = 3
```

이 방식은 `O(log n)` 시간에 특정 값의 등장 횟수를 구할 수 있다.

## 실제 시스템 연결

## 1. C 표준 라이브러리와 이진 탐색

C 표준 라이브러리에는 `bsearch` 함수가 있다. 이 함수는 정렬된 배열에서 특정 값을 찾기 위한 이진 탐색 기반 인터페이스를 제공한다. 사용자는 비교 함수를 제공해야 하며, 배열은 비교 함수 기준으로 정렬되어 있어야 한다.

예시 개념:

```c
void *bsearch(
    const void *key,
    const void *base,
    size_t nmemb,
    size_t size,
    int (*compar)(const void *, const void *)
);
```

`bsearch`는 시스템 프로그래밍, 네이티브 라이브러리, 성능이 중요한 C 기반 프로그램에서 정렬된 데이터 검색에 사용할 수 있다.

---

## 2. C++ STL의 `lower_bound`, `upper_bound`

C++ 표준 라이브러리에는 `std::lower_bound`, `std::upper_bound`, `std::binary_search`, `std::equal_range`가 제공된다.

예시:

```cpp
vector<int> v = {1, 2, 4, 4, 4, 7};

auto lb = lower_bound(v.begin(), v.end(), 4);
auto ub = upper_bound(v.begin(), v.end(), 4);

int count = ub - lb; // 3
```

이 함수들은 정렬된 범위에서 동작한다. Random Access Iterator를 사용하는 `vector`에서는 효율적으로 동작하지만, 연결 리스트처럼 임의 접근이 느린 자료구조에서는 실제 성능 특성이 달라질 수 있다.

---

## 3. 데이터베이스 인덱스

관계형 데이터베이스의 인덱스는 일반적으로 정렬된 구조를 활용해 검색 속도를 높인다. 대표적으로 B-Tree 또는 B+Tree 계열 인덱스가 많이 사용된다. 단순 배열 기반 이진 탐색과 구조는 다르지만, “정렬된 키 공간에서 탐색 범위를 줄인다”는 점에서 이진 탐색과 유사한 사고방식을 가진다.

예를 들어 다음 SQL 질의가 있다고 하자.

```sql
SELECT *
FROM users
WHERE age >= 20 AND age < 30;
```

`age` 컬럼에 인덱스가 있다면 데이터베이스는 `20` 이상의 첫 위치와 `30` 미만의 범위를 찾아 필요한 레코드만 읽을 수 있다. 이는 개념적으로 Lower Bound와 Upper Bound를 활용한 범위 검색과 연결된다.

---

## 4. Linux 명령어와 탐색

Linux에서 파일이나 로그를 찾을 때 `grep`, `find`, `awk` 같은 도구를 자주 사용한다. 이들 도구는 입력 데이터를 순차적으로 읽으며 조건에 맞는 항목을 찾는 경우가 많다. 이는 개념적으로 선형 탐색과 유사하다.

예시:

```bash
grep "ERROR" application.log
```

위 명령은 로그 파일을 읽으면서 `"ERROR"` 문자열이 포함된 라인을 찾는다. 파일 전체를 순차적으로 확인할 수 있으므로, 입력 크기가 커질수록 처리 시간이 증가한다.

단, 실제 구현은 버퍼링, 문자열 매칭 최적화, 정규표현식 엔진 등에 따라 단순한 선형 탐색보다 복잡할 수 있다.

---

## 5. Nginx와 룰 매칭

Nginx 설정에서는 요청 URI, 호스트, 헤더 등에 따라 특정 location 블록이나 설정을 선택한다. 이 과정은 내부적으로 문자열 비교, prefix 매칭, 정규표현식 평가 등을 포함한다. 단순히 모든 설정을 순차 탐색하는 것만은 아니며, 설정 타입에 따라 최적화된 탐색 구조가 사용될 수 있다.

⚠️ 확인 필요: Nginx의 특정 버전 및 설정 유형별 location 매칭 내부 구현 세부사항은 버전에 따라 달라질 수 있으므로, 정확한 동작은 공식 문서와 해당 버전 소스 코드를 확인해야 한다.

## 클라우드 연결

## 1. Docker 이미지 레이어 조회

Docker 이미지는 여러 레이어로 구성된다. 컨테이너 실행 시 파일 시스템은 계층형으로 조합되어 보인다. 파일 접근 과정에서 어떤 레이어에 파일이 있는지 확인하는 동작은 내부 스토리지 드라이버에 따라 달라진다.

개념적으로는 여러 후보 중 원하는 파일 메타데이터를 찾는 탐색 문제가 된다. 단순히 순차적으로 찾는 경우는 선형 탐색과 유사한 비용 모델을 생각할 수 있고, 메타데이터 인덱스나 캐시가 있다면 더 빠른 탐색이 가능하다.

⚠️ 확인 필요: Docker의 파일 조회 과정은 overlay2 등 스토리지 드라이버, 커널 파일시스템, 캐시 상태에 따라 다르므로 단순한 선형 탐색이나 이진 탐색으로 일반화할 수 없다.

## 2. Kubernetes 스케줄링

Kubernetes 스케줄러는 Pod를 배치할 Node를 선택한다. 이 과정에서 노드 목록을 평가하고, 필터링과 스코어링을 수행한다. 노드 후보를 순회하며 조건을 검사하는 과정은 개념적으로 선형 탐색 또는 선형 스캔과 연결된다.

예를 들어 다음 조건을 확인할 수 있다.

```text
- CPU/메모리 요청량을 만족하는가?
- nodeSelector 조건을 만족하는가?
- taint/toleration 조건을 만족하는가?
- affinity/anti-affinity 조건을 만족하는가?
```

클러스터의 노드 수가 커질수록 모든 노드를 단순히 확인하는 비용은 증가할 수 있다. 그래서 실제 스케줄러는 캐시, 인덱싱, 플러그인 구조 등을 활용해 효율성을 높인다.

⚠️ 확인 필요: Kubernetes 스케줄러의 정확한 필터링 최적화 방식은 Kubernetes 버전과 설정, 활성화된 스케줄링 플러그인에 따라 다를 수 있다.

## 3. AWS DynamoDB와 키 기반 조회

AWS DynamoDB는 파티션 키와 정렬 키를 활용해 데이터를 조회할 수 있다. 정렬 키가 있는 테이블이나 인덱스에서는 특정 범위 조건으로 질의할 수 있다.

예시 조건:

```text
partition_key = "USER#123"
sort_key BETWEEN "ORDER#2024-01" AND "ORDER#2024-12"
```

이런 범위 조회는 정렬된 키 공간에서 시작 지점과 끝 지점을 찾는 개념과 연결된다. 알고리즘 관점에서는 Lower Bound / Upper Bound와 유사하게 “어디서부터 읽기 시작하고 어디서 멈출 것인가”가 중요하다.

다만 DynamoDB의 실제 내부 구현은 분산 저장소, 파티셔닝, 인덱싱, 복제 등 복잡한 요소를 포함한다.

⚠️ 확인 필요: DynamoDB의 내부 저장 엔진 세부 구현은 AWS가 모든 세부사항을 공개하지 않으므로, 이진 탐색으로 동작한다고 단정해서는 안 된다.

---

## 4. AWS S3 객체 목록 조회

S3는 버킷 내 객체를 키 이름 기준으로 나열할 수 있다. Prefix를 사용하면 특정 접두사를 가진 객체만 조회할 수 있다.

예시:

```text
logs/2025/01/
logs/2025/02/
logs/2025/03/
```

Prefix 기반 객체 조회는 정렬된 문자열 키 공간에서 특정 범위의 객체를 찾는 개념과 관련이 있다. Lower Bound처럼 특정 prefix가 시작되는 위치를 찾고, 해당 prefix 범위를 벗어나면 중단하는 방식으로 생각할 수 있다.

⚠️ 확인 필요: S3 내부의 객체 저장 및 인덱싱 방식은 공개적으로 완전히 설명되어 있지 않으므로, 실제 구현이 이진 탐색이라고 표현하는 것은 부정확하다.

## 5. 클라우드 로그 분석

AWS CloudWatch Logs, Google Cloud Logging, Azure Monitor 같은 로그 시스템에서는 시간 범위, 키워드, 필드 조건으로 로그를 조회한다. 단순 텍스트 로그 파일에서 특정 문자열을 찾는 것은 선형 탐색과 유사하지만, 대규모 로그 플랫폼은 인덱스, 파티셔닝, 압축, 분산 처리 등을 활용한다.

예시:

```text
timestamp >= T1 AND timestamp < T2
level = ERROR
```

시간순으로 정렬된 로그에서 특정 시간 범위를 찾는 과정은 Lower Bound / Upper Bound와 유사하다. 시작 시간 이상의 첫 로그 위치와 종료 시간 이상의 첫 위치를 찾으면 범위 내 로그만 처리할 수 있다.

## 보안 연결

## 1. 선형 탐색과 서비스 거부 공격

선형 탐색은 데이터가 커질수록 처리 시간이 선형으로 증가한다. 공격자가 매우 큰 입력이나 비효율적인 검색 조건을 반복적으로 보내면 CPU 사용량이 증가할 수 있다. 이는 서비스 거부 공격, 즉 DoS와 연결될 수 있다.

예시:

```text
- 매우 큰 JSON 배열에서 특정 값을 찾게 만드는 요청
- 대량의 로그나 문자열에서 반복 검색을 유도하는 요청
- 필터 조건이 인덱스를 타지 못해 전체 스캔을 유발하는 DB 질의
```

모범 사례:

```text
- 입력 크기 제한
- 요청당 처리 시간 제한
- 페이지네이션 적용
- 인덱스 설계
- 캐싱 활용
- Rate Limiting 적용
```

---

## 2. 이진 탐색의 전제 조건 검증

이진 탐색은 정렬된 데이터에서만 올바르게 동작한다. 정렬되지 않은 데이터에 이진 탐색을 적용하면 잘못된 결과가 나올 수 있다. 보안 관점에서는 권한 목록, 차단 목록, 허용 목록 같은 보안 정책 데이터에 잘못된 탐색을 적용하면 심각한 문제가 될 수 있다.

예를 들어 IP allowlist가 정렬되어 있다고 가정하고 이진 탐색을 수행했는데, 실제 데이터가 정렬되어 있지 않다면 허용되지 않아야 할 IP가 통과하거나, 허용되어야 할 IP가 차단될 수 있다.

모범 사례:

```text
- 탐색 전 정렬 불변식 보장
- 데이터 로딩 시 정렬 검증
- 테스트 케이스에 경계값 포함
- 보안 정책 데이터 변경 시 검증 파이프라인 적용
```

---

## 3. 경계 조건 오류와 인증/인가 문제

Lower Bound와 Upper Bound는 경계 조건이 매우 중요하다. `>=`, `>`, `<`, `<=` 중 어떤 비교를 사용하느냐에 따라 결과가 달라진다. 경계 조건 오류는 범위 기반 접근 제어에서 취약점으로 이어질 수 있다.

예시:

```text
허용 범위: user_id >= 1000 AND user_id < 2000
```

여기서 실수로 다음과 같이 구현하면 문제가 생길 수 있다.

```text
user_id <= 2000
```

그러면 `2000`이 포함되어서는 안 되는데 포함될 수 있다.

모범 사례:

```text
- 범위는 half-open interval [start, end) 형태로 명확히 정의
- Lower Bound / Upper Bound 의미를 코드 주석에 명시
- 경계값 테스트 작성
- 중복 데이터와 빈 구간 테스트 포함
```

---

## 4. 정수 오버플로우

이진 탐색에서 중간 인덱스를 계산할 때 다음과 같이 작성하는 경우가 있다.

```text
mid = (left + right) / 2
```

`left`와 `right`가 매우 큰 정수라면 일부 언어나 환경에서 `left + right`가 정수 범위를 초과할 수 있다. 이 문제는 버그나 잘못된 메모리 접근으로 이어질 수 있다.

더 안전한 방식:

```text
mid = left + (right - left) / 2
```

모범 사례:

```text
- 안전한 mid 계산 사용
- 인덱스 타입 범위 확인
- 언어별 정수 오버플로우 동작 이해
- 정적 분석 도구 사용
```

---

## 5. 타이밍 사이드 채널

탐색 알고리즘의 실행 시간은 입력 데이터나 위치에 따라 달라질 수 있다. 선형 탐색은 찾는 값이 앞에 있으면 빨리 끝나고, 뒤에 있거나 없으면 오래 걸린다. 이진 탐색도 비교 경로에 따라 실행 패턴이 달라질 수 있다.

일반 데이터 검색에서는 문제가 되지 않지만, 비밀 값 비교나 인증 토큰 검증에서 실행 시간이 입력에 따라 달라지면 타이밍 사이드 채널이 될 수 있다.

예시:

```text
- 토큰 문자열을 앞에서부터 비교하다가 다른 문자가 나오면 즉시 종료
- 비밀번호 해시 비교에서 조기 종료
```

모범 사례:

```text
- 비밀 값 비교에는 constant-time 비교 함수 사용
- 인증 토큰, MAC, 서명 검증에 일반 문자열 비교 사용 금지
- 실패 사유를 과도하게 상세히 노출하지 않기
```

## 면접 질문

**Q1. 선형 탐색과 이진 탐색의 차이는 무엇인가요?**  
> 핵심 답변: 선형 탐색은 정렬 여부와 관계없이 앞에서부터 순차적으로 확인하며 시간 복잡도는 `O(n)`이다. 이진 탐색은 정렬된 데이터에서 중간값을 기준으로 탐색 범위를 절반씩 줄이며 시간 복잡도는 `O(log n)`이다. 이진 탐색은 반드시 정렬 조건이 필요하다.

**Q2. 이진 탐색에서 `mid = left + (right - left) / 2`를 사용하는 이유는 무엇인가요?**  
> 핵심 답변: `left + right`가 큰 값일 경우 정수 오버플로우가 발생할 수 있기 때문이다. `left + (right - left) / 2`는 동일한 중간값을 계산하면서 오버플로우 위험을 줄인다.

**Q3. Lower Bound와 Upper Bound의 차이를 설명해보세요.**  
> 핵심 답변: Lower Bound는 정렬된 배열에서 `target` 이상인 첫 번째 위치를 찾는다. Upper Bound는 `target`보다 큰 첫 번째 위치를 찾는다. 즉 Lower Bound 조건은 `arr[i] >= target`, Upper Bound 조건은 `arr[i] > target`이다.

**Q4. 정렬된 배열에서 특정 값의 개수를 `O(log n)`에 구하는 방법은 무엇인가요?**  
> 핵심 답변: `upper_bound(target) - lower_bound(target)`를 계산하면 된다. Lower Bound는 해당 값이 처음 등장하는 위치, Upper Bound는 해당 값보다 큰 값이 처음 등장하는 위치이므로 두 인덱스 차이가 등장 횟수다.

**Q5. 이진 탐색을 사용할 수 없는 대표적인 경우는 무엇인가요?**  
> 핵심 답변: 데이터가 정렬되어 있지 않은 경우 사용할 수 없다. 또한 연결 리스트처럼 임의 접근이 비효율적인 자료구조에서는 이진 탐색의 이론적 장점이 실제 성능으로 이어지기 어렵다. 이진 탐색은 정렬된 데이터와 효율적인 인덱스 접근이 있을 때 적합하다.
