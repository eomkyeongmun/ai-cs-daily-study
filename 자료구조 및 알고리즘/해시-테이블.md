# 해시 테이블 - 해시 함수, 해시 충돌 해결(Chaining, Open Addressing)

## 핵심 개념

해시 테이블(Hash Table)은 **키(Key)를 해시 함수(Hash Function)에 넣어 얻은 해시값을 기반으로 데이터를 저장하고 조회하는 자료구조**이다. 배열은 인덱스를 알면 `O(1)`에 접근할 수 있지만, 문자열이나 객체 같은 임의의 키는 바로 배열 인덱스로 사용할 수 없다. 해시 테이블은 키를 정수 형태의 해시값으로 변환하고, 이를 버킷 배열의 인덱스로 매핑하여 빠른 삽입, 삭제, 조회를 가능하게 한다.

일반적으로 해시 테이블의 평균 시간 복잡도는 삽입, 삭제, 조회 모두 `O(1)`에 가깝다. 그러나 서로 다른 키가 같은 인덱스로 매핑되는 **해시 충돌(Hash Collision)** 이 발생할 수 있으며, 충돌이 많아지면 성능은 `O(n)`까지 악화될 수 있다. 따라서 좋은 해시 함수와 적절한 충돌 해결 전략은 해시 테이블 성능의 핵심이다.

해시 테이블은 프로그래밍 언어의 `Map`, `Dictionary`, `Object`, `Set` 구현뿐 아니라 데이터베이스 인덱스, 캐시, 네트워크 라우팅 테이블, 로드밸런서 설정 조회, 클라우드 서비스의 파티셔닝 전략 등 다양한 시스템에서 사용된다. 특히 대규모 시스템에서는 키를 빠르게 찾는 능력이 전체 응답 시간과 확장성에 직접적인 영향을 준다.

해시 테이블의 핵심 구성 요소는 다음과 같다.

- **해시 함수(Hash Function)**: 키를 정수 해시값으로 변환
- **버킷 배열(Bucket Array)**: 해시값을 기반으로 데이터를 저장하는 배열
- **충돌 해결 전략(Collision Resolution)**: 같은 인덱스에 여러 키가 매핑될 때 처리하는 방식
- **로드 팩터(Load Factor)**: `저장된 요소 수 / 버킷 수`
- **리사이징(Resizing, Rehashing)**: 로드 팩터가 커졌을 때 버킷 배열을 확장하고 재배치하는 과정

## 내부 동작 원리

## 1. 기본 동작 과정

해시 테이블의 기본 연산은 다음과 같이 동작한다.

### 삽입 과정

```text
put("apple", 10)

1. key = "apple"
2. hash("apple") 계산
3. index = hash("apple") % bucket_size
4. bucket[index] 위치에 ("apple", 10) 저장
```

예를 들어 버킷 크기가 8이고, `"apple"`의 해시값이 35라면:

```text
index = 35 % 8 = 3
```

따라서 `"apple"`은 3번 버킷에 저장된다.

```text
Bucket Array

index:   0    1    2    3          4    5    6    7
        ------------------------------------------------
value:  []   []   []  apple:10    []   []   []   []
```

### 조회 과정

```text
get("apple")

1. hash("apple") 계산
2. index = hash("apple") % bucket_size
3. bucket[index]에서 key가 "apple"인 항목 탐색
4. value 반환
```

중요한 점은 조회할 때도 삽입 시와 동일한 해시 함수를 사용해야 한다는 것이다.

---

## 2. 해시 함수

해시 함수는 임의 크기의 키를 고정된 크기의 해시값으로 변환한다.

좋은 해시 함수의 조건은 다음과 같다.

- 같은 키는 항상 같은 해시값을 반환해야 한다.
- 서로 다른 키는 가능한 한 고르게 분포되어야 한다.
- 계산 속도가 빨라야 한다.
- 특정 패턴의 키가 특정 버킷에 몰리지 않아야 한다.
- 보안이 중요한 환경에서는 공격자가 충돌을 쉽게 만들 수 없어야 한다.

예시:

```text
hash("apple")  -> 35
hash("banana") -> 82
hash("orange") -> 11
```

버킷 크기가 8이면:

```text
apple  -> 35 % 8 = 3
banana -> 82 % 8 = 2
orange -> 11 % 8 = 3
```

이때 `"apple"`과 `"orange"`는 같은 3번 버킷에 들어가므로 충돌이 발생한다.

---

## 3. 해시 충돌

해시 충돌은 서로 다른 키가 같은 버킷 인덱스로 매핑되는 현상이다.

```text
hash("apple")  % 8 = 3
hash("orange") % 8 = 3
```

```text
Bucket Array

index:   0    1    2       3                    4    5    6    7
        ----------------------------------------------------------------
value:  []   []  banana  apple, orange         []   []   []   []
```

해시 충돌은 해시 테이블에서 피할 수 없는 문제다. 가능한 키의 수는 매우 많지만 버킷 배열의 크기는 제한되어 있기 때문이다. 이를 비둘기집 원리로 설명할 수 있다.

충돌 해결 방식은 크게 두 가지로 나뉜다.

1. **Chaining**
2. **Open Addressing**

---

## 4. Chaining

Chaining은 하나의 버킷에 여러 개의 항목을 연결 리스트, 동적 배열, 트리 등의 자료구조로 저장하는 방식이다.

```text
index:   0
        [ ]

index:   1
        [ ]

index:   2
        [banana:20]

index:   3
        [apple:10] -> [orange:30]

index:   4
        [ ]
```

### 삽입

```text
put("orange", 30)

1. hash("orange") 계산
2. index = hash("orange") % bucket_size
3. 해당 버킷에 이미 apple이 있음
4. 같은 키가 없으면 체인 뒤에 orange 추가
```

### 조회

```text
get("orange")

1. index 계산
2. 해당 버킷의 체인을 순회
3. key가 "orange"인 노드를 찾으면 value 반환
```

### 삭제

```text
remove("apple")

1. index 계산
2. 해당 버킷의 체인을 순회
3. key가 "apple"인 노드를 제거
```

### 장점

- 구현이 비교적 직관적이다.
- 삭제가 쉽다.
- 로드 팩터가 1을 넘어도 동작할 수 있다.
- 클러스터링 문제에 상대적으로 덜 민감하다.

### 단점

- 추가 포인터 저장 공간이 필요하다.
- 연결 리스트를 사용하면 캐시 지역성이 떨어질 수 있다.
- 충돌이 심하면 한 버킷의 체인이 길어져 `O(n)` 성능이 될 수 있다.

---

## 5. Open Addressing

Open Addressing은 모든 데이터를 버킷 배열 내부에 저장하는 방식이다. 충돌이 발생하면 정해진 규칙에 따라 다른 빈 버킷을 찾아 저장한다.

```text
index:   0    1    2        3        4        5    6    7
        ----------------------------------------------------
value:  []   []  banana   apple   orange    []   []   []
```

여기서 `"orange"`는 원래 3번 버킷에 들어가야 했지만, 3번 버킷이 이미 사용 중이므로 4번 버킷에 저장되었다고 볼 수 있다.

Open Addressing의 대표적인 탐사 방식은 다음과 같다.

---

### 5.1 Linear Probing

충돌이 발생하면 다음 칸을 순서대로 확인한다.

```text
index = h(key)
index, index + 1, index + 2, index + 3, ...
```

예시:

```text
hash("apple")  % 8 = 3
hash("orange") % 8 = 3
```

```text
3번 버킷 충돌
-> 4번 버킷 확인
-> 비어 있으면 저장
```

```text
index:   0    1    2        3        4
        --------------------------------
value:  []   []   []      apple    orange
```

장점:

- 구현이 쉽다.
- 배열을 순차적으로 접근하므로 캐시 지역성이 좋다.

단점:

- **Primary Clustering**이 발생하기 쉽다.
- 연속된 점유 구간이 길어지면 탐색 비용이 증가한다.

---

### 5.2 Quadratic Probing

충돌이 발생하면 제곱 간격으로 탐사한다.

```text
index = h(key) + 1², h(key) + 2², h(key) + 3², ...
```

예시:

```text
h(key), h(key)+1, h(key)+4, h(key)+9 ...
```

장점:

- Linear Probing보다 Primary Clustering을 줄일 수 있다.

단점:

- Secondary Clustering은 여전히 발생할 수 있다.
- 테이블 크기와 탐사 수식에 따라 모든 버킷을 방문하지 못할 수 있다.

---

### 5.3 Double Hashing

충돌이 발생하면 두 번째 해시 함수를 이용해 탐사 간격을 정한다.

```text
index_i = (h1(key) + i * h2(key)) % table_size
```

장점:

- 클러스터링을 줄이는 데 효과적이다.
- 키마다 탐사 순서가 달라진다.

단점:

- 해시 함수를 두 개 계산해야 하므로 비용이 증가할 수 있다.
- `h2(key)`와 테이블 크기의 관계가 적절하지 않으면 모든 버킷을 탐사하지 못할 수 있다.

---

## 6. Open Addressing에서 삭제 문제

Open Addressing에서는 단순히 값을 삭제하고 빈 칸으로 만들면 조회가 깨질 수 있다.

예를 들어:

```text
index:   3        4
        ----------------
value:  apple   orange
```

`orange`는 원래 3번에 들어가야 했지만 충돌 때문에 4번에 저장되었다.

여기서 `apple`을 삭제해 3번을 빈 칸으로 만들면:

```text
get("orange")
1. hash("orange") % 8 = 3
2. 3번 버킷이 비어 있음
3. "orange"가 없다고 잘못 판단
```

이를 방지하기 위해 **삭제 표시(Tombstone)** 를 사용한다.

```text
index:   3           4
        --------------------
value:  DELETED    orange
```

조회 시 `DELETED`는 건너뛰고 계속 탐사한다. 다만 Tombstone이 많아지면 성능이 떨어지므로 주기적인 재해싱이 필요할 수 있다.

---

## 7. 로드 팩터와 리사이징

로드 팩터는 다음과 같이 계산한다.

```text
load factor = 저장된 원소 수 / 버킷 배열 크기
```

로드 팩터가 높아질수록 충돌 가능성이 증가한다. 따라서 많은 해시 테이블 구현은 일정 임계값을 넘으면 버킷 배열을 확장하고 모든 키를 다시 배치한다.

```text
기존 bucket_size = 8
새 bucket_size = 16

기존 index = hash(key) % 8
새 index = hash(key) % 16
```

버킷 크기가 바뀌면 인덱스 계산 결과도 달라질 수 있으므로 기존 데이터를 모두 다시 넣는 **rehashing** 과정이 필요하다.

## 실제 시스템 연결

## 1. 프로그래밍 언어의 Map / Dictionary

많은 프로그래밍 언어는 해시 테이블 기반의 자료구조를 제공한다.

- Java: `HashMap`, `HashSet`
- Python: `dict`, `set`
- JavaScript: `Map`, `Set`, 객체 프로퍼티 저장 구조 일부
- Go: `map`
- C++: `std::unordered_map`, `std::unordered_set`

이 자료구조들은 키 기반 조회를 빠르게 수행하기 위해 해시 함수를 사용한다. 다만 각 언어의 내부 구현은 버전과 런타임에 따라 다를 수 있다.

예를 들어 Java의 `HashMap`은 충돌이 많아질 경우 특정 조건에서 버킷 내부 구조를 연결 리스트에서 트리 구조로 전환할 수 있다. 이 방식은 최악의 경우 성능 악화를 줄이기 위한 설계다.

---

## 2. Linux Kernel

Linux 커널 내부에서도 해시 테이블은 널리 사용된다. 예를 들어 커널은 다양한 객체를 빠르게 찾기 위해 해시 기반 자료구조를 사용한다.

대표적으로 Linux 커널에는 다음과 같은 해시 관련 구조가 있다.

- `hlist`: 해시 버킷에 사용하기 좋은 단방향 변형 리스트 구조
- `rhashtable`: 크기 조정 가능한 해시 테이블 구현
- 네트워크 스택 내부의 연결 추적, 라우팅, 소켓 조회 등에서 해시 기반 조회 구조 사용

⚠️ 확인 필요: Linux 커널의 특정 서브시스템별 해시 테이블 구현 방식은 커널 버전과 설정에 따라 달라질 수 있다.

---

## 3. Nginx

Nginx는 설정 처리와 요청 라우팅 과정에서 빠른 문자열 조회가 필요하다. 예를 들어 서버 이름, MIME 타입, map 지시어 등은 빠른 조회 구조가 중요하다. Nginx 소스 코드에는 해시 관련 구조와 함수들이 있으며, 설정 단계에서 해시 테이블을 구성해 런타임 조회 비용을 줄이는 방식이 사용된다.

예시 연결:

```text
HTTP 요청 Host 헤더
-> 서버 이름 조회
-> 매칭되는 server block 선택
```

이 과정에서 문자열 기반 빠른 조회가 필요하므로 해시 테이블 개념과 연결된다.

---

## 4. 데이터베이스와 캐시 시스템

해시 테이블은 데이터베이스와 캐시 시스템에서도 자주 등장한다.

- DBMS의 Hash Index
- Hash Join
- Redis 내부 dictionary 구조
- Memcached의 키 조회 구조

Redis는 키-값 저장소이므로 키를 빠르게 찾는 자료구조가 핵심이다. Redis의 주요 딕셔너리 구현은 해시 테이블 기반으로 알려져 있으며, 점진적 리해싱(incremental rehashing)을 통해 큰 테이블 리사이징으로 인한 지연을 줄인다.

⚠️ 확인 필요: Redis 내부 구현 세부사항은 버전별로 달라질 수 있으므로 특정 버전 기준 확인이 필요하다.

---

## 5. 분산 시스템의 해싱

해시 함수는 단일 프로세스 내부 자료구조뿐 아니라 분산 시스템에서도 중요하다. 예를 들어 키를 여러 서버나 파티션에 나누어 저장할 때 해시값을 사용한다.

```text
partition = hash(user_id) % number_of_partitions
```

이 방식은 간단하지만 서버 수가 바뀌면 많은 키의 위치가 바뀔 수 있다. 이를 완화하기 위해 **Consistent Hashing**이 사용된다.

## 클라우드 연결

## 1. AWS DynamoDB와 파티션 키

AWS DynamoDB는 파티션 키를 기준으로 데이터를 분산 저장한다. 파티션 키의 선택은 데이터 분포와 처리량에 큰 영향을 준다. 특정 파티션 키에 요청이 몰리면 핫 파티션 문제가 발생할 수 있다.

해시 테이블 관점에서 보면 이는 해시 함수의 분포 문제와 유사하다.

```text
좋은 해시 테이블:
키가 버킷에 고르게 분산됨

좋은 DynamoDB 파티션 설계:
요청이 파티션에 고르게 분산됨
```

따라서 DynamoDB에서는 카디널리티가 높고 접근 패턴이 고르게 분산되는 파티션 키를 설계하는 것이 중요하다.

---

## 2. AWS S3와 객체 키 분산

Amazon S3는 객체 키를 기반으로 데이터를 저장하고 조회한다. 과거에는 특정 접두사(prefix)에 요청이 집중되지 않도록 키 이름을 분산시키는 설계가 권장되었으나, 현재는 S3가 높은 요청률을 자동으로 처리하도록 개선되었다고 AWS 문서에서 설명한다.

⚠️ 확인 필요: S3의 내부 파티셔닝 방식은 공개 문서에서 제한적으로만 설명되므로, 내부적으로 어떤 해시 구조를 사용하는지는 단정하지 않는 것이 좋다.

---

## 3. Kubernetes와 해시 기반 식별

Kubernetes 환경에서도 해시 개념은 자주 등장한다.

예시:

- ReplicaSet 이름에 Pod Template Hash가 포함될 수 있음
- ConfigMap 또는 Secret 변경 감지를 위해 해시 값을 annotation에 사용하는 배포 패턴
- 컨트롤러가 리소스를 빠르게 조회하기 위해 내부적으로 map 자료구조를 사용할 수 있음

예를 들어 Deployment가 ReplicaSet을 생성할 때 Pod 템플릿 변경 여부를 구분하기 위해 해시 기반 값을 활용한다.

⚠️ 확인 필요: Kubernetes 내부 구현은 버전별로 변경될 수 있으므로 특정 필드명과 알고리즘은 공식 문서나 소스 기준 확인이 필요하다.

---

## 4. Docker 이미지 레이어와 콘텐츠 주소화

Docker 및 OCI 이미지에서는 이미지 레이어와 매니페스트를 식별할 때 digest를 사용한다. digest는 일반적으로 암호학적 해시를 기반으로 하며, 콘텐츠가 같으면 같은 식별자를 갖고, 콘텐츠가 바뀌면 digest도 바뀐다.

이는 해시 테이블의 해시 함수와 목적이 다르다. 해시 테이블의 해시 함수는 빠른 버킷 인덱싱이 목적이고, Docker 이미지 digest는 무결성과 콘텐츠 식별이 목적이다. 그러나 둘 다 “데이터를 해시값으로 변환한다”는 공통점을 갖는다.

---

## 5. 로드밸런싱과 Consistent Hashing

클라우드 환경의 로드밸런서, 캐시 클러스터, 샤딩 시스템에서는 consistent hashing이 사용될 수 있다.

예시:

```text
hash(user_id) -> 해시 링 위치 결정
가장 가까운 서버에 요청 전달
```

서버가 추가되거나 제거되어도 전체 키를 재배치하지 않고 일부 키만 이동시키는 것이 장점이다.

활용 사례:

- 분산 캐시 노드 선택
- 샤딩된 데이터 저장소
- 세션 고정 로드밸런싱
- API Gateway 또는 Proxy 계층의 라우팅 전략

⚠️ 확인 필요: 특정 AWS, GCP, Nginx, Envoy 설정에서 consistent hashing 지원 여부와 동작 방식은 제품 버전 및 설정에 따라 다르므로 공식 문서 확인이 필요하다.

## 보안 연결

## 1. Hash Collision DoS

해시 테이블의 대표적인 보안 이슈는 **Hash Collision DoS**이다. 공격자가 의도적으로 같은 버킷에 몰리는 키를 대량으로 보내면, 해시 테이블의 평균 `O(1)` 성능이 `O(n)`에 가까워질 수 있다.

예를 들어 웹 서버가 HTTP 요청 파라미터를 해시 테이블로 파싱한다고 가정하자.

```text
POST /login

a1=value
a2=value
a3=value
...
```

공격자가 충돌을 유발하는 파라미터 이름을 대량으로 보내면 서버는 요청 파싱 과정에서 많은 시간을 소비할 수 있다.

```text
정상 상황:
param lookup -> O(1)

공격 상황:
모든 param이 같은 bucket에 저장
-> 체인 길이 증가
-> lookup/insert 비용 증가
-> CPU 사용량 증가
```

---

## 2. 방어 전략

Hash Collision DoS를 완화하기 위한 방법은 다음과 같다.

### 2.1 해시 시드 랜덤화

프로세스 실행 시 무작위 시드를 사용해 해시값을 계산하면 공격자가 충돌 키를 미리 만들기 어려워진다.

```text
hash(key, random_seed)
```

Python, Ruby, Perl 등 여러 런타임은 과거 해시 충돌 공격 이슈 이후 문자열 해시에 랜덤화를 도입했다.

⚠️ 확인 필요: 각 언어별 해시 랜덤화 도입 버전과 적용 범위는 언어 및 버전에 따라 다르다.

---

### 2.2 보안 해시 함수 사용

보안이 중요한 키에 대해서는 SipHash 같은 키드 해시 함수가 사용될 수 있다. SipHash는 짧은 문자열 해싱에서 해시 충돌 공격을 어렵게 만들기 위해 설계된 함수로, 여러 언어 런타임이나 시스템에서 사용 사례가 있다.

다만 암호학적 해시 함수는 일반 해시 테이블용 해시 함수보다 느릴 수 있으므로 성능과 보안 요구사항을 함께 고려해야 한다.

---

### 2.3 입력 크기 제한

웹 서버나 API 서버는 요청 파라미터 수, 헤더 수, JSON 필드 수 등에 제한을 두어야 한다.

예시:

- 최대 HTTP 헤더 크기 제한
- 최대 요청 바디 크기 제한
- 최대 파라미터 개수 제한
- JSON 중첩 깊이 제한
- 요청 처리 시간 제한

이는 충돌 공격뿐 아니라 일반적인 리소스 고갈 공격에도 효과적이다.

---

### 2.4 충돌 시 자료구조 전환

일부 구현은 한 버킷에 항목이 너무 많이 몰릴 경우 연결 리스트 대신 트리 구조를 사용해 최악의 성능을 완화한다.

예를 들어 Java `HashMap`은 특정 조건에서 충돌 버킷을 트리화하여 조회 성능 악화를 줄인다.

---

## 3. 암호학적 해시와 해시 테이블 해시의 차이

해시 테이블에서 사용하는 해시 함수와 SHA-256 같은 암호학적 해시는 목적이 다르다.

| 구분 | 해시 테이블 해시 | 암호학적 해시 |
|---|---|---|
| 주 목적 | 빠른 인덱싱 | 무결성, 인증, 충돌 저항성 |
| 속도 | 매우 중요 | 상대적으로 덜 중요 |
| 충돌 | 가능하지만 분포가 중요 | 충돌 찾기가 계산적으로 어려워야 함 |
| 사용 예 | HashMap, dict | TLS, Docker digest, 파일 무결성 |

해시 테이블의 해시 함수는 일반적으로 빠른 계산과 균등 분포를 우선한다. 반면 암호학적 해시는 충돌 저항성, 역상 저항성, 제2역상 저항성 같은 보안 속성이 중요하다.

## 면접 질문

**Q1. 해시 테이블이란 무엇이며 평균적으로 왜 O(1) 조회가 가능한가요?**  
> 핵심 답변: 키를 해시 함수로 정수 해시값으로 변환하고, 이를 배열 인덱스로 매핑하기 때문에 전체 데이터를 순회하지 않고 해당 버킷에 바로 접근할 수 있다. 단, 충돌이 적고 로드 팩터가 적절히 유지된다는 전제가 필요하다.

**Q2. 해시 충돌이란 무엇이며 왜 피할 수 없나요?**  
> 핵심 답변: 서로 다른 키가 같은 버킷 인덱스로 매핑되는 현상이다. 가능한 키 공간은 매우 크지만 실제 버킷 수는 유한하기 때문에 비둘기집 원리에 따라 충돌은 원천적으로 피할 수 없다.

**Q3. Chaining과 Open Addressing의 차이는 무엇인가요?**  
> 핵심 답변: Chaining은 각 버킷에 연결 리스트나 트리 같은 별도 자료구조를 두어 충돌 항목을 저장한다. Open Addressing은 충돌 시 같은 배열 안에서 다른 빈 슬롯을 탐사해 저장한다. Chaining은 삭제가 쉽고 로드 팩터가 1을 넘어도 가능하지만 포인터 오버헤드가 있다. Open Addressing은 캐시 지역성이 좋지만 삭제와 클러스터링 관리가 어렵다.

**Q4. Open Addressing에서 삭제 시 Tombstone이 필요한 이유는 무엇인가요?**  
> 핵심 답변: 충돌로 인해 뒤쪽 슬롯에 저장된 키가 있을 수 있기 때문이다. 중간 슬롯을 단순히 빈 칸으로 만들면 조회 과정이 조기 종료되어 실제 존재하는 키를 찾지 못할 수 있다. Tombstone은 “삭제되었지만 탐사는 계속해야 하는 위치”를 표시한다.

**Q5. 해시 테이블의 최악 시간 복잡도는 어떻게 O(n)이 될 수 있으며 이를 완화하는 방법은 무엇인가요?**  
> 핵심 답변: 많은 키가 같은 버킷에 몰리거나 Open Addressing에서 긴 탐사열이 생기면 조회와 삽입이 많은 항목을 순회해야 하므로 O(n)이 될 수 있다. 좋은 해시 함수, 로드 팩터 관리, 리사이징, 해시 랜덤화, 충돌 버킷의 트리화, consistent hashing과 같은 적절한 분산 전략으로 완화할 수 있다.
