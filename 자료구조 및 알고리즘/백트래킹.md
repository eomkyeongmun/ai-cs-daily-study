# 백트래킹 - 상태 공간 트리 탐색 및 가지치기(Pruning)

## 핵심 개념

## 백트래킹: 상태 공간 트리 탐색과 가지치기

백트래킹(Backtracking)은 가능한 해 후보를 **단계적으로 구성**하면서, 현재까지 만든 부분 해가 더 이상 유효한 해로 확장될 수 없다고 판단되면 그 지점에서 탐색을 중단하고 이전 상태로 되돌아가는 설계 패러다임이다. 대표적으로 N-Queen, 스도쿠, 순열/조합 생성, 부분집합 탐색, 그래프 색칠, 제약 만족 문제(CSP, Constraint Satisfaction Problem) 등에 사용된다.

백트래킹의 핵심은 문제를 **상태 공간 트리(State Space Tree)** 로 모델링하는 것이다. 트리의 각 노드는 “현재까지 선택한 결정들의 집합”을 의미하고, 간선은 다음 선택을 의미한다. 루트는 아무 선택도 하지 않은 초기 상태이며, 리프 노드는 완성된 후보 해 또는 더 이상 진행할 수 없는 상태를 나타낸다.

이때 모든 후보를 무작정 탐색하면 완전 탐색(Brute Force)과 다르지 않다. 백트래킹이 중요한 이유는 **가지치기(Pruning)** 를 통해 불필요한 탐색 공간을 크게 줄일 수 있기 때문이다. 예를 들어 N-Queen 문제에서 같은 열이나 대각선에 이미 퀸이 있다면, 그 배치는 더 이상 정답이 될 수 없으므로 이후 행을 탐색하지 않는다. 즉, 백트래킹은 “가능성을 체계적으로 탐색하되, 불가능한 경로는 조기에 버리는 알고리즘적 사고방식”이다.

백트래킹은 최악의 경우 여전히 지수 시간 복잡도를 가질 수 있지만, 적절한 제약 검사와 탐색 순서 최적화를 통해 실제 문제에서는 매우 강력하게 동작한다. 특히 제약 조건이 명확하고, 부분 해의 유효성을 빠르게 판단할 수 있는 문제에서 효과적이다.

## 내부 동작 원리

## 내부 동작 원리

백트래킹은 일반적으로 다음 과정을 반복한다.

1. 현재 상태에서 가능한 선택 후보를 구한다.
2. 각 후보를 하나씩 선택한다.
3. 선택 후의 상태가 유효한지 검사한다.
4. 유효하다면 다음 단계로 재귀적으로 탐색한다.
5. 탐색이 끝나면 선택을 취소하고 이전 상태로 돌아간다.
6. 불가능한 상태라면 그 하위 탐색은 수행하지 않는다.

이를 의사코드로 표현하면 다음과 같다.

```text
backtrack(state):
    if is_solution(state):
        record(state)
        return

    for choice in candidates(state):
        if is_valid(state, choice):
            apply(choice, state)
            backtrack(state)
            undo(choice, state)
```

여기서 중요한 함수는 다음과 같다.

| 구성 요소 | 의미 |
|---|---|
| `state` | 현재까지 구성한 부분 해 |
| `candidates(state)` | 현재 상태에서 선택 가능한 후보 |
| `is_valid(state, choice)` | 후보를 선택했을 때 제약 조건을 위반하지 않는지 검사 |
| `apply()` | 선택을 상태에 반영 |
| `undo()` | 선택 이전 상태로 복구 |
| `is_solution()` | 완전한 해에 도달했는지 판단 |

### 상태 공간 트리 예시

예를 들어 `{A, B, C}`의 순열을 만드는 문제를 생각해보자.

```text
                      []
          /            |            \
        [A]           [B]           [C]
      /    \         /    \        /    \
   [A,B] [A,C]   [B,A] [B,C]   [C,A] [C,B]
    |      |       |      |       |      |
[A,B,C][A,C,B][B,A,C][B,C,A][C,A,B][C,B,A]
```

각 노드는 현재까지 선택한 원소들의 순서를 의미한다. 순열 문제에서는 이미 선택한 원소를 다시 선택하면 안 되므로, “중복 선택 금지”가 가지치기 조건이 된다.

### 가지치기 예시: N-Queen

N-Queen 문제에서는 N×N 체스판에 N개의 퀸을 서로 공격하지 않도록 배치해야 한다. 일반적으로 한 행에 하나씩 퀸을 놓는 방식으로 상태를 구성한다.

```text
row 0: 가능한 열 선택
row 1: row 0의 퀸과 충돌하지 않는 열 선택
row 2: 이전 퀸들과 충돌하지 않는 열 선택
...
```

예를 들어 4-Queen에서 첫 번째 행의 0번 열에 퀸을 놓았다고 하자.

```text
Q . . .
. . . .
. . . .
. . . .
```

다음 행에서는 같은 열과 대각선이 불가능하다.

```text
Q x . .
x x . .
. . x .
. . . x
```

`x` 위치는 이미 공격받는 위치이므로 탐색하지 않는다. 이처럼 백트래킹은 상태 공간 트리를 모두 생성하지 않고, **해가 될 가능성이 없는 부분 트리를 통째로 제거**한다.

### 가지치기의 종류

#### 1. 제약 기반 가지치기

현재 상태가 문제의 제약 조건을 위반하면 탐색을 중단한다.

예:

- N-Queen에서 같은 열 또는 대각선 충돌
- 스도쿠에서 같은 행, 열, 3×3 박스에 같은 숫자 존재
- 그래프 색칠에서 인접 정점이 같은 색을 가짐

#### 2. 한계 기반 가지치기

최적화 문제에서 현재 상태가 이미 기존 최적해보다 나쁠 것이 확실하면 중단한다. 이는 분기 한정법(Branch and Bound)과 밀접하다.

예:

```text
현재 비용 + 남은 최소 예상 비용 >= 현재 최적 비용
```

이면 더 탐색하지 않는다.

#### 3. 중복 상태 가지치기

서로 다른 경로로 같은 상태에 도달할 수 있다면, 이미 방문한 상태를 다시 탐색하지 않는다. 이 경우 메모이제이션이나 방문 집합을 사용할 수 있다.

단, 순수 백트래킹은 일반적으로 DFS 기반 탐색이고, 중복 상태 제거를 적극적으로 사용하면 동적 계획법이나 그래프 탐색 기법과 결합된 형태가 된다.

### 재귀 호출과 스택

백트래킹은 대개 재귀 DFS로 구현된다. 각 재귀 호출은 현재 선택 상태를 호출 스택에 저장한다.

```text
backtrack(row = 0)
 └─ backtrack(row = 1)
     └─ backtrack(row = 2)
         └─ backtrack(row = 3)
```

해를 찾거나 더 이상 진행할 수 없으면 가장 최근 호출부터 반환되며, 이때 선택을 취소한다. 이를 “되돌아가기”라고 한다.

### 시간 복잡도

백트래킹의 최악 시간 복잡도는 보통 지수적이다.

예:

- 부분집합 탐색: `O(2^N)`
- 순열 탐색: `O(N!)`
- N-Queen: 최악의 경우 매우 큰 탐색 공간을 가짐

하지만 가지치기가 강력하게 적용되면 실제 탐색 노드 수는 크게 줄어든다. 따라서 백트래킹의 성능은 단순한 이론적 복잡도뿐 아니라 다음 요소에 크게 좌우된다.

- 제약 조건을 얼마나 빨리 검사하는가
- 후보 선택 순서를 어떻게 정하는가
- 불가능한 상태를 얼마나 일찍 발견하는가
- 중복 상태를 제거할 수 있는가

## 실제 시스템 연결

## 실제 시스템 연결

백트래킹은 단순한 알고리즘 문제 풀이에만 쓰이는 개념이 아니다. 실제 시스템에서도 “가능한 선택지를 탐색하고, 조건을 만족하지 않는 경로를 버리는 방식”은 다양한 형태로 등장한다.

### 1. 정규 표현식 엔진과 백트래킹

많은 정규 표현식 엔진은 패턴 매칭 과정에서 백트래킹을 사용한다. 예를 들어 `a+`와 같은 반복 패턴이나 `(a|aa)+` 같은 선택 패턴이 있을 때, 엔진은 입력 문자열에 대해 가능한 매칭 경로를 시도하고 실패하면 이전 선택 지점으로 돌아가 다른 경로를 탐색할 수 있다.

Nginx는 설정에서 정규 표현식을 사용할 수 있으며, 일반적으로 PCRE 계열 정규 표현식 라이브러리와 연동될 수 있다. 이때 복잡한 정규 표현식이 과도한 백트래킹을 유발하면 요청 처리 성능에 악영향을 줄 수 있다.

⚠️ 확인 필요: 특정 Nginx 빌드가 어떤 PCRE/PCRE2 버전과 어떤 옵션으로 컴파일되었는지는 배포판, 빌드 설정, 운영 환경에 따라 다르므로 실제 시스템에서는 `nginx -V` 등으로 확인해야 한다.

### 2. 패키지 의존성 해결

Linux 배포판의 패키지 관리자는 패키지 버전, 의존성, 충돌 관계를 고려하여 설치 가능한 조합을 찾아야 한다. 이 문제는 제약 만족 문제로 볼 수 있으며, 가능한 패키지 조합을 탐색하면서 충돌하는 경로를 제거하는 방식이 사용될 수 있다.

예를 들어 어떤 패키지 A가 B의 특정 버전을 요구하고, 다른 패키지 C가 B의 다른 버전과 충돌한다면, 패키지 관리자는 그 조합을 배제해야 한다. 이는 상태 공간 트리에서 불가능한 가지를 자르는 것과 유사하다.

⚠️ 확인 필요: 각 패키지 관리자가 내부적으로 사용하는 정확한 알고리즘은 구현체와 버전에 따라 다르다. 일부 시스템은 SAT solver 기반 접근을 사용하고, 일부는 휴리스틱이나 별도 의존성 해결 알고리즘을 사용한다.

### 3. 컴파일러와 제약 기반 탐색

컴파일러의 일부 최적화 문제, 예를 들어 레지스터 할당은 그래프 색칠 문제와 관련된다. 그래프 색칠은 대표적인 백트래킹 적용 문제다. 실제 컴파일러는 성능과 확장성을 위해 단순 백트래킹만 사용하지 않고 휴리스틱, 근사 알고리즘, 그래프 기반 알고리즘 등을 함께 사용한다.

즉, 백트래킹은 컴파일러 내부 문제를 이해하는 이론적 기반이 될 수 있지만, 실제 프로덕션 컴파일러는 문제 규모와 성능 요구 때문에 다양한 최적화 기법을 결합한다.

### 4. 스케줄링과 배치 문제

운영체제, 클라우드 플랫폼, 데이터센터에서는 작업을 어느 자원에 배치할지 결정해야 한다. 이 문제는 CPU, 메모리, 네트워크, affinity/anti-affinity, 장애 도메인, 비용 등의 제약을 포함한다.

Kubernetes의 기본 스케줄러는 일반적으로 후보 노드를 필터링하고 점수화하여 Pod를 배치한다. 이것은 전형적인 깊이 우선 백트래킹과 동일하다고 보기는 어렵지만, “제약 조건을 만족하지 않는 후보를 제거한다”는 점에서 가지치기 사고방식과 연결된다.

⚠️ 확인 필요: Kubernetes 스케줄러의 구체적인 동작은 버전과 설정, 플러그인 구성에 따라 달라질 수 있다.

## 클라우드 연결

## 클라우드 연결

백트래킹은 클라우드 환경에서 직접 알고리즘으로 실행되기도 하고, 클라우드 리소스 배치나 최적화 문제를 모델링하는 사고방식으로도 사용된다.

### 1. Docker와 컨테이너 기반 백트래킹 실행

백트래킹 알고리즘은 계산량이 커질 수 있으므로 실행 환경을 격리하고 재현 가능하게 만드는 것이 중요하다. Docker를 사용하면 동일한 코드와 의존성을 컨테이너 이미지로 패키징하여 여러 환경에서 동일하게 실행할 수 있다.

예를 들어 스도쿠 풀이기, 최적 경로 탐색기, 조합 최적화 solver를 Docker 이미지로 만들면 다음과 같은 장점이 있다.

- 실행 환경 일관성 확보
- CPU, 메모리 제한 설정 가능
- 실패한 탐색 작업 재실행 용이
- 여러 인스턴스에서 병렬 실행 가능

```bash
docker run --cpus="2" --memory="1g" solver-image
```

이처럼 리소스 제한을 설정하면 백트래킹 탐색이 과도하게 실행되어 호스트 시스템 전체에 영향을 주는 것을 줄일 수 있다.

### 2. Kubernetes와 탐색 작업 병렬화

백트래킹의 상태 공간 트리는 여러 하위 트리로 나눌 수 있다. 예를 들어 N-Queen에서 첫 번째 행의 열 선택을 기준으로 하위 문제를 분할할 수 있다.

```text
root
 ├─ col 0 subtree
 ├─ col 1 subtree
 ├─ col 2 subtree
 └─ col 3 subtree
```

Kubernetes에서는 각 하위 트리를 별도의 Job 또는 Pod로 실행할 수 있다. 이 방식은 백트래킹 자체의 논리를 바꾸지는 않지만, 탐색 공간을 병렬 처리하여 전체 실행 시간을 줄이는 데 도움이 될 수 있다.

예시 구조:

```text
Kubernetes Job
 ├─ Pod 1: 첫 번째 선택 = 0
 ├─ Pod 2: 첫 번째 선택 = 1
 ├─ Pod 3: 첫 번째 선택 = 2
 └─ Pod 4: 첫 번째 선택 = 3
```

단, 병렬화에는 다음 문제가 있다.

- 하위 트리별 탐색량이 균등하지 않을 수 있음
- 작업 분배 오버헤드 발생
- 중복 탐색 방지 필요
- 결과 수집과 실패 재시도 처리 필요

### 3. AWS Batch, AWS Lambda와 탐색 분산

AWS Batch는 대량의 배치 작업을 실행하는 데 사용할 수 있다. 백트래킹 문제를 하위 작업으로 나누어 각각을 독립적인 Batch Job으로 실행할 수 있다. AWS Lambda도 짧고 독립적인 하위 탐색 작업에는 사용할 수 있지만, 실행 시간과 리소스 제한이 있으므로 긴 백트래킹 작업에는 적합하지 않을 수 있다.

⚠️ 확인 필요: AWS Lambda의 최대 실행 시간, 메모리, CPU 할당 정책 등 구체적인 제한은 AWS 정책과 시점에 따라 달라질 수 있으므로 공식 문서를 확인해야 한다.

### 4. 클라우드 리소스 배치 문제와 CSP 모델링

클라우드 환경에서 다음과 같은 문제는 제약 만족 문제로 모델링할 수 있다.

- VM 또는 컨테이너를 어느 노드에 배치할 것인가
- 특정 워크로드를 어떤 리전에 배포할 것인가
- 장애 도메인을 어떻게 분산할 것인가
- 비용 제한 내에서 필요한 성능을 어떻게 만족할 것인가
- 데이터 위치 규정과 지연 시간 조건을 동시에 만족할 수 있는가

이러한 문제를 백트래킹, 분기 한정법, 정수 계획법, SAT/SMT solver, 휴리스틱 알고리즘 등으로 풀 수 있다. 실제 클라우드 플랫폼 내부 구현은 공개되지 않은 부분이 많으므로, 백트래킹은 “이런 문제를 이해하는 모델”로 보는 것이 안전하다.

## 보안 연결

## 보안 연결

백트래킹과 가지치기는 보안 관점에서도 중요한 의미를 가진다. 특히 백트래킹이 과도하게 발생하면 서비스 거부(DoS) 취약점으로 이어질 수 있다.

### 1. 정규 표현식 서비스 거부, ReDoS

가장 대표적인 보안 이슈는 ReDoS, 즉 Regular Expression Denial of Service다. 백트래킹 기반 정규 표현식 엔진에서 특정 패턴과 입력 조합은 매우 많은 매칭 경로를 생성할 수 있다.

예를 들어 다음과 같은 패턴은 위험할 수 있다.

```regex
^(a+)+$
```

입력이 대부분 `a`로 구성되어 있고 마지막에 매칭을 실패하게 만드는 문자가 붙으면, 엔진은 여러 반복 분할 가능성을 백트래킹하며 시도할 수 있다.

```text
aaaaaaaaaaaaaaaaX
```

이 경우 입력 길이가 조금만 증가해도 매칭 시간이 급격히 증가할 수 있다. 공격자는 이를 이용해 서버 CPU를 과도하게 사용하게 만들 수 있다.

#### 모범 사례

- 사용자 입력에 적용되는 정규 표현식은 단순하게 작성한다.
- 중첩 반복 패턴을 피한다.
- 정규 표현식 매칭에 타임아웃을 설정한다.
- 가능한 경우 선형 시간 매칭을 제공하는 엔진 사용을 검토한다.
- 입력 길이를 제한한다.
- 보안 테스트에서 악성 입력 케이스를 포함한다.

### 2. 조합 폭발 기반 DoS

백트래킹 알고리즘을 API로 제공하는 경우, 공격자가 매우 큰 탐색 공간을 유도하는 입력을 보낼 수 있다.

예:

- 스도쿠 solver에 극단적으로 어려운 퍼즐 제출
- 조합 최적화 API에 과도한 변수 수 입력
- 경로 탐색 API에 지나치게 많은 후보 경로 제공
- 규칙 엔진에 복잡한 조건 조합 입력

이런 경우 서버는 정상 요청을 처리하지 못할 정도로 CPU와 메모리를 소모할 수 있다.

#### 방어 방법

- 입력 크기 제한
- 탐색 깊이 제한
- 최대 실행 시간 제한
- 최대 노드 방문 수 제한
- 요청당 CPU, 메모리 quota 적용
- 캐싱 또는 사전 계산 사용
- 비동기 작업 큐로 분리
- 사용자별 rate limit 적용

### 3. 재귀 깊이와 스택 오버플로

백트래킹은 재귀로 구현되는 경우가 많다. 입력에 따라 재귀 깊이가 매우 깊어지면 스택 오버플로가 발생할 수 있다. 이는 서비스 장애나 비정상 종료로 이어질 수 있다.

#### 방어 방법

- 최대 재귀 깊이 제한
- 반복문과 명시적 스택으로 구현
- 입력 크기 검증
- 언어별 호출 스택 한계 고려
- 예외 처리 및 실패 응답 설계

### 4. 민감 데이터 탐색 문제

백트래킹은 가능한 조합을 빠르게 탐색하는 데 쓰일 수 있으므로, 공격 도구에서도 활용될 수 있다.

예:

- 패스워드 후보 조합 생성
- 토큰 패턴 추측
- 권한 조합 탐색
- 설정 조합 취약점 탐색

따라서 인증 시스템에서는 단순히 조합 공간이 크다는 이유만으로 안전하다고 판단하면 안 된다. 공격자는 가지치기, 사전 기반 후보 생성, 병렬화, GPU/클라우드 리소스를 사용할 수 있다.

#### 모범 사례

- 강력한 비밀번호 정책
- 다중 인증 적용
- 로그인 시도 제한
- 계정 잠금 또는 지연 정책
- 비밀번호 해시는 검증된 KDF 사용
- 토큰은 충분한 엔트로피를 가진 난수로 생성
- 민감 API에 rate limiting 적용

## 면접 질문

**Q1. 백트래킹과 완전 탐색의 차이는 무엇인가요?**  
> 핵심 답변: 백트래킹은 완전 탐색의 한 형태로 볼 수 있지만, 모든 후보를 끝까지 확인하지 않고 현재 부분 해가 제약 조건을 위반하면 즉시 탐색을 중단한다. 핵심 차이는 가지치기 여부다.

**Q2. 상태 공간 트리란 무엇인가요?**  
> 핵심 답변: 문제의 가능한 선택 과정을 트리로 표현한 것이다. 루트는 초기 상태, 각 노드는 부분 해, 간선은 선택, 리프는 완성된 후보 해 또는 실패 상태를 의미한다. 백트래킹은 이 트리를 DFS 방식으로 탐색한다.

**Q3. 가지치기 조건을 잘 설계하는 것이 왜 중요한가요?**  
> 핵심 답변: 백트래킹의 최악 시간 복잡도는 지수적일 수 있다. 가지치기 조건이 강력하고 빠를수록 불필요한 하위 트리를 조기에 제거할 수 있어 실제 실행 시간이 크게 줄어든다.

**Q4. N-Queen 문제에서 어떤 방식으로 가지치기를 할 수 있나요?**  
> 핵심 답변: 한 행에 하나씩 퀸을 배치한다고 가정하면, 이미 사용한 열과 두 대각선 방향에 퀸이 있는지 검사한다. 같은 열 또는 대각선에 퀸이 있으면 해당 위치는 선택하지 않는다.

**Q5. 백트래킹 알고리즘을 운영 환경 API로 제공할 때 주의할 점은 무엇인가요?**  
> 핵심 답변: 조합 폭발로 인한 CPU 과다 사용, 메모리 증가, 재귀 깊이 초과, 요청 지연을 고려해야 한다. 입력 크기 제한, 시간 제한, 탐색 노드 제한, rate limiting, 비동기 작업 큐, 컨테이너 리소스 제한이 필요하다.
