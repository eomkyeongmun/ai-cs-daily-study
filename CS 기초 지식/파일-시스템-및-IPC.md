# 파일 시스템 및 IPC - 파일 할당 방법, IPC 종류(파이프, 소켓, 공유 메모리)

## 핵심 개념

파일 시스템은 저장 장치의 블록들을 파일과 디렉터리라는 논리적 구조로 조직하고, 이름 기반 접근·권한 관리·메타데이터 관리·공간 할당을 제공하는 운영체제 구성 요소이다. 그중 **파일 할당 방법**은 파일 데이터를 디스크 또는 SSD의 어느 블록에 배치하고, 파일의 논리적 오프셋을 실제 저장 위치로 어떻게 변환할지를 결정한다. 대표적으로 연속 할당, 연결 할당, 인덱스 할당, 그리고 현대 파일 시스템에서 널리 쓰이는 익스텐트 기반 할당이 있다. 이 방식은 성능, 단편화, 랜덤 접근 효율, 메타데이터 크기, 장애 복구 방식에 직접적인 영향을 준다.

IPC(Inter-Process Communication)는 서로 독립된 프로세스가 데이터를 주고받거나 동기화하기 위한 운영체제 메커니즘이다. 프로세스는 기본적으로 독립된 가상 주소 공간을 가지므로, 한 프로세스가 다른 프로세스의 메모리에 직접 접근할 수 없다. 따라서 커널은 **파이프**, **소켓**, **공유 메모리** 같은 통신 수단을 제공한다. 파이프는 보통 부모-자식 프로세스나 로컬 프로세스 간의 단방향 스트림 통신에 적합하고, 소켓은 로컬뿐 아니라 네트워크를 통한 프로세스 간 통신에 사용된다. 공유 메모리는 여러 프로세스가 같은 물리 메모리 영역을 자신의 주소 공간에 매핑하여 빠르게 데이터를 교환하는 방식이다. 파일 시스템과 IPC는 모두 운영체제가 “자원에 대한 안전하고 효율적인 추상화”를 제공한다는 점에서 핵심적이며, 성능 최적화, 서버 아키텍처, 컨테이너 격리, 클라우드 스토리지 설계, 보안 모델 이해에 필수적이다.

## 내부 동작 원리

## 1. 파일 할당 방법

### 1) 연속 할당 Contiguous Allocation

파일을 디스크의 연속된 블록에 저장하는 방식이다.

```text
파일 A: 시작 블록 = 10, 길이 = 5

디스크 블록:
[0][1][2]...[9][10][11][12][13][14][15]...
              |--- 파일 A ---|
```

파일의 메타데이터에는 보통 시작 블록 번호와 길이만 저장하면 되므로 구조가 단순하다. 논리 블록 `i`는 `시작 블록 + i`로 바로 계산할 수 있어 랜덤 접근이 빠르다. 하지만 파일 크기가 증가할 때 뒤쪽에 연속 공간이 없으면 파일을 이동하거나 재할당해야 한다. 또한 시간이 지나면서 빈 공간이 여러 조각으로 흩어지는 **외부 단편화**가 발생할 수 있다.

### 2) 연결 할당 Linked Allocation

파일을 여러 블록에 흩어 저장하고, 각 블록이 다음 블록의 위치를 가리키는 포인터를 가진다.

```text
파일 B:
[블록 7 | next=3] -> [블록 3 | next=20] -> [블록 20 | next=null]
```

연속된 공간이 필요 없으므로 외부 단편화 문제는 줄어든다. 파일 크기가 증가할 때도 새 블록을 연결하면 된다. 그러나 특정 위치로 바로 이동하려면 처음부터 포인터를 따라가야 하므로 랜덤 접근이 느리다. 또한 각 블록에 포인터 공간이 필요하고, 포인터가 손상되면 이후 데이터 접근이 어려워질 수 있다.

FAT(File Allocation Table) 계열 파일 시스템은 연결 정보를 블록 내부가 아니라 별도 테이블에 저장하는 방식으로 이해할 수 있다.

```text
FAT 테이블:
블록 7  -> 3
블록 3  -> 20
블록 20 -> EOF
```

### 3) 인덱스 할당 Indexed Allocation

파일마다 인덱스 블록을 두고, 이 인덱스 블록이 데이터 블록들의 주소를 담는다.

```text
inode 또는 index block
+-------------------+
| data block 40     |
| data block 18     |
| data block 91     |
| data block 22     |
+-------------------+

논리 블록 0 -> 물리 블록 40
논리 블록 1 -> 물리 블록 18
논리 블록 2 -> 물리 블록 91
```

랜덤 접근이 연결 할당보다 효율적이다. 논리 블록 번호를 인덱스로 사용해 실제 블록 번호를 찾을 수 있기 때문이다. 다만 작은 파일에도 인덱스 구조가 필요할 수 있고, 큰 파일은 단일 인덱스 블록만으로 표현하기 어려워 다단계 인덱스가 필요하다.

Unix 계열 파일 시스템의 inode는 직접 블록 포인터와 간접 블록 포인터를 함께 사용하는 전형적인 예로 설명된다.

```text
inode
├─ direct block pointer
├─ direct block pointer
├─ single indirect pointer ──> [block ptr][block ptr][...]
├─ double indirect pointer ──> [indirect block ptr] -> [block ptr...]
└─ triple indirect pointer ──> ...
```

### 4) 익스텐트 기반 할당 Extent-based Allocation

익스텐트는 “연속된 블록들의 묶음”을 하나의 메타데이터 항목으로 표현하는 방식이다.

```text
파일 C의 익스텐트 목록:
Extent 1: 시작 블록 100, 길이 8
Extent 2: 시작 블록 500, 길이 4
Extent 3: 시작 블록 900, 길이 12
```

파일이 완전히 연속되지 않아도, 여러 개의 큰 연속 구간으로 관리할 수 있다. 블록마다 포인터를 저장하는 것보다 메타데이터가 줄고, 순차 I/O 성능에도 유리하다. Linux의 ext4는 익스텐트 기반 할당을 지원한다. XFS도 익스텐트 기반 구조를 사용한다.

## 2. IPC 내부 동작

## 2-1. 파이프 Pipe

파이프는 커널이 관리하는 버퍼를 통해 한 프로세스의 출력이 다른 프로세스의 입력으로 전달되는 IPC 방식이다.

```text
Process A                Kernel Pipe Buffer                Process B
+---------+              +------------------+              +---------+
| write() | -----------> | byte stream data | -----------> | read()  |
+---------+              +------------------+              +---------+
```

일반적인 익명 파이프는 `pipe()` 시스템 콜로 생성되며, 읽기용 파일 디스크립터와 쓰기용 파일 디스크립터가 반환된다.

```text
pipe(fd)
fd[0] = read end
fd[1] = write end
```

부모 프로세스가 파이프를 만든 뒤 `fork()`를 호출하면 자식 프로세스도 같은 파이프 파일 디스크립터를 상속받는다. 셸에서 `ls | grep txt` 같은 명령을 실행하면, 앞 명령의 표준 출력이 파이프의 쓰기 끝에 연결되고, 뒤 명령의 표준 입력이 파이프의 읽기 끝에 연결된다.

FIFO(named pipe)는 파일 시스템에 이름을 가진 파이프 객체를 만들어, 부모-자식 관계가 없는 프로세스도 같은 경로를 통해 통신할 수 있게 한다.

## 2-2. 소켓 Socket

소켓은 프로세스 간 양방향 통신을 위한 엔드포인트이다. 같은 호스트 내 통신에는 Unix domain socket을 사용할 수 있고, 네트워크 통신에는 TCP/IP 또는 UDP/IP 기반 소켓을 사용할 수 있다.

### TCP 서버 소켓의 일반 흐름

```text
Server Process                              Client Process
+-------------+                             +-------------+
| socket()    |                             | socket()    |
| bind()      |                             | connect()   |
| listen()    | <-------------------------  |             |
| accept()    | ------------------------->  |             |
| read/write  | <========================>  | read/write  |
+-------------+                             +-------------+
```

- `socket()` : 통신 엔드포인트 생성
- `bind()` : IP 주소와 포트 또는 Unix socket path에 연결
- `listen()` : 연결 요청 대기 상태로 전환
- `accept()` : 클라이언트 연결을 수락하고 통신용 소켓 생성
- `connect()` : 클라이언트가 서버에 연결 요청
- `read()/write()` 또는 `send()/recv()` : 데이터 송수신

TCP 소켓은 스트림 기반이며 신뢰성 있는 전송, 순서 보장, 흐름 제어를 제공한다. UDP 소켓은 데이터그램 기반이며 연결 설정 없이 메시지를 전송한다. Unix domain socket은 네트워크 스택 일부를 우회하여 같은 머신 내 프로세스 간 통신에 자주 사용된다.

## 2-3. 공유 메모리 Shared Memory

공유 메모리는 여러 프로세스가 동일한 물리 메모리 영역을 각자의 가상 주소 공간에 매핑하는 IPC 방식이다.

```text
Physical Memory
+-----------------------+
| Shared Memory Segment |
+-----------------------+
        ^          ^
        |          |
Process A VA   Process B VA
+---------+    +---------+
| mapping |    | mapping |
+---------+    +---------+
```

동작 흐름은 대략 다음과 같다.

1. 프로세스가 공유 메모리 객체 또는 세그먼트를 생성한다.
2. 커널이 해당 메모리 영역을 관리한다.
3. 각 프로세스가 `mmap()` 또는 System V shared memory API 등을 통해 자신의 가상 주소 공간에 매핑한다.
4. 매핑 후에는 일반 메모리 읽기/쓰기처럼 접근한다.
5. 경쟁 상태를 막기 위해 세마포어, 뮤텍스, 파일 락, futex 등 별도 동기화 기법을 함께 사용한다.

공유 메모리는 파이프나 소켓처럼 매번 커널 버퍼를 경유해 데이터를 복사하는 방식보다 빠를 수 있다. 다만 동기화가 올바르지 않으면 데이터 경합, 불일치, 교착 상태가 발생할 수 있다.

## 실제 시스템 연결

## Linux 파일 시스템

Linux에서 파일은 일반적으로 inode와 데이터 블록으로 관리된다. inode에는 파일 타입, 권한, 소유자, 크기, 타임스탬프, 데이터 블록 위치를 찾기 위한 메타데이터가 포함된다. 파일 이름은 inode 안에 직접 저장되는 것이 아니라 디렉터리 엔트리가 파일 이름과 inode 번호를 매핑한다.

```text
디렉터리 엔트리
"app.log" -> inode 1052

inode 1052
├─ mode, uid, gid, size
├─ timestamps
└─ extent tree 또는 block pointer metadata
```

ext4는 익스텐트 기반 할당을 지원하며, 파일의 연속 블록 범위를 효율적으로 표현한다. XFS 역시 대용량 파일과 병렬 I/O 환경에서 자주 사용되는 파일 시스템이며 익스텐트 기반 구조를 사용한다. Btrfs는 copy-on-write 특성을 가지며 스냅샷, 체크섬 등의 기능을 제공한다.

## Linux IPC

Linux는 POSIX pipe, FIFO, Unix domain socket, TCP/UDP socket, POSIX shared memory, System V shared memory, message queue, semaphore 등 다양한 IPC를 제공한다.

### 파이프 예시

```bash
ps aux | grep nginx
```

위 명령에서 `ps aux`의 표준 출력이 파이프를 통해 `grep nginx`의 표준 입력으로 전달된다.

### Unix domain socket 예시

Nginx는 upstream 서버와 통신할 때 TCP 소켓뿐 아니라 Unix domain socket을 사용할 수 있다. 같은 호스트 내에서 Nginx와 애플리케이션 서버가 통신한다면 Unix domain socket을 통해 로컬 IPC를 구성할 수 있다.

예시 형태:

```nginx
upstream app {
    server unix:/run/app.sock;
}
```

### 공유 메모리 예시

Nginx는 여러 worker process 간에 상태를 공유하기 위해 shared memory zone을 사용할 수 있다. 예를 들어 rate limiting, connection limiting 같은 기능은 공유 메모리 영역을 통해 worker 간 공통 상태를 관리한다.

예시 형태:

```nginx
limit_req_zone $binary_remote_addr zone=req_limit:10m rate=10r/s;
```

여기서 `zone=req_limit:10m`은 공유 메모리 zone을 정의하는 설정이다.

## 데이터베이스와 파일 시스템

데이터베이스는 운영체제 파일 시스템 위에 데이터 파일과 로그 파일을 저장하거나, 특정 환경에서는 raw device 또는 direct I/O를 사용할 수 있다. 데이터베이스의 WAL, redo log, fsync, page cache 정책은 파일 시스템의 동작과 밀접하다. 예를 들어 `fsync()`는 사용자 공간의 쓰기 요청이 커널 버퍼에만 머물지 않고 저장 장치에 반영되도록 요청하는 데 사용된다. 단, 실제 내구성 보장은 파일 시스템, 저장 장치, 캐시 정책, 하드웨어 설정에 따라 영향을 받을 수 있다.

## 클라우드 연결

## Docker와 파일 시스템

Docker 컨테이너는 이미지 레이어와 writable layer를 조합해 파일 시스템 뷰를 제공한다. Linux 환경에서는 OverlayFS가 컨테이너 스토리지 드라이버로 사용될 수 있다. OverlayFS는 lower layer와 upper layer를 합쳐 하나의 merged view를 제공한다.

```text
Container View
+------------------+
| merged directory |
+------------------+
        ^
        |
+-------+--------+
| upper writable |
+----------------+
| lower read-only|
+----------------+
```

컨테이너가 파일을 수정하면 copy-up 동작으로 읽기 전용 lower layer의 파일이 writable upper layer로 복사된 뒤 수정될 수 있다. 이 구조는 이미지 재사용과 빠른 컨테이너 생성에 유리하지만, 쓰기 집약적인 워크로드에서는 별도의 volume 사용이 권장된다.

## Kubernetes와 파일 시스템

Kubernetes에서는 컨테이너의 ephemeral storage, `emptyDir`, `hostPath`, PersistentVolume(PV), PersistentVolumeClaim(PVC) 등을 통해 파일 저장을 다룬다.

- `emptyDir` : Pod 생명주기 동안 유지되는 임시 저장 공간
- `hostPath` : 노드의 파일 시스템 경로를 Pod에 마운트
- PVC/PV : 스토리지 자원을 추상화하여 Pod에 제공
- CSI(Container Storage Interface) : 다양한 스토리지 백엔드를 Kubernetes와 연결하는 표준 인터페이스

파일 시스템 할당 방식 자체는 컨테이너 내부 애플리케이션이 직접 관리하지 않는 경우가 많지만, 실제 성능은 노드의 파일 시스템, 스토리지 드라이버, 클라우드 볼륨 특성에 크게 의존한다.

## Kubernetes와 IPC

Kubernetes의 컨테이너는 Linux namespace 기반 격리를 사용한다. IPC namespace는 System V IPC 객체와 POSIX message queue 등을 격리하는 데 사용된다. Pod 내 컨테이너들은 특정 namespace를 공유할 수 있으며, 같은 Pod 내 컨테이너들은 일반적으로 localhost 네트워크를 공유한다. 공유 메모리의 경우 `/dev/shm` 크기와 마운트 설정이 영향을 줄 수 있다.

⚠️ 확인 필요: Kubernetes 런타임과 배포판에 따라 `/dev/shm`의 기본 크기 및 조정 방식은 다를 수 있으므로, 실제 환경의 container runtime 설정을 확인해야 한다.

## AWS와 파일 시스템

AWS에서 파일 시스템 개념은 여러 서비스와 연결된다.

- **Amazon EBS** : EC2 인스턴스에 연결되는 블록 스토리지. 인스턴스 내부에서 ext4, XFS 등 파일 시스템을 생성해 사용한다.
- **Amazon EFS** : NFS 기반의 관리형 파일 스토리지. 여러 EC2 인스턴스 또는 컨테이너에서 동시에 마운트할 수 있다.
- **Amazon S3** : 객체 스토리지이며 전통적인 POSIX 파일 시스템과는 다르다. 디렉터리와 파일 대신 버킷과 객체 키를 사용한다.

EBS는 블록 장치를 제공하므로 파일 할당, inode, 저널링 같은 세부 동작은 인스턴스 내부 파일 시스템이 담당한다. EFS는 네트워크 파일 시스템이므로 지연 시간, 처리량, 동시 접근, NFS 캐싱 동작을 고려해야 한다.

## 클라우드 환경에서 IPC

마이크로서비스 아키텍처에서는 프로세스 간 통신이 같은 호스트 내부 IPC를 넘어 네트워크 기반 통신으로 확장된다. 같은 노드 내 사이드카와 애플리케이션은 localhost TCP, Unix domain socket, shared volume을 통해 통신할 수 있다. 서로 다른 노드나 서비스 간 통신은 TCP 소켓, HTTP, gRPC, 메시지 브로커 등을 사용한다.

예를 들어 서비스 메시 구조에서는 애플리케이션 컨테이너와 프록시 사이드카가 같은 Pod 안에서 localhost TCP 또는 Unix domain socket을 통해 통신할 수 있다. 이후 프록시가 다른 서비스로 네트워크 요청을 전달한다.

## 보안 연결

## 파일 시스템 보안

파일 시스템 보안의 핵심은 권한, 소유권, 격리, 무결성이다. Linux에서는 사용자 ID, 그룹 ID, permission bit, ACL, mount option, Linux Security Module 기반 정책 등이 파일 접근 제어에 관여한다.

### 주요 보안 이슈

1. **권한 오설정**
   - 민감한 파일에 과도한 읽기/쓰기 권한을 부여하면 정보 유출이나 변조가 발생할 수 있다.
   - 예: private key 파일, 환경 변수 파일, 데이터베이스 설정 파일

2. **심볼릭 링크 공격**
   - 임시 파일을 안전하지 않은 경로에 만들 때 공격자가 심볼릭 링크를 이용해 의도하지 않은 파일을 덮어쓰게 할 수 있다.
   - 임시 파일 생성 시 안전한 API와 적절한 권한 설정이 필요하다.

3. **TOCTOU Race Condition**
   - Time-of-check to time-of-use 취약점은 파일을 검사한 시점과 실제 사용 시점 사이에 파일이 바뀌어 발생한다.
   - 예: 권한 확인 후 파일 열기 전에 공격자가 경로를 교체하는 경우

4. **디스크 잔여 데이터**
   - 삭제된 파일의 데이터가 저장 장치에 남아 있을 수 있다.
   - 클라우드 환경에서는 관리형 스토리지의 보안 정책과 암호화 기능을 함께 고려해야 한다.

5. **마운트 옵션 미흡**
   - `noexec`, `nosuid`, `nodev` 같은 마운트 옵션은 특정 공격면을 줄이는 데 도움이 된다.
   - 단, 애플리케이션 요구사항과 충돌할 수 있어 환경별 검토가 필요하다.

## IPC 보안

### 파이프와 FIFO

파이프는 로컬 프로세스 간 통신이므로 파일 디스크립터 상속과 권한 관리가 중요하다. FIFO는 파일 시스템 경로를 가지므로 파일 권한이 잘못 설정되면 의도하지 않은 프로세스가 읽거나 쓸 수 있다.

모범 사례:

- 불필요한 파일 디스크립터는 `close()`한다.
- 자식 프로세스 실행 시 민감한 FD가 상속되지 않도록 `FD_CLOEXEC` 또는 close-on-exec 설정을 사용한다.
- FIFO 경로의 디렉터리 권한을 제한한다.

### 소켓

네트워크 소켓은 원격 공격면이 되므로 인증, 암호화, 입력 검증, 접근 제어가 필수적이다.

주요 이슈:

- 평문 통신으로 인한 정보 유출
- 인증 없는 내부 API 노출
- 포트 오픈 범위 과다
- Unix domain socket 파일 권한 오설정
- 요청 flooding으로 인한 DoS

모범 사례:

- TLS 등 암호화 사용
- 방화벽, Security Group, Network Policy로 접근 범위 제한
- Unix domain socket 파일 권한 제한
- 인증·인가 적용
- rate limiting 및 connection limiting 적용
- 입력 데이터 크기 제한과 타임아웃 설정

### 공유 메모리

공유 메모리는 매우 빠르지만, 동기화와 권한 관리가 특히 중요하다.

주요 이슈:

- 동기화 부재로 인한 데이터 경합
- 공유 메모리 권한 오설정으로 인한 정보 유출
- 초기화되지 않은 메모리 영역 노출
- 프로세스 종료 후 남은 공유 메모리 객체 관리 미흡
- lock 순서 오류로 인한 deadlock

모범 사례:

- 세마포어, 뮤텍스, futex 등으로 접근 동기화
- 공유 메모리 객체 권한 최소화
- 민감 데이터 저장 지양 또는 암호화 검토
- 사용 후 명시적 unlink 또는 제거
- 구조체 버전 관리 및 경계 검사 수행

## 컨테이너와 클라우드 보안

컨테이너에서 hostPath를 잘못 사용하면 컨테이너가 호스트 파일 시스템에 과도하게 접근할 수 있다. `/var/run/docker.sock` 같은 런타임 소켓을 컨테이너에 마운트하면 컨테이너 탈출에 준하는 위험이 발생할 수 있다. Kubernetes에서는 Pod Security Standards, SecurityContext, readOnlyRootFilesystem, fsGroup, runAsNonRoot, seccomp, AppArmor/SELinux 정책 등을 통해 파일 시스템과 IPC 접근을 제한할 수 있다.

⚠️ 확인 필요: Kubernetes 클러스터의 보안 기능 지원 여부와 기본 정책은 배포판, 버전, 클라우드 제공자 설정에 따라 달라질 수 있다.

## 면접 질문

**Q1. 파일 할당 방법 중 연속 할당, 연결 할당, 인덱스 할당의 차이는 무엇인가요?**  
> 핵심 답변: 연속 할당은 시작 블록과 길이만으로 빠른 랜덤 접근이 가능하지만 외부 단편화와 파일 확장 문제가 있다. 연결 할당은 블록을 포인터로 연결해 외부 단편화는 줄지만 랜덤 접근이 느리다. 인덱스 할당은 인덱스 블록 또는 inode가 데이터 블록 주소를 관리해 랜덤 접근이 효율적이지만 메타데이터 오버헤드가 있다.

**Q2. 익스텐트 기반 할당이 블록 포인터 방식보다 유리한 이유는 무엇인가요?**  
> 핵심 답변: 익스텐트는 연속된 블록 범위를 시작 위치와 길이로 표현하므로 많은 블록을 적은 메타데이터로 관리할 수 있다. 순차 I/O에 유리하고, 큰 파일에서 메타데이터 탐색 비용을 줄일 수 있다. 다만 파일이 심하게 단편화되면 익스텐트 수가 증가할 수 있다.

**Q3. 파이프와 소켓의 차이는 무엇인가요?**  
> 핵심 답변: 파이프는 주로 같은 호스트 내 프로세스 간 바이트 스트림 통신에 사용되며, 익명 파이프는 보통 부모-자식 관계에서 자주 사용된다. 소켓은 로컬 IPC뿐 아니라 네트워크 통신까지 지원한다. TCP 소켓은 연결 지향 스트림 통신, UDP 소켓은 데이터그램 통신, Unix domain socket은 같은 호스트 내 프로세스 간 통신에 사용된다.

**Q4. 공유 메모리가 빠른 이유와 주의할 점은 무엇인가요?**  
> 핵심 답변: 공유 메모리는 여러 프로세스가 같은 물리 메모리 영역을 자신의 주소 공간에 매핑해 직접 읽고 쓰므로 데이터 복사 비용을 줄일 수 있다. 그러나 동시에 접근할 수 있기 때문에 세마포어, 뮤텍스, futex 같은 동기화가 필요하다. 동기화가 없으면 race condition, 데이터 손상, deadlock 문제가 발생할 수 있다.

**Q5. Docker 또는 Kubernetes 환경에서 파일 시스템과 IPC를 다룰 때 주의할 점은 무엇인가요?**  
> 핵심 답변: 컨테이너 writable layer는 영속성과 성능 측면에서 제한이 있으므로 중요한 데이터는 volume이나 PV를 사용해야 한다. hostPath나 런타임 소켓 마운트는 권한 상승 위험이 있다. IPC namespace와 `/dev/shm` 설정, Unix socket 파일 권한, NetworkPolicy, SecurityContext 등을 통해 격리와 접근 제어를 적절히 구성해야 한다.

- [[저널링 파일 시스템]] - 파일 시스템 변경 작업의 일관성과 장애 복구를 위해 로그를 사용하는 방식
- [[익스텐트]] - 연속된 데이터 블록 범위를 하나의 메타데이터 항목으로 표현하는 파일 할당 단위
- [[가상 메모리]] - 공유 메모리 매핑과 프로세스 주소 공간 격리를 이해하는 기반 개념

- [[TCP UDP]] - 네트워크 소켓 통신의 대표적인 전송 계층 프로토콜
- [[세마포어]] - 공유 메모리 접근 제어와 프로세스 동기화에 사용되는 동기화 primitive
- [[뮤텍스]] - 공유 자원에 대한 상호 배제를 제공하는 동기화 기법
- [[Docker Volume]] - 컨테이너의 writable layer와 분리된 영속 스토리지 관리 방식
- [[Kubernetes PersistentVolume]] - Kubernetes에서 스토리지를 추상화하고 Pod에 제공하는 리소스
- [[OverlayFS]] - 컨테이너 이미지 레이어와 writable layer를 합쳐 하나의 파일 시스템 뷰를 제공하는 union filesystem
- [[NFS]] - 네트워크를 통해 파일 시스템을 공유하는 프로토콜로 AWS EFS와 관련 있음
- [[TOCTOU]] - 파일 검사 시점과 사용 시점 사이의 차이로 발생할 수 있는 race condition 취약점
