# 메모리 계층 구조 - 레지스터 - 캐시 - 메인 메모리 - 보조기억장치

## 핵심 개념

메모리 계층 구조는 CPU에 가까운 저장장치일수록 **속도는 빠르지만 용량이 작고 비싸며**, CPU에서 멀어질수록 **속도는 느리지만 용량이 크고 저렴한** 특성을 이용해 전체 시스템의 성능과 비용을 균형 있게 설계하는 구조이다. 대표적인 계층은 **레지스터 → 캐시 → 메인 메모리 → 보조기억장치** 순서로 구성된다. 레지스터는 CPU 내부에 존재하며 명령어 실행에 직접 사용되는 가장 빠른 저장 공간이다. 캐시는 CPU와 메인 메모리 사이의 속도 차이를 줄이기 위한 고속 임시 저장소이다. 메인 메모리는 실행 중인 프로그램과 데이터를 저장하는 주기억장치이며, 보조기억장치는 SSD, HDD처럼 전원이 꺼져도 데이터를 보존하는 비휘발성 저장장치이다.

이 구조가 중요한 이유는 CPU의 연산 속도에 비해 메인 메모리와 보조기억장치 접근 속도가 훨씬 느리기 때문이다. 만약 CPU가 모든 데이터를 느린 저장장치에서 직접 가져와야 한다면 대부분의 시간을 대기 상태로 보내게 된다. 따라서 자주 사용되는 데이터를 더 빠른 계층에 배치하고, 덜 자주 사용되는 데이터는 느린 계층에 두는 방식으로 평균 접근 시간을 줄인다. 이때 핵심이 되는 원리는 **지역성(Locality)** 이다. 프로그램은 짧은 시간 동안 같은 데이터나 인접한 데이터를 반복해서 접근하는 경향이 있으므로, 메모리 계층 구조는 이 특성을 활용해 성능을 크게 개선한다.

## 내부 동작 원리

메모리 계층 구조의 내부 동작은 기본적으로 **요청한 데이터가 가장 빠른 계층에 있는지 확인하고, 없으면 더 느린 계층으로 내려가며 가져오는 방식**으로 이루어진다.

```text
CPU
 │
 ▼
[레지스터]
 │  가장 빠름, CPU 명령어가 직접 사용
 ▼
[L1 캐시]
 │
 ▼
[L2 캐시]
 │
 ▼
[L3 캐시]
 │
 ▼
[메인 메모리, DRAM]
 │
 ▼
[보조기억장치, SSD/HDD]
    가장 느림, 비휘발성 저장
```

CPU가 데이터를 필요로 하면 먼저 레지스터나 캐시에서 해당 데이터를 찾는다. 캐시에 데이터가 있으면 이를 **캐시 히트(Cache Hit)** 라고 하며, CPU는 빠르게 데이터를 사용할 수 있다. 반대로 캐시에 없으면 **캐시 미스(Cache Miss)** 가 발생하고, 하위 계층인 메인 메모리에서 데이터를 가져와 캐시에 적재한다. 만약 필요한 데이터가 메인 메모리에도 없고 디스크에 있다면, 운영체제는 디스크에서 데이터를 읽어 메인 메모리에 올린 뒤 CPU가 접근할 수 있도록 한다.

캐시는 보통 데이터를 한 바이트씩 가져오지 않고 **캐시 라인(Cache Line)** 단위로 가져온다. 이는 공간 지역성을 활용하기 위한 방식이다. 예를 들어 배열을 순차적으로 읽는 프로그램은 현재 주소 주변의 데이터를 곧 사용할 가능성이 높으므로, 인접 데이터를 함께 캐시에 올려두면 이후 접근이 빨라진다.

```text
예: 배열 순회

메모리:
[ A[0] ][ A[1] ][ A[2] ][ A[3] ][ A[4] ] ...

CPU가 A[0] 접근
→ 캐시 미스
→ 메인 메모리에서 A[0] 주변 데이터까지 캐시 라인 단위로 로드
→ 이후 A[1], A[2] 접근 시 캐시 히트 가능성 증가
```

레지스터는 컴파일러와 CPU 명령어 실행 단계에서 직접 활용된다. 예를 들어 산술 연산은 일반적으로 메모리의 값을 바로 연산하기보다 값을 레지스터에 적재한 뒤 수행한다.

```text
메모리의 변수 x, y를 더하는 개념적 흐름

1. x 값을 레지스터 R1에 로드
2. y 값을 레지스터 R2에 로드
3. R1 + R2 결과를 R3에 저장
4. 필요하면 R3 값을 메모리에 다시 저장
```

메인 메모리는 운영체제가 프로세스마다 독립된 주소 공간을 제공하는 기반이 된다. 프로그램은 가상 주소를 사용하고, MMU가 이를 물리 주소로 변환한다. 자주 사용하는 주소 변환 정보는 TLB에 캐시되어 주소 변환 비용을 줄인다.

```text
프로세스의 메모리 접근

프로그램의 가상 주소
        │
        ▼
      MMU
        │
        ├─ TLB hit  → 빠르게 물리 주소 확인
        │
        └─ TLB miss → 페이지 테이블 조회
        ▼
물리 메모리 접근
```

보조기억장치는 파일 시스템, 데이터베이스, 로그 저장소 등 영속성이 필요한 데이터를 저장한다. 메모리가 부족하면 운영체제는 일부 메모리 페이지를 디스크의 스왑 영역으로 내보낼 수 있다. 이를 통해 실행은 계속 가능하지만, 디스크 접근은 메모리 접근보다 느리기 때문에 성능 저하가 발생할 수 있다.

## 실제 시스템 연결

실제 시스템에서는 메모리 계층 구조가 운영체제, 런타임, 애플리케이션 성능에 직접적인 영향을 준다.

Linux에서는 프로세스가 직접 물리 메모리를 다루지 않고 **가상 메모리**를 사용한다. 각 프로세스는 독립적인 가상 주소 공간을 가진 것처럼 동작하며, 커널과 MMU가 가상 주소를 실제 물리 메모리 주소로 변환한다. 이 과정에서 페이지 테이블과 TLB가 사용된다. 또한 Linux는 남는 메모리를 파일 시스템 캐시로 적극 활용한다. 사용자가 `free` 명령어를 실행했을 때 버퍼와 캐시가 많이 보이는 것은 Linux가 디스크 I/O를 줄이기 위해 메모리를 캐시로 사용하기 때문이다.

```bash
free -h
```

위 명령어는 전체 메모리, 사용 중인 메모리, 버퍼/캐시, 사용 가능한 메모리 등을 확인할 때 사용된다.

Nginx 같은 웹 서버는 정적 파일을 제공할 때 운영체제의 페이지 캐시 효과를 크게 받는다. 자주 요청되는 이미지, CSS, JavaScript 파일이 디스크에서 한 번 읽힌 뒤 메모리의 페이지 캐시에 남아 있으면, 이후 요청은 디스크를 직접 읽지 않고 메모리에서 처리될 수 있다. 따라서 동일한 파일 요청이 많은 서버에서는 디스크 성능뿐 아니라 메모리 용량과 페이지 캐시 상태도 중요하다.

데이터베이스 시스템도 메모리 계층 구조에 강하게 의존한다. 예를 들어 PostgreSQL, MySQL 같은 DBMS는 자체 버퍼 풀 또는 shared buffer를 사용해 자주 접근하는 데이터 페이지를 메모리에 유지한다. 디스크에서 매번 데이터를 읽는 대신 메모리 캐시를 활용하면 쿼리 성능이 크게 향상된다. 다만 운영체제 페이지 캐시와 DBMS 내부 캐시가 함께 작동하므로, 메모리 설정을 잘못하면 불필요한 중복 캐싱이나 스왑으로 인한 성능 저하가 발생할 수 있다.

AWS EC2나 GCP Compute Engine 같은 가상 머신에서도 동일한 원리가 적용된다. 인스턴스 타입은 vCPU, 메모리, 스토리지 성능의 조합으로 제공되며, 워크로드 특성에 따라 적절한 계층 자원을 선택해야 한다. 예를 들어 메모리 캐시를 많이 활용하는 Redis 같은 시스템은 메모리 용량과 메모리 대역폭이 중요하고, 대규모 로그 저장이나 분석 워크로드는 스토리지 처리량과 IOPS가 중요할 수 있다.

## 클라우드 연결

클라우드 환경에서도 메모리 계층 구조는 성능, 비용, 안정성에 직접 연결된다. Docker 컨테이너는 호스트 OS의 커널을 공유하며, 컨테이너마다 메모리 제한을 설정할 수 있다. 예를 들어 Docker에서 `--memory` 옵션을 사용하면 컨테이너가 사용할 수 있는 메모리 한도를 제한할 수 있다. 이 제한을 초과하면 애플리케이션이 OOM Killer에 의해 종료될 수 있다.

```bash
docker run --memory=512m nginx
```

Kubernetes에서는 Pod 또는 Container 단위로 `resources.requests`와 `resources.limits`를 설정한다. `requests`는 스케줄링 시 필요한 최소 자원으로 사용되고, `limits`는 컨테이너가 사용할 수 있는 최대 자원을 제한하는 데 사용된다. 메모리 limit을 초과하면 컨테이너가 종료될 수 있으므로, JVM, Node.js, Python 애플리케이션처럼 런타임 메모리 사용량이 변동하는 서비스에서는 신중한 설정이 필요하다.

```yaml
resources:
  requests:
    memory: "512Mi"
    cpu: "500m"
  limits:
    memory: "1Gi"
    cpu: "1"
```

AWS에서는 메모리 계층 구조가 여러 서비스 선택에 반영된다. EC2 인스턴스는 범용, 컴퓨팅 최적화, 메모리 최적화, 스토리지 최적화 등 다양한 계열로 제공된다. 메모리 집약적인 애플리케이션은 메모리 최적화 인스턴스를 고려할 수 있고, 높은 디스크 I/O가 필요한 경우에는 로컬 NVMe 기반 인스턴스 스토어나 성능이 높은 EBS 볼륨 구성이 필요할 수 있다.

AWS ElastiCache for Redis 또는 Memcached는 메인 메모리를 활용해 데이터베이스나 외부 API 호출보다 빠른 응답을 제공하는 캐시 계층 역할을 한다. 이는 컴퓨터 구조의 캐시 개념을 분산 시스템 수준으로 확장한 사례라고 볼 수 있다.

```text
애플리케이션
   │
   ├─ Redis 캐시 hit → 빠른 응답
   │
   └─ Redis 캐시 miss
          │
          ▼
       RDBMS 조회
          │
          ▼
       결과를 Redis에 저장
```

Kubernetes에서도 비슷하게 애플리케이션 내부 캐시, Redis 캐시, 데이터베이스 버퍼 캐시, 클라우드 블록 스토리지 캐시 등이 함께 작동한다. 따라서 클라우드 성능 튜닝에서는 단순히 CPU 개수만 늘리는 것이 아니라, 데이터가 어느 계층에서 병목을 일으키는지 파악해야 한다. 예를 들어 애플리케이션이 CPU-bound인지, memory-bound인지, I/O-bound인지에 따라 해결책이 달라진다.

## 보안 연결

메모리 계층 구조는 보안과도 밀접하게 관련된다. 특히 캐시는 성능을 높이기 위한 구조이지만, 실행 시간 차이나 캐시 히트/미스 차이를 관찰해 민감한 정보를 추론하는 **사이드 채널 공격**의 기반이 될 수 있다. 대표적으로 CPU의 추측 실행과 캐시 상태 변화를 악용하는 Spectre, Meltdown 계열 취약점이 널리 알려져 있다. 이러한 공격은 프로그램이 직접 접근 권한이 없는 데이터를 읽지 못하더라도, 캐시 접근 시간 차이를 통해 비밀 정보를 추론할 수 있음을 보여주었다.

⚠️ 확인 필요: Spectre와 Meltdown의 영향 범위와 완화 방식은 CPU 제조사, 운영체제 버전, 마이크로코드 업데이트 상태에 따라 다르므로 특정 시스템에 대한 정확한 영향은 벤더 문서를 확인해야 한다.

메인 메모리와 관련해서는 버퍼 오버플로우, Use-After-Free, Double Free 같은 메모리 안전성 문제가 중요하다. C/C++처럼 개발자가 직접 메모리를 관리하는 언어에서는 잘못된 포인터 사용이나 경계 검사 누락으로 인해 공격자가 임의 코드 실행, 권한 상승, 정보 유출을 일으킬 수 있다. 이를 완화하기 위해 ASLR, DEP/NX bit, stack canary, Control Flow Integrity 같은 기법이 사용된다.

보조기억장치에서는 데이터 영속성이 보안 이슈가 된다. 디스크에 저장된 데이터는 전원이 꺼진 뒤에도 남기 때문에, 민감 정보는 암호화되어 저장되어야 한다. Linux에서는 LUKS/dm-crypt를 이용한 디스크 암호화가 사용될 수 있고, 클라우드에서는 AWS EBS 암호화, S3 서버 측 암호화, GCP Persistent Disk 암호화 같은 기능을 사용할 수 있다. 단, 암호화 키 관리가 부실하면 암호화 자체의 효과가 약해질 수 있다.

메모리 덤프와 스왑 영역도 주의해야 한다. 애플리케이션 크래시 덤프, 코어 덤프, 스왑 파일에는 비밀번호, 토큰, 개인 정보, 암호화 키 등이 포함될 수 있다. 운영 환경에서는 코어 덤프 생성 정책을 점검하고, 민감 정보가 로그나 덤프에 남지 않도록 해야 한다.

컨테이너 환경에서는 메모리 제한과 격리도 보안과 연결된다. 하나의 컨테이너가 과도한 메모리를 사용하면 같은 노드의 다른 워크로드에 영향을 줄 수 있으므로 Kubernetes의 resource limit, namespace, cgroup 기반 제한을 적절히 설정해야 한다. 이는 단순한 성능 관리가 아니라 서비스 가용성을 보호하는 보안적 조치이기도 하다.

## 면접 질문

**Q1. 메모리 계층 구조가 필요한 이유는 무엇인가요?**  
> 핵심 답변: CPU와 메모리/디스크 간 속도 차이를 완화하기 위해 필요하다. 빠르고 비싼 저장장치는 작게, 느리고 저렴한 저장장치는 크게 구성하여 비용과 성능을 균형 있게 맞춘다. 지역성을 활용해 자주 쓰는 데이터를 빠른 계층에 두면 평균 접근 시간이 줄어든다.

**Q2. 캐시 히트와 캐시 미스의 차이는 무엇인가요?**  
> 핵심 답변: 캐시 히트는 CPU가 요청한 데이터가 캐시에 있어 빠르게 접근하는 경우이고, 캐시 미스는 캐시에 없어 하위 계층인 메인 메모리나 더 느린 저장장치에서 데이터를 가져와야 하는 경우이다. 캐시 미스가 많으면 CPU가 데이터를 기다리는 시간이 늘어나 성능이 저하된다.

**Q3. 시간 지역성과 공간 지역성은 무엇인가요?**  
> 핵심 답변: 시간 지역성은 최근 사용한 데이터나 명령어를 가까운 미래에 다시 사용할 가능성이 높다는 원리이다. 공간 지역성은 접근한 주소 주변의 데이터가 곧 사용될 가능성이 높다는 원리이다. 캐시는 이 두 지역성을 활용해 성능을 높인다.

**Q4. 메인 메모리와 보조기억장치의 차이는 무엇인가요?**  
> 핵심 답변: 메인 메모리는 실행 중인 프로그램과 데이터를 저장하는 휘발성 저장장치이며 CPU가 비교적 빠르게 접근할 수 있다. 보조기억장치는 SSD/HDD처럼 전원이 꺼져도 데이터를 보존하는 비휘발성 저장장치이지만, 메인 메모리보다 접근 지연이 크다.

**Q5. 운영체제의 페이지 캐시는 어떤 역할을 하나요?**  
> 핵심 답변: 디스크에서 읽은 파일 데이터를 메모리에 보관해 이후 동일한 데이터 접근 시 디스크 I/O를 줄이는 역할을 한다. Linux는 남는 메모리를 페이지 캐시로 적극 활용하며, 웹 서버나 데이터베이스 성능에 큰 영향을 줄 수 있다.

## 관련 개념

- [[지역성의 원리]] - 메모리 계층 구조가 성능을 낼 수 있는 핵심 전제이다.
- [[캐시 메모리]] - CPU와 메인 메모리 사이의 속도 차이를 줄이는 핵심 계층이다.
- [[가상 메모리]] - 프로세스에 독립적인 주소 공간을 제공하고 물리 메모리를 효율적으로 관리한다.
- [[페이지 테이블]] - 가상 주소를 물리 주소로 변환하기 위한 운영체제와 하드웨어의 핵심 자료구조이다.
- [[TLB]] - 주소 변환 정보를 캐싱하여 가상 메모리 접근 비용을 줄인다.
- [[스왑 메모리]] - 메인 메모리가 부족할 때 일부 페이지를 보조기억장치로 옮기는 메커니즘이다.
- [[페이지 캐시]] - 파일 I/O 성능을 높이기 위해 디스크 데이터를 메모리에 캐싱한다.
- [[SSD와 HDD]] - 보조기억장치 계층의 대표적인 구현 방식이며 성능 특성이 다르다.
- [[CPU 파이프라인]] - CPU 내부 실행 구조로, 메모리 접근 지연이 파이프라인 성능에 영향을 줄 수 있다.
- [[Spectre와 Meltdown]] - 캐시와 추측 실행을 악용한 대표적인 하드웨어 기반 사이드 채널 취약점이다.
