# 디자인 패턴 - GoF - 생성(Singleton, Factory), 구조(Adapter, Proxy), 행위(Strategy, Observer)

## 핵심 개념

## GoF 디자인 패턴 개요: 생성, 구조, 행위 패턴

디자인 패턴은 반복적으로 등장하는 소프트웨어 설계 문제에 대해 검증된 해결 구조를 이름 붙여 정리한 것이다. GoF, 즉 Gang of Four 디자인 패턴은 객체지향 설계에서 자주 발생하는 문제를 생성 패턴, 구조 패턴, 행위 패턴으로 분류한다. 이 노트에서는 생성 패턴의 **Singleton, Factory**, 구조 패턴의 **Adapter, Proxy**, 행위 패턴의 **Strategy, Observer**를 다룬다.

생성 패턴은 객체 생성 방식을 캡슐화하여 클라이언트 코드가 구체 클래스에 직접 의존하지 않도록 돕는다. Singleton은 시스템 전체에서 하나의 인스턴스만 필요할 때 사용하고, Factory는 객체 생성 책임을 별도 메서드나 객체로 분리한다. 구조 패턴은 클래스나 객체를 조합하여 더 큰 구조를 만들거나 호환되지 않는 인터페이스를 연결한다. Adapter는 기존 인터페이스를 클라이언트가 기대하는 인터페이스로 변환하고, Proxy는 실제 객체 접근을 대리하면서 제어, 캐싱, 지연 로딩, 보안 검사를 수행한다. 행위 패턴은 객체 간 책임 분배와 협력 방식을 다룬다. Strategy는 알고리즘을 교체 가능하게 만들고, Observer는 한 객체의 상태 변화가 여러 객체에 자동 전파되도록 한다.

디자인 패턴이 중요한 이유는 코드의 재사용성, 확장성, 유지보수성을 높이기 때문이다. 또한 팀 내에서 “이 부분은 Strategy로 분리하자”, “여기는 Proxy로 접근 제어하자”처럼 공통 언어를 제공한다. 다만 패턴은 만능 해결책이 아니며, 불필요하게 적용하면 구조가 복잡해지고 오히려 가독성이 떨어질 수 있다. 따라서 패턴은 문제의 맥락, 변경 가능성, 의존성 방향, 테스트 용이성을 함께 고려하여 선택해야 한다.

## 1. Singleton Pattern

Singleton은 특정 클래스의 인스턴스가 애플리케이션 내에서 하나만 생성되도록 보장하고, 그 인스턴스에 전역적으로 접근할 수 있는 지점을 제공하는 생성 패턴이다. 대표적인 사용 예는 설정 객체, 로깅 객체, 애플리케이션 컨텍스트, 스레드 풀 관리자 등이다. 하지만 전역 상태를 만들기 쉽기 때문에 테스트가 어려워지고, 멀티스레드 환경에서 초기화 문제가 발생할 수 있다.

핵심 목적은 다음과 같다.

- 하나의 인스턴스만 생성 보장
- 전역 접근 지점 제공
- 공유 자원 관리
- 불필요한 객체 생성 방지

단, Singleton은 남용하면 전역 변수와 유사한 문제를 만든다. 의존성이 숨겨지고, 테스트 격리가 어려워지며, 병렬 테스트나 상태 초기화에서 문제가 생길 수 있다.

---

## 2. Factory Pattern

Factory는 객체 생성을 클라이언트 코드에서 분리하는 생성 패턴이다. 클라이언트가 `new ConcreteClass()`를 직접 호출하지 않고, Factory에 객체 생성을 위임한다. 이를 통해 클라이언트는 구체 클래스가 아니라 추상 타입이나 인터페이스에 의존할 수 있다.

Factory는 크게 다음 방식으로 사용된다.

- Simple Factory: 객체 생성 메서드를 별도 클래스로 분리
- Factory Method: 객체 생성을 서브클래스에 위임
- Abstract Factory: 관련 객체들의 집합을 생성하는 인터페이스 제공

Factory 패턴은 생성 로직이 복잡하거나, 런타임 조건에 따라 다른 구현체를 선택해야 하거나, 테스트에서 Mock 객체로 교체해야 할 때 유용하다.

---

## 3. Adapter Pattern

Adapter는 호환되지 않는 인터페이스를 가진 기존 클래스를 클라이언트가 기대하는 인터페이스로 사용할 수 있게 변환하는 구조 패턴이다. 이미 존재하는 클래스의 코드를 수정하지 않고 재사용할 수 있다는 점이 핵심이다.

예를 들어 클라이언트가 `PaymentProcessor` 인터페이스를 기대하지만 외부 결제 SDK가 `ExternalPayClient`라는 다른 인터페이스를 제공한다면, Adapter가 두 인터페이스 사이에서 변환 역할을 수행한다.

Adapter는 레거시 시스템 통합, 외부 API 연동, 라이브러리 교체, 호환성 유지에 자주 사용된다.

---

## 4. Proxy Pattern

Proxy는 실제 객체에 대한 접근을 대리하는 구조 패턴이다. 클라이언트는 실제 객체를 직접 호출하지 않고 Proxy를 호출하며, Proxy는 필요에 따라 실제 객체에 요청을 전달한다.

Proxy는 다음과 같은 상황에서 사용된다.

- 지연 초기화 Lazy Loading
- 접근 제어
- 원격 객체 호출
- 캐싱
- 로깅
- 트랜잭션 처리
- 보안 검사

Proxy는 실제 객체와 동일한 인터페이스를 제공하므로 클라이언트는 자신이 실제 객체를 사용하는지 Proxy를 사용하는지 알 필요가 없다.

---

## 5. Strategy Pattern

Strategy는 알고리즘을 객체로 캡슐화하고, 런타임에 교체 가능하게 만드는 행위 패턴이다. 같은 문제를 해결하는 여러 알고리즘이 있고, 상황에 따라 알고리즘을 바꿔야 할 때 유용하다.

예를 들어 결제 시스템에서 신용카드 결제, 계좌이체, 포인트 결제는 모두 “결제한다”는 동일한 목적을 가지지만 내부 알고리즘은 다르다. 이때 각 결제 방식을 Strategy로 분리하면 조건문을 줄이고 확장성을 높일 수 있다.

Strategy는 Open-Closed Principle, 즉 개방-폐쇄 원칙과 밀접하다. 새로운 알고리즘을 추가할 때 기존 Context 코드를 수정하지 않고 새로운 Strategy 구현체를 추가하는 방식으로 확장할 수 있다.

---

## 6. Observer Pattern

Observer는 한 객체의 상태 변화가 발생했을 때, 그 객체에 의존하는 여러 객체에게 자동으로 알림을 전달하는 행위 패턴이다. 상태를 가진 객체를 Subject 또는 Observable이라고 하고, 알림을 받는 객체를 Observer라고 한다.

대표적인 예는 이벤트 리스너, 메시지 구독, UI 이벤트 처리, 알림 시스템 등이다. Observer는 객체 간 직접 의존을 줄이고 일대다 의존 관계를 표현할 수 있다.

다만 Observer를 사용할 때는 구독 해제 누락, 이벤트 폭주, 순환 알림, 비동기 처리 순서 문제, 메모리 누수에 주의해야 한다.

## 1. Singleton 내부 동작 원리

Singleton의 핵심은 다음 세 가지다.

1. 생성자를 외부에서 호출하지 못하게 제한한다.
2. 클래스 내부에 자신의 유일한 인스턴스를 보관한다.
3. 외부에는 인스턴스 접근 메서드만 제공한다.

### 기본 구조

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {
    }

    public static Singleton getInstance() {
        return INSTANCE;
    }
}
```

### 동작 과정

```text
Client
  │
  │ getInstance()
  ▼
Singleton Class
  │
  ├── 이미 생성된 INSTANCE가 있는가?
  │       ├── Yes → 기존 인스턴스 반환
  │       └── No  → 새 인스턴스 생성 후 반환
  ▼
Single Shared Instance
```

### 멀티스레드 고려

지연 초기화 Lazy Initialization 방식에서는 여러 스레드가 동시에 `getInstance()`를 호출하면 인스턴스가 여러 개 생성될 수 있다. 이를 방지하려면 동기화, 정적 초기화, enum Singleton, 또는 Initialization-on-demand holder idiom 같은 방식을 사용한다.

```java
public class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

위 방식은 Java 클래스 로딩 시점을 이용해 지연 초기화와 스레드 안전성을 함께 얻는 방식으로 알려져 있다.

## 2. Factory 내부 동작 원리

Factory는 객체 생성 로직을 캡슐화한다. 클라이언트는 구체 클래스를 직접 알 필요 없이 Factory에 원하는 타입을 요청한다.

### 구조

```text
Client
  │
  │ create("card")
  ▼
PaymentFactory
  │
  ├── "card"     → CardPayment 생성
  ├── "transfer" → BankTransferPayment 생성
  └── "point"    → PointPayment 생성
  ▼
Payment interface
```

### 예시 코드

```java
interface Payment {
    void pay(int amount);
}

class CardPayment implements Payment {
    public void pay(int amount) {
        System.out.println("Card pay: " + amount);
    }
}

class BankTransferPayment implements Payment {
    public void pay(int amount) {
        System.out.println("Bank transfer pay: " + amount);
    }
}

class PaymentFactory {
    public static Payment create(String type) {
        if ("card".equals(type)) {
            return new CardPayment();
        }
        if ("transfer".equals(type)) {
            return new BankTransferPayment();
        }
        throw new IllegalArgumentException("Unsupported payment type");
    }
}
```

### 동작 흐름

1. 클라이언트가 Factory에 객체 생성을 요청한다.
2. Factory는 입력 조건, 설정값, 환경 변수, 타입 정보 등을 기준으로 구현체를 선택한다.
3. 선택된 구체 객체를 생성한다.
4. 클라이언트에는 추상 타입으로 반환한다.
5. 클라이언트는 실제 클래스가 무엇인지 몰라도 기능을 사용할 수 있다.

## 3. Adapter 내부 동작 원리

Adapter는 클라이언트가 원하는 Target 인터페이스를 구현하고, 내부에서 Adaptee의 메서드를 호출한다.

### 구조

```text
Client
  │
  │ request()
  ▼
Target Interface
  ▲
  │ implements
Adapter
  │
  │ specificRequest()
  ▼
Adaptee
```

### 예시 코드

```java
interface PaymentProcessor {
    void pay(int amount);
}

class ExternalPayClient {
    public void makePayment(String value) {
        System.out.println("External payment: " + value);
    }
}

class ExternalPayAdapter implements PaymentProcessor {
    private final ExternalPayClient externalPayClient;

    public ExternalPayAdapter(ExternalPayClient externalPayClient) {
        this.externalPayClient = externalPayClient;
    }

    public void pay(int amount) {
        externalPayClient.makePayment(String.valueOf(amount));
    }
}
```

### 동작 과정

1. 클라이언트는 `PaymentProcessor` 인터페이스만 알고 있다.
2. Adapter는 `PaymentProcessor`를 구현한다.
3. Adapter 내부에는 기존 클래스인 `ExternalPayClient`가 있다.
4. 클라이언트가 `pay()`를 호출하면 Adapter가 인자를 변환한다.
5. Adapter가 `ExternalPayClient.makePayment()`를 호출한다.

핵심은 “인터페이스 변환”이다. 데이터 형식, 메서드 이름, 호출 순서, 예외 타입 등을 변환할 수 있다.

## 4. Proxy 내부 동작 원리

Proxy는 실제 객체와 같은 인터페이스를 구현하고, 실제 객체 호출 전후에 부가 작업을 수행한다.

### 구조

```text
Client
  │
  │ operation()
  ▼
Proxy
  │
  ├── 권한 검사
  ├── 캐시 확인
  ├── 로깅
  ├── 지연 초기화
  │
  ▼
RealSubject
  │
  ▼
Actual Operation
```

### 예시 코드

```java
interface Image {
    void display();
}

class RealImage implements Image {
    private final String path;

    public RealImage(String path) {
        this.path = path;
        loadFromDisk();
    }

    private void loadFromDisk() {
        System.out.println("Loading: " + path);
    }

    public void display() {
        System.out.println("Display: " + path);
    }
}

class ImageProxy implements Image {
    private final String path;
    private RealImage realImage;

    public ImageProxy(String path) {
        this.path = path;
    }

    public void display() {
        if (realImage == null) {
            realImage = new RealImage(path);
        }
        realImage.display();
    }
}
```

### 동작 과정

1. 클라이언트는 Proxy 객체를 받는다.
2. Proxy는 실제 객체와 같은 인터페이스를 제공한다.
3. 클라이언트가 메서드를 호출한다.
4. Proxy가 접근 권한, 캐시, 초기화 여부 등을 확인한다.
5. 필요한 경우 실제 객체를 생성하거나 호출한다.
6. 결과를 클라이언트에 반환한다.

Proxy는 Decorator와 유사하지만 목적이 다르다. Decorator는 기능 확장에 초점이 있고, Proxy는 접근 제어와 대리 호출에 초점이 있다.

## 5. Strategy 내부 동작 원리

Strategy는 Context가 알고리즘 인터페이스에 의존하고, 구체 알고리즘은 별도 클래스로 분리되는 구조다.

### 구조

```text
Client
  │
  │ setStrategy()
  ▼
Context
  │
  │ execute()
  ▼
Strategy Interface
  ▲        ▲        ▲
  │        │        │
Card    Transfer   Point
Strategy Strategy  Strategy
```

### 예시 코드

```java
interface DiscountStrategy {
    int discount(int price);
}

class NoDiscountStrategy implements DiscountStrategy {
    public int discount(int price) {
        return price;
    }
}

class FixedDiscountStrategy implements DiscountStrategy {
    public int discount(int price) {
        return price - 1000;
    }
}

class RateDiscountStrategy implements DiscountStrategy {
    public int discount(int price) {
        return (int) (price * 0.9);
    }
}

class PriceCalculator {
    private DiscountStrategy discountStrategy;

    public PriceCalculator(DiscountStrategy discountStrategy) {
        this.discountStrategy = discountStrategy;
    }

    public int calculate(int price) {
        return discountStrategy.discount(price);
    }
}
```

### 동작 과정

1. 공통 알고리즘 인터페이스를 정의한다.
2. 각 알고리즘을 별도 Strategy 클래스로 구현한다.
3. Context는 구체 알고리즘이 아니라 Strategy 인터페이스에 의존한다.
4. 클라이언트는 상황에 따라 Strategy 구현체를 주입한다.
5. Context는 선택된 Strategy를 실행한다.

Strategy는 긴 `if-else` 또는 `switch` 조건문을 줄이는 데 자주 사용된다. 단, 알고리즘 수가 지나치게 많아지면 클래스 수가 늘어날 수 있다.

## 6. Observer 내부 동작 원리

Observer는 Subject가 Observer 목록을 관리하고, 상태 변화가 발생하면 등록된 Observer에게 알림을 전달한다.

### 구조

```text
Subject
  │
  ├── observers: List<Observer>
  │
  ├── attach(observer)
  ├── detach(observer)
  └── notify()
          │
          ├── observerA.update()
          ├── observerB.update()
          └── observerC.update()
```

### 예시 코드

```java
interface Observer {
    void update(String message);
}

class NewsSubscriber implements Observer {
    private final String name;

    public NewsSubscriber(String name) {
        this.name = name;
    }

    public void update(String message) {
        System.out.println(name + " received: " + message);
    }
}

class NewsPublisher {
    private final List<Observer> observers = new ArrayList<>();

    public void subscribe(Observer observer) {
        observers.add(observer);
    }

    public void unsubscribe(Observer observer) {
        observers.remove(observer);
    }

    public void publish(String message) {
        for (Observer observer : observers) {
            observer.update(message);
        }
    }
}
```

### 동작 과정

1. Observer가 Subject에 등록된다.
2. Subject는 Observer 목록을 보관한다.
3. Subject의 상태가 변경된다.
4. Subject가 `notify()`를 호출한다.
5. 등록된 Observer들의 `update()`가 호출된다.
6. Observer는 전달받은 이벤트나 상태를 기반으로 동작한다.

Observer는 동기 방식과 비동기 방식으로 구현할 수 있다. 동기 방식에서는 Subject가 Observer를 순차 호출하므로 느린 Observer가 전체 처리를 지연시킬 수 있다. 비동기 방식에서는 메시지 큐나 이벤트 버스를 활용해 느슨한 결합을 더 강화할 수 있다.

## 실제 시스템 연결

## 실제 시스템에서의 연결 사례

### 1. Singleton

- **Java `Runtime`**
  - Java의 `Runtime.getRuntime()`은 현재 Java 애플리케이션과 관련된 런타임 객체를 반환한다.
  - Singleton과 유사하게 전역 접근 지점을 제공하는 대표적인 예로 자주 언급된다.

- **Spring Framework Bean**
  - Spring의 기본 Bean scope는 singleton이다.
  - 이는 Spring IoC 컨테이너 안에서 Bean 이름 기준으로 하나의 객체 인스턴스를 공유하는 방식이다.
  - 단, GoF Singleton과 완전히 같지는 않다. GoF Singleton은 클래스 자체가 인스턴스 수를 제어하지만, Spring Singleton Bean은 컨테이너가 객체 생명주기를 관리한다.

- **로깅 시스템**
  - 많은 애플리케이션에서 Logger 인스턴스는 중앙화된 설정을 공유한다.
  - 다만 현대 로깅 프레임워크는 내부적으로 복잡한 팩토리, 캐시, 계층 구조를 사용하므로 단순 Singleton만으로 설명하기는 어렵다.

---

### 2. Factory

- **Java `Calendar.getInstance()`**
  - `Calendar.getInstance()`는 호출 환경에 맞는 `Calendar` 객체를 반환한다.
  - 클라이언트는 구체 구현 클래스를 직접 생성하지 않는다.

- **Java `DocumentBuilderFactory`**
  - XML 파싱에 사용되는 `DocumentBuilderFactory`는 Factory 계열 API의 대표적인 예다.
  - 구체 구현은 환경이나 설정에 따라 선택될 수 있다.

- **Spring BeanFactory / ApplicationContext**
  - Spring의 `BeanFactory`와 `ApplicationContext`는 객체 생성과 의존성 주입을 담당한다.
  - 일반적인 GoF Factory보다 더 넓은 IoC 컨테이너 역할을 수행한다.

---

### 3. Adapter

- **Java `InputStreamReader`**
  - `InputStreamReader`는 바이트 기반 `InputStream`을 문자 기반 `Reader`로 연결한다.
  - 바이트 스트림 인터페이스를 문자 스트림 인터페이스로 변환한다는 점에서 Adapter의 대표적인 예로 볼 수 있다.

- **레거시 시스템 연동**
  - 기존 SOAP API를 내부 REST 스타일 인터페이스로 감싸거나, 외부 결제 SDK를 내부 결제 인터페이스로 감싸는 방식은 Adapter의 전형적인 사용 방식이다.

- **Linux VFS**
  - Linux Virtual File System은 다양한 파일 시스템을 공통 인터페이스로 다루게 해준다.
  - 엄밀히 GoF Adapter라고 단정하기보다는, 서로 다른 구현체를 공통 추상화 뒤에 숨기는 구조적 유사성이 있다.

---

### 4. Proxy

- **Nginx Reverse Proxy**
  - Nginx는 클라이언트 요청을 백엔드 서버로 전달하는 리버스 프록시로 널리 사용된다.
  - TLS 종료, 로드 밸런싱, 캐싱, 요청 제한 등 부가 기능을 수행할 수 있다.

- **Java Dynamic Proxy**
  - `java.lang.reflect.Proxy`는 런타임에 인터페이스 기반 프록시 객체를 생성할 수 있다.
  - AOP, 트랜잭션, 로깅, 권한 검사 등에 활용된다.

- **Spring AOP**
  - Spring AOP는 프록시 기반으로 메서드 호출 전후에 부가 로직을 적용할 수 있다.
  - 예를 들어 `@Transactional`은 트랜잭션 경계를 프록시를 통해 관리하는 대표적인 사례다.

---

### 5. Strategy

- **정렬 알고리즘 선택**
  - 애플리케이션에서 데이터 크기나 특성에 따라 서로 다른 정렬 알고리즘을 선택하는 구조는 Strategy와 잘 맞는다.

- **결제 수단 선택**
  - 전자상거래 시스템에서 카드 결제, 간편 결제, 포인트 결제 등을 `PaymentStrategy`로 분리할 수 있다.

- **인증 방식 선택**
  - Basic Auth, OAuth2, API Key, JWT 검증 로직을 공통 인증 인터페이스 아래 Strategy로 분리할 수 있다.

---

### 6. Observer

- **GUI 이벤트 리스너**
  - 버튼 클릭, 키보드 입력, 마우스 이벤트 등은 Observer 구조와 밀접하다.
  - 이벤트 소스가 Subject 역할을 하고, 리스너가 Observer 역할을 한다.

- **JavaScript EventTarget**
  - 브라우저의 `addEventListener` / `removeEventListener` / 이벤트 디스패치 구조는 Observer와 유사한 이벤트 구독 모델이다.

- **메시지 기반 시스템**
  - Kafka, RabbitMQ, Redis Pub/Sub 같은 시스템은 분산 환경에서 Observer와 유사한 Publish-Subscribe 모델을 제공한다.
  - 단, GoF Observer는 일반적으로 객체 간 직접 알림 구조이고, 메시지 브로커는 네트워크 기반의 분산 Pub/Sub 구조라는 차이가 있다.

## 클라우드 연결

## 클라우드 환경에서의 디자인 패턴 연결

### 1. Singleton과 클라우드

클라우드 환경에서는 Singleton을 단일 프로세스 내부에만 적용할 수 있다는 점을 주의해야 한다. Kubernetes에서 Pod가 여러 개 실행되면 각 Pod 내부에는 별도의 Singleton 인스턴스가 존재한다. 즉, Singleton은 “클러스터 전체에서 하나”를 의미하지 않는다.

```text
Kubernetes Deployment replicas=3

Pod A → Singleton instance A
Pod B → Singleton instance B
Pod C → Singleton instance C
```

따라서 분산 환경에서 전역적으로 하나의 리더나 락이 필요하다면 Singleton 대신 다음과 같은 분산 메커니즘을 고려해야 한다.

- Kubernetes Lease API
- Redis 분산 락
- 데이터베이스 기반 락
- etcd 기반 리더 선출
- AWS DynamoDB conditional write 기반 락 구현

⚠️ 확인 필요: 특정 서비스에서 분산 락을 구현할 때는 해당 서비스의 일관성 모델, 장애 처리 방식, TTL 동작을 반드시 문서 기준으로 검토해야 한다.

---

### 2. Factory와 클라우드

Factory는 클라우드 SDK, 멀티 클라우드 추상화, 환경별 리소스 생성에서 자주 사용된다.

예를 들어 애플리케이션이 실행 환경에 따라 서로 다른 스토리지 클라이언트를 선택할 수 있다.

```text
StorageClientFactory
├── local  → LocalFileStorageClient
├── aws    → S3StorageClient
├── gcp    → CloudStorageClient
└── azure  → BlobStorageClient
```

이 구조를 사용하면 비즈니스 로직은 `StorageClient` 인터페이스에만 의존하고, 실제 구현체 선택은 설정값이나 런타임 환경에 맡길 수 있다.

Docker 환경에서는 환경 변수에 따라 Factory가 구현체를 선택할 수 있다.

```text
STORAGE_TYPE=s3
PAYMENT_PROVIDER=stripe
CACHE_TYPE=redis
```

Kubernetes에서는 ConfigMap이나 Secret을 통해 Factory 선택 값을 주입할 수 있다.

---

### 3. Adapter와 클라우드

클라우드 서비스는 제공자마다 API, 인증 방식, 응답 포맷, 오류 코드가 다르다. Adapter는 이러한 차이를 내부 표준 인터페이스로 감싸는 데 유용하다.

예시:

```text
InternalObjectStorage
  ▲
  ├── S3Adapter
  ├── GCSAdapter
  └── AzureBlobAdapter
```

비즈니스 로직은 다음과 같은 내부 인터페이스만 사용한다.

```java
interface ObjectStorage {
    void upload(String key, byte[] data);
    byte[] download(String key);
}
```

각 Adapter는 AWS S3, Google Cloud Storage, Azure Blob Storage SDK 호출을 내부적으로 수행한다. 이 방식은 멀티 클라우드, 클라우드 마이그레이션, 테스트 환경 구성에 유용하다.

---

### 4. Proxy와 클라우드

클라우드 환경에서 Proxy는 매우 핵심적인 구조다.

대표 사례:

- **AWS Elastic Load Balancing**
  - 클라이언트 요청을 여러 대상 인스턴스, 컨테이너, IP 등으로 분산한다.
- **AWS API Gateway**
  - 클라이언트와 백엔드 서비스 사이에서 인증, 라우팅, 요청 변환, 사용량 제한 등을 수행할 수 있다.
- **Kubernetes Service**
  - Pod 집합에 안정적인 네트워크 접근 지점을 제공한다.
  - 내부적으로 로드 밸런싱 역할을 수행한다.
- **Service Mesh**
  - Envoy 같은 사이드카 프록시를 통해 트래픽 제어, mTLS, 재시도, 타임아웃, 관측성을 제공할 수 있다.
  - Istio, Linkerd 등에서 이 개념이 사용된다.

```text
Client
  │
  ▼
API Gateway / Load Balancer / Service Mesh Proxy
  │
  ├── 인증
  ├── 라우팅
  ├── 속도 제한
  ├── 로깅
  └── TLS 처리
  ▼
Backend Service
```

---

### 5. Strategy와 클라우드

클라우드 환경에서는 배포 전략, 스케일링 전략, 장애 복구 전략, 비용 최적화 전략을 교체 가능하게 설계할 수 있다.

예시:

```text
ScalingStrategy
├── CPUBasedScalingStrategy
├── QueueLengthBasedScalingStrategy
└── ScheduleBasedScalingStrategy
```

Kubernetes의 Horizontal Pod Autoscaler는 CPU, 메모리 또는 커스텀 메트릭을 기준으로 스케일링할 수 있다. 애플리케이션 설계 측면에서는 이러한 정책을 Strategy처럼 추상화할 수 있다.

또한 배포 방식도 Strategy로 볼 수 있다.

- Rolling Deployment
- Blue-Green Deployment
- Canary Deployment

다만 이는 GoF Strategy 패턴의 직접 구현이라기보다, “교체 가능한 정책”이라는 설계 아이디어가 유사한 사례다.

---

### 6. Observer와 클라우드

클라우드 시스템은 이벤트 기반 아키텍처와 밀접하다. Observer 패턴은 이벤트 발행자와 구독자를 분리하는 기본 모델을 제공한다.

대표 사례:

- AWS SNS: Pub/Sub 메시징
- AWS EventBridge: 이벤트 라우팅
- Google Cloud Pub/Sub: 메시징 서비스
- Kubernetes Watch API: 리소스 변경 이벤트 감시
- Docker 이벤트 스트림: 컨테이너 상태 변화 이벤트 감시

```text
Event Source
  │
  ▼
Event Bus / Message Broker
  │
  ├── Subscriber A
  ├── Subscriber B
  └── Subscriber C
```

GoF Observer는 일반적으로 단일 프로세스 내부 객체 간 관계를 설명하지만, 클라우드에서는 메시지 브로커와 이벤트 버스를 통해 분산 Observer 구조로 확장된다.

## 보안 연결

## 디자인 패턴과 보안 이슈

### 1. Singleton 보안 이슈

Singleton은 전역 상태를 제공하므로 보안적으로 주의해야 한다.

#### 주요 위험

- 민감 정보가 Singleton 객체에 장기간 저장될 수 있음
- 테스트나 요청 간 상태가 공유되어 정보 누출 가능
- 멀티스레드 환경에서 race condition 발생 가능
- 리플렉션이나 역직렬화를 통해 인스턴스가 추가 생성될 수 있음

#### 모범 사례

- Singleton에 사용자별 세션 정보나 요청별 민감 정보를 저장하지 않는다.
- 불변 객체로 설계하거나 내부 상태 변경을 최소화한다.
- Java에서는 역직렬화 시 `readResolve()`를 고려한다.
- 멀티스레드 환경에서는 thread-safe 초기화 방식을 사용한다.
- 가능하다면 의존성 주입 컨테이너를 통해 생명주기를 관리한다.

---

### 2. Factory 보안 이슈

Factory는 입력값에 따라 객체를 생성하기 때문에, 외부 입력이 생성 타입 선택에 직접 사용되면 위험할 수 있다.

#### 주요 위험

- 허용되지 않은 클래스 생성
- 리플렉션 기반 Factory에서 임의 클래스 로딩
- 설정 조작을 통한 악성 구현체 주입
- 의존성 혼동 공격

#### 모범 사례

- 외부 입력을 클래스 이름으로 직접 사용하지 않는다.
- 허용 목록 allowlist 기반으로 생성 가능한 타입을 제한한다.
- Factory 설정값은 검증한다.
- Secret, 인증 클라이언트, 권한 객체 생성은 엄격히 통제한다.
- 리플렉션 사용 시 패키지, 클래스, 인터페이스 구현 여부를 검증한다.

---

### 3. Adapter 보안 이슈

Adapter는 외부 시스템과 내부 시스템의 경계에 위치하는 경우가 많다. 이 때문에 입력 검증과 오류 변환이 중요하다.

#### 주요 위험

- 외부 API 응답을 검증 없이 내부 모델로 변환
- 오류 메시지에 민감 정보 포함
- 인증 토큰, API Key 전달 과정에서 노출
- 데이터 포맷 변환 중 인코딩 문제 발생
- 외부 SDK의 예외를 그대로 노출

#### 모범 사례

- Adapter 경계에서 입력값과 응답값을 검증한다.
- 외부 오류를 내부 표준 오류로 변환하되 민감 정보는 제거한다.
- 인증 정보는 로그에 남기지 않는다.
- 데이터 인코딩, 문자셋, 시간대, 금액 단위 변환을 명확히 처리한다.
- 외부 시스템 timeout, retry, circuit breaker를 고려한다.

---

### 4. Proxy 보안 이슈

Proxy는 보안 통제 지점으로 매우 자주 사용된다. 하지만 잘못 설정하면 보안 취약점의 원인이 된다.

#### 주요 위험

- 잘못된 리버스 프록시 설정으로 내부 서비스 노출
- `X-Forwarded-For`, `X-Forwarded-Proto` 헤더 신뢰 오류
- 인증 우회
- 캐시 오염 Cache Poisoning
- SSRF Server-Side Request Forgery
- TLS 종료 지점 이후 내부 평문 통신 노출
- 과도한 권한을 가진 프록시 계정

#### 모범 사례

- 신뢰 가능한 프록시에서 온 헤더만 신뢰한다.
- 내부 서비스는 외부에서 직접 접근할 수 없도록 네트워크 정책을 적용한다.
- 프록시 계층에서 인증, 인가, rate limiting을 적용한다.
- 캐시 키에 인증 관련 헤더와 사용자 컨텍스트를 적절히 반영한다.
- mTLS, 보안 그룹, NetworkPolicy 등을 사용한다.
- 요청 크기 제한, 타임아웃, 업로드 제한을 설정한다.

### 5. Strategy 보안 이슈

Strategy는 알고리즘 교체를 쉽게 만들지만, 잘못된 Strategy가 선택되면 보안 정책이 약화될 수 있다.

#### 주요 위험

- 약한 암호화 알고리즘 Strategy 선택
- 인증 Strategy 오설정
- 권한 검증 Strategy 누락
- 외부 설정값 조작으로 보안 수준 낮은 구현체 사용
- 테스트용 Strategy가 운영 환경에 적용

#### 모범 사례

- 보안 관련 Strategy는 allowlist로 제한한다.
- 운영 환경에서는 안전한 기본값 secure default을 사용한다.
- 인증, 암호화, 권한 검증 Strategy 선택 로그를 남긴다.
- 테스트용 구현체가 운영 빌드에 포함되지 않도록 관리한다.
- 암호화 알고리즘은 검증된 표준과 라이브러리를 사용한다.

### 6. Observer 보안 이슈

Observer는 이벤트 전파 구조이므로 정보 노출과 이벤트 폭주에 주의해야 한다.

#### 주요 위험

- 민감 정보가 이벤트 메시지에 포함되어 여러 구독자에게 전파
- 구독 해제 누락으로 메모리 누수
- 악성 Observer가 이벤트 처리 지연
- 이벤트 재처리로 인한 중복 작업
- 권한 없는 구독자에게 이벤트 전달
- 이벤트 루프 또는 순환 알림 발생

#### 모범 사례

- 이벤트 payload에는 필요한 최소 정보만 포함한다.
- 구독자 권한을 검증한다.
- 이벤트 버스 사용 시 topic, queue 접근 권한을 제한한다.
- idempotency key를 사용해 중복 처리를 방지한다.
- dead letter queue를 구성해 실패 이벤트를 격리한다.
- Observer 실행 실패가 전체 Subject를 중단시키지 않도록 예외 처리를 설계한다.

## 면접 질문

**Q1. Singleton 패턴의 장점과 단점은 무엇인가요?**  
> 핵심 답변: Singleton은 하나의 인스턴스를 공유해야 하는 설정, 로거, 리소스 관리자 등에 유용하다. 전역 접근 지점을 제공하고 객체 생성을 제한할 수 있다. 하지만 전역 상태로 인해 테스트가 어려워지고, 의존성이 숨겨지며, 멀티스레드 환경에서 초기화 문제가 발생할 수 있다. 분산 환경에서는 프로세스마다 Singleton이 생기므로 클러스터 전체의 단일성을 보장하지 않는다.

**Q2. Factory 패턴을 사용하는 이유는 무엇인가요?**  
> 핵심 답변: 객체 생성 로직을 클라이언트로부터 분리하기 위해 사용한다. 클라이언트는 구체 클래스가 아니라 인터페이스에 의존할 수 있고, 런타임 조건이나 설정에 따라 다른 구현체를 선택할 수 있다. 생성 로직이 복잡하거나 구현체 교체 가능성이 높은 경우 Factory가 유용하다.

**Q3. Adapter와 Proxy의 차이는 무엇인가요?**  
> 핵심 답변: Adapter는 호환되지 않는 인터페이스를 변환하기 위한 패턴이다. 목적은 기존 객체를 클라이언트가 기대하는 인터페이스로 사용할 수 있게 만드는 것이다. Proxy는 실제 객체 접근을 대리하면서 접근 제어, 지연 로딩, 캐싱, 로깅, 보안 검사 등을 수행한다. Adapter는 인터페이스 변환, Proxy는 접근 제어와 대리 호출이 핵심이다.
