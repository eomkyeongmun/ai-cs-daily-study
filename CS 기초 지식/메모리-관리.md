# 메모리 관리 - 연속 메모리 할당, 페이징, 세그멘테이션, 외부/내부 단편화

## 핵심 개념

메모리 관리는 운영체제가 제한된 물리 메모리(RAM)를 여러 프로세스가 안전하고 효율적으로 사용할 수 있도록 배분, 회수, 보호, 주소 변환을 수행하는 핵심 기능이다. 프로그램은 실행 중 코드, 데이터, 힙, 스택 등을 메모리에 적재해야 하며, 운영체제는 각 프로세스가 자신의 주소 공간만 접근하도록 격리해야 한다. 초기 시스템에서는 프로세스를 물리 메모리의 연속된 공간에 배치하는 **연속 메모리 할당** 방식이 사용되었지만, 프로세스 크기 변화와 빈 공간 관리 문제로 인해 **외부 단편화**가 발생하기 쉽다. 이를 해결하기 위해 현대 운영체제는 메모리를 고정 크기 블록으로 나누는 **페이징**을 널리 사용한다. 페이징은 프로세스의 논리 주소 공간을 페이지 단위로 나누고, 물리 메모리는 프레임 단위로 나누어 비연속적으로 매핑할 수 있게 한다. 반면 **세그멘테이션**은 코드, 데이터, 스택처럼 의미 있는 논리 단위로 메모리를 나누는 방식이다.

메모리 관리가 중요한 이유는 성능, 안정성, 보안이 모두 여기에 의존하기 때문이다. 잘못된 메모리 할당 정책은 메모리 낭비와 성능 저하를 일으키고, 주소 보호가 부실하면 한 프로세스가 다른 프로세스나 커널 메모리를 침범할 수 있다. 또한 가상 메모리, 페이지 교체, 메모리 매핑 파일, 컨테이너 메모리 제한, 클라우드 인스턴스의 메모리 최적화도 모두 메모리 관리 개념 위에 구축된다.

핵심적으로 이해해야 할 네 가지는 다음과 같다.

1. **연속 메모리 할당**
   - 하나의 프로세스를 물리 메모리의 연속된 공간에 배치한다.
   - 구현은 단순하지만 외부 단편화가 발생하기 쉽다.

2. **페이징**
   - 논리 메모리를 페이지, 물리 메모리를 프레임으로 나눈다.
   - 비연속 할당이 가능하며 외부 단편화를 크게 줄인다.
   - 단, 마지막 페이지 내부에 사용되지 않는 공간이 생길 수 있어 내부 단편화가 발생할 수 있다.

3. **세그멘테이션**
   - 프로그램을 코드, 데이터, 힙, 스택 등 논리적 의미 단위로 나눈다.
   - 보호와 공유에 유리하지만 가변 크기 할당이므로 외부 단편화가 발생할 수 있다.

4. **단편화**
   - **외부 단편화**: 전체 여유 공간은 충분하지만 연속된 큰 공간이 없어 할당하지 못하는 문제.
   - **내부 단편화**: 할당된 블록 내부에서 실제로 사용하지 않는 공간이 낭비되는 문제.

## 내부 동작 원리

## 1. 연속 메모리 할당

연속 메모리 할당은 각 프로세스가 물리 메모리의 하나의 연속 구간을 차지하는 방식이다. 운영체제는 메모리의 빈 구간을 관리하다가 새 프로세스가 들어오면 충분히 큰 빈 공간을 찾아 할당한다.

대표적인 할당 전략은 다음과 같다.

- **First Fit**
  - 처음 발견한 충분히 큰 빈 공간에 할당한다.
  - 빠르지만 앞쪽에 작은 빈 공간이 많이 남을 수 있다.

- **Best Fit**
  - 요청 크기와 가장 비슷한 빈 공간에 할당한다.
  - 남는 공간을 최소화하려 하지만 작은 조각이 많이 생길 수 있다.

- **Worst Fit**
  - 가장 큰 빈 공간에 할당한다.
  - 큰 빈 공간을 쪼개어 중간 크기의 빈 공간을 남기려는 전략이다.

### 연속 할당 예시

```text
초기 메모리 상태

+---------+---------+---------+---------+---------+
|   OS    |  Free   |  Free   |  Free   |  Free   |
+---------+---------+---------+---------+---------+

프로세스 A, B, C 할당 후

+---------+---------+---------+---------+---------+
|   OS    |    A    |    B    |    C    |  Free   |
+---------+---------+---------+---------+---------+

B 종료 후

+---------+---------+---------+---------+---------+
|   OS    |    A    |  Free   |    C    |  Free   |
+---------+---------+---------+---------+---------+
```

이때 B가 사용하던 공간과 뒤쪽 Free 공간이 떨어져 있다. 전체 Free 공간의 합은 충분해도 새 프로세스 D가 연속된 큰 공간을 요구하면 할당하지 못할 수 있다. 이것이 외부 단편화다.

## 2. 페이징

페이징은 가상 주소 공간과 물리 메모리를 고정 크기 블록으로 나누는 방식이다.

- 가상 메모리의 블록: **페이지(Page)**
- 물리 메모리의 블록: **프레임(Frame)**
- 페이지와 프레임의 크기는 동일하다.
- 프로세스의 페이지는 물리 메모리의 임의 프레임에 배치될 수 있다.

주소 변환은 보통 다음과 같이 이루어진다.

```text
가상 주소 = [페이지 번호 p | 페이지 오프셋 d]

페이지 번호 p -> 페이지 테이블 조회 -> 프레임 번호 f

물리 주소 = [프레임 번호 f | 페이지 오프셋 d]
```

### 페이징 주소 변환 다이어그램

```text
프로세스 가상 주소 공간

+---------+---------+---------+---------+
| Page 0  | Page 1  | Page 2  | Page 3  |
+---------+---------+---------+---------+

페이지 테이블

+---------+---------+
| Page No | FrameNo |
+---------+---------+
|   0     |   5     |
|   1     |   2     |
|   2     |   8     |
|   3     |   1     |
+---------+---------+

물리 메모리

+---------+---------+---------+---------+---------+
| Frame 0 | Frame 1 | Frame 2 | Frame 3 | Frame 4 |
+---------+---------+---------+---------+---------+
                      ↑
                    Page 1

+---------+---------+---------+---------+
| Frame 5 | Frame 6 | Frame 7 | Frame 8 |
+---------+---------+---------+---------+
    ↑                               ↑
  Page 0                          Page 2
```

페이징의 장점은 프로세스를 연속된 물리 메모리에 배치할 필요가 없다는 점이다. 따라서 외부 단편화 문제를 크게 완화한다. 하지만 프로세스 크기가 페이지 크기의 배수가 아닐 경우 마지막 페이지 일부가 사용되지 않을 수 있다. 이것이 내부 단편화다.

예를 들어 페이지 크기가 4KB이고 프로세스가 10KB를 사용한다면 3개의 페이지, 즉 12KB가 할당된다. 이때 마지막 2KB는 사용되지 않을 수 있다.

```text
프로세스 크기: 10KB
페이지 크기: 4KB

+------+------+
| 4KB  | 사용 |
+------+------+

+------+------+
| 4KB  | 사용 |
+------+------+

+------+------+
| 2KB  | 사용 |
| 2KB  | 낭비 |
+------+------+
```

## 3. TLB와 페이지 테이블

페이징에서는 모든 메모리 접근마다 페이지 테이블을 조회해야 하므로 성능 비용이 발생한다. 이를 줄이기 위해 CPU에는 일반적으로 **TLB(Translation Lookaside Buffer)** 라는 고속 캐시가 있다.

동작 과정은 다음과 같다.

1. CPU가 가상 주소를 생성한다.
2. MMU가 페이지 번호를 추출한다.
3. TLB에서 해당 페이지 번호의 변환 정보를 찾는다.
4. TLB hit이면 즉시 프레임 번호를 얻는다.
5. TLB miss이면 페이지 테이블을 조회한다.
6. 페이지 테이블 엔트리가 유효하면 TLB에 캐시하고 주소 변환을 수행한다.
7. 유효하지 않으면 페이지 폴트가 발생한다.

```text
CPU
 |
 | 가상 주소
 v
MMU
 |
 +--> TLB 조회
 |      |
 |      +-- hit  --> 물리 주소 생성
 |      |
 |      +-- miss --> 페이지 테이블 조회
 |
 v
물리 메모리 접근
```

## 4. 페이지 폴트

페이지 폴트는 프로세스가 접근한 페이지가 현재 물리 메모리에 없거나 접근 권한이 없는 경우 발생하는 예외다. 모든 페이지 폴트가 오류는 아니다. 가상 메모리 시스템에서는 필요한 페이지를 디스크에서 메모리로 가져오기 위해 정상적으로 페이지 폴트를 활용한다.

일반적인 페이지 폴트 처리 과정은 다음과 같다.

1. 프로세스가 특정 가상 주소에 접근한다.
2. 페이지 테이블 엔트리가 invalid 상태이거나 권한 위반이 확인된다.
3. CPU가 페이지 폴트 예외를 발생시킨다.
4. 운영체제 커널의 페이지 폴트 핸들러가 실행된다.
5. 접근이 합법적인지 확인한다.
6. 합법적이고 페이지가 디스크나 파일에 있으면 빈 프레임을 확보한다.
7. 필요하면 기존 페이지를 디스크로 내보내는 페이지 교체를 수행한다.
8. 필요한 페이지를 메모리에 적재한다.
9. 페이지 테이블을 갱신한다.
10. 중단된 명령을 재실행한다.

## 5. 세그멘테이션

세그멘테이션은 프로그램을 논리적 단위인 세그먼트로 나누어 관리한다.

대표적인 세그먼트는 다음과 같다.

- 코드 세그먼트
- 데이터 세그먼트
- 힙 세그먼트
- 스택 세그먼트
- 공유 라이브러리 세그먼트

주소는 보통 다음과 같이 표현된다.

```text
논리 주소 = [세그먼트 번호 s | 오프셋 d]
```

세그먼트 테이블에는 각 세그먼트의 기준 주소(base)와 한계값(limit)이 저장된다.

```text
세그먼트 테이블

+-----------+-----------+-----------+
| SegmentNo |   Base    |   Limit   |
+-----------+-----------+-----------+
|     0     |   1000    |    400    |
|     1     |   5000    |   1200    |
|     2     |   9000    |    800    |
+-----------+-----------+-----------+
```

주소 변환 과정은 다음과 같다.

1. 세그먼트 번호로 세그먼트 테이블을 조회한다.
2. 오프셋이 limit보다 작은지 검사한다.
3. 유효하면 `base + offset`으로 물리 주소를 계산한다.
4. 오프셋이 limit 이상이면 보호 오류가 발생한다.

```text
논리 주소: Segment 1, Offset 300

Segment 1:
Base = 5000
Limit = 1200

Offset 300 < Limit 1200 이므로 유효

물리 주소 = 5000 + 300 = 5300
```

세그멘테이션은 논리 단위별 보호와 공유에 유리하다. 예를 들어 코드 세그먼트는 읽기/실행 권한만 부여하고, 데이터 세그먼트는 읽기/쓰기 권한을 부여할 수 있다. 하지만 세그먼트 크기가 가변적이므로 연속 메모리 할당과 마찬가지로 외부 단편화가 발생할 수 있다.

## 6. 외부 단편화와 내부 단편화 비교

| 구분 | 외부 단편화 | 내부 단편화 |
|---|---|---|
| 발생 위치 | 할당된 블록 사이의 빈 공간 | 할당된 블록 내부의 미사용 공간 |
| 주요 원인 | 가변 크기 할당 | 고정 크기 블록 할당 |
| 대표 사례 | 연속 메모리 할당, 세그멘테이션 | 페이징, 고정 크기 파티션 |
| 문제 | 총 여유 공간은 충분하지만 큰 연속 공간 부족 | 할당은 되었지만 일부 공간 낭비 |
| 해결/완화 | 압축, 병합, 페이징 | 블록 크기 조정, 작은 단위 할당 |

## 실제 시스템 연결

## Linux에서의 메모리 관리

현대 Linux는 프로세스마다 독립적인 가상 주소 공간을 제공하고, 페이지 기반 가상 메모리 시스템을 사용한다. 각 프로세스는 자신만의 주소 공간을 가진 것처럼 동작하지만, 실제 물리 메모리에는 페이지 단위로 매핑된다.

Linux 프로세스의 주소 공간은 일반적으로 다음과 같은 영역으로 구성된다.

```text
높은 주소
+----------------------+
| Stack                |
+----------------------+
| Memory Mapping Area  |
| Shared Libraries     |
| mmap 영역            |
+----------------------+
| Heap                 |
+----------------------+
| BSS                  |
+----------------------+
| Data                 |
+----------------------+
| Text / Code          |
+----------------------+
낮은 주소
```

이 구조는 세그멘테이션의 논리적 구분과 유사하게 보일 수 있지만, 실제 메모리 관리는 주로 페이징 기반으로 이루어진다. Linux에서 실행 파일, 공유 라이브러리, 익명 메모리, 파일 매핑 메모리는 모두 가상 메모리 영역으로 관리되며, 필요할 때 페이지 단위로 물리 메모리에 적재될 수 있다.

## mmap

Linux의 `mmap`은 파일이나 익명 메모리를 프로세스의 가상 주소 공간에 매핑하는 시스템 호출이다. 예를 들어 데이터베이스나 웹 서버는 큰 파일을 직접 읽기보다 `mmap`을 통해 파일 내용을 메모리처럼 접근할 수 있다.

```text
파일
+---------+---------+---------+
| block 0 | block 1 | block 2 |
+---------+---------+---------+
       |
       v
프로세스 가상 주소 공간
+---------+---------+---------+
| page 0  | page 1  | page 2  |
+---------+---------+---------+
```

실제로 해당 페이지를 처음 접근하면 페이지 폴트가 발생하고, 운영체제가 파일의 해당 부분을 메모리에 적재한다. 이를 통해 불필요한 선적재를 줄일 수 있다.

## Copy-on-Write

Linux의 `fork()`는 부모 프로세스의 주소 공간을 자식 프로세스에 복사하는 것처럼 보이지만, 실제로는 많은 경우 페이지를 즉시 복사하지 않고 공유한다. 부모나 자식 중 하나가 해당 페이지에 쓰기를 시도하면 그때 페이지를 복사한다. 이를 **Copy-on-Write(COW)** 라고 한다.

```text
fork 직후

Parent Page A ─┐
                ├── Physical Frame X
Child Page A  ─┘

Child가 쓰기 시도

Parent Page A ─── Physical Frame X
Child Page A  ─── Physical Frame Y
```

COW는 불필요한 메모리 복사를 줄여 프로세스 생성 성능과 메모리 효율성을 높인다.

## x86 계열 시스템과 세그멘테이션

x86 아키텍처에는 세그멘테이션 기능이 존재한다. 다만 현대 64비트 운영체제에서는 일반적인 메모리 격리와 주소 변환을 주로 페이징으로 처리한다.  
⚠️ 확인 필요: 구체적인 세그먼트 레지스터 활용 방식은 운영체제, CPU 모드, ABI에 따라 차이가 있으므로 특정 시스템의 구현을 확인해야 한다.

## Nginx와 메모리

Nginx는 이벤트 기반 구조를 사용하며, 워커 프로세스들이 요청을 처리한다. 각 워커 프로세스는 독립된 가상 주소 공간을 갖고, 커널은 페이지 테이블을 통해 이를 물리 메모리에 매핑한다. 정적 파일 제공 시 운영체제의 페이지 캐시가 활용될 수 있으며, 자주 접근되는 파일 데이터가 메모리에 캐시되어 디스크 I/O를 줄인다.

Nginx 자체가 페이징을 직접 제어하는 것은 아니지만, 실제 성능은 다음과 같은 OS 메모리 기능과 밀접하다.

- 페이지 캐시
- 파일 디스크립터와 버퍼 관리
- `sendfile`
- 메모리 매핑
- 워커 프로세스별 주소 공간 격리

## 클라우드 연결

## Docker와 메모리 관리

Docker 컨테이너는 호스트 OS 커널을 공유하지만, 프로세스는 일반 Linux 프로세스처럼 가상 메모리와 페이지 테이블 기반 메모리 관리를 받는다. 컨테이너는 별도의 커널을 갖는 VM이 아니며, Linux의 namespace와 cgroup을 활용해 격리와 자원 제한을 제공한다.

컨테이너 메모리 제한은 주로 cgroup을 통해 적용된다. 예를 들어 Docker에서 메모리 제한을 설정하면 해당 컨테이너의 프로세스들이 사용할 수 있는 메모리 양이 제한된다.

```bash
docker run --memory=512m nginx
```

이 제한을 초과하면 커널의 OOM Killer가 컨테이너 내 프로세스를 종료할 수 있다.  
⚠️ 확인 필요: OOM 발생 시 어떤 프로세스가 종료되는지와 로그 위치는 커널 버전, cgroup 버전, 컨테이너 런타임 설정에 따라 달라질 수 있다.

## Kubernetes와 메모리 Requests/Limits

Kubernetes는 컨테이너 단위로 메모리 request와 limit을 설정할 수 있다.

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

- **request**
  - 스케줄러가 Pod를 어느 노드에 배치할지 판단할 때 사용한다.
  - 최소한 이 정도 메모리가 필요하다는 의미다.

- **limit**
  - 컨테이너가 사용할 수 있는 메모리 상한이다.
  - 초과 시 OOMKilled 상태가 될 수 있다.

운영체제 관점에서 Kubernetes의 메모리 제한도 결국 호스트 커널의 메모리 관리, 페이지 캐시, cgroup, OOM 정책과 연결된다. Pod 내부에서 `free` 명령을 실행했을 때 보이는 메모리 정보는 환경과 설정에 따라 해석에 주의가 필요하다.

## AWS EC2와 가상 메모리

AWS EC2 인스턴스는 선택한 인스턴스 타입에 따라 vCPU와 메모리 용량이 정해진다. EC2 내부에서 실행되는 Linux나 Windows는 일반 서버와 마찬가지로 가상 메모리, 페이징, 페이지 캐시를 사용한다.

메모리 관리 관점에서 EC2 운영 시 중요한 요소는 다음과 같다.

- 인스턴스 타입별 메모리 용량
- 애플리케이션의 RSS, VMS, page fault 추이
- swap 사용 여부
- 페이지 캐시 사용량
- OOM 발생 여부
- NUMA 특성  
  ⚠️ 확인 필요: NUMA 구성은 인스턴스 타입과 하이퍼바이저/하드웨어 구성에 따라 다를 수 있으므로 실제 인스턴스에서 확인해야 한다.

## AWS Lambda와 메모리

AWS Lambda는 함수에 할당하는 메모리 크기를 설정할 수 있고, 메모리 설정은 실행 환경의 자원 할당과 연관된다.  
⚠️ 확인 필요: Lambda에서 메모리 설정과 CPU 성능 할당의 구체적인 비율 및 세부 동작은 AWS 공식 문서의 최신 내용을 확인해야 한다.

메모리 관리 관점에서는 함수 실행 중 객체 생성, 캐시 사용, 대용량 파일 처리 방식이 중요하다. 메모리 사용량이 과도하면 성능 저하나 실행 실패로 이어질 수 있다.

## GCP, AWS, Kubernetes에서 공통적으로 중요한 지표

클라우드 환경에서 메모리 관리 문제를 분석할 때는 다음 지표를 자주 확인한다.

- RSS: 실제 물리 메모리에 상주하는 프로세스 메모리
- VMS/VSZ: 프로세스가 확보한 가상 메모리 크기
- Page Fault: 페이지 폴트 발생 수
- Major Page Fault: 디스크 I/O가 필요한 페이지 폴트
- Minor Page Fault: 디스크 I/O 없이 처리 가능한 페이지 폴트
- Swap 사용량
- OOM Kill 발생 여부
- Page Cache 사용량
- 컨테이너 memory working set  
  ⚠️ 확인 필요: “working set”의 계산 방식은 모니터링 도구와 런타임에 따라 차이가 있을 수 있다.

## 보안 연결

## 1. 메모리 보호와 주소 공간 격리

운영체제의 메모리 관리는 보안의 핵심이다. 각 프로세스가 독립된 가상 주소 공간을 갖기 때문에, 일반적으로 한 프로세스는 다른 프로세스의 메모리에 직접 접근할 수 없다. 페이지 테이블 엔트리에는 읽기, 쓰기, 실행 가능 여부와 사용자/커널 접근 권한 같은 보호 정보가 포함될 수 있다.

예를 들어 사용자 프로세스가 커널 전용 페이지에 접근하려고 하면 권한 위반으로 예외가 발생한다. 이 구조가 없다면 악성 프로세스가 다른 프로세스의 비밀번호, 암호화 키, 세션 토큰 등을 읽을 수 있다.

## 2. NX Bit와 실행 방지

현대 시스템에서는 페이지 단위로 실행 권한을 제어할 수 있다. NX bit 또는 XD bit로 알려진 실행 방지 기능은 데이터 영역이나 스택 영역에서 코드 실행을 막는 데 사용된다.

예를 들어 스택 버퍼 오버플로우 공격에서 공격자가 쉘코드를 스택에 주입하더라도, 스택 페이지가 실행 불가능으로 표시되어 있으면 실행이 차단될 수 있다.

```text
페이지 권한 예시

+-------------+----------+----------+----------+
| 영역        | Read     | Write    | Execute  |
+-------------+----------+----------+----------+
| Code        | Yes      | No       | Yes      |
| Data        | Yes      | Yes      | No       |
| Stack       | Yes      | Yes      | No       |
+-------------+----------+----------+----------+
```

## 3. ASLR

ASLR(Address Space Layout Randomization)은 프로세스의 코드, 스택, 힙, 라이브러리 등의 가상 주소 배치를 무작위화하여 공격자가 정확한 주소를 예측하기 어렵게 만드는 보안 기법이다. ASLR은 메모리 손상 취약점이 존재하더라도 익스플로잇 성공 가능성을 낮춘다.

단, ASLR은 단독 방어책이 아니며 정보 누출 취약점이 있으면 우회될 수 있다. 따라서 스택 카나리, RELRO, PIE, NX와 함께 사용하는 것이 일반적이다.

## 4. 페이지 권한과 W^X 원칙

W^X는 Writable과 Executable이 동시에 허용되지 않도록 하는 원칙이다. 즉, 어떤 메모리 페이지가 쓰기 가능하면 실행 불가능해야 하고, 실행 가능하면 쓰기 불가능해야 한다.

이 원칙은 JIT 컴파일러, 브라우저 엔진, 동적 코드 생성 시스템에서 특히 중요하다. JIT는 실행 중 코드를 생성해야 하므로 메모리를 쓰기 가능 상태로 만들었다가 실행 가능 상태로 전환하는 과정이 필요하다. 이 과정이 부주의하면 공격자가 쓰기 가능한 실행 페이지를 악용할 수 있다.

## 5. Rowhammer

Rowhammer는 DRAM의 물리적 특성을 악용해 인접한 메모리 셀의 비트를 뒤집는 공격 기법이다. 이는 운영체제의 논리적 메모리 보호만으로 완전히 막기 어렵고, 하드웨어, 메모리 컨트롤러, ECC 메모리, 커널 완화 기법 등이 함께 고려된다.

⚠️ 확인 필요: 특정 시스템에서 Rowhammer 방어 가능 여부는 DRAM 종류, CPU, 메모리 컨트롤러, ECC 적용 여부, 커널 설정에 따라 크게 달라진다.

## 6. Meltdown/Spectre 계열 취약점과 메모리 격리

Meltdown과 Spectre는 CPU의 추측 실행 및 캐시 부채널을 악용해 보호되어야 할 메모리 정보가 유출될 수 있음을 보인 취약점 계열이다. 이들은 전통적인 페이지 권한 검사만으로는 충분하지 않을 수 있음을 보여준다.

운영체제와 CPU 제조사는 KPTI, 마이크로코드 업데이트, 컴파일러 완화 기법 등을 통해 대응해 왔다.  
⚠️ 확인 필요: 특정 CPU와 운영체제에서 적용되는 완화 기법과 성능 영향은 제품, 커널 버전, 설정에 따라 다르므로 최신 벤더 문서를 확인해야 한다.

## 7. 보안 모범 사례

- 최소 권한 원칙에 따라 메모리 권한을 설정한다.
- 스택과 힙은 실행 불가능하게 설정한다.
- ASLR, NX, PIE, RELRO, Stack Canary를 활성화한다.
- 컨테이너에 메모리 limit을 설정해 리소스 고갈 공격을 완화한다.
- 민감 정보는 사용 후 가능한 한 빠르게 제거한다.
- 코어 덤프에 민감 정보가 포함될 수 있으므로 운영 환경에서는 정책적으로 관리한다.
- swap에 민감 정보가 기록될 수 있으므로 암호화나 비활성화 정책을 검토한다.
- 커널, 런타임, 하이퍼바이저 보안 패치를 주기적으로 적용한다.

## 면접 질문

**Q1. 연속 메모리 할당에서 외부 단편화가 발생하는 이유는 무엇인가요?**  
> 핵심 답변: 프로세스가 가변 크기의 연속된 물리 메모리 공간을 요구하기 때문이다. 프로세스 생성과 종료가 반복되면 빈 공간이 여러 곳에 흩어지고, 전체 여유 공간은 충분해도 하나의 큰 연속 공간이 없어 새 프로세스를 할당하지 못할 수 있다.

**Q2. 페이징은 외부 단편화를 어떻게 해결하나요?**  
> 핵심 답변: 프로세스를 고정 크기 페이지로 나누고 물리 메모리도 같은 크기의 프레임으로 나누어 비연속적으로 배치할 수 있게 한다. 따라서 프로세스 전체가 하나의 연속된 물리 공간에 들어갈 필요가 없으며 외부 단편화가 크게 줄어든다. 다만 마지막 페이지 내부에 사용되지 않는 공간이 생겨 내부 단편화가 발생할 수 있다.

**Q3. 내부 단편화와 외부 단편화의 차이는 무엇인가요?**  
> 핵심 답변: 내부 단편화는 할당된 블록 내부에서 사용되지 않는 공간이 낭비되는 현상이고, 외부 단편화는 할당된 블록들 사이에 작은 빈 공간들이 흩어져 큰 연속 공간을 확보하지 못하는 현상이다. 내부 단편화는 고정 크기 할당에서, 외부 단편화는 가변 크기 할당에서 주로 발생한다.

**Q4. 페이지 테이블과 TLB의 역할은 무엇인가요?**  
> 핵심 답변: 페이지 테이블은 가상 페이지 번호를 물리 프레임 번호로 매핑하는 자료구조다. TLB는 최근 사용한 주소 변환 정보를 저장하는 CPU 내부의 고속 캐시다. TLB hit이면 페이지 테이블 조회 없이 빠르게 물리 주소를 얻을 수 있고, TLB miss이면 페이지 테이블을 조회해야 한다.

**Q5. 세그멘테이션과 페이징의 차이는 무엇인가요?**  
> 핵심 답변: 세그멘테이션은 코드, 데이터, 스택처럼 의미 있는 논리 단위로 메모리를 나누며 각 세그먼트 크기가 다를 수 있다. 페이징은 의미와 무관하게 고정 크기 페이지로 나눈다. 세그멘테이션은 보호와 공유에 유리하지만 외부 단편화가 생길 수 있고, 페이징은 외부 단편화를 줄이지만 내부 단편화가 발생할 수 있다.

- [[cgroup]] - Linux에서 프로세스 그룹의 CPU, 메모리 등 자원 사용량을 제한하는 기능
- [[ASLR]] - 메모리 주소 배치를 무작위화해 익스플로잇 난이도를 높이는 보안 기법
- [[NX Bit]] - 데이터 영역에서 코드 실행을 방지하기 위한 페이지 실행 권한 제어 기능
- [[힙과 스택]] - 프로세스 주소 공간 내 동적 할당과 함수 호출 정보를 관리하는 주요 영역
- [[커널 메모리]] - 운영체제 커널이 사용하는 보호된 메모리 영역
- [[NUMA]] - 메모리 접근 비용이 CPU와 메모리의 물리적 위치에 따라 달라지는 구조
