# 프로세스와 스레드 - 차이점, Context Switching, 멀티 프로세스 vs 멀티 스레드

## 핵심 개념

## 프로세스와 스레드 핵심 개념

**프로세스(Process)**는 실행 중인 프로그램의 인스턴스이다. 운영체제는 각 프로세스에 독립적인 **가상 주소 공간**, 실행 상태, 파일 디스크립터, 레지스터 상태, 권한 정보 등을 부여한다. 즉, 프로세스는 운영체제가 자원을 할당하고 보호하는 기본 단위라고 볼 수 있다.

**스레드(Thread)**는 프로세스 내부에서 실행되는 흐름의 단위이다. 하나의 프로세스 안에는 하나 이상의 스레드가 존재할 수 있으며, 같은 프로세스의 스레드들은 일반적으로 **코드 영역, 데이터 영역, 힙 영역, 열린 파일 정보** 등을 공유한다. 반면 각 스레드는 자신의 **스택, 레지스터, 프로그램 카운터**를 가진다.

프로세스와 스레드의 차이를 이해하는 것은 운영체제, 서버 개발, 병렬 처리, 성능 최적화, 장애 격리, 보안 설계에서 매우 중요하다. 예를 들어 웹 서버를 만들 때 요청마다 프로세스를 만들지, 스레드를 만들지, 이벤트 기반으로 처리할지에 따라 성능과 안정성이 크게 달라진다. 멀티 프로세스는 격리성이 좋지만 상대적으로 자원 사용량이 크고, 멀티 스레드는 자원 공유가 쉬워 효율적이지만 동기화 문제가 발생하기 쉽다.

### 프로세스와 스레드 비교

| 구분 | 프로세스 | 스레드 |
|---|---|---|
| 기본 의미 | 실행 중인 프로그램 인스턴스 | 프로세스 내부 실행 흐름 |
| 메모리 공간 | 일반적으로 독립적인 주소 공간 | 같은 프로세스 내 메모리 공유 |
| 생성 비용 | 상대적으로 큼 | 상대적으로 작음 |
| 통신 방식 | IPC 필요 | 공유 메모리 사용 가능 |
| 장애 영향 | 한 프로세스 장애가 다른 프로세스에 직접 영향 적음 | 한 스레드 오류가 전체 프로세스에 영향 가능 |
| 동기화 필요성 | IPC 사용 시 필요 | 공유 자원 접근 시 매우 중요 |
| 대표 사용 사례 | 브라우저 탭 분리, 웹 서버 워커 프로세스 | 웹 서버 요청 처리, 병렬 계산, 백그라운드 작업 |

핵심적으로 **프로세스는 자원 격리의 단위**, **스레드는 실행 흐름의 단위**라고 정리할 수 있다.

## 내부 동작 원리

### 1. 프로세스의 구성

운영체제는 프로세스를 관리하기 위해 프로세스 제어 블록, 즉 **PCB(Process Control Block)**에 해당하는 자료구조를 사용한다. Linux에서는 프로세스와 스레드를 모두 태스크(task)라는 관점에서 관리하며, 내부적으로 `task_struct`라는 커널 자료구조가 중요한 역할을 한다.

프로세스는 일반적으로 다음 정보를 가진다.

```text
프로세스
├── 코드 영역       : 실행할 명령어
├── 데이터 영역     : 전역 변수, 정적 변수
├── 힙 영역         : 동적 메모리 할당 영역
├── 스택 영역       : 함수 호출, 지역 변수
├── 파일 디스크립터 : 열린 파일, 소켓 등
├── 레지스터 상태   : CPU 실행 상태
└── 주소 공간 정보  : 가상 메모리 매핑 정보
```

각 프로세스는 독립적인 가상 주소 공간을 가지므로, 한 프로세스가 사용하는 주소 `0x1000`과 다른 프로세스가 사용하는 주소 `0x1000`은 실제 물리 메모리에서 서로 다른 위치일 수 있다. 이를 통해 운영체제는 프로세스 간 메모리 보호를 제공한다.

---

### 2. 스레드의 구성

하나의 프로세스 내부에서 여러 스레드는 많은 자원을 공유한다.

```text
하나의 프로세스
├── 공유 영역
│   ├── 코드
│   ├── 데이터
│   ├── 힙
│   ├── 열린 파일
│   └── 주소 공간
│
├── 스레드 1
│   ├── 스택
│   ├── 레지스터
│   └── 프로그램 카운터
│
├── 스레드 2
│   ├── 스택
│   ├── 레지스터
│   └── 프로그램 카운터
│
└── 스레드 3
    ├── 스택
    ├── 레지스터
    └── 프로그램 카운터
```

이 구조 덕분에 스레드는 같은 데이터를 쉽게 공유할 수 있다. 하지만 동시에 여러 스레드가 같은 변수나 자료구조를 수정하면 **경쟁 상태(Race Condition)**가 발생할 수 있다. 따라서 mutex, semaphore, condition variable, read-write lock, atomic operation 같은 동기화 기법이 필요하다.

### 3. Context Switching

**Context Switching**은 CPU가 현재 실행 중인 프로세스나 스레드의 실행 상태를 저장하고, 다른 프로세스나 스레드의 실행 상태를 복원하여 실행을 이어가는 과정이다.

운영체제는 시분할 방식으로 여러 작업을 번갈아 실행한다. CPU 코어 하나는 특정 시점에 하나의 실행 흐름만 실행할 수 있으므로, 여러 프로세스나 스레드가 동시에 실행되는 것처럼 보이게 하려면 빠르게 전환해야 한다.

### Context Switching 과정

```text
[실행 중인 Task A]
       |
       | 1. 타이머 인터럽트, I/O 대기, 시스템 콜, 우선순위 변경 등 발생
       v
[커널 모드 진입]
       |
       | 2. Task A의 레지스터, 프로그램 카운터, 스택 포인터 등 저장
       v
[스케줄러 실행]
       |
       | 3. 다음 실행할 Task B 선택
       v
[Task B의 이전 상태 복원]
       |
       | 4. 레지스터, 프로그램 카운터, 메모리 매핑 정보 등 복원
       v
[Task B 실행 재개]
```

### 프로세스 간 Context Switching

프로세스 간 전환에서는 일반적으로 주소 공간이 바뀐다. 따라서 CPU의 메모리 관리 장치(MMU)가 사용하는 페이지 테이블 관련 정보도 변경될 수 있다. 이 과정에서 TLB(Translation Lookaside Buffer)의 효율이 떨어질 수 있다. TLB는 가상 주소를 물리 주소로 빠르게 변환하기 위한 캐시이므로, 주소 공간이 바뀌면 기존 캐시 정보가 덜 유용해질 수 있다.

```text
Process A 주소 공간  --->  Process B 주소 공간
코드/데이터/힙/스택       코드/데이터/힙/스택
페이지 테이블 A           페이지 테이블 B
```

따라서 프로세스 간 Context Switching은 스레드 간 Context Switching보다 상대적으로 비용이 클 수 있다.

---

### 스레드 간 Context Switching

같은 프로세스 내 스레드 간 전환은 주소 공간을 공유하므로, 프로세스 간 전환보다 가벼운 경우가 많다. 주로 스레드별 레지스터, 스택 포인터, 프로그램 카운터 등을 저장하고 복원한다.

```text
Thread A
├── Stack A
├── Register A
└── PC A

전환 후

Thread B
├── Stack B
├── Register B
└── PC B

공유:
├── Code
├── Data
├── Heap
└── File Descriptor
```

다만 스레드 전환도 비용이 없는 것은 아니다. 커널 스케줄링, 캐시 오염, 락 경합, CPU 코어 간 이동에 따른 캐시 지역성 저하 등이 성능에 영향을 줄 수 있다.

### 4. 멀티 프로세스 vs 멀티 스레드

### 멀티 프로세스

멀티 프로세스는 여러 개의 프로세스를 생성해 작업을 나누어 처리하는 방식이다.

```text
Master Process
├── Worker Process 1
├── Worker Process 2
├── Worker Process 3
└── Worker Process 4
```

장점:

- 프로세스 간 메모리 격리가 강하다.
- 하나의 프로세스가 죽어도 다른 프로세스는 계속 동작할 수 있다.
- 보안 경계 설정에 유리하다.
- 멀티코어 CPU를 활용할 수 있다.

단점:

- 프로세스 생성과 전환 비용이 상대적으로 크다.
- 프로세스 간 데이터 공유가 어렵다.
- IPC가 필요하다.
- 메모리 사용량이 커질 수 있다.

대표 IPC 방식:

- pipe
- named pipe
- socket
- shared memory
- message queue
- signal

---

### 멀티 스레드

멀티 스레드는 하나의 프로세스 안에서 여러 스레드를 생성해 작업을 나누어 처리하는 방식이다.

```text
Single Process
├── Thread 1
├── Thread 2
├── Thread 3
└── Thread 4
```

장점:

- 메모리 공유가 쉽다.
- 프로세스보다 생성 및 전환 비용이 낮은 경우가 많다.
- 같은 주소 공간을 사용하므로 데이터 전달이 빠르다.
- I/O 작업과 계산 작업을 병행하기 좋다.

단점:

- 동기화 문제가 발생하기 쉽다.
- 한 스레드의 메모리 오류가 전체 프로세스를 망가뜨릴 수 있다.
- 디버깅이 어렵다.
- 데드락, 라이브락, 기아 상태 같은 동시성 문제가 생길 수 있다.

---

### 선택 기준

| 상황 | 적합한 방식 |
|---|---|
| 장애 격리가 중요 | 멀티 프로세스 |
| 보안 격리가 중요 | 멀티 프로세스 |
| 공유 데이터가 많음 | 멀티 스레드 |
| 메모리 효율이 중요 | 멀티 스레드 |
| CPU 코어를 활용해야 함 | 둘 다 가능 |
| 요청 간 격리가 필요 | 멀티 프로세스 또는 컨테이너 |
| 동기화 복잡도를 줄이고 싶음 | 멀티 프로세스 또는 이벤트 기반 |

## 실제 시스템 연결

## 실제 시스템 연결

### 1. Linux에서의 프로세스와 스레드

Linux는 프로세스와 스레드를 모두 **task**라는 실행 단위로 관리한다. 커널 내부에서는 `task_struct`가 각 실행 단위의 상태를 표현한다. 프로세스 생성에는 `fork()`가 사용될 수 있고, 스레드 생성에는 POSIX thread 라이브러리의 `pthread_create()`가 흔히 사용된다.

Linux에서 `fork()`는 부모 프로세스의 주소 공간을 자식 프로세스에 복사한 것처럼 보이게 한다. 실제로는 성능을 위해 **Copy-on-Write(COW)** 기법을 사용한다. 부모와 자식이 같은 물리 페이지를 공유하다가, 어느 한쪽이 해당 페이지에 쓰기 작업을 하면 그때 복사한다.

```text
fork() 직후
Parent Process ─┐
                 ├── 같은 물리 페이지 공유
Child Process  ─┘

쓰기 발생 후
Parent Process ── Page A
Child Process  ── Page A'
```

스레드는 `clone()` 시스템 콜 계열을 통해 구현될 수 있으며, 어떤 자원을 공유할지 플래그로 지정할 수 있다. 예를 들어 주소 공간, 파일 디스크립터, 시그널 처리 정보 등을 공유할 수 있다.

---

### 2. Linux 스케줄러와 Context Switching

Linux 커널은 실행 가능한 태스크 중 하나를 선택해 CPU에 할당한다. 일반적인 사용자 프로세스는 완전 공정 스케줄러(CFS, Completely Fair Scheduler)의 대상이 된다. 스케줄러는 태스크의 실행 시간, 우선순위, CPU 사용량 등을 고려해 다음 실행 대상을 선택한다.

Context Switching은 다음 상황에서 발생할 수 있다.

- 타임 슬라이스 또는 스케줄링 조건 충족
- I/O 대기로 인한 sleep 상태 전환
- 더 높은 우선순위 작업 등장
- 명시적 yield
- 시스템 콜 또는 인터럽트 이후 스케줄링 필요

실제 시스템에서 Context Switching이 과도하게 많으면 CPU가 유용한 애플리케이션 작업보다 전환 작업에 시간을 많이 쓰게 된다. Linux에서는 다음 도구로 관련 정보를 확인할 수 있다.

```bash
top
htop
vmstat
pidstat
perf
```

예를 들어 `vmstat`의 `cs` 항목은 초당 context switch 수를 나타낸다.

### 3. Nginx

Nginx는 일반적으로 **master process + worker process** 구조를 사용한다.

```text
nginx master process
├── nginx worker process
├── nginx worker process
├── nginx worker process
└── nginx worker process
```

Master process는 설정 로드, worker 관리, 시그널 처리 등을 담당하고, worker process가 실제 클라이언트 요청을 처리한다. Nginx worker는 이벤트 기반 비동기 I/O 모델을 사용하여 많은 연결을 비교적 적은 수의 worker로 처리할 수 있다.

이 구조는 멀티 프로세스의 장점을 활용한다.

- worker 간 장애 격리
- 멀티코어 활용
- 설정 reload 시 안정적 교체 가능
- 이벤트 기반 처리로 스레드 폭증 방지

---

### 4. 웹 브라우저

현대 웹 브라우저는 탭, 렌더러, GPU, 네트워크 등을 여러 프로세스로 분리하는 구조를 사용한다. 이를 통해 특정 탭이나 렌더링 작업에서 문제가 발생해도 전체 브라우저가 중단되는 위험을 줄일 수 있다. 또한 사이트 격리와 샌드박싱 같은 보안 기능과도 연결된다.

---

### 5. JVM과 스레드

Java 애플리케이션은 일반적으로 JVM 프로세스 안에서 여러 Java 스레드를 실행한다. 서버 애플리케이션에서는 요청 처리, GC 작업, 비동기 작업, 스케줄링 작업 등이 여러 스레드로 동작한다.

예를 들어 Spring 기반 웹 서버는 내부적으로 스레드 풀을 사용해 요청을 처리할 수 있다. 이때 스레드 수가 너무 많으면 context switching과 메모리 사용량이 증가하고, 너무 적으면 요청 대기 시간이 길어질 수 있다.

## 클라우드 연결

## 클라우드 연결

### 1. Docker와 프로세스

Docker 컨테이너는 독립적인 가상 머신이 아니라, 호스트 OS 커널을 공유하면서 격리된 프로세스 집합으로 실행된다. 컨테이너 내부의 PID 1 프로세스가 종료되면 일반적으로 해당 컨테이너도 종료된다.

```text
Host Linux Kernel
├── Container A
│   └── PID namespace 안의 Process
├── Container B
│   └── PID namespace 안의 Process
└── Container C
    └── PID namespace 안의 Process
```

Docker는 Linux namespace와 cgroup을 활용한다.

- PID namespace: 프로세스 ID 공간 격리
- mount namespace: 파일 시스템 마운트 격리
- network namespace: 네트워크 인터페이스 격리
- user namespace: 사용자 및 권한 격리
- cgroup: CPU, 메모리, I/O 등 자원 제한 및 회계

컨테이너는 결국 프로세스이므로, 컨테이너 안의 애플리케이션도 프로세스와 스레드 구조를 그대로 가진다.

---

### 2. Kubernetes와 프로세스 관리

Kubernetes는 컨테이너를 Pod 단위로 배치하고 관리한다. Pod 안에는 하나 이상의 컨테이너가 포함될 수 있으며, 같은 Pod 안의 컨테이너들은 네트워크 namespace를 공유한다.

```text
Kubernetes Node
├── Pod A
│   ├── Container 1
│   │   └── App Process / Threads
│   └── Container 2
│       └── Sidecar Process
└── Pod B
    └── Container
        └── App Process / Threads
```

프로세스와 스레드 개념은 Kubernetes 운영에서 중요하다.

- CPU request/limit 설정은 프로세스와 스레드의 CPU 사용에 영향
- 메모리 limit 초과 시 컨테이너가 종료될 수 있음
- 애플리케이션 스레드 수가 과도하면 CPU throttling, 메모리 증가, latency 증가 가능
- readiness probe, liveness probe는 프로세스 상태와 서비스 가능 여부 확인에 사용

---

### 3. AWS ECS / EKS

AWS ECS와 EKS에서 컨테이너는 내부적으로 프로세스 기반으로 실행된다. ECS Task나 Kubernetes Pod 안의 애플리케이션은 여전히 운영체제의 프로세스와 스레드 모델 위에서 동작한다.

운영 관점에서 중요한 지표:

- CPU 사용률
- 메모리 사용률
- 스레드 수
- 프로세스 수
- context switch 수
- run queue 길이
- I/O wait

AWS CloudWatch Container Insights 같은 모니터링 도구를 사용하면 컨테이너와 노드 수준의 자원 사용을 관찰할 수 있다.

---

### 4. 서버리스와 실행 모델

AWS Lambda 같은 서버리스 환경에서는 개발자가 프로세스 생성이나 스레드 관리 자체를 직접 다루지 않는 경우가 많다. 하지만 런타임 내부에서는 여전히 프로세스와 스레드가 존재한다.

예를 들어 함수 코드가 외부 API를 많이 호출한다면 비동기 I/O나 스레드 풀 사용 방식이 성능에 영향을 줄 수 있다. 또한 함수 인스턴스의 메모리 설정은 CPU 성능과도 연관될 수 있으므로, 스레드 수나 병렬 처리 수준을 무작정 늘리는 것은 적절하지 않을 수 있다.

⚠️ 확인 필요: 특정 클라우드 서비스에서 메모리 크기와 CPU 할당량의 정확한 비율은 서비스 종류와 시점에 따라 달라질 수 있으므로 공식 문서를 확인해야 한다.

## 보안 연결

## 보안 연결

### 1. 프로세스 격리와 보안

프로세스는 서로 다른 가상 주소 공간을 가지므로, 한 프로세스가 다른 프로세스의 메모리에 직접 접근하지 못하도록 운영체제가 보호한다. 이 특성은 보안의 기본 전제 중 하나이다.

예를 들어 웹 브라우저가 탭이나 사이트를 별도 프로세스로 분리하면, 한 사이트에서 발생한 취약점이 다른 사이트의 메모리에 접근하는 것을 어렵게 만들 수 있다. 컨테이너나 샌드박스도 프로세스 격리, namespace, 권한 제한, syscall 제한 등을 조합해 보안 경계를 만든다.

하지만 프로세스 격리는 완전한 보안 보장이 아니다. 커널 취약점, 잘못된 권한 설정, 공유 볼륨 오남용, 민감 정보 노출 등으로 격리가 깨질 수 있다.

---

### 2. 멀티 스레드와 Race Condition

멀티 스레드 프로그램에서는 여러 스레드가 같은 메모리나 파일, 데이터베이스 레코드에 동시에 접근할 수 있다. 이때 적절한 동기화가 없으면 race condition이 발생한다.

예시:

```text
Thread A: balance 읽기 -> 100
Thread B: balance 읽기 -> 100
Thread A: balance + 10 저장 -> 110
Thread B: balance - 20 저장 -> 80
```

의도한 결과는 `90`일 수 있지만 실제 결과는 `80`이 된다. 금융, 인증, 권한 검증 로직에서 이런 문제가 발생하면 보안 취약점으로 이어질 수 있다.

대표적인 보안 문제:

- 중복 결제
- 쿠폰 중복 사용
- 재고 초과 판매
- 권한 검증 우회
- 파일 생성/삭제 시점 경쟁
- TOCTOU(Time-of-Check to Time-of-Use) 취약점

---

### 3. Deadlock과 서비스 거부

스레드 동기화가 잘못되면 deadlock이 발생할 수 있다.

```text
Thread A: Lock 1 획득 → Lock 2 대기
Thread B: Lock 2 획득 → Lock 1 대기
```

이 경우 두 스레드는 영원히 대기할 수 있고, 요청 처리가 멈추며 서비스 거부 상태로 이어질 수 있다. 공격자가 의도적으로 특정 요청 패턴을 유발해 락 경합이나 deadlock 가능성을 높일 수도 있다.

모범 사례:

- 락 획득 순서를 고정한다.
- 락 범위를 최소화한다.
- timeout이 있는 락을 사용한다.
- 공유 상태를 줄인다.
- 불변 객체나 메시지 큐 기반 구조를 고려한다.
- 스레드 덤프와 모니터링을 통해 대기 상태를 관찰한다.

---

### 4. Context Switching과 DoS

Context Switching이 과도하게 많아지면 CPU 자원이 실제 업무 처리보다 스케줄링과 전환에 낭비될 수 있다. 공격자가 대량의 연결, 짧은 요청, 스레드 생성 폭증을 유발하면 서버는 성능 저하나 서비스 거부 상태에 빠질 수 있다.

방어 방법:

- 스레드 풀 크기 제한
- 연결 수 제한
- 요청 rate limiting
- backpressure 적용
- timeout 설정
- 이벤트 기반 I/O 사용
- 커널 및 런타임 모니터링

---

### 5. 컨테이너 보안

컨테이너는 프로세스 격리를 사용하지만 호스트 커널을 공유한다. 따라서 컨테이너 내부 프로세스가 과도한 권한을 가지면 위험하다.

모범 사례:

- root 사용자로 실행하지 않기
- 불필요한 Linux capability 제거
- read-only root filesystem 고려
- seccomp, AppArmor, SELinux 적용
- 컨테이너 이미지 최소화
- 민감 정보는 환경 변수나 파일에 평문으로 장기간 노출하지 않도록 관리
- PID namespace 공유 여부 신중히 설정
- hostPID, hostNetwork 사용 제한

## 면접 질문

**Q1. 프로세스와 스레드의 가장 큰 차이는 무엇인가요?**  
> 핵심 답변: 프로세스는 운영체제로부터 독립적인 주소 공간과 자원을 할당받는 실행 단위이고, 스레드는 프로세스 내부의 실행 흐름이다. 프로세스 간 메모리는 기본적으로 분리되어 있고, 같은 프로세스의 스레드들은 코드, 데이터, 힙, 파일 디스크립터 등을 공유한다. 따라서 프로세스는 격리성이 좋고, 스레드는 공유와 통신이 쉽다.

**Q2. Context Switching이란 무엇이며 왜 비용이 발생하나요?**  
> 핵심 답변: Context Switching은 CPU가 현재 실행 중인 프로세스나 스레드의 상태를 저장하고 다른 실행 단위의 상태를 복원하는 과정이다. 레지스터, 프로그램 카운터, 스택 포인터 등을 저장/복원해야 하며, 프로세스 전환의 경우 주소 공간 변경과 TLB 효율 저하가 발생할 수 있다. 또한 캐시 지역성 저하와 스케줄러 실행 비용도 성능에 영향을 준다.

**Q3. 멀티 프로세스가 멀티 스레드보다 유리한 상황은 언제인가요?**  
> 핵심 답변: 장애 격리와 보안 격리가 중요한 경우 멀티 프로세스가 유리하다. 한 프로세스가 비정상 종료되어도 다른 프로세스에 미치는 영향이 상대적으로 작고, 주소 공간이 분리되어 있어 메모리 침범 위험도 줄어든다. 웹 브라우저의 탭 분리나 Nginx의 worker process 구조가 대표적 예시다.

**Q4. 멀티 스레드 프로그래밍에서 주의해야 할 문제는 무엇인가요?**  
> 핵심 답변: 여러 스레드가 공유 자원에 동시에 접근할 때 race condition이 발생할 수 있다. 이를 막기 위해 mutex, semaphore, atomic operation, condition variable 같은 동기화 기법이 필요하다. 하지만 동기화가 과도하거나 잘못되면 deadlock, livelock, starvation, 성능 저하가 발생할 수 있다.

**Q5. 프로세스 간 통신과 스레드 간 통신은 어떻게 다른가요?**  
> 핵심 답변: 스레드는 같은 프로세스의 메모리를 공유하므로 변수나 자료구조를 통해 쉽게 데이터를 주고받을 수 있다. 반면 프로세스는 주소 공간이 분리되어 있으므로 pipe, socket, shared memory, message queue, signal 같은 IPC 기법이 필요하다. IPC는 격리성을 유지하는 대신 설계와 비용이 더 복잡할 수 있다.
