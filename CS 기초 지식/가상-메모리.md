# 가상 메모리 - 요구 페이징, 페이지 교체 알고리즘(FIFO, LRU, LFU), Thrashing

## 핵심 개념

가상 메모리는 프로세스가 실제 물리 메모리보다 크거나 독립적인 연속 주소 공간을 가진 것처럼 실행되도록 만드는 운영체제 메모리 관리 기법이다. 프로세스는 직접 물리 주소를 다루지 않고, CPU가 생성한 가상 주소를 MMU와 페이지 테이블을 통해 물리 주소로 변환한다. 이를 통해 프로세스 간 메모리 격리, 메모리 보호, 효율적인 메모리 사용, 큰 프로그램 실행, 파일 매핑, 공유 라이브러리 사용 등이 가능해진다.

요구 페이징은 가상 메모리의 핵심 기법 중 하나로, 프로세스의 모든 페이지를 처음부터 물리 메모리에 올리지 않고 실제로 접근되는 시점에 필요한 페이지만 적재한다. 접근한 페이지가 메모리에 없으면 페이지 폴트가 발생하고, 운영체제는 디스크나 파일 시스템, 스왑 영역 등에서 해당 페이지를 가져와 물리 프레임에 적재한다. 이 방식은 초기 로딩 시간을 줄이고 메모리 사용량을 절약하지만, 페이지 폴트가 너무 자주 발생하면 성능이 크게 저하된다.

페이지 교체 알고리즘은 물리 메모리가 부족할 때 어떤 페이지를 내보낼지 결정하는 정책이다. 대표적으로 FIFO, LRU, LFU가 있다. FIFO는 가장 오래 전에 들어온 페이지를 교체하고, LRU는 가장 오래 사용되지 않은 페이지를 교체하며, LFU는 사용 빈도가 가장 낮은 페이지를 교체한다. 이상적인 목표는 미래에 사용되지 않을 페이지를 제거하는 것이지만, 운영체제는 미래를 알 수 없기 때문에 과거 접근 패턴을 기반으로 근사한다.

Thrashing은 프로세스들이 실제 계산보다 페이지 교체와 페이지 폴트 처리에 대부분의 시간을 소비하는 상태를 말한다. 주로 실행 중인 프로세스들의 작업 집합이 물리 메모리에 비해 너무 클 때 발생한다. Thrashing이 발생하면 CPU 사용률이 낮아지거나 I/O 대기가 증가하고, 시스템 전체 응답성이 급격히 나빠진다. 따라서 가상 메모리, 요구 페이징, 페이지 교체 정책, Thrashing 제어는 운영체제 성능과 안정성을 이해하는 데 매우 중요한 개념이다.

## 내부 동작 원리

## 1. 가상 주소 변환 과정

프로세스가 메모리에 접근할 때 CPU는 가상 주소를 생성한다. 이 주소는 일반적으로 페이지 번호와 페이지 내부 오프셋으로 나뉜다.

```text
가상 주소
+------------------+----------------+
| Virtual Page No. | Page Offset    |
+------------------+----------------+
        |                 |
        v                 v
   페이지 테이블 조회     페이지 내부 위치
        |
        v
+------------------+----------------+
| Physical Frame   | Page Offset    |
+------------------+----------------+
물리 주소
```

동작 흐름은 다음과 같다.

1. CPU가 가상 주소를 생성한다.
2. MMU가 TLB를 먼저 조회한다.
3. TLB에 변환 정보가 있으면 즉시 물리 주소로 변환한다.
4. TLB에 없으면 페이지 테이블을 조회한다.
5. 페이지 테이블 엔트리에 해당 페이지가 물리 메모리에 존재한다고 표시되어 있으면 물리 프레임 번호를 얻는다.
6. 존재하지 않으면 페이지 폴트가 발생한다.
7. 운영체제 커널이 개입하여 해당 페이지를 메모리에 적재하거나, 잘못된 접근이면 프로세스를 종료한다.

## 2. 요구 페이징 동작 과정

요구 페이징에서는 프로세스 실행 시 전체 코드와 데이터를 모두 물리 메모리에 올리지 않는다. 대신 페이지 테이블에는 각 페이지가 현재 메모리에 있는지 여부를 나타내는 비트가 존재한다. 보통 이를 valid bit, present bit 등으로 설명한다.

```text
프로세스 실행
   |
   v
특정 가상 페이지 접근
   |
   v
페이지 테이블 확인
   |
   +-- present = 1 --> 물리 메모리 접근
   |
   +-- present = 0 --> 페이지 폴트 발생
                         |
                         v
                  OS 페이지 폴트 핸들러 실행
                         |
                         v
              빈 프레임 존재 여부 확인
                 |                     |
                 v                     v
              빈 프레임 사용       교체 대상 페이지 선택
                                       |
                                       v
                              필요 시 디스크에 기록
                                       |
                                       v
                           새 페이지를 메모리에 적재
                         |
                         v
                    페이지 테이블 갱신
                         |
                         v
                   중단된 명령어 재실행
```

페이지 폴트는 항상 나쁜 것은 아니다. 예를 들어 처음 실행되는 코드 페이지나 지연 로딩된 데이터 페이지에 접근할 때 발생하는 페이지 폴트는 요구 페이징의 정상적인 동작이다. 하지만 페이지 폴트가 지나치게 빈번하면 디스크 I/O 또는 스토리지 접근이 증가하여 성능이 크게 저하된다.

## 3. 페이지 교체 알고리즘

### FIFO, First-In First-Out

FIFO는 메모리에 가장 먼저 들어온 페이지를 가장 먼저 내보내는 방식이다. 구현이 단순하고 큐 자료구조로 관리할 수 있다.

```text
메모리 적재 순서 큐

Front                               Rear
[ P1 ] -> [ P2 ] -> [ P3 ] -> [ P4 ]

새 페이지 P5 필요, 빈 프레임 없음
교체 대상: P1
```

장점은 단순함이다. 단점은 오래 전에 적재되었지만 자주 사용하는 페이지도 제거될 수 있다는 점이다. 또한 FIFO는 페이지 프레임 수를 늘렸는데도 페이지 폴트가 증가할 수 있는 Belady's anomaly가 발생할 수 있다.

### LRU, Least Recently Used

LRU는 가장 오랫동안 사용되지 않은 페이지를 교체한다. 최근에 사용한 페이지는 가까운 미래에도 다시 사용될 가능성이 높다는 locality 원리에 기반한다.

```text
최근 사용 순서

가장 오래됨                         가장 최근
[ P2 ] -> [ P4 ] -> [ P1 ] -> [ P3 ]

새 페이지 P5 필요
교체 대상: P2
```

LRU는 FIFO보다 일반적으로 더 좋은 성능을 보일 수 있지만, 정확한 LRU 구현은 모든 메모리 접근마다 사용 시간을 갱신해야 하므로 비용이 크다. 실제 운영체제는 하드웨어의 accessed bit, referenced bit 또는 근사 알고리즘을 이용해 LRU와 비슷한 효과를 낸다.

### LFU, Least Frequently Used

LFU는 사용 횟수가 가장 적은 페이지를 교체한다.

```text
페이지별 사용 횟수

P1: 10회
P2: 1회
P3: 3회
P4: 1회

교체 후보: P2 또는 P4
```

LFU는 장기적으로 거의 사용되지 않는 페이지를 제거하는 데 유리할 수 있다. 하지만 과거에 많이 사용되었지만 현재는 사용되지 않는 페이지가 계속 남는 문제가 있다. 이를 보완하기 위해 사용 횟수에 aging을 적용하는 방식이 사용될 수 있다.

## 4. Thrashing 발생 원리

Thrashing은 프로세스들의 working set, 즉 일정 시간 동안 실제로 자주 접근하는 페이지 집합이 물리 메모리보다 커질 때 발생한다.

```text
물리 메모리 용량
+--------------------------------+
| P1 일부 | P2 일부 | P3 일부     |
+--------------------------------+

각 프로세스의 Working Set
P1: [A B C D E]
P2: [F G H I]
P3: [J K L M N]

총 필요한 페이지 수 > 실제 프레임 수
```

이 경우 한 프로세스가 필요한 페이지를 가져오면 다른 프로세스의 페이지가 쫓겨나고, 다시 그 프로세스가 실행될 때 페이지 폴트가 발생한다. 시스템은 계산보다 페이지를 읽고 쓰는 데 대부분의 시간을 쓰게 된다.

Thrashing의 전형적인 징후는 다음과 같다.

- 페이지 폴트율 급증
- 디스크 또는 스토리지 I/O 대기 증가
- CPU가 실제 작업을 충분히 수행하지 못함
- 시스템 응답성 저하
- 스왑 사용량 증가
- 컨테이너나 프로세스의 OOM 발생 가능성 증가

Thrashing 완화 방법은 다음과 같다.

- 동시에 실행되는 프로세스 수 줄이기
- 물리 메모리 증설
- 메모리 누수 제거
- 프로세스별 메모리 제한 조정
- 스왑 사용 정책 조정
- Working Set 기반 메모리 관리
- Page Fault Frequency 기반 제어

## 실제 시스템 연결

## Linux에서의 가상 메모리

Linux는 프로세스마다 독립적인 가상 주소 공간을 제공한다. 각 프로세스는 자신만의 주소 공간을 가진 것처럼 동작하지만, 실제로는 페이지 테이블을 통해 물리 메모리의 프레임에 매핑된다. 동일한 실행 파일의 코드 영역이나 공유 라이브러리 영역은 여러 프로세스가 공유할 수 있으며, 쓰기가 발생하면 Copy-on-Write 방식으로 별도 페이지가 만들어질 수 있다.

Linux에서 요구 페이징은 일반적인 실행 파일 로딩, 공유 라이브러리 로딩, mmap, 파일 매핑, 익명 메모리 할당 등에 폭넓게 사용된다. 예를 들어 프로세스가 `malloc()`으로 큰 메모리를 요청하더라도, 실제 물리 페이지는 해당 메모리에 접근하는 시점에 할당될 수 있다. 이는 overcommit 정책과도 관련이 있다.

⚠️ 확인 필요: Linux의 세부 페이지 교체 구현은 커널 버전과 설정에 따라 달라질 수 있다. 일반적으로 Linux는 전통적인 순수 FIFO, 순수 LRU를 그대로 구현하기보다는 active/inactive list, referenced bit, reclaim 정책 등을 활용해 LRU에 가까운 근사 방식을 사용한다고 설명할 수 있다.

## Linux에서 관찰할 수 있는 지표

가상 메모리와 Thrashing을 분석할 때 자주 보는 도구는 다음과 같다.

```bash
free -h
vmstat 1
top
htop
sar
ps
cat /proc/meminfo
```

예를 들어 `vmstat`의 `si`, `so`는 swap in, swap out을 의미한다. 이 값이 지속적으로 높고 시스템 응답성이 낮다면 메모리 부족이나 Thrashing을 의심할 수 있다. `top`이나 `htop`에서는 프로세스별 메모리 사용량, 스왑 사용 여부, CPU 대기 상태 등을 확인할 수 있다.

## Nginx와 가상 메모리

Nginx 같은 서버 프로세스도 운영체제의 가상 메모리 위에서 실행된다. Nginx는 다수의 워커 프로세스를 사용하며, 각 워커는 독립적인 가상 주소 공간을 가진다. 정적 파일을 제공할 때는 커널의 페이지 캐시가 성능에 큰 영향을 준다. 자주 접근되는 파일이 페이지 캐시에 있으면 디스크 접근 없이 메모리에서 빠르게 응답할 수 있다.

다만 페이지 캐시는 가상 메모리의 페이지 관리와 밀접하게 연결되어 있으므로, 시스템 메모리가 부족하면 애플리케이션 메모리와 페이지 캐시 사이에서 경쟁이 발생할 수 있다. 메모리 압박이 심해지면 페이지 캐시가 줄어들거나, 익명 페이지가 스왑으로 밀려나면서 응답 시간이 증가할 수 있다.

## 데이터베이스와 Thrashing

데이터베이스 서버에서는 Thrashing이 특히 치명적이다. 예를 들어 DB 버퍼 풀, OS 페이지 캐시, 애플리케이션 메모리 사용량의 합이 물리 메모리를 초과하면 스왑이 발생할 수 있다. DB는 자체 캐시를 가지고 있기 때문에 OS 페이지 캐시와 중복될 수 있으며, 잘못된 메모리 설정은 성능 저하로 이어질 수 있다.

실무에서는 DB 버퍼 풀 크기, 커넥션 수, 쿼리 메모리 사용량, OS 페이지 캐시, 컨테이너 메모리 제한을 함께 고려해야 한다.

## 클라우드 연결

## Docker와 가상 메모리

Docker 컨테이너는 독립적인 커널을 갖는 것이 아니라 호스트 Linux 커널 위에서 실행된다. 따라서 컨테이너 내부의 프로세스도 호스트 커널의 가상 메모리 관리 대상이다. 컨테이너마다 cgroups를 통해 메모리 사용량을 제한할 수 있다.

예를 들어 Docker에서 다음과 같이 메모리 제한을 줄 수 있다.

```bash
docker run --memory=512m my-app
```

이 제한을 초과하면 컨테이너 내부 프로세스가 OOM Killer에 의해 종료될 수 있다. 컨테이너 환경에서는 호스트 전체 메모리가 충분해 보여도, 해당 컨테이너의 cgroup 제한 때문에 OOM이 발생할 수 있다.

## Kubernetes와 메모리 관리

Kubernetes에서는 Pod나 Container에 `resources.requests.memory`와 `resources.limits.memory`를 설정할 수 있다.

```yaml
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"
```

- `requests.memory`: 스케줄링 시 필요한 최소 메모리 기준
- `limits.memory`: 컨테이너가 사용할 수 있는 최대 메모리 제한

컨테이너가 메모리 limit을 초과하면 OOMKilled 상태가 될 수 있다. 이때 애플리케이션 로그에는 명확한 예외가 남지 않을 수도 있으므로, Kubernetes 이벤트와 컨테이너 종료 사유를 함께 확인해야 한다.

Thrashing 관점에서 Kubernetes는 다음 문제가 자주 발생할 수 있다.

- Pod 메모리 limit이 너무 낮음
- JVM heap, Node.js heap, DB buffer 설정이 컨테이너 limit보다 큼
- 노드에 과도한 Pod 배치
- 메모리 request를 낮게 잡아 실제 사용량과 괴리가 큼
- 스왑 정책이 클러스터 설정과 맞지 않음

⚠️ 확인 필요: Kubernetes의 swap 지원과 기본 동작은 버전, 노드 OS, kubelet 설정에 따라 달라질 수 있으므로 실제 운영 환경의 설정을 확인해야 한다.

## AWS EC2와 가상 메모리

AWS EC2 인스턴스도 일반 서버와 마찬가지로 운영체제의 가상 메모리 기능을 사용한다. 인스턴스 타입에 따라 물리 메모리 용량이 다르며, 메모리 사용량이 높은 워크로드에서는 인스턴스 크기 선택이 중요하다.

스왑은 EC2에서 사용할 수 있지만, AMI와 운영체제 설정에 따라 기본 구성 여부가 다를 수 있다. 스왑을 EBS 볼륨에 구성하면 메모리 부족 상황에서 프로세스가 즉시 종료되는 것을 완화할 수 있지만, EBS는 RAM보다 훨씬 느리므로 스왑 의존적인 상태는 성능 문제로 이어진다.

⚠️ 확인 필요: 특정 AMI에서 스왑이 기본 활성화되어 있는지 여부는 AMI 종류와 버전에 따라 다르므로 배포 전 직접 확인해야 한다.

## AWS ECS/EKS와 OOM

AWS ECS와 EKS에서도 컨테이너 메모리 제한은 매우 중요하다. 애플리케이션이 제한을 초과하면 컨테이너가 종료될 수 있으며, 서비스가 재시작 루프에 빠질 수 있다. 특히 Java 애플리케이션에서는 JVM heap 크기뿐만 아니라 metaspace, thread stack, direct buffer, native memory도 함께 고려해야 한다.

## 클라우드 모니터링 포인트

클라우드 환경에서는 다음 지표를 함께 보는 것이 좋다.

- 메모리 사용률
- 스왑 사용량
- 페이지 폴트율
- 디스크 I/O 대기
- 컨테이너 OOMKilled 횟수
- 노드별 메모리 pressure
- 애플리케이션 응답 시간
- 재시작 횟수

## 보안 연결

## 1. 가상 메모리와 프로세스 격리

가상 메모리는 보안의 핵심 기반이다. 각 프로세스가 독립적인 가상 주소 공간을 사용하므로, 정상적인 상황에서는 한 프로세스가 다른 프로세스의 메모리를 직접 읽거나 쓸 수 없다. 페이지 테이블에는 읽기, 쓰기, 실행 권한 같은 보호 정보가 포함될 수 있으며, 이를 통해 잘못된 접근은 페이지 폴트나 보호 예외로 처리된다.

예를 들어 읽기 전용 코드 영역에 쓰기를 시도하거나, 사용자 모드 프로세스가 커널 메모리에 직접 접근하려 하면 운영체제는 이를 차단한다.

## 2. NX bit와 실행 방지

현대 시스템은 메모리 페이지에 실행 권한을 별도로 설정할 수 있다. 이를 통해 스택이나 힙에 주입된 데이터를 코드처럼 실행하는 공격을 어렵게 만든다. 일반적으로 NX bit 또는 DEP 같은 이름으로 알려져 있다.

```text
페이지 권한 예시

코드 영역: Read + Execute
데이터 영역: Read + Write
스택 영역: Read + Write
커널 영역: 사용자 모드 접근 금지
```

모범 사례는 다음과 같다.

- 쓰기 가능한 페이지와 실행 가능한 페이지를 분리한다.
- W^X 정책, 즉 writable과 executable을 동시에 허용하지 않는 정책을 적용한다.
- 컴파일러와 운영체제의 보안 옵션을 활성화한다.

## 3. ASLR과 가상 주소 공간

ASLR, Address Space Layout Randomization은 프로세스의 스택, 힙, 라이브러리, 실행 파일 매핑 위치 등을 무작위화하여 공격자가 정확한 주소를 예측하기 어렵게 만든다. 이는 버퍼 오버플로우, ROP 공격 등의 난도를 높인다.

ASLR은 가상 메모리 구조를 활용하는 대표적인 보안 기법이다. 단, 정보 유출 취약점으로 주소가 노출되면 효과가 약해질 수 있다.

## 4. Page Fault와 Side Channel

페이지 폴트와 캐시, TLB, 메모리 접근 시간은 사이드 채널 공격과 관련될 수 있다. 공격자는 직접 데이터를 읽지 못하더라도 접근 시간 차이나 페이지 폴트 발생 패턴을 통해 민감한 정보를 추론하려고 할 수 있다.

예를 들어 메모리 접근 패턴이 비밀 값에 따라 달라지는 암호 알고리즘은 타이밍 공격에 취약할 수 있다. 따라서 암호 구현에서는 constant-time 기법이 중요하다.

## 5. Swap과 민감정보 유출

메모리의 일부가 스왑 영역으로 내려가면, 프로세스 메모리에 있던 민감한 정보가 디스크에 기록될 수 있다. 예를 들어 비밀번호, 토큰, 개인키, 세션 정보 등이 스왑에 남을 가능성이 있다.

모범 사례는 다음과 같다.

- 민감 정보를 가능한 짧은 시간만 메모리에 보관한다.
- 사용 후 메모리를 명시적으로 지운다.
- 스왑 암호화를 고려한다.
- 민감한 키 자료는 OS 또는 런타임의 보안 메모리 기능을 사용한다.
- 필요 시 특정 메모리가 스왑되지 않도록 잠그는 기능을 검토한다.

⚠️ 확인 필요: 메모리 잠금 기능의 사용 가능 여부와 제한은 운영체제, 권한, 컨테이너 설정에 따라 다르므로 실제 환경에서 확인해야 한다.

## 6. Rowhammer와 하드웨어 메모리 공격

Rowhammer는 DRAM의 물리적 특성을 악용하여 인접 메모리 셀의 비트를 뒤집을 수 있는 공격 유형으로 알려져 있다. 가상 메모리 자체의 결함이라기보다는 하드웨어 메모리와 메모리 관리 구조가 함께 관련되는 보안 이슈다. ECC 메모리, 하드웨어 완화, 커널 패치 등이 방어에 도움이 될 수 있다.

## 면접 질문

**Q1. 가상 메모리가 필요한 이유는 무엇인가요?**  
> 핵심 답변: 프로세스마다 독립적인 주소 공간을 제공하여 메모리 보호와 격리를 가능하게 한다. 실제 물리 메모리보다 큰 주소 공간을 제공할 수 있고, 요구 페이징을 통해 필요한 페이지만 메모리에 올려 효율성을 높인다. 공유 라이브러리, mmap, Copy-on-Write 같은 기능의 기반이 된다.

**Q2. 요구 페이징에서 페이지 폴트가 발생하면 어떤 일이 일어나나요?**  
> 핵심 답변: CPU가 접근한 페이지가 물리 메모리에 없으면 페이지 폴트가 발생한다. 운영체제의 페이지 폴트 핸들러가 실행되고, 접근이 유효한지 확인한다. 유효하면 빈 프레임을 찾거나 페이지 교체 알고리즘으로 희생 페이지를 선택한다. 필요한 페이지를 디스크, 파일, 스왑 등에서 읽어 메모리에 적재하고 페이지 테이블을 갱신한 뒤 중단된 명령을 재실행한다.

**Q3. FIFO, LRU, LFU 페이지 교체 알고리즘의 차이는 무엇인가요?**  
> 핵심 답변: FIFO는 가장 먼저 메모리에 들어온 페이지를 교체한다. 구현은 쉽지만 자주 쓰는 페이지도 제거할 수 있고 Belady's anomaly가 발생할 수 있다. LRU는 가장 오래 사용되지 않은 페이지를 교체하며 locality 원리에 기반한다. 성능은 좋을 수 있지만 정확한 구현 비용이 크다. LFU는 사용 횟수가 가장 적은 페이지를 교체하지만 오래전에 많이 사용된 페이지가 계속 남는 문제가 있어 aging이 필요할 수 있다.

**Q4. Thrashing이란 무엇이며 어떻게 해결할 수 있나요?**  
> 핵심 답변: Thrashing은 시스템이 실제 연산보다 페이지 폴트 처리와 페이지 교체에 대부분의 시간을 쓰는 상태다. 프로세스들의 working set이 물리 메모리보다 클 때 주로 발생한다. 해결 방법으로는 물리 메모리 증설, 동시 실행 프로세스 수 감소, 메모리 누수 수정, working set 관리, 스왑 정책 조정, 컨테이너 메모리 limit 조정 등이 있다.

**Q5. 컨테이너 환경에서 메모리 부족 문제를 분석할 때 무엇을 확인해야 하나요?**  
> 핵심 답변: 호스트 전체 메모리뿐 아니라 컨테이너 cgroup limit, Kubernetes requests/limits, OOMKilled 이벤트, 스왑 사용 여부, 페이지 폴트율, 애플리케이션 런타임 메모리 설정을 확인해야 한다. 특히 JVM이나 DB는 자체 메모리 설정이 컨테이너 제한과 맞지 않으면 OOM 또는 Thrashing이 발생할 수 있다.

## 관련 개념

- [[페이지 테이블]] - 가상 주소를 물리 주소로 변환하기 위한 핵심 자료구조이다.
- [[TLB]] - 주소 변환 속도를 높이기 위한 캐시로, 가상 메모리 성능에 직접 영향을 준다.
- [[페이지 폴트]] - 요구 페이징에서 필요한 페이지가 메모리에 없을 때 발생하는 예외이다.
- [[스왑 메모리]] - 물리 메모리가 부족할 때 페이지를 디스크로 내보내는 공간이다.
- [[Copy-on-Write]] - 프로세스 fork나 공유 페이지에서 실제 쓰기 발생 시 복사하는 최적화 기법이다.
- [[Working Set]] - 프로세스가 일정 시간 동안 집중적으로 사용하는 페이지 집합으로 Thrashing 분석에 중요하다.
- [[Belady's Anomaly]] - FIFO에서 프레임 수가 증가해도 페이지 폴트가 증가할 수 있는 현상이다.
- [[MMU]] - CPU의 가상 주소를 물리 주소로 변환하는 하드웨어 장치이다.
- [[mmap]] - 파일이나 메모리 객체를 프로세스 주소 공간에 매핑하는 시스템 호출이다.
- [[OOM Killer]] - Linux에서 메모리 부족 시 프로세스를 종료해 시스템을 보호하는 메커니즘이다.
- [[cgroups]] - Linux에서 프로세스 그룹의 CPU, 메모리 등 자원 사용량을 제한하고 관리하는 기능이다.
- [[ASLR]] - 가상 주소 배치를 무작위화하여 메모리 공격을 어렵게 만드는 보안 기법이다.
