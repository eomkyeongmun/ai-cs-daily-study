# 중앙처리장치 (CPU) - ALU, 제어장치, 레지스터, 명령어 사이클(Fetch, Decode, Execute)

## 핵심 개념

CPU(Central Processing Unit, 중앙처리장치)는 컴퓨터 시스템에서 명령어를 해석하고 실행하는 핵심 하드웨어이다. 프로그램은 메모리에 저장된 명령어와 데이터의 집합이며, CPU는 이를 순차적으로 또는 분기 흐름에 따라 가져와 실행한다. CPU의 핵심 구성 요소는 크게 **ALU(Arithmetic Logic Unit, 산술논리장치)**, **제어장치(Control Unit)**, **레지스터(Register)** 로 나눌 수 있다.

**ALU**는 덧셈, 뺄셈, 비트 AND/OR/XOR, 시프트, 비교 연산 등을 수행한다. 실제 프로그램의 산술 계산, 조건문 판단, 주소 계산 등은 대부분 ALU의 연산을 기반으로 한다.  
**제어장치**는 명령어를 해석하고, CPU 내부 구성 요소와 메모리, 입출력 장치가 어떤 순서로 동작해야 하는지 제어 신호를 생성한다. 즉, “무엇을 언제 어디로 이동시키고 어떤 연산을 수행할지”를 결정한다.  
**레지스터**는 CPU 내부에 존재하는 매우 빠른 임시 저장 공간이다. 메모리보다 훨씬 빠르게 접근할 수 있기 때문에 현재 실행 중인 명령어, 연산 대상 데이터, 메모리 주소, 실행 결과 등을 저장하는 데 사용된다.

CPU가 프로그램을 실행하는 기본 흐름은 **명령어 사이클(Instruction Cycle)** 이다. 일반적으로 **Fetch → Decode → Execute** 단계로 설명한다. Fetch는 메모리에서 명령어를 가져오는 단계, Decode는 명령어의 의미를 해석하는 단계, Execute는 실제 연산이나 메모리 접근, 분기 등을 수행하는 단계이다. 이 개념은 컴퓨터 구조의 중심이며, 운영체제의 프로세스 실행, 컴파일러의 코드 생성, 성능 최적화, 보안 취약점 분석까지 폭넓게 연결된다.

## 내부 동작 원리

CPU 내부 동작은 “명령어와 데이터가 레지스터, ALU, 메모리 사이를 이동하고, 제어장치가 이를 조율하는 과정”으로 볼 수 있다.

대표적인 단순 CPU 구조를 텍스트 다이어그램으로 표현하면 다음과 같다.

```text
            ┌──────────────────────────┐
            │          CPU             │
            │                          │
            │  ┌───────────────┐       │
            │  │ Control Unit  │       │
            │  └───────┬───────┘       │
            │          │ 제어 신호       │
            │  ┌───────▼───────┐       │
            │  │     ALU       │       │
            │  └───────┬───────┘       │
            │          │               │
            │  ┌───────▼────────────┐  │
            │  │ Registers          │  │
            │  │ PC, IR, GPR, SP... │  │
            │  └────────┬───────────┘  │
            └───────────┼──────────────┘
                        │
              Address/Data/Control Bus
                        │
                 ┌──────▼──────┐
                 │   Memory    │
                 └─────────────┘
```

## 1. 주요 레지스터

CPU 아키텍처마다 이름과 개수는 다르지만, 개념적으로 다음과 같은 레지스터들이 중요하다.

- **PC(Program Counter)**  
  다음에 실행할 명령어의 메모리 주소를 저장한다. 일부 아키텍처에서는 Instruction Pointer(IP)라고도 부른다.

- **IR(Instruction Register)**  
  메모리에서 가져온 현재 명령어를 저장한다.

- **GPR(General Purpose Register, 범용 레지스터)**  
  연산 대상 데이터, 중간 결과, 함수 인자, 반환값 등을 저장하는 데 사용된다.

- **SP(Stack Pointer)**  
  현재 스택의 위치를 가리킨다. 함수 호출, 지역 변수, 반환 주소 관리에 중요하다.

- **Flag Register / Status Register**  
  ALU 연산 결과의 상태를 저장한다. 예를 들어 결과가 0인지, 음수인지, 자리올림이 발생했는지, 오버플로가 발생했는지 등을 나타낼 수 있다.

## 2. 명령어 사이클

명령어 사이클은 CPU가 명령어 하나를 처리하는 기본 과정이다.

```text
┌─────────┐      ┌──────────┐      ┌───────────┐
│ Fetch   │ ───▶ │ Decode   │ ───▶ │ Execute   │
└─────────┘      └──────────┘      └───────────┘
     ▲                                  │
     └──────── 다음 명령어로 이동 ◀──────┘
```

### 2-1. Fetch 단계

Fetch 단계에서는 CPU가 메모리에서 다음 명령어를 가져온다.

일반적인 흐름은 다음과 같다.

```text
1. PC에 저장된 주소를 메모리 주소 버스로 전달
2. 메모리에서 해당 주소의 명령어를 읽음
3. 읽은 명령어를 IR에 저장
4. PC를 다음 명령어 주소로 갱신
```

예시:

```text
PC = 0x1000
Memory[0x1000] = ADD R1, R2, R3

Fetch 후:
IR = ADD R1, R2, R3
PC = 다음 명령어 주소
```

명령어 길이가 고정인 아키텍처에서는 PC 증가가 비교적 단순하다. 반면 x86처럼 가변 길이 명령어를 사용하는 아키텍처에서는 명령어 길이 해석이 더 복잡하다.

### 2-2. Decode 단계

Decode 단계에서는 IR에 저장된 명령어를 제어장치가 해석한다.

예를 들어 다음 명령어가 있다고 하자.

```asm
ADD R1, R2, R3
```

이는 보통 다음 의미로 해석된다.

```text
R1 = R2 + R3
```

Decode 단계에서 CPU는 다음 정보를 파악한다.

- 어떤 연산을 수행할 것인가?  
  예: ADD, SUB, LOAD, STORE, JUMP

- 어떤 레지스터를 읽을 것인가?  
  예: R2, R3

- 결과를 어디에 저장할 것인가?  
  예: R1

- 메모리 접근이 필요한가?

- 분기 명령어인가?

제어장치는 이 해석 결과를 바탕으로 ALU, 레지스터 파일, 메모리 인터페이스 등에 제어 신호를 보낸다.

### 2-3. Execute 단계

Execute 단계에서는 실제 명령어의 동작이 수행된다.

명령어 유형별 예시는 다음과 같다.

#### 산술/논리 명령어

```asm
ADD R1, R2, R3
```

동작:

```text
1. R2 값과 R3 값을 레지스터 파일에서 읽음
2. ALU가 두 값을 더함
3. 결과를 R1에 저장
4. Flag Register 갱신 가능
```

#### 메모리 읽기 명령어

```asm
LOAD R1, [R2]
```

동작:

```text
1. R2에 저장된 값을 메모리 주소로 사용
2. 해당 주소의 데이터를 메모리에서 읽음
3. 읽은 값을 R1에 저장
```

#### 메모리 쓰기 명령어

```asm
STORE R1, [R2]
```

동작:

```text
1. R2에 저장된 값을 메모리 주소로 사용
2. R1의 값을 해당 메모리 주소에 기록
```

#### 분기 명령어

```asm
JMP 0x2000
```

동작:

```text
1. PC 값을 0x2000으로 변경
2. 다음 Fetch는 0x2000 주소에서 수행
```

조건 분기 명령어는 Flag Register 또는 비교 결과를 기반으로 PC를 갱신할지 결정한다.

## 3. ALU 내부 동작

ALU는 여러 산술/논리 회로를 조합한 장치이다. 예를 들어 덧셈은 전가산기(full adder)를 여러 비트로 연결해 구현할 수 있다.

```text
입력 A ─┐
        ├──▶ ALU ───▶ 결과
입력 B ─┘       │
                └──▶ 상태 플래그
```

ALU가 생성할 수 있는 대표적인 상태 플래그는 다음과 같다.

- **Zero Flag**: 결과가 0이면 설정
- **Sign/Negative Flag**: 결과가 음수로 해석되면 설정
- **Carry Flag**: unsigned 연산에서 자리올림 또는 빌림 발생 시 설정
- **Overflow Flag**: signed 연산에서 표현 범위를 벗어났을 때 설정

## 4. 제어장치의 구현 방식

제어장치는 크게 다음 방식으로 설명할 수 있다.

- **하드와이어드 제어(Hardwired Control)**  
  논리 회로로 제어 신호를 직접 생성한다. 일반적으로 빠르지만 수정이 어렵다.

- **마이크로프로그램 제어(Microprogrammed Control)**  
  명령어 실행을 더 작은 마이크로명령어들의 순서로 제어한다. 복잡한 명령어를 구현하기에 유리하지만, 구조에 따라 속도나 복잡도 측면에서 차이가 있다.

현대 CPU는 파이프라이닝, 슈퍼스칼라 실행, 비순차 실행(out-of-order execution), 분기 예측, 캐시 계층 등 훨씬 복잡한 기법을 사용한다. 그러나 그 내부에서도 기본 개념은 여전히 “명령어를 가져오고, 해석하고, 실행한다”는 명령어 사이클에 기반한다.

## 실제 시스템 연결

CPU의 ALU, 제어장치, 레지스터, 명령어 사이클은 운영체제와 실제 애플리케이션 실행에서 직접적으로 드러난다.

## 1. Linux에서의 CPU 실행

Linux에서 프로세스는 실행 가능한 바이너리 파일을 메모리에 적재한 뒤 CPU에서 명령어를 실행한다. 예를 들어 C 프로그램을 컴파일하면 기계어 명령어가 포함된 실행 파일이 생성된다. CPU는 이 명령어를 Fetch, Decode, Execute 과정을 거쳐 실행한다.

간단한 C 코드:

```c
int add(int a, int b) {
    return a + b;
}
```

컴파일러는 이를 특정 CPU 아키텍처의 기계어 명령어로 변환한다. 예를 들어 x86-64 또는 ARM64에서는 함수 인자와 반환값이 특정 레지스터를 통해 전달될 수 있다. 정확한 레지스터 사용 규칙은 ABI(Application Binary Interface)에 따라 정해진다.

Linux에서 CPU 정보를 확인하는 명령어 예시는 다음과 같다.

```bash
lscpu
cat /proc/cpuinfo
```

이 명령어들은 CPU 아키텍처, 코어 수, 스레드 수, 지원 명령어 집합 등의 정보를 보여준다.

## 2. 컨텍스트 스위칭과 레지스터

운영체제는 여러 프로세스를 동시에 실행하는 것처럼 보이게 하기 위해 CPU 사용 시간을 나누어 배정한다. 한 프로세스에서 다른 프로세스로 전환할 때, Linux 커널은 현재 프로세스의 CPU 실행 상태를 저장하고 다음 프로세스의 상태를 복원한다.

이때 중요한 것이 레지스터 상태이다.

```text
프로세스 A 실행 중
  ↓
커널이 A의 PC, SP, 범용 레지스터 등 저장
  ↓
프로세스 B의 저장된 레지스터 상태 복원
  ↓
프로세스 B 실행 재개
```

즉, 프로세스는 자신이 계속 CPU를 사용한 것처럼 보이지만 실제로는 운영체제가 레지스터와 실행 문맥을 저장/복원하고 있다.

## 3. Nginx와 CPU

Nginx는 이벤트 기반 구조를 사용하여 많은 네트워크 연결을 처리할 수 있는 웹 서버이다. 요청 처리 과정에서 CPU는 다음과 같은 작업을 수행한다.

- 네트워크 패킷 처리와 시스템 콜 수행
- HTTP 요청 파싱
- TLS 암호화/복호화
- 파일 경로 처리
- 압축 처리
- 로그 문자열 생성

특히 TLS 처리나 압축은 CPU 연산량이 커질 수 있다. 이때 CPU의 ALU, 벡터 연산 명령어, 암호화 관련 명령어 지원 여부가 성능에 영향을 줄 수 있다. 예를 들어 일부 CPU는 AES 연산을 가속하는 명령어를 제공하며, 이를 지원하는 라이브러리와 함께 사용하면 암호화 처리 성능이 향상될 수 있다.

## 4. AWS, GCP의 인스턴스와 CPU

AWS EC2나 Google Cloud Compute Engine 같은 클라우드 VM은 물리 서버의 CPU 자원을 가상화하여 제공한다. 사용자는 vCPU 단위로 CPU 자원을 할당받는다. vCPU는 클라우드 사업자와 인스턴스 유형에 따라 물리 코어 또는 하드웨어 스레드와 매핑되는 방식이 다를 수 있다.

실제 애플리케이션 성능은 다음 요소의 영향을 받는다.

- CPU 아키텍처: x86-64, ARM64 등
- 코어 수 및 스레드 수
- 클럭, 캐시 크기, 메모리 대역폭
- 가상화 오버헤드
- CPU 크레딧 또는 버스트 정책이 있는 인스턴스 유형 여부
- NUMA 구조 여부
- 컴파일된 바이너리가 해당 아키텍처를 지원하는지 여부

예를 들어 ARM64 기반 서버에서 x86-64 전용 바이너리는 그대로 실행되지 않는다. 멀티 아키텍처 이미지를 사용하거나 해당 아키텍처용으로 다시 빌드해야 한다.

## 클라우드 연결

CPU 개념은 Docker, Kubernetes, AWS 같은 클라우드 환경에서 자원 제한, 스케줄링, 성능 분석과 직접 연결된다.

## 1. Docker와 CPU 제한

Docker 컨테이너는 독립된 CPU를 갖는 것이 아니라 호스트 커널의 스케줄링을 통해 CPU 시간을 할당받는다. Linux에서는 cgroups를 통해 컨테이너별 CPU 사용량을 제한하거나 가중치를 부여할 수 있다.

예시:

```bash
docker run --cpus="1.5" nginx
```

이 설정은 컨테이너가 사용할 수 있는 CPU 시간을 제한한다. 컨테이너 내부의 프로세스는 여전히 CPU 명령어를 Fetch, Decode, Execute 방식으로 실행하지만, 실제 실행 기회는 호스트 OS 스케줄러와 cgroup 제한에 의해 결정된다.

## 2. Kubernetes의 CPU request와 limit

Kubernetes에서 Pod는 CPU request와 limit을 설정할 수 있다.

```yaml
resources:
  requests:
    cpu: "500m"
  limits:
    cpu: "1"
```

- **CPU request**: 스케줄러가 노드를 선택할 때 고려하는 최소 CPU 요청량
- **CPU limit**: 컨테이너가 사용할 수 있는 CPU 사용량의 상한

CPU limit이 낮게 설정되면 컨테이너는 CPU throttling을 경험할 수 있다. CPU throttling이 발생하면 프로세스가 실행 가능한 상태여도 CPU 시간을 충분히 받지 못해 응답 지연이 증가할 수 있다.

## 3. 클라우드 인스턴스 아키텍처와 명령어 집합

클라우드 환경에서는 x86-64와 ARM64 인스턴스가 모두 사용된다. CPU 아키텍처가 다르면 명령어 집합도 다르다. 따라서 바이너리 호환성과 컨테이너 이미지 아키텍처가 중요하다.

예를 들어 Docker 이미지는 멀티 아키텍처 매니페스트를 지원할 수 있다.

```bash
docker buildx build --platform linux/amd64,linux/arm64 .
```

이 방식으로 서로 다른 CPU 아키텍처용 이미지를 빌드할 수 있다.

## 4. AWS 서비스와 CPU

AWS EC2는 다양한 CPU 특성을 가진 인스턴스 패밀리를 제공한다. 일반적으로 워크로드 특성에 따라 다음과 같이 선택한다.

- 웹 서버: 범용 인스턴스
- CPU 집약적 작업: 컴퓨팅 최적화 인스턴스
- 메모리 중심 작업: 메모리 최적화 인스턴스
- 머신러닝 추론/학습: GPU 또는 전용 가속기 기반 인스턴스

CPU 집약적 작업의 예시는 다음과 같다.

- 동영상 인코딩
- 압축/해제
- 대규모 빌드 작업
- 암호화/복호화
- 과학 계산
- 고성능 웹 요청 처리

## 5. 성능 모니터링

클라우드에서 CPU 병목을 분석할 때는 단순히 CPU 사용률만 보는 것이 부족하다. 다음 지표를 함께 확인해야 한다.

- CPU utilization
- Load average
- CPU steal time
- Context switch 수
- CPU throttling 여부
- run queue 길이
- 캐시 미스, branch miss 같은 하드웨어 성능 카운터

Linux에서는 다음 도구들이 사용된다.

```bash
top
htop
vmstat
mpstat
pidstat
perf
```

`perf`는 CPU 성능 카운터를 활용하여 함수별 CPU 사용량, 캐시 미스, 분기 예측 실패 등을 분석할 수 있다. 다만 클라우드 환경에서는 가상화 설정이나 권한 제한 때문에 일부 하드웨어 카운터 접근이 제한될 수 있다.

## 보안 연결

CPU 구조는 보안과 깊게 연결된다. 명령어 실행 방식, 레지스터, 캐시, 분기 예측, 예외 처리, 권한 수준은 시스템 보안의 기반이자 취약점의 원인이 되기도 한다.

## 1. 권한 수준과 CPU

현대 CPU는 일반적으로 사용자 모드와 커널 모드 같은 권한 수준을 제공한다. 일반 애플리케이션은 사용자 모드에서 실행되고, 운영체제 커널은 더 높은 권한 수준에서 실행된다. 사용자 프로그램이 파일 시스템, 네트워크, 프로세스 제어 같은 민감한 작업을 수행하려면 시스템 콜을 통해 커널에 요청해야 한다.

```text
User Process
   │
   │ system call
   ▼
Kernel Mode
   │
   │ 권한 확인 후 작업 수행
   ▼
Return to User Mode
```

이 권한 분리는 악성 프로그램이 임의로 하드웨어나 커널 메모리에 접근하는 것을 막는 핵심 보안 메커니즘이다.

## 2. 레지스터와 민감 정보

레지스터에는 함수 인자, 암호 키 조각, 포인터, 반환 주소, 중간 연산 결과 등이 저장될 수 있다. 따라서 취약한 프로그램에서는 레지스터나 스택에 남은 민감 정보가 디버깅, 메모리 덤프, 취약점 악용 과정에서 노출될 수 있다.

보안 모범 사례:

- 암호 키는 필요 이상으로 오래 메모리나 레지스터에 남기지 않는다.
- 민감 데이터를 처리한 버퍼는 안전하게 지운다.
- 컴파일러 최적화로 인해 지우기 코드가 제거되지 않도록 주의한다.
- 코어 덤프에 민감 정보가 포함되지 않도록 운영 정책을 설정한다.

## 3. 명령어 실행과 사이드 채널 공격

CPU는 성능 향상을 위해 캐시, 분기 예측, 추측 실행(speculative execution), 비순차 실행 같은 기법을 사용한다. 이들은 프로그램의 논리적 결과를 바꾸지 않도록 설계되지만, 캐시 접근 시간 같은 미세한 차이를 통해 정보가 유출될 수 있다.

대표적으로 알려진 유형은 다음과 같다.

- 캐시 타이밍 공격
- 분기 예측 기반 사이드 채널
- 추측 실행 기반 사이드 채널
- 동시 멀티스레딩 환경에서의 자원 경합 기반 정보 유출

Spectre와 Meltdown은 CPU의 성능 최적화 기능과 관련된 대표적인 사이드 채널 취약점 계열로 알려져 있다. 이 취약점들은 소프트웨어의 권한 검사를 우회하거나 민감 데이터에 대한 접근 흔적을 캐시 상태로 남겨 공격자가 추론할 수 있게 하는 방식과 관련된다.

## 4. 버퍼 오버플로와 CPU 실행 흐름

CPU는 PC 또는 IP가 가리키는 주소의 명령어를 실행한다. 버퍼 오버플로 취약점은 공격자가 스택의 반환 주소나 함수 포인터 같은 제어 흐름 데이터를 덮어써서 CPU가 공격자가 원하는 위치의 코드를 실행하도록 유도할 수 있다.

방어 기법:

- ASLR(Address Space Layout Randomization)
- Stack Canary
- NX/DEP: 데이터 영역에서 코드 실행 방지
- PIE(Position Independent Executable)
- CFI(Control Flow Integrity)
- 안전한 언어 또는 메모리 안전 기능 사용

## 5. 컨테이너와 CPU 보안

Docker나 Kubernetes 컨테이너는 CPU를 가상화된 독립 하드웨어로 제공받는 것이 아니라 호스트 커널 위에서 프로세스로 실행된다. 따라서 컨테이너 격리는 커널 네임스페이스, cgroups, capabilities, seccomp, LSM(AppArmor, SELinux 등)에 의존한다.

CPU 관련 보안 고려사항:

- 컨테이너 간 사이드 채널 가능성 완화
- 동일 노드에 민감 워크로드와 불신 워크로드를 함께 배치하지 않기
- seccomp로 불필요한 시스템 콜 제한
- 커널과 CPU 마이크로코드 업데이트 적용
- 클라우드 보안 공지에 따른 취약점 패치 적용

## 면접 질문

**Q1. CPU의 ALU, 제어장치, 레지스터는 각각 어떤 역할을 하나요?**  
> 핵심 답변: ALU는 산술/논리 연산을 수행하고, 제어장치는 명령어를 해석해 제어 신호를 생성하며, 레지스터는 CPU 내부의 고속 임시 저장 공간이다. 세 요소가 함께 동작하여 명령어를 실행한다.

**Q2. 명령어 사이클의 Fetch, Decode, Execute 단계를 설명해보세요.**  
> 핵심 답변: Fetch는 PC가 가리키는 메모리 주소에서 명령어를 가져와 IR에 저장하는 단계이다. Decode는 제어장치가 명령어의 연산 종류와 피연산자를 해석하는 단계이다. Execute는 ALU 연산, 메모리 접근, 분기 등 실제 동작을 수행하는 단계이다.

**Q3. 레지스터가 메모리보다 중요한 이유는 무엇인가요?**  
> 핵심 답변: 레지스터는 CPU 내부에 있어 메모리보다 훨씬 빠르게 접근할 수 있다. CPU는 모든 연산을 메모리에서 직접 수행하기보다 데이터를 레지스터로 가져와 처리한다. 따라서 레지스터 활용은 성능과 명령어 실행 효율에 큰 영향을 준다.

**Q4. 프로그램 카운터(PC)는 어떤 역할을 하나요?**  
> 핵심 답변: PC는 다음에 실행할 명령어의 주소를 저장한다. 일반 명령어 실행 후에는 다음 명령어 주소로 갱신되고, 분기나 함수 호출, 인터럽트가 발생하면 특정 주소로 변경된다. CPU의 실행 흐름을 결정하는 핵심 레지스터이다.

**Q5. CPU 구조와 보안 취약점은 어떻게 연결되나요?**  
> 핵심 답변: CPU의 권한 수준은 사용자 모드와 커널 모드를 분리해 보안을 제공한다. 반면 캐시, 분기 예측, 추측 실행 같은 성능 최적화 기능은 사이드 채널 공격의 원인이 될 수 있다. 또한 스택 반환 주소 변조는 CPU의 제어 흐름을 탈취하는 공격으로 이어질 수 있다.
