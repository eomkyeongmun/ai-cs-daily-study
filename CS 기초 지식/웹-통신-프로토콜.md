# 웹 통신 프로토콜 - HTTP/1.1, HTTP/2, HTTP/3의 차이점 및 발전 과정

## 핵심 개념

HTTP는 웹 브라우저, 모바일 앱, 서버, 프록시, CDN 등이 데이터를 주고받기 위해 사용하는 애플리케이션 계층 프로토콜이다. HTTP/1.1, HTTP/2, HTTP/3는 모두 “클라이언트가 요청하고 서버가 응답한다”는 HTTP 의미론, 즉 메서드, 상태 코드, 헤더, URI, 캐시 등의 개념은 유지하면서 전송 효율과 지연 시간 문제를 개선해 온 발전 단계라고 볼 수 있다.

HTTP/1.1은 텍스트 기반 프로토콜이며, 하나의 TCP 연결에서 여러 요청을 처리할 수 있는 지속 연결을 지원한다. 하지만 같은 연결 안에서 응답 순서가 막히는 Head-of-Line Blocking 문제가 있고, 많은 리소스를 병렬로 받기 위해 여러 TCP 연결을 여는 방식에 의존하는 경우가 많았다.

HTTP/2는 TCP 위에서 동작하지만, 메시지를 바이너리 프레임으로 분할하고 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리하는 멀티플렉싱을 도입했다. 또한 HPACK 기반 헤더 압축을 통해 반복되는 헤더 전송 비용을 줄였다. 하지만 TCP 자체의 패킷 손실이 발생하면 해당 TCP 연결 위의 모든 스트림이 영향을 받는 전송 계층 수준의 Head-of-Line Blocking은 남아 있다.

HTTP/3는 TCP 대신 QUIC 위에서 동작한다. QUIC은 UDP 위에서 구현된 전송 프로토콜이며, 연결 설정 지연을 줄이고 스트림별 독립적인 흐름 제어를 제공하여 TCP 기반 HTTP/2의 일부 한계를 개선한다. HTTP/3는 특히 모바일 네트워크, 무선 환경, 패킷 손실이 있는 환경에서 지연 시간과 연결 복구 측면의 장점이 있다. 이 차이를 이해하는 것은 웹 성능 최적화, 서버 설정, CDN 선택, TLS 정책, 클라우드 로드밸런싱 설계에서 매우 중요하다.

## 내부 동작 원리

## 1. HTTP/1.1 동작 원리

HTTP/1.1은 기본적으로 TCP 연결 위에서 텍스트 형식의 요청과 응답을 주고받는다.

```text
Client                        Server
  | ---- TCP 3-way handshake --> |
  | ---- HTTP Request ---------> |
  | <--- HTTP Response --------- |
  | ---- HTTP Request ---------> |
  | <--- HTTP Response --------- |
```

예시 요청:

```http
GET /index.html HTTP/1.1
Host: example.com
User-Agent: browser
Accept: text/html
```

HTTP/1.1의 주요 특징은 다음과 같다.

- 텍스트 기반 메시지
- 지속 연결, 즉 Keep-Alive 사용 가능
- 요청-응답 순서 중심 처리
- 파이프라이닝 개념은 존재하지만 실제 브라우저 환경에서는 여러 이유로 널리 활용되지 않음
- 병렬 다운로드를 위해 도메인당 여러 TCP 연결을 여는 방식이 사용됨

HTTP/1.1의 병목은 다음과 같다.

```text
하나의 연결에서 요청 A, B, C를 보냈을 때

Request A -> Response A 지연
Request B -> Response B 대기
Request C -> Response C 대기
```

앞선 응답이 지연되면 뒤의 응답 처리도 영향을 받을 수 있다. 이를 애플리케이션 계층의 Head-of-Line Blocking이라고 부른다.

---

## 2. HTTP/2 동작 원리

HTTP/2는 HTTP 의미론은 유지하지만, 전송 형식을 텍스트가 아닌 바이너리 프레임으로 바꾸었다. 하나의 TCP 연결 안에서 여러 스트림을 동시에 사용한다.

```text
Client                                  Server
  | -------- TCP 연결 + TLS ----------> |
  |                                     |
  | == Stream 1: GET /index.html =====> |
  | == Stream 3: GET /app.js =========> |
  | == Stream 5: GET /style.css ======> |
  |                                     |
  | <== Stream 3: app.js frame ======== |
  | <== Stream 1: html frame ========== |
  | <== Stream 5: css frame =========== |
```

HTTP/2의 기본 단위는 다음과 같다.

- Connection: 클라이언트와 서버 사이의 TCP 연결
- Stream: 하나의 요청-응답 흐름
- Frame: HTTP/2 통신의 최소 단위
- Header Frame: 헤더 정보 전달
- Data Frame: 본문 데이터 전달

HTTP/2의 핵심 개선점은 멀티플렉싱이다.

```text
HTTP/1.1:
Connection 1 -> Request A -> Response A
Connection 2 -> Request B -> Response B
Connection 3 -> Request C -> Response C

HTTP/2:
Single Connection
  ├─ Stream 1 -> Request A / Response A
  ├─ Stream 3 -> Request B / Response B
  └─ Stream 5 -> Request C / Response C
```

또한 HTTP/2는 HPACK 헤더 압축을 사용한다. HTTP 요청에는 Cookie, User-Agent, Accept, Authorization 등 반복되는 헤더가 많다. HTTP/2는 정적 테이블과 동적 테이블을 활용해 반복 헤더를 인덱스로 표현하여 전송량을 줄인다.

하지만 HTTP/2는 TCP 위에서 동작하기 때문에 TCP 패킷 손실 시 문제가 생긴다.

```text
TCP 연결 내부:
[Frame A1][Frame B1][Frame C1][Frame A2][Frame B2]

중간 패킷 손실 발생
=> TCP는 순서 보장을 위해 손실된 패킷 재전송 대기
=> 여러 HTTP/2 스트림이 함께 지연
```

이것이 HTTP/2의 TCP 계층 Head-of-Line Blocking이다.

---

## 3. HTTP/3 동작 원리

HTTP/3는 QUIC 위에서 동작한다. QUIC은 UDP를 기반으로 하지만, 단순히 “UDP라서 빠르다”는 의미는 아니다. QUIC은 자체적으로 신뢰성 있는 전송, 흐름 제어, 혼잡 제어, 스트림 관리, TLS 기반 보안 기능을 포함한다.

```text
Client                                  Server
  | -------- UDP / QUIC 연결 --------> |
  | ---- TLS 1.3 기반 암호화 협상 ----> |
  |                                     |
  | == QUIC Stream A: GET /html =====> |
  | == QUIC Stream B: GET /js =======> |
  | == QUIC Stream C: GET /css ======> |
  |                                     |
  | <== Stream B response ============ |
  | <== Stream A response ============ |
  | <== Stream C response ============ |
```

HTTP/3의 계층 구조는 다음과 같다.

```text
HTTP/1.1:
HTTP
TCP
IP

HTTP/2:
HTTP/2 Framing
TCP
IP

HTTP/3:
HTTP/3
QUIC
UDP
IP
```

QUIC의 중요한 특징은 스트림별 독립성이다.

```text
QUIC Connection
  ├─ Stream 1: HTML
  ├─ Stream 2: CSS
  └─ Stream 3: JS

Stream 2에서 패킷 손실 발생
=> Stream 2는 재전송 대기
=> Stream 1, Stream 3은 계속 처리 가능
```

즉 HTTP/3는 HTTP/2에서 남아 있던 TCP 수준의 Head-of-Line Blocking 문제를 줄인다.

또한 QUIC은 연결 식별자를 사용한다. TCP 연결은 일반적으로 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트에 강하게 묶인다. 반면 QUIC은 Connection ID를 사용하여 네트워크가 바뀌는 상황, 예를 들어 모바일 기기가 Wi-Fi에서 LTE/5G로 전환되는 상황에서 연결 유지에 유리하다.

## HTTP/1.1, HTTP/2, HTTP/3 비교

| 항목 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | QUIC over UDP |
| 메시지 형식 | 텍스트 | 바이너리 프레임 | 바이너리 프레임 |
| 멀티플렉싱 | 제한적 | 지원 | 지원 |
| 헤더 압축 | 기본 없음 | HPACK | QPACK |
| HOL Blocking | 애플리케이션 계층에서 발생 가능 | TCP 계층에서 발생 가능 | 스트림 단위로 완화 |
| TLS | 선택 가능 | 실무에서는 대부분 TLS 사용 | QUIC에 TLS 1.3 통합 |
| 연결 이동성 | 제한적 | 제한적 | Connection ID 기반으로 유리 |
| 대표 장점 | 단순성, 호환성 | 병렬 처리, 헤더 압축 | 낮은 지연, 손실 환경 개선 |
| 대표 한계 | 다중 연결 필요, HOL Blocking | TCP 손실 영향 | UDP 차단 환경, 운영 복잡성 |

## 실제 시스템 연결

## 1. Linux에서의 관점

Linux 서버에서 HTTP/1.1과 HTTP/2는 일반적으로 TCP 소켓을 통해 처리된다. `ss`, `netstat`, `tcpdump`, `curl` 같은 도구로 연결 상태와 프로토콜 협상을 확인할 수 있다.

예시:

```bash
curl -I --http1.1 https://example.com
curl -I --http2 https://example.com
curl -I --http3 https://example.com
```

단, `curl --http3` 사용 가능 여부는 curl 빌드 옵션과 QUIC/TLS 라이브러리 지원에 따라 달라진다.

TCP 기반 HTTP/1.1, HTTP/2에서는 다음 Linux 커널 요소가 성능에 영향을 준다.

- TCP 혼잡 제어 알고리즘
- 소켓 버퍼 크기
- SYN backlog
- 파일 디스크립터 제한
- TLS 처리 성능
- NIC offload 기능

HTTP/3는 UDP 기반이므로 방화벽, NAT, 커널 UDP 버퍼, 로드밸런서의 UDP 지원 여부가 중요하다.

---

## 2. Nginx에서의 관점

Nginx는 HTTP/1.1 서버로 널리 사용되며, HTTP/2도 많이 사용된다. 일반적으로 TLS 서버 블록에서 HTTP/2를 활성화한다.

예시:

```nginx
server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/nginx/cert.pem;
    ssl_certificate_key /etc/nginx/key.pem;

    location / {
        proxy_pass http://app;
    }
}
```

HTTP/3 지원은 Nginx 빌드 버전, 모듈, 배포판 패키지 구성에 따라 달라질 수 있다.  
⚠️ 확인 필요: 운영 환경에서 사용하는 Nginx 패키지가 HTTP/3/QUIC을 안정적으로 지원하는지는 배포판, Nginx 버전, 빌드 옵션을 직접 확인해야 한다.

HTTP/2를 사용할 때 Nginx는 클라이언트와는 HTTP/2로 통신하고, 백엔드 애플리케이션 서버와는 HTTP/1.1로 프록시하는 구성이 흔하다.

```text
Browser -- HTTP/2 --> Nginx -- HTTP/1.1 --> App Server
```

이 구조에서는 외부 클라이언트 구간의 성능은 개선되지만, 백엔드 구간은 별도로 튜닝해야 한다.

---

## 3. AWS에서의 관점

AWS에서는 CloudFront, Application Load Balancer, API Gateway 등 여러 서비스가 HTTP 프로토콜 처리에 관여한다.

일반적인 구조:

```text
User Browser
   |
   | HTTPS / HTTP/2 또는 HTTP/3
   v
CloudFront CDN
   |
   | HTTP/1.1 또는 HTTP/2
   v
ALB / Nginx / Application
```

CloudFront 같은 CDN은 클라이언트와 가까운 엣지에서 TLS 종료, 캐싱, 압축, 프로토콜 협상을 수행한다. HTTP/2나 HTTP/3를 클라이언트 구간에 적용하면 다수의 정적 리소스 요청에서 지연 시간을 줄이는 데 도움이 될 수 있다.

⚠️ 확인 필요: 특정 AWS 서비스의 HTTP/3 지원 범위, 기본 활성화 여부, 오리진 연결 프로토콜 지원 여부는 시점과 리전에 따라 달라질 수 있으므로 공식 문서를 확인해야 한다.

---

## 4. GCP에서의 관점

GCP의 Cloud Load Balancing, Cloud CDN, Cloud Run, GKE Ingress 등도 HTTP/1.1, HTTP/2, TLS 종료, 프록시 동작과 관련된다.

예시 구조:

```text
Client
  |
  | HTTPS
  v
Google Cloud Load Balancer
  |
  | HTTP/1.1 또는 HTTP/2
  v
GKE / Cloud Run / VM
```

클라우드 로드밸런서는 보통 클라이언트 연결과 백엔드 연결을 분리해서 관리한다. 따라서 사용자가 HTTP/2로 접속하더라도 백엔드 애플리케이션이 반드시 HTTP/2를 직접 처리하는 것은 아닐 수 있다.

⚠️ 확인 필요: GCP의 특정 로드밸런서, Cloud CDN, Cloud Run, GKE Ingress의 HTTP/3 지원 여부와 제한사항은 제품별 공식 문서를 확인해야 한다.

## 클라우드 연결

## 1. Docker와 HTTP 프로토콜

Docker 컨테이너에서 실행되는 웹 애플리케이션은 보통 내부적으로 HTTP/1.1 서버를 실행한다. 예를 들어 Node.js, Spring Boot, Django, FastAPI 애플리케이션은 컨테이너 내부에서 HTTP 포트를 열고, 외부의 Nginx, Envoy, Traefik, 클라우드 로드밸런서가 TLS와 HTTP/2 또는 HTTP/3를 처리하는 경우가 많다.

```text
Client -- HTTP/2/3 --> Reverse Proxy -- HTTP/1.1 --> Docker Container
```

이 구조는 애플리케이션이 복잡한 TLS/QUIC 처리를 직접 담당하지 않아도 된다는 장점이 있다.

---

## 2. Kubernetes와 HTTP/1.1, HTTP/2, HTTP/3

Kubernetes에서는 Ingress Controller, Service Mesh, Gateway API가 HTTP 프로토콜 처리에 관여한다.

대표 구조:

```text
Client
  |
  | HTTPS / HTTP/2
  v
Ingress Controller
  |
  | HTTP/1.1 또는 HTTP/2
  v
Service
  |
  v
Pod
```

Kubernetes에서 중요한 점은 다음과 같다.

- Ingress Controller가 HTTP/2를 종료할 수 있음
- 백엔드 Pod와는 HTTP/1.1로 통신할 수 있음
- gRPC는 HTTP/2를 기반으로 하므로 Ingress와 로드밸런서가 HTTP/2를 올바르게 지원해야 함
- HTTP/3는 UDP 기반이므로 Service, LoadBalancer, 방화벽, Ingress Controller의 UDP/QUIC 지원 여부 확인이 필요함

HTTP/3를 Kubernetes에서 사용하려면 일반 TCP 기반 Ingress 설정만으로는 부족할 수 있다. UDP 포트, QUIC 지원 프록시, 클라우드 로드밸런서 기능이 모두 맞아야 한다.

---

## 3. AWS 서비스와의 연결

AWS 환경에서는 다음과 같이 역할을 분리하는 경우가 많다.

```text
Route 53
  |
CloudFront
  |
Application Load Balancer
  |
ECS / EKS / EC2 / Lambda
```

각 계층에서 HTTP 프로토콜 처리가 달라질 수 있다.

- CloudFront: 클라이언트와 가까운 엣지에서 캐싱, TLS 종료, HTTP/2 또는 HTTP/3 처리 가능
- ALB: TLS 종료, HTTP/1.1 및 HTTP/2 처리와 관련
- ECS/EKS: 컨테이너 애플리케이션 실행
- API Gateway: HTTP API, REST API 요청 처리
- Lambda: 서버리스 백엔드 실행

중요한 설계 포인트는 “클라이언트-엣지 구간”과 “엣지-오리진 구간”의 프로토콜이 다를 수 있다는 것이다.

```text
Browser -- HTTP/3 --> CloudFront -- HTTP/1.1 --> Origin
```

이 경우 브라우저 사용자는 HTTP/3의 일부 장점을 얻을 수 있지만, 오리진 구간 병목은 별도로 최적화해야 한다.

---

## 4. Service Mesh와 HTTP/2

Istio, Linkerd, Envoy 기반 서비스 메시에서는 HTTP/2와 gRPC가 중요하게 다뤄진다. 마이크로서비스 간 통신에서 gRPC를 사용하면 HTTP/2 스트림 기반 통신을 활용한다.

```text
Service A -- gRPC over HTTP/2 --> Service B
```

서비스 메시 프록시는 다음 작업을 수행할 수 있다.

- TLS/mTLS 처리
- 라우팅
- 재시도
- 타임아웃
- 서킷 브레이킹
- 관측성 메트릭 수집

단, HTTP/2 멀티플렉싱은 연결 수를 줄여주지만, 잘못된 타임아웃, 과도한 재시도, 큰 메시지 전송이 결합되면 장애 전파가 커질 수 있다.

## 보안 연결

## 1. TLS와 HTTP 버전

HTTP/1.1은 평문 HTTP와 HTTPS 모두 가능하다. 그러나 실무 웹 서비스에서는 HTTPS가 사실상 기본이다. HTTP/2는 표준상 TLS 없이도 정의될 수 있지만, 주요 브라우저 환경에서는 일반적으로 TLS 기반 HTTP/2가 사용된다. HTTP/3는 QUIC에 TLS 1.3이 통합되어 암호화가 기본 전제다.

```text
HTTP/1.1: HTTP 또는 HTTPS
HTTP/2: 주로 HTTPS
HTTP/3: QUIC + TLS 1.3
```

보안상 권장 사항:

- HTTPS 사용
- 오래된 TLS 버전 비활성화
- 강력한 cipher suite 사용
- HSTS 적용
- 인증서 자동 갱신 체계 구축
- TLS 종료 지점 이후 내부 구간 보안 검토

---

## 2. HTTP/2 관련 보안 이슈

HTTP/2는 멀티플렉싱과 프레임 기반 구조를 사용하므로 HTTP/1.1과 다른 공격면이 있다.

대표적인 위험 요소:

- 과도한 스트림 생성으로 인한 리소스 고갈
- 큰 헤더 또는 비정상 헤더 압축 패턴으로 인한 메모리 사용 증가
- 프레임 처리 구현 버그
- 서버 설정 미흡으로 인한 DoS 가능성

HTTP/2에서는 다음 설정이 중요하다.

- 최대 동시 스트림 수 제한
- 헤더 크기 제한
- 요청 본문 크기 제한
- 타임아웃 설정
- 비정상 연결 조기 종료
- 프록시와 백엔드 간 프로토콜 변환 검증

---

## 3. HTTP/3와 QUIC 보안 이슈

HTTP/3는 UDP 기반이기 때문에 기존 TCP 중심 보안 장비나 방화벽 정책과 다르게 동작할 수 있다. QUIC은 암호화 범위가 넓어 중간 장비가 내부 정보를 관찰하기 어렵다. 이는 프라이버시 측면에서 장점이지만, 네트워크 보안 모니터링 관점에서는 도전이 될 수 있다.

주의할 점:

- UDP 443 허용 여부
- DDoS 방어 체계의 UDP 처리 능력
- QUIC 트래픽 가시성 확보
- 로드밸런서의 QUIC 지원 여부
- HTTP/3 미지원 클라이언트를 위한 HTTP/2 또는 HTTP/1.1 fallback

HTTP/3를 활성화할 때는 다음과 같은 방식이 일반적이다.

```text
Client -- HTTP/3 가능 --> HTTP/3 사용
Client -- HTTP/3 불가 또는 UDP 차단 --> HTTP/2 또는 HTTP/1.1 사용
```

## 4. 요청 스머글링과 프로토콜 변환

HTTP Request Smuggling은 프록시와 백엔드 서버가 요청 경계를 다르게 해석할 때 발생할 수 있는 취약점이다. HTTP/1.1의 `Content-Length`, `Transfer-Encoding` 처리 차이가 대표적인 원인이다.

프로토콜 변환 환경에서는 특히 주의해야 한다.

```text
Client -- HTTP/2 --> Proxy -- HTTP/1.1 --> Backend
```

프록시는 HTTP/2 요청을 HTTP/1.1로 변환할 수 있다. 이때 헤더 정규화, 요청 본문 길이 계산, 금지 헤더 처리에 문제가 있으면 보안 취약점이 발생할 수 있다.

모범 사례:

- 프록시와 백엔드 서버를 최신 보안 패치 상태로 유지
- 중복 또는 모호한 헤더 차단
- Content-Length와 Transfer-Encoding 처리 정책 명확화
- HTTP/2 pseudo-header 검증
- 백엔드에 직접 접근하지 못하도록 네트워크 제한

---

## 5. 운영 보안 모범 사례

- 외부 노출 구간은 HTTPS 사용
- HTTP/2, HTTP/3 활성화 시 리소스 제한값 설정
- WAF, CDN, DDoS 방어 서비스와 함께 사용
- ALPN 협상 결과 모니터링
- 비정상 스트림 수, 연결 수, 헤더 크기 모니터링
- 로그에서 프로토콜 버전 기록
- 클라이언트 fallback 동작 테스트
- 스테이징 환경에서 부하 테스트 후 적용

## 면접 질문

**Q1. HTTP/1.1, HTTP/2, HTTP/3의 가장 큰 차이는 무엇인가요?**  
> 핵심 답변: HTTP/1.1은 텍스트 기반이며 요청-응답 순서 제약이 크다. HTTP/2는 TCP 위에서 바이너리 프레임과 멀티플렉싱, HPACK 헤더 압축을 제공한다. HTTP/3는 TCP 대신 QUIC over UDP를 사용하여 스트림 단위 독립성과 연결 설정 지연 개선을 제공한다.

**Q2. HTTP/2의 멀티플렉싱이 무엇이고 어떤 문제를 해결하나요?**  
> 핵심 답변: 하나의 TCP 연결 안에서 여러 요청과 응답을 독립적인 스트림으로 동시에 주고받는 방식이다. HTTP/1.1에서 여러 리소스를 받기 위해 다수의 TCP 연결을 사용하던 문제와 애플리케이션 계층의 Head-of-Line Blocking을 완화한다. 단, TCP 패킷 손실에 의한 HOL Blocking은 남는다.

**Q3. HTTP/3가 UDP를 사용하는 이유는 무엇인가요?**  
> 핵심 답변: HTTP/3는 QUIC을 사용하며 QUIC은 UDP 위에서 동작한다. 이는 기존 TCP의 순서 보장 방식으로 인한 연결 전체 지연 문제를 줄이고, 스트림별 독립 처리, 빠른 연결 설정, Connection ID 기반 연결 이동성을 제공하기 위한 설계다. UDP 자체가 신뢰성을 제공하는 것은 아니며 QUIC이 신뢰성, 흐름 제어, 혼잡 제어를 구현한다.

**Q4. HTTP/2에서도 Head-of-Line Blocking이 남아 있는 이유는 무엇인가요?**  
> 핵심 답변: HTTP/2는 애플리케이션 계층에서는 여러 스트림을 멀티플렉싱하지만, 전송 계층은 여전히 TCP다. TCP는 바이트 스트림의 순서 보장을 위해 손실된 패킷이 재전송될 때까지 이후 데이터를 애플리케이션에 전달하지 못할 수 있다. 따라서 하나의 TCP 연결 위의 여러 HTTP/2 스트림이 함께 지연될 수 있다.

**Q5. 실무에서 HTTP/3를 도입할 때 확인해야 할 점은 무엇인가요?**  
> 핵심 답변: UDP 443 허용 여부, CDN과 로드밸런서의 HTTP/3/QUIC 지원, 클라이언트 fallback, 방화벽과 DDoS 방어 체계, 로그와 모니터링, 백엔드 오리진 프로토콜, 성능 테스트 결과를 확인해야 한다. HTTP/3를 켜도 오리진 구간이 HTTP/1.1이면 전체 성능 병목은 남을 수 있다.

## 관련 개념

- [[TCP]] - HTTP/1.1과 HTTP/2의 기반 전송 프로토콜이며 순서 보장과 혼잡 제어를 제공한다.
- [[UDP]] - HTTP/3의 기반인 QUIC이 사용하는 전송 계층 프로토콜이다.
- [[QUIC]] - HTTP/3의 핵심 기반 프로토콜로 스트림 멀티플렉싱, TLS 1.3 통합, 연결 이동성을 제공한다.
- [[TLS]] - HTTPS, HTTP/2 실무 배포, HTTP/3 보안의 핵심 암호화 계층이다.
- [[ALPN]] - TLS 핸드셰이크 과정에서 HTTP/1.1, HTTP/2, HTTP/3 등 사용할 애플리케이션 프로토콜을 협상하는 데 사용된다.
- [[Head-of-Line Blocking]] - HTTP/1.1, HTTP/2, HTTP/3의 발전 배경을 이해하는 핵심 성능 문제다.
- [[HPACK]] - HTTP/2에서 사용하는 헤더 압축 방식이다.
- [[QPACK]] - HTTP/3에서 사용하는 헤더 압축 방식으로 QUIC 스트림 특성에 맞게 설계되었다.
- [[CDN]] - CloudFront, Cloud CDN 같은 엣지 계층에서 HTTP/2와 HTTP/3 성능 최적화가 자주 적용된다.
- [[Reverse Proxy]] - Nginx, Envoy, Traefik 등이 클라이언트와 백엔드 사이에서 HTTP 프로토콜 변환과 TLS 종료를 수행한다.
- [[gRPC]] - HTTP/2를 기반으로 하는 RPC 프레임워크로 Kubernetes와 서비스 메시 환경에서 자주 사용된다.
- [[HTTP Request Smuggling]] - 프록시와 백엔드 간 HTTP 해석 차이에서 발생할 수 있는 대표적인 웹 보안 취약점이다.
