# 객체 지향 프로그래밍 - 4대 특성(캡슐화, 상속, 다형성, 추상화), SOLID 원칙

## 핵심 개념

# 객체 지향 프로그래밍(OOP) 핵심 개념

객체 지향 프로그래밍(Object-Oriented Programming, OOP)은 소프트웨어를 **객체(Object)** 중심으로 설계하고 구현하는 프로그래밍 패러다임이다. 객체는 데이터인 **상태(State, 필드/속성)** 와 동작인 **행위(Behavior, 메서드)** 를 함께 가진다. OOP의 목적은 현실 세계나 도메인 개념을 코드 구조에 가깝게 반영하여, 복잡한 시스템을 더 이해하기 쉽고 변경하기 쉬운 단위로 나누는 것이다.

OOP의 대표적인 4대 특성은 **캡슐화, 상속, 다형성, 추상화**이다. 캡슐화는 객체 내부 구현을 숨기고 필요한 인터페이스만 노출한다. 상속은 기존 클래스의 속성과 동작을 재사용하거나 확장한다. 다형성은 같은 인터페이스로 서로 다른 구현을 사용할 수 있게 한다. 추상화는 복잡한 구현 세부사항을 감추고 핵심 개념만 드러낸다.

OOP가 중요한 이유는 대규모 소프트웨어에서 **변경의 영향 범위를 줄이고**, 코드 재사용성을 높이며, 협업 시 역할과 책임을 명확히 나눌 수 있기 때문이다. 특히 비즈니스 규칙이 자주 바뀌는 시스템에서는 객체 간 책임을 잘 분리하는 것이 유지보수성과 확장성에 큰 영향을 준다. 다만 OOP 자체가 좋은 설계를 보장하지는 않는다. 잘못된 상속 구조, 과도한 추상화, 거대한 객체는 오히려 복잡도를 증가시킨다. 따라서 OOP는 **SOLID 원칙**과 같은 설계 원칙과 함께 이해해야 한다.

## OOP의 4대 특성

### 1. 캡슐화 Encapsulation

캡슐화는 객체의 내부 상태와 구현 세부사항을 외부에서 직접 접근하지 못하도록 숨기고, 정해진 메서드나 인터페이스를 통해서만 접근하도록 하는 개념이다.

예를 들어 `Account` 객체가 `balance`라는 잔액 필드를 가진다고 할 때, 외부 코드가 `balance` 값을 직접 수정할 수 있다면 음수 잔액, 잘못된 통화 단위, 권한 없는 변경 같은 문제가 발생할 수 있다. 캡슐화를 적용하면 `deposit()`, `withdraw()` 같은 메서드를 통해 유효성 검사를 거친 뒤 상태가 변경된다.

핵심 목적은 다음과 같다.

- 객체 내부 불변식 유지
- 변경 영향 범위 축소
- 외부 코드와 내부 구현의 결합도 감소
- 잘못된 상태 변경 방지

### 2. 상속 Inheritance

상속은 기존 클래스의 속성과 메서드를 새로운 클래스가 물려받아 재사용하거나 확장하는 기능이다. 예를 들어 `Animal` 클래스를 상속받아 `Dog`, `Cat` 클래스를 만들 수 있다.

상속은 코드 재사용에 유용하지만, 항상 좋은 선택은 아니다. 부모 클래스의 구현 변경이 자식 클래스에 영향을 주기 때문에 결합도가 강해질 수 있다. 따라서 단순한 코드 재사용 목적이라면 상속보다 **합성 Composition** 을 우선 고려하는 것이 일반적으로 권장된다.

상속은 “is-a” 관계가 성립할 때 적합하다.

```text
Dog is an Animal  -> 적절한 상속 후보
Car has an Engine -> 상속보다 합성이 적합
```

### 3. 다형성 Polymorphism

다형성은 동일한 메시지나 인터페이스 호출이 실제 객체 타입에 따라 서로 다른 동작을 수행하는 특성이다. 대표적인 예는 인터페이스나 부모 클래스 타입으로 객체를 참조하고, 실행 시점에 실제 구현체의 메서드가 호출되는 것이다.

예를 들어 `Payment` 인터페이스가 있고 `CardPayment`, `BankTransferPayment`, `KakaoPayPayment`가 이를 구현한다면, 결제 서비스는 구체적인 결제 방식에 의존하지 않고 `payment.pay()`만 호출하면 된다.

다형성은 확장성에 매우 중요하다. 새로운 결제 방식이 추가되어도 기존 결제 흐름 코드를 크게 수정하지 않고 새로운 구현 클래스를 추가할 수 있다.

### 4. 추상화 Abstraction

추상화는 복잡한 내부 구현을 감추고, 사용자가 알아야 할 핵심 기능만 표현하는 것이다. 예를 들어 데이터베이스 연결 객체는 내부적으로 TCP 연결, 인증, 쿼리 직렬화, 결과 파싱 등을 처리하지만, 사용자는 `query()` 같은 메서드만 호출하면 된다.

추상화는 인터페이스, 추상 클래스, API, 모듈 경계 등을 통해 구현된다. 좋은 추상화는 사용자가 불필요한 세부사항을 몰라도 시스템을 사용할 수 있게 하며, 구현 변경이 외부 사용 코드에 미치는 영향을 줄인다.

## SOLID 원칙

SOLID는 객체 지향 설계에서 유지보수성과 확장성을 높이기 위한 다섯 가지 원칙이다.

### S: 단일 책임 원칙 SRP, Single Responsibility Principle

하나의 클래스나 모듈은 하나의 책임만 가져야 하며, 변경될 이유도 하나여야 한다는 원칙이다. 예를 들어 `UserService`가 사용자 생성, 이메일 발송, 로그 기록, 결제 처리까지 모두 담당하면 변경 이유가 많아지고 유지보수가 어려워진다.

### O: 개방-폐쇄 원칙 OCP, Open-Closed Principle

소프트웨어 요소는 확장에는 열려 있고, 수정에는 닫혀 있어야 한다는 원칙이다. 새로운 기능을 추가할 때 기존 코드를 직접 수정하기보다 새로운 구현을 추가하는 방식이 이상적이다. 인터페이스와 다형성이 자주 사용된다.

### L: 리스코프 치환 원칙 LSP, Liskov Substitution Principle

하위 타입은 상위 타입을 대체할 수 있어야 한다는 원칙이다. 즉, 부모 타입을 사용하는 코드가 자식 타입을 사용해도 올바르게 동작해야 한다. 자식 클래스가 부모 클래스의 계약을 깨면 LSP 위반이다.

대표적인 예로 `Rectangle`을 상속한 `Square`가 있다. 정사각형은 수학적으로 직사각형이지만, `setWidth()`, `setHeight()`를 독립적으로 변경할 수 있다는 직사각형의 행위 계약을 정사각형이 만족하지 못할 수 있다.

### I: 인터페이스 분리 원칙 ISP, Interface Segregation Principle

클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강요받지 않아야 한다는 원칙이다. 거대한 인터페이스 하나보다 역할별로 작은 인터페이스를 나누는 것이 좋다.

예를 들어 `MultiFunctionDevice` 인터페이스에 `print()`, `scan()`, `fax()`가 모두 있다면, 단순 프린터 클래스도 `scan()`, `fax()`를 구현해야 하는 문제가 생긴다. 이 경우 `Printable`, `Scannable`, `Faxable`로 분리하는 것이 적절하다.

### D: 의존성 역전 원칙 DIP, Dependency Inversion Principle

고수준 모듈은 저수준 모듈에 직접 의존하지 않고, 둘 다 추상화에 의존해야 한다는 원칙이다. 또한 추상화는 세부 구현에 의존하지 않고, 세부 구현이 추상화에 의존해야 한다.

예를 들어 `OrderService`가 `MySQLOrderRepository`에 직접 의존하면 저장소 구현 변경이 어렵다. 대신 `OrderRepository` 인터페이스에 의존하고, 실제 구현체로 `MySQLOrderRepository`, `DynamoDBOrderRepository` 등을 주입하면 변경에 유연해진다.

## 내부 동작 원리

# 내부 동작 원리

## 1. 객체의 기본 구조

객체는 일반적으로 다음 요소로 구성된다.

```text
+-------------------------+
| Object                  |
+-------------------------+
| State / Fields          |
| - id                    |
| - name                  |
| - status                |
+-------------------------+
| Behavior / Methods      |
| - activate()            |
| - deactivate()          |
| - changeName()          |
+-------------------------+
```

프로그래밍 언어마다 구현 방식은 다르지만, 객체는 메모리상에 상태 데이터를 가지며, 메서드는 해당 객체의 상태를 읽거나 변경한다. Java, C++, C#, Python 등 대부분의 객체 지향 언어는 클래스 또는 프로토타입을 통해 객체 구조와 동작을 정의한다.

⚠️ 확인 필요: 언어별 객체 메모리 레이아웃은 런타임과 컴파일러 구현에 따라 다르므로 특정 언어의 세부 구조를 설명할 때는 해당 버전과 구현체를 확인해야 한다.

## 2. 캡슐화의 동작 원리

캡슐화는 접근 제어자와 메서드 호출을 통해 구현된다.

```java
class Account {
    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException();
        }
        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}
```

외부 코드는 다음처럼 `balance`를 직접 변경할 수 없다.

```text
외부 코드
   |
   | deposit(1000)
   v
+-------------------+
| Account           |
+-------------------+
| private balance   |  <- 직접 접근 불가
+-------------------+
| deposit()         |  <- 검증 후 상태 변경
| getBalance()      |
+-------------------+
```

이 구조에서는 상태 변경이 객체 내부 메서드를 통해 이루어지므로, 객체가 자신의 불변식을 스스로 지킬 수 있다.

## 3. 상속의 동작 원리

상속은 부모 클래스의 필드와 메서드를 자식 클래스가 재사용하거나 재정의하는 구조다.

```text
        +----------------+
        | Animal         |
        +----------------+
        | name           |
        +----------------+
        | eat()          |
        | makeSound()    |
        +----------------+
                ^
                |
      +---------+---------+
      |                   |
+-----------+       +-----------+
| Dog       |       | Cat       |
+-----------+       +-----------+
| bark()    |       | meow()    |
| makeSound() 재정의 | makeSound() 재정의 |
+-----------+       +-----------+
```

자식 클래스는 부모의 공통 기능을 물려받고, 필요한 경우 메서드를 오버라이딩한다.

```java
class Animal {
    void makeSound() {
        System.out.println("sound");
    }
}

class Dog extends Animal {
    @Override
    void makeSound() {
        System.out.println("bark");
    }
}
```

상속의 핵심은 재사용과 확장이지만, 부모와 자식 간 결합도가 높아지는 단점이 있다. 부모 클래스의 protected 필드나 구현 세부사항에 자식 클래스가 강하게 의존하면 변경에 취약해진다.

## 4. 다형성의 동작 원리

다형성은 보통 다음 두 가지 방식으로 설명할 수 있다.

### 컴파일 타임 다형성

메서드 오버로딩처럼 컴파일 시점에 호출 대상이 결정되는 경우다.

```java
print(String value)
print(int value)
```

### 런타임 다형성

상위 타입 참조가 실제 하위 타입 객체를 가리키고, 실행 시점에 실제 객체의 메서드가 호출되는 경우다.

```java
Payment payment = new CardPayment();
payment.pay();
```

동작 구조는 다음과 같다.

```text
Client Code
    |
    | Payment.pay()
    v
+------------------+
| Payment          |  인터페이스
+------------------+
| pay()            |
+------------------+
        ^
        |
+----------------------+----------------------+
|                                             |
+------------------+             +----------------------+
| CardPayment      |             | BankTransferPayment  |
+------------------+             +----------------------+
| pay() 구현       |             | pay() 구현           |
+------------------+             +----------------------+
```

클라이언트는 `CardPayment`인지 `BankTransferPayment`인지 몰라도 `Payment` 인터페이스만 알면 된다. 실제 호출 대상은 런타임 객체 타입에 따라 결정된다.

⚠️ 확인 필요: Java의 가상 메서드 호출, C++의 vtable, Python의 동적 디스패치 등 구체 구현은 언어와 런타임에 따라 다르다.

## 5. 추상화의 동작 원리

추상화는 사용자가 필요한 계약만 보게 하고 구현 세부사항은 감춘다.

```text
Application Service
        |
        | save(order)
        v
+----------------------+
| OrderRepository      |  추상화 계층
+----------------------+
| save(order)          |
| findById(id)         |
+----------------------+
        ^
        |
+----------------------+----------------------+
|                                             |
+----------------------+       +----------------------+
| MySQLOrderRepository |       | DynamoOrderRepository |
+----------------------+       +----------------------+
| SQL로 저장           |       | DynamoDB API로 저장   |
+----------------------+       +----------------------+
```

서비스 계층은 `OrderRepository`라는 추상화에만 의존한다. 실제 저장 방식은 구현체가 담당한다. 이 구조는 저장소 변경, 테스트용 mock 구현, 클라우드 서비스 교체에 유리하다.

## 6. SOLID의 내부 설계 흐름

SOLID를 적용한 설계 흐름은 다음과 같다.

```text
요구사항 분석
   |
   v
책임 식별 SRP
   |
   v
역할별 인터페이스 정의 ISP
   |
   v
구현체 분리 및 다형성 적용 OCP
   |
   v
상위 타입 계약 검증 LSP
   |
   v
의존성 주입 및 추상화 의존 DIP
```

예를 들어 알림 시스템을 설계한다고 하면 다음과 같다.

```text
+----------------------+
| NotificationService  |
+----------------------+
| send(message)        |
+----------------------+
          |
          | depends on
          v
+----------------------+
| Notifier             |  인터페이스
+----------------------+
| notify(message)      |
+----------------------+
    ^             ^
    |             |
+---------+   +-----------+
| Email   |   | Slack     |
|Notifier |   |Notifier   |
+---------+   +-----------+
```

`NotificationService`는 `EmailNotifier`나 `SlackNotifier`에 직접 의존하지 않고 `Notifier` 인터페이스에 의존한다. 새로운 `SmsNotifier`가 추가되어도 기존 서비스 코드는 크게 바뀌지 않는다.

## 실제 시스템 연결

# 실제 시스템 연결

## 1. Linux 커널과 객체 지향적 설계

Linux 커널은 주로 C 언어로 작성되어 있지만, 여러 곳에서 객체 지향적인 설계 방식을 사용한다. C는 전통적인 클래스 기반 OOP 언어는 아니지만, `struct`와 함수 포인터를 활용해 캡슐화, 추상화, 다형성과 유사한 구조를 만들 수 있다.

대표적인 예는 파일 시스템 인터페이스다. Linux 커널은 다양한 파일 시스템을 동일한 방식으로 다루기 위해 공통 연산 구조를 제공한다.

```text
VFS Virtual File System
        |
        v
+----------------------+
| file_operations      |
+----------------------+
| open                 |
| read                 |
| write                |
| release              |
+----------------------+
        ^
        |
+----------------------+----------------------+
| ext4 구현             | procfs 구현           |
+----------------------+----------------------+
```

사용자 공간 프로그램은 `read()`, `write()` 같은 시스템 콜을 호출하지만, 실제 내부에서는 파일 타입이나 파일 시스템에 따라 다른 구현이 실행된다. 이는 다형성과 추상화의 실제 예로 볼 수 있다.

⚠️ 확인 필요: 커널 내부 구조와 함수명은 커널 버전에 따라 세부 구현이 달라질 수 있다.

## 2. Nginx 모듈 구조

Nginx는 C로 작성된 고성능 웹 서버이며, 모듈 기반 아키텍처를 가진다. HTTP 처리, 로드 밸런싱, 캐싱, 압축, 로그 처리 등 여러 기능이 모듈로 분리된다.

객체 지향 관점에서 보면 각 모듈은 특정 책임을 가진 컴포넌트이며, Nginx 코어는 정해진 모듈 인터페이스와 라이프사이클을 통해 모듈을 호출한다. 이는 추상화와 인터페이스 기반 설계에 가깝다.

```text
Client Request
      |
      v
+-------------+
| Nginx Core  |
+-------------+
      |
      v
+-----------------------------+
| HTTP Module Chain           |
+-----------------------------+
| access module               |
| rewrite module              |
| proxy module                |
| gzip module                 |
+-----------------------------+
```

Nginx는 전통적인 클래스 기반 OOP 시스템은 아니지만, 모듈 단위 책임 분리와 확장 구조는 OOP 설계 원칙과 연결된다.

## 3. AWS SDK와 객체 지향 추상화

AWS SDK는 여러 프로그래밍 언어에서 AWS 서비스 API를 호출할 수 있도록 클라이언트 객체를 제공한다. 예를 들어 S3 클라이언트, DynamoDB 클라이언트, SQS 클라이언트처럼 서비스별 객체를 사용한다.

```text
Application
    |
    v
+----------------+
| S3 Client      |
+----------------+
| putObject()    |
| getObject()    |
+----------------+
    |
    v
AWS S3 API
```

개발자는 HTTP 요청 서명, 엔드포인트 구성, 재시도, 응답 파싱 같은 세부사항을 직접 구현하지 않고 SDK 객체의 메서드를 호출한다. 이는 추상화와 캡슐화의 예다.

⚠️ 확인 필요: AWS SDK의 구체적인 클래스명과 메서드명은 언어 및 SDK 버전에 따라 다르다.

## 4. GCP 클라이언트 라이브러리

GCP도 Cloud Storage, Pub/Sub, BigQuery 등 서비스별 클라이언트 라이브러리를 제공한다. 애플리케이션은 클라이언트 객체를 통해 클라우드 리소스를 조작한다.

```text
Application
    |
    v
+----------------------+
| Pub/Sub Publisher    |
+----------------------+
| publish(message)     |
+----------------------+
    |
    v
GCP Pub/Sub
```

이 구조는 애플리케이션 코드가 HTTP/gRPC 세부 구현보다 서비스의 도메인 동작에 집중하게 해준다.

⚠️ 확인 필요: GCP 클라이언트 라이브러리의 내부 통신 방식은 서비스와 언어별 라이브러리 버전에 따라 다를 수 있다.

## 5. 엔터프라이즈 애플리케이션

Spring, .NET, Django, NestJS 같은 프레임워크는 객체 지향 설계를 적극적으로 활용한다. 예를 들어 Spring 애플리케이션에서는 Controller, Service, Repository 계층을 분리하는 경우가 많다.

```text
Controller
    |
    v
Service
    |
    v
Repository
    |
    v
Database
```

이 구조는 SRP와 DIP를 적용하기 쉽다. Controller는 HTTP 요청/응답 처리에 집중하고, Service는 비즈니스 로직을 담당하며, Repository는 데이터 접근을 담당한다.

다만 계층 분리가 항상 좋은 설계를 의미하지는 않는다. 비즈니스 규칙이 빈약하고 데이터 전달만 하는 객체가 많아지면 이른바 빈약한 도메인 모델이 될 수 있다.

## 클라우드 연결

# 클라우드 연결

## 1. Docker와 객체 지향 설계

Docker 자체가 OOP 개념은 아니지만, 애플리케이션을 컨테이너 단위로 캡슐화한다는 점에서 캡슐화와 유사한 설계 사고를 제공한다. 컨테이너는 애플리케이션 코드, 런타임, 의존성, 설정 일부를 하나의 실행 단위로 묶는다.

```text
+-----------------------------+
| Docker Container            |
+-----------------------------+
| Application                 |
| Runtime                     |
| Libraries                   |
| Environment Configuration   |
+-----------------------------+
```

OOP에서 객체 내부 구현을 숨기고 인터페이스를 통해 사용하는 것처럼, 컨테이너는 내부 실행 환경을 이미지로 정의하고 외부에는 포트, 볼륨, 환경 변수 같은 경계를 제공한다.

## 2. Kubernetes와 객체 모델

Kubernetes는 시스템 상태를 선언적으로 관리하며, Pod, Deployment, Service, ConfigMap, Secret 등 여러 리소스를 객체처럼 표현한다.

```text
+----------------+
| Deployment     |
+----------------+
| desired state  |
| replicas       |
| selector       |
| template       |
+----------------+
```

Kubernetes 컨트롤러는 사용자가 선언한 desired state와 실제 상태를 비교하고 조정한다.

```text
Desired State
      |
      v
+------------------+
| Controller       |
+------------------+
      |
      v
Actual State 조정
```

이 관점에서 Kubernetes 리소스는 상태를 가진 객체이며, 컨트롤러는 객체의 상태 전이를 관리하는 역할을 한다고 볼 수 있다.

## 3. Kubernetes Controller와 SOLID

커스텀 컨트롤러나 Operator를 설계할 때 SOLID 원칙이 유용하다.

- SRP: 하나의 컨트롤러는 특정 리소스의 조정 책임에 집중
- OCP: 새로운 리소스 타입이나 전략 추가 시 기존 로직 수정 최소화
- ISP: 클라이언트 인터페이스를 필요한 Kubernetes API 동작별로 분리
- DIP: 컨트롤러 로직이 구체적인 API 클라이언트 구현보다 인터페이스에 의존

예시 구조:

```text
+----------------------+
| BackupController     |
+----------------------+
| reconcile()          |
+----------------------+
          |
          v
+----------------------+
| BackupStorage        | 인터페이스
+----------------------+
| upload()             |
| delete()             |
+----------------------+
    ^              ^
    |              |
+---------+   +-------------+
| S3      |   | GCS         |
| Storage |   | Storage     |
+---------+   +-------------+
```

이 구조에서는 백업 저장소가 AWS S3에서 GCS로 바뀌어도 컨트롤러의 핵심 로직 변경을 줄일 수 있다.

## 4. AWS 서비스와 객체 지향 추상화

AWS 환경에서 애플리케이션은 다양한 외부 서비스에 의존한다. 예를 들어 주문 서비스가 다음 리소스를 사용할 수 있다.

```text
OrderService
    |
    +--> RDS
    +--> SQS
    +--> S3
    +--> CloudWatch
```

이때 `OrderService`가 AWS SDK의 구체 클래스에 직접 의존하면 테스트와 교체가 어려워질 수 있다. DIP를 적용하면 다음과 같이 추상화한다.

```text
OrderService
    |
    v
+----------------------+
| MessageQueue         |
+----------------------+
| send(message)        |
+----------------------+
    ^
    |
+----------------------+
| SqsMessageQueue      |
+----------------------+
```

로컬 테스트에서는 `InMemoryMessageQueue`를 사용할 수 있고, 운영 환경에서는 `SqsMessageQueue`를 사용할 수 있다.

## 5. 마이크로서비스와 OOP

마이크로서비스 아키텍처에서는 서비스 간 경계가 중요하다. OOP의 캡슐화 개념은 마이크로서비스의 데이터 소유권과 API 경계 설계에 응용될 수 있다.

```text
User Service
+----------------------+
| User 데이터 소유      |
| User 비즈니스 로직    |
| User API             |
+----------------------+

Order Service
+----------------------+
| Order 데이터 소유     |
| Order 비즈니스 로직   |
| Order API            |
+----------------------+
```

각 서비스는 자신의 데이터와 로직을 캡슐화하고, 다른 서비스는 API를 통해서만 접근한다. 이는 객체 간 직접 필드 접근을 막고 메서드를 통해 상호작용하는 캡슐화와 유사하다.

다만 마이크로서비스는 분산 시스템이므로 네트워크 지연, 장애 전파, 데이터 일관성, 인증/인가 같은 추가 문제가 있다. 단순히 OOP 객체를 네트워크 서비스로 나눈다고 좋은 마이크로서비스가 되는 것은 아니다.

## 보안 연결

# 보안 연결

## 1. 캡슐화와 보안

캡슐화는 보안에서 중요한 방어 수단이다. 객체의 내부 상태를 외부에서 직접 변경할 수 없게 하면 잘못된 상태 조작이나 권한 우회 가능성을 줄일 수 있다.

예를 들어 사용자의 권한을 나타내는 `role` 필드가 외부에서 직접 수정 가능하다면 공격자가 일반 사용자를 관리자로 변경하는 취약점이 생길 수 있다.

나쁜 예:

```java
class User {
    public String role;
}
```

개선 예:

```java
class User {
    private String role;

    public void changeRole(String newRole, User actor) {
        if (!actor.isAdmin()) {
            throw new SecurityException();
        }
        this.role = newRole;
    }
}
```

이처럼 상태 변경 메서드 내부에 권한 검증과 감사 로그를 넣을 수 있다.

## 2. 추상화와 보안 경계

추상화는 보안 정책을 일관되게 적용하는 데 도움을 준다. 예를 들어 파일 저장 기능을 `FileStorage` 인터페이스로 추상화하면, 실제 구현체에서 경로 검증, 확장자 제한, 암호화, 접근 제어를 공통적으로 적용할 수 있다.

```text
Application
    |
    v
+----------------------+
| SecureFileStorage    |
+----------------------+
| validatePath()       |
| scanFile()           |
| encrypt()            |
| save()               |
+----------------------+
```

반대로 추상화가 잘못되면 보안 세부사항이 숨겨져 위험할 수 있다. 예를 들어 내부적으로 평문 저장을 하는 구현체를 사용하면서 외부 API 이름만 `SecureStorage`라고 붙이면 실제 보안은 보장되지 않는다.

## 3. 상속과 보안 위험

상속은 부모 클래스의 보안 정책을 자식 클래스가 우회하거나 약화시킬 수 있다는 위험이 있다. 예를 들어 부모 클래스의 `validate()` 메서드가 중요한 검증을 수행하는데, 자식 클래스가 이를 오버라이딩하면서 검증을 생략하면 취약점이 발생할 수 있다.

```text
BaseUploader.upload()
   |
   +--> validate()
   +--> save()

MaliciousOrBuggyUploader.validate()
   |
   +--> 아무 검증도 하지 않음
```

보안상 중요한 메서드는 오버라이딩을 제한하거나, 템플릿 메서드 패턴을 사용할 때 불변 조건을 부모 클래스에 남겨야 한다.

예:

```java
final void upload(File file) {
    validateCommonSecurity(file);
    doUpload(file);
}
```

## 4. 다형성과 권한 검증 누락

다형성은 확장성을 높이지만, 구현체마다 보안 검증 수준이 달라질 수 있다. 예를 들어 `PaymentProcessor` 인터페이스를 구현한 여러 결제 처리 클래스 중 일부가 서명 검증이나 금액 검증을 누락하면 문제가 된다.

```text
PaymentProcessor
    ^
    |
+-------------------+----------------------+
| SafeProcessor     | UnsafeProcessor      |
| 서명 검증 수행     | 서명 검증 누락        |
+-------------------+----------------------+
```

이를 방지하려면 다음 원칙이 필요하다.

- 공통 보안 검증은 상위 계층에서 수행
- 보안 관련 계약을 인터페이스 문서에 명확히 정의
- 테스트에서 모든 구현체에 동일한 보안 요구사항 검증
- 코드 리뷰에서 구현체별 검증 누락 확인

## 5. SOLID와 보안 설계

SOLID는 보안성에도 영향을 준다.

- SRP: 인증, 인가, 로깅, 비즈니스 로직을 분리하면 보안 정책 누락을 찾기 쉽다.
- OCP: 새로운 인증 방식 추가 시 기존 검증 로직을 깨뜨릴 가능성을 줄인다.
- LSP: 하위 클래스가 상위 클래스의 보안 계약을 약화시키지 않아야 한다.
- ISP: 불필요한 권한 메서드를 노출하지 않도록 인터페이스를 작게 나눈다.
- DIP: 암호화, 인증, 저장소 구현을 추상화하면 테스트와 교체가 쉬워진다.

## 6. 보안 모범 사례

- 민감한 필드는 public으로 노출하지 않는다.
- setter를 무분별하게 만들지 않는다.
- 상태 변경 메서드에 권한 검증, 입력 검증, 감사 로그를 포함한다.
- 인터페이스 계약에 보안 요구사항을 명시한다.
- 상속보다 합성을 우선 고려한다.
- 보안 검증 로직을 구현체마다 중복하지 말고 공통 계층에서 처리한다.
- 테스트 더블이나 mock 사용 시 운영 보안 검증이 생략되지 않도록 주의한다.
- DTO와 도메인 객체를 구분하여 외부 입력이 핵심 도메인 상태를 직접 오염시키지 않게 한다.

> 핵심 답변: 캡슐화는 상태와 구현을 숨기고 메서드를 통해 접근하게 하는 것, 상속은 기존 타입을 확장하거나 재사용하는 것, 다형성은 같은 인터페이스로 다양한 구현을 사용할 수 있는 것, 추상화는 복잡한 세부 구현을 감추고 핵심 계약만 드러내는 것이다. 유지보수성, 확장성, 결합도 감소와 관련된다.

**Q2. 상속과 합성의 차이는 무엇이며, 언제 합성을 선호해야 하나요?**  
> 핵심 답변: 상속은 “is-a” 관계에서 부모의 속성과 동작을 물려받는 구조이고, 합성은 객체가 다른 객체를 필드로 포함하여 기능을 위임하는 “has-a” 구조다. 상속은 부모-자식 결합도가 높으므로 단순 코드 재사용 목적이라면 합성을 선호하는 것이 좋다. 합성은 런타임 교체와 테스트에도 유리하다.

**Q3. 다형성이 OCP와 어떻게 연결되나요?**  
> 핵심 답변: OCP는 기존 코드를 수정하지 않고 기능을 확장하는 것을 목표로 한다. 다형성을 사용하면 클라이언트 코드는 인터페이스에 의존하고, 새로운 기능은 인터페이스 구현체를 추가하는 방식으로 확장할 수 있다. 예를 들어 새로운 결제 수단을 추가할 때 `Payment` 인터페이스 구현체만 추가하면 기존 결제 흐름 수정이 줄어든다.

**Q4. LSP를 위반하는 예를 들어 설명해주세요.**  
> 핵심 답변: 하위 타입이 상위 타입의 계약을 지키지 못하면 LSP 위반이다. 대표적으로 `Rectangle`을 상속한 `Square`가 있다. 상위 타입인 `Rectangle`은 너비와 높이를 독립적으로 변경할 수 있다는 기대가 있는데, `Square`는 두 값이 항상 같아야 하므로 이 계약을 깨뜨릴 수 있다. 이 경우 상속 구조가 부적절할 수 있다.

**Q5. DIP와 의존성 주입은 어떤 관계가 있나요?**  
> 핵심 답변: DIP는 고수준 모듈이 저수준 구현체가 아니라 추상화에 의존해야 한다는 설계 원칙이다. 의존성 주입은 이 원칙을 구현하는 방법 중 하나다. 예를 들어 `OrderService`가 `MySQLRepository`를 직접 생성하지 않고 `OrderRepository` 인터페이스를 생성자나 설정을 통해 주입받으면 저장소 구현 교체와 테스트가 쉬워진다.

## 관련 개념

# 관련 개념

- [[클래스와 객체]] - OOP의 기본 구성 단위로, 클래스는 설계도이고 객체는 실행 시점의 인스턴스다.
- [[캡슐화]] - 객체 내부 상태 보호와 변경 영향 범위 축소의 핵심 개념이다.
- [[상속]] - 타입 계층과 코드 재사용을 제공하지만 강한 결합을 만들 수 있다.
- [[다형성]] - 인터페이스 기반 확장과 런타임 동작 분기에 중요한 개념이다.
- [[추상화]] - 복잡한 구현 세부사항을 감추고 핵심 계약만 제공하는 설계 방식이다.
- [[SOLID]] - 객체 지향 설계의 대표적인 다섯 가지 원칙이다.
- [[의존성 주입]] - DIP를 구현하는 대표적인 패턴으로 테스트와 교체 가능성을 높인다.
- [[인터페이스]] - 구현과 사용자를 분리하여 다형성과 추상화를 가능하게 한다.
- [[합성 Composition]] - 상속의 대안으로 객체 간 기능 위임을 통해 유연한 구조를 만든다.
- [[디자인 패턴]] - OOP 설계 문제를 해결하기 위한 반복 가능한 설계 해법이다.
- [[도메인 주도 설계]] - 비즈니스 도메인을 중심으로 객체와 모델을 설계하는 접근 방식이다.
- [[계층형 아키텍처]] - Controller, Service, Repository 등 책임을 계층별로 분리하는 구조다.
