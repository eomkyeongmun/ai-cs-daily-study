# 주소 및 이름 변환 - DNS 작동 원리, ARP/RARP, MAC 주소와 IP 주소

## 핵심 개념

주소 및 이름 변환은 네트워크 통신에서 “사람이 이해하기 쉬운 이름”, “논리적 주소”, “물리적 주소”를 서로 연결하는 핵심 과정이다. 대표적으로 DNS는 `www.example.com` 같은 도메인 이름을 IP 주소로 변환하고, ARP는 같은 LAN 안에서 IP 주소에 대응하는 MAC 주소를 찾는다. MAC 주소는 데이터 링크 계층에서 프레임 전달에 사용되는 물리적 식별자이고, IP 주소는 네트워크 계층에서 목적지 네트워크와 호스트를 식별하는 논리적 주소다.

사용자가 웹사이트에 접속할 때 브라우저는 먼저 도메인 이름을 IP 주소로 변환해야 한다. 그다음 IP 패킷을 목적지까지 보내기 위해, 로컬 네트워크에서는 다음 홉의 MAC 주소를 알아야 한다. 예를 들어 같은 LAN에 있는 서버로 통신한다면 서버의 MAC 주소가 필요하고, 외부 인터넷으로 나간다면 기본 게이트웨이의 MAC 주소가 필요하다. 이때 DNS와 ARP가 각각 이름 해석과 주소 해석 역할을 수행한다.

DNS가 없다면 사용자는 복잡한 IP 주소를 직접 기억해야 하며, IP가 변경될 때마다 접속 정보도 수정해야 한다. ARP가 없다면 IP 기반 통신을 실제 이더넷 프레임 전달과 연결하기 어렵다. 즉, DNS는 “이름 → IP” 변환을, ARP는 “IP → MAC” 변환을 담당하며, 두 기술은 TCP/IP 네트워크가 실질적으로 동작하기 위한 기반 요소다.

RARP는 ARP의 반대 개념으로, MAC 주소를 기반으로 IP 주소를 알아내기 위해 사용되던 프로토콜이다. 과거 디스크 없는 워크스테이션이 부팅 시 자신의 IP 주소를 얻기 위해 사용했으나, 현재 일반적인 환경에서는 DHCP가 그 역할을 대체한다. 따라서 현대 네트워크를 이해할 때는 DNS, ARP, DHCP의 관계를 함께 파악하는 것이 중요하다.

## 내부 동작 원리

## 1. DNS 작동 원리

DNS는 계층적이고 분산된 이름 해석 시스템이다. 도메인 이름은 오른쪽에서 왼쪽으로 계층 구조를 가진다.

예:

```text
www.example.com.
 └─ 루트(.)
    └─ com
       └─ example
          └─ www
```

DNS 질의는 보통 다음 순서로 진행된다.

```text
[사용자 브라우저]
      |
      v
[OS Stub Resolver]
      |
      v
[Recursive DNS Resolver]
      |
      v
[Root DNS Server]
      |
      v
[TLD DNS Server: .com]
      |
      v
[Authoritative DNS Server: example.com]
      |
      v
[IP 주소 응답]
```

### DNS 질의 과정

1. 사용자가 브라우저에 `www.example.com` 입력
2. 브라우저 또는 OS가 로컬 DNS 캐시 확인
3. 캐시에 없으면 OS의 Stub Resolver가 Recursive Resolver에 질의
4. Recursive Resolver가 루트 DNS 서버에 질의
5. 루트 서버는 `.com` TLD 서버 정보를 응답
6. Recursive Resolver가 `.com` TLD 서버에 질의
7. TLD 서버는 `example.com`의 권한 있는 DNS 서버 정보를 응답
8. Recursive Resolver가 권한 있는 DNS 서버에 질의
9. 권한 있는 DNS 서버가 `www.example.com`의 IP 주소 응답
10. Recursive Resolver는 결과를 캐싱하고 클라이언트에 전달
11. 클라이언트는 해당 IP 주소로 TCP 또는 UDP 통신 시작

### Recursive Query와 Iterative Query

DNS 질의에는 크게 두 가지 방식이 있다.

- **Recursive Query**
  - 클라이언트가 DNS 서버에게 “최종 답을 찾아서 알려달라”고 요청하는 방식
  - 일반적으로 클라이언트 → Recursive Resolver 구간에서 사용

- **Iterative Query**
  - DNS 서버가 “나는 최종 답은 모르지만 다음에 물어볼 서버는 안다”고 응답하는 방식
  - Recursive Resolver → Root/TLD/Authoritative 서버 구간에서 주로 사용

### 주요 DNS 레코드

| 레코드 | 의미 |
|---|---|
| A | 도메인을 IPv4 주소로 매핑 |
| AAAA | 도메인을 IPv6 주소로 매핑 |
| CNAME | 별칭 도메인을 실제 도메인으로 매핑 |
| MX | 메일 서버 지정 |
| NS | 권한 있는 네임서버 지정 |
| TXT | 텍스트 정보 저장, SPF/DKIM 등에도 사용 |
| PTR | IP 주소를 도메인 이름으로 역방향 조회 |

### DNS 캐싱과 TTL

DNS 응답에는 TTL(Time To Live)이 포함된다. TTL은 해당 DNS 응답을 캐시에 얼마나 오래 저장할 수 있는지를 나타낸다. TTL이 길면 DNS 서버 부하가 줄고 응답 속도가 빨라지지만, IP 변경 사항이 반영되는 데 시간이 더 걸릴 수 있다. TTL이 짧으면 변경 반영은 빠르지만 DNS 질의가 더 자주 발생할 수 있다.

## 2. ARP 작동 원리

ARP(Address Resolution Protocol)는 IPv4 네트워크에서 IP 주소에 대응하는 MAC 주소를 찾는 프로토콜이다. 이더넷 환경에서 실제 프레임 전달은 MAC 주소 기반으로 이루어지므로, IP 패킷을 보내기 전에 다음 홉의 MAC 주소를 알아야 한다.

예를 들어 호스트 A가 같은 LAN의 호스트 B에게 통신하려고 한다.

```text
Host A
IP: 192.168.1.10
MAC: AA:AA:AA:AA:AA:AA

Host B
IP: 192.168.1.20
MAC: BB:BB:BB:BB:BB:BB
```

ARP 과정은 다음과 같다.

```text
1) Host A → Broadcast
   "192.168.1.20의 MAC 주소를 아는가?"

2) LAN 내 모든 호스트가 수신

3) Host B → Unicast
   "192.168.1.20은 BB:BB:BB:BB:BB:BB이다."

4) Host A는 ARP Cache에 저장

5) 이후 Host A는 Host B의 MAC 주소로 이더넷 프레임 전송
```

ARP Request는 브로드캐스트로 전송된다.

```text
Destination MAC: FF:FF:FF:FF:FF:FF
Source MAC:      AA:AA:AA:AA:AA:AA
내용: "192.168.1.20의 MAC 주소는?"
```

ARP Reply는 일반적으로 유니캐스트로 전송된다.

```text
Destination MAC: AA:AA:AA:AA:AA:AA
Source MAC:      BB:BB:BB:BB:BB:BB
내용: "192.168.1.20 = BB:BB:BB:BB:BB:BB"
```

### 다른 네트워크로 통신할 때

목적지 IP가 같은 서브넷에 없으면, 호스트는 목적지 서버의 MAC 주소를 직접 찾지 않는다. 대신 기본 게이트웨이의 MAC 주소를 ARP로 찾고, 이더넷 프레임의 목적지 MAC을 게이트웨이 MAC으로 설정한다.

```text
[Host A] --LAN-- [Default Gateway] --Internet-- [Remote Server]

IP 패킷 목적지: Remote Server IP
이더넷 프레임 목적지 MAC: Default Gateway MAC
```

중요한 점은 IP 패킷의 목적지 IP는 최종 서버 주소로 유지되지만, 각 링크 구간의 이더넷 프레임 목적지 MAC 주소는 다음 홉에 맞게 계속 바뀐다는 것이다.

## 3. RARP 작동 원리

RARP(Reverse ARP)는 MAC 주소를 이용해 IP 주소를 알아내는 프로토콜이다. 개념적으로는 ARP의 반대 방향이다.

```text
ARP:
IP 주소 → MAC 주소

RARP:
MAC 주소 → IP 주소
```

RARP는 과거 디스크 없는 시스템이 네트워크 부팅 시 자신의 IP 주소를 얻기 위해 사용되었다. 클라이언트는 자신의 MAC 주소를 기반으로 RARP 서버에 IP 주소를 요청한다.

```text
[RARP Client]
MAC: AA:AA:AA:AA:AA:AA
      |
      | "내 MAC 주소에 해당하는 IP는?"
      v
[RARP Server]
      |
      | "192.168.1.10을 사용하라"
      v
[RARP Client]
```

하지만 RARP는 같은 물리 네트워크 내에서 동작해야 하고, 제공 가능한 설정 정보가 제한적이다. 현대 네트워크에서는 IP 주소뿐 아니라 서브넷 마스크, 기본 게이트웨이, DNS 서버 등 다양한 네트워크 설정을 함께 제공할 수 있는 DHCP가 일반적으로 사용된다.

## 4. MAC 주소와 IP 주소의 차이

| 구분 | MAC 주소 | IP 주소 |
|---|---|---|
| 계층 | 데이터 링크 계층 | 네트워크 계층 |
| 목적 | 같은 링크 내 프레임 전달 | 네트워크 간 패킷 라우팅 |
| 범위 | 로컬 네트워크 중심 | 전역 또는 사설 네트워크 |
| 변경 가능성 | NIC에 할당되지만 소프트웨어적으로 변경 가능 | 네트워크 설정에 따라 변경 가능 |
| 예시 | `00:1A:2B:3C:4D:5E` | `192.168.1.10`, `2001:db8::1` |
| 관련 프로토콜 | Ethernet, ARP | IP, ICMP, TCP, UDP |

MAC 주소는 같은 LAN 안에서 “누구에게 프레임을 전달할 것인가”를 결정하는 데 사용된다. IP 주소는 라우터를 거쳐 다른 네트워크로 이동할 때 “최종 목적지는 어디인가”를 나타낸다.

패킷이 라우터를 통과할 때 IP 주소는 일반적으로 최종 목적지를 유지하지만, MAC 주소는 링크마다 다음 홉의 MAC 주소로 변경된다.

```text
Host A → Router 1 → Router 2 → Server

구간 1:
Src MAC = Host A
Dst MAC = Router 1
Src IP  = Host A
Dst IP  = Server

구간 2:
Src MAC = Router 1
Dst MAC = Router 2
Src IP  = Host A
Dst IP  = Server

구간 3:
Src MAC = Router 2
Dst MAC = Server
Src IP  = Host A
Dst IP  = Server
```

## 실제 시스템 연결

## Linux에서 DNS 확인

Linux에서는 `/etc/resolv.conf` 파일을 통해 DNS Resolver 설정을 확인할 수 있다.

```bash
cat /etc/resolv.conf
```

예시:

```text
nameserver 8.8.8.8
nameserver 1.1.1.1
```

단, 현대 Linux 배포판에서는 `systemd-resolved`, NetworkManager, DHCP 클라이언트 등이 `/etc/resolv.conf`를 동적으로 관리할 수 있다.

DNS 조회는 다음 도구로 확인할 수 있다.

```bash
dig www.example.com
nslookup www.example.com
host www.example.com
```

`dig` 사용 예:

```bash
dig www.example.com A
```

확인할 수 있는 주요 정보:

- 질의한 레코드 타입
- 응답 IP 주소
- TTL
- 응답한 DNS 서버
- 권한 응답 여부
- 질의 시간

로컬 호스트 이름 해석에는 `/etc/hosts`도 관여한다.

```bash
cat /etc/hosts
```

예:

```text
127.0.0.1 localhost
192.168.1.100 internal-api.local
```

일반적으로 Linux의 이름 해석 순서는 `/etc/nsswitch.conf`의 `hosts` 항목에 영향을 받는다.

```bash
cat /etc/nsswitch.conf
```

예:

```text
hosts: files dns
```

이 경우 `/etc/hosts`를 먼저 확인하고, 없으면 DNS를 조회한다.

## Linux에서 ARP 확인

Linux에서는 ARP 캐시 또는 Neighbor Table을 확인할 수 있다.

```bash
ip neigh
```

예:

```text
192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
```

기존 명령으로는 다음도 사용된다.

```bash
arp -n
```

하지만 `arp` 명령은 일부 환경에서 오래된 net-tools 패키지에 포함되어 있으며, 현대 Linux에서는 `ip neigh` 사용이 권장되는 경우가 많다.

ARP 캐시를 삭제하려면 다음과 같이 할 수 있다.

```bash
sudo ip neigh flush all
```

특정 인터페이스에서 ARP 패킷을 관찰하려면 `tcpdump`를 사용할 수 있다.

```bash
sudo tcpdump -i eth0 arp
```

예상되는 출력 형태:

```text
ARP, Request who-has 192.168.1.20 tell 192.168.1.10
ARP, Reply 192.168.1.20 is-at bb:bb:bb:bb:bb:bb
```

## Nginx와 DNS

Nginx는 업스트림 서버를 도메인 이름으로 지정할 수 있다.

```nginx
upstream backend {
    server api.example.com:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

주의할 점은 Nginx의 DNS 해석 시점과 캐싱 동작이 설정 방식에 따라 달라질 수 있다는 것이다. 컨테이너나 Kubernetes처럼 백엔드 IP가 자주 변하는 환경에서는 Nginx의 DNS 재해석 동작을 고려해야 한다.

예를 들어 `resolver` 지시어를 사용해 런타임 DNS 조회를 명시할 수 있다.

```nginx
resolver 127.0.0.11 valid=10s;
```

Docker 컨테이너 환경에서는 `127.0.0.11`이 Docker 내장 DNS 서버로 사용되는 경우가 있다.

## AWS에서 DNS와 주소 변환

AWS에서는 Route 53이 관리형 DNS 서비스로 사용된다. Route 53을 통해 도메인 이름을 AWS 리소스에 연결할 수 있다.

예:

- 도메인 → Application Load Balancer
- 도메인 → CloudFront 배포
- 도메인 → S3 정적 웹사이트 엔드포인트
- 도메인 → EC2 Public IP 또는 Elastic IP

AWS VPC 내부에서는 프라이빗 DNS 이름과 프라이빗 IP 주소가 사용된다. EC2 인스턴스는 VPC DNS Resolver를 통해 내부 리소스 이름을 해석할 수 있다.

AWS 보안 그룹은 IP와 포트 기준으로 트래픽을 제어한다. 반면 같은 서브넷 내의 실제 이더넷 수준 전달은 AWS 인프라 내부에서 추상화되어 있으며, 사용자가 일반적인 물리 LAN의 ARP 동작을 직접 제어하지는 않는다.

⚠️ 확인 필요: AWS의 특정 가상 네트워크 구현 세부사항은 리전, 인스턴스 유형, 네트워크 가상화 기술 세대에 따라 공개 범위와 동작 세부가 다를 수 있다.

## GCP에서 DNS

GCP에서는 Cloud DNS를 통해 관리형 DNS 존을 운영할 수 있다. 또한 VPC 내부 리소스는 내부 DNS 이름을 통해 접근할 수 있다.

예:

```text
vm-name.zone.c.project-id.internal
```

⚠️ 확인 필요: GCP 내부 DNS 이름의 정확한 형식과 동작은 프로젝트 설정, VPC 설정, 문서 업데이트에 따라 달라질 수 있으므로 실제 운영 환경에서는 공식 문서를 확인해야 한다.

## Docker와 DNS

Docker는 사용자 정의 브리지 네트워크에서 컨테이너 이름 기반 DNS 해석을 제공한다. 같은 Docker 네트워크에 속한 컨테이너는 컨테이너 이름 또는 서비스 이름으로 서로를 찾을 수 있다.

예:

```bash
docker network create app-net

docker run -d --name redis --network app-net redis
docker run -it --name app --network app-net alpine sh
```

`app` 컨테이너 안에서:

```bash
ping redis
```

이때 `redis`라는 이름이 해당 컨테이너의 IP 주소로 해석된다.

Docker 기본 bridge 네트워크와 사용자 정의 bridge 네트워크의 DNS 동작은 차이가 있다. 일반적으로 컨테이너 이름 기반 자동 DNS는 사용자 정의 bridge 네트워크에서 더 명확하게 지원된다.

---

## Docker와 ARP/MAC

컨테이너는 가상 이더넷 인터페이스를 통해 네트워크에 연결된다. Linux에서는 보통 veth pair, bridge, network namespace 등을 사용해 컨테이너 네트워크를 구성한다.

개념적 구조:

```text
[Container eth0]
      |
   veth pair
      |
[Host docker bridge]
      |
[Host NIC]
      |
[External Network]
```

컨테이너 내부에도 IP 주소와 MAC 주소가 있으며, 같은 브리지 네트워크 내 컨테이너 간 통신에서는 ARP가 사용될 수 있다. 다만 Docker 네트워크 드라이버, 오버레이 네트워크, 클라우드 CNI 환경에서는 실제 L2 동작이 추상화될 수 있다.

## Kubernetes DNS

Kubernetes에서는 Service와 Pod 이름을 DNS로 해석할 수 있다. 일반적으로 CoreDNS가 클러스터 DNS 역할을 수행한다.

예:

```text
my-service.default.svc.cluster.local
```

Pod에서 위 이름을 조회하면 Kubernetes Service의 ClusterIP로 해석된다.

```text
[Pod]
  |
  | DNS Query: my-service.default.svc.cluster.local
  v
[CoreDNS]
  |
  | Service ClusterIP 응답
  v
[Pod]
```

Kubernetes DNS는 서비스 디스커버리의 핵심이다. Pod IP는 생성과 삭제에 따라 변할 수 있지만, Service 이름은 안정적인 접근 지점을 제공한다.

---

## Kubernetes와 ARP

Kubernetes에서 Pod 간 통신은 CNI(Container Network Interface) 플러그인에 의해 구현된다. 플러그인에 따라 L2 기반, 라우팅 기반, 오버레이 터널링 기반 방식이 사용될 수 있다.

예:

- Flannel
- Calico
- Cilium
- Weave Net

⚠️ 확인 필요: 각 CNI의 ARP 처리 방식, encapsulation 방식, eBPF 사용 여부는 버전과 설정에 따라 달라질 수 있다.

Kubernetes Service는 iptables, IPVS, eBPF 등의 방식으로 트래픽을 Pod로 전달할 수 있다. 이 과정에서 사용자는 보통 개별 Pod의 MAC 주소를 직접 다루지 않는다.

## AWS Route 53과 DNS

AWS Route 53은 퍼블릭 DNS와 프라이빗 DNS를 모두 제공할 수 있다. 주요 사용 사례는 다음과 같다.

- Public Hosted Zone: 인터넷에서 접근 가능한 도메인 관리
- Private Hosted Zone: VPC 내부에서만 해석되는 도메인 관리
- Health Check 기반 장애 조치
- Latency-based Routing
- Weighted Routing
- Geolocation Routing

예:

```text
api.example.com
  └─ ALIAS → Application Load Balancer
```

AWS Route 53의 ALIAS 레코드는 AWS 리소스에 도메인을 연결할 때 자주 사용된다. 일반 CNAME과 달리 루트 도메인에도 사용할 수 있다는 장점이 있다.

## AWS VPC와 DNS Resolver

AWS VPC에는 DNS 해석과 관련된 설정이 있다.

- DNS resolution
- DNS hostnames

이 설정을 통해 VPC 내부에서 EC2 인스턴스의 DNS 이름 해석과 퍼블릭/프라이빗 DNS 사용 여부가 달라질 수 있다.

또한 Route 53 Resolver를 사용하면 온프레미스 DNS와 AWS VPC DNS를 연결할 수 있다.

예:

```text
[On-Prem DNS]
      |
      v
[Route 53 Resolver Inbound Endpoint]
      |
      v
[AWS Private Hosted Zone]
```

반대로 AWS에서 온프레미스 DNS로 질의를 전달하려면 Outbound Endpoint와 Resolver Rule을 사용할 수 있다.

## 보안 연결

## DNS 보안 이슈

DNS는 인터넷의 핵심 인프라이지만, 기본 DNS 프로토콜은 응답의 진위를 강하게 검증하지 않는다. 따라서 여러 보안 문제가 발생할 수 있다.

### 1. DNS Spoofing / Cache Poisoning

공격자가 조작된 DNS 응답을 주입하여 사용자를 악성 IP로 유도하는 공격이다.

```text
사용자: bank.example.com 접속
공격자: bank.example.com = 악성 서버 IP
사용자: 악성 서버로 접속
```

대응 방안:

- DNSSEC 사용 검토
- 신뢰할 수 있는 Recursive Resolver 사용
- DNS 응답 검증 기능 사용
- 중요 도메인의 레코드 변경 모니터링
- HTTPS 인증서 검증을 통한 추가 보호

### 2. DNSSEC

DNSSEC은 DNS 응답에 전자서명을 추가하여 데이터 무결성과 출처 인증을 제공하는 기술이다. DNSSEC은 DNS 응답이 변조되지 않았는지 검증할 수 있게 한다.

단, DNSSEC은 통신 내용을 암호화하지 않는다. 즉, 누가 어떤 도메인을 조회하는지는 별도 보호가 없다. DNS 질의의 기밀성을 보호하려면 DoT(DNS over TLS) 또는 DoH(DNS over HTTPS) 같은 기술을 고려할 수 있다.

### 3. DNS Tunneling

DNS 질의와 응답을 이용해 데이터를 은닉 전송하는 기법이다. 악성코드가 방화벽을 우회하여 명령 제어 서버와 통신할 때 사용될 수 있다.

대응 방안:

- 비정상적으로 긴 서브도메인 탐지
- TXT 레코드 과다 사용 탐지
- 외부 DNS 직접 질의 제한
- 내부 DNS Resolver 강제 사용
- DNS 로그 분석

### 4. Subdomain Takeover

CNAME이 더 이상 사용하지 않는 외부 서비스 도메인을 가리킬 때, 공격자가 해당 외부 리소스를 점유해 서브도메인을 탈취하는 공격이다.

대응 방안:

- 사용하지 않는 DNS 레코드 정리
- 클라우드 리소스 삭제 전 DNS 레코드 제거
- 외부 SaaS 연결 레코드 주기 점검
- 와일드카드 DNS 사용 최소화

## ARP 보안 이슈

ARP는 인증 절차가 없는 프로토콜이다. 같은 LAN에 있는 공격자가 거짓 ARP Reply를 보내면 다른 호스트의 ARP 캐시가 오염될 수 있다.

### 1. ARP Spoofing / ARP Poisoning

공격자가 자신을 게이트웨이로 속이는 예:

```text
정상:
Host A → Gateway MAC

공격 후:
Host A → Attacker MAC
Attacker → Gateway
```

이 경우 공격자는 중간자 공격(MITM)을 수행할 수 있다.

가능한 피해:

- 트래픽 도청
- 세션 탈취
- 악성 페이지 삽입
- 통신 차단
- DNS 응답 조작과 결합한 피싱

대응 방안:

- 스위치의 Dynamic ARP Inspection 사용
- DHCP Snooping과 연계
- 정적 ARP 설정 사용
- 네트워크 세그멘테이션
- HTTPS, SSH 등 암호화 프로토콜 사용
- 비정상 ARP 트래픽 모니터링

### 2. Gratuitous ARP 악용

Gratuitous ARP는 호스트가 자신의 IP-MAC 매핑을 네트워크에 알리기 위해 사용하는 ARP 메시지다. 정상적으로는 IP 충돌 감지, HA 구성, MAC 테이블 갱신 등에 사용될 수 있다. 하지만 공격자가 이를 악용하면 ARP 캐시를 조작할 수 있다.

대응 방안:

- ARP 변경 이벤트 모니터링
- 중요 서버에 정적 ARP 고려
- 스위치 보안 기능 활성화
- 불필요한 L2 브로드캐스트 도메인 축소

---

## MAC 주소 관련 보안

MAC 주소는 네트워크 인터페이스 식별에 사용되지만 절대적인 인증 수단으로 신뢰해서는 안 된다. 많은 운영체제에서 MAC 주소는 소프트웨어적으로 변경할 수 있다.

### MAC Spoofing

공격자가 허용된 MAC 주소로 위장하는 공격이다.

대응 방안:

- MAC 필터링만으로 보안 설계하지 않기
- 802.1X 기반 네트워크 접근 제어 사용
- 포트 보안 기능 사용
- NAC(Network Access Control) 도입
- 로그 기반 이상 징후 탐지

---

## IP 주소 관련 보안

IP 주소도 신뢰의 단독 기준으로 사용하기 어렵다. 사설망 내부에서는 IP 기반 접근 제어가 자주 사용되지만, IP 스푸핑, NAT, 프록시, 클라우드 환경의 동적 IP 변경 등을 고려해야 한다.

대응 방안:

- IP Allowlist는 보조 수단으로 사용
- 인증과 인가를 별도로 강제
- mTLS, VPN, Zero Trust 접근 모델 검토
- 보안 그룹과 NACL의 최소 권한 원칙 적용
- 내부망도 신뢰하지 않는 설계 적용

---

## 클라우드 환경 보안 모범 사례

클라우드에서는 전통적 L2 네트워크가 많이 추상화된다. 하지만 DNS 보안은 여전히 중요하다.

모범 사례:

- Route 53 Hosted Zone 변경 권한 최소화
- DNS 레코드 변경에 대한 감사 로그 활성화
- 도메인 등록 계정 MFA 적용
- 중요 도메인 DNSSEC 적용 검토
- 내부 Private Hosted Zone 권한 분리
- Kubernetes CoreDNS 설정 변경 권한 제한
- 외부 DNS로의 직접 질의 통제
- 컨테이너 이미지 내 악성 DNS 설정 점검
- `/etc/hosts` 변조 탐지
- DNS 로그 기반 이상 행위 탐지

## 면접 질문

**Q1. DNS가 도메인 이름을 IP 주소로 변환하는 과정을 설명해주세요.**  
> 핵심 답변: 클라이언트는 먼저 로컬 캐시와 OS Resolver를 확인한다. 캐시에 없으면 Recursive Resolver에 질의한다. Recursive Resolver는 Root DNS, TLD DNS, Authoritative DNS를 순차적으로 조회하여 최종 IP 주소를 얻고, 결과를 캐싱한 뒤 클라이언트에 응답한다.

**Q2. ARP는 왜 필요한가요?**  
> 핵심 답변: IP 주소는 네트워크 계층의 논리 주소이고, 이더넷 프레임 전달에는 MAC 주소가 필요하다. 같은 LAN에서 IP 패킷을 실제 프레임으로 전송하려면 목적지 또는 다음 홉의 MAC 주소를 알아야 하며, ARP가 IP 주소를 MAC 주소로 변환한다.

**Q3. 목적지 서버가 다른 네트워크에 있을 때 ARP는 어떤 MAC 주소를 찾나요?**  
> 핵심 답변: 최종 목적지 서버의 MAC 주소가 아니라 기본 게이트웨이의 MAC 주소를 찾는다. IP 패킷의 목적지 IP는 최종 서버로 유지되지만, 이더넷 프레임의 목적지 MAC은 다음 홉인 게이트웨이의 MAC 주소가 된다.

**Q4. MAC 주소와 IP 주소의 차이는 무엇인가요?**  
> 핵심 답변: MAC 주소는 데이터 링크 계층에서 같은 링크 내 프레임 전달에 사용되고, IP 주소는 네트워크 계층에서 네트워크 간 라우팅에 사용된다. 라우터를 지날 때 MAC 주소는 홉마다 바뀌지만, IP 주소는 일반적으로 최종 출발지와 목적지를 유지한다.

**Q5. ARP Spoofing이 무엇이고 어떻게 방어할 수 있나요?**  
> 핵심 답변: 공격자가 거짓 ARP 응답을 보내 다른 호스트의 ARP 캐시를 오염시키는 공격이다. 이를 통해 중간자 공격이 가능하다. 방어 방법으로는 Dynamic ARP Inspection, DHCP Snooping, 정적 ARP, 네트워크 분리, HTTPS/SSH 같은 암호화 통신 사용, ARP 모니터링이 있다.

## 관련 개념

- [[DNS]] - 도메인 이름을 IP 주소로 변환하는 핵심 시스템
- [[ARP]] - IPv4 주소를 MAC 주소로 변환하는 데이터 링크 계층 보조 프로토콜
- [[RARP]] - MAC 주소를 기반으로 IP 주소를 얻기 위한 과거 프로토콜
- [[DHCP]] - 현대 네트워크에서 IP 주소와 네트워크 설정을 자동 할당하는 프로토콜
- [[MAC 주소]] - LAN 내 프레임 전달에 사용되는 데이터 링크 계층 주소
- [[IP 주소]] - 네트워크 간 라우팅을 위한 논리 주소
- [[라우팅]] - IP 패킷을 목적지 네트워크까지 전달하는 과정
- [[이더넷]] - MAC 주소 기반 프레임 전달을 제공하는 대표적인 링크 계층 기술
- [[NAT]] - 사설 IP와 공인 IP 간 주소 변환 기술
- [[DNSSEC]] - DNS 응답의 무결성과 출처 인증을 제공하는 보안 확장
- [[DoH]] - HTTPS를 통해 DNS 질의를 전송하여 기밀성을 높이는 방식
- [[DoT]] - TLS를 통해 DNS 질의를 보호하는 방식
- [[Kubernetes Service]] - 동적으로 변하는 Pod 집합에 안정적인 네트워크 접근점을 제공
- [[CoreDNS]] - Kubernetes에서 주로 사용되는 클러스터 DNS 서버
- [[Route 53]] - AWS의 관리형 DNS 서비스
- [[VPC]] - 클라우드 환경에서 논리적으로 격리된 가상 네트워크
- [[Subnet]] - IP 네트워크를 더 작은 네트워크 단위로 나눈 것
- [[Default Gateway]] - 외부 네트워크로 나가는 패킷의 다음 홉 역할을 하는 장비
- [[ARP Spoofing]] - 거짓 ARP 정보를 이용해 트래픽을 가로채는 공격
- [[DHCP Snooping]] - DHCP 메시지를 감시하여 비인가 DHCP 서버와 ARP 공격을 방어하는 스위치 보안 기능
