# 연결 설정 - 3-way Handshake (연결), 4-way Handshake (해제)

## 핵심 개념

TCP의 **3-way Handshake**는 클라이언트와 서버가 데이터를 주고받기 전에 신뢰성 있는 연결을 설정하기 위해 수행하는 절차이다. TCP는 연결 지향 프로토콜이므로, 실제 애플리케이션 데이터 전송 전에 양쪽이 통신 가능 상태인지 확인하고, 초기 순서 번호인 **Initial Sequence Number, ISN**을 교환한다. 이 과정은 `SYN → SYN+ACK → ACK`의 세 단계로 이루어진다.

반대로 **4-way Handshake**는 TCP 연결을 종료할 때 사용되는 절차이다. TCP 연결은 양방향 통신이 가능하기 때문에, 한쪽이 더 이상 데이터를 보내지 않겠다고 선언하더라도 반대쪽은 아직 보낼 데이터가 남아 있을 수 있다. 따라서 연결 해제는 일반적으로 `FIN → ACK → FIN → ACK`의 네 단계로 이루어진다. 이를 통해 양쪽 송신 방향을 독립적으로 닫을 수 있다.

이 개념이 중요한 이유는 TCP 기반의 거의 모든 네트워크 서비스, 예를 들어 HTTP, HTTPS, SSH, MySQL, Redis, gRPC 등이 연결 설정과 해제 과정을 기반으로 동작하기 때문이다. 또한 장애 분석, 지연 시간 분석, SYN Flood 같은 보안 공격 대응, 서버의 `TIME_WAIT`, `CLOSE_WAIT` 상태 문제 해결에도 반드시 필요하다. 단순히 “연결된다” 또는 “끊어진다”가 아니라, 운영체제 커널 수준에서 상태 전이가 발생하며 이 상태가 서비스 안정성과 성능에 직접 영향을 준다.

## 내부 동작 원리

## 1. 3-way Handshake: TCP 연결 설정

TCP 연결 설정은 다음 세 단계로 이루어진다.

```text
Client                                      Server
  |                                           |
  |  1. SYN, seq = x                         |
  |------------------------------------------>|
  |                                           |
  |  2. SYN + ACK, seq = y, ack = x + 1       |
  |<------------------------------------------|
  |                                           |
  |  3. ACK, ack = y + 1                     |
  |------------------------------------------>|
  |                                           |
  |              ESTABLISHED                  |
```

### 단계별 설명

#### 1단계: Client → Server: SYN

클라이언트는 서버에 연결을 요청하기 위해 `SYN` 플래그가 설정된 TCP 세그먼트를 보낸다.

```text
SYN = 1
seq = x
```

여기서 `x`는 클라이언트의 초기 순서 번호, 즉 ISN이다. 이 시점에서 클라이언트의 TCP 상태는 일반적으로 `SYN_SENT`가 된다.

#### 2단계: Server → Client: SYN + ACK

서버는 클라이언트의 연결 요청을 수락할 수 있으면 `SYN`과 `ACK` 플래그가 모두 설정된 세그먼트를 보낸다.

```text
SYN = 1
ACK = 1
seq = y
ack = x + 1
```

`ack = x + 1`은 클라이언트가 보낸 SYN을 정상적으로 받았다는 의미다. TCP에서 SYN은 실제 데이터 바이트를 포함하지 않더라도 순서 번호 공간을 1만큼 소비한다.

서버의 상태는 일반적으로 `SYN_RECEIVED`가 된다.

#### 3단계: Client → Server: ACK

클라이언트는 서버의 SYN을 확인했다는 의미로 ACK를 보낸다.

```text
ACK = 1
ack = y + 1
```

이후 클라이언트와 서버는 모두 `ESTABLISHED` 상태가 되며, 애플리케이션 데이터를 주고받을 수 있다.

## 2. 4-way Handshake: TCP 연결 해제

TCP 연결 종료는 보통 다음과 같이 진행된다.

```text
Client                                      Server
  |                                           |
  |  1. FIN, seq = u                         |
  |------------------------------------------>|
  |                                           |
  |  2. ACK, ack = u + 1                     |
  |<------------------------------------------|
  |                                           |
  |        Client는 더 이상 송신하지 않음       |
  |        Server는 아직 송신 가능             |
  |                                           |
  |  3. FIN, seq = v                         |
  |<------------------------------------------|
  |                                           |
  |  4. ACK, ack = v + 1                     |
  |------------------------------------------>|
  |                                           |
  |              CLOSED                       |
```

### 단계별 설명

#### 1단계: 연결 종료 요청 측 → FIN

먼저 연결을 종료하려는 쪽이 `FIN` 플래그가 설정된 세그먼트를 보낸다.

```text
FIN = 1
seq = u
```

FIN은 “나는 더 이상 보낼 데이터가 없다”는 의미다. 단, 이것은 해당 방향의 송신 종료를 의미하며, 반대 방향의 데이터 수신은 계속 가능하다. 이 상태를 **Half-Close**라고도 한다.

#### 2단계: 상대방 → ACK

상대방은 FIN을 받았다는 의미로 ACK를 보낸다.

```text
ACK = 1
ack = u + 1
```

FIN 역시 SYN과 마찬가지로 순서 번호 공간을 1만큼 소비한다.

#### 3단계: 상대방 → FIN

상대방도 더 이상 보낼 데이터가 없으면 FIN을 보낸다.

```text
FIN = 1
seq = v
```

#### 4단계: 최초 종료 요청 측 → ACK

최초 종료 요청 측은 상대방의 FIN을 확인하고 ACK를 보낸다.

```text
ACK = 1
ack = v + 1
```

이후 최초 종료 요청 측은 일반적으로 `TIME_WAIT` 상태에 들어간다.

## 3. TCP 상태 전이

대표적인 TCP 상태는 다음과 같다.

```text
연결 설정:
CLOSED → SYN_SENT → ESTABLISHED
CLOSED → LISTEN → SYN_RECEIVED → ESTABLISHED

연결 종료:
ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

### 주요 상태 설명

- `LISTEN`: 서버가 연결 요청을 기다리는 상태
- `SYN_SENT`: 클라이언트가 SYN을 보내고 SYN+ACK을 기다리는 상태
- `SYN_RECEIVED`: 서버가 SYN을 받고 SYN+ACK을 보낸 상태
- `ESTABLISHED`: TCP 연결이 성립된 상태
- `FIN_WAIT_1`: FIN을 보낸 뒤 ACK 또는 FIN을 기다리는 상태
- `FIN_WAIT_2`: 자신의 FIN에 대한 ACK를 받은 뒤, 상대방의 FIN을 기다리는 상태
- `CLOSE_WAIT`: 상대방의 FIN을 받은 뒤, 애플리케이션이 소켓을 닫기를 기다리는 상태
- `LAST_ACK`: FIN을 보낸 뒤 마지막 ACK를 기다리는 상태
- `TIME_WAIT`: 마지막 ACK를 보낸 쪽이 일정 시간 동안 대기하는 상태

## 4. 왜 연결 설정은 3단계이고, 해제는 보통 4단계인가?

연결 설정에서는 양쪽 모두 통신 의사를 동시에 확인해야 한다.

```text
Client: 연결하고 싶다
Server: 나도 가능하다
Client: 확인했다
```

따라서 최소 3단계가 필요하다.

반면 연결 해제는 양방향 스트림을 각각 닫아야 한다. 한쪽이 FIN을 보냈다고 해서 상대방도 즉시 보낼 데이터가 없는 것은 아니다. 따라서 한쪽 송신 종료에 대한 ACK와, 반대쪽 송신 종료를 알리는 FIN이 분리될 수 있다.

다만 실제 패킷에서는 상대방이 FIN을 보내는 시점에 ACK도 함께 포함될 수 있다. 따라서 항상 물리적으로 4개의 패킷이 오가는 것은 아니며, 상황에 따라 FIN과 ACK가 하나의 세그먼트로 합쳐질 수 있다.

## 실제 시스템 연결

## 1. Linux에서 확인하기

Linux에서는 TCP 연결 상태를 `ss`, `netstat`, `tcpdump` 등으로 확인할 수 있다.

### `ss` 명령어

```bash
ss -tan
```

예시 출력 형태:

```text
State       Recv-Q Send-Q Local Address:Port  Peer Address:Port
ESTAB       0      0      10.0.0.10:443       10.0.0.20:53124
TIME-WAIT   0      0      10.0.0.10:443       10.0.0.20:53120
LISTEN      0      128    0.0.0.0:80          0.0.0.0:*
```

여기서 `ESTAB`은 연결이 성립된 상태, `TIME-WAIT`은 TCP 종료 후 대기 상태, `LISTEN`은 서버가 연결 요청을 기다리는 상태를 의미한다.

### `tcpdump`로 Handshake 확인

```bash
sudo tcpdump -i eth0 tcp port 80
```

3-way Handshake는 다음과 같은 흐름으로 관찰된다.

```text
Client > Server: Flags [S]
Server > Client: Flags [S.]
Client > Server: Flags [.]
```

`[S]`는 SYN, `[S.]`는 SYN+ACK, `[.]`는 ACK를 의미한다.

4-way Handshake는 다음과 유사하게 나타난다.

```text
Client > Server: Flags [F.]
Server > Client: Flags [.]
Server > Client: Flags [F.]
Client > Server: Flags [.]
```

`[F.]`는 FIN+ACK를 의미한다.

## 2. Nginx와 TCP 연결

Nginx는 클라이언트의 HTTP 요청을 처리하기 전에 먼저 TCP 연결을 수립한다. HTTP/1.1의 Keep-Alive가 활성화되어 있으면 하나의 TCP 연결에서 여러 HTTP 요청과 응답을 처리할 수 있다.

예를 들어 브라우저가 Nginx 서버에 HTTPS 요청을 보낼 때 흐름은 일반적으로 다음과 같다.

```text
TCP 3-way Handshake
→ TLS Handshake
→ HTTP Request
→ HTTP Response
→ TCP 연결 유지 또는 종료
```

즉, HTTPS에서는 TCP 연결 설정 이후에 TLS Handshake가 추가로 수행된다.

Nginx 설정 중 연결 유지와 관련된 대표적인 설정은 다음과 같다.

```nginx
keepalive_timeout 65;
```

이 설정은 HTTP Keep-Alive 연결을 얼마나 유지할지에 영향을 준다. 다만 실제 연결 종료 시점은 클라이언트, 서버 설정, 프록시, 로드 밸런서, 네트워크 장비의 정책에 따라 달라질 수 있다.

## 3. Linux 서버에서 자주 보는 문제

### `TIME_WAIT`이 많은 경우

`TIME_WAIT`은 비정상 상태가 아니라 TCP의 정상적인 종료 과정에서 나타나는 상태다. 마지막 ACK가 손실되었을 가능성에 대비하고, 이전 연결의 지연된 패킷이 같은 4-tuple 연결에 영향을 주지 않도록 일정 시간 대기한다.

TCP 연결의 4-tuple은 다음으로 구성된다.

```text
Source IP
Source Port
Destination IP
Destination Port
```

짧은 연결을 매우 많이 생성하는 서비스에서는 `TIME_WAIT`이 많이 보일 수 있다.

### `CLOSE_WAIT`이 많은 경우

`CLOSE_WAIT`은 상대방이 FIN을 보냈고, 로컬 애플리케이션이 아직 소켓을 닫지 않은 상태다. 이 상태가 장시간 많이 쌓이면 애플리케이션이 `close()`를 적절히 호출하지 않았거나, 연결 종료 처리가 지연되고 있을 가능성이 있다.

운영 관점에서 `CLOSE_WAIT` 누적은 애플리케이션 코드나 커넥션 관리 로직을 점검해야 하는 신호로 자주 해석된다.

## 4. 데이터베이스와 TCP 연결

MySQL, PostgreSQL, Redis 같은 데이터베이스도 일반적으로 TCP 연결을 사용한다. 애플리케이션이 매 요청마다 DB 연결을 새로 만들면 매번 3-way Handshake 비용이 발생한다. 이를 줄이기 위해 커넥션 풀을 사용한다.

```text
애플리케이션 요청
→ 커넥션 풀에서 기존 TCP 연결 재사용
→ DB 쿼리 수행
→ 연결을 닫지 않고 풀에 반환
```

커넥션 풀은 TCP Handshake 비용, 인증 비용, TLS 사용 시 TLS Handshake 비용을 줄이는 데 도움이 된다.

## 클라우드 연결

## 1. Docker와 TCP Handshake

Docker 컨테이너 내부의 애플리케이션도 일반적으로 호스트 커널의 네트워크 스택을 통해 TCP 연결을 사용한다. 컨테이너가 브리지 네트워크를 사용할 경우, 컨테이너의 IP와 호스트의 NAT 규칙을 거쳐 외부와 통신할 수 있다.

예를 들어 다음과 같이 컨테이너 포트를 호스트에 매핑한다.

```bash
docker run -p 8080:80 nginx
```

이 경우 클라이언트가 호스트의 `8080` 포트로 접속하면, Docker 네트워크 설정을 통해 컨테이너의 `80` 포트로 전달된다. 이때 클라이언트와 서버 사이의 통신은 TCP 연결 설정 과정을 포함한다.

```text
Client
→ Host IP:8080
→ Docker NAT/port mapping
→ Container IP:80
→ Nginx
```

## 2. Kubernetes와 TCP 연결

Kubernetes에서 Service는 Pod 앞단에 안정적인 가상 엔드포인트를 제공한다. 클라이언트가 Service IP로 접속하면, kube-proxy 또는 CNI 구현에 따라 트래픽이 실제 Pod로 전달된다.

```text
Client Pod
→ Service ClusterIP
→ kube-proxy / iptables / IPVS 등
→ Target Pod
```

TCP 연결 관점에서 중요한 점은 다음과 같다.

- Pod가 재시작되면 기존 TCP 연결은 유지되지 않는다.
- Service는 L4 레벨에서 연결을 분산할 수 있다.
- Readiness Probe가 실패한 Pod는 Service Endpoint에서 제외될 수 있다.
- 장시간 유지되는 TCP 연결은 로드 밸런싱 변경의 영향을 즉시 받지 않을 수 있다.

예를 들어 HTTP Keep-Alive나 gRPC는 하나의 TCP 연결을 오래 유지할 수 있기 때문에, Pod 수가 늘어도 기존 연결은 기존 Pod에 남아 있을 수 있다.

## 3. AWS Load Balancer와 TCP 연결

AWS에서 TCP 연결은 사용 중인 로드 밸런서 유형에 따라 처리 방식이 다르다.

### Application Load Balancer, ALB

ALB는 주로 HTTP/HTTPS 트래픽을 처리하는 L7 로드 밸런서다. 클라이언트와 ALB 사이, ALB와 대상 서버 사이에 별도의 연결이 형성될 수 있다.

```text
Client ⇄ ALB ⇄ Target
```

즉 클라이언트가 대상 서버와 직접 하나의 TCP 연결을 유지하는 것이 아니라, ALB가 중간에서 연결을 종단하거나 프록시 역할을 한다.

### Network Load Balancer, NLB

NLB는 L4 로드 밸런서로 TCP, UDP 등의 트래픽을 처리할 수 있다. TCP 연결은 5-tuple 또는 flow 정보를 기반으로 대상에 분산된다.

```text
Client
→ NLB
→ Target EC2 또는 IP Target
```

로드 밸런서의 idle timeout, target deregistration, health check 설정은 TCP 연결 유지와 종료에 영향을 줄 수 있다.

⚠️ 확인 필요: AWS 서비스별 기본 idle timeout 값은 로드 밸런서 종류와 설정 시점에 따라 달라질 수 있으므로, 실제 운영 환경에서는 공식 문서와 현재 설정값을 확인해야 한다.

## 4. 클라우드 환경에서 자주 발생하는 연결 문제

### Idle Timeout

클라우드 로드 밸런서, NAT Gateway, 방화벽, 프록시 등은 유휴 TCP 연결을 일정 시간 후 종료할 수 있다. 애플리케이션은 연결이 살아 있다고 생각하지만 중간 장비가 이미 상태를 삭제한 경우, 다음 요청에서 오류가 발생할 수 있다.

대응 방법:

- TCP Keepalive 설정
- 애플리케이션 레벨 heartbeat
- 커넥션 풀의 max idle time 조정
- 로드 밸런서 idle timeout과 애플리케이션 timeout 정렬

### Ephemeral Port Exhaustion

클라이언트가 짧은 TCP 연결을 대량으로 생성하면 임시 포트가 고갈될 수 있다. 특히 NAT를 거치는 클라우드 환경에서는 여러 내부 인스턴스나 컨테이너의 연결이 제한된 외부 IP와 포트 공간을 공유할 수 있다.

대응 방법:

- 커넥션 재사용
- HTTP Keep-Alive 사용
- 커넥션 풀 사용
- NAT Gateway 또는 외부 IP 확장 검토
- 불필요한 짧은 연결 감소

## 보안 연결

## 1. SYN Flood 공격

SYN Flood는 TCP 3-way Handshake의 특성을 악용하는 대표적인 DoS 공격이다. 공격자는 대량의 SYN 패킷을 서버에 보내고, 마지막 ACK를 보내지 않거나 위조된 출발지 IP를 사용한다. 서버는 `SYN_RECEIVED` 상태의 반쯤 열린 연결을 유지해야 하므로, backlog 큐나 리소스가 고갈될 수 있다.

```text
Attacker → Server: SYN
Server → Spoofed IP: SYN+ACK
ACK 없음
Server: half-open connection 증가
```

### 대응 방법

- SYN Cookies 활성화
- 방화벽 또는 보안 그룹에서 비정상 트래픽 제한
- 로드 밸런서, CDN, DDoS 보호 서비스 사용
- TCP backlog 및 커널 파라미터 튜닝
- Rate limiting 적용

Linux에서는 SYN Cookies가 SYN Flood 완화에 사용될 수 있다.

```bash
sysctl net.ipv4.tcp_syncookies
```

⚠️ 확인 필요: 특정 배포판이나 커널 버전에 따라 기본값과 권장 튜닝 방식이 다를 수 있으므로 운영 환경에서는 현재 커널 문서와 배포판 가이드를 확인해야 한다.

---

## 2. TCP 연결 자체는 암호화되지 않는다

TCP는 신뢰성 있는 바이트 스트림을 제공하지만, 암호화나 인증을 제공하지 않는다. 따라서 TCP만 사용하면 중간자 공격, 패킷 스니핑, 세션 탈취 위험이 존재할 수 있다.

보안을 위해 일반적으로 TCP 위에 TLS를 사용한다.

```text
TCP 3-way Handshake
→ TLS Handshake
→ 암호화된 애플리케이션 데이터 전송
```

예시:

- HTTP → HTTPS
- MySQL TCP 연결 → TLS 옵션 사용 가능
- Redis TCP 연결 → TLS 구성 가능
- gRPC → HTTP/2 over TLS 사용 가능

---

## 3. RST 패킷과 연결 강제 종료

TCP에서는 `RST` 플래그를 사용해 연결을 즉시 종료할 수 있다. 정상적인 4-way Handshake와 달리 RST는 비정상적이거나 강제적인 종료를 의미하는 경우가 많다.

예를 들어 다음 상황에서 RST가 발생할 수 있다.

- 존재하지 않는 포트로 연결 시도
- 애플리케이션이 비정상적으로 소켓 종료
- 방화벽이나 로드 밸런서가 연결 차단
- TCP 상태와 맞지 않는 패킷 수신

보안 장비는 의도적으로 RST를 보내 연결을 끊기도 한다. 그러나 RST가 많다면 네트워크 중간 장비, 애플리케이션 예외, 타임아웃 설정 불일치 등을 점검해야 한다.

---

## 4. TIME_WAIT와 포트 재사용의 보안적 의미

`TIME_WAIT`은 단순한 낭비 상태가 아니라, 이전 연결의 지연 패킷이 새 연결에 잘못 전달되는 것을 방지하는 역할을 한다. 이 상태를 과도하게 줄이거나 무리하게 재사용하면 예기치 않은 연결 오류나 데이터 혼선 가능성이 생길 수 있다.

따라서 운영 환경에서는 다음 원칙이 중요하다.

- 무조건 `TIME_WAIT`을 제거하려 하지 않는다.
- 연결 재사용과 커넥션 풀을 우선 고려한다.
- 커널 파라미터 변경은 부하 테스트와 장애 시나리오 검증 후 적용한다.
- 보안 장비, NAT, 로드 밸런서의 세션 타임아웃과 함께 검토한다.

---

## 5. TCP Spoofing과 ISN

TCP 연결은 Sequence Number를 기반으로 데이터 순서를 관리한다. 초기 순서 번호가 예측 가능하면 공격자가 세션에 패킷을 주입할 가능성이 커질 수 있다. 현대 운영체제는 일반적으로 ISN을 예측하기 어렵게 생성한다.

⚠️ 확인 필요: 특정 OS, 커널 버전, 네트워크 장비의 ISN 생성 방식은 구현에 따라 다를 수 있으므로 실제 보안 평가에서는 해당 시스템의 문서를 확인해야 한다.

## 면접 질문

**Q1. TCP 3-way Handshake가 필요한 이유는 무엇인가요?**  
> 핵심 답변: 클라이언트와 서버가 서로 통신 가능함을 확인하고, 양쪽의 초기 순서 번호인 ISN을 교환하기 위해 필요하다. 이를 통해 신뢰성 있는 양방향 TCP 연결을 시작할 수 있다.

**Q2. 3-way Handshake의 각 단계에서 어떤 플래그가 사용되나요?**  
> 핵심 답변: 첫 번째는 클라이언트의 `SYN`, 두 번째는 서버의 `SYN+ACK`, 세 번째는 클라이언트의 `ACK`이다. 이후 양쪽은 `ESTABLISHED` 상태가 된다.

**Q3. TCP 연결 종료는 왜 4-way Handshake로 설명되나요?**  
> 핵심 답변: TCP는 양방향 스트림이므로 한쪽이 송신을 종료하더라도 상대방은 아직 보낼 데이터가 남아 있을 수 있다. 따라서 한쪽의 FIN에 대한 ACK와 상대방의 FIN, 그에 대한 ACK가 분리되어 일반적으로 네 단계가 된다.

**Q4. TIME_WAIT 상태는 왜 필요한가요?**  
> 핵심 답변: 마지막 ACK가 손실되었을 때 재전송된 FIN에 대응하고, 이전 연결의 지연 패킷이 같은 4-tuple의 새 연결에 영향을 주지 않도록 하기 위해 필요하다.

**Q5. CLOSE_WAIT이 서버에 많이 쌓이면 어떤 문제를 의심해야 하나요?**  
> 핵심 답변: 상대방이 연결 종료를 요청했지만 로컬 애플리케이션이 소켓을 닫지 않은 상태다. 애플리케이션의 연결 종료 처리 누락, 커넥션 관리 버그, 스레드 또는 이벤트 루프 지연 등을 의심할 수 있다.
