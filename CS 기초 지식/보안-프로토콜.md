# 보안 프로토콜 - HTTPS, SSL/TLS 핸드셰이크, 대칭키/비대칭키 암호화

## 핵심 개념

## 보안 프로토콜: HTTPS, SSL/TLS, 대칭키/비대칭키 암호화

HTTPS는 **HTTP over TLS**를 의미하며, 기존 HTTP 통신에 **암호화, 무결성 검증, 서버 인증**을 추가한 보안 통신 방식이다. HTTP는 기본적으로 평문으로 데이터를 주고받기 때문에 중간자 공격자가 패킷을 가로채면 URL, 쿠키, 로그인 정보, API 응답 등을 읽거나 변조할 수 있다. HTTPS는 이를 방지하기 위해 TLS 프로토콜을 사용한다.

SSL과 TLS는 네트워크 통신을 보호하기 위한 암호화 프로토콜이다. SSL은 과거에 사용되던 프로토콜이며 현재는 보안상 이유로 사용이 권장되지 않는다. 현대 웹 보안에서는 TLS가 표준적으로 사용된다. 흔히 “SSL 인증서”라고 부르지만 실제로는 대부분 **TLS 인증서** 또는 **X.509 인증서**를 의미한다.

TLS는 크게 세 가지 보안 목표를 제공한다.

1. **기밀성 Confidentiality**  
   데이터를 암호화하여 제3자가 내용을 읽지 못하게 한다.

2. **무결성 Integrity**  
   전송 중 데이터가 변조되었는지 검증한다.

3. **인증 Authentication**  
   클라이언트가 접속한 서버가 신뢰할 수 있는 서버인지 인증서를 통해 확인한다.

TLS에서는 대칭키 암호화와 비대칭키 암호화가 함께 사용된다. 비대칭키 암호화는 공개키와 개인키를 사용하는 방식으로, 주로 **서버 인증**, **키 교환**, **전자서명 검증**에 사용된다. 반면 대칭키 암호화는 하나의 동일한 키로 암호화와 복호화를 수행하며, 실제 애플리케이션 데이터 전송 구간에서 사용된다. 대칭키 암호화는 비대칭키 암호화보다 일반적으로 연산 비용이 낮기 때문에 대량 데이터 암호화에 적합하다.

HTTPS와 TLS가 중요한 이유는 단순히 데이터를 숨기는 데 그치지 않는다. 사용자가 접속한 사이트가 진짜인지 확인하고, 로그인 세션 쿠키가 탈취되지 않도록 보호하며, API 요청과 응답이 중간에서 변조되지 않도록 한다. 오늘날 브라우저, 모바일 앱, 클라우드 API, 마이크로서비스 간 통신에서 TLS는 사실상 기본 보안 계층으로 사용된다.

## 내부 동작 원리

## 내부 동작 원리

HTTPS 통신은 크게 다음 단계로 구성된다.

```text
[Client]
   |
   | 1. TCP 연결
   v
[Server]
   |
   | 2. TLS Handshake
   |    - TLS 버전 협상
   |    - 암호 스위트 협상
   |    - 서버 인증서 전달
   |    - 키 교환
   |    - 세션 키 생성
   v
[Secure Channel]
   |
   | 3. HTTP 요청/응답을 암호화하여 전송
   v
[HTTPS Application Data]
```

### 1. TCP 연결

HTTPS는 일반적으로 TCP 위에서 동작한다. 클라이언트는 서버의 443 포트로 TCP 연결을 맺는다.

```text
Client  ---------------- TCP 3-way handshake ----------------> Server
```

TCP 연결이 성립된 후 TLS 핸드셰이크가 시작된다.

## TLS 핸드셰이크 개요

TLS 핸드셰이크는 클라이언트와 서버가 안전한 통신을 시작하기 전에 다음 사항을 합의하는 과정이다.

- 사용할 TLS 버전
- 사용할 암호 알고리즘 조합
- 서버 인증서 검증
- 세션 키 생성을 위한 키 교환
- 이후 데이터 암호화에 사용할 대칭키 생성

TLS 1.2와 TLS 1.3은 핸드셰이크 구조가 다르다. 현대 환경에서는 TLS 1.3 사용이 권장된다.

---

## TLS 1.2 핸드셰이크의 일반적인 흐름

```text
Client                                              Server
  |                                                    |
  | ---- ClientHello --------------------------------> |
  |      지원 TLS 버전, Cipher Suite, Random           |
  |                                                    |
  | <--- ServerHello --------------------------------- |
  |      선택된 TLS 버전, Cipher Suite, Random         |
  |                                                    |
  | <--- Certificate -------------------------------- |
  |      서버 인증서 체인                              |
  |                                                    |
  | <--- ServerKeyExchange -------------------------- |
  |      키 교환 정보                                  |
  |                                                    |
  | <--- ServerHelloDone ---------------------------- |
  |                                                    |
  | ---- ClientKeyExchange --------------------------> |
  |      키 교환 데이터                                |
  |                                                    |
  | ---- ChangeCipherSpec ---------------------------> |
  | ---- Finished -----------------------------------> |
  |                                                    |
  | <--- ChangeCipherSpec --------------------------- |
  | <--- Finished ----------------------------------- |
  |                                                    |
  | ===== 암호화된 HTTP 데이터 송수신 =====             |
```

### 주요 단계 설명

#### 1. ClientHello

클라이언트가 서버에 다음 정보를 보낸다.

- 지원하는 TLS 버전
- 지원하는 암호 스위트 목록
- 클라이언트 랜덤 값
- 확장 필드, 예: SNI, ALPN 등

SNI는 Server Name Indication의 약자로, 하나의 IP 주소에서 여러 도메인의 인증서를 제공할 때 사용된다. ALPN은 Application-Layer Protocol Negotiation으로, HTTP/1.1 또는 HTTP/2 같은 애플리케이션 프로토콜 협상에 사용된다.

#### 2. ServerHello

서버는 클라이언트가 제안한 항목 중 사용할 TLS 버전과 암호 스위트를 선택한다. 또한 서버 랜덤 값을 전송한다.

#### 3. Certificate

서버는 자신의 인증서 체인을 클라이언트에게 전달한다. 클라이언트는 인증서를 다음 기준으로 검증한다.

- 인증서가 신뢰할 수 있는 CA에 의해 서명되었는가
- 인증서의 도메인 이름이 접속한 호스트명과 일치하는가
- 인증서 유효 기간이 만료되지 않았는가
- 인증서 체인이 올바른가
- 인증서가 폐기되었는지 확인 가능한가

#### 4. 키 교환

클라이언트와 서버는 대칭키를 직접 전송하지 않고, 키 교환 알고리즘을 통해 동일한 세션 키를 생성한다. 현대 TLS에서는 주로 Diffie-Hellman 계열, 특히 ECDHE가 사용된다.

ECDHE를 사용하면 매 세션마다 임시 키를 생성하기 때문에, 서버의 장기 개인키가 나중에 유출되더라도 과거 통신 내용을 복호화하기 어렵다. 이를 **전방향 안전성 Forward Secrecy**이라고 한다.

#### 5. Finished 메시지

양쪽은 지금까지의 핸드셰이크 내용이 변조되지 않았음을 검증하고, 이후 통신부터 대칭키 기반 암호화 채널을 사용한다.

## TLS 1.3 핸드셰이크의 특징

TLS 1.3은 TLS 1.2보다 핸드셰이크 과정을 단순화하고, 안전하지 않은 알고리즘을 제거했다. 일반적인 TLS 1.3 핸드셰이크는 더 적은 왕복으로 완료될 수 있다.

```text
Client                                              Server
  |                                                    |
  | ---- ClientHello + Key Share --------------------> |
  |      지원 버전, 암호 스위트, 키 공유 정보           |
  |                                                    |
  | <--- ServerHello + Key Share --------------------- |
  | <--- EncryptedExtensions ------------------------- |
  | <--- Certificate -------------------------------- |
  | <--- CertificateVerify --------------------------- |
  | <--- Finished ----------------------------------- |
  |                                                    |
  | ---- Finished -----------------------------------> |
  |                                                    |
  | ===== 암호화된 HTTP 데이터 송수신 =====             |
```

TLS 1.3에서는 많은 핸드셰이크 메시지가 더 이른 시점부터 암호화된다. 또한 정적 RSA 키 교환 방식은 제거되었고, 전방향 안전성을 제공하는 키 교환 방식이 기본적으로 사용된다.

## 대칭키 암호화와 비대칭키 암호화

### 대칭키 암호화

대칭키 암호화는 같은 키로 암호화와 복호화를 수행한다.

```text
Plaintext --[대칭키 K로 암호화]--> Ciphertext
Ciphertext --[대칭키 K로 복호화]--> Plaintext
```

특징:

- 암호화와 복호화 속도가 빠르다.
- 대량 데이터 처리에 적합하다.
- 키를 안전하게 공유하는 문제가 있다.
- TLS의 실제 데이터 전송 구간에서 사용된다.

대표적으로 TLS에서는 AES-GCM, ChaCha20-Poly1305 같은 인증 암호화 방식이 사용된다.

### 비대칭키 암호화

비대칭키 암호화는 공개키와 개인키 쌍을 사용한다.

```text
공개키: 누구나 알 수 있음
개인키: 소유자만 보관

데이터 --[공개키로 암호화]--> 암호문
암호문 --[개인키로 복호화]--> 데이터
```

또는 전자서명에서는 반대 개념으로 사용된다.

```text
서버가 개인키로 서명
클라이언트가 공개키로 서명 검증
```

TLS에서 비대칭키 기술은 주로 다음에 사용된다.

- 서버 인증서 검증
- 서버가 개인키 소유자임을 증명
- 키 교환 과정에서 신뢰 보장
- 전자서명 검증

## 인증서 체인

서버 인증서는 보통 다음과 같은 체인 구조를 가진다.

```text
Root CA
  |
  v
Intermediate CA
  |
  v
Server Certificate
```

클라이언트는 서버 인증서부터 시작해 중간 인증서, 루트 인증서까지의 서명 체인을 검증한다. 루트 CA 인증서는 운영체제나 브라우저의 신뢰 저장소에 포함되어 있다.

## 실제 시스템 연결

### Linux에서 인증서 확인

Linux 환경에서는 `openssl` 명령어로 서버의 TLS 인증서와 핸드셰이크 정보를 확인할 수 있다.

```bash
openssl s_client -connect example.com:443 -servername example.com
```

확인 가능한 정보:

- 서버 인증서 체인
- TLS 버전
- 선택된 암호 스위트
- 인증서 유효 기간
- 인증서 발급자
- SNI 동작 여부

인증서 파일의 내용을 확인할 수도 있다.

```bash
openssl x509 -in cert.pem -text -noout
```

## Nginx에서 HTTPS 설정

Nginx는 TLS 종료 지점으로 자주 사용된다. 일반적인 HTTPS 서버 블록은 다음과 같은 형태다.

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://app_backend;
    }
}
```

여기서 Nginx는 클라이언트와 TLS 세션을 맺고, 내부 애플리케이션 서버로 요청을 프록시한다. 이 구조를 **TLS termination**이라고 한다.

```text
Client --HTTPS--> Nginx --HTTP 또는 HTTPS--> Application Server
```

내부 구간도 민감한 데이터가 오간다면 HTTPS 또는 mTLS를 사용하는 것이 바람직하다.

## Let's Encrypt와 Certbot

Let's Encrypt는 공개적으로 신뢰되는 인증서를 발급하는 CA다. Certbot은 Let's Encrypt 인증서 발급과 갱신 자동화에 많이 사용된다.

예시:

```bash
sudo certbot --nginx -d example.com
```

인증서는 만료일이 있으므로 자동 갱신 설정이 중요하다.

```bash
sudo certbot renew --dry-run
```

## AWS에서 HTTPS 구성

AWS에서는 여러 서비스에서 TLS를 처리할 수 있다.

### Application Load Balancer

ALB는 HTTPS 리스너를 구성하고 ACM 인증서를 연결할 수 있다.

```text
Client --HTTPS--> ALB --HTTP/HTTPS--> EC2, ECS, EKS Service
```

장점:

- 인증서 중앙 관리
- 여러 대상 그룹으로 라우팅
- HTTP/2 지원 가능
- 보안 그룹과 연계 가능

### AWS Certificate Manager

ACM은 AWS 서비스에서 사용할 TLS 인증서를 발급, 가져오기, 관리하는 서비스다. ALB, CloudFront, API Gateway 등과 통합된다.

### CloudFront

CloudFront는 CDN 계층에서 HTTPS를 제공한다.

```text
Client --HTTPS--> CloudFront --HTTPS/HTTP--> Origin
```

Origin과 CloudFront 사이도 HTTPS로 구성할 수 있다.

---

## GCP에서 HTTPS 구성

GCP에서는 HTTPS Load Balancer를 통해 TLS termination을 수행할 수 있다.

```text
Client --HTTPS--> Google Cloud Load Balancer --HTTP/HTTPS--> Backend Service
```

Google-managed SSL certificate를 사용하면 인증서 발급과 갱신을 Google Cloud가 관리할 수 있다.

## Docker, Kubernetes, AWS와의 연관성

### Docker와 TLS

Docker 컨테이너 자체는 일반적으로 TLS를 직접 처리하지 않고, 앞단의 리버스 프록시나 로드 밸런서가 HTTPS를 처리하는 경우가 많다.

```text
Client --HTTPS--> Nginx Container --HTTP--> App Container
```

Docker Compose 예시 구조:

```yaml
services:
  nginx:
    image: nginx
    ports:
      - "443:443"
    volumes:
      - ./certs:/etc/nginx/certs
      - ./nginx.conf:/etc/nginx/nginx.conf

  app:
    image: my-app
    expose:
      - "8080"
```

이 구조에서 Nginx가 TLS 종료를 담당하고, 애플리케이션 컨테이너는 내부 네트워크에서 HTTP로 통신할 수 있다. 단, 내부 네트워크가 신뢰할 수 없거나 멀티테넌트 환경이라면 내부 통신도 TLS를 적용하는 것이 좋다.

## Kubernetes Ingress와 TLS

Kubernetes에서는 Ingress 리소스를 통해 외부 HTTPS 트래픽을 내부 서비스로 라우팅할 수 있다.

```text
Client --HTTPS--> Ingress Controller --HTTP/HTTPS--> Service --> Pod
```

Ingress TLS 예시:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  tls:
    - hosts:
        - example.com
      secretName: example-tls
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
```

TLS 인증서와 개인키는 Kubernetes Secret에 저장된다.

```bash
kubectl create secret tls example-tls \
  --cert=fullchain.pem \
  --key=privkey.pem
```

다만 Secret은 기본적으로 base64 인코딩된 형태로 저장되므로, etcd 암호화, RBAC 제한, Secret 접근 제어가 필요하다.

## cert-manager

Kubernetes 환경에서는 cert-manager를 사용해 인증서 발급과 갱신을 자동화할 수 있다. Let's Encrypt와 연동해 Ingress TLS 인증서를 자동 발급하는 구성이 흔히 사용된다.

```text
Ingress
  |
  v
cert-manager
  |
  v
ACME Challenge
  |
  v
Let's Encrypt
  |
  v
TLS Secret 생성 또는 갱신
```

## AWS EKS와 TLS

EKS에서는 다음 방식으로 HTTPS를 구성할 수 있다.

1. AWS Load Balancer Controller를 사용해 ALB 생성
2. ACM 인증서를 ALB에 연결
3. ALB에서 TLS termination 수행
4. 트래픽을 Kubernetes Service/Pod로 전달

```text
Client --HTTPS--> ALB --HTTP/HTTPS--> EKS Ingress/Service --> Pod
```

ALB Ingress Annotation을 사용해 ACM 인증서 ARN을 연결할 수 있다.

```yaml
metadata:
  annotations:
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:region:account:certificate/cert-id
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
```

## 서비스 메시와 mTLS

Istio, Linkerd 같은 서비스 메시에서는 서비스 간 통신에 mTLS를 적용할 수 있다.

```text
Service A Sidecar ==mTLS== Service B Sidecar
```

mTLS는 양방향 TLS로, 클라이언트와 서버가 서로 인증서를 검증한다. 일반 HTTPS에서는 주로 클라이언트가 서버를 검증하지만, mTLS에서는 서버도 클라이언트를 인증한다.

서비스 메시에서 mTLS를 사용하면 다음을 강화할 수 있다.

- 서비스 간 신원 확인
- 내부 트래픽 암호화
- Zero Trust 네트워크 구성
- 정책 기반 접근 제어

## 보안 연결

## 보안 연결

### 1. 중간자 공격 방어

HTTPS의 핵심 방어 대상 중 하나는 MITM, 즉 중간자 공격이다.

```text
Client ---- Attacker ---- Server
```

공격자가 트래픽을 가로채더라도 TLS가 올바르게 구성되어 있으면 데이터를 복호화하거나 변조하기 어렵다. 단, 클라이언트가 인증서 검증을 제대로 하지 않으면 MITM 공격에 취약해질 수 있다.

---

## 2. 인증서 검증 실패

클라이언트가 다음과 같은 검증을 생략하면 HTTPS의 보안성이 크게 약화된다.

- 인증서 호스트명 검증
- 인증서 체인 검증
- 유효 기간 검증
- 신뢰 가능한 CA 여부 확인

특히 개발 환경에서 `verify=false`, `curl -k`, `InsecureSkipVerify` 같은 설정을 사용한 뒤 운영 환경에 그대로 배포하면 위험하다.

---

## 3. 오래된 프로토콜과 취약한 암호 스위트

SSL 및 오래된 TLS 버전은 알려진 취약점이 존재하므로 사용하지 않는 것이 권장된다. 운영 환경에서는 일반적으로 TLS 1.2 이상을 사용하도록 설정한다.

피해야 할 예:

- SSLv2
- SSLv3
- 취약한 RC4 기반 암호 스위트
- 익명 Diffie-Hellman
- 약한 키 길이의 인증서

Nginx 예시:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

---

## 4. 개인키 보호

TLS 인증서의 개인키가 유출되면 서버 신원 증명 체계가 무너질 수 있다. 특히 전방향 안전성을 제공하지 않는 방식에서는 과거에 수집된 트래픽 복호화 위험도 커질 수 있다.

개인키 보호 방법:

- 파일 권한 제한
- Secret Manager 또는 HSM 사용
- 인증서와 키의 접근 권한 최소화
- 키 로테이션
- 저장소에 개인키 커밋 금지

Linux 예시:

```bash
chmod 600 privkey.pem
chown root:root privkey.pem
```

---

## 5. HSTS

HSTS는 HTTP Strict Transport Security의 약자로, 브라우저에게 해당 도메인은 HTTPS로만 접속해야 한다고 알려주는 보안 헤더다.

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

HSTS를 사용하면 사용자가 실수로 `http://example.com`에 접속하더라도 브라우저가 HTTPS로 강제 전환할 수 있다.

단, `includeSubDomains`를 설정하면 하위 도메인 전체에 적용되므로 모든 하위 도메인이 HTTPS를 정상 지원해야 한다.

---

## 6. 쿠키 보안 속성

HTTPS를 사용하더라도 쿠키 설정이 부적절하면 세션 탈취 위험이 커질 수 있다.

권장 속성:

```http
Set-Cookie: sessionid=abc; Secure; HttpOnly; SameSite=Lax
```

- `Secure`: HTTPS 연결에서만 쿠키 전송
- `HttpOnly`: JavaScript에서 쿠키 접근 방지
- `SameSite`: CSRF 위험 완화에 도움

---

## 7. 인증서 만료

인증서가 만료되면 브라우저와 클라이언트는 연결을 신뢰하지 않는다. 운영 서비스에서는 인증서 만료 모니터링과 자동 갱신이 필수다.

운영 모범 사례:

- 만료일 모니터링
- 자동 갱신 설정
- 갱신 후 서비스 reload 검증
- 인증서 체인 누락 여부 확인

---

## 8. TLS 종료 지점 이후의 평문 구간

로드 밸런서나 Nginx에서 TLS를 종료한 뒤 백엔드로 HTTP를 사용하면 내부 구간은 평문이 된다.

```text
Client --HTTPS--> Load Balancer --HTTP--> Backend
```

이 구성이 항상 잘못된 것은 아니지만, 내부 네트워크 보안 수준에 따라 위험할 수 있다. 민감한 시스템이나 Zero Trust 환경에서는 백엔드 구간도 HTTPS 또는 mTLS를 적용하는 것이 좋다.

## 면접 질문

**Q1. HTTPS는 HTTP와 무엇이 다른가요?**  
> 핵심 답변: HTTPS는 HTTP 메시지를 TLS 보안 계층 위에서 전송한다. HTTP는 평문 통신이지만 HTTPS는 암호화, 무결성 검증, 서버 인증을 제공한다. 이를 통해 도청, 변조, 중간자 공격 위험을 줄인다.

**Q2. TLS 핸드셰이크의 목적은 무엇인가요?**  
> 핵심 답변: 클라이언트와 서버가 사용할 TLS 버전과 암호 스위트를 협상하고, 서버 인증서를 검증하며, 이후 데이터 암호화에 사용할 세션 키를 안전하게 생성하는 과정이다.

**Q3. TLS에서 대칭키와 비대칭키를 함께 사용하는 이유는 무엇인가요?**  
> 핵심 답변: 비대칭키 암호화는 인증과 키 교환에 유용하지만 연산 비용이 크다. 대칭키 암호화는 빠르기 때문에 실제 데이터 전송에 적합하다. TLS는 비대칭키 기반 절차로 안전하게 세션 키를 만들고, 이후 대칭키로 데이터를 암호화한다.

**Q4. 서버 인증서는 어떻게 신뢰할 수 있나요?**  
> 핵심 답변: 서버 인증서는 CA가 서명한 X.509 인증서다. 클라이언트는 인증서 체인을 따라 루트 CA까지 검증하고, 루트 CA가 신뢰 저장소에 있는지 확인한다. 또한 도메인 일치 여부, 유효 기간, 서명 유효성 등을 검증한다.

**Q5. Forward Secrecy란 무엇인가요?**  
> 핵심 답변: 서버의 장기 개인키가 나중에 유출되더라도 과거 세션의 암호화된 트래픽을 복호화하기 어렵게 하는 성질이다. TLS에서는 ECDHE 같은 임시 키 교환 방식을 통해 전방향 안전성을 제공한다.

## 관련 개념

- [[HTTP]] - HTTPS는 HTTP 메시지를 TLS 위에서 전송하는 방식이다.
- [[TCP]] - HTTPS는 일반적으로 TCP 연결 위에서 동작한다.
- [[TLS]] - HTTPS의 보안 기능을 제공하는 핵심 프로토콜이다.
- [[SSL]] - TLS의 이전 세대 프로토콜로, 현대 환경에서는 사용이 권장되지 않는다.
- [[대칭키 암호화]] - TLS에서 실제 애플리케이션 데이터 암호화에 사용된다.
- [[비대칭키 암호화]] - 인증서 검증, 전자서명, 키 교환 과정과 관련된다.
- [[PKI]] - 인증서와 CA 기반 신뢰 체계를 설명하는 핵심 개념이다.
- [[X.509 인증서]] - TLS 서버 인증서의 표준 형식이다.
- [[CA]] - 인증서를 발급하고 신뢰 체인을 구성하는 인증 기관이다.
- [[Diffie-Hellman 키 교환]] - TLS에서 세션 키 생성을 위해 사용되는 키 교환 개념이다.
- [[Forward Secrecy]] - 과거 통신 보호를 위한 TLS 보안 특성이다.
- [[mTLS]] - 클라이언트와 서버가 서로 인증서를 검증하는 양방향 TLS 방식이다.
- [[HSTS]] - 브라우저가 HTTPS 접속을 강제하도록 하는 보안 헤더다.
- [[Nginx]] - TLS termination과 HTTPS 리버스 프록시에 자주 사용된다.
- [[Kubernetes Ingress]] - Kubernetes에서 HTTPS 트래픽을 서비스로 라우팅하는 데 사용된다.
