# 동기화 - 임계 구역, Mutex, Semaphore, Monitor, Race Condition

## 핵심 개념

동기화(Synchronization)는 여러 실행 흐름, 즉 프로세스나 스레드가 공유 자원에 접근할 때 실행 순서와 접근 방식을 제어하여 데이터 일관성과 프로그램의 올바른 동작을 보장하는 운영체제 핵심 개념이다. 현대 운영체제에서는 여러 프로세스와 스레드가 동시에 실행되며, 이들이 메모리, 파일, 데이터베이스 연결, 네트워크 소켓, 커널 자료구조 같은 공유 자원을 함께 사용할 수 있다. 이때 적절한 동기화가 없으면 실행 순서에 따라 결과가 달라지는 Race Condition이 발생할 수 있다.

대표적인 예로 두 스레드가 동시에 `count++` 연산을 수행한다고 가정할 수 있다. `count++`는 한 줄의 코드처럼 보이지만 실제로는 메모리에서 값을 읽고, CPU 레지스터에서 값을 증가시키고, 다시 메모리에 저장하는 여러 단계로 나뉜다. 두 스레드가 같은 값을 읽은 뒤 각각 증가 결과를 저장하면 증가 연산이 한 번 누락될 수 있다. 이러한 문제는 단순한 숫자 카운터뿐 아니라 은행 계좌 잔액, 재고 수량, 파일 쓰기 순서, 커널의 프로세스 테이블 관리 등 다양한 곳에서 치명적인 오류로 이어질 수 있다.

임계 구역(Critical Section)은 공유 자원에 접근하는 코드 영역을 의미한다. 운영체제 동기화의 목표는 한 순간에 하나의 실행 흐름만 임계 구역에 들어가도록 하거나, 정해진 수만큼만 접근하도록 제한하는 것이다. 이를 위해 Mutex, Semaphore, Monitor 같은 동기화 도구가 사용된다. Mutex는 상호 배제(Mutual Exclusion)를 제공하여 한 시점에 하나의 스레드만 자원을 소유하게 한다. Semaphore는 정수 카운터를 기반으로 여러 개의 자원 접근을 제어할 수 있다. Monitor는 공유 데이터와 그 데이터에 접근하는 메서드, 그리고 조건 변수를 하나로 묶어 더 구조화된 동기화를 제공하는 추상화이다.

동기화가 중요한 이유는 단순히 오류를 막는 데 그치지 않는다. 올바른 동기화는 데이터 일관성, 시스템 안정성, 보안, 성능, 확장성에 직접적인 영향을 준다. 반대로 과도하거나 잘못된 동기화는 Deadlock, Starvation, Priority Inversion, 성능 병목을 유발할 수 있다. 따라서 동기화는 “공유 자원을 안전하게 보호하는 것”과 “동시성을 최대한 활용하는 것” 사이의 균형을 설계하는 문제라고 할 수 있다.

## 내부 동작 원리

동기화의 내부 동작은 크게 “공유 자원 접근 전 진입 제어”, “임계 구역 실행”, “자원 해제 및 대기자 깨우기”로 설명할 수 있다.

가장 기본적인 구조는 다음과 같다.

```text
Thread A                         Thread B

lock(mutex)                      lock(mutex)
   |                                |
   v                                v
[Critical Section]              대기 또는 블록
   |
   v
unlock(mutex)  ----------------> Thread B 진입 가능
```

임계 구역 문제를 올바르게 해결하려면 일반적으로 다음 조건이 중요하다.

1. **상호 배제(Mutual Exclusion)**  
   한 시점에 하나의 프로세스 또는 스레드만 임계 구역에 들어갈 수 있어야 한다.

2. **진행(Progress)**  
   임계 구역에 아무도 없고 진입하려는 스레드가 있다면, 무한히 지연되지 않고 누군가는 들어갈 수 있어야 한다.

3. **한정 대기(Bounded Waiting)**  
   어떤 스레드가 임계 구역 진입을 요청한 뒤 무한히 기다리지 않도록 제한이 있어야 한다.

### 1. Race Condition의 내부 원리

Race Condition은 프로그램의 결과가 스레드나 프로세스의 실행 순서, 즉 타이밍에 의존할 때 발생한다. 예를 들어 다음 코드가 있다고 하자.

```c
count++;
```

이 연산은 개념적으로 다음 단계로 나뉠 수 있다.

```text
1. 메모리에서 count 읽기
2. 읽은 값을 1 증가
3. 증가한 값을 메모리에 저장
```

두 스레드가 동시에 실행하면 다음과 같은 문제가 발생할 수 있다.

```text
초기 count = 10

Thread A: count 읽기 -> 10
Thread B: count 읽기 -> 10
Thread A: 10 + 1 = 11
Thread B: 10 + 1 = 11
Thread A: count에 11 저장
Thread B: count에 11 저장

기대 결과: 12
실제 결과: 11
```

이처럼 공유 데이터에 대한 읽기-수정-쓰기 연산이 원자적으로 수행되지 않으면 Race Condition이 발생한다.

---

### 2. Mutex의 내부 동작

Mutex는 Mutual Exclusion의 줄임말로, 하나의 스레드만 특정 임계 구역에 들어갈 수 있도록 하는 잠금 객체이다. 일반적인 동작은 다음과 같다.

```text
lock(mutex)
    mutex가 비어 있으면 획득
    mutex가 이미 잠겨 있으면 대기

critical section 실행

unlock(mutex)
    mutex 해제
    대기 중인 스레드 중 하나를 깨움
```

도식화하면 다음과 같다.

```text
        +----------------+
        |   Mutex Lock   |
        +----------------+
           /          \
      available      locked
         |              |
 Thread 진입        Thread 대기
         |
         v
 +-------------------+
 | Critical Section  |
 +-------------------+
         |
         v
   Mutex Unlock
```

Mutex 구현은 사용자 공간 라이브러리와 운영체제 커널의 협력으로 이루어지는 경우가 많다. 경쟁이 없는 경우에는 사용자 공간에서 원자적 연산을 통해 빠르게 lock/unlock을 처리하고, 이미 잠겨 있어 오래 기다려야 하는 경우에는 커널에 도움을 요청하여 스레드를 sleep 상태로 전환할 수 있다. Linux의 futex는 이러한 방식과 관련된 대표적인 메커니즘이다.

Mutex의 핵심은 원자적 명령어이다. CPU는 Test-and-Set, Compare-and-Swap(CAS), Exchange 같은 원자적 연산을 제공할 수 있으며, 이를 이용해 여러 CPU 코어가 동시에 같은 잠금 상태를 변경하지 못하도록 한다.

### 3. Semaphore의 내부 동작

Semaphore는 정수 값을 가진 동기화 도구이다. 이 값은 사용 가능한 자원의 개수 또는 통과 가능한 실행 흐름의 수를 의미한다. 대표 연산은 `wait(P)`와 `signal(V)`이다.

```text
wait(semaphore):
    값이 0보다 크면 1 감소하고 진입
    값이 0이면 대기

signal(semaphore):
    값을 1 증가
    대기 중인 스레드가 있으면 하나를 깨움
```

예를 들어 세마포어 값이 3이면 동시에 최대 3개의 스레드가 특정 자원을 사용할 수 있다.

```text
Semaphore = 3

Thread A 진입 -> Semaphore = 2
Thread B 진입 -> Semaphore = 1
Thread C 진입 -> Semaphore = 0
Thread D 대기 -> 사용 가능한 자원 없음

Thread B 종료 -> Semaphore = 1
Thread D 깨어남 -> Semaphore = 0
```

Semaphore에는 크게 두 종류가 있다.

- **Binary Semaphore**  
  값이 0 또는 1만 가능하다. Mutex와 유사하게 사용할 수 있지만, 소유권 개념이 반드시 동일한 것은 아니다.

- **Counting Semaphore**  
  값이 0 이상의 정수이며, 여러 개의 동일 자원 접근을 제어할 때 사용한다.

Mutex와 Semaphore의 중요한 차이는 소유권 개념이다. 일반적으로 Mutex는 lock을 획득한 스레드가 unlock해야 한다는 소유권 개념이 강하다. 반면 Semaphore는 한 스레드가 wait하고 다른 스레드가 signal하는 방식의 동기화에도 사용될 수 있다.

### 4. Monitor의 내부 동작

Monitor는 공유 데이터와 해당 데이터를 조작하는 메서드, 그리고 조건 변수를 하나로 묶은 고수준 동기화 추상화이다. Monitor 내부에서는 한 번에 하나의 스레드만 실행될 수 있도록 보장하는 것이 일반적인 모델이다.

구조는 다음과 같다.

```text
+-----------------------------------+
|              Monitor              |
|                                   |
|  Shared Data                      |
|  - buffer                         |
|  - count                          |
|                                   |
|  Methods                          |
|  - put()                          |
|  - get()                          |
|                                   |
|  Condition Variables              |
|  - notFull                        |
|  - notEmpty                       |
+-----------------------------------+
          ^                ^
          |                |
     Thread A          Thread B
```

생산자-소비자 문제를 Monitor로 표현하면 다음과 같다.

```text
Producer:
    monitor.put(item)
        buffer가 가득 차면 notFull 조건에서 wait
        buffer에 item 삽입
        notEmpty signal

Consumer:
    monitor.get()
        buffer가 비어 있으면 notEmpty 조건에서 wait
        buffer에서 item 제거
        notFull signal
```

조건 변수(Condition Variable)는 특정 조건이 만족될 때까지 스레드를 기다리게 하는 도구이다. 예를 들어 버퍼가 비어 있으면 소비자는 기다리고, 생산자가 데이터를 넣으면 소비자를 깨운다. 여기서 주의할 점은 조건 변수의 `wait`는 일반적으로 monitor lock을 잠시 해제하고 대기 상태로 들어가며, 깨어난 뒤 다시 lock을 획득하고 조건을 확인한다는 것이다. 그래서 조건 확인은 보통 `if`가 아니라 `while`로 작성한다.

```java
while (buffer.isEmpty()) {
    wait();
}
```

이는 Spurious Wakeup이나 다른 스레드가 먼저 조건을 변경한 상황에 대비하기 위함이다.

---

### 5. Deadlock, Starvation, Priority Inversion

동기화 도구는 Race Condition을 막지만, 잘못 사용하면 다른 문제가 생긴다.

#### Deadlock

두 개 이상의 스레드가 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태이다.

```text
Thread A: lock X 획득
Thread B: lock Y 획득
Thread A: lock Y 요청 -> 대기
Thread B: lock X 요청 -> 대기

결과: 둘 다 영원히 대기
```

#### Starvation

어떤 스레드가 계속 우선순위에서 밀려 자원을 얻지 못하는 상태이다.

#### Priority Inversion

낮은 우선순위 스레드가 잠금을 보유하고 있고, 높은 우선순위 스레드가 그 잠금을 기다리는 상황에서 중간 우선순위 스레드들이 CPU를 계속 사용하여 높은 우선순위 스레드가 지연되는 현상이다. 이를 완화하기 위해 Priority Inheritance 같은 기법이 사용될 수 있다.

## 실제 시스템 연결

실제 운영체제와 시스템 소프트웨어는 동기화를 매우 광범위하게 사용한다.

### 1. Linux의 동기화

Linux 커널은 다양한 동기화 primitive를 제공한다. 대표적으로 spinlock, mutex, semaphore, read-write lock, RCU(Read-Copy-Update), atomic operation 등이 있다.

- **Spinlock**  
  잠금이 풀릴 때까지 CPU를 사용하며 반복 확인하는 방식이다. 커널 내부에서 짧은 임계 구역에 사용된다. 대기 시간이 길면 CPU를 낭비할 수 있으므로 주의가 필요하다.

- **Mutex**  
  잠금이 오래 걸릴 수 있는 상황에서 스레드 또는 태스크를 잠들게 할 수 있는 방식으로 사용된다.

- **Semaphore**  
  제한된 개수의 자원을 제어하는 데 사용할 수 있다.

- **RCU**  
  읽기 작업이 매우 많은 환경에서 읽기 성능을 높이기 위한 동기화 기법이다. 커널 자료구조 조회 등에 사용된다.

Linux 사용자 공간에서는 POSIX Threads, 즉 pthread 라이브러리를 통해 `pthread_mutex_t`, `pthread_cond_t`, `sem_t` 등을 사용할 수 있다.

```c
pthread_mutex_lock(&lock);
/* critical section */
pthread_mutex_unlock(&lock);
```

또한 Linux의 futex는 Fast Userspace Mutex의 약자로, 경쟁이 없는 경우 사용자 공간에서 처리하고 경쟁이 발생한 경우 커널을 통해 대기/깨우기를 수행하는 메커니즘이다. 이는 pthread mutex 같은 고수준 동기화 구현에 활용될 수 있다.

---

### 2. 데이터베이스 시스템

DBMS는 동시 트랜잭션을 처리하기 위해 Lock, Latch, MVCC 같은 기법을 사용한다. 예를 들어 두 사용자가 동시에 같은 계좌 잔액을 수정하면 Race Condition이 발생할 수 있다. 이를 막기 위해 데이터베이스는 행 수준 잠금(row-level lock), 테이블 잠금, 트랜잭션 격리 수준 등을 제공한다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

이 과정에서 DBMS는 다른 트랜잭션이 중간 상태를 잘못 읽거나 동시에 충돌하는 수정을 하지 않도록 동기화한다.

---

### 3. Nginx와 멀티 프로세스 모델

Nginx는 일반적으로 master process와 여러 worker process 구조를 사용한다. 각 worker는 이벤트 기반으로 많은 연결을 처리한다. 공유 메모리 영역을 사용하는 기능에서는 동기화가 필요할 수 있다. 예를 들어 rate limiting, shared cache metadata, connection counters 같은 기능은 여러 worker가 공유 상태를 다룰 수 있으므로 적절한 잠금이나 원자적 연산이 필요하다.

⚠️ 확인 필요: Nginx 내부의 구체적인 동기화 primitive와 사용 위치는 버전 및 빌드 옵션에 따라 다를 수 있으므로, 특정 구현을 분석할 때는 해당 버전의 소스 코드를 확인해야 한다.

---

### 4. Java, Go, Python 런타임

Java는 `synchronized` 키워드와 `java.util.concurrent` 패키지를 통해 Monitor, Lock, Semaphore, CountDownLatch, ConcurrentHashMap 등 다양한 동기화 도구를 제공한다.

```java
synchronized (obj) {
    // critical section
}
```

Go는 `sync.Mutex`, `sync.RWMutex`, channel 등을 제공한다. Go의 channel은 데이터 전달과 동기화를 함께 표현할 수 있는 수단이다.

Python은 `threading.Lock`, `RLock`, `Semaphore`, `Condition` 등을 제공한다. 다만 CPython에는 GIL(Global Interpreter Lock)이 존재한다. GIL은 Python 바이트코드 실행을 직렬화하는 역할을 하지만, 모든 Race Condition을 자동으로 막아주는 것은 아니다. 특히 I/O, C 확장, 공유 자료구조 조작 시에는 명시적 동기화가 필요할 수 있다.

## 클라우드 연결

클라우드 환경에서는 동기화 문제가 단일 서버 내부를 넘어 컨테이너, 노드, 분산 시스템 전체로 확장된다.

### 1. Docker와 컨테이너 내부 동기화

Docker 컨테이너 안에서 실행되는 애플리케이션도 일반 프로세스와 마찬가지로 스레드 동기화 문제를 가진다. 컨테이너는 격리된 실행 환경을 제공하지만, 애플리케이션 내부의 Race Condition을 자동으로 해결하지는 않는다.

예를 들어 하나의 컨테이너 안에서 멀티스레드 웹 서버가 전역 캐시를 공유한다면 Mutex나 Concurrent 자료구조가 필요할 수 있다.

```text
Container
  └── Web Application
        ├── Thread 1
        ├── Thread 2
        └── Shared In-Memory Cache
```

또한 여러 컨테이너가 같은 볼륨을 공유하여 파일에 동시에 쓰는 경우 파일 잠금이나 애플리케이션 레벨 동기화가 필요할 수 있다.

---

### 2. Kubernetes와 분산 동기화

Kubernetes 환경에서는 여러 Pod가 동시에 실행되므로 동기화 범위가 더 넓어진다. 단일 프로세스 내부 Mutex는 같은 프로세스의 스레드 간 동기화에만 유효하다. 여러 Pod 또는 여러 노드에 걸친 동기화에는 분산 락이나 외부 조정 시스템이 필요할 수 있다.

예를 들어 다음 상황을 생각할 수 있다.

```text
Pod A  ─┐
Pod B  ─┼──> 동일한 배치 작업 실행 시도
Pod C  ─┘
```

이때 동시에 같은 작업이 실행되면 중복 결제, 중복 이메일 발송, 중복 리소스 생성 같은 문제가 발생할 수 있다. 이를 방지하기 위해 다음과 같은 방법을 사용할 수 있다.

- Kubernetes Lease API를 이용한 리더 선출
- Redis 기반 분산 락
- 데이터베이스 트랜잭션 잠금
- etcd 기반 coordination
- 메시지 큐의 visibility timeout 또는 deduplication 기능 활용

⚠️ 확인 필요: Redis 기반 분산 락의 안전성은 구현 방식, 장애 모델, 시간 동기화, 네트워크 파티션 조건에 따라 달라질 수 있다. 중요한 금융성 작업에는 데이터베이스 트랜잭션 또는 합의 기반 시스템을 함께 검토해야 한다.

---

### 3. AWS 서비스와 동기화

AWS 환경에서는 동기화 문제가 여러 서비스에서 나타난다.

- **Amazon RDS / Aurora**  
  데이터베이스 트랜잭션과 잠금을 통해 동시 업데이트를 제어한다.

- **Amazon DynamoDB**  
  조건부 쓰기(Conditional Write)를 사용하여 낙관적 동시성 제어를 구현할 수 있다. 예를 들어 version 필드를 두고 현재 version이 기대값과 같을 때만 업데이트하도록 할 수 있다.

- **Amazon SQS**  
  메시지를 여러 컨슈머가 처리할 때 visibility timeout을 통해 같은 메시지가 동시에 여러 컨슈머에게 처리되지 않도록 돕는다. 다만 처리 실패나 timeout 초과 시 재전달될 수 있으므로 consumer는 idempotent하게 설계하는 것이 중요하다.

- **AWS Lambda**  
  여러 Lambda 인스턴스가 동시에 실행될 수 있으므로, 공유 외부 자원에 접근할 때 동시성 제어가 필요하다. 예를 들어 같은 S3 객체를 갱신하거나 같은 DB row를 업데이트하는 경우 Race Condition이 발생할 수 있다.

- **Amazon S3**  
  객체 저장소에 동시에 쓰기 작업을 수행하는 경우 애플리케이션 차원의 충돌 제어가 필요할 수 있다.  
  ⚠️ 확인 필요: S3의 일관성 모델과 조건부 요청 지원 세부사항은 시점과 API 동작에 따라 확인이 필요하므로 최신 AWS 공식 문서를 기준으로 검증해야 한다.

### 4. 분산 시스템에서의 동기화 한계

운영체제 수준의 Mutex는 한 머신 내부에서는 유용하지만, 분산 시스템에서는 적용 범위가 제한된다. 네트워크 지연, 노드 장애, 클럭 차이, 파티션 등으로 인해 “누가 락을 가지고 있는가”를 판단하기가 훨씬 어려워진다.

```text
Single Machine:
Thread A <-> Mutex <-> Thread B

Distributed System:
Node A <-> Network <-> Lock Service <-> Network <-> Node B
```

분산 환경에서는 다음 개념이 중요해진다.

- 분산 락
- 리더 선출
- 합의 알고리즘
- 멱등성
- 낙관적 동시성 제어
- 재시도와 중복 처리 방지
- 트랜잭션 격리 수준

## 보안 연결

동기화 문제는 단순한 안정성 문제가 아니라 보안 취약점으로 이어질 수 있다. 특히 Race Condition은 공격자가 타이밍을 조작하여 권한 검사를 우회하거나 파일 시스템 상태를 바꾸는 방식으로 악용될 수 있다.

### 1. TOCTOU 취약점

대표적인 보안 Race Condition은 TOCTOU(Time-of-Check to Time-of-Use)이다. 이는 검사 시점과 사용 시점 사이에 대상이 바뀌는 문제이다.

예를 들어 프로그램이 어떤 파일에 대해 권한을 검사한 뒤 파일을 열어 수정한다고 하자.

```text
1. /tmp/user_file 권한 검사
2. 검사 통과
3. 파일 열기
4. 파일에 쓰기
```

공격자가 2번과 3번 사이에 `/tmp/user_file`을 심볼릭 링크로 바꾸어 민감한 파일을 가리키게 만들면, 프로그램이 의도하지 않은 파일을 수정할 수 있다.

```text
Program: 권한 검사 완료
Attacker: 파일을 심볼릭 링크로 교체
Program: 교체된 대상 파일 사용
```

이러한 문제를 막기 위해서는 검사와 사용을 분리하지 않고 원자적인 방식으로 처리하거나, 안전한 파일 열기 옵션과 파일 디스크립터 기반 검증을 사용해야 한다.

---

### 2. 권한 상승과 Race Condition

운영체제나 백그라운드 서비스에서 Race Condition이 발생하면 권한 상승 취약점으로 이어질 수 있다. 특히 높은 권한으로 실행되는 프로세스가 임시 파일, 소켓, 공유 메모리, PID 파일 등을 안전하지 않게 다룰 때 위험하다.

모범 사례는 다음과 같다.

- 예측 가능한 임시 파일명을 사용하지 않는다.
- 임시 파일 생성 시 안전한 API를 사용한다.
- 심볼릭 링크 공격을 고려한다.
- 파일 권한과 소유자를 파일 디스크립터 기준으로 검증한다.
- 공유 디렉터리에서는 원자적 생성 연산을 사용한다.
- 권한이 필요한 작업과 사용자 입력 기반 작업을 분리한다.

---

### 3. Deadlock을 이용한 서비스 거부

동기화 오류는 서비스 거부(DoS)로 이어질 수 있다. 공격자가 특정 요청 패턴을 반복하여 서버 내부 락을 오래 점유하게 만들거나 Deadlock에 가까운 상태를 유발하면, 정상 요청이 처리되지 않을 수 있다.

예를 들어 웹 서버가 전역 Mutex로 세션 저장소를 보호하는데, 특정 요청이 락을 획득한 뒤 외부 API 응답을 기다린다면 문제가 된다.

```text
Request A:
    global lock 획득
    외부 API 호출 대기
    lock 해제

Request B, C, D:
    global lock 대기
```

이 경우 외부 API가 지연되면 전체 서비스 처리량이 급격히 떨어질 수 있다. 임계 구역 안에서는 가능한 한 짧고 예측 가능한 작업만 수행해야 하며, 네트워크 I/O나 디스크 I/O처럼 지연 가능성이 큰 작업은 락 밖에서 처리하는 것이 바람직하다.

---

### 4. 동기화와 메모리 안전성

멀티스레드 환경에서 잘못된 동기화는 Use-After-Free, Double Free, 데이터 손상 같은 메모리 안전성 문제와 연결될 수 있다. 예를 들어 한 스레드가 객체를 해제하는 동안 다른 스레드가 같은 객체를 사용하면 심각한 취약점이 될 수 있다.

```text
Thread A: object 포인터 읽음
Thread B: object free
Thread A: 이미 해제된 object 접근
```

이를 막기 위해 참조 카운팅, 소유권 모델, RCU, hazard pointer, lock 기반 보호 같은 기법이 사용된다.

---

### 5. 보안 모범 사례

- 공유 상태를 최소화한다.
- 불변 객체(immutable object)를 적극 활용한다.
- 임계 구역을 짧게 유지한다.
- 락 획득 순서를 전역적으로 정한다.
- 외부 입력 처리와 권한 작업 사이에 Race Condition이 없는지 검토한다.
- 파일 시스템 작업에서는 TOCTOU를 고려한다.
- 분산 환경에서는 멱등성과 재시도 안전성을 설계한다.
- 보안 테스트 시 동시 요청, 병렬 실행, 지연 삽입 테스트를 포함한다.
- Lock timeout, circuit breaker, backpressure를 고려한다.
- 가능한 경우 검증된 동시성 라이브러리와 프레임워크를 사용한다.

## 면접 질문

**Q1. Race Condition이란 무엇이며, 간단한 예를 들어 설명해보세요.**  
> 핵심 답변: Race Condition은 여러 스레드나 프로세스가 공유 자원에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 문제이다. 예를 들어 두 스레드가 동시에 `count++`를 수행하면 읽기-증가-쓰기 단계가 겹쳐 증가 연산이 누락될 수 있다. 해결하려면 Mutex, Semaphore, atomic operation 등을 사용해 임계 구역을 보호해야 한다.

**Q2. Mutex와 Semaphore의 차이를 설명해보세요.**  
> 핵심 답변: Mutex는 한 번에 하나의 스레드만 임계 구역에 들어가도록 하는 상호 배제 도구이며, 일반적으로 lock을 획득한 스레드가 unlock해야 하는 소유권 개념이 있다. Semaphore는 정수 카운터를 기반으로 여러 개의 자원 접근을 제어할 수 있으며, Counting Semaphore는 동시에 N개의 접근을 허용할 수 있다. Binary Semaphore는 Mutex와 비슷하게 사용할 수 있지만 소유권 의미가 다를 수 있다.

**Q3. Monitor란 무엇이며 Condition Variable은 왜 필요한가요?**  
> 핵심 답변: Monitor는 공유 데이터와 해당 데이터를 조작하는 메서드, 그리고 동기화 메커니즘을 묶은 고수준 추상화이다. 한 번에 하나의 스레드만 Monitor 내부 코드를 실행하도록 보장하는 모델이 일반적이다. Condition Variable은 특정 조건이 만족될 때까지 스레드를 기다리게 하고, 조건이 바뀌면 다른 스레드가 signal로 깨울 수 있게 한다. `wait` 후에는 조건을 `while`로 재확인하는 것이 중요하다.

**Q4. Deadlock이 발생하는 조건과 예방 방법을 설명해보세요.**  
> 핵심 답변: Deadlock은 여러 스레드가 서로가 가진 자원을 기다리며 진행하지 못하는 상태이다. 일반적으로 상호 배제, 점유 대기, 비선점, 순환 대기 조건이 동시에 만족되면 발생할 수 있다. 예방 방법으로는 락 획득 순서를 고정하기, timeout 사용, 필요한 락을 한 번에 획득하기, 임계 구역 줄이기, try-lock 사용, Deadlock detection 도입 등이 있다.

**Q5. 분산 환경에서 일반 Mutex를 사용할 수 없는 이유와 대안은 무엇인가요?**  
> 핵심 답변: 일반 Mutex는 같은 프로세스 또는 같은 머신 내부의 스레드 동기화에 사용된다. Kubernetes 같은 분산 환경에서는 여러 Pod와 노드가 네트워크를 통해 동작하므로 로컬 Mutex로는 전체 시스템의 동시 접근을 제어할 수 없다. 대안으로는 데이터베이스 트랜잭션 락, Redis 기반 분산 락, etcd/Consul 같은 coordination 시스템, Kubernetes Lease, 메시지 큐 기반 직렬화, 낙관적 동시성 제어 등이 있다. 중요한 작업은 장애 상황과 중복 실행을 고려해 멱등하게 설계해야 한다.

## 관련 개념

- [[프로세스]] - 동기화는 여러 프로세스가 공유 자원에 접근할 때 필요한 제어 방식이다.
- [[스레드]] - 동일 프로세스 내 스레드들은 메모리를 공유하므로 Race Condition이 발생하기 쉽다.
- [[임계 구역]] - 공유 자원에 접근하는 코드 영역으로 동기화의 핵심 대상이다.
- [[상호 배제]] - 한 시점에 하나의 실행 흐름만 자원에 접근하도록 보장하는 원칙이다.
- [[Race Condition]] - 동기화가 부족할 때 실행 순서에 따라 결과가 달라지는 문제이다.
- [[Mutex]] - 임계 구역을 보호하기 위한 대표적인 상호 배제 도구이다.
- [[Semaphore]] - 제한된 개수의 자원 접근을 제어하는 카운터 기반 동기화 도구이다.
- [[Monitor]] - 공유 데이터와 동기화 로직을 캡슐화한 고수준 동시성 추상화이다.
- [[Condition Variable]] - 특정 조건이 만족될 때까지 스레드를 대기시키는 동기화 도구이다.
- [[Deadlock]] - 여러 실행 흐름이 서로의 자원을 기다리며 무한 대기하는 상태이다.
- [[Starvation]] - 특정 스레드가 계속 자원을 얻지 못하고 지연되는 문제이다.
- [[Priority Inversion]] - 낮은 우선순위 작업이 보유한 락 때문에 높은 우선순위 작업이 지연되는 현상이다.
- [[Atomic Operation]] - 중간에 끼어들 수 없는 단일 연산으로 동기화 구현의 기반이 된다.
- [[Compare-And-Swap]] - 락프리 자료구조와 Mutex 구현에 활용되는 원자적 명령 패턴이다.
- [[Futex]] - Linux에서 사용자 공간 동기화와 커널 대기/깨우기를 결합하는 메커니즘이다.
- [[분산 락]] - 여러 노드나 Pod 사이에서 공유 자원 접근을 제어하기 위한 분산 동기화 방법이다.
- [[트랜잭션 격리 수준]] - 데이터베이스에서 동시 트랜잭션 간 간섭을 제어하는 개념이다.
- [[TOCTOU]] - 검사 시점과 사용 시점 사이의 상태 변화로 발생하는 Race Condition 보안 취약점이다.
