# 교착 상태 - 발생 4가지 조건, 예방/회피(은행원 알고리즘)/탐지/회복

## 핵심 개념

# 교착 상태(Deadlock)

교착 상태란 둘 이상의 프로세스 또는 스레드가 서로가 점유한 자원을 기다리며 영원히 진행하지 못하는 상태를 말한다. 운영체제에서 자원은 CPU, 메모리, 파일, 락, 세마포어, 네트워크 소켓, 데이터베이스 연결, 디바이스 등 다양하게 해석될 수 있다. 예를 들어 프로세스 A가 자원 X를 점유한 채 자원 Y를 기다리고, 프로세스 B가 자원 Y를 점유한 채 자원 X를 기다리면 두 프로세스는 더 이상 실행을 진행할 수 없다.

교착 상태는 단순히 “느려지는 현상”이 아니라, 특정 실행 단위들이 무한 대기 상태에 빠지는 문제다. 시스템 전체가 멈출 수도 있고, 일부 서비스나 요청만 응답하지 않는 형태로 나타날 수도 있다. 따라서 운영체제, 데이터베이스, 분산 시스템, 클라우드 환경, 멀티스레드 애플리케이션에서 매우 중요한 개념이다.

교착 상태가 발생하려면 다음 4가지 조건이 동시에 성립해야 한다. 이를 Coffman 조건이라고 부른다.

1. **상호 배제(Mutual Exclusion)**  
   하나의 자원을 동시에 여러 프로세스가 사용할 수 없다. 예를 들어 프린터, 쓰기 락, 뮤텍스는 한 번에 하나의 실행 주체만 사용할 수 있다.

2. **점유와 대기(Hold and Wait)**  
   프로세스가 이미 하나 이상의 자원을 점유한 상태에서 다른 자원을 추가로 기다린다.

3. **비선점(No Preemption)**  
   점유된 자원을 운영체제가 강제로 빼앗을 수 없다. 자원을 점유한 프로세스가 스스로 반납해야 한다.

4. **순환 대기(Circular Wait)**  
   프로세스들이 원형으로 서로의 자원을 기다린다. 예를 들어 P1은 P2가 가진 자원을 기다리고, P2는 P3가 가진 자원을 기다리며, P3는 다시 P1이 가진 자원을 기다리는 구조다.

교착 상태를 다루는 방법은 크게 **예방**, **회피**, **탐지**, **회복**으로 나눌 수 있다. 예방은 네 가지 발생 조건 중 하나 이상이 성립하지 않도록 설계하는 방식이다. 회피는 시스템이 안전 상태를 유지하도록 자원 할당을 조심스럽게 결정하는 방식이며, 대표적인 예가 **은행원 알고리즘(Banker’s Algorithm)**이다. 탐지는 이미 교착 상태가 발생했는지 검사하는 방법이고, 회복은 교착 상태가 확인된 뒤 프로세스 종료나 자원 선점 등을 통해 시스템을 정상 상태로 되돌리는 방법이다.

교착 상태 개념이 중요한 이유는 실제 운영체제뿐만 아니라 데이터베이스 트랜잭션, 멀티스레드 서버, 컨테이너 오케스트레이션, 분산 락, 클라우드 리소스 관리에서도 동일한 문제가 발생하기 때문이다. 특히 현대 시스템은 수많은 동시 요청과 공유 자원을 다루기 때문에, 교착 상태를 이해하지 못하면 장애 원인 분석과 안정적인 시스템 설계가 어렵다.

## 내부 동작 원리

# 내부 동작 원리

## 1. 자원 할당 그래프(Resource Allocation Graph)

교착 상태는 자원 할당 그래프로 설명할 수 있다. 일반적으로 프로세스는 원, 자원은 사각형으로 표현한다.

- `P -> R` : 프로세스 P가 자원 R을 요청 중
- `R -> P` : 자원 R이 프로세스 P에 할당됨

예시:

```text
[P1] ──요청──> [R2]
 ^              |
 |              할당
 |              v
[R1] <──요청── [P2]
 |              ^
 할당           |
 v              |
[P1]          [R2]
```

더 단순하게 표현하면 다음과 같다.

```text
R1 → P1 → R2 → P2 → R1
```

이 구조는 순환 대기 상태를 나타낸다.  
자원이 각 타입당 하나씩만 존재하는 경우, 자원 할당 그래프에 사이클이 있으면 교착 상태가 발생한다. 다만 자원 타입마다 인스턴스가 여러 개 있는 경우에는 사이클이 있다고 해서 반드시 교착 상태라고 단정할 수는 없다.

## 2. 교착 상태 발생 4가지 조건

### 2.1 상호 배제

상호 배제는 특정 자원을 동시에 하나의 프로세스만 사용할 수 있는 조건이다. 읽기 전용 파일처럼 여러 프로세스가 동시에 접근 가능한 자원은 상호 배제 조건이 약하다. 반면 뮤텍스, 프린터, 배타적 파일 락, 데이터베이스 행 쓰기 락은 상호 배제가 강하게 적용된다.

```text
P1 ── lock(mutex) 성공
P2 ── lock(mutex) 대기
```

### 2.2 점유와 대기

프로세스가 이미 자원을 가진 상태에서 다른 자원을 기다리는 상황이다.

```text
P1: R1 점유 중, R2 요청
P2: R2 점유 중, R1 요청
```

이 조건이 없으면 프로세스는 필요한 자원을 모두 한 번에 얻거나, 얻지 못하면 아무것도 점유하지 않아야 한다.

### 2.3 비선점

운영체제나 시스템이 이미 할당된 자원을 강제로 회수하지 못하는 상태다. CPU는 선점 스케줄링이 가능하지만, 뮤텍스나 파일 쓰기 작업 같은 자원은 임의로 빼앗으면 데이터 불일치가 발생할 수 있다.

### 2.4 순환 대기

프로세스들이 원형 체인으로 서로의 자원을 기다린다.

```text
P1 waits for R2 held by P2
P2 waits for R3 held by P3
P3 waits for R1 held by P1
```

다이어그램:

```text
+----+      +----+      +----+
| P1 | ---> | P2 | ---> | P3 |
+----+      +----+      +----+
  ^                       |
  |                       v
  +-----------------------+
```

## 3. 교착 상태 예방(Prevention)

교착 상태 예방은 네 가지 조건 중 하나 이상을 구조적으로 깨뜨리는 방식이다.

### 3.1 상호 배제 제거

가능한 경우 자원을 공유 가능하게 만든다. 예를 들어 읽기 전용 데이터는 여러 프로세스가 동시에 읽을 수 있다. 하지만 프린터, 쓰기 락, 뮤텍스처럼 본질적으로 배타적 접근이 필요한 자원은 상호 배제를 없애기 어렵다.

### 3.2 점유와 대기 제거

프로세스가 실행 전에 필요한 모든 자원을 한꺼번에 요청하도록 하거나, 추가 자원을 요청하기 전에 이미 가진 자원을 모두 반납하도록 한다.

장점:
- 교착 상태 가능성을 줄일 수 있다.

단점:
- 자원 이용률이 낮아질 수 있다.
- 필요한 자원을 미리 알기 어렵다.
- 기아 상태가 발생할 수 있다.

### 3.3 비선점 제거

어떤 프로세스가 자원을 기다려야 할 때, 이미 가진 자원을 강제로 반납하게 한다. 이후 모든 자원을 다시 획득하면 실행을 재개한다.

단점:
- 모든 자원에 적용하기 어렵다.
- 락이나 파일 쓰기 중간 상태를 강제로 회수하면 데이터 일관성이 깨질 수 있다.

### 3.4 순환 대기 제거

자원에 전역 순서를 부여하고, 모든 프로세스가 그 순서대로만 자원을 요청하도록 한다.

예시:

```text
자원 순서: R1 < R2 < R3

허용:
P1: R1 요청 → R2 요청 → R3 요청

금지:
P1: R3 요청 → R1 요청
```

이 방식은 실무에서 락 순서 규칙으로 자주 사용된다. 예를 들어 여러 뮤텍스를 획득해야 한다면 항상 동일한 순서로 락을 획득하도록 코딩한다.

## 4. 교착 상태 회피(Avoidance)

교착 상태 회피는 자원을 할당하기 전에 “이 할당이 시스템을 위험한 상태로 만드는가?”를 검사한다. 즉, 교착 상태가 실제로 발생하기 전에 안전하지 않은 상태로 들어가지 않도록 한다.

핵심 개념은 **안전 상태(Safe State)**다.

- 안전 상태: 모든 프로세스가 어떤 순서로든 필요한 자원을 얻고 정상 종료할 수 있는 상태
- 불안전 상태: 교착 상태가 발생할 가능성이 있는 상태
- 교착 상태: 실제로 프로세스들이 영원히 대기하는 상태

중요한 점은 **불안전 상태가 곧 교착 상태는 아니다**. 다만 불안전 상태에서는 이후 요청 순서에 따라 교착 상태가 발생할 수 있다.

## 5. 은행원 알고리즘(Banker’s Algorithm)

은행원 알고리즘은 대표적인 교착 상태 회피 알고리즘이다. 은행이 고객에게 대출할 때 모든 고객이 최대 한도까지 요청하더라도 파산하지 않도록 대출을 승인하는 방식에서 이름이 유래했다.

은행원 알고리즘은 각 프로세스가 앞으로 최대로 요청할 수 있는 자원량을 미리 알고 있다고 가정한다.

주요 자료구조:

| 이름 | 의미 |
|---|---|
| Available | 현재 사용 가능한 자원 수 |
| Max | 각 프로세스가 최대로 필요로 하는 자원 수 |
| Allocation | 각 프로세스에 현재 할당된 자원 수 |
| Need | 앞으로 추가로 필요한 자원 수, `Need = Max - Allocation` |

자원 요청 처리 과정:

```text
1. 프로세스 Pi가 Request[i]를 요청한다.
2. Request[i] <= Need[i]인지 확인한다.
3. Request[i] <= Available인지 확인한다.
4. 일단 자원을 할당했다고 가정한다.
5. 안전성 알고리즘으로 safe sequence가 존재하는지 검사한다.
6. 안전하면 실제 할당한다.
7. 안전하지 않으면 요청을 보류한다.
```

안전성 검사 과정:

```text
Work = Available
Finish[i] = false

반복:
  Finish[i] == false 이고 Need[i] <= Work 인 프로세스 Pi를 찾는다.
  찾으면:
    Work = Work + Allocation[i]
    Finish[i] = true
  찾지 못하면 반복 종료

모든 Finish[i]가 true이면 안전 상태
하나라도 false이면 불안전 상태
```

간단한 다이어그램:

```text
요청 발생
   |
   v
요청량이 Need 이하인가?
   |
   v
요청량이 Available 이하인가?
   |
   v
가상 할당
   |
   v
안전성 검사
   |
   +── 안전함 ──> 실제 할당
   |
   +── 불안전 ──> 대기
```

은행원 알고리즘의 한계:

- 각 프로세스의 최대 자원 요구량을 미리 알아야 한다.
- 프로세스 수와 자원 수가 고정적이라는 가정이 필요하다.
- 실제 범용 운영체제에서는 모든 자원에 이 알고리즘을 적용하기 어렵다.
- 검사 비용이 발생한다.

따라서 은행원 알고리즘은 운영체제 이론에서 매우 중요하지만, 실제 범용 OS의 모든 자원 관리에 그대로 사용된다고 보기는 어렵다.

## 6. 교착 상태 탐지(Detection)

탐지는 교착 상태를 예방하거나 회피하지 않고, 시스템 상태를 주기적으로 검사하여 교착 상태 발생 여부를 확인하는 방식이다.

자원 타입당 인스턴스가 하나인 경우에는 **대기 그래프(Wait-for Graph)**를 사용할 수 있다.

```text
P1 → P2
```

이는 P1이 P2가 가진 자원을 기다린다는 의미다.  
대기 그래프에 사이클이 있으면 교착 상태가 존재한다.

예시:

```text
P1 → P2 → P3 → P1
```

이 경우 P1, P2, P3는 서로 순환 대기 중이다.

자원 인스턴스가 여러 개인 경우에는 은행원 알고리즘의 안전성 검사와 유사한 방식으로 탐지 알고리즘을 사용할 수 있다. 현재 사용 가능한 자원과 각 프로세스의 요청량을 기반으로 완료 가능한 프로세스를 찾아가며, 끝까지 완료 불가능한 프로세스가 남으면 교착 상태 후보로 판단한다.

## 7. 교착 상태 회복(Recovery)

교착 상태가 탐지되면 시스템은 회복 작업을 수행해야 한다.

대표적인 방법은 다음과 같다.

### 7.1 프로세스 종료

교착 상태에 관련된 프로세스를 종료한다.

방식:
- 교착 상태에 포함된 모든 프로세스를 종료
- 하나씩 종료하면서 교착 상태가 풀리는지 확인

고려 기준:
- 프로세스 우선순위
- 지금까지 실행한 시간
- 종료 시 손실 비용
- 보유 자원 수
- 재시작 가능 여부

### 7.2 자원 선점

일부 프로세스에서 자원을 강제로 회수하여 다른 프로세스에 할당한다.

고려할 문제:
- 어떤 프로세스를 희생자로 선택할 것인가
- 선점된 프로세스를 어떤 상태로 롤백할 것인가
- 같은 프로세스만 반복 희생되어 기아 상태가 발생하지 않게 할 수 있는가

### 7.3 롤백

프로세스나 트랜잭션을 이전의 안전한 상태로 되돌린다. 데이터베이스 시스템에서는 트랜잭션 abort와 rollback을 통해 교착 상태를 해소하는 경우가 많다.

# 실제 시스템 연결

## 1. Linux와 교착 상태

Linux 같은 범용 운영체제는 다양한 락과 동기화 메커니즘을 제공한다. 예를 들어 커널 내부에서는 스핀락, 뮤텍스, 세마포어, RCU(Read-Copy-Update) 등이 사용된다. 사용자 공간에서는 `pthread_mutex`, 파일 락, futex 기반 동기화 등이 사용된다.

멀티스레드 프로그램에서 다음과 같은 코드는 교착 상태를 만들 수 있다.

```c
// Thread 1
pthread_mutex_lock(&lockA);
pthread_mutex_lock(&lockB);

// Thread 2
pthread_mutex_lock(&lockB);
pthread_mutex_lock(&lockA);
```

Thread 1이 `lockA`를 얻고 Thread 2가 `lockB`를 얻은 뒤, 서로 상대 락을 기다리면 교착 상태가 발생할 수 있다. 이를 방지하려면 항상 동일한 락 획득 순서를 유지해야 한다.

```c
// 모든 스레드가 동일하게 lockA -> lockB 순서로 획득
pthread_mutex_lock(&lockA);
pthread_mutex_lock(&lockB);
```

Linux에서는 사용자 프로그램의 일반적인 mutex deadlock을 운영체제가 자동으로 해결해주지 않는다. 개발자가 타임아웃, 락 순서 규칙, 데드락 탐지 도구 등을 사용해 예방해야 한다.

## 2. 데이터베이스 시스템

데이터베이스는 교착 상태가 자주 논의되는 대표적인 실제 시스템이다. 트랜잭션들이 서로 다른 행이나 테이블에 락을 잡고 상대방의 락 해제를 기다리면 교착 상태가 발생할 수 있다.

예시:

```text
Transaction T1:
  UPDATE account SET balance = balance - 100 WHERE id = 1;
  UPDATE account SET balance = balance + 100 WHERE id = 2;

Transaction T2:
  UPDATE account SET balance = balance - 50 WHERE id = 2;
  UPDATE account SET balance = balance + 50 WHERE id = 1;
```

T1은 `id=1` 행의 락을 잡고 `id=2`를 기다리고, T2는 `id=2` 행의 락을 잡고 `id=1`을 기다릴 수 있다.

많은 DBMS는 교착 상태 탐지 기능을 제공하며, 교착 상태가 발견되면 트랜잭션 중 하나를 희생자로 선택해 중단하고 롤백한다. 애플리케이션은 해당 트랜잭션을 재시도하는 로직을 갖추는 것이 일반적인 모범 사례다.

## 3. 웹 서버와 애플리케이션 서버

Nginx 자체는 이벤트 기반 아키텍처를 사용하여 많은 연결을 효율적으로 처리하지만, 백엔드 애플리케이션이나 업스트림 서비스에서 교착 상태가 발생하면 요청이 지연되거나 타임아웃될 수 있다.

예를 들어 Java, Go, Python, Node.js 백엔드 서버에서 다음과 같은 문제가 발생할 수 있다.

- 스레드 풀 고갈
- DB 커넥션 풀 고갈
- 분산 락 미해제
- 서로 다른 서비스 간 동기 호출 순환
- 요청 처리 중 락 획득 순서 불일치

이런 경우 Nginx 입장에서는 단순히 upstream timeout, gateway timeout 형태로 보일 수 있다. 실제 원인은 애플리케이션 내부의 락 대기나 데이터베이스 교착 상태일 수 있다.

## 4. 운영체제와 드라이버

디바이스 드라이버나 커널 모듈에서 락 순서를 잘못 설계하면 시스템 전체 안정성에 영향을 줄 수 있다. 커널 수준 교착 상태는 일반 애플리케이션 교착 상태보다 더 치명적일 수 있다. 커널 코드에서는 락 계층 구조를 명확히 정의하고, 인터럽트 컨텍스트와 프로세스 컨텍스트의 락 사용을 신중히 설계해야 한다.

⚠️ 확인 필요: 특정 Linux 커널 버전별 데드락 탐지 기능과 설정 옵션은 버전과 배포판에 따라 다를 수 있으므로, 실제 운영 환경에서는 해당 커널 문서를 확인해야 한다.

## 클라우드 연결

# 클라우드 연결

## 1. Docker와 교착 상태

Docker 컨테이너 안에서 실행되는 애플리케이션도 일반 프로세스와 마찬가지로 교착 상태에 빠질 수 있다. 컨테이너는 격리된 실행 환경을 제공하지만, 애플리케이션 내부의 락, 스레드, 커넥션 풀 문제를 자동으로 해결하지는 않는다.

예시:

```text
Container A:
  Service waits for DB connection

DB connection pool:
  모든 커넥션이 트랜잭션 락 대기 상태

Result:
  요청 처리 스레드가 반환되지 않음
  신규 요청도 대기
```

이 경우 컨테이너는 살아 있지만 애플리케이션은 응답하지 않을 수 있다. 따라서 Docker 환경에서는 다음이 중요하다.

- health check 설정
- 요청 타임아웃 설정
- graceful shutdown
- connection pool timeout
- lock timeout
- deadlock 발생 시 재시도 로직

## 2. Kubernetes와 교착 상태

Kubernetes는 컨테이너 오케스트레이션 시스템으로, Pod 스케줄링, 자동 복구, 롤링 업데이트 등을 제공한다. 하지만 애플리케이션 내부 교착 상태를 직접 이해하고 해결하지는 않는다.

Kubernetes에서 교착 상태와 관련된 주요 연결 지점은 다음과 같다.

### 2.1 Liveness Probe

애플리케이션이 교착 상태로 인해 응답 불능 상태가 되었을 때 liveness probe가 실패하면 kubelet이 컨테이너를 재시작할 수 있다. 이는 교착 상태 회복의 한 형태로 볼 수 있다.

다만 단순 HTTP health endpoint가 별도 스레드에서 정상 응답한다면, 실제 비즈니스 로직은 교착 상태인데도 liveness probe는 성공할 수 있다. 따라서 헬스체크 설계가 중요하다.

### 2.2 Readiness Probe

DB 교착 상태나 커넥션 풀 고갈 등으로 요청을 처리할 수 없는 경우 readiness probe를 실패시키면 해당 Pod로 트래픽이 전달되지 않게 할 수 있다.

### 2.3 Resource Request와 Limit

CPU나 메모리 부족은 교착 상태와 동일한 개념은 아니지만, 스레드 지연, 타임아웃 누락, 락 보유 시간 증가를 통해 교착 상태와 유사한 장애를 악화시킬 수 있다.

## 3. AWS 서비스와 교착 상태

AWS 환경에서도 교착 상태는 여러 계층에서 나타날 수 있다.

### 3.1 Amazon RDS

RDS에서 MySQL, PostgreSQL 등 관계형 데이터베이스를 사용할 때 트랜잭션 락 교착 상태가 발생할 수 있다. DBMS는 교착 상태를 탐지하고 트랜잭션 중 하나를 중단할 수 있다. 애플리케이션은 deadlock error를 받았을 때 트랜잭션을 재시도하도록 설계하는 것이 좋다.

### 3.2 Amazon ECS / EKS

ECS나 EKS에서 실행되는 컨테이너 애플리케이션이 내부적으로 교착 상태에 빠질 수 있다. 이때 태스크나 Pod는 계속 실행 중으로 보일 수 있으므로, CloudWatch 메트릭, 로그, health check, tracing을 통해 비정상 대기를 탐지해야 한다.

### 3.3 AWS Lambda

Lambda는 요청 단위 실행 모델을 제공하지만, 함수 코드 내부에서 비동기 작업, 외부 API 호출, DB 락 대기, 커넥션 관리 문제가 있으면 타임아웃이 발생할 수 있다. 이것이 전통적인 OS 교착 상태와 항상 동일한 것은 아니지만, 자원 대기와 순환 의존성이 있으면 유사한 장애 패턴이 나타날 수 있다.

## 4. 분산 시스템에서의 교착 상태

클라우드 환경에서는 단일 머신 내부 락뿐 아니라 분산 락과 서비스 간 의존성에서도 교착 상태가 발생할 수 있다.

예시:

```text
Service A:
  Lock X 획득
  Service B 호출

Service B:
  Lock Y 획득
  Service A 호출

Service A:
  Lock Y 필요

Service B:
  Lock X 필요
```

이러한 문제를 줄이기 위한 방법:

- 분산 락에 TTL 설정
- 락 획득 순서 통일
- 외부 호출 중 락 보유 최소화
- 타임아웃 설정
- 재시도에 지수 백오프 적용
- 서킷 브레이커 사용
- idempotency key를 통한 안전한 재시도

## 보안 연결

# 보안 연결

## 1. 교착 상태와 서비스 거부(DoS)

교착 상태는 보안 관점에서 서비스 거부(DoS, Denial of Service)와 연결될 수 있다. 공격자가 특정 요청 패턴을 반복적으로 보내 애플리케이션의 락, 스레드 풀, DB 커넥션 풀, 파일 핸들 등을 고갈시키면 정상 사용자가 서비스를 이용하지 못할 수 있다.

예를 들어 다음과 같은 상황이 가능하다.

```text
1. 공격자가 오래 걸리는 트랜잭션을 다수 생성
2. 트랜잭션이 주요 테이블이나 행의 락을 오래 보유
3. 정상 요청들이 락 대기
4. 커넥션 풀이 고갈
5. API 서버 전체 응답 지연 또는 장애
```

이것이 항상 전통적인 교착 상태는 아니지만, 자원 대기와 고갈이라는 점에서 운영 안정성과 보안 모두에 영향을 준다.

## 2. 락 미해제와 예외 처리

보안상 중요한 코드에서 예외 발생 시 락을 해제하지 않으면 교착 상태가 발생할 수 있다. 예를 들어 인증, 결제, 권한 변경 로직에서 락을 잡은 뒤 예외 처리 경로에서 unlock을 누락하면 이후 요청이 계속 대기할 수 있다.

잘못된 예:

```java
lock.lock();
processPayment();
lock.unlock();
```

`processPayment()`에서 예외가 발생하면 `unlock()`이 실행되지 않을 수 있다.

개선 예:

```java
lock.lock();
try {
    processPayment();
} finally {
    lock.unlock();
}
```

`finally`를 사용하면 예외 발생 여부와 관계없이 락을 해제할 가능성이 높아진다.

## 3. 타임아웃 부재

락 대기, DB 쿼리, 외부 API 호출에 타임아웃이 없으면 장애가 무기한 대기로 확산될 수 있다. 보안 공격자는 느린 요청이나 응답하지 않는 외부 의존성을 악용해 시스템 리소스를 점유하게 만들 수 있다.

모범 사례:

- DB lock timeout 설정
- HTTP client timeout 설정
- connection acquisition timeout 설정
- distributed lock TTL 설정
- 작업 큐 visibility timeout 설정
- 요청 단위 deadline 전파

## 4. 분산 락 보안

Redis, ZooKeeper, etcd 같은 시스템을 이용해 분산 락을 구현할 때는 락 해제 실패, 네트워크 파티션, 클라이언트 중단 등을 고려해야 한다. 락에 TTL이 없으면 락 소유자가 죽은 뒤에도 다른 노드가 영원히 대기할 수 있다.

주의할 점:

- 락에는 만료 시간을 설정한다.
- 락 해제 시 소유자 토큰을 검증한다.
- 락 보유 중 외부 호출을 최소화한다.
- 락 만료 후에도 작업이 계속될 수 있는 경우 데이터 정합성을 별도로 보호한다.
- 가능한 경우 데이터베이스의 원자적 연산이나 낙관적 락을 고려한다.

## 5. 권한과 자원 선점

교착 상태 회복을 위해 프로세스 종료나 자원 선점을 수행할 때는 권한 제어가 중요하다. 운영 환경에서 임의 사용자가 다른 사용자의 프로세스를 종료하거나 락을 해제할 수 있으면 보안 문제가 된다. 관리자 권한, 감사 로그, 변경 승인 절차가 필요하다.

## 6. 보안 모범 사례 요약

- 공유 자원 접근 시 락 순서를 문서화한다.
- 모든 락 획득에는 가능한 경우 타임아웃을 둔다.
- 예외 경로에서도 락이 해제되도록 `finally`, defer, RAII 등을 사용한다.
- DB 트랜잭션은 짧게 유지한다.
- 사용자 입력으로 인해 장시간 락이 유지되지 않도록 한다.
- deadlock error 발생 시 안전한 재시도 정책을 적용한다.
- 모니터링 지표에 lock wait, thread pool usage, connection pool usage를 포함한다.

## 면접 질문

**Q1. 교착 상태가 발생하기 위한 4가지 조건은 무엇인가요?**  
> 핵심 답변: 상호 배제, 점유와 대기, 비선점, 순환 대기이다. 네 조건이 동시에 만족될 때 교착 상태가 발생할 수 있다. 하나라도 깨뜨리면 교착 상태를 예방할 수 있다.

**Q2. 교착 상태 예방과 회피의 차이는 무엇인가요?**  
> 핵심 답변: 예방은 교착 상태의 4가지 필요 조건 중 하나 이상이 성립하지 않도록 시스템 구조를 제한하는 방식이다. 회피는 자원 요청이 들어올 때마다 안전 상태를 유지할 수 있는지 검사하고, 불안전 상태로 가는 할당을 거부하거나 지연하는 방식이다.

**Q3. 은행원 알고리즘은 어떤 알고리즘이며, 왜 실제 시스템에 적용하기 어려운가요?**  
> 핵심 답변: 은행원 알고리즘은 각 프로세스의 최대 자원 요구량, 현재 할당량, 사용 가능 자원을 기반으로 자원 할당 후에도 안전 순서가 존재하는지 검사하는 교착 상태 회피 알고리즘이다. 실제 시스템에서는 프로세스의 최대 요구량을 미리 알기 어렵고, 프로세스와 자원이 동적으로 변하며, 검사 비용도 있기 때문에 범용적으로 적용하기 어렵다.

**Q4. 자원 할당 그래프에서 사이클이 있으면 항상 교착 상태인가요?**  
> 핵심 답변: 자원 타입마다 인스턴스가 하나뿐이면 사이클은 교착 상태를 의미한다. 하지만 자원 타입에 여러 인스턴스가 있으면 사이클이 있어도 다른 인스턴스 할당으로 진행 가능할 수 있으므로 반드시 교착 상태라고 할 수는 없다.

**Q5. 실제 애플리케이션에서 교착 상태를 줄이기 위한 방법은 무엇인가요?**  
> 핵심 답변: 락 획득 순서를 통일하고, 락 보유 시간을 줄이며, 외부 API 호출 중 락을 잡지 않고, 타임아웃을 설정하고, 예외 발생 시 반드시 락을 해제해야 한다. DB 트랜잭션은 짧게 유지하고 deadlock error 발생 시 재시도 로직을 구현하는 것이 좋다.

## 관련 개념

- [[프로세스]] - 교착 상태는 여러 프로세스가 자원을 기다릴 때 발생하는 대표적인 운영체제 문제다.
- [[스레드]] - 멀티스레드 프로그램에서 뮤텍스나 세마포어 사용 오류로 교착 상태가 자주 발생한다.
- [[뮤텍스]] - 상호 배제를 구현하는 대표적인 동기화 도구이며 교착 상태의 주요 원인이 될 수 있다.
- [[세마포어]] - 제한된 개수의 자원을 관리할 때 사용되며 잘못 사용하면 교착 상태가 발생할 수 있다.
- [[모니터]] - 고수준 동기화 추상화로, 조건 변수 사용 방식에 따라 대기 문제가 발생할 수 있다.
- [[동기화]] - 교착 상태는 동시성 제어와 동기화의 대표적인 부작용이다.
- [[기아 상태]] - 교착 상태 회복이나 자원 할당 정책에서 특정 프로세스가 계속 선택되지 못할 때 발생할 수 있다.
- [[라이브락]] - 프로세스들이 계속 상태를 바꾸지만 실제 작업은 진행하지 못하는 상태로 교착 상태와 비교된다.
- [[은행원 알고리즘]] - 교착 상태 회피를 설명하는 대표적인 알고리즘이다.
- [[자원 할당 그래프]] - 프로세스와 자원 사이의 요청 및 할당 관계를 시각화하여 교착 상태를 분석하는 도구다.
- [[데이터베이스 트랜잭션]] - 트랜잭션 락 충돌과 교착 상태 탐지 및 롤백이 실제로 자주 다뤄지는 영역이다.
- [[분산 락]] - 클라우드와 분산 시스템에서 교착 상태나 락 미해제 문제와 밀접하게 연결된다.
