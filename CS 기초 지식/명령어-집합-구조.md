# 명령어 집합 구조 - CISC vs RISC의 특징과 장단점

## 핵심 개념

## 명령어 집합 구조(ISA)와 CISC vs RISC

명령어 집합 구조(Instruction Set Architecture, ISA)는 **소프트웨어가 하드웨어를 바라보는 추상 인터페이스**이다. 즉, CPU가 어떤 명령어를 이해하고 실행할 수 있는지, 레지스터는 어떻게 구성되는지, 메모리 접근 방식은 무엇인지, 산술·논리 연산은 어떤 형태로 제공되는지를 정의한다. 대표적인 ISA 계열로는 **x86/x86-64**, **ARM/AArch64**, **RISC-V** 등이 있다.

CISC(Complex Instruction Set Computer)는 이름 그대로 **복잡하고 다양한 명령어를 제공하는 구조**를 말한다. 하나의 명령어가 메모리 접근, 연산, 저장 같은 여러 작업을 한 번에 수행할 수 있도록 설계된 경우가 많다. 대표적으로 x86 계열이 CISC적 특성을 가진 ISA로 분류된다.

반면 RISC(Reduced Instruction Set Computer)는 **단순하고 규칙적인 명령어 집합**을 지향한다. 일반적으로 명령어 길이가 고정되어 있거나 비교적 규칙적이고, 메모리 접근은 주로 `load/store` 명령어로 분리하며, 산술 연산은 레지스터 간에 수행하는 방식이 많다. ARM, RISC-V, MIPS 등이 RISC 계열로 자주 설명된다.

CISC와 RISC의 차이는 단순히 “명령어가 많다/적다”의 문제가 아니다. 핵심은 **명령어의 복잡도, 디코딩 난이도, 파이프라인 설계, 컴파일러 최적화, 전력 효율, 성능 확장 방식**과 깊게 연결된다. 현대 CPU에서는 이 구분이 과거보다 흐려졌다. 예를 들어 x86 CPU는 외부적으로는 CISC ISA를 제공하지만, 내부적으로는 복잡한 x86 명령어를 더 단순한 마이크로 연산, 즉 micro-op으로 변환해 실행하는 경우가 많다. 반대로 ARM 같은 RISC 계열 CPU도 고성능화를 위해 복잡한 분기 예측, 비순차 실행, SIMD 확장 등을 포함한다.

이 주제가 중요한 이유는 운영체제, 컴파일러, 클라우드 인스턴스 선택, 컨테이너 이미지 호환성, 성능 튜닝, 보안 취약점 이해에 직접 연결되기 때문이다. 예를 들어 같은 Linux라도 x86-64용 바이너리는 ARM64 서버에서 그대로 실행되지 않는다. Docker 이미지도 CPU 아키텍처별로 다르게 빌드되어야 하며, 클라우드에서는 x86 기반 인스턴스와 ARM 기반 인스턴스의 가격·성능·전력 효율 특성을 비교해야 한다.

## 내부 동작 원리

## CISC와 RISC의 내부 동작 원리

CPU는 일반적으로 다음과 같은 과정을 통해 명령어를 실행한다.

```text
[메모리의 명령어]
        ↓
[Instruction Fetch: 명령어 가져오기]
        ↓
[Decode: 명령어 해석]
        ↓
[Register Read / Operand Fetch: 피연산자 준비]
        ↓
[Execute: ALU/FPU/Load-Store Unit 실행]
        ↓
[Memory Access: 필요 시 메모리 접근]
        ↓
[Write Back: 결과 저장]
```

이 과정에서 CISC와 RISC는 특히 **Decode 단계**, **명령어 실행 방식**, **메모리 접근 모델**에서 차이를 보인다.

---

## 1. CISC의 동작 특징

CISC 구조에서는 하나의 명령어가 여러 동작을 포함할 수 있다. 예를 들어 개념적으로 다음과 같은 명령을 생각할 수 있다.

```asm
ADD [memory_address], register
```

이 명령어는 단순히 덧셈만 하는 것이 아니라 다음 작업을 포함할 수 있다.

```text
1. 메모리 주소 계산
2. 메모리에서 값 읽기
3. 레지스터 값과 덧셈
4. 결과를 다시 메모리 또는 레지스터에 저장
```

CISC의 특징은 다음과 같다.

- 명령어 길이가 가변적인 경우가 많다.
- 주소 지정 방식이 다양하다.
- 하나의 명령어가 여러 사이클에 걸쳐 실행될 수 있다.
- 명령어 디코딩 로직이 복잡해질 수 있다.
- 프로그램 코드 크기를 줄이는 데 유리한 경우가 있다.

현대 x86 CPU에서는 복잡한 x86 명령어를 내부적으로 더 단순한 micro-op으로 변환해 실행하는 방식이 널리 사용된다.

```text
[x86 CISC 명령어]
        ↓
[복잡한 디코더]
        ↓
[micro-op 1] [micro-op 2] [micro-op 3]
        ↓
[내부 실행 유닛]
        ↓
[결과 저장]
```

즉, 외부에서는 CISC ISA를 유지하면서 내부 실행은 RISC적 형태와 유사하게 구성되는 경우가 있다. 이는 기존 x86 소프트웨어와의 호환성을 유지하면서도 파이프라인, 비순차 실행, 병렬 실행을 효율적으로 구현하기 위한 설계 방식이다.

---

## 2. RISC의 동작 특징

RISC 구조는 명령어를 단순하고 규칙적으로 만드는 것을 목표로 한다. 대표적인 설계 원칙은 다음과 같다.

- 명령어 길이가 고정되어 있거나 규칙적이다.
- 산술 연산은 주로 레지스터 간에 수행한다.
- 메모리 접근은 `load`와 `store` 명령어로 분리한다.
- 명령어 디코딩이 상대적으로 단순하다.
- 파이프라인 설계에 유리하다.
- 컴파일러가 명령어 조합을 최적화하기 쉽다.

예를 들어 메모리의 값을 더하려면 보통 다음과 같은 단계가 필요하다.

```asm
LOAD R1, [A]      ; 메모리 A의 값을 R1에 로드
LOAD R2, [B]      ; 메모리 B의 값을 R2에 로드
ADD  R3, R1, R2   ; R1 + R2를 R3에 저장
STORE [C], R3     ; 결과를 메모리 C에 저장
```

이를 다이어그램으로 표현하면 다음과 같다.

```text
[LOAD]  메모리 → 레지스터
[LOAD]  메모리 → 레지스터
[ADD]   레지스터 → ALU → 레지스터
[STORE] 레지스터 → 메모리
```

RISC는 한 명령어가 하는 일이 작기 때문에 전체 명령어 수는 늘어날 수 있다. 그러나 각 명령어가 단순하고 일정한 형식을 가지므로 CPU 파이프라인을 구성하기 쉽고, 병렬 실행 및 예측 실행 같은 고성능 기법을 적용하기 유리하다.

---

## 3. CISC vs RISC 비교

| 구분 | CISC | RISC |
|---|---|---|
| 설계 철학 | 복잡한 명령어로 많은 작업 수행 | 단순한 명령어를 빠르게 조합 |
| 명령어 길이 | 가변 길이인 경우가 많음 | 고정 길이 또는 규칙적 형식이 많음 |
| 디코딩 | 복잡한 편 | 단순한 편 |
| 메모리 접근 | 연산 명령어가 메모리에 직접 접근할 수 있는 경우가 많음 | 주로 load/store로 분리 |
| 코드 크기 | 상대적으로 작아질 수 있음 | 상대적으로 커질 수 있음 |
| 파이프라인 | 설계가 복잡할 수 있음 | 설계가 비교적 유리 |
| 대표 ISA | x86, x86-64 | ARM, RISC-V, MIPS |
| 현대적 특징 | 내부 micro-op 변환 사용 가능 | 고성능 구현에서 복잡한 내부 구조 사용 |

## 4. 장단점 정리

### CISC 장점

- 복잡한 명령어로 코드 밀도를 높일 수 있다.
- 오래된 소프트웨어와의 호환성을 유지하기 쉽다.
- x86 생태계처럼 성숙한 소프트웨어·하드웨어 생태계를 가질 수 있다.
- 컴파일러가 생성해야 하는 명령어 수가 줄어드는 경우가 있다.

### CISC 단점

- 명령어 디코딩이 복잡하다.
- 파이프라인 및 병렬 실행 설계가 어려워질 수 있다.
- 전력 효율 측면에서 불리할 수 있는 요소가 있다.
- CPU 내부 구현이 복잡해질 수 있다.

### RISC 장점

- 명령어 구조가 단순하고 규칙적이다.
- 파이프라인 구성과 병렬 처리에 유리하다.
- 전력 효율이 좋은 설계를 만들기 쉽다.
- 컴파일러 최적화와 하드웨어 구현이 비교적 명확하다.
- 모바일, 임베디드, 클라우드 ARM 서버 등에서 널리 사용된다.

### RISC 단점

- 같은 작업에 더 많은 명령어가 필요할 수 있다.
- 코드 크기가 증가할 수 있다.
- 특정 복잡 연산은 여러 명령어 조합으로 구현해야 한다.
- ISA와 생태계에 따라 기존 x86 소프트웨어와의 호환성 문제가 생길 수 있다.

## 실제 시스템 연결

## 실제 시스템에서의 CISC와 RISC

## 1. Linux와 CPU 아키텍처

Linux는 특정 CPU ISA에 종속된 운영체제가 아니라 다양한 아키텍처를 지원하는 운영체제 커널이다. 실제로 Linux는 x86-64, ARM64, RISC-V 등 여러 ISA에서 동작할 수 있다. 하지만 **바이너리 실행 파일은 ISA에 종속적**이다.

예를 들어 x86-64 Linux에서 빌드한 실행 파일은 일반적으로 ARM64 Linux에서 그대로 실행되지 않는다.

```bash
$ uname -m
x86_64
```

또는 ARM64 환경에서는 다음과 같이 나올 수 있다.

```bash
$ uname -m
aarch64
```

이 값은 현재 시스템의 CPU 아키텍처를 확인할 때 자주 사용된다.

---

## 2. x86-64 서버

전통적인 서버 환경에서는 x86-64 아키텍처가 매우 널리 사용되어 왔다. Intel Xeon, AMD EPYC 계열 CPU가 대표적인 x86-64 서버 CPU에 해당한다. x86-64는 CISC적 ISA인 x86 계열의 64비트 확장 구조로 볼 수 있다.

실무에서 x86-64의 장점은 다음과 같다.

- 오래된 소프트웨어와의 높은 호환성
- 풍부한 라이브러리 및 드라이버 지원
- 성숙한 가상화 생태계
- 다양한 상용 소프트웨어 지원

예를 들어 일반적인 Linux 서버, 데이터베이스 서버, Nginx 웹 서버, Java 애플리케이션 서버는 x86-64 환경에서 오랫동안 운영되어 왔다.

---

## 3. ARM64 서버

ARM은 RISC 계열 ISA로 분류된다. 과거에는 모바일 및 임베디드 환경에서 강세였지만, 현재는 서버와 클라우드 환경에서도 사용된다. ARM64, 즉 AArch64는 64비트 ARM 아키텍처를 의미한다.

ARM64 서버의 장점으로 자주 언급되는 요소는 다음과 같다.

- 전력 효율 중심 설계에 유리
- 클라우드 환경에서 비용 대비 성능을 개선할 수 있는 경우가 있음
- 컨테이너 기반 워크로드와 잘 결합 가능
- 웹 서버, 마이크로서비스, 캐시 서버 등 수평 확장형 서비스에 적합한 경우가 많음

다만 ARM64 환경에서는 사용하는 소프트웨어, 라이브러리, 네이티브 확장 모듈이 해당 아키텍처를 지원하는지 확인해야 한다.

---

## 4. Nginx와 아키텍처

Nginx 자체는 특정 ISA에만 종속된 소프트웨어가 아니다. 같은 Nginx라도 x86-64용으로 빌드된 바이너리와 ARM64용으로 빌드된 바이너리는 다르다.

예를 들어 Docker Hub에서 제공되는 공식 이미지 중 상당수는 여러 아키텍처를 지원하는 multi-arch 형태로 제공된다. 이 경우 사용자는 동일한 이미지 태그를 사용하더라도, Docker가 실행 환경에 맞는 아키텍처 이미지를 자동으로 선택할 수 있다.

```bash
docker run nginx
```

x86-64 머신에서는 x86-64용 Nginx 이미지가, ARM64 머신에서는 ARM64용 Nginx 이미지가 선택될 수 있다. 단, 실제 지원 여부는 해당 이미지의 manifest를 확인해야 한다.

---

## 5. 컴파일러와 ISA

C/C++ 같은 언어는 소스 코드는 같아도 컴파일 결과물이 ISA에 따라 달라진다.

```bash
gcc main.c -o app
```

위 명령으로 생성된 `app`은 현재 컴파일 환경의 아키텍처에 맞게 생성된다. ARM64용 바이너리를 x86-64 머신에서 만들려면 크로스 컴파일러나 별도의 빌드 환경이 필요하다.

예를 들어 Go 언어에서는 다음과 같이 타깃 아키텍처를 지정할 수 있다.

```bash
GOOS=linux GOARCH=arm64 go build -o app-arm64
GOOS=linux GOARCH=amd64 go build -o app-amd64
```

여기서 `amd64`는 일반적으로 x86-64 아키텍처를 가리키는 Go의 아키텍처 명칭이다.

## 클라우드 연결

## 클라우드 환경에서의 CISC와 RISC

## 1. AWS와 ARM 기반 인스턴스

AWS는 x86 기반 인스턴스뿐 아니라 ARM 기반 인스턴스도 제공한다. AWS Graviton 계열 프로세서는 ARM 기반 서버 프로세서이다. 사용자는 워크로드 특성에 따라 x86 인스턴스와 ARM 인스턴스를 선택할 수 있다.

ARM 기반 인스턴스는 다음과 같은 워크로드에서 고려될 수 있다.

- 웹 서버
- 마이크로서비스
- 컨테이너 기반 애플리케이션
- 캐시 서버
- 일부 데이터 처리 작업
- 스케일아웃 구조의 백엔드 서비스

다만 모든 워크로드가 ARM에서 자동으로 더 좋은 것은 아니다. 다음 요소를 확인해야 한다.

- 애플리케이션이 ARM64에서 빌드 가능한가?
- 사용하는 라이브러리가 ARM64를 지원하는가?
- Docker 이미지가 multi-arch인가?
- 성능 병목이 CPU, 메모리, I/O 중 어디에 있는가?
- JIT, 네이티브 확장, 암호화 라이브러리 등이 ARM 최적화를 지원하는가?

---

## 2. Docker와 Multi-Architecture Image

Docker 컨테이너 이미지는 CPU 아키텍처와 무관한 것처럼 보이지만, 실제로 이미지 내부의 실행 파일은 특정 ISA용 바이너리이다. 따라서 x86-64용 바이너리만 들어 있는 이미지는 ARM64 노드에서 실행되지 않을 수 있다.

이를 해결하기 위해 Docker는 multi-architecture image를 지원한다. 하나의 이미지 태그가 여러 아키텍처별 이미지를 가리키는 manifest list를 가질 수 있다.

```text
nginx:latest
 ├── linux/amd64 이미지
 ├── linux/arm64 이미지
 └── 기타 지원 아키텍처 이미지
```

이미지 정보를 확인할 때는 다음과 같은 명령을 사용할 수 있다.

```bash
docker buildx imagetools inspect nginx:latest
```

멀티 아키텍처 이미지를 빌드할 때는 `docker buildx`를 사용할 수 있다.

```bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myrepo/myapp:latest \
  --push .
```

이 과정에서 CISC 계열 x86-64와 RISC 계열 ARM64를 모두 지원하는 컨테이너 배포가 가능해진다.

---

## 3. Kubernetes와 노드 아키텍처

Kubernetes 클러스터는 서로 다른 CPU 아키텍처의 노드를 포함할 수 있다. 예를 들어 일부 노드는 x86-64, 일부 노드는 ARM64일 수 있다. 이때 스케줄러는 파드가 어느 노드에서 실행될지 결정하지만, 컨테이너 이미지가 해당 노드의 아키텍처를 지원하지 않으면 실행에 실패할 수 있다.

Kubernetes 노드는 일반적으로 아키텍처 정보를 라벨로 가진다.

```bash
kubernetes.io/arch=amd64
kubernetes.io/arch=arm64
```

특정 아키텍처 노드에만 파드를 배치하려면 `nodeSelector` 또는 node affinity를 사용할 수 있다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: arch-specific-pod
spec:
  nodeSelector:
    kubernetes.io/arch: arm64
  containers:
    - name: app
      image: myrepo/myapp:latest
```

이 설정은 해당 파드를 ARM64 노드에 배치하도록 제한한다. 하지만 이미지도 ARM64를 지원해야 정상 실행된다.

## 4. CI/CD와 아키텍처별 빌드

클라우드 네이티브 환경에서는 하나의 애플리케이션을 여러 아키텍처용으로 빌드해야 하는 경우가 많다. 특히 다음과 같은 상황에서 중요하다.

- 개발자는 Apple Silicon 같은 ARM64 장비를 사용
- 운영 서버는 x86-64
- 일부 클라우드 인스턴스는 ARM64
- Kubernetes 클러스터가 혼합 아키텍처로 구성됨

CI/CD 파이프라인에서는 다음을 고려해야 한다.

```text
소스 코드
   ↓
아키텍처별 빌드
   ├── linux/amd64
   └── linux/arm64
   ↓
멀티 아키텍처 이미지 생성
   ↓
레지스트리 푸시
   ↓
Kubernetes 또는 ECS/EKS 등에 배포
```

이때 테스트도 아키텍처별로 수행하는 것이 바람직하다. 같은 코드라도 네이티브 라이브러리, SIMD 명령어, 메모리 정렬, 엔디언 관련 코드에서 차이가 발생할 수 있다.

## CISC와 RISC 관련 보안 이슈

## 1. CPU 아키텍처와 보안 취약점

CPU ISA와 내부 마이크로아키텍처는 보안과도 깊게 연결된다. 특히 현대 CPU의 고성능 기능인 다음 요소들은 보안 취약점과 관련될 수 있다.

- speculative execution, 추측 실행
- out-of-order execution, 비순차 실행
- branch prediction, 분기 예측
- cache hierarchy, 캐시 계층
- micro-op cache
- SMT/Hyper-Threading 계열 동시 멀티스레딩

Spectre, Meltdown 계열 취약점은 단순히 CISC 또는 RISC 중 하나만의 문제가 아니라, 현대 CPU의 성능 최적화 기법과 관련된 보안 이슈로 이해해야 한다. 일부 취약점은 특정 CPU 제품군이나 특정 마이크로아키텍처에 더 직접적으로 연결된다.

---

## 2. CISC와 공격 표면

CISC 계열 ISA는 명령어 형식이 복잡하고 가변 길이인 경우가 많다. 특히 x86에서는 명령어가 바이트 단위로 다양한 위치에서 해석될 수 있기 때문에, 공격자가 ROP(Return-Oriented Programming)나 JOP(Jump-Oriented Programming)에 사용할 수 있는 gadget을 찾는 과정에서 많은 후보가 생길 수 있다.

다만 “CISC라서 무조건 취약하다”라고 말할 수는 없다. 실제 보안성은 ISA뿐 아니라 운영체제 보호 기법, 컴파일러 보안 옵션, 메모리 보호 기능, 실행 권한 정책, CPU의 하드웨어 보안 기능에 의해 결정된다.

---

## 3. RISC와 공격 표면

RISC 계열 ISA는 명령어 형식이 규칙적이고 고정 길이에 가까운 경우가 많아 명령어 디코딩 관점에서는 단순한 편이다. 이 특성은 일부 코드 재사용 공격의 gadget 구성 방식에 영향을 줄 수 있다.

하지만 RISC 구조도 보안 취약점에서 자유롭지 않다. ARM 기반 시스템에서도 메모리 손상 취약점, 권한 상승 취약점, 사이드 채널 공격, 잘못된 펌웨어 구성 문제 등이 발생할 수 있다.

즉, RISC의 단순한 명령어 구조는 구현과 검증 측면에서 장점이 될 수 있지만, 시스템 전체 보안을 자동으로 보장하지는 않는다.

---

## 4. 아키텍처별 보안 기능

현대 CPU와 운영체제는 다양한 하드웨어 보안 기능을 제공한다. 예시는 다음과 같다.

- NX bit / execute disable: 데이터 영역 실행 방지
- ASLR: 주소 공간 배치 난수화
- Stack Canary: 스택 오버플로 탐지
- SMEP/SMAP: 커널 보호 관련 기능
- ARM Pointer Authentication: 포인터 무결성 검증 지원
- ARM Memory Tagging Extension: 메모리 태깅 기반 오류 탐지 지원
- Intel CET: 제어 흐름 보호 지원

⚠️ 확인 필요: 위 기능들의 지원 여부는 CPU 모델, 운영체제 커널 버전, 컴파일러 옵션, 배포판 설정에 따라 달라질 수 있다.

---

## 5. 클라우드 보안 관점

클라우드에서 x86 인스턴스와 ARM 인스턴스를 혼용할 때는 보안 정책도 아키텍처별로 점검해야 한다.

주요 체크리스트는 다음과 같다.

```text
[빌드 보안]
- amd64/arm64 각각 동일한 보안 옵션으로 빌드되는가?
- PIE, RELRO, stack protector, FORTIFY_SOURCE 등이 적용되는가?
- 네이티브 라이브러리의 아키텍처별 취약점이 관리되는가?

[이미지 보안]
- multi-arch 이미지의 각 아키텍처별 레이어가 스캔되는가?
- amd64 이미지는 안전하지만 arm64 이미지에 오래된 패키지가 들어 있지는 않은가?
- SBOM이 아키텍처별로 생성되는가?

[런타임 보안]
- seccomp 프로파일이 해당 아키텍처의 syscall 번호와 호환되는가?
- eBPF, Falco, Cilium 등 보안 도구가 해당 아키텍처를 지원하는가?
- 커널 취약점 패치가 모든 노드 풀에 적용되는가?

[운영 보안]
- Kubernetes 노드 라벨과 taint/toleration이 의도대로 구성되었는가?
- 서로 다른 아키텍처 노드가 동일한 보안 기준으로 관리되는가?
```

특히 seccomp는 시스템 콜 필터링에 사용되며, 아키텍처별 syscall 차이를 고려해야 한다. 컨테이너 이미지만 multi-arch로 만들고 보안 정책을 검증하지 않으면 특정 아키텍처에서만 실행 실패 또는 정책 우회 위험이 생길 수 있다.

## 면접 질문

**Q1. CISC와 RISC의 핵심 차이는 무엇인가요?**  
> 핵심 답변: CISC는 복잡하고 다양한 명령어로 하나의 명령어가 여러 작업을 수행할 수 있는 구조이고, RISC는 단순하고 규칙적인 명령어를 조합해 작업을 수행하는 구조이다. CISC는 디코딩이 복잡할 수 있고 코드 밀도에 유리할 수 있으며, RISC는 파이프라인과 병렬 실행, 전력 효율 측면에서 유리한 설계를 만들기 쉽다.

**Q2. x86 CPU는 CISC인데 왜 내부적으로 RISC처럼 동작한다고 하나요?**  
> 핵심 답변: 현대 x86 CPU는 외부적으로는 x86 CISC ISA를 제공하지만, 복잡한 x86 명령어를 내부적으로 micro-op이라는 더 단순한 연산으로 변환해 실행하는 경우가 많다. 이를 통해 기존 소프트웨어 호환성을 유지하면서도 파이프라인, 비순차 실행, 병렬 실행 같은 고성능 기법을 적용할 수 있다.

**Q3. RISC에서 load/store 구조가 중요한 이유는 무엇인가요?**  
> 핵심 답변: RISC에서는 메모리 접근을 `LOAD`와 `STORE`로 분리하고 산술 연산은 주로 레지스터 간에 수행한다. 이렇게 하면 명령어 형식이 단순해지고 실행 단계가 예측 가능해져 파이프라인 설계와 컴파일러 최적화가 쉬워진다.

**Q4. Docker 이미지가 CPU 아키텍처와 관련 있는 이유는 무엇인가요?**  
> 핵심 답변: 컨테이너는 커널을 공유하지만 이미지 내부의 실행 파일은 특정 ISA용 바이너리이다. x86-64용 바이너리만 포함된 이미지는 ARM64 노드에서 실행되지 않을 수 있다. 이를 해결하기 위해 multi-architecture image와 manifest list를 사용한다.

**Q5. CISC와 RISC 중 어느 쪽이 보안상 더 안전한가요?**  
> 핵심 답변: 단순히 CISC 또는 RISC라는 이유만으로 더 안전하다고 말할 수 없다. 보안성은 ISA뿐 아니라 CPU 마이크로아키텍처, 운영체제 보호 기능, 컴파일러 옵션, 메모리 보호 기법, 패치 상태에 의해 결정된다. 다만 명령어 길이, 디코딩 방식, gadget 구성 가능성 등은 공격 기법에 영향을 줄 수 있다.

## 관련 개념

- [[ISA]] - CPU가 제공하는 명령어, 레지스터, 메모리 모델을 정의하는 소프트웨어와 하드웨어의 인터페이스이다.
- [[마이크로아키텍처]] - 같은 ISA라도 CPU 내부 구현 방식이 달라질 수 있으며, 성능과 보안에 큰 영향을 준다.
- [[파이프라이닝]] - RISC 설계 철학과 밀접하게 연결되는 CPU 성능 향상 기법이다.
- [[비순차 실행]] - 현대 CISC/RISC CPU 모두에서 사용되는 고성능 실행 기법이다.
- [[분기 예측]] - 파이프라인 효율을 높이지만 Spectre 같은 보안 이슈와도 관련된다.
- [[micro-op]] - 복잡한 명령어를 내부적으로 더 단순한 연산으로 변환해 실행할 때 사용되는 개념이다.
- [[x86-64]] - 대표적인 CISC 계열 ISA로 서버, PC, 클라우드 환경에서 널리 사용된다.
- [[ARM64]] - 대표적인 RISC 계열 64비트 ISA로 모바일, 임베디드, 클라우드 서버에서 사용된다.
- [[RISC-V]] - 개방형 RISC ISA로 연구, 임베디드, 일부 상용 시스템에서 사용된다.
- [[컴파일러 최적화]] - ISA 특성에 따라 명령어 선택, 레지스터 할당, 파이프라인 활용 전략이 달라진다.
- [[Docker Multi-Arch Image]] - 서로 다른 CPU 아키텍처에서 동일한 이미지 태그를 사용할 수 있게 하는 배포 방식이다.
- [[Kubernetes Node Selector]] - 특정 CPU 아키텍처 노드에 파드를 배치할 때 사용할 수 있는 스케줄링 기능이다.
- [[Spectre]] - 추측 실행 및 캐시 사이드 채널과 관련된 대표적인 CPU 보안 취약점 계열이다.
- [[ROP]] - ISA의 명령어 구조와 코드 배치에 영향을 받는 코드 재사용 공격 기법이다.
