# Cache - Cache Memory and Locality

## 핵심 개념

## Cache Memory and Locality 핵심 개념

캐시 메모리(Cache Memory)는 CPU와 메인 메모리(DRAM) 사이의 속도 차이를 완화하기 위해 사용되는 작고 빠른 저장 공간이다. CPU 연산 속도는 매우 빠르지만, 메인 메모리 접근은 상대적으로 느리기 때문에 매번 DRAM에서 데이터를 가져오면 CPU가 대기하는 시간이 크게 증가한다. 캐시는 최근에 사용했거나 곧 사용할 가능성이 높은 데이터와 명령어를 CPU 가까이에 저장하여 평균 메모리 접근 시간을 줄이는 역할을 한다.

캐시가 효과적인 이유는 프로그램이 보이는 **지역성(Locality)** 때문이다. 지역성은 프로그램이 메모리에 접근할 때 일정한 패턴을 보이는 성질이다. 대표적으로 **시간 지역성(Temporal Locality)** 과 **공간 지역성(Spatial Locality)** 이 있다. 시간 지역성은 한 번 접근한 데이터가 가까운 미래에 다시 접근될 가능성이 높다는 의미이고, 공간 지역성은 어떤 주소에 접근하면 그 주변 주소도 곧 접근될 가능성이 높다는 의미이다.

예를 들어 반복문에서 같은 변수나 배열 원소를 여러 번 읽는 경우 시간 지역성이 나타난다. 배열을 순차적으로 순회하는 경우에는 현재 접근한 원소 근처의 원소를 곧 접근하므로 공간 지역성이 나타난다. CPU 캐시는 이러한 지역성을 활용하여 필요한 데이터뿐 아니라 인접한 데이터까지 **캐시 라인(Cache Line)** 단위로 가져온다.

캐시 메모리는 컴퓨터 구조에서 매우 중요한 개념이다. 프로그램 성능은 단순히 CPU 클럭이나 명령어 수만으로 결정되지 않고, 메모리 계층 구조를 얼마나 효율적으로 사용하는지에 크게 영향을 받는다. 같은 알고리즘이라도 데이터 접근 패턴이 캐시 친화적인지에 따라 실행 시간이 크게 달라질 수 있다. 따라서 시스템 프로그래밍, 데이터베이스, 운영체제, 고성능 컴퓨팅, 클라우드 환경에서 캐시와 지역성에 대한 이해는 필수적이다.

## 내부 동작 원리

## 내부 동작 원리

### 1. 메모리 계층 구조

일반적인 컴퓨터 시스템은 다음과 같은 메모리 계층 구조를 가진다.

```text
CPU Register
   ↓ 가장 빠름, 가장 작음
L1 Cache
   ↓
L2 Cache
   ↓
L3 Cache / LLC(Last Level Cache)
   ↓
Main Memory(DRAM)
   ↓
SSD / HDD / Network Storage
   ↓ 가장 느림, 가장 큼
```

CPU에 가까울수록 속도는 빠르지만 용량은 작고 비용은 높다. 반대로 CPU에서 멀어질수록 용량은 커지지만 접근 지연 시간이 증가한다. 캐시는 이 계층 구조에서 CPU와 DRAM 사이를 중재한다.

### 2. 캐시 접근 과정

CPU가 특정 메모리 주소의 데이터를 읽으려 할 때 일반적인 흐름은 다음과 같다.

```text
CPU가 주소 A 요청
        ↓
L1 캐시에 주소 A가 있는지 확인
        ↓
있으면 Cache Hit → L1에서 데이터 반환
        ↓
없으면 Cache Miss
        ↓
L2 캐시 확인
        ↓
없으면 L3 캐시 확인
        ↓
없으면 DRAM에서 캐시 라인 단위로 가져옴
        ↓
상위 캐시에 저장 후 CPU에 전달
```

캐시에 요청한 데이터가 있으면 **캐시 히트(Cache Hit)** 라고 한다. 반대로 캐시에 없어서 더 낮은 계층의 메모리에서 데이터를 가져와야 하면 **캐시 미스(Cache Miss)** 라고 한다. 캐시의 성능은 보통 히트율이 높을수록 좋아진다.

### 3. 캐시 라인

캐시는 바이트 단위가 아니라 보통 **캐시 라인(Cache Line)** 이라는 고정 크기 블록 단위로 데이터를 저장한다. CPU가 어떤 주소를 요청하면 해당 주소가 포함된 캐시 라인 전체를 가져온다.

```text
메모리 주소 공간
+------+------+------+------+------+------+------+------+
| A[0] | A[1] | A[2] | A[3] | A[4] | A[5] | A[6] | A[7] |
+------+------+------+------+------+------+------+------+
          ↑ CPU가 A[2] 요청

캐시에는 A[2]만이 아니라 주변 데이터가 포함된 블록이 적재됨
```

이 방식은 공간 지역성을 활용한다. 배열을 순차적으로 접근할 때 한 번의 메모리 로드로 주변 원소까지 캐시에 들어오기 때문에 이후 접근이 빠르게 처리된다.

### 4. 주소 매핑 방식

캐시는 메모리의 모든 데이터를 저장할 수 없으므로, 메모리 주소를 캐시의 특정 위치에 매핑해야 한다. 대표적인 방식은 다음과 같다.

#### Direct-Mapped Cache

하나의 메모리 블록이 캐시의 정확히 한 위치에만 들어갈 수 있다.

```text
Memory Block Number mod Number of Cache Lines → Cache Line Index
```

장점은 구조가 단순하고 빠르다는 점이다. 단점은 서로 다른 메모리 블록이 같은 캐시 라인에 매핑되면 계속 서로를 밀어내는 **충돌 미스(Conflict Miss)** 가 발생할 수 있다.

#### Fully Associative Cache

메모리 블록이 캐시의 어느 위치에도 들어갈 수 있다.

```text
메모리 블록 → 캐시 내 임의 위치
```

충돌 미스가 줄어들지만, 캐시 전체에서 태그를 비교해야 하므로 하드웨어 비용이 커질 수 있다.

#### Set-Associative Cache

Direct-Mapped와 Fully Associative의 절충 방식이다. 캐시는 여러 개의 세트(Set)로 나뉘고, 각 메모리 블록은 특정 세트에 매핑되지만 그 세트 안에서는 여러 위치 중 하나에 저장될 수 있다.

```text
Memory Block
   ↓
Set Index 계산
   ↓
해당 Set 내부의 여러 Way 중 하나에 저장
```

현대 CPU 캐시는 일반적으로 Set-Associative 구조를 많이 사용한다.

### 5. 캐시 주소 구성

메모리 주소는 보통 다음과 같이 나뉜다.

```text
+----------------+-------------+--------------+
|      Tag       | Set Index   | Block Offset |
+----------------+-------------+--------------+
```

- **Tag**: 캐시에 저장된 데이터가 실제 어떤 메모리 블록인지 식별
- **Set Index**: 캐시의 어느 세트에 접근할지 결정
- **Block Offset**: 캐시 라인 내부에서 원하는 바이트 위치 결정

CPU가 주소를 요청하면 Set Index로 캐시 세트를 찾고, 해당 세트 안의 태그들과 주소의 Tag를 비교한다. 일치하는 태그가 있으면 캐시 히트이고, 없으면 캐시 미스이다.

### 6. 캐시 미스의 종류

캐시 미스는 주로 다음과 같이 분류한다.

#### Compulsory Miss

처음 접근하는 데이터라서 캐시에 존재할 수 없는 경우이다. Cold Miss라고도 한다.

#### Capacity Miss

캐시 전체 용량이 부족해서 필요한 데이터가 캐시에서 밀려난 경우이다.

#### Conflict Miss

캐시에 빈 공간이 있어도 매핑 구조 때문에 특정 세트나 라인에서 충돌이 발생하여 생기는 미스이다.

#### Coherence Miss

멀티코어 시스템에서 다른 코어가 같은 메모리 위치를 수정하여 기존 캐시 라인이 무효화되는 경우 발생할 수 있다.

### 7. 교체 정책

캐시에 새 데이터를 넣어야 하는데 해당 위치가 이미 차 있다면 기존 데이터를 제거해야 한다. 이를 결정하는 기준이 **교체 정책(Replacement Policy)** 이다.

대표적인 정책은 다음과 같다.

- **LRU, Least Recently Used**: 가장 오래 사용되지 않은 데이터를 제거
- **FIFO**: 먼저 들어온 데이터를 먼저 제거
- **Random**: 임의로 제거
- **Pseudo-LRU**: 실제 LRU보다 하드웨어 비용을 줄인 근사 방식

실제 CPU의 캐시 교체 정책은 구현마다 다르며, 완전한 LRU가 아닐 수 있다.  
⚠️ 확인 필요: 특정 CPU 모델의 정확한 캐시 교체 정책은 제조사 문서나 마이크로아키텍처 분석 자료를 확인해야 한다.

### 8. 쓰기 정책

CPU가 데이터를 수정할 때 캐시와 메모리를 어떻게 동기화할지도 중요하다.

#### Write-Through

캐시에 쓰는 동시에 하위 메모리에도 즉시 반영한다.

- 장점: 메모리와 캐시의 일관성 유지가 단순함
- 단점: 쓰기 트래픽이 많아질 수 있음

#### Write-Back

먼저 캐시에만 쓰고, 해당 캐시 라인이 나중에 교체될 때 메모리에 반영한다.

- 장점: 메모리 쓰기 횟수 감소
- 단점: 캐시에 수정된 Dirty 상태를 관리해야 함

#### Write-Allocate

쓰기 미스가 발생하면 해당 블록을 캐시에 가져온 뒤 쓴다.

#### No-Write-Allocate

쓰기 미스가 발생해도 캐시에 가져오지 않고 메모리에 직접 쓴다.

### 9. 지역성과 코드 예시

#### 공간 지역성이 좋은 코드

```c
int sum = 0;
for (int i = 0; i < n; i++) {
    sum += arr[i];
}
```

배열 `arr`를 순차적으로 접근하므로 캐시 라인에 함께 적재된 인접 원소들을 효율적으로 사용할 수 있다.

#### 공간 지역성이 나쁜 코드

```c
int sum = 0;
for (int i = 0; i < n; i += 1024) {
    sum += arr[i];
}
```

큰 간격으로 접근하면 캐시 라인에 함께 들어온 주변 데이터를 거의 사용하지 못할 수 있다.

#### 2차원 배열 접근

C 언어의 2차원 배열은 일반적으로 row-major 순서로 저장된다. 따라서 다음 코드는 캐시 친화적이다.

```c
for (int i = 0; i < rows; i++) {
    for (int j = 0; j < cols; j++) {
        sum += matrix[i][j];
    }
}
```

반면 다음 코드는 행을 건너뛰며 접근하므로 캐시 효율이 떨어질 수 있다.

```c
for (int j = 0; j < cols; j++) {
    for (int i = 0; i < rows; i++) {
        sum += matrix[i][j];
    }
}
```

## 실제 시스템 연결

## 실제 시스템 연결

### 1. Linux에서 CPU 캐시 정보 확인

Linux에서는 CPU 캐시 계층 정보를 여러 방식으로 확인할 수 있다.

```bash
lscpu
```

`lscpu` 명령은 CPU 아키텍처, 코어 수, 스레드 수, 캐시 정보 등을 출력한다. 또한 다음 경로에서도 캐시 정보를 확인할 수 있다.

```bash
/sys/devices/system/cpu/cpu0/cache/
```

예를 들어 각 캐시 인덱스 디렉터리에는 다음과 같은 정보가 있을 수 있다.

```bash
cat /sys/devices/system/cpu/cpu0/cache/index0/level
cat /sys/devices/system/cpu/cpu0/cache/index0/type
cat /sys/devices/system/cpu/cpu0/cache/index0/size
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
```

이 정보는 캐시 레벨, 데이터/명령어/통합 캐시 여부, 크기, 캐시 라인 크기 등을 파악하는 데 사용된다.

### 2. perf를 이용한 캐시 성능 분석

Linux의 `perf` 도구를 사용하면 캐시 미스와 관련된 하드웨어 이벤트를 측정할 수 있다.

```bash
perf stat ./program
```

더 구체적으로는 다음과 같은 이벤트를 사용할 수 있다.

```bash
perf stat -e cache-references,cache-misses ./program
```

이 결과를 통해 프로그램이 캐시를 얼마나 효율적으로 사용하는지 대략적으로 분석할 수 있다.  
⚠️ 확인 필요: 사용 가능한 perf 이벤트 이름과 의미는 CPU 아키텍처, 커널 버전, perf 버전에 따라 달라질 수 있다.

### 3. 데이터베이스 시스템

데이터베이스는 캐시와 지역성을 매우 중요하게 고려한다.

예를 들어 B-Tree 인덱스는 디스크 I/O를 줄이기 위한 자료구조로 알려져 있지만, 메모리 상에서도 노드 접근 패턴과 캐시 효율이 성능에 영향을 준다. 최근 데이터베이스 엔진은 메모리 접근 패턴, 페이지 캐시, 버퍼 풀, CPU 캐시 친화적인 자료구조를 고려한다.

대표적인 최적화 관점은 다음과 같다.

- 자주 접근하는 인덱스 페이지를 메모리에 유지
- 순차 스캔에서 공간 지역성 활용
- 컬럼 기반 저장소에서 연속된 컬럼 데이터를 순차 처리
- 해시 테이블에서 캐시 미스를 줄이는 레이아웃 설계

### 4. Nginx와 캐시

Nginx에서 말하는 캐시는 주로 HTTP 응답 캐시, 프록시 캐시, 파일 캐시 등을 의미한다. 이는 CPU 캐시와는 계층이 다르지만, 기본 아이디어는 같다. 느린 계층으로의 접근을 줄이기 위해 자주 사용하는 데이터를 빠른 계층에 저장한다.

예를 들어 Nginx reverse proxy cache는 백엔드 서버에 반복적으로 요청하지 않고, 캐시된 응답을 빠르게 반환할 수 있다.

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m;

server {
    location / {
        proxy_cache my_cache;
        proxy_pass http://backend;
    }
}
```

여기서 Nginx 캐시는 애플리케이션/네트워크 계층의 캐시이고, CPU 캐시는 하드웨어 계층의 캐시이다. 계층은 다르지만 모두 지역성과 재사용성을 활용한다.

### 5. NUMA 시스템과 캐시

멀티소켓 서버에서는 NUMA, 즉 Non-Uniform Memory Access 구조가 사용될 수 있다. CPU 소켓마다 가까운 메모리 영역이 있고, 다른 소켓의 메모리에 접근하면 지연 시간이 증가할 수 있다. 캐시 역시 코어별, 소켓별 공유 구조와 관련된다.

Linux에서는 다음 명령으로 NUMA 정보를 확인할 수 있다.

```bash
numactl --hardware
```

NUMA 환경에서는 스레드가 실행되는 CPU와 데이터가 위치한 메모리 노드를 맞추는 것이 중요할 수 있다. 이를 잘못 배치하면 캐시 효율과 메모리 접근 성능이 저하될 수 있다.

### 6. false sharing

멀티스레드 프로그램에서 서로 다른 스레드가 서로 다른 변수를 수정하더라도, 그 변수들이 같은 캐시 라인에 위치하면 성능 문제가 발생할 수 있다. 이를 **False Sharing** 이라고 한다.

```c
struct Counter {
    long a;
    long b;
};
```

스레드 1이 `a`를 수정하고 스레드 2가 `b`를 수정하더라도 `a`와 `b`가 같은 캐시 라인에 있으면 캐시 일관성 프로토콜 때문에 라인이 계속 무효화될 수 있다. 이를 줄이기 위해 패딩을 넣거나 캐시 라인 정렬을 사용할 수 있다.

## 클라우드 연결

## 클라우드 연결

### 1. Docker 컨테이너와 CPU 캐시

Docker 컨테이너는 애플리케이션 프로세스를 격리하지만, 일반적으로 물리 CPU의 캐시 자체를 컨테이너별로 완전히 분리하지는 않는다. 같은 호스트에서 실행되는 여러 컨테이너는 CPU 코어와 캐시 계층을 공유할 수 있다. 따라서 CPU 집약적인 컨테이너들이 같은 호스트에서 실행되면 캐시 경쟁이 발생할 수 있다.

예를 들어 두 컨테이너가 큰 메모리 영역을 반복적으로 스캔하면 LLC, 즉 Last Level Cache를 서로 밀어내며 성능 저하가 발생할 수 있다.

Docker에서는 CPU 사용량을 제한하거나 특정 CPU에 고정할 수 있다.

```bash
docker run --cpuset-cpus="0-1" my-image
```

이 옵션은 컨테이너가 사용할 CPU를 제한할 수 있다. 다만 CPU 캐시를 직접적으로 독점시키는 것은 아니다.

### 2. Kubernetes와 CPU 자원 관리

Kubernetes에서도 Pod는 노드의 CPU와 캐시를 공유한다. CPU request와 limit은 스케줄링과 CPU 사용량 제어에 영향을 주지만, 일반적인 설정만으로 캐시 사용량을 직접 보장하지는 않는다.

CPU 민감도가 높은 워크로드에서는 다음을 고려할 수 있다.

- CPU request를 명확히 설정
- CPU limit으로 과도한 경쟁 방지
- 전용 노드 풀 사용
- Pod anti-affinity로 경쟁 워크로드 분산
- CPU Manager 정책 활용

Kubernetes의 CPU Manager는 특정 조건에서 Pod에 전용 CPU를 할당할 수 있다.  
⚠️ 확인 필요: CPU Manager의 세부 동작은 Kubernetes 버전, kubelet 설정, QoS 클래스, 노드 환경에 따라 달라질 수 있다.

### 3. 클라우드 VM과 noisy neighbor

AWS EC2, Google Compute Engine, Azure VM과 같은 클라우드 VM은 물리 호스트 위에서 실행된다. 동일 물리 호스트에 여러 테넌트의 VM이 배치될 수 있으며, 이 경우 CPU, 메모리 대역폭, 캐시 같은 공유 자원에서 경쟁이 발생할 수 있다. 이를 흔히 **Noisy Neighbor 문제**라고 한다.

클라우드 제공자는 하이퍼바이저와 스케줄링 정책을 통해 격리와 성능 안정성을 제공하려 하지만, 공유 하드웨어 자원의 특성상 워크로드에 따라 성능 변동이 발생할 수 있다.

성능 민감한 시스템에서는 다음을 고려할 수 있다.

- 전용 호스트 또는 전용 인스턴스 사용
- 더 큰 인스턴스 타입 선택
- CPU pinning 또는 placement 관련 기능 검토
- 벤치마크를 통한 인스턴스 타입 비교
- 지연 시간 민감 서비스는 워크로드 격리

⚠️ 확인 필요: 특정 클라우드 제공자의 인스턴스 격리 수준, CPU 모델, 캐시 구조는 리전, 인스턴스 타입, 시점에 따라 달라질 수 있다.

### 4. AWS에서의 연결

AWS EC2 인스턴스는 CPU 아키텍처와 인스턴스 패밀리에 따라 캐시 구조와 메모리 성능이 다를 수 있다. 고성능 컴퓨팅, 데이터 분석, 인메모리 데이터베이스 워크로드는 CPU 캐시와 메모리 대역폭의 영향을 크게 받는다.

예를 들어 다음과 같은 워크로드는 캐시 효율이 중요하다.

- Redis, Memcached 같은 인메모리 캐시 서버
- 실시간 추천 시스템
- 머신러닝 추론
- 대규모 로그 처리
- 고성능 컴퓨팅 시뮬레이션

AWS에서는 워크로드 특성에 따라 Compute Optimized, Memory Optimized 등 인스턴스 패밀리를 선택한다. 하지만 인스턴스 패밀리 이름만으로 CPU 캐시 성능을 확정할 수는 없다. 실제 성능은 벤치마크로 확인하는 것이 안전하다.

### 5. GCP에서의 연결

GCP Compute Engine에서도 머신 타입에 따라 CPU 플랫폼과 메모리 특성이 달라질 수 있다. 성능 민감 애플리케이션은 가능한 경우 CPU 플랫폼, 머신 타입, 리전 가용성을 확인하고 벤치마크해야 한다.

캐시 친화적인 애플리케이션 설계는 클라우드에서도 그대로 중요하다.

- 배열/버퍼 순차 접근
- 데이터 구조 압축
- 불필요한 포인터 추적 감소
- 배치 처리 크기 조정
- 스레드 간 false sharing 방지

### 6. 분산 캐시와 CPU 캐시의 차이

클라우드에서 Redis, Memcached, CDN, HTTP cache를 “캐시”라고 부르지만, 이들은 CPU 캐시와 목적과 계층이 다르다.

| 구분 | CPU Cache | Redis/Memcached |
|---|---|---|
| 위치 | CPU와 메모리 사이 | 애플리케이션/네트워크 계층 |
| 단위 | 캐시 라인 | Key-Value |
| 제어 주체 | 하드웨어 중심 | 애플리케이션/운영자 |
| 목적 | 메모리 접근 지연 감소 | DB/API 접근 감소 |
| 지역성 | 메모리 주소 기반 | 요청/데이터 재사용 기반 |

핵심 원리는 모두 “느린 계층 접근을 줄이기 위해 빠른 계층에 재사용 가능성이 높은 데이터를 둔다”는 점에서 연결된다.

## 보안 연결

## 보안 연결

### 1. 캐시 사이드 채널 공격

CPU 캐시는 여러 프로세스, 스레드, VM, 컨테이너가 공유할 수 있다. 이 공유 특성 때문에 공격자가 직접 접근 권한이 없는 데이터에 대해서도 캐시 접근 시간 차이를 관찰하여 정보를 추론하는 **캐시 사이드 채널 공격(Cache Side-Channel Attack)** 이 가능할 수 있다.

대표적인 공격 기법은 다음과 같다.

- **Flush+Reload**
- **Prime+Probe**
- **Evict+Time**

이 공격들은 캐시 히트와 캐시 미스의 시간 차이를 이용한다. 예를 들어 특정 메모리 위치가 캐시에 들어와 있으면 접근이 빠르고, 그렇지 않으면 느리다. 공격자는 이 차이를 반복 측정하여 피해자의 메모리 접근 패턴을 추론할 수 있다.

### 2. Spectre와 Meltdown 계열

Spectre와 Meltdown 계열 취약점은 CPU의 추측 실행 또는 비순차 실행과 관련된 취약점으로 알려져 있다. 이 공격들은 비밀 값을 직접 architectural state로 노출하지 않더라도, 캐시 상태와 같은 microarchitectural state에 흔적을 남기고 이를 시간 측정으로 추론하는 방식을 사용할 수 있다.

중요한 점은 캐시가 단순한 성능 최적화 장치가 아니라 보안 경계에 영향을 줄 수 있는 마이크로아키텍처 자원이라는 것이다.

⚠️ 확인 필요: 특정 CPU, 운영체제, 마이크로코드에서 어떤 Spectre/Meltdown 완화책이 적용되는지는 모델과 패치 상태에 따라 달라진다.

### 3. 클라우드 멀티테넌시와 캐시 보안

클라우드 환경에서는 여러 사용자의 VM이나 컨테이너가 같은 물리 호스트의 CPU 자원을 공유할 수 있다. 이론적으로 공유 캐시를 통한 사이드 채널이 문제가 될 수 있다. 클라우드 제공자는 하이퍼바이저 격리, 마이크로코드 패치, 스케줄링 정책, 전용 호스트 옵션 등을 통해 위험을 줄인다.

보안이 특히 중요한 워크로드에서는 다음과 같은 방법을 고려할 수 있다.

- 전용 호스트 또는 전용 인스턴스 사용
- 민감 워크로드와 일반 워크로드 분리
- 최신 커널 및 마이크로코드 업데이트
- 사이드 채널 완화 옵션 확인
- 암호화 라이브러리의 constant-time 구현 사용

### 4. 암호화와 캐시 타이밍 공격

암호화 알고리즘 구현에서 비밀 키 값에 따라 메모리 접근 패턴이 달라지면 캐시 타이밍 공격에 취약할 수 있다. 예를 들어 테이블 기반 구현은 입력이나 키에 따라 다른 테이블 위치를 참조할 수 있고, 이 접근 패턴이 캐시에 흔적을 남길 수 있다.

보안 모범 사례는 다음과 같다.

- 비밀 값에 따른 분기 최소화
- 비밀 값에 따른 메모리 주소 접근 최소화
- constant-time 암호화 라이브러리 사용
- 검증된 암호화 라이브러리 사용
- 자체 암호 구현 지양

### 5. 캐시 격리와 완화 기법

시스템 수준에서는 다음과 같은 완화 기법이 사용될 수 있다.

- 코어/스레드 격리
- SMT/Hyper-Threading 비활성화 검토
- 프로세스/VM 스케줄링 격리
- 페이지 테이블 격리 같은 OS 완화 기법
- 브라우저의 고정밀 타이머 제한
- 하드웨어 또는 OS의 캐시 파티셔닝 기능 활용

⚠️ 확인 필요: Intel CAT(Cache Allocation Technology) 같은 캐시 파티셔닝 기능의 사용 가능 여부와 설정 방법은 CPU 모델, BIOS, 커널, 클라우드 환경에 따라 다르다.

### 6. 성능과 보안의 트레이드오프

캐시 보안 완화책은 종종 성능 저하를 가져올 수 있다. 예를 들어 더 강한 격리, SMT 비활성화, 추가적인 메모리 장벽, 커널 패치 등은 일부 워크로드에서 처리량이나 지연 시간에 영향을 줄 수 있다. 따라서 보안 수준, 위협 모델, 성능 요구사항을 함께 고려해야 한다.

## 면접 질문

## 면접 질문 5개

**Q1. 캐시 메모리가 필요한 이유는 무엇인가요?**  
> 핵심 답변: CPU와 DRAM 사이의 속도 차이를 줄이기 위해 사용한다. 프로그램은 시간 지역성과 공간 지역성을 보이므로, 최근 사용했거나 근처에 있는 데이터를 빠른 캐시에 저장하면 평균 메모리 접근 시간이 줄어든다.

**Q2. 시간 지역성과 공간 지역성의 차이를 설명해보세요.**  
> 핵심 답변: 시간 지역성은 한 번 접근한 데이터가 가까운 미래에 다시 접근될 가능성이 높다는 성질이다. 공간 지역성은 어떤 주소에 접근하면 그 주변 주소도 곧 접근될 가능성이 높다는 성질이다. 반복문 변수 재사용은 시간 지역성, 배열 순차 접근은 공간 지역성의 예이다.

**Q3. 캐시 미스의 종류에는 어떤 것들이 있나요?**  
> 핵심 답변: 처음 접근해서 발생하는 compulsory miss, 캐시 용량 부족으로 발생하는 capacity miss, 매핑 충돌로 발생하는 conflict miss가 대표적이다. 멀티코어 환경에서는 캐시 일관성 때문에 발생하는 coherence miss도 고려할 수 있다.

**Q4. Direct-Mapped Cache와 Set-Associative Cache의 차이는 무엇인가요?**  
> 핵심 답변: Direct-Mapped Cache는 각 메모리 블록이 캐시의 한 위치에만 들어갈 수 있어 구조가 단순하지만 충돌 미스가 많을 수 있다. Set-Associative Cache는 특정 세트 안의 여러 way 중 하나에 저장할 수 있어 충돌 미스를 줄일 수 있다.

**Q5. False Sharing이 무엇이고 어떻게 해결할 수 있나요?**  
> 핵심 답변: 서로 다른 스레드가 서로 다른 변수를 수정하더라도 그 변수들이 같은 캐시 라인에 있으면 캐시 일관성 프로토콜 때문에 성능 저하가 발생할 수 있다. 패딩, 캐시 라인 정렬, 데이터 구조 분리, 스레드별 로컬 데이터 사용 등으로 완화할 수 있다.

## 관련 개념

## 관련 개념

- [[Memory Hierarchy]] - 캐시는 레지스터, DRAM, SSD 등과 함께 메모리 계층 구조의 핵심 요소이다.
- [[Temporal Locality]] - 캐시가 최근 사용한 데이터를 유지하는 근거가 되는 지역성 개념이다.
- [[Spatial Locality]] - 캐시 라인 단위 로딩이 효과적인 이유를 설명하는 지역성 개념이다.
- [[Cache Line]] - 캐시가 데이터를 저장하고 이동시키는 기본 블록 단위이다.
- [[Cache Hit]] - 요청한 데이터가 캐시에 존재하여 빠르게 접근되는 상황이다.
- [[Cache Miss]] - 요청한 데이터가 캐시에 없어 하위 메모리 계층에 접근해야 하는 상황이다.
- [[Set-Associative Cache]] - 현대 캐시에서 널리 사용되는 주소 매핑 방식이다.
- [[Write-Back Cache]] - 수정된 데이터를 즉시 메모리에 쓰지 않고 나중에 반영하는 캐시 쓰기 정책이다.
- [[Cache Coherence]] - 멀티코어 시스템에서 각 코어의 캐시가 일관된 메모리 값을 보도록 하는 메커니즘이다.
- [[MESI Protocol]] - 캐시 일관성을 유지하기 위해 사용되는 대표적인 프로토콜 계열 중 하나이다.
- [[False Sharing]] - 같은 캐시 라인에 있는 독립 변수들이 멀티스레드 환경에서 성능 저하를 유발하는 현상이다.
- [[NUMA]] - 메모리 접근 시간이 CPU와 메모리 위치에 따라 달라지는 구조로 캐시 성능과 밀접하다.
- [[Prefetching]] - 향후 사용할 가능성이 높은 데이터를 미리 캐시에 가져오는 최적화 기법이다.
- [[Cache Side Channel Attack]] - 캐시 접근 시간 차이를 이용해 비밀 정보를 추론하는 보안 공격이다.
- [[Spectre]] - 추측 실행과 캐시 사이드 채널을 활용할 수 있는 대표적인 마이크로아키텍처 취약점이다.
