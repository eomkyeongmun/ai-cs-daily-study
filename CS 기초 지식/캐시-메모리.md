# 캐시 메모리 - 캐시 지역성, 매핑 방식(Direct, Associative, Set-Associative), 히트/미스

## 핵심 개념

# 캐시 메모리(Cache Memory)

캐시 메모리는 CPU와 메인 메모리(DRAM) 사이의 속도 차이를 줄이기 위해 사용되는 작고 빠른 저장 장치이다. CPU는 연산 속도가 매우 빠르지만, 메인 메모리 접근은 상대적으로 느리기 때문에 매번 DRAM에서 데이터를 가져오면 전체 성능이 크게 저하된다. 캐시는 최근에 사용했거나 곧 사용할 가능성이 높은 데이터와 명령어를 저장하여 CPU가 더 빠르게 접근할 수 있도록 한다.

캐시가 효과적인 이유는 프로그램이 보이는 **지역성(Locality)** 때문이다. 지역성은 크게 두 가지로 나뉜다. 첫째, **시간 지역성(Temporal Locality)**은 한 번 접근한 데이터나 명령어가 가까운 미래에 다시 접근될 가능성이 높다는 성질이다. 예를 들어 반복문에서 같은 변수나 명령어가 반복적으로 사용된다. 둘째, **공간 지역성(Spatial Locality)**은 특정 주소에 접근하면 그 주변 주소도 곧 접근될 가능성이 높다는 성질이다. 배열을 순차적으로 순회하는 경우가 대표적이다.

캐시는 보통 데이터를 **캐시 라인(Cache Line)** 단위로 저장한다. CPU가 특정 주소를 요청하면 캐시는 해당 주소의 데이터가 캐시에 있는지 확인한다. 있으면 **캐시 히트(Cache Hit)**, 없으면 **캐시 미스(Cache Miss)**라고 한다. 히트가 많을수록 CPU는 메모리 대기 시간을 줄일 수 있고, 프로그램 성능은 향상된다. 반대로 미스가 많으면 하위 캐시나 메인 메모리까지 접근해야 하므로 지연 시간이 증가한다.

캐시 설계에서 중요한 요소는 **매핑 방식**이다. 메모리 블록을 캐시의 어느 위치에 둘 것인지 결정하는 방식으로, 대표적으로 **Direct Mapped Cache**, **Fully Associative Cache**, **Set-Associative Cache**가 있다. Direct 방식은 단순하고 빠르지만 충돌 미스가 많을 수 있고, Fully Associative 방식은 유연하지만 하드웨어 비용이 크다. Set-Associative 방식은 둘의 절충안으로 실제 CPU 캐시에서 널리 사용된다.

캐시 메모리는 컴퓨터 구조, 운영체제, 컴파일러 최적화, 데이터베이스, 네트워크 서버, 클라우드 성능 튜닝, 보안 취약점 분석까지 폭넓게 연결된다. 특히 현대 시스템에서는 캐시 히트율이 애플리케이션 성능에 큰 영향을 주며, 캐시 타이밍 차이를 악용한 보안 공격도 존재하기 때문에 반드시 이해해야 하는 핵심 개념이다.

## 내부 동작 원리

# 내부 동작 원리

## 1. 캐시 접근 흐름

CPU가 메모리 주소를 요청하면 캐시는 다음 순서로 동작한다.

```text
CPU 주소 요청
   ↓
캐시에서 해당 주소 검색
   ↓
┌───────────────┐
│ 캐시에 존재? │
└───────┬───────┘
        │
   ┌────┴────┐
   │         │
 Hit       Miss
   │         │
데이터 반환  하위 캐시 또는 메모리 접근
             ↓
        캐시에 블록 적재
             ↓
        CPU에 데이터 반환
```

CPU는 일반적으로 바이트 단위 주소를 요청하지만, 캐시는 데이터를 한 바이트씩 저장하지 않고 **캐시 라인** 또는 **블록** 단위로 가져온다. 예를 들어 어떤 주소 `A`를 읽을 때, 캐시는 `A`만 가져오는 것이 아니라 그 주변의 연속된 주소 범위까지 함께 가져온다. 이는 공간 지역성을 활용하기 위한 방식이다.

---

## 2. 주소 분해: Tag, Index, Offset

캐시는 메모리 주소를 보통 다음과 같은 필드로 나누어 해석한다.

```text
메모리 주소
┌────────────┬────────────┬────────────┐
│    Tag     │   Index    │   Offset   │
└────────────┴────────────┴────────────┘
```

- **Offset**
  - 캐시 라인 내부에서 몇 번째 바이트 또는 워드인지 나타낸다.
  - 캐시 라인 크기가 클수록 offset 비트 수가 증가한다.

- **Index**
  - 캐시 내 어느 위치 또는 어느 세트(Set)를 확인할지 결정한다.
  - Direct Mapped Cache와 Set-Associative Cache에서 중요하다.

- **Tag**
  - 실제로 원하는 메모리 블록이 맞는지 확인하는 식별자 역할을 한다.
  - 같은 index에 여러 메모리 블록이 매핑될 수 있으므로 tag 비교가 필요하다.

캐시 엔트리에는 보통 다음 정보가 저장된다.

```text
┌────────┬────────┬──────────────┐
│ Valid  │  Tag   │    Data      │
└────────┴────────┴──────────────┘
```

- **Valid Bit**: 해당 캐시 라인이 유효한 데이터를 담고 있는지 표시
- **Tag**: 메모리 블록 식별자
- **Data**: 실제 캐시 라인 데이터

쓰기 정책에 따라 **Dirty Bit**이 추가될 수 있다.

```text
┌────────┬────────┬────────┬──────────────┐
│ Valid  │ Dirty  │  Tag   │    Data      │
└────────┴────────┴────────┴──────────────┘
```

- **Dirty Bit**: 캐시 데이터가 메모리보다 최신인지 표시  
  - Write-back 정책에서 중요하다.

## 3. 캐시 지역성

## 3.1 시간 지역성

한 번 사용한 데이터가 곧 다시 사용될 가능성이 높다는 원리이다.

예시:

```c
int sum = 0;

for (int i = 0; i < 1000; i++) {
    sum += i;
}
```

위 코드에서 `sum`은 반복문이 실행되는 동안 계속 접근된다. 따라서 `sum`이 캐시에 올라오면 반복적으로 히트할 가능성이 높다.

---

## 3.2 공간 지역성

특정 주소에 접근하면 인접한 주소도 곧 접근될 가능성이 높다는 원리이다.

예시:

```c
int arr[1000];

for (int i = 0; i < 1000; i++) {
    arr[i] = i;
}
```

배열 `arr`는 메모리에 연속적으로 배치된다. `arr[0]`에 접근하면 이후 `arr[1]`, `arr[2]` 등에 접근할 가능성이 높다. 캐시가 한 번에 캐시 라인 단위로 데이터를 가져오기 때문에 순차 접근은 캐시 효율이 좋다.

반면 다음과 같은 접근은 캐시 효율이 낮을 수 있다.

```c
for (int i = 0; i < 1000; i++) {
    arr[i * 64] = i;
}
```

접근 간격이 커지면 한 캐시 라인에 포함된 주변 데이터를 활용하지 못하고 미스가 증가할 수 있다.

---

## 4. 캐시 매핑 방식

## 4.1 Direct Mapped Cache

Direct Mapped Cache는 메모리의 각 블록이 캐시의 정확히 한 위치에만 들어갈 수 있는 방식이다.

```text
메모리 블록 번호 mod 캐시 라인 수 = 캐시 위치
```

구조:

```text
메모리 블록
B0 ─────→ Cache Line 0
B1 ─────→ Cache Line 1
B2 ─────→ Cache Line 2
B3 ─────→ Cache Line 3
B4 ─────→ Cache Line 0
B5 ─────→ Cache Line 1
```

장점:

- 구조가 단순하다.
- 검색할 위치가 하나이므로 접근이 빠르다.
- 하드웨어 구현 비용이 낮다.

단점:

- 서로 다른 메모리 블록이 같은 캐시 라인에 매핑되면 계속 교체된다.
- **충돌 미스(Conflict Miss)**가 발생하기 쉽다.

예를 들어 `B0`와 `B4`가 모두 Cache Line 0에 매핑된다면, 프로그램이 `B0`, `B4`, `B0`, `B4`를 반복 접근할 때 매번 교체가 발생할 수 있다.

---

## 4.2 Fully Associative Cache

Fully Associative Cache는 메모리 블록이 캐시의 어느 위치에나 들어갈 수 있는 방식이다.

```text
메모리 블록 B0 → Cache Line 0, 1, 2, 3 중 아무 곳 가능
```

구조:

```text
메모리 블록
B0 ──┐
B1 ──┼──→ Cache 전체 라인 중 빈 곳 또는 교체 대상
B2 ──┘
```

장점:

- 충돌 미스가 가장 적다.
- 메모리 블록 배치가 유연하다.

단점:

- 캐시 전체의 tag를 병렬로 비교해야 한다.
- 하드웨어 복잡도와 비용이 증가한다.
- 캐시가 커질수록 구현이 부담스럽다.

Fully Associative 방식은 작은 캐시나 TLB 같은 구조에서 활용될 수 있지만, 큰 캐시 전체를 완전 연관 방식으로 구성하는 것은 비용과 전력 측면에서 불리할 수 있다.

---

## 4.3 Set-Associative Cache

Set-Associative Cache는 Direct Mapped와 Fully Associative의 절충안이다. 캐시를 여러 개의 **세트(Set)**로 나누고, 각 메모리 블록은 특정 세트에만 매핑되지만 그 세트 안에서는 여러 위치 중 하나에 들어갈 수 있다.

예: 2-way Set-Associative Cache

```text
캐시
Set 0: [Way 0] [Way 1]
Set 1: [Way 0] [Way 1]
Set 2: [Way 0] [Way 1]
Set 3: [Way 0] [Way 1]
```

매핑:

```text
메모리 블록 번호 mod 세트 수 = 세트 번호
```

예시:

```text
B0 ─────→ Set 0의 Way 0 또는 Way 1
B1 ─────→ Set 1의 Way 0 또는 Way 1
B2 ─────→ Set 2의 Way 0 또는 Way 1
B3 ─────→ Set 3의 Way 0 또는 Way 1
B4 ─────→ Set 0의 Way 0 또는 Way 1
```

장점:

- Direct Mapped보다 충돌 미스가 적다.
- Fully Associative보다 하드웨어 비용이 낮다.
- 실제 CPU 캐시에서 널리 사용되는 방식이다.

단점:

- 같은 세트에 속한 way들의 tag를 비교해야 하므로 Direct보다 복잡하다.
- 세트 내 교체 정책이 필요하다.

## 5. 캐시 히트와 미스

## 5.1 Cache Hit

CPU가 요청한 데이터가 캐시에 존재하는 경우이다.

```text
CPU 요청 주소
   ↓
Index로 세트 선택
   ↓
Tag 비교 성공
   ↓
Offset으로 데이터 선택
   ↓
CPU에 반환
```

히트율은 다음과 같이 표현한다.

```text
Hit Rate = Cache Hit 수 / 전체 메모리 접근 수
```

---

## 5.2 Cache Miss

CPU가 요청한 데이터가 캐시에 없는 경우이다.

```text
CPU 요청 주소
   ↓
캐시 검색
   ↓
Tag 불일치 또는 Valid Bit = 0
   ↓
Miss 발생
   ↓
하위 캐시 또는 메인 메모리 접근
   ↓
캐시에 데이터 적재
   ↓
CPU에 반환
```

미스율은 다음과 같다.

```text
Miss Rate = Cache Miss 수 / 전체 메모리 접근 수
```

또는

```text
Miss Rate = 1 - Hit Rate
```

---

## 6. 캐시 미스의 종류: 3C 모델

캐시 미스는 보통 다음 세 가지로 설명한다.

## 6.1 Compulsory Miss

처음 접근하는 데이터는 캐시에 없으므로 발생하는 미스이다. **Cold Miss**라고도 한다.

예:

```text
프로그램 시작 후 arr[0] 첫 접근
```

---

## 6.2 Capacity Miss

캐시 용량이 부족해서 필요한 데이터가 캐시에서 밀려나 발생하는 미스이다.

예:

```text
작업 집합 크기 > 캐시 크기
```

대규모 배열이나 큰 데이터셋을 반복 접근할 때 발생할 수 있다.

---

## 6.3 Conflict Miss

여러 메모리 블록이 같은 캐시 위치 또는 같은 세트에 매핑되어 서로 밀어내면서 발생하는 미스이다.

특히 Direct Mapped Cache에서 두드러진다.

```text
B0 → Cache Line 0
B4 → Cache Line 0

접근 순서: B0 → B4 → B0 → B4
결과: 반복적인 충돌 미스
```

---

## 7. 캐시 교체 정책

Set-Associative 또는 Fully Associative 캐시에서는 새 블록을 넣기 위해 어떤 기존 블록을 제거할지 결정해야 한다.

대표적인 정책:

- **LRU(Least Recently Used)**
  - 가장 오랫동안 사용되지 않은 블록을 제거
  - 시간 지역성을 활용
  - 정확한 LRU는 way 수가 커질수록 구현 비용이 증가할 수 있음

- **FIFO(First-In, First-Out)**
  - 가장 먼저 들어온 블록을 제거

- **Random Replacement**
  - 임의의 블록을 제거
  - 구현이 단순함

- **Pseudo-LRU**
  - LRU와 유사하게 동작하지만 구현 비용을 줄인 방식
  - 실제 하드웨어에서 사용될 수 있음

---

## 8. 쓰기 정책

캐시에서 쓰기 동작은 읽기보다 더 복잡하다.

## 8.1 Write-Through

캐시에 쓰는 동시에 메인 메모리에도 즉시 반영한다.

장점:

- 메모리와 캐시의 일관성이 비교적 단순하다.

단점:

- 쓰기 트래픽이 증가할 수 있다.

---

## 8.2 Write-Back

일단 캐시에만 쓰고, 해당 캐시 라인이 교체될 때 메인 메모리에 반영한다.

장점:

- 메모리 쓰기 횟수를 줄일 수 있다.

단점:

- Dirty Bit 관리가 필요하다.
- 캐시 일관성 유지가 복잡해질 수 있다.

---

## 8.3 Write-Allocate

쓰기 미스가 발생했을 때 해당 블록을 캐시에 가져온 뒤 쓰는 방식이다.

---

## 8.4 No-Write-Allocate

쓰기 미스가 발생했을 때 캐시에 가져오지 않고 메모리에 직접 쓰는 방식이다.

## 실제 시스템 연결

# 실제 시스템 연결

## 1. 현대 CPU의 다단계 캐시

일반적인 현대 CPU는 여러 단계의 캐시를 사용한다.

```text
CPU Core
   ↓
L1 Cache
   ↓
L2 Cache
   ↓
L3 Cache
   ↓
Main Memory
```

일반적으로 L1 캐시는 가장 빠르지만 용량이 작고, L2는 L1보다 크지만 느리며, L3는 여러 코어가 공유하는 경우가 많다. 단, 실제 구조는 CPU 제조사와 세대, 제품군에 따라 다르다.

또한 많은 CPU는 명령어 캐시와 데이터 캐시를 분리하는 구조를 사용한다.

```text
CPU Core
 ├── L1 I-Cache: 명령어 캐시
 └── L1 D-Cache: 데이터 캐시
```

- **I-Cache**: 실행할 명령어 저장
- **D-Cache**: 연산에 필요한 데이터 저장

이러한 분리는 명령어 fetch와 데이터 load/store를 동시에 효율적으로 처리하기 위한 목적이 있다.

## 2. Linux에서 캐시 관련 관찰

Linux에서는 하드웨어 캐시의 구조를 일부 확인할 수 있다.

예:

```bash
lscpu
```

출력에는 CPU 모델, 코어 수, L1/L2/L3 캐시 정보 등이 포함될 수 있다.

또는 다음 경로에서 캐시 정보를 확인할 수 있다.

```bash
/sys/devices/system/cpu/cpu0/cache/
```

예:

```bash
ls /sys/devices/system/cpu/cpu0/cache/
```

```text
index0  index1  index2  index3
```

각 index 디렉터리에는 다음과 같은 파일이 있을 수 있다.

```bash
cat /sys/devices/system/cpu/cpu0/cache/index0/level
cat /sys/devices/system/cpu/cpu0/cache/index0/type
cat /sys/devices/system/cpu/cpu0/cache/index0/size
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
cat /sys/devices/system/cpu/cpu0/cache/index0/ways_of_associativity
```

확인 가능한 정보:

- 캐시 레벨
- Instruction/Data/Unified 여부
- 캐시 크기
- 캐시 라인 크기
- 연관도, 즉 몇-way set associative인지

## 3. Linux perf를 통한 캐시 미스 측정

Linux에서는 `perf` 도구를 사용해 캐시 관련 이벤트를 측정할 수 있다.

예:

```bash
perf stat ./program
```

또는 캐시 이벤트를 명시할 수 있다.

```bash
perf stat -e cache-references,cache-misses ./program
```

가능한 출력 예:

```text
cache-references
cache-misses
```

이 값들을 통해 프로그램의 캐시 효율을 추정할 수 있다.

⚠️ 확인 필요: `perf`에서 사용할 수 있는 정확한 이벤트 이름과 의미는 CPU 아키텍처, 커널 버전, perf 버전에 따라 달라질 수 있다.

## 4. 행 우선 접근과 열 우선 접근

C 언어의 2차원 배열은 일반적으로 row-major order, 즉 행 우선으로 메모리에 배치된다.

```c
int arr[1024][1024];
```

효율적인 접근:

```c
for (int i = 0; i < 1024; i++) {
    for (int j = 0; j < 1024; j++) {
        arr[i][j]++;
    }
}
```

비효율적일 수 있는 접근:

```c
for (int j = 0; j < 1024; j++) {
    for (int i = 0; i < 1024; i++) {
        arr[i][j]++;
    }
}
```

첫 번째 코드는 메모리상 연속된 위치를 순차적으로 접근하므로 공간 지역성이 좋다. 두 번째 코드는 큰 간격으로 메모리를 접근하게 되어 캐시 미스가 증가할 수 있다.

## 5. 데이터베이스와 캐시 지역성

DBMS는 디스크 I/O뿐 아니라 CPU 캐시 효율도 고려한다. 예를 들어 B-Tree 인덱스는 범위 탐색에 적합하지만, 노드 포인터를 따라가며 메모리의 여러 위치를 접근할 수 있다. 반면 LSM Tree나 columnar storage 같은 구조는 워크로드에 따라 순차 접근성과 압축 효율을 높일 수 있다.

⚠️ 확인 필요: 특정 DBMS가 내부적으로 어떤 캐시 라인 최적화를 사용하는지는 버전과 스토리지 엔진 구현에 따라 다르다.

## 6. Nginx와 캐시 지역성

Nginx 같은 고성능 네트워크 서버는 이벤트 기반 구조를 사용하여 많은 연결을 처리한다. 이때 CPU 캐시 관점에서는 다음 요소가 중요하다.

- 데이터 구조가 작고 연속적일수록 캐시 친화적이다.
- 워커 프로세스가 특정 CPU에 고정되면 캐시 재사용성이 좋아질 수 있다.
- 불필요한 공유 상태를 줄이면 캐시 일관성 트래픽을 줄일 수 있다.

⚠️ 확인 필요: 특정 Nginx 설정이 캐시 히트율에 미치는 영향은 CPU, 커널, 워크로드, 네트워크 카드, TLS 사용 여부 등에 따라 다르다.

## 1. Docker 컨테이너와 CPU 캐시

Docker 컨테이너는 프로세스 격리 기술을 사용하지만, 물리 CPU의 캐시 계층 자체를 독립적으로 소유하는 것은 아니다. 같은 호스트에서 실행되는 여러 컨테이너는 CPU 코어와 캐시 자원을 공유할 수 있다.

```text
Physical Host
 ├── Container A ──┐
 ├── Container B ──┼── CPU Core / Cache / Memory 공유
 └── Container C ──┘
```

따라서 컨테이너 간에는 다음과 같은 성능 간섭이 발생할 수 있다.

- L3 캐시 경쟁
- 메모리 대역폭 경쟁
- NUMA 노드 간 접근 비용 증가
- 컨텍스트 스위칭으로 인한 캐시 오염

이를 완화하기 위해 CPU affinity, cpuset, cgroup CPU 제한 등을 사용할 수 있다.

예:

```bash
docker run --cpuset-cpus="0-1" my-app
```

이 옵션은 컨테이너가 특정 CPU에서 실행되도록 제한하는 데 사용된다.

## 2. Kubernetes와 캐시 친화적 스케줄링

예: CPU Manager static policy

```text
Pod with Guaranteed QoS
   ↓
전용 CPU 코어 할당 가능

스케줄링 변동 감소
   ↓
캐시 재사용성 향상 가능
```

⚠️ 확인 필요: CPU Manager의 동작 조건과 설정 방식은 Kubernetes 버전 및 클러스터 구성에 따라 달라질 수 있다.

## 보안 연결

# 보안 연결

## 1. 캐시 타이밍 사이드 채널

캐시 접근 시간은 히트와 미스에서 차이가 난다. 공격자는 이 시간 차이를 측정하여 피해자가 어떤 데이터를 접근했는지 추론할 수 있다. 이를 **캐시 타이밍 사이드 채널(Cache Timing Side Channel)**이라고 한다.

```text
캐시 히트  → 빠름
캐시 미스  → 느림
시간 차이  → 정보 유출 가능
```

대표적인 공격 기법으로는 다음이 알려져 있다.

- Prime+Probe
- Flush+Reload
- Evict+Time

이들은 공유 캐시나 공유 메모리, 정밀한 시간 측정 기능 등을 활용하여 피해자의 메모리 접근 패턴을 추론할 수 있다.

---

## 2. Spectre와 Meltdown 계열 취약점

CPU의 추측 실행, 비순차 실행, 캐시 상태 변화가 결합되면 민감한 정보가 캐시 사이드 채널을 통해 유출될 수 있다. Spectre와 Meltdown 계열 취약점은 하드웨어 최적화가 보안 경계를 약화시킬 수 있음을 보여준 대표적 사례이다.

일반적인 개념 흐름:

```text
추측 실행
   ↓
권한상 직접 읽을 수 없어야 하는 데이터가 내부적으로 사용될 수 있음
   ↓
캐시 상태 변화 발생
   ↓
공격자가 캐시 접근 시간 측정
   ↓
비밀 정보 추론
```

⚠️ 확인 필요: Spectre, Meltdown의 세부 변종과 영향 범위는 CPU 아키텍처, 마이크로코드, 운영체제 패치 상태에 따라 달라진다.

---

## 3. 클라우드 멀티테넌시와 캐시 공격

클라우드 환경에서는 여러 고객의 VM 또는 컨테이너가 같은 물리 호스트의 CPU 자원을 공유할 수 있다. 이론적으로 공유 캐시를 이용한 사이드 채널 공격 가능성이 존재한다.

```text
Tenant A VM ──┐
              ├── Shared LLC Cache
Tenant B VM ──┘
```

공격자는 같은 물리 호스트에 배치된 피해자의 워크로드와 캐시를 공유할 경우, 캐시 접근 패턴을 관찰해 정보를 추론하려 할 수 있다.

모범 사례:

- 민감 워크로드는 전용 호스트 또는 격리 수준이 높은 환경 사용 검토
- 하이퍼바이저 및 OS 보안 패치 유지
- SMT 비활성화 검토
- 암호화 라이브러리는 constant-time 구현 사용
- 정밀 타이머 접근 제한 검토
- 보안 민감 코드에서 secret-dependent memory access 피하기

⚠️ 확인 필요: 특정 클라우드 제공자의 하드웨어 격리 수준과 완화책은 서비스 종류, 리전, 인스턴스 타입, 시점에 따라 달라질 수 있다.

---

## 4. 암호화 코드와 캐시

암호화 알고리즘 구현에서 비밀 키에 따라 메모리 접근 패턴이 달라지면 캐시 타이밍 공격에 취약할 수 있다. 예를 들어 lookup table 기반 구현은 키 값에 따라 다른 테이블 위치를 접근할 수 있고, 공격자는 캐시 시간 차이를 통해 키 정보를 추론할 수 있다.

보안 구현 원칙:

- secret-dependent branch 피하기
- secret-dependent memory lookup 피하기
- constant-time 알고리즘 사용
- 검증된 암호화 라이브러리 사용
- 컴파일러 최적화가 constant-time 속성을 깨지 않는지 검토

⚠️ 확인 필요: 특정 라이브러리의 constant-time 보장 범위는 버전, 빌드 옵션, CPU 아키텍처에 따라 다를 수 있다.

---

## 5. False Sharing과 성능 기반 DoS

False sharing은 서로 다른 스레드가 서로 다른 변수를 사용하더라도 그 변수들이 같은 캐시 라인에 존재하여 캐시 일관성 트래픽이 증가하는 현상이다. 이는 보안 취약점이라기보다는 성능 문제에 가깝지만, 고부하 서비스에서는 응답 지연 증가나 처리량 저하로 이어질 수 있다.

```text
Cache Line
┌──────────────┬──────────────┐
│ Thread A var │ Thread B var │
└──────────────┴──────────────┘

Thread A와 B가 각각 다른 변수 갱신
   ↓
같은 캐시 라인을 공유하므로 invalidation 반복
   ↓
성능 저하
```

완화 방법:

- 자주 쓰는 공유 변수 분리
- padding 또는 alignment 사용
- per-thread counter 사용
- lock contention 줄이기

## 면접 질문

**Q1. 캐시 메모리가 필요한 이유는 무엇인가요?**  
> 핵심 답변: CPU와 메인 메모리 사이의 속도 차이를 줄이기 위해 필요하다. CPU가 자주 사용하거나 곧 사용할 가능성이 높은 데이터와 명령어를 캐시에 저장하면 메모리 접근 지연을 줄이고 전체 성능을 높일 수 있다. 캐시가 효과적인 근거는 시간 지역성과 공간 지역성이다.

**Q2. 시간 지역성과 공간 지역성의 차이를 설명하세요.**  
> 핵심 답변: 시간 지역성은 한 번 접근한 데이터가 가까운 미래에 다시 접근될 가능성이 높다는 성질이다. 반복문에서 같은 변수나 명령어를 반복 사용하는 경우가 예다. 공간 지역성은 특정 주소를 접근하면 주변 주소도 곧 접근될 가능성이 높다는 성질이다. 배열을 순차적으로 순회하는 경우가 대표적이다.

**Q3. Direct Mapped Cache와 Fully Associative Cache의 차이는 무엇인가요?**  
> 핵심 답변: Direct Mapped Cache는 각 메모리 블록이 캐시의 하나의 고정된 위치에만 들어갈 수 있어 구조가 단순하고 빠르지만 충돌 미스가 많을 수 있다. Fully Associative Cache는 메모리 블록이 캐시의 어느 위치에나 들어갈 수 있어 충돌 미스가 적지만, 모든 라인의 tag를 비교해야 하므로 하드웨어 비용과 복잡도가 크다.

**Q4. Set-Associative Cache는 왜 사용하나요?**  
> 핵심 답변: Direct Mapped와 Fully Associative의 절충안이기 때문이다. 메모리 블록은 특정 세트에 매핑되지만, 그 세트 안의 여러 way 중 하나에 저장될 수 있다. 따라서 Direct 방식보다 충돌 미스를 줄이고, Fully Associative보다 구현 비용을 낮출 수 있다.

**Q5. 캐시 미스의 종류를 설명하세요.**  
> 핵심 답변: 대표적으로 3C 모델이 있다. Compulsory Miss는 처음 접근하기 때문에 발생하는 미스, Capacity Miss는 캐시 용량이 부족해 필요한 데이터가 밀려나 발생하는 미스, Conflict Miss는 여러 메모리 블록이 같은 캐시 위치나 세트에 매핑되어 서로 교체되며 발생하는 미스이다.

## 관련 개념

- [[메모리 계층 구조]] - 캐시는 레지스터, 메인 메모리, 보조 저장장치 사이의 계층 구조에서 핵심 역할을 한다.
- [[CPU 파이프라인]] - 캐시 미스는 명령어 실행 흐름을 지연시켜 파이프라인 stall을 유발할 수 있다.
- [[가상 메모리]] - CPU의 메모리 접근은 주소 변환과 캐시 접근이 함께 고려되어야 한다.
- [[TLB]] - TLB는 가상 주소를 물리 주소로 변환하는 캐시 역할을 하며 캐시 메모리와 밀접하다.
- [[NUMA]] - 멀티소켓 시스템에서 메모리 위치와 캐시 계층은 접근 지연에 큰 영향을 준다.
- [[캐시 일관성]] - 멀티코어 환경에서 각 코어의 캐시가 같은 메모리 값을 일관되게 유지해야 한다.
- [[False Sharing]] - 서로 다른 변수가 같은 캐시 라인에 있어 불필요한 캐시 무효화가 발생하는 현상이다.
- [[성능 프로파일링]] - perf 같은 도구로 캐시 미스, 캐시 참조 등 성능 이벤트를 분석할 수 있다.
- [[운영체제 스케줄링]] - 스레드가 어떤 CPU에서 실행되는지에 따라 캐시 재사용성과 성능이 달라질 수 있다.
- [[사이드 채널 공격]] - 캐시 접근 시간 차이를 이용해 민감 정보를 추론하는 공격과 연결된다.
