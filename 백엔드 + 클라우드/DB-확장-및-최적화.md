# DB 확장 및 최적화 - 파티셔닝, 샤딩, 레플리케이션(Master-Slave), 커넥션 풀

## 핵심 개념

DB 확장 및 최적화는 데이터베이스가 증가하는 데이터량, 트래픽, 동시 접속, 복잡한 쿼리를 안정적으로 처리하도록 구조와 운영 방식을 개선하는 과정이다. 대표적인 기법으로 **파티셔닝**, **샤딩**, **레플리케이션**, **커넥션 풀**이 있다.

**파티셔닝(Partitioning)**은 하나의 논리적 테이블을 여러 물리적 단위로 나누는 방식이다. 예를 들어 주문 테이블을 월별, 지역별, 고객 ID 범위별로 나눌 수 있다. 목적은 특정 범위의 데이터만 빠르게 조회하거나, 오래된 데이터를 쉽게 관리하고, 인덱스 크기를 줄여 성능을 높이는 것이다.

**샤딩(Sharding)**은 데이터를 여러 데이터베이스 서버에 분산 저장하는 방식이다. 파티셔닝이 보통 하나의 DB 인스턴스 내부에서 테이블을 나누는 개념이라면, 샤딩은 여러 DB 노드로 데이터를 수평 분산하는 확장 전략이다. 단일 DB 서버의 CPU, 메모리, 디스크 I/O 한계를 넘어서기 위해 사용된다.

**레플리케이션(Replication)**은 하나의 데이터베이스 변경 사항을 다른 데이터베이스로 복제하는 구조이다. 전통적인 Master-Slave 구조에서는 Master가 쓰기를 담당하고 Slave가 복제 데이터를 받아 읽기 요청을 처리한다. 이를 통해 읽기 부하 분산, 장애 대응, 백업 안정성을 확보할 수 있다.

**커넥션 풀(Connection Pool)**은 애플리케이션이 DB 연결을 매 요청마다 새로 생성하지 않고, 미리 생성된 연결을 재사용하는 기법이다. DB 연결 생성은 TCP 연결, 인증, 세션 초기화 등이 필요해 비용이 크다. 커넥션 풀은 이 비용을 줄이고, 동시에 DB에 과도한 연결이 몰리는 것을 제어한다.

이 네 가지는 백엔드 시스템에서 성능, 확장성, 안정성을 확보하기 위한 핵심 개념이다. 데이터가 적고 트래픽이 낮을 때는 단일 DB와 단순 쿼리 최적화만으로 충분할 수 있지만, 서비스가 성장하면 단일 노드의 한계, 읽기/쓰기 병목, 커넥션 폭주, 장애 복구 문제를 반드시 고려해야 한다.

## 내부 동작 원리

## 1. 파티셔닝 내부 동작 원리

파티셔닝은 하나의 테이블을 여러 파티션으로 나누고, DB 엔진이 쿼리 조건에 따라 필요한 파티션만 접근하도록 한다.

대표적인 방식은 다음과 같다.

- **Range Partitioning**  
  날짜, 숫자 범위 기준으로 나눈다.  
  예: `created_at` 기준으로 2024년 1월, 2월, 3월 데이터 분리

- **List Partitioning**  
  특정 값 목록 기준으로 나눈다.  
  예: `region = 'KR'`, `region = 'US'`, `region = 'JP'`

- **Hash Partitioning**  
  특정 컬럼의 해시값을 기준으로 균등 분산한다.  
  예: `user_id % 4` 결과에 따라 4개 파티션에 저장

- **Composite Partitioning**  
  Range와 Hash 등 여러 방식을 조합한다.

### 파티셔닝 동작 흐름

```text
애플리케이션
   |
   | SELECT * FROM orders WHERE created_at >= '2024-01-01'
   v
DB Query Optimizer
   |
   | 파티션 키 조건 분석
   v
Partition Pruning
   |
   | 필요한 파티션만 선택
   v
orders_2024_01, orders_2024_02 ...
```

여기서 중요한 개념은 **Partition Pruning**이다. 쿼리 조건이 파티션 키를 포함하면 DB는 모든 파티션을 읽지 않고 필요한 파티션만 읽을 수 있다. 예를 들어 월별 파티션 테이블에서 `created_at` 조건이 명확하면 해당 월의 파티션만 접근한다. 반대로 파티션 키를 사용하지 않는 쿼리는 여러 파티션을 모두 탐색할 수 있어 성능상 이점이 줄어든다.

## 2. 샤딩 내부 동작 원리

샤딩은 데이터를 여러 DB 서버에 나누어 저장한다. 이때 어떤 데이터를 어느 샤드에 저장할지 결정하는 기준을 **샤딩 키(Sharding Key)**라고 한다.

예를 들어 `user_id`를 샤딩 키로 사용하면 다음과 같이 분산할 수 있다.

```text
user_id % 4 = 0 -> Shard 0
user_id % 4 = 1 -> Shard 1
user_id % 4 = 2 -> Shard 2
user_id % 4 = 3 -> Shard 3
```

### 샤딩 구조 다이어그램

```text
                Application
                     |
              Sharding Router
        /------------+------------\
       v             v             v
   Shard A       Shard B       Shard C
 users 1~N    users N~M    users M~K
```

샤딩 라우터는 애플리케이션 내부에 구현될 수도 있고, 별도의 미들웨어나 프록시 계층으로 존재할 수도 있다. 요청이 들어오면 샤딩 키를 기준으로 대상 샤드를 결정하고, 해당 DB에만 쿼리를 보낸다.

### 샤딩의 주요 난점

- **샤딩 키 선택이 어렵다.**
  - 특정 샤드에 트래픽이 몰리면 핫스팟이 발생한다.
- **조인 처리가 복잡해진다.**
  - 서로 다른 샤드에 있는 테이블 간 조인은 일반적인 단일 DB 조인처럼 처리하기 어렵다.
- **트랜잭션 처리가 복잡하다.**
  - 여러 샤드에 걸친 원자적 트랜잭션은 구현과 운영 비용이 높다.
- **리샤딩이 어렵다.**
  - 샤드 수를 늘리거나 줄일 때 데이터 재배치가 필요하다.

## 3. 레플리케이션 내부 동작 원리

전통적인 Master-Slave 구조에서는 Master DB가 쓰기 요청을 처리하고, 변경 로그를 Slave DB로 전달한다. Slave는 이 로그를 재생하여 Master와 동일한 데이터 상태를 따라간다.

```text
Client
  |
  | Write
  v
Master DB
  |
  | Binary Log / WAL / Replication Log
  v
Slave DB 1
Slave DB 2
  ^
  |
  | Read
Application
```

DBMS마다 로그 명칭과 내부 구현은 다르지만, 일반적인 원리는 다음과 같다.

1. 애플리케이션이 Master에 INSERT, UPDATE, DELETE 요청을 보낸다.
2. Master는 변경 내용을 트랜잭션 로그에 기록한다.
3. Slave는 Master의 변경 로그를 가져오거나 전달받는다.
4. Slave는 로그를 순서대로 적용한다.
5. 애플리케이션은 읽기 요청을 Slave로 분산할 수 있다.

### 동기식과 비동기식 복제

- **비동기 복제**
  - Master가 Slave 반영 여부를 기다리지 않고 클라이언트에 성공 응답을 반환한다.
  - 쓰기 지연은 낮지만, Master 장애 시 일부 데이터가 Slave에 반영되지 않았을 수 있다.

- **동기 복제**
  - Master가 하나 이상의 Replica 반영을 확인한 후 성공 응답을 반환한다.
  - 데이터 정합성은 높아지지만 쓰기 지연이 증가할 수 있다.

- **반동기 복제**
  - Master가 최소한의 Replica 응답을 기다리는 방식이다.
  - DBMS 구현에 따라 세부 동작은 다르다.

### Replication Lag

Slave가 Master의 변경 사항을 즉시 반영하지 못하는 지연을 **Replication Lag**라고 한다. 이 지연이 커지면 사용자가 방금 수정한 데이터를 Slave에서 조회했을 때 이전 값이 보일 수 있다. 이를 **Read-after-write inconsistency**라고도 한다.

## 4. 커넥션 풀 내부 동작 원리

DB 커넥션은 단순한 함수 호출이 아니라 네트워크 연결, 인증, 세션 설정이 필요한 자원이다. 요청마다 커넥션을 새로 만들면 지연 시간이 증가하고 DB 서버의 연결 수가 급격히 증가한다.

커넥션 풀은 일정 수의 DB 연결을 미리 생성해두고 재사용한다.

```text
Application Threads
   |     |     |
   v     v     v
Connection Pool
 [conn1][conn2][conn3][conn4]
   |     |     |     |
   v     v     v     v
Database Server
```

### 동작 과정

1. 애플리케이션 시작 시 또는 첫 요청 시 풀에 커넥션을 생성한다.
2. 요청 스레드가 DB 작업을 위해 풀에서 커넥션을 빌린다.
3. SQL 실행 후 커넥션을 닫는 대신 풀에 반환한다.
4. 다른 요청이 같은 커넥션을 재사용한다.
5. 풀의 모든 커넥션이 사용 중이면 요청은 대기하거나 타임아웃된다.

### 주요 설정

- **maximum pool size**
  - 동시에 사용할 수 있는 최대 커넥션 수
- **minimum idle**
  - 유휴 상태로 유지할 최소 커넥션 수
- **connection timeout**
  - 커넥션을 얻기 위해 기다리는 최대 시간
- **idle timeout**
  - 유휴 커넥션을 유지하는 시간
- **max lifetime**
  - 커넥션을 재생성하기 전까지 유지하는 최대 시간

커넥션 풀 크기는 단순히 크게 잡는 것이 정답이 아니다. DB 서버가 처리할 수 있는 동시 쿼리 수보다 많은 커넥션을 허용하면 오히려 컨텍스트 스위칭, 락 경쟁, I/O 대기 증가로 성능이 악화될 수 있다.

## 실제 시스템 연결

## 1. Linux 환경에서의 연결

DB 성능 문제는 애플리케이션 코드뿐 아니라 Linux 시스템 자원과 밀접하게 연결된다.

### 주요 확인 지표

- CPU 사용률
- 메모리 사용량
- 디스크 I/O 대기
- 네트워크 연결 수
- 파일 디스크립터 수
- TCP 연결 상태
- 프로세스별 리소스 사용량

예를 들어 커넥션 풀이 너무 크면 DB 서버에는 많은 TCP 연결이 생성된다. Linux에서는 각 소켓이 파일 디스크립터를 사용하므로, 파일 디스크립터 제한이 낮으면 연결 실패가 발생할 수 있다.

```bash
ulimit -n
```

위 명령으로 현재 셸의 파일 디스크립터 제한을 확인할 수 있다.

DB 서버의 네트워크 연결 상태는 다음과 같은 도구로 확인할 수 있다.

```bash
ss -tan
```

디스크 I/O 병목은 `iostat`, `vmstat`, `top`, `htop` 등의 도구로 확인할 수 있다.

## 2. MySQL 계열 사례

MySQL에서는 파티셔닝, 레플리케이션, 커넥션 풀 사용이 모두 일반적으로 활용된다.

### 파티셔닝

MySQL은 Range, List, Hash, Key 파티셔닝 등을 지원한다. 예를 들어 로그성 테이블을 날짜 기준 Range Partition으로 구성하면 오래된 파티션 삭제가 쉬워진다.

```sql
ALTER TABLE access_logs DROP PARTITION p202401;
```

파티션 단위 삭제는 대량 DELETE보다 효율적일 수 있다. 단, 실제 효과는 테이블 구조, 인덱스, 스토리지 엔진, 쿼리 패턴에 따라 달라진다.

### 레플리케이션

MySQL 계열에서는 Primary에서 발생한 변경 사항을 Binary Log 기반으로 Replica에 전달하는 방식이 널리 사용된다. 읽기 요청은 Replica로 보내고, 쓰기 요청은 Primary로 보내는 구조를 많이 사용한다.

```text
Application
   |
   +--> Write -> Primary
   |
   +--> Read  -> Replica 1
   +--> Read  -> Replica 2
```

주의할 점은 복제 지연이다. 결제, 주문 상태 변경, 권한 변경처럼 즉시 일관성이 필요한 조회는 Replica가 아니라 Primary에서 읽는 전략이 필요할 수 있다.

## 3. PostgreSQL 사례

PostgreSQL은 테이블 파티셔닝과 스트리밍 레플리케이션을 지원한다. PostgreSQL의 복제는 WAL, 즉 Write-Ahead Log를 기반으로 동작한다.

읽기 부하가 큰 서비스에서는 Primary는 쓰기를 담당하고, Standby 서버는 읽기를 담당하도록 구성할 수 있다.

```text
PostgreSQL Primary
       |
       | WAL Streaming
       v
PostgreSQL Standby
```

PostgreSQL에서 파티션 테이블을 사용할 때도 쿼리 조건이 파티션 키를 포함해야 파티션 프루닝 효과를 기대할 수 있다.

## 4. Nginx와 DB 확장 구조

Nginx는 직접 DB 샤딩이나 레플리케이션을 수행하지는 않지만, 백엔드 애플리케이션 서버 앞단에서 트래픽을 분산한다. 이때 애플리케이션 서버들은 공통 DB 클러스터에 접근할 수 있다.

```text
Client
  |
  v
Nginx Load Balancer
  |
  +--> App Server 1 --> DB Pool --> Primary/Replica
  +--> App Server 2 --> DB Pool --> Primary/Replica
  +--> App Server 3 --> DB Pool --> Primary/Replica
```

이 구조에서 주의할 점은 애플리케이션 서버 수가 늘어나면 전체 DB 커넥션 수도 함께 증가한다는 것이다.

예를 들어 앱 서버 10대가 각각 최대 커넥션 풀 50개를 가지면 DB 입장에서는 최대 500개의 애플리케이션 커넥션이 발생할 수 있다. 따라서 커넥션 풀 설정은 개별 서버 기준이 아니라 전체 서비스 기준으로 계산해야 한다.

## 5. 대규모 서비스에서의 조합

실제 시스템에서는 네 가지 개념이 함께 사용되는 경우가 많다.

```text
Client
  |
  v
Load Balancer
  |
  v
Application Servers
  |
  v
Connection Pool
  |
  v
Shard Router
  |
  +--> Shard 1 Primary --> Shard 1 Replica
  +--> Shard 2 Primary --> Shard 2 Replica
  +--> Shard 3 Primary --> Shard 3 Replica
```

이 구조에서는 다음과 같은 전략을 사용할 수 있다.

- 사용자 ID 기준으로 샤딩
- 각 샤드 내부에서 Primary/Replica 구성
- 날짜 기준으로 테이블 파티셔닝
- 애플리케이션 서버별 커넥션 풀 제한
- 읽기 요청은 Replica로 분산
- 쓰기 직후 조회는 Primary로 라우팅

## 클라우드 연결

## 1. Docker와의 연결

Docker 환경에서 DB를 컨테이너로 실행할 수 있지만, 운영 환경에서는 데이터 영속성, 백업, 디스크 성능, 장애 복구를 반드시 고려해야 한다.

DB 컨테이너를 사용할 때 중요한 요소는 다음과 같다.

- Docker Volume을 통한 데이터 영속화
- 컨테이너 재시작 시 데이터 보존
- 네트워크 지연과 컨테이너 네트워크 설정
- DB 설정 파일 관리
- 백업 파일 외부 저장

```text
App Container
   |
   | Docker Network
   v
DB Container
   |
   v
Docker Volume
```

커넥션 풀은 애플리케이션 컨테이너 내부에서 동작하는 경우가 많다. 컨테이너 수가 오토스케일링으로 증가하면 전체 DB 커넥션 수가 증가하므로, 풀 크기를 보수적으로 설정해야 한다.

---

## 2. Kubernetes와의 연결

Kubernetes에서는 애플리케이션 Pod가 수평 확장될 수 있다. 이때 각 Pod가 자체 커넥션 풀을 가지면 전체 DB 연결 수는 다음과 같이 증가한다.

```text
전체 최대 DB 커넥션 수 = Pod 수 × Pod당 최대 커넥션 풀 크기
```

예를 들어 Pod가 증가하면 DB가 감당해야 할 연결 수도 비례해 늘어난다. 따라서 HPA를 사용할 때는 DB 연결 한계도 함께 고려해야 한다.

### Kubernetes 구조 예시

```text
Ingress
  |
  v
Service
  |
  +--> App Pod 1 --> Connection Pool
  +--> App Pod 2 --> Connection Pool
  +--> App Pod 3 --> Connection Pool
                         |
                         v
                    Managed DB
```

Kubernetes에서 DB를 직접 StatefulSet으로 운영할 수도 있지만, 운영 난이도가 높다. 스토리지, 백업, 장애 조치, 복제, 업그레이드, 모니터링을 직접 관리해야 하기 때문이다. 많은 서비스는 클라우드 관리형 DB를 사용해 운영 부담을 줄인다.

---

## 3. AWS와의 연결

AWS에서는 DB 확장과 최적화를 위해 여러 관리형 서비스를 사용할 수 있다.

### Amazon RDS

Amazon RDS는 MySQL, PostgreSQL, MariaDB 등 여러 엔진을 관리형으로 제공한다. 운영자는 OS 패치, 백업, 모니터링, 일부 장애 복구 기능을 서비스에 위임할 수 있다.

RDS에서는 Read Replica를 구성해 읽기 트래픽을 분산할 수 있다.

```text
Application
   |
   +--> Write -> RDS Primary
   |
   +--> Read  -> RDS Read Replica
```

주의할 점은 Read Replica에도 복제 지연이 발생할 수 있다는 것이다. 따라서 강한 일관성이 필요한 읽기는 Primary로 보내는 전략이 필요하다.

### Amazon Aurora

Amazon Aurora는 AWS의 관리형 관계형 데이터베이스 서비스이다. Aurora는 읽기 복제본을 통해 읽기 확장을 지원하며, 클러스터 엔드포인트와 리더 엔드포인트를 제공한다.

```text
Application
   |
   +--> Writer Endpoint -> Aurora Writer
   |
   +--> Reader Endpoint -> Aurora Readers
```

애플리케이션은 Writer Endpoint로 쓰기를 보내고, Reader Endpoint로 읽기를 보낼 수 있다.

### Amazon ElastiCache와의 관계

DB 확장 이전에 캐시를 도입해 읽기 부하를 낮출 수 있다. Redis 또는 Memcached 기반 캐시는 반복 조회가 많은 데이터를 DB 대신 메모리에서 제공한다. 단, 캐시는 DB의 대체재가 아니라 부하 완화 수단이다.

---

## 4. GCP와의 연결

GCP에서는 Cloud SQL을 통해 MySQL, PostgreSQL, SQL Server 계열의 관리형 DB를 사용할 수 있다. Cloud SQL은 읽기 복제본을 제공하며, 백업과 모니터링 기능을 함께 제공한다.

```text
GKE App Pods
   |
   v
Cloud SQL Proxy 또는 직접 연결
   |
   v
Cloud SQL Primary / Read Replica
```

GKE에서 Cloud SQL에 접근할 때는 인증, 네트워크, 권한 제어를 함께 고려해야 한다. Cloud SQL Auth Proxy를 사용할 수 있으며, IAM과 서비스 계정을 연계해 접근을 제어할 수 있다.

## 5. 클라우드에서 샤딩을 고려할 때

클라우드 관리형 DB는 수직 확장, 읽기 복제, 스토리지 확장, 백업 자동화 등을 제공하지만, 모든 상황에서 무한 확장을 보장하지는 않는다. 단일 Writer의 한계, 특정 테이블의 쓰기 병목, 매우 큰 데이터셋 관리 문제는 여전히 발생할 수 있다.

샤딩은 다음과 같은 경우 고려된다.

- 단일 DB 인스턴스의 쓰기 처리량 한계에 도달한 경우
- 데이터 크기가 단일 노드 운영 한계를 초과하는 경우
- 특정 테넌트 또는 사용자 그룹별 격리가 필요한 경우
- 지역별 데이터 분산이 필요한 경우

다만 샤딩은 애플리케이션 복잡도를 크게 증가시키므로, 인덱스 최적화, 쿼리 개선, 캐싱, 읽기 복제, 수직 확장, 파티셔닝을 먼저 검토한 뒤 도입하는 것이 일반적이다.

## 보안 연결

## 1. 파티셔닝과 보안

파티셔닝은 보안 기능 자체는 아니지만, 데이터 관리와 접근 제어 전략에 영향을 준다. 예를 들어 개인정보가 포함된 테이블을 날짜별 또는 지역별로 파티셔닝하면 데이터 보존 기간 정책이나 삭제 정책을 적용하기 쉬워질 수 있다.

하지만 파티션을 나눈다고 해서 데이터가 자동으로 암호화되거나 접근 제어가 강화되는 것은 아니다. 파티션별 접근 권한 제어가 필요한 경우 DBMS 기능과 애플리케이션 권한 모델을 함께 설계해야 한다.

### 주의 사항

- 파티션에 개인정보가 포함된 경우 동일하게 암호화 정책 적용
- 오래된 파티션 삭제 시 백업 데이터에도 삭제 정책 반영 필요
- 파티션 키에 민감한 정보 사용 시 노출 위험 검토
- 로그성 테이블 파티션에도 개인정보가 남을 수 있음

---

## 2. 샤딩과 보안

샤딩 환경에서는 데이터가 여러 DB 서버에 분산되므로 보안 관리 지점이 늘어난다.

### 주요 보안 이슈

- 샤드별 계정과 권한 관리
- 샤드 간 네트워크 접근 제어
- 샤딩 라우터의 권한 과다 문제
- 특정 샤드 백업 파일 유출 위험
- 샤드별 암호화 설정 불일치
- 운영자가 잘못된 샤드에 접근하는 문제

### 모범 사례

- 샤드별 최소 권한 계정 사용
- 애플리케이션 계정과 운영자 계정 분리
- 네트워크 레벨에서 DB 접근 IP 제한
- TLS 기반 DB 연결 사용
- 백업 파일 암호화
- 샤드 메타데이터 저장소 접근 제어
- 감사 로그 활성화

샤딩 구조에서는 샤드 매핑 정보가 매우 중요하다. 예를 들어 어떤 사용자가 어느 샤드에 저장되어 있는지 나타내는 메타데이터가 유출되면 공격자가 특정 데이터 위치를 추론할 수 있다. 따라서 샤딩 라우팅 정보도 보호 대상이다.

---

## 3. 레플리케이션과 보안

레플리케이션은 데이터 복제 구조이기 때문에 보안상 공격 표면이 증가한다. Replica도 Primary와 동일하거나 거의 동일한 데이터를 가지므로, Replica가 침해되면 실질적으로 전체 데이터 유출로 이어질 수 있다.

### 주요 보안 이슈

- Replica DB 접근 권한 과다
- 복제 계정 권한 과다
- 암호화되지 않은 복제 트래픽
- 테스트용 Replica에 운영 데이터 복제
- Replica 백업 파일 관리 부실
- 읽기 전용 Replica에서 민감 정보 조회 가능

### 모범 사례

- 복제 전용 계정은 필요한 최소 권한만 부여
- Primary-Replica 간 통신 암호화
- Replica도 Primary와 동일 수준의 보안 설정 적용
- 운영 데이터가 복제되는 환경에는 동일한 접근 통제 적용
- 민감 정보 마스킹 또는 토큰화 검토
- Replica 접근 감사 로그 수집
- 장애 조치 시 권한 설정 검증

특히 읽기 전용 Replica라고 해서 안전한 것은 아니다. 읽기 권한만으로도 개인정보, 인증 정보, 결제 정보 등 민감 데이터를 조회할 수 있다. 따라서 읽기 권한도 엄격히 통제해야 한다.

---

## 4. 커넥션 풀과 보안

커넥션 풀은 DB 연결을 재사용하므로 세션 상태 관리가 중요하다. 이전 요청에서 설정한 세션 변수, 임시 테이블, 트랜잭션 상태, 사용자 컨텍스트가 다음 요청에 영향을 주면 보안 문제가 발생할 수 있다.

### 주요 보안 이슈

- 커넥션 반환 전 트랜잭션 미종료
- 세션 변수 또는 Role이 초기화되지 않음
- Prepared Statement 또는 임시 객체의 부적절한 재사용
- DB 계정 공유로 인한 감사 추적 어려움
- 커넥션 문자열에 비밀번호 하드코딩
- 과도한 풀 크기로 인한 DB 자원 고갈

### 모범 사례

- 커넥션 반환 전 트랜잭션 종료 보장
- 커넥션 풀의 validation query 또는 health check 사용
- DB 계정 비밀번호는 Secret Manager 또는 환경 변수로 관리
- 애플리케이션별 최소 권한 DB 계정 사용
- TLS 연결 사용
- SQL Injection 방지를 위해 Prepared Statement 사용
- 커넥션 누수 감지 설정 활성화
- 풀 크기 제한으로 DB DoS 위험 완화

커넥션 풀에서 중요한 보안 원칙은 “재사용되는 연결이 깨끗한 상태인지 보장하는 것”이다. 트랜잭션이 열린 상태로 반환되거나, 특정 사용자 권한이 설정된 세션이 다른 사용자 요청에서 재사용되면 심각한 데이터 노출로 이어질 수 있다.

---

## 5. 공통 보안 체크리스트

- DB 계정은 최소 권한 원칙 적용
- Primary, Replica, Shard 모두 동일 수준의 보안 기준 적용
- DB 연결은 가능한 암호화
- 백업 파일 암호화 및 접근 제어
- 운영 DB 접근은 감사 로그 기록
- 민감 정보는 암호화, 마스킹, 토큰화 검토
- 개발/테스트 환경에 운영 데이터 복제 금지 또는 비식별화
- 방화벽, 보안 그룹, 네트워크 ACL로 접근 제한
- 장애 조치 후 권한과 네트워크 정책 재검증

## 면접 질문

**Q1. 파티셔닝과 샤딩의 차이는 무엇인가요?**  
> 핵심 답변: 파티셔닝은 하나의 논리적 테이블을 여러 물리적 파티션으로 나누는 방식이고, 보통 단일 DB 인스턴스 내부 최적화에 가깝다. 샤딩은 데이터를 여러 DB 서버에 분산 저장해 수평 확장을 달성하는 방식이다. 파티셔닝은 쿼리 범위 축소와 관리 편의성이 목적이고, 샤딩은 단일 서버 한계를 넘기 위한 확장 전략이다.

**Q2. 파티셔닝을 적용했는데도 쿼리가 빨라지지 않는 이유는 무엇일 수 있나요?**  
> 핵심 답변: 쿼리 조건에 파티션 키가 포함되지 않아 Partition Pruning이 발생하지 않을 수 있다. 또는 파티션 수가 너무 많아 메타데이터 관리 비용이 증가했을 수 있다. 인덱스 설계가 부적절하거나, 쿼리가 여러 파티션을 모두 스캔하는 구조일 수도 있다. 파티셔닝은 모든 쿼리를 자동으로 빠르게 만드는 기능이 아니다.

**Q3. Master-Slave 레플리케이션 구조에서 읽기 요청을 Slave로 보내면 어떤 문제가 생길 수 있나요?**  
> 핵심 답변: 복제 지연으로 인해 최신 데이터가 보이지 않을 수 있다. 사용자가 방금 변경한 데이터를 Slave에서 조회하면 이전 값이 반환될 수 있다. 이를 해결하기 위해 쓰기 직후 일정 시간 동안 Primary에서 읽거나, 강한 일관성이 필요한 요청은 Primary로 라우팅하는 전략을 사용할 수 있다.

**Q4. 커넥션 풀 크기를 크게 설정하면 항상 성능이 좋아지나요?**  
> 핵심 답변: 아니다. 커넥션 풀이 너무 크면 DB 서버에 과도한 동시 쿼리가 몰려 CPU, 메모리, 락, 디스크 I/O 경합이 증가할 수 있다. 또한 애플리케이션 서버 수가 늘어나면 전체 커넥션 수는 `서버 수 × 풀 크기`로 증가한다. 적절한 풀 크기는 DB 처리 능력, 쿼리 응답 시간, 애플리케이션 동시성, 인프라 구조를 고려해 결정해야 한다.

**Q5. 샤딩 키를 선택할 때 고려해야 할 요소는 무엇인가요?**  
> 핵심 답변: 데이터가 균등하게 분산되는지, 특정 샤드에 트래픽이 몰리지 않는지, 주요 쿼리가 샤딩 키를 기준으로 라우팅될 수 있는지, 조인과 트랜잭션 범위가 샤드 내부에 머물 수 있는지를 고려해야 한다. 잘못된 샤딩 키는 핫스팟, 복잡한 크로스 샤드 쿼리, 리샤딩 비용 증가를 유발한다.

- [[Read Replica]] - 읽기 부하 분산을 위해 사용되는 복제 DB 인스턴스이다.
- [[Connection Pool]] - DB 연결 재사용을 통해 연결 생성 비용과 자원 사용을 줄인다.
- [[트랜잭션]] - 샤딩과 레플리케이션 구조에서 일관성 보장을 논의할 때 중요하다.
- [[CAP 이론]] - 분산 DB 환경에서 일관성, 가용성, 분할 허용성의 관계를 이해하는 데 필요하다.
- [[캐시]] - DB 확장 이전 또는 병행해서 읽기 부하를 줄이는 전략이다.
- [[로드 밸런싱]] - 애플리케이션 서버와 읽기 Replica로 트래픽을 분산하는 데 활용된다.
- [[WAL]] - PostgreSQL 등에서 변경 사항을 기록하고 복제와 복구에 사용하는 로그 구조이다.
- [[Binary Log]] - MySQL 계열에서 복제와 변경 기록에 사용되는 로그 개념이다.
- [[장애 조치]] - Primary 장애 시 Replica 승격과 서비스 지속성을 다루는 운영 개념이다.
- [[데이터베이스 백업]] - 파티션, 샤드, Replica 구조에서도 반드시 설계해야 하는 복구 전략이다.
