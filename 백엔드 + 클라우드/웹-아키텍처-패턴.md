# 웹 아키텍처 패턴 - MVC, 계층형 아키텍처, 헥사고날 아키텍처

## 핵심 개념

## 웹 아키텍처 패턴 개요

웹 아키텍처 패턴은 웹 애플리케이션을 구성하는 코드와 책임을 어떻게 나눌지에 대한 설계 방식이다. 백엔드 시스템은 요청 처리, 비즈니스 규칙, 데이터 저장, 외부 API 연동, 인증과 권한 처리 등 다양한 책임을 가진다. 이러한 책임이 한곳에 섞이면 코드 변경이 어렵고, 테스트가 복잡해지며, 장애 원인 추적도 어려워진다. MVC, 계층형 아키텍처, 헥사고날 아키텍처는 모두 “관심사의 분리”를 통해 유지보수성, 테스트 용이성, 확장성을 높이기 위한 대표적인 구조다. 다만 목적과 분리 기준은 서로 다르다. MVC는 주로 사용자 요청과 화면 또는 응답 처리 흐름을 Model, View, Controller로 나누는 패턴이고, 계층형 아키텍처는 Presentation, Application 또는 Service, Domain, Infrastructure 같은 계층으로 책임을 분리한다. 헥사고날 아키텍처는 비즈니스 로직을 중심에 두고 외부 시스템을 포트와 어댑터로 분리하여 외부 기술 변화에 덜 영향을 받도록 설계한다.

## MVC

MVC는 Model, View, Controller의 약자다. Controller는 클라이언트 요청을 받아 적절한 처리를 호출하고, Model은 데이터와 비즈니스 상태를 표현하며, View는 결과를 사용자에게 보여주는 역할을 담당한다. 전통적인 서버 사이드 렌더링 웹 애플리케이션에서는 View가 HTML 템플릿을 의미하는 경우가 많고, REST API 중심 백엔드에서는 View가 JSON 응답 직렬화나 응답 DTO 구성으로 해석되기도 한다. MVC의 목적은 요청 처리 로직, 데이터 처리 로직, 표현 로직을 분리해 변경 영향을 줄이는 것이다. 예를 들어 화면 템플릿이 변경되어도 핵심 비즈니스 로직에는 영향을 덜 주고, 데이터 저장 방식이 바뀌어도 Controller의 요청 라우팅 구조는 크게 변하지 않도록 설계할 수 있다.

## 계층형 아키텍처

계층형 아키텍처는 시스템을 여러 계층으로 나누고, 각 계층이 명확한 책임을 갖도록 구성하는 방식이다. 일반적으로 Presentation Layer, Application 또는 Service Layer, Domain Layer, Persistence 또는 Infrastructure Layer로 나눈다. Presentation Layer는 HTTP 요청, 응답, 인증 컨텍스트 처리 등을 담당하고, Service Layer는 유스케이스 실행 흐름과 트랜잭션 경계를 관리한다. Domain Layer는 핵심 비즈니스 규칙을 표현하며, Infrastructure Layer는 데이터베이스, 메시지 브로커, 외부 API, 파일 시스템 같은 기술 세부사항을 담당한다. 이 구조의 중요성은 변경의 파급 범위를 줄이는 데 있다. 데이터베이스 접근 방식이 바뀌더라도 도메인 규칙은 유지될 수 있고, API 표현 방식이 REST에서 GraphQL로 바뀌어도 내부 유스케이스 로직을 최대한 재사용할 수 있다.

## 헥사고날 아키텍처

헥사고날 아키텍처는 Alistair Cockburn이 제안한 Ports and Adapters 아키텍처로 알려져 있다. 핵심 아이디어는 애플리케이션의 비즈니스 로직을 중심에 두고, 데이터베이스, 웹 프레임워크, 외부 API, 메시지 큐 같은 외부 요소를 어댑터로 분리하는 것이다. 중심부는 외부 기술을 직접 알지 않고, 포트라는 인터페이스를 통해 외부 세계와 통신한다. 예를 들어 주문 생성 유스케이스는 `OrderRepository`라는 포트에 의존하고, 실제 구현체는 JPA, MyBatis, MongoDB, DynamoDB 어댑터 등이 될 수 있다. 이 패턴이 중요한 이유는 테스트와 기술 교체에 강하기 때문이다. 비즈니스 로직은 메모리 기반 가짜 어댑터로도 테스트할 수 있고, 웹 요청이 아닌 배치 작업이나 메시지 소비자에서도 같은 유스케이스를 호출할 수 있다.

## 내부 동작 원리

## MVC 내부 동작 원리

MVC 기반 웹 요청 흐름은 일반적으로 다음과 같다.

```text
Client
  ↓ HTTP Request
Front Controller / Router
  ↓
Controller
  ↓
Service 또는 Model 호출
  ↓
Model / Domain / Repository
  ↓
Database
  ↑
Controller
  ↓
View 또는 Response Serializer
  ↓ HTTP Response
Client
```

1. 클라이언트가 HTTP 요청을 보낸다.
2. 웹 서버 또는 애플리케이션 서버가 요청을 애플리케이션 프레임워크로 전달한다.
3. 라우터 또는 Front Controller가 URL, HTTP Method, Header 등을 기준으로 적절한 Controller를 찾는다.
4. Controller는 요청 파라미터, Path Variable, Body를 검증하거나 DTO로 변환한다.
5. Controller는 직접 비즈니스 로직을 처리하기보다는 보통 Service 또는 Model 계층을 호출한다.
6. Model은 데이터와 상태를 표현하고, 필요한 경우 Repository를 통해 데이터베이스와 상호작용한다.
7. 처리 결과는 View 템플릿, JSON, XML 등의 응답 형태로 변환된다.
8. 클라이언트는 최종 응답을 받는다.

서버 사이드 MVC에서는 View가 HTML 렌더링을 담당한다.

```text
Controller → Model 데이터 전달 → Template Engine → HTML Response
```

REST API에서는 View가 명시적인 템플릿이 아닐 수 있다.

```text
Controller → Response DTO → JSON Serializer → HTTP Response
```

주의할 점은 MVC가 반드시 데이터베이스 접근 구조까지 완벽히 정의하지는 않는다는 것이다. 실제 백엔드에서는 MVC 위에 Service, Repository 계층을 추가하여 계층형 구조와 함께 사용하는 경우가 많다.

## 계층형 아키텍처 내부 동작 원리

대표적인 계층형 아키텍처 흐름은 다음과 같다.

```text
[Presentation Layer]
Controller, Request DTO, Response DTO
        ↓
[Application / Service Layer]
Use Case, Transaction, Authorization Flow
        ↓
[Domain Layer]
Entity, Value Object, Domain Service, Business Rule
        ↓
[Infrastructure / Persistence Layer]
Repository Implementation, ORM, SQL Mapper, External API Client
        ↓
Database, Message Broker, Object Storage, Third-party API
```

일반적인 요청 처리 과정은 다음과 같다.

1. Presentation Layer가 HTTP 요청을 수신한다.
2. 요청 데이터를 Request DTO로 변환하고 기본 입력 검증을 수행한다.
3. Application 또는 Service Layer가 유스케이스를 실행한다.
4. Service Layer는 필요한 도메인 객체를 조회하고, 비즈니스 규칙을 적용한다.
5. Domain Layer는 핵심 규칙을 수행한다. 예를 들어 주문 금액 계산, 재고 차감 가능 여부 판단, 상태 전이 검증 등이 여기에 속한다.
6. Infrastructure Layer는 데이터베이스 저장, 외부 API 호출, 메시지 발행 같은 기술 작업을 수행한다.
7. 결과가 다시 상위 계층으로 올라가 응답 DTO로 변환된다.

계층형 구조에서 중요한 규칙은 의존성 방향이다. 일반적인 구조에서는 상위 계층이 하위 계층을 호출한다. 다만 도메인 중심 설계를 적용하면 Domain Layer가 Infrastructure 구현에 직접 의존하지 않도록 인터페이스를 도메인 또는 애플리케이션 쪽에 두고 구현체를 Infrastructure에 둘 수 있다.

```text
좋은 방향 예시:
Controller → OrderService → OrderRepository(interface) ← JpaOrderRepository

나쁜 방향 예시:
Domain Entity → 특정 ORM Query 직접 실행
```

계층형 아키텍처의 장점은 이해하기 쉽고 대부분의 웹 프레임워크와 잘 맞는다는 점이다. 단점은 프로젝트가 커질수록 Service Layer가 비대해지는 “비대한 서비스 계층” 문제가 생길 수 있다는 것이다.

## 헥사고날 아키텍처 내부 동작 원리

헥사고날 아키텍처는 애플리케이션 중심부와 외부 세계를 분리한다.

```text
                    [Web Adapter]
                         ↓
                  Inbound Port
                         ↓
[CLI Adapter] → [Application Core] ← [Message Consumer Adapter]
                         ↓
                  Outbound Port
                         ↓
          [DB Adapter] [External API Adapter] [Cache Adapter]
```

구성 요소는 다음과 같다.

- **Application Core**: 유스케이스와 도메인 규칙이 위치한다.
- **Inbound Port**: 외부에서 애플리케이션을 호출하기 위한 인터페이스다.
- **Outbound Port**: 애플리케이션이 외부 시스템에 요청하기 위한 인터페이스다.
- **Inbound Adapter**: REST Controller, GraphQL Resolver, CLI Command, Message Consumer 등 입력 수단이다.
- **Outbound Adapter**: DB Repository 구현체, 외부 API Client, 메시지 발행기, 캐시 구현체 등 출력 수단이다.

예시 흐름은 다음과 같다.

```text
HTTP POST /orders
  ↓
OrderController  ── Inbound Adapter
  ↓
CreateOrderUseCase  ── Inbound Port
  ↓
OrderService / Domain Model  ── Application Core
  ↓
PaymentPort, OrderRepositoryPort  ── Outbound Port
  ↓
PgPaymentAdapter, JpaOrderRepositoryAdapter  ── Outbound Adapter
  ↓
Payment Gateway, Database
```

핵심은 내부 코어가 외부 어댑터의 구체 클래스를 직접 알지 않는다는 점이다. 코어는 인터페이스에 의존하고, 실제 구현체 연결은 DI 컨테이너나 설정 코드에서 수행한다. 이 방식은 테스트 시 유리하다.

```text
운영 환경:
CreateOrderUseCase → JpaOrderRepositoryAdapter

테스트 환경:
CreateOrderUseCase → InMemoryOrderRepositoryFake
```

헥사고날 아키텍처는 외부 기술 변경에 강하지만, 작은 프로젝트에서는 인터페이스와 어댑터 수가 많아져 복잡도가 증가할 수 있다. 따라서 시스템 규모와 변경 가능성을 고려해 적용 범위를 정해야 한다.

## 실제 시스템 연결

## Linux 환경과 웹 아키텍처 패턴

Linux 서버에서 웹 애플리케이션은 보통 프로세스로 실행된다. 예를 들어 Java Spring Boot, Node.js Express, Python Django/FastAPI, Go HTTP 서버 등이 Linux 프로세스로 실행되고, Nginx 같은 웹 서버 또는 리버스 프록시가 앞단에서 요청을 전달한다.

```text
Client
  ↓
Nginx
  ↓
Backend Application Process
  ↓
Database / Cache / External API
```

이때 애플리케이션 내부 구조가 MVC, 계층형, 헥사고날 중 어떤 패턴을 따르더라도 Linux 입장에서는 하나 이상의 프로세스와 네트워크 포트로 동작한다. 그러나 내부 구조가 잘 분리되어 있으면 장애 원인 분석과 기능 변경이 쉬워진다. 예를 들어 HTTP 500 오류가 발생했을 때 Controller 요청 매핑 문제인지, Service 비즈니스 로직 문제인지, Repository의 SQL 문제인지 분리해서 추적할 수 있다.

## Nginx와 MVC

Nginx는 정적 파일 서빙, 리버스 프록시, TLS 종료, 로드 밸런싱 등에 자주 사용된다. MVC 애플리케이션과 함께 사용할 경우 Nginx는 클라이언트 요청을 백엔드 Controller로 전달하는 앞단 역할을 한다.

```text
Browser
  ↓ HTTPS
Nginx
  ↓ HTTP 또는 HTTPS
Spring MVC / Django / Rails
  ↓
Controller → Model → View
```

서버 사이드 렌더링 구조에서는 백엔드가 HTML을 생성하고 Nginx가 이를 클라이언트에 전달한다. API 서버 구조에서는 백엔드가 JSON 응답을 생성하고, 프론트엔드 정적 파일은 Nginx 또는 CDN에서 제공할 수 있다.

## Spring, Django, Rails의 MVC 계열 구조

Spring MVC는 DispatcherServlet을 중심으로 Controller, Model, ViewResolver 등의 구성 요소를 제공한다. Django는 공식적으로 MTV(Model-Template-View) 패턴이라는 용어를 사용하지만, 관심사의 분리 측면에서 MVC와 비교해 설명되는 경우가 많다. Ruby on Rails는 MVC 구조를 적극적으로 사용하는 웹 프레임워크로 알려져 있다.

⚠️ 확인 필요: 프레임워크별 최신 내부 구현 세부사항은 버전별로 달라질 수 있으므로 사용하는 버전의 공식 문서를 확인해야 한다.

## 실제 계층형 아키텍처 예시

일반적인 백엔드 프로젝트 구조는 다음처럼 구성될 수 있다.

```text
src/main/java/com/example/order
 ├── controller
 │    └── OrderController.java
 ├── service
 │    └── OrderService.java
 ├── domain
 │    ├── Order.java
 │    └── OrderStatus.java
 ├── repository
 │    └── OrderRepository.java
 └── infrastructure
      └── JpaOrderRepository.java
```

실제 운영 시스템에서는 이 구조가 인증, 결제, 주문, 배송, 정산 등 도메인별 모듈과 결합된다. 계층형 아키텍처는 팀원이 빠르게 구조를 이해하기 좋고, 대부분의 웹 프레임워크 예제와도 잘 맞는다. 다만 모든 비즈니스 로직이 `OrderService` 같은 클래스에 몰리면 유지보수가 어려워질 수 있다.

## 실제 헥사고날 아키텍처 예시

헥사고날 구조에서는 패키지를 기술 계층이 아니라 역할 중심으로 나눌 수 있다.

```text
order
 ├── application
 │    ├── port
 │    │    ├── in
 │    │    │    └── CreateOrderUseCase.java
 │    │    └── out
 │    │         └── SaveOrderPort.java
 │    └── service
 │         └── CreateOrderService.java
 ├── domain
 │    └── Order.java
 └── adapter
      ├── in
      │    └── web
      │         └── OrderController.java
      └── out
           └── persistence
                └── JpaOrderPersistenceAdapter.java
```

이 구조에서는 REST API, 배치 작업, 메시지 소비자가 모두 같은 `CreateOrderUseCase`를 호출할 수 있다.

```text
REST Controller ┐
Batch Job       ├── CreateOrderUseCase → Domain → SaveOrderPort
Message Consumer┘
```

이 방식은 입력 채널이 여러 개인 시스템, 외부 시스템 연동이 잦은 시스템, 테스트 가능성이 중요한 시스템에서 특히 유용하다.

## Docker와 아키텍처 패턴

Docker는 애플리케이션 실행 환경을 컨테이너 이미지로 패키징한다. MVC, 계층형, 헥사고날 아키텍처는 애플리케이션 내부 코드 구조에 관한 개념이고, Docker는 실행 및 배포 단위에 관한 기술이다. 서로 다른 계층의 개념이지만 함께 사용하면 효과적이다.

```text
Docker Image
 ├── Application Code
 │    ├── Controller
 │    ├── Service
 │    ├── Domain
 │    └── Adapter / Repository
 ├── Runtime
 └── Config
```

헥사고날 아키텍처에서는 환경별 어댑터를 바꿔 끼우기 쉽다. 예를 들어 로컬 개발에서는 In-memory DB 어댑터를 사용하고, 운영 컨테이너에서는 PostgreSQL 어댑터를 사용할 수 있다. 다만 운영 코드에서 환경별 구현체가 혼란스럽게 섞이지 않도록 설정 관리가 중요하다.

## Kubernetes와 계층형 구조

Kubernetes는 컨테이너화된 애플리케이션의 배포, 확장, 복구를 관리한다. 웹 애플리케이션 내부가 MVC든 헥사고날이든 Kubernetes는 Pod, Service, Ingress 같은 리소스를 통해 트래픽을 전달한다.

```text
Client
  ↓
Ingress
  ↓
Service
  ↓
Pod
  ↓
Application Container
  ↓
Database / Cache / Message Broker
```

계층형 아키텍처와 Kubernetes는 책임 분리 관점에서 함께 이해할 수 있다. 애플리케이션 내부에서는 Controller, Service, Repository로 관심사를 나누고, 인프라에서는 Ingress, Service, Deployment, ConfigMap, Secret으로 배포 책임을 나눈다.

주의할 점은 애플리케이션 내부 계층을 Kubernetes 리소스와 1:1로 대응시키면 안 된다는 것이다. 예를 들어 Controller Layer를 별도 Pod로 나누고 Service Layer를 별도 Pod로 나누는 방식은 일반적인 계층형 아키텍처의 의미와 다르다. 그런 구조는 분산 시스템 또는 마이크로서비스 설계 문제가 된다.

## AWS와 웹 아키텍처 패턴

AWS에서 웹 애플리케이션은 다양한 방식으로 배포될 수 있다.

```text
Route 53
  ↓
CloudFront / ALB
  ↓
ECS / EKS / EC2 / Lambda
  ↓
RDS / DynamoDB / ElastiCache / SQS / SNS / S3
```

- **MVC 애플리케이션**: EC2, ECS, EKS, Elastic Beanstalk 등에 배포해 HTTP 요청을 Controller에서 처리할 수 있다.
- **계층형 애플리케이션**: Service Layer에서 RDS 트랜잭션 처리, SQS 메시지 발행, S3 파일 저장 등을 조합할 수 있다.
- **헥사고날 애플리케이션**: Outbound Port를 통해 저장소나 메시징 시스템에 접근하고, AWS용 Adapter에서 RDS, DynamoDB, SQS, SNS, S3 등을 구현할 수 있다.

예시:

```text
CreateOrderUseCase
  ↓
OrderRepositoryPort
  ↓
DynamoDbOrderRepositoryAdapter 또는 RdsOrderRepositoryAdapter
```

이렇게 구성하면 저장소 변경 가능성을 코드 구조상 더 명확하게 관리할 수 있다.

## 서버리스와 헥사고날 아키텍처

AWS Lambda, Google Cloud Functions, Azure Functions 같은 서버리스 환경에서는 HTTP 요청, 이벤트, 메시지 등 다양한 트리거가 함수 실행을 유발한다. 헥사고날 아키텍처는 이런 구조와 잘 맞는다. Lambda Handler를 Inbound Adapter로 보고, 실제 비즈니스 로직은 Application Core에 둔다.

```text
API Gateway Event
  ↓
Lambda Handler  ── Inbound Adapter
  ↓
Use Case
  ↓
Domain
  ↓
DynamoDB / SQS / External API Adapter
```

이렇게 하면 Lambda에 종속적인 코드가 핵심 비즈니스 로직으로 퍼지는 것을 줄일 수 있다. 테스트할 때도 Lambda 이벤트 객체 없이 Use Case를 직접 호출할 수 있다.

## GCP와 실제 연결

GCP에서는 Cloud Run, Google Kubernetes Engine, Compute Engine, App Engine 등을 통해 웹 애플리케이션을 실행할 수 있다. Cloud SQL, Firestore, Pub/Sub, Cloud Storage 같은 서비스는 Infrastructure Layer 또는 Outbound Adapter에서 다루는 외부 시스템으로 볼 수 있다.

```text
Cloud Load Balancing
  ↓
Cloud Run / GKE
  ↓
Application Core
  ↓
Cloud SQL / Firestore / Pub/Sub / Cloud Storage
```

헥사고날 아키텍처에서는 `EventPublisherPort`를 만들고 Pub/Sub 구현체를 어댑터로 둘 수 있다. 계층형 구조에서는 Infrastructure Layer에 Pub/Sub Client를 두고 Service Layer가 이를 호출하는 형태가 될 수 있다.

## 보안 연결

## MVC와 보안

MVC 구조에서 보안상 중요한 지점은 Controller와 View다. Controller는 외부 입력이 처음 애플리케이션 코드로 들어오는 경계이므로 입력 검증, 인증 여부 확인, 권한 확인이 중요하다. View는 사용자에게 응답을 렌더링하는 영역이므로 XSS 방어가 중요하다.

대표적인 보안 이슈는 다음과 같다.

- **입력값 검증 누락**: 잘못된 데이터가 Service나 DB 계층까지 전달될 수 있다.
- **Mass Assignment 취약점**: 요청 Body를 도메인 객체나 엔티티에 직접 바인딩할 때, 사용자가 변경하면 안 되는 필드까지 수정될 수 있다.
- **XSS**: View 템플릿에서 사용자 입력을 적절히 이스케이프하지 않으면 스크립트가 실행될 수 있다.
- **CSRF**: 쿠키 기반 인증을 사용하는 웹 애플리케이션에서 상태 변경 요청이 위조될 수 있다.
- **민감 정보 노출**: View 또는 JSON 응답에 비밀번호 해시, 내부 ID, 토큰 등이 포함될 수 있다.

모범 사례는 다음과 같다.

```text
HTTP Request
  ↓
Controller: 인증, 권한, 입력 검증
  ↓
DTO 변환
  ↓
Service: 비즈니스 권한 검증
  ↓
Domain: 상태 전이 규칙 검증
  ↓
Repository
```

Controller에서 기본 검증을 하더라도, 중요한 권한 검사는 Service 또는 Domain 수준에서도 확인하는 것이 안전하다. API 경로만 보호하고 내부 유스케이스를 보호하지 않으면 다른 진입점이 생겼을 때 문제가 될 수 있다.

## 계층형 아키텍처와 보안

계층형 아키텍처에서는 보안 책임을 계층별로 분리할 수 있다.

- **Presentation Layer**: 인증 토큰 검증, 요청 크기 제한, 기본 입력 형식 검증
- **Application / Service Layer**: 사용자 권한, 소유권, 유스케이스 실행 가능 여부 확인
- **Domain Layer**: 비즈니스 불변식, 상태 전이 규칙 강제
- **Infrastructure Layer**: SQL Injection 방어, 안전한 외부 API 호출, Secret 관리

예를 들어 “사용자가 자신의 주문만 취소할 수 있다”는 규칙은 단순히 Controller에서만 검사하면 위험하다. 같은 취소 기능이 관리자 도구, 배치, 메시지 소비자 등 다른 경로에서 호출될 수 있기 때문이다. 따라서 Service Layer 또는 Domain Layer에서 소유권과 상태 전이 규칙을 함께 검증하는 것이 좋다.

```text
CancelOrderService
  ↓
주문 조회
  ↓
요청 사용자와 주문 소유자 비교
  ↓
주문 상태가 취소 가능한지 확인
  ↓
취소 처리
```

Infrastructure Layer에서는 SQL Injection 방어를 위해 Prepared Statement, ORM의 파라미터 바인딩, 안전한 쿼리 빌더를 사용하는 것이 일반적이다. 단, ORM을 사용한다고 모든 Injection 위험이 사라지는 것은 아니다. 문자열 결합으로 동적 쿼리를 만들면 여전히 위험할 수 있다.

## 헥사고날 아키텍처와 보안

헥사고날 아키텍처에서는 보안 경계를 Inbound Adapter, Application Core, Outbound Adapter로 나누어 생각할 수 있다.

```text
Inbound Adapter
  - 인증 토큰 파싱
  - 요청 형식 검증
  - API Rate Limit 연동

Application Core
  - 권한 정책
  - 도메인 규칙
  - 유스케이스 실행 가능 여부

Outbound Adapter
  - DB 접근 제어
  - Secret 사용
  - 외부 API TLS 검증
  - Timeout / Retry 정책
```

중요한 원칙은 외부 어댑터에만 보안 규칙을 두지 않는 것이다. 예를 들어 REST Controller에서만 권한 검사를 하고 메시지 소비자에서는 같은 검사를 하지 않으면, 메시지 경로를 통해 권한 우회가 발생할 수 있다. 따라서 핵심 권한 정책은 Application Core 또는 Domain 정책으로 위치시키는 것이 안전하다.

헥사고날 아키텍처는 테스트 측면에서도 보안에 유리하다. `UserAuthorizationPort`, `PermissionChecker`, `PolicyService` 같은 추상화를 두면 권한 시나리오를 단위 테스트로 검증하기 쉽다.

```text
테스트 예시:
- 소유자가 아닌 사용자는 주문 취소 불가
- 이미 배송된 주문은 일반 사용자가 취소 불가
- 관리자는 특정 조건에서 취소 가능
```

## 클라우드 환경 보안과 연결

클라우드 환경에서는 애플리케이션 아키텍처와 IAM, Secret 관리, 네트워크 보안이 함께 고려되어야 한다.

- AWS에서는 IAM Role을 통해 애플리케이션이 S3, SQS, DynamoDB 등에 접근할 수 있다.
- Kubernetes에서는 Secret, ServiceAccount, NetworkPolicy 등을 사용해 접근 범위를 제한할 수 있다.
- Docker 이미지에는 비밀번호, API Key, 개인 키를 포함하지 않는 것이 모범 사례다.
- Nginx 또는 Ingress에서 TLS를 종료하더라도 내부 통신 보안 요구사항은 시스템 정책에 따라 별도로 검토해야 한다.
- Outbound Adapter는 외부 API 호출 시 Timeout을 설정하고, TLS 인증서 검증을 비활성화하지 않아야 한다.

헥사고날 구조에서는 AWS S3 Adapter, GCP Pub/Sub Adapter, DB Adapter처럼 외부 연동 코드가 분리되므로 Secret 사용 지점을 파악하기 쉽다. 계층형 구조에서는 Infrastructure Layer가 Secret과 외부 Client 설정을 담당하도록 분리하는 것이 좋다.

## 면접 질문

**Q1. MVC 패턴에서 Model, View, Controller의 역할은 무엇인가요?**  
> 핵심 답변: Controller는 요청을 받아 흐름을 제어하고, Model은 데이터와 상태 또는 비즈니스 정보를 표현하며, View는 결과를 사용자에게 표현한다. REST API에서는 View가 JSON 응답 직렬화나 Response DTO 구성으로 해석될 수 있다. 핵심은 요청 처리, 데이터 처리, 표현 로직의 분리다.

**Q2. 계층형 아키텍처에서 Controller에 비즈니스 로직을 많이 넣으면 어떤 문제가 생기나요?**  
> 핵심 답변: Controller가 HTTP 요청 처리와 비즈니스 규칙을 동시에 담당하게 되어 재사용성과 테스트 용이성이 떨어진다. 같은 기능을 배치, 메시지 소비자, 다른 API에서 재사용하기 어렵고, 인증·권한·검증 로직이 중복될 수 있다. 비즈니스 로직은 Service 또는 Domain Layer로 이동시키는 것이 일반적으로 좋다.

**Q3. 계층형 아키텍처와 헥사고날 아키텍처의 가장 큰 차이는 무엇인가요?**  
> 핵심 답변: 계층형 아키텍처는 계층 간 책임 분리에 초점을 두며 일반적으로 Presentation → Service → Domain/Repository → Infrastructure 흐름을 가진다. 헥사고날 아키텍처는 Application Core를 중심에 두고 외부 시스템을 Port와 Adapter로 분리한다. 핵심 차이는 비즈니스 로직이 외부 기술에 의존하지 않도록 의존성 방향을 더 강하게 통제한다는 점이다.

**Q4. 헥사고날 아키텍처에서 Port와 Adapter는 각각 무엇인가요?**  
> 핵심 답변: Port는 애플리케이션 코어가 외부와 통신하기 위해 정의한 인터페이스다. Inbound Port는 외부가 애플리케이션을 호출하는 진입점이고, Outbound Port는 애플리케이션이 DB, 외부 API, 메시지 브로커 등을 호출하기 위한 추상화다. Adapter는 이 Port를 실제 기술로 연결하는 구현체다.

**Q5. MVC, 계층형, 헥사고날 중 어떤 구조를 선택해야 하나요?**  
> 핵심 답변: 작은 CRUD 중심 애플리케이션은 MVC와 단순 계층형 구조만으로 충분할 수 있다. 비즈니스 규칙이 복잡하고 테스트가 중요하며 외부 시스템 연동이 많거나 입력 채널이 여러 개라면 헥사고날 아키텍처가 유리할 수 있다. 중요한 것은 패턴 자체가 아니라 변경 가능성, 팀 역량, 시스템 복잡도에 맞게 책임과 의존성을 관리하는 것이다.
