# 시스템 확장 - Scale-up vs Scale-out, 로드 밸런싱(L4 vs L7) 전략

## 핵심 개념

## 시스템 확장: Scale-up vs Scale-out, L4 vs L7 로드 밸런싱

시스템 확장이란 증가하는 트래픽, 데이터, 요청 처리량을 감당하기 위해 서버와 인프라의 처리 능력을 키우는 아키텍처 전략이다. 백엔드 시스템은 초기에는 단일 서버로도 충분할 수 있지만, 사용자가 늘어나면 CPU, 메모리, 네트워크 대역폭, 디스크 I/O, 데이터베이스 커넥션 수 등이 병목이 된다. 이때 대표적인 확장 방식이 **Scale-up**과 **Scale-out**이다.

**Scale-up**은 기존 서버의 성능을 높이는 방식이다. 예를 들어 CPU 코어 수를 늘리거나, 메모리를 증설하거나, 더 빠른 디스크를 사용하는 방식이다. 구조가 단순하고 애플리케이션 변경이 적다는 장점이 있지만, 하드웨어 성능에는 물리적 한계가 있고 장애 발생 시 단일 장애 지점이 될 수 있다.

반면 **Scale-out**은 서버 대수를 늘려 여러 인스턴스가 요청을 나누어 처리하게 하는 방식이다. 수평 확장이라고도 하며, 대규모 웹 서비스에서 일반적으로 사용된다. Scale-out을 제대로 활용하려면 여러 서버 앞단에서 요청을 분산하는 **로드 밸런서**가 필요하다.

로드 밸런싱은 클라이언트 요청을 여러 서버로 분산하여 특정 서버에 부하가 집중되지 않도록 하는 기술이다. 로드 밸런서는 동작 계층에 따라 주로 **L4 로드 밸런서**와 **L7 로드 밸런서**로 구분한다. L4는 OSI 4계층인 전송 계층 정보를 기반으로 TCP/UDP 연결을 분산하고, L7은 OSI 7계층인 애플리케이션 계층 정보를 기반으로 HTTP 헤더, URL 경로, 쿠키, 호스트명 등을 분석하여 라우팅한다.

이 개념이 중요한 이유는 시스템의 성능, 가용성, 장애 대응, 배포 전략, 비용 구조에 직접적인 영향을 주기 때문이다. 단순히 서버를 많이 늘린다고 좋은 아키텍처가 되는 것은 아니며, 애플리케이션의 상태 관리, 세션 처리, 데이터베이스 병목, 캐시 전략, 네트워크 구조까지 함께 고려해야 안정적인 확장이 가능하다.

## 내부 동작 원리

## 1. Scale-up 동작 원리

Scale-up은 하나의 서버 자원을 더 강하게 만드는 방식이다.

```text
[Client]
   |
   v
[Single Server]
 CPU ↑ / RAM ↑ / Disk I/O ↑ / Network ↑
   |
   v
[Database]
```

예를 들어 기존 서버가 4 vCPU, 8GB RAM으로 동작하다가 트래픽 증가로 CPU 사용률이 지속적으로 높아지면 8 vCPU, 16GB RAM 인스턴스로 변경할 수 있다. 이 방식은 애플리케이션 구조 변경이 적고 운영이 단순하다.

하지만 다음과 같은 한계가 있다.

- 서버 한 대의 성능에는 상한이 있다.
- 서버 장애 시 전체 서비스가 중단될 수 있다.
- 고성능 장비는 비용이 비선형적으로 증가할 수 있다.
- 배포나 점검 시 서비스 중단 위험이 크다.

따라서 Scale-up은 초기 단계, 단순한 시스템, 상태 공유가 복잡한 시스템에서는 유용하지만, 대규모 트래픽 처리에는 Scale-out과 함께 고려되는 경우가 많다.

---

## 2. Scale-out 동작 원리

Scale-out은 동일한 역할의 서버 인스턴스를 여러 대 두고 요청을 나누어 처리하는 방식이다.

```text
             ┌──────────────┐
[Client] --> │ Load Balancer│
             └──────┬───────┘
                    |
     ┌──────────────┼──────────────┐
     v              v              v
[App Server 1] [App Server 2] [App Server 3]
     |              |              |
     └──────────────┼──────────────┘
                    v
              [Database / Cache]
```

Scale-out에서 핵심은 각 애플리케이션 서버가 가능한 한 **무상태성 Stateless**을 유지하는 것이다. 예를 들어 사용자의 로그인 세션을 특정 서버 메모리에만 저장하면, 다음 요청이 다른 서버로 전달될 때 인증 상태를 알 수 없다. 이를 해결하기 위해 세션을 Redis 같은 외부 저장소에 두거나, JWT 같은 토큰 기반 인증을 사용할 수 있다.

Scale-out의 주요 장점은 다음과 같다.

- 서버를 추가해 처리량을 늘릴 수 있다.
- 일부 서버 장애 시에도 전체 서비스가 계속 동작할 수 있다.
- 무중단 배포, 카나리 배포, 블루-그린 배포와 잘 결합된다.
- 클라우드 환경에서 오토스케일링과 연동하기 좋다.

단점도 있다.

- 로드 밸런서, 서비스 디스커버리, 헬스 체크가 필요하다.
- 데이터베이스나 캐시가 새로운 병목이 될 수 있다.
- 분산 시스템 특유의 네트워크 장애, 일관성 문제가 발생할 수 있다.
- 세션, 파일 업로드, 로컬 캐시 등 상태 관리가 복잡해진다.

## 3. 로드 밸런싱 기본 과정

로드 밸런서는 일반적으로 다음 순서로 동작한다.

```text
1. 클라이언트가 서비스 도메인으로 요청
2. DNS가 로드 밸런서의 IP 또는 엔드포인트 반환
3. 클라이언트가 로드 밸런서에 연결
4. 로드 밸런서가 백엔드 서버 상태 확인
5. 알고리즘에 따라 대상 서버 선택
6. 요청 또는 연결을 해당 서버로 전달
7. 서버 응답을 클라이언트에게 반환
```

대표적인 분산 알고리즘은 다음과 같다.

| 알고리즘 | 설명 |
|---|---|
| Round Robin | 서버에 순서대로 요청 분배 |
| Weighted Round Robin | 서버 성능에 따라 가중치를 두고 분배 |
| Least Connections | 현재 연결 수가 가장 적은 서버로 분배 |
| IP Hash | 클라이언트 IP를 해시하여 특정 서버로 분배 |
| Least Response Time | 응답 시간이 짧은 서버를 우선 선택 |

로드 밸런서는 단순히 요청을 나누는 장치가 아니라, 장애 감지와 트래픽 제어 역할도 한다. 일반적으로 백엔드 서버에 대한 **헬스 체크 Health Check**를 수행하고, 실패한 서버는 트래픽 대상에서 제외한다.

## 4. L4 로드 밸런싱 동작 원리

L4 로드 밸런서는 전송 계층 정보를 기반으로 동작한다. 주로 다음 정보를 사용한다.

- 출발지 IP
- 출발지 포트
- 목적지 IP
- 목적지 포트
- 프로토콜 TCP/UDP

L4 로드 밸런서는 HTTP 메시지의 URL, 헤더, 쿠키 내용은 일반적으로 해석하지 않는다. 대신 TCP 연결 또는 UDP 패킷 단위로 빠르게 트래픽을 분산한다.

```text
[Client]
   |
 TCP/UDP
   v
[L4 Load Balancer]
   |
   ├── TCP Connection -> [Server A]
   ├── TCP Connection -> [Server B]
   └── TCP Connection -> [Server C]
```

L4 방식은 애플리케이션 계층을 깊게 분석하지 않기 때문에 상대적으로 처리 오버헤드가 낮고, HTTP뿐 아니라 다양한 TCP/UDP 기반 프로토콜에 사용할 수 있다. 예를 들어 데이터베이스 프록시, 게임 서버, 실시간 통신, TCP 기반 API 게이트웨이 앞단에 사용할 수 있다.

다만 URL 경로별 라우팅, HTTP 헤더 기반 라우팅, 쿠키 기반 세션 유지 등 세밀한 제어는 어렵다.

---

## 5. L7 로드 밸런싱 동작 원리

L7 로드 밸런서는 애플리케이션 계층 정보를 분석하여 요청을 분산한다. HTTP/HTTPS 환경에서 많이 사용되며 다음 정보를 기반으로 라우팅할 수 있다.

- URL Path: `/api`, `/static`, `/admin`
- Host Header: `api.example.com`, `www.example.com`
- HTTP Header
- Cookie
- Query Parameter
- HTTP Method
- Content type

예시 구조는 다음과 같다.

```text
[Client]
   |
 HTTPS Request
   v
[L7 Load Balancer]
   |
   ├── /api/*     -> [API Server Group]
   ├── /static/*  -> [Static Server Group]
   ├── /admin/*   -> [Admin Server Group]
   └── Host: img.example.com -> [Image Server Group]
```

L7 로드 밸런서는 요청 내용을 이해할 수 있기 때문에 다음과 같은 전략이 가능하다.

- 경로 기반 라우팅
- 도메인 기반 라우팅
- 헤더 기반 카나리 배포
- 쿠키 기반 Sticky Session
- TLS 종료 Termination
- WAF 연동
- HTTP 리다이렉트
- 압축, 캐싱, 인증 연동

단점은 L4보다 처리해야 할 정보가 많아 상대적으로 오버헤드가 크고, HTTPS 요청을 분석하려면 TLS 종료 또는 TLS 복호화 구조가 필요하다는 점이다.

## 실제 시스템 연결

## 1. Linux에서의 확장과 로드 밸런싱

Linux 서버에서 Scale-up은 CPU, 메모리, 디스크, 네트워크 인터페이스 성능 향상으로 볼 수 있다. 운영 중인 서버에서는 다음 지표를 관찰하여 병목을 판단한다.

```bash
top
htop
vmstat
iostat
sar
ss -ant
```

예를 들어 CPU 사용률이 높다면 애플리케이션 연산 병목일 수 있고, `iostat`에서 디스크 대기 시간이 높다면 디스크 I/O 병목일 수 있다. `ss -ant`를 통해 TCP 연결 상태를 확인하면 연결 수 증가나 TIME_WAIT 누적 등을 확인할 수 있다.

Linux 기반 로드 밸런싱에는 다음 기술들이 사용될 수 있다.

- **IPVS**: Linux 커널 레벨의 L4 로드 밸런싱 기능
- **iptables/nftables**: 패킷 필터링 및 NAT
- **HAProxy**: L4/L7 로드 밸런싱 지원
- **Nginx**: HTTP 리버스 프록시 및 L7 로드 밸런싱에 널리 사용
- **Envoy**: 서비스 메시와 클라우드 네이티브 환경에서 많이 사용되는 프록시

---

## 2. Nginx 로드 밸런싱 예시

Nginx는 HTTP 기반 L7 로드 밸런서 또는 리버스 프록시로 자주 사용된다.

```nginx
upstream backend {
    server app1.example.internal:8080;
    server app2.example.internal:8080;
    server app3.example.internal:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

위 구성은 들어오는 HTTP 요청을 `backend` upstream 그룹의 서버들로 분산한다. Nginx는 기본적으로 라운드 로빈 방식으로 upstream 서버를 선택한다.

경로 기반 라우팅도 가능하다.

```nginx
upstream api_servers {
    server api1.example.internal:8080;
    server api2.example.internal:8080;
}

upstream static_servers {
    server static1.example.internal:8080;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://api_servers;
    }

    location /static/ {
        proxy_pass http://static_servers;
    }
}
```

이 방식은 L7 로드 밸런싱에 해당한다.

## 3. HAProxy 예시

HAProxy는 L4와 L7 로드 밸런싱을 모두 지원하는 대표적인 오픈소스 로드 밸런서다.

L4 TCP 모드 예시:

```haproxy
frontend tcp_front
    bind *:3306
    mode tcp
    default_backend mysql_back

backend mysql_back
    mode tcp
    balance roundrobin
    server db1 10.0.1.10:3306 check
    server db2 10.0.1.11:3306 check
```

L7 HTTP 모드 예시:

```haproxy
frontend http_front
    bind *:80
    mode http
    acl is_api path_beg /api
    use_backend api_back if is_api
    default_backend web_back

backend api_back
    mode http
    balance roundrobin
    server api1 10.0.2.10:8080 check
    server api2 10.0.2.11:8080 check

backend web_back
    mode http
    balance roundrobin
    server web1 10.0.3.10:8080 check
```

TCP 모드는 L4에 가깝고, HTTP 모드는 L7 기능을 활용한다.

## 4. AWS 실제 서비스 연결

AWS에서는 로드 밸런서 유형에 따라 역할이 나뉜다.

| AWS 서비스 | 계층 | 주요 용도 |
|---|---:|---|
| Network Load Balancer, NLB | L4 | TCP, UDP, TLS 트래픽 처리 |
| Application Load Balancer, ALB | L7 | HTTP, HTTPS, gRPC 등 애플리케이션 라우팅 |
| Gateway Load Balancer, GWLB | L3/L4 관련 | 방화벽, IDS/IPS 같은 네트워크 어플라이언스 배치 |

ALB는 호스트 기반 라우팅, 경로 기반 라우팅, HTTP 헤더 기반 라우팅 등을 지원한다. NLB는 높은 성능의 TCP/UDP 처리에 적합하며, 클라이언트 IP 보존이 필요한 환경에서 사용될 수 있다.

예시:

```text
[Internet]
    |
[Route 53]
    |
[ALB]
    |
    ├── /api/*  -> [EC2 Auto Scaling Group: API]
    └── /web/*  -> [EC2 Auto Scaling Group: Web]
```

이 구조에서는 Route 53이 도메인을 ALB로 연결하고, ALB가 경로 기반으로 EC2 인스턴스 그룹에 요청을 전달한다.

---

## 5. GCP 실제 서비스 연결

GCP에서는 Cloud Load Balancing 제품군을 통해 글로벌 또는 리전 기반 로드 밸런싱을 제공한다. HTTP(S) Load Balancer는 L7 기능을 제공하고, TCP/UDP Load Balancer는 L4 트래픽 분산에 사용된다.

예시 구조:

```text
[Client]
   |
[Google Cloud HTTP(S) Load Balancer]
   |
   ├── /api  -> [Managed Instance Group A]
   └── /img  -> [Cloud Storage or Backend Bucket]
```

GCP HTTP(S) Load Balancer는 URL 맵을 사용해 호스트와 경로 기반 라우팅을 구성할 수 있다.

## 클라우드 연결

## 1. Docker와 Scale-out

Docker 환경에서 Scale-out은 동일한 애플리케이션 컨테이너를 여러 개 실행하는 방식으로 구현할 수 있다.

```text
[Load Balancer]
   |
   ├── [app container 1]
   ├── [app container 2]
   └── [app container 3]
```

컨테이너는 가볍고 빠르게 생성될 수 있기 때문에 수평 확장에 적합하다. 하지만 컨테이너가 사라지면 내부 파일 시스템 상태도 사라질 수 있으므로, 중요한 데이터는 외부 볼륨, 오브젝트 스토리지, 데이터베이스, 캐시 등에 저장해야 한다.

Docker Compose에서는 단일 호스트 내에서 여러 컨테이너를 실행할 수 있지만, 다중 노드 오케스트레이션과 자동 복구, 자동 확장을 위해서는 Kubernetes 같은 플랫폼을 사용하는 경우가 많다.

---

## 2. Kubernetes와 Scale-out

Kubernetes에서는 애플리케이션을 Pod 단위로 실행하고, Deployment를 통해 원하는 Pod 개수를 유지한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  template:
    metadata:
      labels:
        app: api-server
    spec:
      containers:
      - name: api-server
        image: example/api-server:1.0
        ports:
        - containerPort: 8080
```

위 설정은 `api-server` Pod를 3개 유지한다. Kubernetes Service는 이 Pod들 앞에서 내부 로드 밸런싱을 수행한다.

```text
[Client]
   |
[Ingress / LoadBalancer Service]
   |
[Kubernetes Service]
   |
   ├── [Pod 1]
   ├── [Pod 2]
   └── [Pod 3]
```

Kubernetes에서 자주 등장하는 확장 관련 개념은 다음과 같다.

- **Deployment**: 동일한 Pod 복제본 관리
- **ReplicaSet**: 지정된 수의 Pod 유지
- **Service**: Pod 집합에 대한 안정적인 네트워크 엔드포인트 제공
- **Ingress**: HTTP/HTTPS 라우팅 규칙 제공
- **Horizontal Pod Autoscaler, HPA**: CPU, 메모리 또는 커스텀 메트릭 기반 Pod 수 조정
- **Cluster Autoscaler**: 노드 리소스 부족 시 클러스터 노드 수 조정

Kubernetes에서 L4와 L7의 구분도 중요하다.

| 구성 요소 | 성격 |
|---|---|
| Service type ClusterIP | 클러스터 내부 L4 로드 밸런싱 |
| Service type LoadBalancer | 클라우드 로드 밸런서와 연동 |
| Ingress | 주로 L7 HTTP/HTTPS 라우팅 |
| Ingress Controller | Nginx, HAProxy, Traefik, Envoy 등으로 구현 가능 |

## 3. AWS와 Auto Scaling

AWS에서는 EC2 Auto Scaling Group과 Load Balancer를 결합하여 Scale-out 구조를 만든다.

```text
[Client]
   |
[ALB or NLB]
   |
[Auto Scaling Group]
   ├── [EC2 instance 1]
   ├── [EC2 instance 2]
   └── [EC2 instance 3]
```

Auto Scaling Group은 설정된 최소, 최대, 희망 인스턴스 수를 기준으로 EC2 인스턴스를 유지한다. CPU 사용률, 네트워크 사용량, ALB 요청 수 같은 CloudWatch 지표를 기준으로 확장 정책을 설정할 수 있다.

컨테이너 기반 AWS 서비스와도 연결된다.

- **ECS Service**: 여러 Task를 실행하고 ALB/NLB와 연결 가능
- **EKS**: Kubernetes 기반 워크로드 확장
- **AWS Lambda**: 서버리스 방식으로 이벤트 기반 확장
- **Elastic Load Balancing**: ALB, NLB, GWLB 제공

## 4. 로드 밸런서와 배포 전략

Scale-out 구조에서는 여러 서버가 동시에 존재하므로 점진적 배포가 가능하다.

```text
[Load Balancer]
   |
   ├── [v1 Server]
   ├── [v1 Server]
   └── [v2 Server]  ← 일부 트래픽만 전달
```

대표적인 배포 전략은 다음과 같다.

| 전략 | 설명 |
|---|---|
| Rolling Update | 서버를 순차적으로 교체 |
| Blue-Green Deployment | 기존 환경과 신규 환경을 분리하고 트래픽 전환 |
| Canary Deployment | 일부 사용자나 일부 비율만 새 버전으로 전달 |
| A/B Testing | 사용자 그룹별로 다른 버전 제공 |

L7 로드 밸런서는 헤더, 쿠키, 경로 기반 제어가 가능하므로 카나리 배포나 A/B 테스트와 잘 맞는다.

## 보안 연결

## 1. 로드 밸런서와 TLS 종료

L7 로드 밸런서는 HTTPS 트래픽을 처리하기 위해 TLS 종료를 수행하는 경우가 많다.

```text
[Client]
   |
 HTTPS
   v
[Load Balancer]  ← TLS Termination
   |
 HTTP or HTTPS
   v
[Backend Server]
```

TLS 종료를 로드 밸런서에서 수행하면 인증서 관리가 중앙화되고, 백엔드 서버의 암복호화 부담을 줄일 수 있다. 하지만 로드 밸런서와 백엔드 서버 사이가 평문 HTTP라면 내부 네트워크 구간에서 트래픽이 노출될 위험이 있다. 보안이 중요한 환경에서는 백엔드 구간도 HTTPS 또는 mTLS를 사용하는 것이 좋다.

---

## 2. 클라이언트 IP 보존과 신뢰 경계

로드 밸런서를 거치면 백엔드 서버는 실제 클라이언트 IP 대신 로드 밸런서 IP를 보게 될 수 있다. 이를 해결하기 위해 HTTP에서는 일반적으로 다음 헤더가 사용된다.

```text
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
Forwarded
```

하지만 이 헤더들은 클라이언트가 임의로 조작할 수도 있으므로, 애플리케이션은 반드시 **신뢰할 수 있는 프록시가 설정한 헤더만 신뢰**해야 한다. 예를 들어 Nginx나 애플리케이션 프레임워크에서 trusted proxy 설정을 올바르게 구성해야 한다.

잘못된 설정은 다음 문제를 유발할 수 있다.

- IP 기반 접근 제어 우회
- HTTPS 리다이렉트 오류
- 보안 쿠키 설정 오류
- 감사 로그의 클라이언트 IP 위조
- Rate Limiting 우회

---

## 3. L7 로드 밸런서와 HTTP 공격

L7 로드 밸런서는 HTTP 요청을 직접 해석하므로 웹 공격 방어 지점이 될 수 있다. 하지만 동시에 HTTP 계층 공격의 대상이 될 수도 있다.

관련 공격 예시는 다음과 같다.

- HTTP request smuggling
- Host header injection
- Slowloris 계열의 느린 HTTP 요청 공격
- 비정상적으로 큰 헤더 또는 바디를 통한 리소스 고갈
- 경로 정규화 차이를 이용한 우회
- 잘못된 CORS 설정

모범 사례는 다음과 같다.

- 최대 헤더 크기와 요청 바디 크기 제한
- 타임아웃 설정
- 허용 Host 헤더 검증
- WAF 연동
- 정규화된 경로 기준으로 라우팅
- 불필요한 HTTP 메서드 차단
- 업스트림 서버와 프록시의 HTTP 파싱 차이 최소화

---

## 4. L4 로드 밸런서와 네트워크 보안

L4 로드 밸런서는 TCP/UDP 레벨에서 동작하므로 네트워크 계층 보안 정책과 밀접하다.

고려해야 할 사항은 다음과 같다.

- 보안 그룹 또는 방화벽으로 허용 포트 최소화
- 백엔드 서버가 로드 밸런서에서 오는 트래픽만 허용
- SYN Flood 같은 TCP 기반 공격에 대비
- UDP 기반 서비스의 증폭 공격 가능성 검토
- 헬스 체크 엔드포인트 보호
- 관리 포트와 서비스 포트 분리

특히 백엔드 서버를 인터넷에 직접 노출하지 않고, 로드 밸런서를 통해서만 접근 가능하게 구성하는 것이 일반적인 보안 모범 사례다.

---

## 5. Sticky Session의 보안 및 운영 이슈

Sticky Session은 같은 사용자의 요청을 동일한 서버로 보내는 방식이다. 세션을 서버 메모리에 저장하는 레거시 구조에서 사용되기도 한다.

```text
User A -> Load Balancer -> Server 1
User A -> Load Balancer -> Server 1
User B -> Load Balancer -> Server 2
```

하지만 Sticky Session은 다음 문제를 만들 수 있다.

- 특정 서버에 부하가 집중될 수 있음
- 서버 장애 시 해당 서버의 세션 손실 가능
- 수평 확장 효과 감소
- 세션 고정 공격 방어 필요
- 쿠키 기반 고정 방식 사용 시 Secure, HttpOnly, SameSite 속성 고려 필요

가능하다면 세션 상태를 외부 저장소로 분리하여 애플리케이션 서버를 무상태로 유지하는 것이 Scale-out에 유리하다.

## 면접 질문

**Q1. Scale-up과 Scale-out의 차이를 설명해보세요.**  
> 핵심 답변: Scale-up은 기존 서버의 CPU, 메모리, 디스크 등 성능을 높이는 수직 확장이고, Scale-out은 서버 대수를 늘려 부하를 분산하는 수평 확장이다. Scale-up은 구조가 단순하지만 물리적 한계와 단일 장애 지점 문제가 있고, Scale-out은 가용성과 확장성이 좋지만 로드 밸런싱, 상태 관리, 분산 시스템 복잡도가 증가한다.

**Q2. Scale-out 환경에서 애플리케이션을 Stateless하게 만드는 이유는 무엇인가요?**  
> 핵심 답변: 요청이 어떤 서버로 전달될지 보장할 수 없기 때문이다. 서버 로컬 메모리에 세션이나 상태를 저장하면 다른 서버가 요청을 처리할 때 상태를 알 수 없다. 따라서 세션은 Redis 같은 외부 저장소에 두거나, JWT 같은 토큰 기반 방식을 사용해 서버 간 상태 의존성을 줄인다.

**Q3. L4 로드 밸런서와 L7 로드 밸런서의 차이는 무엇인가요?**  
> 핵심 답변: L4는 TCP/UDP의 IP, 포트, 프로토콜 정보를 기반으로 연결을 분산한다. HTTP URL이나 헤더 내용은 일반적으로 보지 않는다. L7은 HTTP 같은 애플리케이션 계층 정보를 분석하여 경로, 호스트, 헤더, 쿠키 기반 라우팅을 수행할 수 있다. L4는 단순하고 빠른 연결 분산에 적합하고, L7은 세밀한 트래픽 제어에 적합하다.

**Q4. 로드 밸런서의 헬스 체크는 왜 중요한가요?**  
> 핵심 답변: 장애가 발생한 서버로 요청을 계속 보내면 사용자 요청이 실패하기 때문이다. 로드 밸런서는 주기적으로 백엔드 서버의 상태를 확인하고, 비정상 서버를 트래픽 대상에서 제외한다. 헬스 체크는 단순 포트 확인뿐 아니라 애플리케이션이 실제로 요청을 처리할 수 있는지 확인하는 방식으로 설계하는 것이 좋다.

**Q5. L7 로드 밸런서를 사용할 때 발생할 수 있는 보안 이슈는 무엇인가요?**  
> 핵심 답변: TLS 종료 구간의 평문 통신 위험, X-Forwarded-For 헤더 위조, Host header injection, HTTP request smuggling, 과도한 요청 바디나 헤더를 이용한 리소스 고갈 등이 있다. trusted proxy 설정, WAF, 요청 크기 제한, 타임아웃 설정, 백엔드 구간 암호화, Host 검증이 중요하다.

## 관련 개념

- [[수직 확장 Scale-up]] - 단일 서버의 자원 성능을 높이는 확장 방식이다.
- [[수평 확장 Scale-out]] - 서버 인스턴스 수를 늘려 부하를 분산하는 방식이다.
- [[로드 밸런서]] - 여러 백엔드 서버에 트래픽을 분산하는 핵심 구성 요소다.
- [[L4 로드 밸런싱]] - TCP/UDP 계층에서 연결 단위로 트래픽을 분산한다.
- [[L7 로드 밸런싱]] - HTTP 경로, 헤더, 쿠키 등 애플리케이션 정보를 기반으로 라우팅한다.
- [[리버스 프록시]] - 클라이언트 요청을 대신 받아 내부 서버로 전달하며 로드 밸런싱과 보안 기능을 제공할 수 있다.
- [[헬스 체크]] - 백엔드 서버의 정상 동작 여부를 확인하여 장애 서버를 트래픽 대상에서 제외한다.
- [[오토스케일링]] - 지표 기반으로 서버나 컨테이너 수를 자동 조정하는 확장 전략이다.
- [[Stateless 아키텍처]] - 서버가 사용자 상태를 로컬에 저장하지 않아 수평 확장에 유리한 구조다.
- [[Sticky Session]] - 같은 사용자의 요청을 동일한 서버로 보내는 세션 유지 방식이다.
- [[TLS Termination]] - 로드 밸런서나 프록시에서 TLS 연결을 종료하고 내부로 요청을 전달하는 방식이다.
- [[Kubernetes Service]] - Pod 집합에 대한 안정적인 네트워크 접근점과 로드 밸런싱을 제공한다.
- [[Ingress Controller]] - Kubernetes에서 HTTP/HTTPS 기반 L7 라우팅을 수행하는 구성 요소다.
- [[AWS ALB]] - AWS에서 HTTP/HTTPS 기반 L7 로드 밸런싱을 제공하는 서비스다.
- [[AWS NLB]] - AWS에서 TCP/UDP/TLS 기반 L4 로드 밸런싱을 제공하는 서비스다.
