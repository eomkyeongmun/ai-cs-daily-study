# 클라우드 기초 - IaaS, PaaS, SaaS 비교, VPC, 서브넷, 보안 그룹

## 핵심 개념

클라우드 컴퓨팅은 사용자가 물리 서버, 네트워크 장비, 스토리지, 데이터센터를 직접 소유·운영하지 않고, 인터넷을 통해 필요한 컴퓨팅 자원을 임대해 사용하는 방식이다. 백엔드 인프라 관점에서 핵심은 “어디까지 직접 관리하고, 어디부터 클라우드 제공자가 관리하는가”를 이해하는 것이다. 이 기준에 따라 대표적으로 IaaS, PaaS, SaaS로 나뉜다.

**IaaS(Infrastructure as a Service)**는 가상 머신, 네트워크, 디스크, 방화벽 같은 기본 인프라를 제공한다. 사용자는 OS, 런타임, 미들웨어, 애플리케이션을 직접 설치하고 운영한다. AWS EC2, Google Compute Engine, Azure Virtual Machines가 대표적이다. 서버 설정 자유도가 높지만 운영 책임도 크다.

**PaaS(Platform as a Service)**는 애플리케이션 실행 플랫폼을 제공한다. 사용자는 주로 코드와 설정에 집중하고, OS 패치, 런타임 관리, 일부 스케일링은 플랫폼이 담당한다. AWS Elastic Beanstalk, Google App Engine, Heroku 등이 예시다. 개발 생산성이 높지만 플랫폼 제약이 존재한다.

**SaaS(Software as a Service)**는 완성된 소프트웨어를 인터넷으로 제공하는 형태다. 사용자는 인프라나 애플리케이션 내부 구현을 관리하지 않고 기능을 사용한다. Gmail, Slack, Salesforce, Google Workspace 등이 해당한다.

이 세 모델과 함께 백엔드 클라우드 기초에서 반드시 이해해야 할 개념이 **VPC, 서브넷, 보안 그룹**이다. **VPC(Virtual Private Cloud)**는 클라우드 안에서 논리적으로 격리된 가상 네트워크 공간이다. **서브넷(Subnet)**은 VPC 내부 IP 범위를 더 작은 네트워크 단위로 나눈 것이다. 일반적으로 퍼블릭 서브넷은 인터넷과 직접 통신 가능한 리소스를 배치하고, 프라이빗 서브넷은 DB나 내부 API처럼 외부 노출을 제한해야 하는 리소스를 배치한다. **보안 그룹(Security Group)**은 인스턴스나 네트워크 인터페이스 단위에 적용되는 가상 방화벽으로, 허용할 인바운드·아웃바운드 트래픽을 정의한다.

이 개념들이 중요한 이유는 클라우드 장애, 비용 폭증, 보안 사고의 상당수가 네트워크 설계와 권한 설정 실수에서 발생할 수 있기 때문이다. 백엔드 개발자는 단순히 코드를 배포하는 것뿐 아니라, 애플리케이션이 어떤 네트워크 경로로 접근되고, 어떤 포트가 열려 있으며, 어떤 계층이 외부에 노출되는지 이해해야 안정적이고 안전한 시스템을 설계할 수 있다.

## 내부 동작 원리

## 1. IaaS, PaaS, SaaS의 책임 분리 구조

클라우드 서비스 모델은 관리 책임 범위를 기준으로 이해할 수 있다.

```text
관리 영역                 On-Premise     IaaS          PaaS          SaaS
---------------------------------------------------------------------------
애플리케이션              사용자         사용자        사용자        제공자
데이터                    사용자         사용자        사용자        사용자/제공자
런타임                    사용자         사용자        제공자        제공자
미들웨어                  사용자         사용자        제공자        제공자
운영체제                  사용자         사용자        제공자        제공자
가상화                    사용자         제공자        제공자        제공자
서버                      사용자         제공자        제공자        제공자
스토리지                  사용자         제공자        제공자        제공자
네트워크                  사용자         제공자        제공자        제공자
데이터센터                사용자         제공자        제공자        제공자
```

- **IaaS**: 가상 머신과 네트워크는 제공되지만, OS 설정, 패키지 설치, 웹 서버 구성, 보안 패치 책임은 사용자에게 있다.
- **PaaS**: 사용자는 코드와 환경 변수, 배포 설정을 제공한다. 플랫폼은 런타임, OS, 스케일링 일부를 관리한다.
- **SaaS**: 사용자는 소프트웨어 기능을 사용하고 계정, 권한, 데이터 설정을 관리한다.

## 2. VPC 내부 동작 원리

VPC는 클라우드 제공자의 물리 네트워크 위에 만들어지는 **논리적 격리 네트워크**다. 사용자는 VPC에 사설 IP 대역을 할당하고, 그 안에 서브넷, 라우팅 테이블, 게이트웨이, 보안 정책을 구성한다.

예시 구조:

```text
Internet
   |
[Internet Gateway]
   |
[Public Route Table]
   |
-------------------------------------------------
| VPC 10.0.0.0/16                               |
|                                               |
|  Public Subnet 10.0.1.0/24                    |
|  - Load Balancer                              |
|  - Bastion Host                               |
|                                               |
|  Private Subnet 10.0.2.0/24                   |
|  - Application Server                         |
|  - Internal API                               |
|                                               |
|  Private Subnet 10.0.3.0/24                   |
|  - Database                                   |
-------------------------------------------------
```

위 구조에서 VPC 전체 IP 범위는 `10.0.0.0/16`이고, 이를 여러 서브넷으로 나눈다. 퍼블릭 서브넷은 인터넷 게이트웨이로 향하는 라우트가 있고, 프라이빗 서브넷은 일반적으로 직접 인터넷에서 접근되지 않도록 구성한다.

## 3. 서브넷과 라우팅 동작

서브넷은 IP 범위와 가용 영역 또는 리전 내 위치에 따라 구성된다. AWS의 경우 서브넷은 하나의 가용 영역에 속한다. GCP는 VPC와 서브넷 구조가 AWS와 다르며, GCP의 서브넷은 리전 단위 리소스다.

라우팅 테이블은 목적지 IP 대역에 따라 패킷을 어디로 보낼지 결정한다.

```text
예시 라우팅 테이블

Destination      Target
--------------------------------
10.0.0.0/16      local
0.0.0.0/0        Internet Gateway
```

- `10.0.0.0/16 -> local`: 같은 VPC 내부 통신
- `0.0.0.0/0 -> Internet Gateway`: 그 외 모든 IPv4 목적지는 인터넷 게이트웨이로 전달

퍼블릭 서브넷이 되려면 일반적으로 다음 조건이 필요하다.

1. 서브넷 라우팅 테이블에 인터넷 게이트웨이로 향하는 기본 경로가 있음
2. 인스턴스 또는 로드 밸런서가 퍼블릭 IP 또는 이에 준하는 외부 접근 경로를 가짐
3. 보안 그룹과 네트워크 ACL에서 해당 트래픽을 허용함

프라이빗 서브넷의 서버가 패키지 업데이트나 외부 API 호출을 위해 인터넷으로 나가야 할 때는 일반적으로 NAT Gateway 또는 NAT 인스턴스를 사용한다.

```text
Private Instance
   |
Private Subnet Route Table
   |
0.0.0.0/0 -> NAT Gateway
   |
Public Subnet
   |
Internet Gateway
   |
Internet
```

이 구조에서는 외부에서 프라이빗 인스턴스로 직접 접속할 수는 없지만, 프라이빗 인스턴스가 외부로 나가는 요청은 가능하다.

## 4. 보안 그룹 동작 원리

보안 그룹은 클라우드 리소스에 적용되는 가상 방화벽이다. AWS 기준으로 보안 그룹은 **상태 저장(Stateful)** 방식이다. 즉, 인바운드 요청을 허용하면 그 응답 트래픽은 별도의 아웃바운드 규칙 없이도 추적되어 허용된다. 단, 실제 동작은 클라우드 제공자와 리소스 유형에 따라 세부 차이가 있을 수 있다.

예시:

```text
[Client 1.2.3.4]
      |
      | TCP 443
      v
[Load Balancer Security Group]
Inbound:
- TCP 443 from 0.0.0.0/0

Outbound:
- TCP 8080 to App Security Group
      |
      v
[App Server Security Group]
Inbound:
- TCP 8080 from Load Balancer Security Group

Outbound:
- TCP 3306 to DB Security Group
      |
      v
[DB Security Group]
Inbound:
- TCP 3306 from App Security Group
```

이 방식의 핵심은 IP를 무분별하게 열기보다 **보안 그룹 간 참조**를 활용해 “로드 밸런서에서 온 요청만 앱 서버가 받는다”, “앱 서버에서 온 요청만 DB가 받는다”처럼 계층별 접근을 제한하는 것이다.

## 실제 시스템 연결

## 1. Linux 서버와 IaaS

IaaS에서 백엔드 개발자가 가장 자주 접하는 것은 Linux 기반 가상 머신이다. 예를 들어 AWS EC2나 GCP Compute Engine에 Ubuntu 또는 Amazon Linux 계열 이미지를 사용해 서버를 만들고, SSH로 접속해 다음 작업을 수행할 수 있다.

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable nginx
sudo systemctl start nginx
```

이 경우 클라우드 제공자는 가상 머신, 디스크, 네트워크 연결을 제공하지만, Nginx 설치, 설정 파일 관리, OS 보안 패치, 로그 관리, 장애 대응은 사용자의 책임이다.

## 2. Nginx와 보안 그룹

Nginx를 웹 서버 또는 리버스 프록시로 사용할 때 보안 그룹 설정이 매우 중요하다.

```text
Internet
   |
TCP 443
   |
[Nginx Server]
   |
TCP 8080
   |
[Spring Boot / Node.js App]
```

일반적인 구성은 다음과 같다.

- 외부 사용자는 `443` 포트로 Nginx에 접속
- Nginx는 내부 애플리케이션의 `8080` 포트로 프록시
- 보안 그룹은 외부에 `443`만 허용
- `8080`은 인터넷 전체에 열지 않고, Nginx 서버 또는 로드 밸런서에서만 접근 허용

이렇게 하면 애플리케이션 서버가 직접 외부에 노출되는 것을 줄일 수 있다.

## 3. AWS 예시

AWS에서 기본적인 3계층 구조는 다음처럼 구성할 수 있다.

```text
Route 53
   |
Application Load Balancer
   |
Public Subnet
   |
Private Subnet - EC2 Auto Scaling Group
   |
Private Subnet - RDS
```

- **Route 53**: DNS 서비스
- **Application Load Balancer(ALB)**: HTTP/HTTPS 요청 분산
- **EC2 Auto Scaling Group**: 애플리케이션 서버 자동 확장
- **RDS**: 관리형 관계형 데이터베이스
- **VPC**: 전체 네트워크 격리 공간
- **Subnet**: 퍼블릭·프라이빗 계층 분리
- **Security Group**: 계층별 접근 제어

예시 보안 그룹 정책:

```text
ALB-SG
Inbound:
- TCP 443 from 0.0.0.0/0

APP-SG
Inbound:
- TCP 8080 from ALB-SG

DB-SG
Inbound:
- TCP 5432 from APP-SG
```

PostgreSQL을 사용한다면 기본 포트는 일반적으로 `5432`이고, MySQL은 일반적으로 `3306`이다. 단, 실제 운영에서는 포트 변경 여부와 데이터베이스 엔진 설정을 확인해야 한다.

## 4. GCP 예시

GCP에서는 VPC 네트워크, 서브넷, 방화벽 규칙을 사용한다. AWS 보안 그룹과 유사한 역할을 하는 것은 **VPC 방화벽 규칙**이다. GCP의 방화벽 규칙은 네트워크 태그나 서비스 계정 등을 기준으로 인스턴스에 적용할 수 있다.

```text
GCP VPC
 |
Subnetwork
 |
Compute Engine Instance
 |
Firewall Rule
```

예를 들어 웹 서버 태그가 붙은 VM에 대해 `tcp:443`을 허용하고, 데이터베이스 VM에는 애플리케이션 서버의 서비스 계정 또는 태그에서 오는 트래픽만 허용하는 방식으로 계층을 분리할 수 있다.

## 5. SaaS 실제 사례

SaaS는 백엔드 개발자가 직접 인프라를 운영하지 않지만, 실무에서는 자주 사용한다.

- GitHub: 코드 저장소 및 협업
- Slack: 업무 커뮤니케이션
- Datadog: 모니터링 SaaS
- Sentry: 에러 추적 SaaS
- Google Workspace: 메일, 문서, 계정 협업

SaaS 사용 시에는 인프라 운영 부담은 줄어들지만, 계정 권한, API 토큰, 감사 로그, 데이터 보관 정책을 신중히 관리해야 한다.

## 클라우드 연결

## 1. Docker와의 연결

Docker는 애플리케이션과 실행 환경을 컨테이너 이미지로 패키징한다. IaaS 환경에서는 사용자가 EC2나 Compute Engine 같은 VM에 Docker를 설치하고 컨테이너를 직접 실행할 수 있다.

```text
IaaS VM
 |
Docker Engine
 |
Container: Nginx
Container: App
Container: Redis
```

이 방식은 자유도가 높지만, 컨테이너 스케줄링, 롤링 배포, 장애 복구, 네트워크 연결을 직접 설계해야 한다.

PaaS에서는 Docker 이미지를 제출하면 플랫폼이 실행 환경을 관리하는 경우가 있다. 예를 들어 Google Cloud Run은 컨테이너 이미지를 기반으로 서버리스 방식에 가깝게 서비스를 실행할 수 있다. AWS App Runner도 컨테이너 기반 애플리케이션 실행을 지원한다.

## 2. Kubernetes와의 연결

Kubernetes는 컨테이너 오케스트레이션 시스템이다. 클라우드에서는 관리형 Kubernetes 서비스가 자주 사용된다.

- AWS EKS
- Google Kubernetes Engine
- Azure Kubernetes Service

Kubernetes에서도 VPC, 서브넷, 보안 정책은 중요하다. 노드가 어느 서브넷에 배치되는지, Pod가 어떤 IP 대역을 사용하는지, LoadBalancer Service가 퍼블릭으로 노출되는지, Ingress Controller가 어떤 보안 그룹 또는 방화벽 규칙을 사용하는지 이해해야 한다.

```text
Internet
   |
Cloud Load Balancer
   |
Kubernetes Ingress
   |
Service
   |
Pod
```

Kubernetes 자체의 NetworkPolicy는 Pod 간 통신을 제어하는 데 사용된다. 하지만 클라우드 VPC 보안 그룹이나 방화벽과는 계층이 다르다. 일반적으로 외부 진입 제어는 클라우드 로드 밸런서·보안 그룹·방화벽에서 처리하고, 클러스터 내부 세분화는 NetworkPolicy로 보완한다.

## 3. AWS 서비스와의 연결

AWS에서는 VPC와 서브넷 개념이 거의 모든 네트워크형 서비스와 연결된다.

- **EC2**: VPC와 서브넷에 배치됨
- **RDS**: DB Subnet Group을 통해 여러 서브넷에 배치 가능
- **ElastiCache**: VPC 내부 캐시 클러스터 구성
- **EKS**: 노드와 로드 밸런서가 VPC 네트워크를 사용
- **Lambda**: 필요 시 VPC에 연결 가능
- **ALB/NLB**: 서브넷에 배치되어 트래픽을 대상 그룹으로 전달
- **VPC Endpoint**: 인터넷을 거치지 않고 AWS 서비스에 사설 연결 가능

예를 들어 프라이빗 서브넷의 EC2가 S3에 접근할 때 NAT Gateway를 사용할 수도 있지만, S3용 VPC Endpoint를 구성하면 인터넷 경로를 사용하지 않고 AWS 내부 네트워크 경로로 접근할 수 있다.

## 4. PaaS와 네트워크 추상화

PaaS는 네트워크 세부사항을 많이 숨긴다. 하지만 완전히 사라지는 것은 아니다. 예를 들어 PaaS 애플리케이션이 데이터베이스에 접근하려면 다음 요소를 고려해야 한다.

- 데이터베이스가 퍼블릭 접근 가능한지
- 사설 네트워크 연결을 지원하는지
- 허용 IP 목록이 필요한지
- TLS 연결을 강제하는지
- 서비스 간 인증 방식은 무엇인지

PaaS를 사용하면 OS와 런타임 운영 부담은 줄지만, 네트워크 접근 경로와 권한 모델은 여전히 설계해야 한다.

## 보안 연결

## 1. 공동 책임 모델

클라우드 보안의 기본은 **공동 책임 모델(Shared Responsibility Model)**이다. 클라우드 제공자는 물리 데이터센터, 하드웨어, 기본 가상화 계층 등 “클라우드 자체의 보안”을 책임지고, 사용자는 자신이 구성한 리소스, 데이터, 계정, 접근 권한, 네트워크 설정 등 “클라우드 안에서의 보안”을 책임진다.

서비스 모델별로 사용자 책임 범위는 다르다.

- IaaS: OS 패치, 방화벽, 계정, 애플리케이션 보안 책임이 큼
- PaaS: 코드, 데이터, 환경 변수, 접근 제어 책임이 중요
- SaaS: 계정 권한, 데이터 공유 설정, 감사 로그, API 토큰 관리가 중요

## 2. VPC 설계 보안

VPC 설계에서 중요한 원칙은 **최소 노출**이다.

권장 구조:

```text
Public Subnet:
- Load Balancer
- Bastion Host 또는 관리형 접속 경로

Private Subnet:
- Application Server
- Worker Server
- Database
- Cache
```

모범 사례:

- DB를 퍼블릭 서브넷에 배치하지 않음
- 관리 포트 SSH `22`, RDP `3389`를 인터넷 전체에 열지 않음
- 퍼블릭 IP 부여를 최소화
- 프라이빗 리소스의 외부 통신은 NAT Gateway 또는 VPC Endpoint 사용
- 라우팅 테이블을 서브넷 목적에 맞게 분리
- 운영, 개발, 스테이징 환경의 VPC 또는 계정을 분리

## 3. 보안 그룹 모범 사례

보안 그룹은 “기본 거부, 필요한 것만 허용” 원칙으로 설계한다.

나쁜 예:

```text
Inbound:
- TCP 22 from 0.0.0.0/0
- TCP 3306 from 0.0.0.0/0
- TCP 8080 from 0.0.0.0/0
```

좋은 예:

```text
ALB-SG:
- TCP 443 from 0.0.0.0/0

APP-SG:
- TCP 8080 from ALB-SG

DB-SG:
- TCP 3306 from APP-SG

ADMIN-SG:
- TCP 22 from 회사 VPN 대역
```

핵심은 인터넷 전체에 데이터베이스, 내부 API, 관리 포트를 열지 않는 것이다.

## 4. 흔한 보안 이슈

- **과도하게 열린 인바운드 규칙**: `0.0.0.0/0` 또는 `::/0`에 민감 포트 공개
- **퍼블릭 DB 노출**: RDS, MongoDB, Elasticsearch 등을 외부에 직접 노출
- **잘못된 라우팅 테이블**: 프라이빗이어야 할 서브넷이 인터넷 게이트웨이를 통해 외부 접근 가능
- **하드코딩된 클라우드 키**: Git 저장소에 Access Key, Secret Key 노출
- **과도한 IAM 권한**: 필요한 범위보다 큰 권한 부여
- **SaaS 계정 관리 부실**: 퇴사자 계정 미회수, MFA 미적용
- **로그 미수집**: 네트워크 흐름, API 호출, 인증 이벤트 추적 불가

## 5. 보안 강화 방법

- MFA 적용
- IAM 최소 권한 원칙 적용
- 보안 그룹과 방화벽 규칙 정기 점검
- VPC Flow Logs 또는 클라우드 제공자의 네트워크 로그 활성화
- CloudTrail, Cloud Logging 등 감사 로그 활성화
- Secret Manager, AWS Secrets Manager, HashiCorp Vault 등으로 비밀 관리
- 인프라를 Terraform 같은 IaC로 관리하고 코드 리뷰 적용
- 운영 DB는 프라이빗 네트워크에 배치
- 관리 접속은 VPN, Bastion Host, Session Manager 등 통제된 경로 사용
- TLS 적용 및 인증서 자동 갱신 체계 구성

## 면접 질문

**Q1. IaaS, PaaS, SaaS의 차이를 설명해보세요.**  
> 핵심 답변: IaaS는 VM, 네트워크, 스토리지 같은 인프라를 제공하고 사용자가 OS와 애플리케이션을 관리한다. PaaS는 런타임과 플랫폼을 제공해 사용자가 주로 코드와 설정에 집중한다. SaaS는 완성된 소프트웨어를 제공하며 사용자는 기능과 데이터, 계정 설정을 관리한다. 차이는 관리 책임 범위다.

**Q2. VPC와 서브넷의 관계는 무엇인가요?**  
> 핵심 답변: VPC는 클라우드 내 논리적으로 격리된 가상 네트워크이고, 서브넷은 VPC 내부 IP 대역을 더 작은 단위로 나눈 네트워크다. 서브넷은 퍼블릭, 프라이빗 등 목적에 따라 분리되며 라우팅 테이블과 게이트웨이 설정에 따라 외부 접근 가능 여부가 결정된다.

**Q3. 퍼블릭 서브넷과 프라이빗 서브넷의 차이는 무엇인가요?**  
> 핵심 답변: 퍼블릭 서브넷은 인터넷 게이트웨이로 향하는 경로와 외부 접근 가능한 리소스를 가진 서브넷이다. 프라이빗 서브넷은 외부에서 직접 접근할 수 없도록 구성하며, 일반적으로 애플리케이션 서버, 데이터베이스, 캐시를 배치한다. 프라이빗 리소스가 인터넷으로 나갈 때는 NAT Gateway나 VPC Endpoint를 사용할 수 있다.

**Q4. 보안 그룹과 네트워크 ACL의 차이는 무엇인가요?**  
> 핵심 답변: AWS 기준으로 보안 그룹은 인스턴스나 네트워크 인터페이스 단위에 적용되는 상태 저장 방화벽이고, 네트워크 ACL은 서브넷 단위에 적용되는 상태 비저장 필터링이다. 보안 그룹은 허용 규칙 중심이고, NACL은 허용과 거부 규칙을 모두 정의할 수 있다. 일반적으로 세밀한 리소스 접근 제어는 보안 그룹을 중심으로 설계한다.

**Q5. 데이터베이스를 클라우드에 배치할 때 어떤 네트워크 보안 구성이 바람직한가요?**  
> 핵심 답변: 데이터베이스는 프라이빗 서브넷에 배치하고 퍼블릭 IP를 부여하지 않는 것이 일반적이다. 보안 그룹은 애플리케이션 서버 보안 그룹에서 오는 DB 포트만 허용한다. 운영자는 VPN, Bastion, Session Manager 등 통제된 경로로 접근해야 하며, TLS, 인증, 백업, 감사 로그, 최소 권한 IAM도 함께 고려해야 한다.
