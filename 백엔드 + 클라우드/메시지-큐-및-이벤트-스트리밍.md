# 메시지 큐 및 이벤트 스트리밍 - Kafka, RabbitMQ 차이점, Pub/Sub 모델, 비동기 처리

## 핵심 개념

메시지 큐(Message Queue)와 이벤트 스트리밍(Event Streaming)은 서비스 간 직접 호출을 줄이고, 데이터를 비동기적으로 전달하기 위한 백엔드 아키텍처 핵심 구성요소이다. 전통적인 동기 HTTP 호출에서는 요청한 서비스가 응답을 받을 때까지 기다려야 하며, 호출 대상 장애가 곧 호출자 장애로 전파될 수 있다. 반면 메시지 큐와 이벤트 스트리밍을 사용하면 생산자(Producer)가 메시지나 이벤트를 브로커에 전달하고, 소비자(Consumer)가 자신의 처리 속도에 맞춰 이를 가져가거나 전달받는다. 이를 통해 서비스 간 결합도를 낮추고, 장애 격리, 부하 완충, 재시도, 확장성, 이벤트 기반 아키텍처 구현이 가능해진다.

Kafka와 RabbitMQ는 모두 메시징 시스템으로 사용되지만 설계 철학이 다르다. Kafka는 대용량 이벤트 로그를 저장하고 순차적으로 읽는 이벤트 스트리밍 플랫폼에 가깝다. 메시지는 토픽(Topic)의 파티션(Partition)에 append-only 로그 형태로 저장되며, Consumer Group 단위로 읽기 위치(offset)를 관리한다. 따라서 동일한 이벤트를 여러 소비자 그룹이 독립적으로 재처리할 수 있고, 로그 기반 데이터 파이프라인, 실시간 분석, CDC(Change Data Capture), 이벤트 소싱 등에 적합하다.

RabbitMQ는 AMQP 기반 메시지 브로커로 널리 사용되며, 큐 중심의 메시지 라우팅과 작업 분배에 강점이 있다. Producer는 Exchange에 메시지를 보내고, Exchange는 Routing Key와 Binding 규칙에 따라 Queue로 메시지를 전달한다. Consumer는 Queue에서 메시지를 소비하며, Ack/Nack을 통해 처리 성공 여부를 브로커에 알린다. 작업 큐, 비동기 이메일 발송, 주문 처리, RPC 스타일 비동기 요청 등에 자주 사용된다.

Pub/Sub 모델은 발행자(Publisher)가 특정 구독자(Subscriber)를 직접 알 필요 없이 주제나 채널에 메시지를 발행하고, 구독자가 관심 있는 메시지를 수신하는 구조이다. 이는 마이크로서비스 환경에서 서비스 간 의존성을 줄이고, 새로운 소비자를 쉽게 추가할 수 있게 해준다. 비동기 처리는 사용자의 요청 흐름에서 오래 걸리는 작업을 분리하여 응답 지연을 줄이고, 시스템 전체 처리량과 복원력을 높이는 데 중요하다.

## 내부 동작 원리

## 1. 기본 메시징 흐름

일반적인 메시지 기반 비동기 처리 흐름은 다음과 같다.

```text
[Client]
   |
   v
[API Server] -- 메시지 발행 --> [Message Broker] --> [Consumer Worker]
   |                                      |
   |                                      v
   +---- 빠른 응답 반환              [DB / 외부 API / 파일 처리]
```

예를 들어 사용자가 회원가입을 하면 API 서버는 회원 정보를 저장한 뒤 “Welcome Email 발송” 메시지를 브로커에 넣고 즉시 응답한다. 이메일 발송 Worker는 나중에 메시지를 가져와 SMTP 서버나 외부 이메일 API를 호출한다. 이 구조에서는 이메일 시스템이 일시적으로 느려져도 회원가입 API 응답이 직접적으로 지연되지 않는다.

## 2. Kafka 내부 동작 원리

Kafka의 핵심 단위는 Topic, Partition, Offset, Consumer Group이다.

```text
Producer
   |
   v
Topic: order-events
 ├─ Partition 0: [offset 0][offset 1][offset 2]...
 ├─ Partition 1: [offset 0][offset 1][offset 2]...
 └─ Partition 2: [offset 0][offset 1][offset 2]...
          |
          v
Consumer Group A
 ├─ Consumer 1 -> Partition 0
 ├─ Consumer 2 -> Partition 1
 └─ Consumer 3 -> Partition 2
```

Kafka에서 Producer는 특정 Topic에 이벤트를 기록한다. Topic은 여러 Partition으로 나뉠 수 있으며, 각 Partition은 순서가 보장되는 append-only 로그이다. 같은 Partition 안에서는 메시지 순서가 유지되지만, 서로 다른 Partition 간의 전체 순서는 보장되지 않는다. 특정 키를 기준으로 메시지를 보내면 같은 키를 가진 이벤트가 같은 Partition으로 들어가도록 구성할 수 있어, 예를 들어 같은 주문 ID의 이벤트 순서를 유지하는 데 활용할 수 있다.

Consumer는 Consumer Group에 속해 메시지를 읽는다. 하나의 Consumer Group 안에서는 하나의 Partition이 일반적으로 하나의 Consumer에게 할당된다. 따라서 Consumer 수를 늘리면 병렬 처리량을 높일 수 있지만, 같은 Consumer Group 내에서 Consumer 수가 Partition 수보다 많으면 일부 Consumer는 처리할 Partition을 받지 못할 수 있다.

Kafka는 메시지를 소비했다고 즉시 삭제하지 않는다. 설정된 보존 정책에 따라 일정 기간 또는 용량 기준으로 로그를 유지한다. Consumer는 offset을 통해 자신이 어디까지 읽었는지 관리한다. 이 구조 덕분에 새로운 Consumer Group을 추가하면 과거 이벤트를 처음부터 다시 읽거나, 장애 발생 후 특정 offset부터 재처리할 수 있다.

Kafka의 처리 흐름은 다음과 같이 요약할 수 있다.

```text
1. Producer가 Topic에 이벤트 전송
2. Kafka Broker가 이벤트를 특정 Partition에 append
3. Consumer가 Partition에서 offset 기준으로 pull
4. Consumer가 처리 성공 후 offset commit
5. 장애 발생 시 마지막 commit offset 이후부터 재처리 가능
```

## 3. RabbitMQ 내부 동작 원리

RabbitMQ는 Queue와 Exchange 기반으로 동작한다.

```text
Producer
   |
   v
[Exchange]
   | routing key / binding rule
   v
[Queue]
   |
   v
Consumer
```

Producer는 Queue에 직접 메시지를 넣기보다 Exchange에 메시지를 발행한다. Exchange는 메시지를 어떤 Queue로 보낼지 결정한다. 대표적인 Exchange 유형은 다음과 같다.

- Direct Exchange: Routing Key가 정확히 일치하는 Queue로 전달
- Fanout Exchange: Binding된 모든 Queue로 메시지 브로드캐스트
- Topic Exchange: 패턴 기반 Routing Key 매칭
- Headers Exchange: 메시지 Header 조건 기반 라우팅

RabbitMQ의 일반적인 처리 과정은 다음과 같다.

```text
1. Producer가 Exchange에 메시지 발행
2. Exchange가 Binding 규칙에 따라 Queue에 메시지 전달
3. Consumer가 Queue에서 메시지 수신
4. Consumer가 처리 성공 시 Ack 전송
5. 처리 실패 시 Nack 또는 Reject로 재전달/폐기 가능
```

RabbitMQ에서는 Consumer가 메시지를 처리한 후 Ack를 보내면 해당 메시지는 Queue에서 제거된다. Consumer가 Ack를 보내기 전에 죽으면 브로커는 해당 메시지를 다시 Queue에 넣어 다른 Consumer가 처리하도록 할 수 있다. 이 구조는 작업 큐나 명령 처리에 적합하다.

## 4. Kafka vs RabbitMQ 핵심 차이

| 구분 | Kafka | RabbitMQ |
|---|---|---|
| 중심 모델 | 로그 기반 이벤트 스트리밍 | 큐 기반 메시지 브로커 |
| 메시지 저장 | Topic Partition에 로그로 저장 | Queue에 저장 후 Ack 시 제거 |
| 소비 방식 | Consumer가 pull | Consumer가 push 방식으로 전달받는 형태가 일반적이며 prefetch로 흐름 제어 |
| 재처리 | offset 기반 재처리 용이 | Ack 후 제거되므로 기본적으로 재처리 어려움 |
| 순서 보장 | Partition 내부 순서 보장 | Queue 내부 순서가 기본이나 재전달, 다중 Consumer 환경에서 처리 완료 순서는 달라질 수 있음 |
| 확장 방식 | Partition 기반 수평 확장 | Queue, Consumer, Exchange 설계 기반 확장 |
| 적합한 용도 | 이벤트 로그, 실시간 파이프라인, 분석, CDC | 작업 큐, 비동기 명령 처리, 라우팅 복잡한 메시징 |
| 라우팅 | 상대적으로 단순한 Topic/Partition 중심 | Exchange와 Binding으로 다양한 라우팅 가능 |

## 5. Pub/Sub 모델

Pub/Sub 모델은 Publisher와 Subscriber를 분리한다.

```text
Publisher A ----\
Publisher B ----- > [Topic / Channel / Exchange] ---> Subscriber 1
Publisher C ----/                              └----> Subscriber 2
                                                   └-> Subscriber 3
```

이 모델에서 Publisher는 어떤 Subscriber가 메시지를 받을지 알 필요가 없다. Subscriber도 Publisher의 내부 구현을 몰라도 된다. 이로 인해 새로운 기능을 추가할 때 기존 서비스를 수정하지 않고 구독자만 추가할 수 있다. 예를 들어 “주문 생성 이벤트”가 발행되면 결제 서비스, 알림 서비스, 재고 서비스, 분석 서비스가 각각 독립적으로 이벤트를 소비할 수 있다.

## 6. 비동기 처리의 핵심 고려사항

비동기 처리는 단순히 “나중에 처리”하는 것이 아니라 안정적인 재시도와 중복 처리 대응이 중요하다. 메시징 시스템에서는 네트워크 장애, Consumer 장애, Ack 실패, offset commit 실패 등으로 인해 같은 메시지가 두 번 처리될 수 있다. 따라서 대부분의 실무 시스템은 “정확히 한 번 처리”를 전적으로 브로커에만 의존하기보다, 애플리케이션 레벨에서 멱등성(Idempotency)을 보장하는 방식으로 설계한다.

예를 들어 결제 승인 메시지를 처리할 때 메시지가 두 번 들어와도 같은 결제 ID에 대해 한 번만 승인되도록 DB에 unique constraint를 두거나 처리 이력 테이블을 사용하는 방식이 필요하다.

## 실제 시스템 연결

## 1. Linux 환경에서의 연결

Kafka와 RabbitMQ는 모두 서버 프로세스로 실행되며, Linux 환경에서는 파일 디스크립터, 네트워크 소켓, 디스크 I/O, 페이지 캐시, 프로세스 메모리 관리와 밀접하게 연결된다.

Kafka는 로그 기반 시스템이므로 디스크에 순차 쓰기를 많이 수행한다. 순차 쓰기는 일반적으로 랜덤 쓰기보다 효율적이며, 운영체제 페이지 캐시를 활용해 읽기 성능을 높일 수 있다. Kafka 운영 시에는 디스크 용량, I/O 처리량, 네트워크 대역폭, 파일 핸들 제한 등을 신중히 고려해야 한다.

RabbitMQ는 메시지를 메모리와 디스크에 관리하며, durable queue와 persistent message를 사용하면 브로커 재시작 후에도 메시지를 보존할 수 있다. 다만 디스크 영속성을 활성화하면 성능과 안정성 사이의 균형을 고려해야 한다. Linux에서 RabbitMQ 운영 시에는 Erlang VM 기반 런타임 특성, 메모리 watermark, 파일 디스크립터 제한 등을 함께 확인해야 한다.

## 2. 웹 서비스 예시

전자상거래 주문 시스템을 예로 들 수 있다.

```text
[Order API]
   |
   | 주문 생성 이벤트 발행
   v
[Kafka Topic: order-created]
   ├── [Payment Service]
   ├── [Inventory Service]
   ├── [Notification Service]
   └── [Analytics Service]
```

Kafka를 사용하면 주문 생성 이벤트를 여러 서비스가 독립적으로 소비할 수 있다. 분석 서비스가 장애로 멈췄다가 복구되어도 offset을 기준으로 중단 지점부터 다시 읽을 수 있다.

반면 작업 큐 중심의 처리는 RabbitMQ가 잘 맞는 경우가 많다.

```text
[API Server]
   |
   | email.send 메시지
   v
[RabbitMQ Exchange]
   |
   v
[email_queue]
   |
   v
[Email Worker Pool]
```

여기서는 여러 Email Worker가 같은 Queue를 소비하면서 작업을 분산 처리한다. Worker 하나가 실패해도 Ack되지 않은 메시지는 다시 전달될 수 있다.

## 3. Nginx와의 연결

Nginx는 일반적으로 HTTP 요청을 백엔드 API 서버로 라우팅하는 리버스 프록시 역할을 한다. 메시지 큐 자체를 직접 대체하지는 않는다. 하지만 사용자 요청 흐름에서 Nginx 뒤의 API 서버가 메시지 브로커에 작업을 위임하는 구조는 흔하다.

```text
[Client]
   |
   v
[Nginx]
   |
   v
[Backend API]
   |
   v
[Kafka / RabbitMQ]
   |
   v
[Worker Service]
```

예를 들어 대용량 이미지 처리 요청에서 API 서버가 파일 업로드 메타데이터를 저장하고 “이미지 리사이징 작업” 메시지를 RabbitMQ에 넣으면, Worker가 비동기로 이미지를 처리한다. 이때 Nginx는 업로드 요청 제한, 타임아웃, 프록시 버퍼링 등을 관리하고, 비동기 처리는 메시지 브로커가 담당한다.

## 4. 데이터베이스와의 연결

메시지 발행과 DB 트랜잭션을 함께 다룰 때는 주의가 필요하다. 예를 들어 주문 DB 저장은 성공했지만 Kafka 이벤트 발행이 실패하면 다른 서비스는 주문 생성 사실을 모를 수 있다. 반대로 이벤트 발행은 성공했지만 DB 저장이 롤백되면 잘못된 이벤트가 전파될 수 있다.

이를 해결하기 위해 Transactional Outbox 패턴이 자주 사용된다.

```text
1. 비즈니스 데이터와 outbox 테이블을 같은 DB 트랜잭션으로 저장
2. 별도 Publisher가 outbox 테이블을 읽어 Kafka/RabbitMQ에 발행
3. 발행 성공 후 outbox 상태를 갱신
```

이 패턴은 DB 변경과 이벤트 발행 사이의 불일치를 줄이는 데 사용된다.

## 5. 실제 사용 패턴

- Kafka
  - 사용자 행동 로그 수집
  - 실시간 추천 시스템 이벤트 파이프라인
  - 결제/주문 이벤트 스트리밍
  - CDC 기반 데이터 동기화
  - 데이터 레이크 또는 분석 시스템으로 이벤트 전달

- RabbitMQ
  - 이메일/SMS 발송 작업 큐
  - 이미지/동영상 변환 작업
  - 비동기 보고서 생성
  - 복잡한 라우팅이 필요한 업무 메시징
  - 제한된 Worker Pool로 외부 API 호출량 제어

## 클라우드 연결

## 1. Docker와의 연결

개발 환경에서는 Kafka와 RabbitMQ를 Docker Compose로 실행하는 경우가 많다. Docker를 사용하면 로컬 환경에서 브로커, 애플리케이션, DB를 격리된 컨테이너로 구성할 수 있다.

```text
[app container] ---> [kafka container]
       |
       └---------> [postgres container]
```

RabbitMQ는 관리 UI 플러그인을 포함한 이미지를 사용하면 큐, Exchange, Binding, Consumer 상태를 웹 UI에서 확인할 수 있다. Kafka는 단일 브로커 개발 환경과 운영 클러스터 구성이 다르므로, 로컬 테스트 결과를 그대로 운영 성능으로 일반화해서는 안 된다.

## 2. Kubernetes와의 연결

Kubernetes 환경에서는 메시지 브로커 자체를 클러스터 내부에 운영하거나, 외부 관리형 서비스를 사용할 수 있다.

```text
[Deployment: API Pods]
        |
        v
[Service]
        |
        v
[Kafka/RabbitMQ Cluster or Managed Service]
        |
        v
[Deployment: Worker Pods]
```

Consumer Worker는 Kubernetes Deployment로 수평 확장할 수 있다. Kafka의 경우 Consumer 수를 늘릴 때 Partition 수와 Consumer Group 구조를 함께 고려해야 한다. RabbitMQ의 경우 Worker Pod 수를 늘리면 Queue 소비 병렬성이 증가하지만, prefetch 설정과 메시지 처리 시간이 적절하지 않으면 특정 Consumer에 메시지가 몰리거나 처리 지연이 발생할 수 있다.

Kubernetes에서 직접 Kafka나 RabbitMQ를 운영할 때는 StatefulSet, PersistentVolume, PodDisruptionBudget, anti-affinity, readiness/liveness probe 등을 고려해야 한다. 특히 메시지 브로커는 상태ful(stateful) 시스템이므로 stateless 웹 서버보다 운영 난도가 높다.

## 3. AWS 서비스와의 연결

AWS에서는 Kafka와 RabbitMQ를 직접 EC2나 EKS에 설치할 수도 있고, 관리형 서비스를 사용할 수도 있다.

- Amazon MSK: Apache Kafka 호환 관리형 서비스
- Amazon MQ: RabbitMQ 및 ActiveMQ를 지원하는 관리형 메시지 브로커 서비스
- Amazon SQS: 완전관리형 메시지 큐 서비스
- Amazon SNS: Pub/Sub 방식의 알림 및 팬아웃 서비스
- Amazon EventBridge: 이벤트 버스 기반 이벤트 라우팅 서비스
- AWS Lambda: 메시지 이벤트를 트리거로 서버리스 처리 가능

예를 들어 주문 이벤트 팬아웃 구조는 SNS + SQS로도 구현할 수 있다.

```text
[Order Service]
   |
   v
[SNS Topic]
   ├── [SQS Queue: payment]
   ├── [SQS Queue: inventory]
   └── [SQS Queue: notification]
```

Kafka가 필요한 경우는 대용량 스트리밍, replay, offset 기반 소비, 여러 데이터 파이프라인 연계가 중요한 상황이다. 단순 작업 큐라면 SQS가 운영 부담을 크게 줄일 수 있다.

## 4. GCP 서비스와의 연결

GCP에서는 Google Cloud Pub/Sub가 대표적인 관리형 메시징 서비스이다. Topic과 Subscription을 기반으로 Pub/Sub 모델을 제공하며, 이벤트 기반 마이크로서비스, 로그 파이프라인, 비동기 작업 처리에 사용할 수 있다. Dataflow, Cloud Functions, Cloud Run과 연결하여 스트리밍 처리 파이프라인을 만들 수 있다.

```text
[Cloud Run Service]
   |
   v
[Pub/Sub Topic]
   |
   v
[Subscription]
   |
   v
[Cloud Function / Dataflow / Worker]
```

Kafka를 GCP에서 사용하려면 직접 운영하거나 Kafka 호환/관리형 솔루션을 선택할 수 있다. RabbitMQ 역시 Compute Engine이나 GKE 위에서 직접 운영하거나 외부 관리형 서비스를 사용할 수 있다.

## 5. 클라우드 아키텍처 선택 기준

- 단순 비동기 작업 큐: SQS, RabbitMQ, Cloud Pub/Sub
- 복잡한 라우팅: RabbitMQ, EventBridge
- 대용량 이벤트 스트리밍 및 재처리: Kafka, Amazon MSK
- 서버리스 이벤트 처리: SNS/SQS/Lambda, Pub/Sub/Cloud Functions
- 운영 부담 최소화: 관리형 메시징 서비스 우선 검토
- 세밀한 브로커 제어 필요: 직접 운영 또는 전용 클러스터

## 보안 연결

## 1. 인증과 인가

메시지 브로커는 서비스 간 핵심 데이터를 전달하므로 인증(Authentication)과 인가(Authorization)가 반드시 필요하다. 인증 없이 접근 가능한 Kafka나 RabbitMQ는 공격자가 메시지를 읽거나 위조 메시지를 발행할 수 있는 심각한 위험이 된다.

Kafka에서는 SASL, TLS, ACL 등을 이용해 클라이언트 인증과 권한 제어를 구성할 수 있다. RabbitMQ에서는 사용자 계정, virtual host, permission 설정을 통해 리소스 접근 범위를 제한할 수 있다. 운영 환경에서는 기본 계정, 기본 비밀번호, 과도한 권한을 제거해야 한다.

## 2. 전송 구간 암호화

Producer, Broker, Consumer 간 통신에는 민감한 데이터가 포함될 수 있다. 네트워크 구간에서 메시지가 평문으로 전달되면 스니핑이나 중간자 공격 위험이 있다. 따라서 TLS를 사용해 전송 구간 암호화를 적용하는 것이 모범 사례이다.

```text
Producer -- TLS --> Broker -- TLS --> Consumer
```

내부 VPC나 사설망에서 통신하더라도, 보안 요구사항이 높은 시스템에서는 암호화를 적용하는 것이 바람직하다.

## 3. 메시지 데이터 보안

메시지 안에는 개인정보, 결제 정보, 인증 토큰 등이 포함될 수 있다. 메시징 시스템은 여러 Consumer가 같은 이벤트를 볼 수 있기 때문에 최소 데이터 원칙이 중요하다. 필요하지 않은 민감 정보를 이벤트에 포함하지 말고, 필요한 경우 식별자만 전달한 뒤 권한 있는 서비스가 별도로 조회하도록 설계할 수 있다.

예를 들어 “user-created” 이벤트에 비밀번호 해시나 주민등록번호 같은 민감 정보를 넣는 것은 피해야 한다. 또한 로그 수집 시스템에 메시지 payload가 그대로 기록되지 않도록 주의해야 한다.

## 4. 중복 처리와 재전송 악용

메시징 시스템에서는 장애 복구 과정에서 메시지가 재전달될 수 있다. 공격자나 버그가 같은 메시지를 반복 발행하면 결제 중복 승인, 포인트 중복 지급, 쿠폰 중복 발급 같은 문제가 발생할 수 있다. 따라서 Consumer는 멱등성을 가져야 한다.

모범 사례는 다음과 같다.

- 메시지에 고유한 event_id 또는 command_id 포함
- 처리 이력 테이블 저장
- DB unique constraint 활용
- 외부 API 호출 전 중복 여부 확인
- 금전 처리에는 상태 전이 검증 적용

## 5. Poison Message와 Dead Letter Queue

Poison Message는 Consumer가 계속 실패하게 만드는 메시지이다. 예를 들어 잘못된 스키마, 누락된 필드, 처리 불가능한 상태를 가진 메시지가 반복 재시도되면 Worker 리소스를 계속 소모할 수 있다.

이를 방지하기 위해 Dead Letter Queue 또는 Dead Letter Exchange를 사용한다.

```text
[Main Queue]
   |
   | 처리 실패 N회
   v
[Dead Letter Queue]
   |
   v
[운영자 분석 / 수동 재처리]
```

Kafka에서도 실패 이벤트를 별도 실패 토픽으로 보내는 방식이 사용된다.

## 6. 권한 분리와 네트워크 격리

Producer와 Consumer에 필요한 권한은 다르다. 예를 들어 주문 API는 order-created 토픽에 write 권한만 있으면 되고, 분석 서비스는 read 권한만 있으면 된다. 모든 서비스에 모든 토픽의 read/write 권한을 주는 것은 위험하다.

네트워크 측면에서는 브로커를 public internet에 직접 노출하지 않고, VPC 내부, 보안 그룹, 방화벽, Kubernetes NetworkPolicy 등을 활용해 접근 가능한 서비스만 제한하는 것이 좋다.

## 7. 스키마 검증

이벤트 스키마가 깨지면 Consumer 장애가 발생할 수 있다. Kafka 환경에서는 Schema Registry와 Avro, Protobuf, JSON Schema 등을 사용해 이벤트 스키마 호환성을 관리하는 방식이 널리 쓰인다. RabbitMQ에서도 메시지 payload 스키마를 애플리케이션 레벨에서 검증해야 한다.

스키마 변경 시에는 하위 호환성, 필드 추가/삭제 정책, Consumer 배포 순서를 고려해야 한다.

## 면접 질문

**Q1. Kafka와 RabbitMQ의 가장 큰 차이는 무엇인가요?**  
> 핵심 답변: Kafka는 Topic-Partition 기반의 append-only 로그를 저장하고 Consumer가 offset으로 읽는 이벤트 스트리밍 플랫폼에 가깝다. RabbitMQ는 Exchange와 Queue를 중심으로 메시지를 라우팅하고 Ack 기반으로 제거하는 메시지 브로커이다. Kafka는 대용량 이벤트 재처리와 스트리밍에 강하고, RabbitMQ는 작업 큐와 복잡한 라우팅에 강하다.

**Q2. Pub/Sub 모델의 장점은 무엇인가요?**  
> 핵심 답변: Publisher와 Subscriber가 직접 의존하지 않아 결합도가 낮아진다. 하나의 이벤트를 여러 서비스가 독립적으로 소비할 수 있고, 신규 기능 추가 시 기존 발행자 코드를 크게 변경하지 않아도 된다. 마이크로서비스, 이벤트 기반 아키텍처, 팬아웃 처리에 적합하다.

**Q3. Kafka에서 Partition과 Consumer Group은 왜 중요한가요?**  
> 핵심 답변: Partition은 병렬성과 순서 보장의 단위이다. 같은 Partition 내에서는 순서가 보장되며, 여러 Partition을 통해 처리량을 확장할 수 있다. Consumer Group은 같은 작업을 수행하는 Consumer들의 논리적 그룹이며, 하나의 Partition은 같은 그룹 내에서 일반적으로 하나의 Consumer에게 할당된다. 서로 다른 Consumer Group은 같은 이벤트를 독립적으로 읽을 수 있다.

**Q4. 메시지 큐 기반 비동기 처리에서 중복 처리는 왜 발생하며 어떻게 대응하나요?**  
> 핵심 답변: Consumer 장애, Ack 실패, offset commit 실패, 네트워크 장애 등으로 메시지가 재전달될 수 있다. 따라서 Consumer는 멱등하게 설계해야 한다. event_id 저장, 처리 이력 테이블, DB unique constraint, 상태 전이 검증, 외부 API 호출 전 중복 확인 등을 사용한다.

**Q5. Dead Letter Queue는 언제 사용하나요?**  
> 핵심 답변: 메시지 처리 실패가 반복되어 정상 Queue에서 계속 재시도되면 전체 처리량과 안정성에 영향을 줄 수 있다. 특정 횟수 이상 실패한 메시지를 Dead Letter Queue나 실패 토픽으로 이동시켜 정상 메시지 처리를 보호하고, 운영자가 원인을 분석하거나 수동 재처리할 수 있게 한다.

## 관련 개념

- [[이벤트 기반 아키텍처]] - 서비스 간 상태 변화를 이벤트로 전달하는 설계 방식이며 Kafka, RabbitMQ 활용의 핵심 배경이다.
- [[메시지 큐]] - 비동기 작업 처리와 서비스 간 결합도 완화를 위한 기본 개념이다.
- [[Pub/Sub 패턴]] - 발행자와 구독자를 분리해 팬아웃과 확장성을 제공하는 메시징 모델이다.
- [[Apache Kafka]] - 로그 기반 이벤트 스트리밍 플랫폼으로 Topic, Partition, Offset 개념이 중요하다.
- [[RabbitMQ]] - Exchange, Queue, Binding, Ack 기반의 메시지 브로커이다.
- [[Consumer Group]] - Kafka에서 병렬 소비와 독립적 이벤트 처리를 가능하게 하는 핵심 개념이다.
- [[Dead Letter Queue]] - 처리 실패 메시지를 격리하여 시스템 안정성을 높이는 패턴이다.
- [[멱등성]] - 메시지 중복 처리로 인한 부작용을 방지하기 위한 필수 설계 원칙이다.
- [[Transactional Outbox 패턴]] - DB 트랜잭션과 이벤트 발행 간 불일치를 줄이기 위한 패턴이다.
- [[Backpressure]] - 생산 속도와 소비 속도의 차이로 인한 과부하를 제어하는 개념이다.
- [[At-least-once Delivery]] - 메시지가 최소 한 번 전달되는 보장 방식이며 중복 처리 가능성을 포함한다.
- [[Exactly-once Semantics]] - 중복 없이 한 번만 처리되는 것처럼 보장하려는 메시징 처리 개념이다.
- [[Schema Registry]] - 이벤트 스키마를 관리하여 Producer와 Consumer 간 호환성을 유지하는 도구이다.
- [[CDC]] - 데이터베이스 변경 사항을 이벤트 스트림으로 전달하는 방식으로 Kafka와 자주 연결된다.
