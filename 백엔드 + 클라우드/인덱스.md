# 인덱스 - B-Tree, B+Tree, 클러스터링 vs 논클러스터링, 복합 인덱스

## 핵심 개념

# 인덱스(Index) 핵심 개념

데이터베이스 인덱스는 테이블의 데이터를 더 빠르게 찾기 위해 별도로 유지하는 자료구조입니다. 책의 목차나 색인처럼, 전체 데이터를 처음부터 끝까지 스캔하지 않고 원하는 행이 있는 위치를 빠르게 좁혀 가도록 도와줍니다. 인덱스가 없으면 조건 검색 시 테이블 전체를 읽는 **Full Table Scan**이 발생할 수 있지만, 적절한 인덱스가 있으면 필요한 범위만 탐색하는 **Index Scan**, **Index Seek**, **Range Scan**이 가능해집니다.

백엔드 시스템에서 인덱스는 조회 성능, 정렬 성능, 조인 성능, 유니크 제약 조건 유지에 큰 영향을 줍니다. 특히 사용자 수가 많고 데이터가 증가하는 서비스에서는 인덱스 설계가 API 응답 시간과 서버 비용을 직접 좌우합니다. 하지만 인덱스는 항상 좋은 것만은 아닙니다. 인덱스도 별도의 저장 공간을 사용하며, `INSERT`, `UPDATE`, `DELETE` 시 인덱스도 함께 갱신해야 하므로 쓰기 성능이 저하될 수 있습니다. 따라서 인덱스는 “많이 만들수록 좋은 것”이 아니라, 실제 쿼리 패턴과 데이터 분포를 기준으로 신중하게 설계해야 합니다.

대표적인 인덱스 자료구조는 **B-Tree 계열**입니다. 대부분의 관계형 데이터베이스는 디스크 기반 저장소에서 효율적인 탐색을 위해 B-Tree 또는 B+Tree 계열 구조를 사용합니다. B-Tree와 B+Tree는 트리의 높이를 낮게 유지하여 디스크 I/O 횟수를 줄이고, 범위 검색에도 적합합니다. 또한 인덱스는 저장 방식에 따라 **클러스터링 인덱스**와 **논클러스터링 인덱스**로 나뉘며, 여러 컬럼을 묶어 만든 **복합 인덱스**는 조건절, 정렬, 조인에서 매우 중요한 역할을 합니다.

핵심적으로 인덱스는 다음 질문에 답하기 위한 도구입니다.

- 어떤 컬럼으로 자주 검색하는가?
- 어떤 컬럼으로 정렬하는가?
- 어떤 컬럼으로 조인하는가?
- 조건의 선택도, 즉 결과를 얼마나 좁혀 주는가?
- 읽기 성능 향상과 쓰기 비용 증가 사이의 균형은 적절한가?

## 내부 동작 원리

# 인덱스 내부 동작 원리

## 1. B-Tree

B-Tree는 균형 트리 자료구조입니다. 모든 리프 노드가 같은 깊이에 위치하도록 유지되며, 하나의 노드가 여러 개의 키와 자식 포인터를 가질 수 있습니다. 이 구조는 디스크나 SSD 같은 블록 기반 저장장치에서 효율적입니다. 한 번의 I/O로 여러 키를 포함한 페이지를 읽을 수 있기 때문입니다.

단순 이진 탐색 트리와 비교하면 다음과 같은 차이가 있습니다.

```text
이진 탐색 트리 예시
        50
       /  \
     20    80
    / \    / \
  10  30  70 90
```

이진 탐색 트리는 한 노드에 키가 하나이고 자식이 최대 2개입니다. 반면 B-Tree는 하나의 노드에 여러 키를 저장합니다.

```text
B-Tree 예시
              [30 | 60]
             /    |    \
     [10|20]  [40|50]  [70|80|90]
```

탐색 과정은 다음과 같습니다.

1. 루트 노드에서 시작한다.
2. 노드 내부의 키들과 검색 키를 비교한다.
3. 해당 키가 있으면 찾는다.
4. 없으면 적절한 자식 포인터를 따라 내려간다.
5. 리프 노드까지 반복한다.

B-Tree의 장점은 트리 높이가 낮다는 것입니다. 노드 하나에 많은 키를 저장할 수 있으므로 수백만 건 이상의 데이터도 비교적 적은 단계로 탐색할 수 있습니다.

## 2. B+Tree

B+Tree는 B-Tree의 변형으로, 많은 데이터베이스 인덱스에서 사용되는 대표적인 구조입니다. B+Tree의 중요한 특징은 다음과 같습니다.

- 내부 노드는 탐색을 위한 키와 자식 포인터를 저장한다.
- 실제 데이터 또는 데이터 위치 정보는 주로 리프 노드에 저장된다.
- 리프 노드들이 연결 리스트처럼 연결되어 범위 검색에 유리하다.

```text
B+Tree 예시

              [30 | 60]
             /    |    \
          /       |       \
   [10|20] -> [30|40|50] -> [60|70|80|90]
      |             |               |
   data/ref      data/ref        data/ref
```

여기서 화살표는 리프 노드 간 연결을 의미합니다. 예를 들어 `WHERE age BETWEEN 30 AND 70` 같은 범위 검색을 수행할 때, 먼저 `30`이 있는 리프 노드를 찾은 후, 오른쪽 리프 노드로 순차 이동하면서 `70`까지 읽을 수 있습니다. 이 방식은 정렬된 순서로 데이터를 읽을 수 있어 범위 검색, `ORDER BY`, `MIN`, `MAX` 등에 효과적입니다.

## 3. 인덱스 탐색 과정

예를 들어 다음과 같은 테이블이 있다고 가정합니다.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255),
    age INT,
    created_at TIMESTAMP
);

CREATE INDEX idx_users_email ON users(email);
```

`email` 컬럼에 B+Tree 인덱스가 있다면 다음 쿼리는 인덱스를 사용할 가능성이 높습니다.

```sql
SELECT *
FROM users
WHERE email = 'a@example.com';
```

동작 과정은 일반적으로 다음과 같습니다.

1. 옵티마이저가 실행 계획을 만든다.
2. `email` 조건에 사용할 수 있는 인덱스가 있는지 확인한다.
3. 인덱스 루트 페이지에서 검색을 시작한다.
4. 내부 노드를 거쳐 리프 노드까지 이동한다.
5. 리프 노드에서 `a@example.com`에 해당하는 엔트리를 찾는다.
6. 필요한 컬럼이 인덱스에 모두 있으면 인덱스만 읽고 끝낸다.
7. 필요한 컬럼이 인덱스에 없으면 테이블의 실제 행을 추가로 읽는다.

이때 6번처럼 인덱스만 읽고 쿼리를 처리할 수 있는 경우를 흔히 **커버링 인덱스**라고 합니다.

## 4. 클러스터링 인덱스 vs 논클러스터링 인덱스

### 클러스터링 인덱스

클러스터링 인덱스는 테이블의 실제 데이터가 인덱스 키 순서와 밀접하게 정렬되어 저장되는 방식입니다. 즉, 인덱스의 리프 레벨이 실제 데이터 페이지이거나 실제 데이터와 강하게 연결됩니다.

대표적으로 MySQL InnoDB에서는 기본 키가 클러스터드 인덱스로 사용됩니다. InnoDB 테이블의 데이터 행은 기본 키 기준으로 구성된 B+Tree의 리프 페이지에 저장됩니다.

```text
InnoDB 클러스터드 인덱스 개념

          [PK: 100 | 200]
          /            \
 [PK 1, row] ...   [PK 200, row] ...
```

특징은 다음과 같습니다.

- 기본 키 검색이 빠르다.
- 기본 키 범위 검색이 효율적이다.
- 테이블 자체가 기본 키 인덱스 구조에 가깝다.
- 기본 키 값이 크거나 자주 변경되면 비용이 커질 수 있다.
- 보조 인덱스가 기본 키 값을 참조하는 구조에서는 기본 키 크기가 보조 인덱스 크기에도 영향을 줄 수 있다.

### 논클러스터링 인덱스

논클러스터링 인덱스는 인덱스 구조와 실제 데이터 저장 순서가 분리된 방식입니다. 인덱스 리프에는 검색 키와 함께 실제 행을 찾기 위한 포인터, 행 식별자, 또는 기본 키 값이 저장됩니다.

```text
논클러스터링 인덱스 개념

email index
[a@example.com] -> row locator
[b@example.com] -> row locator
[c@example.com] -> row locator

table heap or clustered data
row1
row2
row3
```

특징은 다음과 같습니다.

- 여러 개 생성할 수 있다.
- 다양한 검색 조건을 지원할 수 있다.
- 인덱스 검색 후 실제 행을 다시 읽는 추가 비용이 발생할 수 있다.
- 조회 컬럼이 인덱스에 모두 포함되어 있으면 테이블 접근을 줄일 수 있다.

## 5. 복합 인덱스

복합 인덱스는 두 개 이상의 컬럼으로 구성된 인덱스입니다.

```sql
CREATE INDEX idx_orders_user_status_created
ON orders(user_id, status, created_at);
```

이 인덱스는 내부적으로 다음과 같은 정렬 순서를 가집니다.

```text
(user_id, status, created_at)
```

즉, 먼저 `user_id`로 정렬하고, 같은 `user_id` 안에서 `status`로 정렬하고, 같은 `status` 안에서 `created_at`으로 정렬합니다.

```text
(user_id, status, created_at)

(1, 'PAID',   '2024-01-01')
(1, 'PAID',   '2024-01-02')
(1, 'READY',  '2024-01-01')
(2, 'PAID',   '2024-01-01')
(2, 'READY',  '2024-01-03')
```

복합 인덱스에서 중요한 원칙은 **왼쪽부터 사용한다**는 것입니다. 이를 흔히 **Leftmost Prefix Rule**, 즉 왼쪽 접두어 원칙이라고 합니다.

위 인덱스는 다음 조건에 잘 활용될 수 있습니다.

```sql
WHERE user_id = 1
```

```sql
WHERE user_id = 1 AND status = 'PAID'
```

```sql
WHERE user_id = 1 AND status = 'PAID'
ORDER BY created_at
```

하지만 다음 조건은 인덱스를 충분히 활용하기 어렵습니다.

```sql
WHERE status = 'PAID'
```

왜냐하면 인덱스의 첫 번째 컬럼인 `user_id` 조건이 없기 때문입니다. 다만 일부 데이터베이스는 통계, 스킵 스캔 등 최적화 기법을 사용할 수 있으므로 실제 사용 여부는 실행 계획으로 확인해야 합니다.

복합 인덱스 설계 시 고려할 점은 다음과 같습니다.

- 동등 조건 `=`에 자주 쓰이는 컬럼을 앞에 둔다.
- 범위 조건 `>`, `<`, `BETWEEN` 이후의 컬럼은 인덱스 활용이 제한될 수 있다.
- `ORDER BY`, `GROUP BY`와 정렬 방향을 고려한다.
- 선택도가 높은 컬럼이 유리한 경우가 많지만, 항상 절대 규칙은 아니다.
- 실제 쿼리 패턴과 실행 계획을 기준으로 판단해야 한다.

## 실제 시스템 연결

# 실제 시스템에서의 인덱스

## 1. MySQL InnoDB

MySQL의 InnoDB 스토리지 엔진은 B+Tree 계열 인덱스를 사용합니다. InnoDB에서 기본 키는 클러스터드 인덱스로 구성되며, 실제 행 데이터는 기본 키 인덱스의 리프 페이지에 저장됩니다.

예를 들어 다음 테이블이 있습니다.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    name VARCHAR(100),
    created_at DATETIME,
    INDEX idx_users_email(email)
) ENGINE=InnoDB;
```

- `id`는 클러스터드 인덱스입니다.
- `idx_users_email`은 보조 인덱스입니다.
- 보조 인덱스의 리프에는 일반적으로 보조 인덱스 키와 기본 키 값이 저장됩니다.
- `email`로 검색한 뒤 실제 행 전체가 필요하면 기본 키를 이용해 클러스터드 인덱스를 다시 조회합니다.

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'a@example.com';
```

`EXPLAIN`을 통해 인덱스 사용 여부, 접근 방식, 예상 행 수 등을 확인할 수 있습니다.

## 2. PostgreSQL

PostgreSQL은 기본 인덱스 타입으로 B-tree를 제공합니다. PostgreSQL의 일반 테이블은 기본적으로 힙 구조로 저장되며, 인덱스는 테이블의 물리적 행 위치를 가리키는 식별자를 저장합니다. 특정 컬럼에 인덱스를 생성하면 조건 검색, 정렬, 조인 성능을 개선할 수 있습니다.

```sql
CREATE INDEX idx_users_email
ON users(email);
```

PostgreSQL에서는 다음과 같이 실행 계획을 확인합니다.

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'a@example.com';
```

`EXPLAIN ANALYZE`는 실제 실행까지 수행하므로 운영 환경에서는 주의가 필요합니다. PostgreSQL은 B-tree 외에도 Hash, GiST, SP-GiST, GIN, BRIN 같은 다양한 인덱스 타입을 제공합니다. 예를 들어 배열, JSONB, 전문 검색에는 GIN 인덱스가 자주 사용됩니다.

## 3. SQL Server

SQL Server는 클러스터드 인덱스와 논클러스터드 인덱스 개념을 명확히 제공합니다. 클러스터드 인덱스는 테이블 데이터의 논리적 정렬 기준이 되며, 테이블당 일반적으로 하나만 가질 수 있습니다. 논클러스터드 인덱스는 별도의 구조로 존재하며, 클러스터드 인덱스 키 또는 행 위치 정보를 통해 실제 데이터를 찾습니다.

```sql
CREATE CLUSTERED INDEX idx_orders_id
ON orders(id);

CREATE NONCLUSTERED INDEX idx_orders_user_id
ON orders(user_id);
```

## 4. Linux 파일 시스템과의 연결

데이터베이스 인덱스는 결국 디스크의 파일에 저장됩니다. Linux 환경에서 데이터베이스는 인덱스 페이지와 데이터 페이지를 파일 형태로 관리하며, 운영체제의 페이지 캐시, 디스크 I/O 스케줄링, 파일 시스템 성능의 영향을 받습니다.

인덱스가 효과적이면 읽어야 할 데이터 페이지 수가 줄어들어 디스크 I/O가 감소합니다. 반대로 인덱스가 없거나 잘못 설계되면 대량의 페이지를 읽게 되어 I/O 대기 시간이 증가할 수 있습니다.

실제 운영에서는 다음 지표를 함께 봅니다.

- DB 실행 계획
- 버퍼 캐시 적중률
- 디스크 읽기/쓰기 IOPS
- 쿼리 응답 시간
- Lock 대기
- CPU 사용률

## 5. Nginx와 백엔드 API 관점

Nginx 자체가 데이터베이스 인덱스를 사용하는 것은 아니지만, Nginx 뒤에 있는 백엔드 API 서버의 응답 시간은 데이터베이스 쿼리 성능에 크게 영향을 받습니다. 예를 들어 로그인 API에서 `email` 검색에 인덱스가 없다면 사용자 수 증가에 따라 응답 시간이 급격히 늘어날 수 있습니다.

```sql
SELECT id, password_hash
FROM users
WHERE email = ?;
```

이 쿼리는 일반적으로 `email` 컬럼에 인덱스가 있어야 효율적입니다. 특히 로그인, 주문 조회, 게시글 목록, 관리자 검색 기능처럼 빈번하게 호출되는 API에서는 인덱스 설계가 전체 서비스 처리량에 직접적인 영향을 줍니다.

## 클라우드 연결

# 클라우드 환경에서의 인덱스

## 1. Docker와 인덱스

Docker 컨테이너에서 데이터베이스를 실행할 때 인덱스는 컨테이너 내부 프로세스가 관리하는 데이터 파일에 저장됩니다. 중요한 점은 데이터베이스 파일을 컨테이너의 임시 파일 시스템에만 두면 컨테이너 삭제 시 데이터가 사라질 수 있다는 것입니다. 따라서 일반적으로 Docker Volume이나 외부 스토리지를 사용합니다.

```yaml
services:
  mysql:
    image: mysql
    volumes:
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:
```

인덱스 생성은 데이터 파일 변경을 동반하므로, 볼륨 성능이 낮으면 인덱스 생성, 대량 삽입, 쿼리 성능에 영향을 줄 수 있습니다.

## 2. Kubernetes와 Stateful Workload

Kubernetes에서 데이터베이스를 직접 운영할 경우 일반적으로 StatefulSet과 PersistentVolume을 사용합니다. 인덱스는 데이터베이스의 영속 데이터에 포함되므로 PersistentVolume에 저장됩니다.

고려할 점은 다음과 같습니다.

- PersistentVolume의 IOPS와 지연 시간
- 인덱스 생성 중 디스크 사용량 증가
- 재시작 시 캐시가 비어 초기 쿼리 성능이 낮아질 가능성
- 마이그레이션 작업 중 Lock 발생 가능성
- Read Replica와 인덱스 변경 전파

운영 데이터베이스를 Kubernetes에서 직접 관리하는 것은 백업, 장애 조치, 복구, 스토리지 성능 관리까지 고려해야 하므로 복잡도가 높습니다. 많은 팀은 관리형 데이터베이스 서비스를 사용합니다.

## 3. AWS RDS / Aurora

AWS RDS는 MySQL, PostgreSQL, MariaDB, SQL Server 등 여러 데이터베이스 엔진을 관리형으로 제공합니다. 인덱스 구조 자체는 선택한 엔진의 동작을 따릅니다. 예를 들어 RDS for MySQL에서 InnoDB를 사용하면 InnoDB의 B+Tree 기반 인덱스와 클러스터드 인덱스 특성을 이해해야 합니다.

AWS 환경에서 인덱스와 관련해 자주 보는 요소는 다음과 같습니다.

- Amazon RDS Performance Insights로 느린 쿼리 분석
- CloudWatch 지표로 CPU, IOPS, 지연 시간 확인
- Read Replica에서 읽기 트래픽 분산
- 인덱스 생성 시 스토리지 사용량 증가
- 운영 중 인덱스 생성으로 인한 Lock 또는 성능 저하 가능성

Aurora 역시 MySQL 호환 또는 PostgreSQL 호환 엔진을 제공하므로 SQL 레벨의 인덱스 설계 원칙은 해당 엔진의 특성을 따릅니다.

## 4. GCP Cloud SQL / AlloyDB

GCP Cloud SQL은 MySQL, PostgreSQL, SQL Server용 관리형 데이터베이스를 제공합니다. 인덱스 사용 여부는 데이터베이스 엔진의 옵티마이저와 통계 정보에 의해 결정됩니다. Cloud SQL에서도 실행 계획 분석, 느린 쿼리 로그, 모니터링 지표를 활용해 인덱스 문제를 찾습니다.

AlloyDB는 PostgreSQL 호환 관리형 데이터베이스 서비스입니다. PostgreSQL 호환 쿼리와 인덱스 설계를 기반으로 성능 튜닝을 수행합니다.

## 5. 클라우드 마이그레이션과 인덱스

온프레미스 데이터베이스를 클라우드로 이전할 때 인덱스는 매우 중요합니다. 동일한 스키마라도 스토리지 성능, 캐시 크기, CPU, 네트워크 구조가 달라지면 실행 계획이 달라질 수 있습니다.

마이그레이션 시 확인해야 할 항목은 다음과 같습니다.

- 기존 인덱스가 실제로 사용되고 있는가?
- 중복 인덱스가 있는가?
- 누락 인덱스로 인해 Full Scan이 발생하는가?
- 통계 정보가 최신인가?
- 대량 데이터 이관 후 `ANALYZE` 또는 통계 갱신이 필요한가?
- 읽기/쓰기 비율에 맞는 인덱스 개수인가?

## 보안 연결

# 인덱스와 보안

## 1. 인덱스는 보안 기능이 아니다

인덱스는 성능 최적화 도구이지 접근 제어 기능이 아닙니다. 특정 컬럼에 인덱스를 만들었다고 해서 데이터가 보호되는 것은 아닙니다. 인덱스 파일에도 키 값이나 키의 일부가 저장될 수 있으므로, 민감 정보가 인덱스에 포함될 경우 데이터 파일, 백업, 스냅샷, 복제본 관리가 중요합니다.

예를 들어 이메일, 전화번호, 주민등록번호와 같은 개인정보 컬럼에 인덱스를 생성하면 해당 값이 인덱스 구조에도 포함될 수 있습니다. 따라서 데이터베이스 파일, 백업, 로그, 덤프 파일에 대한 접근 권한을 엄격히 관리해야 합니다.

## 2. 개인정보와 인덱스

개인정보 컬럼에 인덱스를 만들 때는 다음을 고려해야 합니다.

- 정말 검색 조건으로 필요한가?
- 전체 값을 인덱싱해야 하는가?
- 해시 값을 별도 컬럼으로 저장해 검색할 수 있는가?
- 암호화된 값에 대해 검색이 가능한 구조인가?
- 백업과 복제본에도 동일한 보호가 적용되는가?

예를 들어 이메일을 정확히 일치 검색해야 한다면, 애플리케이션에서 정규화한 이메일의 해시 값을 저장하고 그 해시 컬럼에 인덱스를 거는 방식을 고려할 수 있습니다. 단, 해시 기반 검색은 부분 검색이나 범위 검색에는 적합하지 않습니다. 또한 낮은 엔트로피 값을 단순 해시하면 사전 공격에 취약할 수 있으므로 솔트, 키드 해시, HMAC 등 보안 설계를 신중히 검토해야 합니다.

## 3. 암호화와 인덱스

일반적인 강한 암호화는 값을 무작위처럼 보이게 만들기 때문에 범위 검색이나 정렬 인덱스와 잘 맞지 않습니다. 예를 들어 암호화된 생년월일 컬럼에 대해 `BETWEEN` 검색을 수행하기는 어렵습니다.

가능한 접근은 다음과 같습니다.

- 정확 일치 검색용 해시 컬럼 추가
- 민감도 낮은 파생 컬럼 인덱싱
- 검색 전용 토큰화 시스템 사용
- 데이터베이스 투명 데이터 암호화 사용
- 애플리케이션 레벨 암호화와 검색 요구사항 분리

투명 데이터 암호화는 디스크에 저장된 데이터와 인덱스 파일 보호에 도움이 될 수 있지만, 데이터베이스에 정상 접속한 사용자의 쿼리 결과까지 자동으로 숨겨 주는 것은 아닙니다. 따라서 접근 제어와 감사 로그가 함께 필요합니다.

## 4. SQL Injection과 인덱스

SQL Injection은 인덱스 문제가 아니라 입력값 검증 및 쿼리 파라미터화 문제입니다. 하지만 공격자가 인덱스를 우회하는 조건을 유도하거나 대량 스캔을 발생시키는 쿼리를 실행하게 만들면 성능 저하 또는 서비스 거부에 가까운 문제가 발생할 수 있습니다.

예를 들어 다음과 같은 동적 SQL은 위험합니다.

```sql
SELECT *
FROM users
WHERE email = '" + userInput + "';
```

모범 사례는 Prepared Statement 또는 바인딩 파라미터를 사용하는 것입니다.

```sql
SELECT *
FROM users
WHERE email = ?;
```

## 5. 인덱스와 서비스 거부 위험

인덱스가 없거나 잘못 설계된 검색 API는 공격자가 의도적으로 무거운 검색 조건을 반복 호출할 때 쉽게 병목이 될 수 있습니다. 예를 들어 `%keyword%` 형태의 LIKE 검색은 일반적인 B-Tree 인덱스를 효율적으로 사용하기 어렵습니다.

```sql
SELECT *
FROM posts
WHERE title LIKE '%spring%';
```

이런 검색을 외부에 노출할 경우 다음 대책을 고려해야 합니다.

- 검색 조건 제한
- 페이지 크기 제한
- Rate Limiting
- 타임아웃 설정
- 전문 검색 엔진 또는 Full-Text Index 사용
- 적절한 인덱스 설계
- 관리자 검색 API 별도 보호

## 6. 유니크 인덱스와 무결성 보안

유니크 인덱스는 데이터 무결성을 보장하는 데 중요합니다. 예를 들어 이메일 중복 가입 방지는 애플리케이션 로직만으로 처리하면 Race Condition이 발생할 수 있습니다.

```sql
CREATE UNIQUE INDEX ux_users_email
ON users(email);
```

동시 요청이 들어와도 데이터베이스의 유니크 제약이 최종적으로 중복을 막아 줍니다. 이는 보안 관점에서도 계정 식별자 중복, 권한 매핑 오류, 중복 주문 처리 같은 문제를 줄이는 데 도움이 됩니다.

## 면접 질문

# 면접 질문

**Q1. B-Tree와 B+Tree의 차이는 무엇인가요?**  
> 핵심 답변: B-Tree는 내부 노드와 리프 노드 모두에 키와 데이터를 저장할 수 있는 균형 트리이고, B+Tree는 일반적으로 내부 노드는 탐색용 키와 포인터를 저장하고 실제 데이터 또는 데이터 참조는 리프 노드에 모으는 구조입니다. B+Tree는 리프 노드들이 연결되어 있어 범위 검색과 순차 읽기에 유리합니다. 많은 관계형 데이터베이스 인덱스는 B+Tree 계열 구조를 사용합니다.

**Q2. 클러스터링 인덱스와 논클러스터링 인덱스의 차이는 무엇인가요?**  
> 핵심 답변: 클러스터링 인덱스는 데이터의 실제 저장 구조가 인덱스 키 순서와 밀접하게 연결된 방식입니다. 예를 들어 InnoDB에서는 기본 키가 클러스터드 인덱스이며 리프 페이지에 실제 행 데이터가 저장됩니다. 논클러스터링 인덱스는 별도의 인덱스 구조를 가지고, 리프에는 실제 행을 찾기 위한 포인터나 기본 키 값이 저장됩니다. 논클러스터링 인덱스는 여러 개 만들 수 있지만 실제 행 조회를 위한 추가 접근 비용이 발생할 수 있습니다.

**Q3. 복합 인덱스에서 컬럼 순서가 중요한 이유는 무엇인가요?**  
> 핵심 답변: 복합 인덱스는 지정된 컬럼 순서대로 정렬됩니다. `(user_id, status, created_at)` 인덱스는 먼저 `user_id`, 그다음 `status`, 그다음 `created_at` 순서로 정렬됩니다. 따라서 왼쪽 접두어 원칙에 따라 `user_id` 조건이 있는 쿼리는 잘 활용할 수 있지만, `status`만 단독 조건으로 사용하는 쿼리에서는 효율적으로 사용하기 어렵습니다. 컬럼 순서는 실제 WHERE, JOIN, ORDER BY 패턴을 기준으로 설계해야 합니다.

**Q4. 인덱스를 많이 만들면 왜 문제가 될 수 있나요?**  
> 핵심 답변: 인덱스는 별도 저장 공간을 사용하며, 쓰기 작업 시 테이블뿐 아니라 관련 인덱스도 함께 갱신해야 합니다. 따라서 인덱스가 많으면 `INSERT`, `UPDATE`, `DELETE` 성능이 저하될 수 있고, 디스크 사용량과 캐시 부담도 증가합니다. 또한 옵티마이저가 선택할 후보가 많아지고 중복 인덱스 관리가 어려워질 수 있습니다. 인덱스는 쿼리 성능 개선 효과와 쓰기 비용을 함께 고려해야 합니다.

**Q5. 커버링 인덱스란 무엇이고 왜 빠른가요?**  
> 핵심 답변: 커버링 인덱스는 쿼리에 필요한 컬럼이 모두 인덱스에 포함되어 있어 테이블의 실제 행을 추가로 읽지 않아도 되는 인덱스입니다. 예를 들어 `SELECT email FROM users WHERE email = ?`에서 `email` 인덱스만으로 결과를 반환할 수 있다면 테이블 접근이 줄어듭니다. 테이블 랜덤 I/O를 줄일 수 있어 성능상 유리하지만, 포함 컬럼이 많아지면 인덱스 크기와 쓰기 비용이 증가할 수 있습니다.

- [[커버링 인덱스]] - 쿼리에 필요한 컬럼을 모두 포함하여 테이블 접근을 줄이는 인덱스입니다.
- [[선택도]] - 인덱스가 검색 결과를 얼마나 잘 좁혀 주는지 판단하는 기준입니다.
- [[카디널리티]] - 컬럼 값의 고유한 정도를 나타내며 인덱스 효율성 판단에 사용됩니다.
- [[Full Table Scan]] - 인덱스를 효과적으로 사용하지 못하고 테이블 전체를 읽는 접근 방식입니다.
- [[Index Range Scan]] - B-Tree 계열 인덱스에서 범위 조건을 처리할 때 자주 사용되는 접근 방식입니다.
- [[데이터베이스 통계 정보]] - 옵티마이저가 인덱스 사용 여부를 판단하는 데 활용하는 메타데이터입니다.
- [[유니크 인덱스]] - 중복 값을 방지하고 데이터 무결성을 보장하는 인덱스입니다.
- [[MVCC]] - PostgreSQL, InnoDB 등에서 동시성 제어와 인덱스 가시성 판단에 영향을 주는 개념입니다.
