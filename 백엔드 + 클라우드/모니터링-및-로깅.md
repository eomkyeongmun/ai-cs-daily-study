# 모니터링 및 로깅 - Prometheus, Grafana, ELK(Elasticsearch, Logstash, Kibana) 스택

## 핵심 개념

모니터링과 로깅은 백엔드 인프라 운영에서 시스템의 “현재 상태”와 “과거에 발생한 사건”을 관찰하기 위한 핵심 기술이다. **모니터링**은 CPU 사용률, 메모리 사용량, HTTP 요청 수, 응답 시간, 에러율 같은 지표(metric)를 수집하여 시스템이 정상적으로 동작하는지 지속적으로 확인하는 과정이다. 대표적인 도구로 **Prometheus**와 **Grafana**가 있다. Prometheus는 시계열 데이터베이스 기반의 모니터링 시스템으로, 애플리케이션이나 서버에서 노출하는 메트릭을 주기적으로 수집하고 PromQL을 통해 질의한다. Grafana는 Prometheus, Elasticsearch, Loki 등 다양한 데이터 소스를 시각화하는 대시보드 도구다.

반면 **로깅**은 애플리케이션, 웹 서버, 운영체제, 데이터베이스 등에서 발생한 이벤트를 텍스트 또는 구조화된 데이터로 기록하는 것이다. 로그는 장애 원인 분석, 보안 감사, 사용자 행위 추적, 성능 병목 파악에 중요하다. **ELK 스택**은 Elasticsearch, Logstash, Kibana로 구성된 대표적인 로그 수집·저장·분석 플랫폼이다. Elasticsearch는 검색 및 분석 엔진, Logstash는 로그 수집·가공 파이프라인, Kibana는 로그 검색 및 시각화 UI 역할을 한다.

모니터링과 로깅은 서로 보완적이다. 예를 들어 Prometheus가 “API 에러율이 급증했다”는 사실을 알려주면, ELK에서 해당 시간대의 애플리케이션 로그를 검색해 어떤 예외가 발생했는지 확인할 수 있다. 운영 환경에서는 단순히 서버가 살아 있는지 확인하는 수준을 넘어, 서비스 품질, 장애 탐지, 용량 계획, 보안 대응을 위해 모니터링과 로깅 체계를 함께 설계하는 것이 중요하다.

## 내부 동작 원리

## 1. Prometheus의 내부 동작 원리

Prometheus는 기본적으로 **Pull 기반**으로 동작한다. 즉, 모니터링 대상이 Prometheus 서버로 데이터를 보내는 것이 아니라, Prometheus가 주기적으로 각 대상의 HTTP 엔드포인트에 접근해 메트릭을 가져온다.

일반적인 흐름은 다음과 같다.

```text
[Application / Exporter]
        |
        |  /metrics 엔드포인트 노출
        v
[Prometheus Server]
        |
        |  scrape_interval마다 메트릭 수집
        v
[TSDB: Time Series Database]
        |
        |  PromQL 질의
        v
[Grafana Dashboard / Alertmanager]
```

### 주요 구성 요소

- **Exporter**
  - 기존 시스템의 상태를 Prometheus가 이해할 수 있는 메트릭 형식으로 노출하는 컴포넌트다.
  - 예: Node Exporter는 Linux 서버의 CPU, 메모리, 디스크, 네트워크 지표를 노출한다.
  - Nginx, MySQL, PostgreSQL, Redis 등 다양한 exporter가 존재한다.

- **Scrape**
  - Prometheus가 주기적으로 `/metrics` 같은 HTTP 엔드포인트를 호출하여 메트릭을 수집하는 과정이다.
  - 수집 대상은 정적 설정 파일 또는 Kubernetes Service Discovery 같은 동적 방식으로 등록될 수 있다.

- **TSDB**
  - Prometheus는 메트릭을 시계열 데이터로 저장한다.
  - 각 시계열은 메트릭 이름과 label 조합으로 식별된다.
  - 예:
    ```text
    http_requests_total{method="GET", status="200", service="api"}
    ```

- **PromQL**
  - Prometheus Query Language의 약자다.
  - 특정 지표의 현재 값, 일정 시간 동안의 증가율, 평균, 분위수 등을 계산할 수 있다.
  - 예:
    ```promql
    rate(http_requests_total[5m])
    ```
    최근 5분 동안 HTTP 요청 수의 초당 증가율을 계산한다.

- **Alertmanager**
  - Prometheus에서 발생한 알림을 받아 이메일, Slack, PagerDuty 등으로 전달할 수 있다.
  - 중복 알림 억제, 그룹화, 라우팅 등의 기능을 제공한다.

## 2. Grafana의 내부 동작 원리

Grafana는 직접 데이터를 수집하기보다는 여러 데이터 소스에 질의하여 결과를 시각화한다.

```text
[User Browser]
      |
      v
[Grafana Web UI]
      |
      | Data Source Query
      v
[Prometheus / Elasticsearch / Loki / CloudWatch 등]
      |
      v
[Graph, Table, Alert, Dashboard]
```

Grafana는 데이터 소스별 쿼리를 실행하고, 결과를 패널 형태로 표현한다. 예를 들어 Prometheus를 데이터 소스로 등록하면 PromQL을 사용해 CPU 사용률, 요청 처리량, 에러율 등을 그래프로 표현할 수 있다. Elasticsearch를 데이터 소스로 등록하면 특정 로그 패턴이나 에러 발생 추이를 시각화할 수 있다.

Grafana 대시보드는 보통 다음 요소로 구성된다.

- **Data Source**: Prometheus, Elasticsearch, CloudWatch 등
- **Dashboard**: 여러 패널을 묶은 화면
- **Panel**: 그래프, 테이블, 게이지, 히트맵 등 시각화 단위
- **Variable**: 서비스명, 인스턴스명, 네임스페이스 등을 동적으로 선택하는 변수
- **Alert Rule**: 특정 조건 충족 시 알림 발생

## 3. ELK 스택의 내부 동작 원리

ELK는 로그 데이터를 수집, 변환, 저장, 검색, 시각화하는 파이프라인이다.

```text
[Application / Nginx / Linux syslog]
        |
        | 로그 파일, stdout, syslog 등
        v
[Logstash]
        |
        | input -> filter -> output
        v
[Elasticsearch]
        |
        | index 저장, 역색인 생성
        v
[Kibana]
        |
        | 검색, 대시보드, 시각화
        v
[Operator / Developer]
```

### Logstash

Logstash는 로그 파이프라인 도구다. 일반적으로 다음 세 단계로 구성된다.

```text
input  ->  filter  ->  output
```

- **input**
  - 로그를 어디서 받을지 정의한다.
  - 예: 파일, Beats, TCP, UDP, Kafka 등

- **filter**
  - 로그를 파싱하거나 변환한다.
  - 예: grok 패턴으로 Nginx access log 파싱, timestamp 변환, 필드 추가, 민감정보 마스킹

- **output**
  - 처리된 로그를 어디로 보낼지 정의한다.
  - 예: Elasticsearch, 파일, Kafka 등

예시 흐름:

```text
Nginx access.log
 -> Filebeat 또는 Logstash input
 -> grok filter로 IP, method, path, status, latency 추출
 -> Elasticsearch index에 저장
 -> Kibana에서 status:500 조건으로 검색
```

### Elasticsearch

Elasticsearch는 JSON 문서를 저장하고 검색하는 분산 검색 엔진이다. 로그 한 줄은 보통 하나의 문서(document)로 저장된다. Elasticsearch는 문서를 index에 저장하고, 검색 성능을 위해 역색인(inverted index)을 구성한다.

예를 들어 다음 로그가 있다고 하자.

```json
{
  "timestamp": "2026-01-01T10:00:00Z",
  "level": "ERROR",
  "service": "payment-api",
  "message": "Payment gateway timeout",
  "trace_id": "abc123"
}
```

Elasticsearch는 `level`, `service`, `message`, `trace_id` 같은 필드 기반 검색과 집계를 지원한다. Kibana에서는 `level: ERROR AND service: payment-api` 같은 조건으로 로그를 검색할 수 있다.

### Kibana

Kibana는 Elasticsearch에 저장된 데이터를 검색하고 시각화하는 웹 UI다. 운영자는 Kibana를 통해 특정 시간대 로그를 검색하거나, 에러 발생 수, HTTP 상태 코드 분포, 사용자 요청 패턴 등을 시각화할 수 있다.

## 실제 시스템 연결

## Linux 서버 모니터링

Linux 서버에서는 **Node Exporter**를 사용해 CPU, 메모리, 디스크, 네트워크 관련 지표를 Prometheus로 수집할 수 있다.

예시 지표:

```text
node_cpu_seconds_total
node_memory_MemAvailable_bytes
node_filesystem_avail_bytes
node_network_receive_bytes_total
```

실제 운영에서는 다음과 같은 대시보드를 구성한다.

- CPU 사용률
- 메모리 사용률
- 디스크 사용률
- inode 사용률
- 네트워크 송수신량
- 서버별 load average

이 지표들은 서버 장애의 조기 징후를 파악하는 데 유용하다. 예를 들어 디스크 사용률이 지속적으로 증가하면 로그 파일 누적, 데이터베이스 파일 증가, 백업 파일 방치 등을 의심할 수 있다.

## Nginx 로그 분석

Nginx는 access log와 error log를 남긴다. access log는 HTTP 요청의 IP, 요청 경로, 상태 코드, 응답 크기, user-agent, 처리 시간 등을 포함할 수 있다.

ELK를 사용하면 다음과 같은 분석이 가능하다.

- 5xx 에러가 많이 발생하는 URL 확인
- 특정 IP에서 과도한 요청이 발생하는지 확인
- 응답 시간이 긴 API 경로 분석
- user-agent 기반 봇 트래픽 탐지
- 시간대별 요청량 추이 분석

예시 파이프라인:

```text
Nginx access.log
 -> Filebeat
 -> Logstash
 -> Elasticsearch
 -> Kibana Dashboard
```

## Spring Boot / Node.js 애플리케이션

백엔드 애플리케이션에서는 Prometheus client library를 사용해 직접 메트릭을 노출할 수 있다.

예시 메트릭:

- HTTP 요청 수
- HTTP 응답 시간
- 비즈니스 이벤트 수
- DB 커넥션 풀 사용량
- JVM heap memory
- Node.js event loop delay

Spring Boot에서는 Actuator와 Micrometer를 조합해 Prometheus 형식의 메트릭 엔드포인트를 제공할 수 있다. Node.js에서는 prom-client 같은 라이브러리를 사용해 `/metrics` 엔드포인트를 만들 수 있다.

로그 측면에서는 JSON 형식의 구조화 로그를 남기는 것이 운영에 유리하다.

예시:

```json
{
  "timestamp": "2026-01-01T10:00:00Z",
  "level": "ERROR",
  "service": "order-api",
  "trace_id": "d9f1a2",
  "user_id": "12345",
  "message": "Failed to create order",
  "exception": "Database timeout"
}
```

구조화 로그를 사용하면 Kibana에서 `trace_id`, `service`, `level` 기준으로 쉽게 필터링할 수 있다.

## 장애 대응 시나리오

예를 들어 결제 API에서 장애가 발생했다고 가정한다.

1. Grafana에서 `payment-api`의 5xx 비율이 증가한 것을 확인한다.
2. Prometheus에서 DB 커넥션 풀 사용률과 응답 시간 지표를 확인한다.
3. Kibana에서 같은 시간대 `payment-api`의 ERROR 로그를 검색한다.
4. 로그의 `trace_id`를 기준으로 요청 흐름을 추적한다.
5. Nginx access log에서 특정 API 경로에 요청이 집중되었는지 확인한다.
6. 원인이 외부 결제 게이트웨이 timeout인지, 내부 DB 병목인지 판단한다.

이처럼 메트릭은 “무엇이 이상한가”를 빠르게 알려주고, 로그는 “왜 이상한가”를 분석하는 데 도움을 준다.

## 클라우드 연결

## Docker 환경

Docker 컨테이너 환경에서는 애플리케이션이 stdout/stderr로 로그를 출력하는 방식이 일반적이다. 컨테이너 런타임은 이를 수집하고, Filebeat, Fluent Bit, Logstash 같은 에이전트가 중앙 로그 시스템으로 전달할 수 있다.

Prometheus는 컨테이너 내부 애플리케이션의 `/metrics` 엔드포인트 또는 Docker 관련 exporter를 통해 메트릭을 수집할 수 있다.

```text
[Container App]
   | stdout logs
   v
[Docker Logging Driver / Agent]
   v
[Elasticsearch]

[Container App /metrics]
   v
[Prometheus]
   v
[Grafana]
```

## Kubernetes 환경

Kubernetes에서는 모니터링과 로깅 구성이 더 중요해진다. Pod는 언제든 재시작되거나 다른 노드로 이동할 수 있기 때문에, 로컬 로그 파일에만 의존하면 장애 분석이 어렵다.

### Prometheus와 Kubernetes

Prometheus는 Kubernetes Service Discovery를 통해 Pod, Service, Endpoint를 자동으로 발견할 수 있다. 일반적으로 다음 구성 요소가 함께 사용된다.

- **Prometheus Operator**
  - Kubernetes에서 Prometheus 설정을 Custom Resource로 관리할 수 있게 한다.
- **ServiceMonitor / PodMonitor**
  - 어떤 Service 또는 Pod를 scrape할지 선언적으로 정의한다.
- **kube-state-metrics**
  - Deployment, Pod, Node, PersistentVolume 등 Kubernetes 객체 상태를 메트릭으로 제공한다.
- **cAdvisor**
  - 컨테이너 CPU, 메모리, 파일시스템, 네트워크 지표를 제공한다.

예시 모니터링 대상:

- Pod 재시작 횟수
- Container CPU throttling
- Node 메모리 압박
- Deployment replica 불일치
- HPA 스케일링 상태
- Ingress 요청 수와 latency

### ELK와 Kubernetes

Kubernetes 로깅에서는 각 노드에 DaemonSet 형태로 로그 수집 에이전트를 배포하는 방식이 흔하다.

```text
[Pod stdout/stderr]
      |
      v
[Node 로그 파일]
      |
      v
[Filebeat / Fluent Bit DaemonSet]
      |
      v
[Logstash or Elasticsearch]
      |
      v
[Kibana]
```

Kubernetes 환경에서는 로그에 다음 메타데이터를 함께 붙이는 것이 중요하다.

- namespace
- pod name
- container name
- node name
- deployment 또는 app label
- cluster name

이 정보가 있어야 Kibana에서 특정 네임스페이스나 서비스 단위로 로그를 필터링할 수 있다.

## AWS와의 연관성

AWS에서는 자체 관측성 서비스인 **Amazon CloudWatch**가 널리 사용된다. EC2, ECS, EKS, RDS, ALB, Lambda 등의 메트릭과 로그를 CloudWatch로 수집할 수 있다. Prometheus 기반 구성을 원한다면 **Amazon Managed Service for Prometheus**를 사용할 수 있고, Grafana 대시보드는 **Amazon Managed Grafana**로 운영할 수 있다.

AWS 환경에서 가능한 구성:

```text
[EKS Workloads]
   -> Prometheus / Managed Prometheus
   -> Grafana / Managed Grafana

[EC2 / ALB / RDS Logs]
   -> CloudWatch Logs
   -> Subscription Filter
   -> Elasticsearch/OpenSearch 계열 분석 시스템
```

⚠️ 확인 필요: AWS의 관리형 검색 서비스 명칭과 세부 기능은 시점에 따라 변경될 수 있으므로, 실제 설계 시 현재 AWS 문서를 확인해야 한다.

## GCP와의 연관성

GCP에서는 Cloud Monitoring과 Cloud Logging을 통해 VM, GKE, Cloud Run, Cloud SQL 등의 메트릭과 로그를 수집할 수 있다. GKE에서는 Prometheus 기반 모니터링을 직접 배포하거나 관리형 Prometheus 기능을 사용할 수 있다.

일반적인 설계 관점은 다음과 같다.

- 클라우드 네이티브 기본 관측성: Cloud Monitoring / Cloud Logging
- 오픈소스 기반 관측성: Prometheus / Grafana / ELK 또는 EFK
- 하이브리드 환경: Prometheus federation, remote write, 로그 포워딩 활용

## EFK 스택과의 관계

Kubernetes 환경에서는 Logstash 대신 Fluentd 또는 Fluent Bit을 사용하는 **EFK 스택**도 자주 사용된다.

```text
Elasticsearch + Fluentd/Fluent Bit + Kibana
```

Logstash는 강력한 필터링 기능이 장점이지만, 상대적으로 무겁게 느껴질 수 있다. Fluent Bit은 경량 로그 수집 에이전트로 컨테이너 환경에서 자주 사용된다.

## 보안 연결

## 1. 로그에 민감정보를 남기지 않기

로그에는 사용자 입력, 요청 헤더, 인증 토큰, 쿠키, 개인정보가 포함될 수 있다. 다음 정보는 로그에 직접 남기지 않는 것이 좋다.

- 비밀번호
- Access Token / Refresh Token
- API Key
- Session ID
- 주민등록번호 등 고유식별정보
- 신용카드 번호
- 인증 쿠키
- 개인정보 원문

불가피하게 기록해야 한다면 마스킹 또는 해싱을 적용해야 한다.

예:

```text
email: user@example.com -> u***@example.com
card_number: 1234-5678-9012-3456 -> ****-****-****-3456
```

## 2. Grafana, Kibana 접근 제어

Grafana와 Kibana는 운영 시스템의 내부 상태와 로그를 볼 수 있는 강력한 도구다. 접근 제어가 부실하면 다음 문제가 발생할 수 있다.

- 내부 API 경로 노출
- 사용자 개인정보 노출
- 인증 토큰 또는 세션 정보 유출
- 장애 상황 및 인프라 구조 노출
- 쿼리를 통한 과도한 리소스 사용

모범 사례:

- SSO 또는 중앙 인증 시스템 연동
- 역할 기반 접근 제어, 즉 RBAC 적용
- 관리자 권한 최소화
- 외부 인터넷에 직접 노출하지 않기
- VPN, Private Subnet, Zero Trust 접근 제어 활용
- 감사 로그 활성화

## 3. Elasticsearch 보안

Elasticsearch는 로그와 문서를 저장하는 핵심 시스템이므로 보안 설정이 매우 중요하다.

주의할 점:

- 인증 없이 외부에 노출하지 않기
- TLS 적용
- 인덱스별 접근 권한 분리
- 스냅샷 저장소 접근 권한 관리
- 민감 로그 저장 시 암호화 고려
- 불필요한 동적 스크립트나 위험한 기능 제한 검토

Elasticsearch가 외부에 잘못 노출되면 대량의 로그 데이터가 유출될 수 있다. 특히 로그에는 내부 IP, 사용자 정보, 요청 파라미터, 장애 스택트레이스 등이 포함될 수 있으므로 별도의 보안 정책이 필요하다.

## 4. Prometheus 보안

Prometheus의 `/metrics` 엔드포인트는 단순한 수치 정보처럼 보이지만, 실제로는 내부 시스템 구조를 유추할 수 있는 정보가 포함될 수 있다.

예:

- 서비스 이름
- 인스턴스 주소
- 내부 경로
- 데이터베이스 연결 상태
- 큐 길이
- 에러 종류
- 외부 의존성 이름

따라서 `/metrics` 엔드포인트는 외부에 공개하지 않는 것이 원칙이다. Kubernetes에서는 NetworkPolicy, Ingress 제한, mTLS, 인증 프록시 등을 통해 접근을 제한할 수 있다.

## 5. 로그 위변조와 감사

보안 감사 목적의 로그는 위변조 방지가 중요하다. 공격자가 침입 후 로그를 삭제하거나 조작하면 사고 원인 분석이 어려워진다.

모범 사례:

- 로그를 중앙 저장소로 실시간 전송
- 애플리케이션 서버 로컬에만 로그를 보관하지 않기
- 로그 보존 기간 정책 수립
- 접근 권한 분리
- 삭제 작업에 대한 감사 로그 남기기
- 중요한 보안 로그는 별도 저장소 또는 WORM 성격의 저장 방식 고려

## 6. 알림 피로와 보안 대응

알림이 너무 많으면 운영자가 중요한 보안 이벤트를 놓칠 수 있다. 이를 alert fatigue라고 한다. 보안 모니터링에서는 다음과 같은 기준을 잘 설계해야 한다.

- 실패한 로그인 시도 급증
- 특정 IP의 비정상 요청 증가
- 401/403 응답 급증
- 관리자 API 접근 증가
- 비정상적인 트래픽 패턴
- 로그 수집 중단
- 특정 서비스의 에러율 급증

알림은 심각도별로 분류하고, 실제 대응 가능한 수준으로 조정해야 한다.

## 면접 질문

**Q1. Prometheus와 ELK의 차이는 무엇인가요?**  
> 핵심 답변: Prometheus는 주로 시계열 메트릭 수집과 알림에 사용되고, ELK는 로그 수집·검색·분석에 사용된다. Prometheus는 “현재 시스템 상태와 추세” 파악에 강하고, ELK는 “특정 이벤트와 원인 분석”에 강하다. 둘은 대체 관계라기보다 상호 보완 관계다.

**Q2. Prometheus가 Pull 방식을 사용하는 이유와 장단점은 무엇인가요?**  
> 핵심 답변: Prometheus는 모니터링 대상의 `/metrics` 엔드포인트를 주기적으로 scrape한다. Pull 방식은 대상 상태 확인이 쉽고, 중앙에서 수집 주기를 제어하기 좋다. 반면 방화벽, NAT, 짧게 실행되는 batch job 환경에서는 수집이 어려울 수 있어 Pushgateway 같은 보조 구성이 사용될 수 있다.

**Q3. Grafana는 Prometheus와 어떤 관계인가요?**  
> 핵심 답변: Prometheus는 메트릭을 수집·저장·질의하는 시스템이고, Grafana는 Prometheus 같은 데이터 소스를 시각화하는 대시보드 도구다. Grafana 자체가 Prometheus 메트릭을 수집하는 것은 아니며, PromQL 질의를 실행해 그래프나 테이블로 보여준다.

**Q4. ELK 스택에서 Logstash의 역할은 무엇인가요?**  
> 핵심 답변: Logstash는 로그 파이프라인 도구로 input, filter, output 단계로 동작한다. 다양한 소스에서 로그를 받아 grok, mutate, date 같은 필터로 파싱·변환한 뒤 Elasticsearch, Kafka, 파일 등으로 출력한다. 로그 형식을 구조화하고 검색 가능한 필드로 만드는 데 중요하다.

**Q5. 운영 환경에서 로그와 메트릭을 설계할 때 주의할 점은 무엇인가요?**  
> 핵심 답변: 메트릭은 cardinality가 과도하게 증가하지 않도록 label 설계를 주의해야 하고, 로그는 민감정보를 남기지 않도록 해야 한다. 또한 수집 비용, 저장 기간, 검색 성능, 접근 권한, 알림 기준, 장애 시나리오를 함께 고려해야 한다. 메트릭은 장애 탐지, 로그는 원인 분석에 초점을 맞추는 것이 좋다.

## 관련 개념

- [[시계열 데이터베이스]] - Prometheus는 메트릭을 시간 순서의 시계열 데이터로 저장한다.
- [[PromQL]] - Prometheus에서 메트릭을 조회하고 계산하기 위한 질의 언어다.
- [[Exporter]] - Linux, DB, Nginx 등 외부 시스템의 상태를 Prometheus 메트릭으로 변환해 노출한다.
- [[Alertmanager]] - Prometheus 알림을 그룹화, 라우팅, 억제하여 운영자에게 전달한다.
- [[구조화 로그]] - JSON 같은 형식으로 로그를 남겨 Elasticsearch에서 필드 기반 검색을 쉽게 만든다.
- [[역색인]] - Elasticsearch가 빠른 검색을 위해 사용하는 핵심 자료구조다.
- [[Kubernetes Service Discovery]] - Prometheus가 Kubernetes 리소스를 자동으로 발견해 scrape 대상으로 등록하는 데 사용된다.
- [[Observability]] - 메트릭, 로그, 트레이스를 통해 시스템 내부 상태를 추론하는 개념이다.
- [[분산 추적]] - trace_id를 기반으로 마이크로서비스 간 요청 흐름을 추적한다.
- [[SRE]] - 서비스 신뢰성을 유지하기 위해 모니터링, 알림, SLO 등을 체계적으로 관리하는 운영 방법론이다.
