# 인증 및 인가 - 세션/쿠키, JWT(Access/Refresh Token), OAuth 2.0, SSO

## 핵심 개념

인증(Authentication)과 인가(Authorization)는 백엔드 아키텍처에서 사용자와 시스템 리소스를 안전하게 연결하기 위한 핵심 보안 개념이다. **인증**은 “사용자가 누구인지 확인하는 과정”이며, 예를 들어 아이디/비밀번호 로그인, 소셜 로그인, MFA 등이 여기에 해당한다. 반면 **인가**는 “인증된 사용자가 특정 리소스나 기능에 접근할 권한이 있는지 판단하는 과정”이다. 예를 들어 로그인한 사용자가 관리자 페이지에 접근할 수 있는지, 특정 API를 호출할 수 있는지 판단하는 것이 인가다.

웹 백엔드에서는 인증 상태를 유지하기 위해 주로 **세션/쿠키**, **JWT 기반 Access Token/Refresh Token**, **OAuth 2.0**, **SSO** 같은 방식을 사용한다. HTTP는 기본적으로 상태를 저장하지 않는 Stateless 프로토콜이므로, 서버는 매 요청마다 사용자를 식별할 방법이 필요하다. 세션 기반 인증은 서버에 로그인 상태를 저장하고 클라이언트는 세션 ID를 쿠키로 전달한다. JWT 기반 인증은 서버가 서명된 토큰을 발급하고 클라이언트가 이를 요청마다 전달한다. OAuth 2.0은 사용자가 비밀번호를 직접 공유하지 않고도 제3자 애플리케이션에 제한된 권한을 위임할 수 있게 하는 표준 프레임워크다. SSO는 한 번의 로그인으로 여러 서비스에 접근할 수 있도록 하는 인증 통합 방식이다.

이 주제가 중요한 이유는 인증/인가 설계가 서비스의 보안성, 확장성, 사용자 경험, 운영 복잡도에 직접적인 영향을 주기 때문이다. 잘못 설계된 인증 시스템은 계정 탈취, 권한 상승, 세션 하이재킹, 토큰 탈취, CSRF, XSS 같은 심각한 보안 사고로 이어질 수 있다. 반대로 적절한 인증/인가 구조를 설계하면 마이크로서비스, 모바일 앱, 웹 프론트엔드, API Gateway, 클라우드 환경에서도 일관된 접근 제어를 구현할 수 있다.

## 내부 동작 원리

## 1. 세션/쿠키 기반 인증

세션 기반 인증은 서버가 사용자의 로그인 상태를 저장하고, 클라이언트는 서버가 발급한 세션 ID를 쿠키에 담아 매 요청마다 전달하는 방식이다.

### 동작 과정

```text
[1] 사용자 로그인 요청
Browser -> Server: ID/PW 전송

[2] 서버 인증 성공
Server:
  - 사용자 정보 검증
  - 세션 저장소에 session_id 생성 및 저장
  - Set-Cookie 헤더로 session_id 전달

[3] 브라우저 쿠키 저장
Browser:
  - session_id 쿠키 저장

[4] 이후 요청
Browser -> Server:
  Cookie: session_id=abc123

[5] 서버 세션 조회
Server:
  - session_id로 세션 저장소 조회
  - 사용자 식별
  - 권한 확인 후 응답
```

### 구조 다이어그램

```text
+----------+       Cookie: session_id       +-------------+
| Browser  | ----------------------------> | Web Server  |
+----------+                               +-------------+
                                                |
                                                | session_id 조회
                                                v
                                         +--------------+
                                         | Session Store |
                                         | Redis / DB    |
                                         +--------------+
```

세션 저장소는 서버 메모리, Redis, Memcached, RDBMS 등을 사용할 수 있다. 단일 서버에서는 메모리 세션도 가능하지만, 여러 서버로 확장하면 모든 서버가 동일한 세션 상태를 공유해야 하므로 Redis 같은 외부 세션 저장소를 사용하는 경우가 많다.

쿠키는 브라우저가 자동으로 요청에 포함시키는 저장 매체다. 인증 쿠키에는 보통 `HttpOnly`, `Secure`, `SameSite` 속성을 설정한다.

```http
Set-Cookie: SESSIONID=abc123; HttpOnly; Secure; SameSite=Lax
```

- `HttpOnly`: JavaScript에서 쿠키 접근 방지
- `Secure`: HTTPS 연결에서만 쿠키 전송
- `SameSite`: 크로스 사이트 요청 시 쿠키 전송 범위 제한

## 2. JWT 기반 Access Token / Refresh Token

JWT, 즉 JSON Web Token은 JSON 형태의 클레임을 담고, 서명을 통해 위변조 여부를 검증할 수 있는 토큰 형식이다. 일반적으로 다음 세 부분으로 구성된다.

```text
header.payload.signature
```

### JWT 구성

```text
Header:
  - alg: 서명 알고리즘
  - typ: JWT

Payload:
  - sub: 사용자 식별자
  - exp: 만료 시간
  - iat: 발급 시간
  - roles: 권한 정보 등

Signature:
  - Header와 Payload를 비밀키 또는 개인키로 서명한 값
```

JWT는 기본적으로 **인코딩된 토큰**이지 암호화된 토큰이 아니다. 따라서 Payload는 Base64URL로 디코딩할 수 있으므로 비밀번호, 주민등록번호, 카드번호 같은 민감 정보를 넣으면 안 된다.

### Access Token / Refresh Token 흐름

```text
[1] 로그인
Client -> Auth Server: ID/PW

[2] 인증 성공
Auth Server -> Client:
  Access Token 발급
  Refresh Token 발급

[3] API 요청
Client -> Resource Server:
  Authorization: Bearer AccessToken

[4] 서버 검증
Resource Server:
  - 서명 검증
  - exp 만료 확인
  - 권한 claim 확인

[5] Access Token 만료
Client -> Auth Server:
  Refresh Token으로 재발급 요청

[6] 재발급
Auth Server:
  - Refresh Token 유효성 확인
  - 새 Access Token 발급
```

### 구조 다이어그램

```text
+--------+       login        +-------------+
| Client | ----------------> | Auth Server |
+--------+                   +-------------+
    |                               |
    | Access Token / Refresh Token  |
    v                               |
+--------+    Bearer Token     +-----------------+
| Client | ------------------> | Resource Server |
+--------+                     +-----------------+
                                     |
                                     | JWT signature 검증
                                     v
                              +--------------+
                              | Public Key / |
                              | Secret Key   |
                              +--------------+
```

Access Token은 일반적으로 짧은 만료 시간을 갖고 API 접근에 사용된다. Refresh Token은 Access Token을 재발급받기 위한 용도로 사용되며, 상대적으로 더 민감하게 보호해야 한다. Refresh Token은 서버 저장소에 저장하거나, 회전 전략을 적용하여 재사용을 탐지하는 방식이 자주 사용된다.

## 3. OAuth 2.0

OAuth 2.0은 인증 자체보다는 **인가 위임 Authorization Delegation**을 위한 표준 프레임워크다. 사용자가 자신의 비밀번호를 제3자 애플리케이션에 직접 제공하지 않고도, 특정 리소스에 제한된 접근 권한을 부여할 수 있다.

OAuth 2.0의 주요 역할은 다음과 같다.

| 역할 | 설명 |
|---|---|
| Resource Owner | 리소스 소유자, 보통 사용자 |
| Client | 리소스 접근을 요청하는 애플리케이션 |
| Authorization Server | 사용자 인증 및 권한 부여, 토큰 발급 |
| Resource Server | 보호된 리소스를 제공하는 API 서버 |

### Authorization Code Grant + PKCE 흐름

현재 웹/모바일 환경에서 널리 권장되는 방식은 Authorization Code Grant이며, 공개 클라이언트에서는 PKCE를 함께 사용하는 것이 보안상 권장된다.

```text
[1] Client가 Authorization Server로 리다이렉트
Client -> Browser -> Authorization Server

[2] 사용자 로그인 및 동의
User:
  - 로그인
  - 권한 scope 승인

[3] Authorization Code 발급
Authorization Server -> Browser -> Client:
  code 전달

[4] Client가 code로 token 요청
Client -> Authorization Server:
  code, redirect_uri, code_verifier 등 전달

[5] Token 발급
Authorization Server -> Client:
  Access Token
  Refresh Token(optional)
  ID Token(OpenID Connect 사용 시)

[6] API 호출
Client -> Resource Server:
  Authorization: Bearer AccessToken
```

### 다이어그램

```text
+----------+        redirect         +----------------------+
| Browser  | ---------------------> | Authorization Server |
+----------+                         +----------------------+
     ^                                         |
     | authorization code                      |
     |                                         v
+----------+     token request        +----------------------+
| Client   | ----------------------> | Authorization Server |
+----------+                         +----------------------+
     |
     | Access Token
     v
+-----------------+
| Resource Server |
+-----------------+
```

OAuth 2.0은 “소셜 로그인”에서 자주 사용되지만, 순수 OAuth 2.0은 인증 프로토콜이 아니라 인가 프레임워크다. 로그인 사용자 정보를 표준화된 방식으로 얻고 싶다면 OAuth 2.0 위에 만들어진 **OpenID Connect, OIDC**를 사용한다.

## 4. SSO

SSO, Single Sign-On은 사용자가 한 번 로그인하면 여러 애플리케이션이나 서비스에 추가 로그인 없이 접근할 수 있게 하는 인증 통합 방식이다. 기업 내부 시스템, SaaS, 마이크로서비스, 멀티 도메인 서비스에서 자주 사용된다.

SSO는 일반적으로 중앙 인증 서버 또는 Identity Provider, IdP를 중심으로 동작한다.

```text
[1] 사용자가 Service A 접근
Browser -> Service A

[2] 로그인 상태 없음
Service A -> Browser:
  IdP로 리다이렉트

[3] IdP에서 로그인
Browser -> IdP:
  ID/PW, MFA 등

[4] 인증 성공
IdP:
  인증 세션 생성
  토큰 또는 assertion 발급

[5] Service A 접근 허용

[6] 사용자가 Service B 접근
Service B:
  IdP 로그인 세션 확인
  추가 로그인 없이 접근 허용
```

### SSO 다이어그램

```text
                  +----------------+
                  | Identity       |
                  | Provider, IdP  |
                  +----------------+
                    ^            ^
                    |            |
          redirect  |            | redirect
                    |            |
+-------------+     |            |     +-------------+
| Service A   | ----+            +---- | Service B   |
+-------------+                        +-------------+
       ^                                      ^
       |                                      |
       +-------------- Browser --------------+
```

SSO 구현에는 SAML 2.0, OpenID Connect, Kerberos 등 다양한 프로토콜이 사용된다. 웹과 모바일 기반의 현대 애플리케이션에서는 OIDC가 많이 사용되고, 기업용 SaaS 연동에서는 SAML 2.0도 널리 사용된다.

## 실제 시스템 연결

## 1. Linux와 인증/인가

Linux 시스템 자체도 인증과 인가 구조를 갖는다. 로그인 인증은 `/etc/passwd`, `/etc/shadow`, PAM, LDAP, Kerberos 등과 연결될 수 있다. 인가는 UID, GID, 파일 권한, sudo 정책 등을 통해 제어된다.

```bash
ls -l app.log
-rw-r----- 1 appuser appgroup 1024 Jan 1 10:00 app.log
```

위 예시에서 파일 소유자, 그룹, 읽기/쓰기 권한이 인가의 기준이 된다. 백엔드 애플리케이션도 운영체제 권한 모델 위에서 실행되므로, 애플리케이션 프로세스가 어떤 사용자 권한으로 실행되는지 중요하다.

---

## 2. Nginx와 인증 처리

Nginx는 리버스 프록시로서 인증/인가 흐름에 자주 참여한다. 예를 들어 다음과 같은 역할을 할 수 있다.

- HTTPS 종료
- 인증 서버로 요청 프록시
- 특정 경로에 Basic Auth 적용
- JWT 검증 모듈 또는 외부 인증 서버 연동
- `auth_request`를 통한 인증 위임

예시 구조:

```text
Client -> Nginx -> Auth Service
              |
              +-> Backend API
```

Nginx의 `auth_request` 패턴은 요청을 백엔드로 전달하기 전에 별도의 인증 서비스에 먼저 검증 요청을 보내는 방식이다.

```text
[1] Client -> Nginx: /api/orders
[2] Nginx -> Auth Service: 인증 확인
[3] Auth Service -> Nginx: 200 OK 또는 401 Unauthorized
[4] Nginx -> Backend API: 인증 성공 시 전달
```

## 3. Redis 세션 저장소

세션 기반 인증을 여러 서버에서 운영할 때 Redis를 세션 저장소로 사용하는 경우가 많다.

```text
+----------+       +---------------+
| Server A | ----> |               |
+----------+       |               |
                   | Redis Session |
+----------+       | Store         |
| Server B | ----> |               |
+----------+       +---------------+
```

이 구조에서는 로드밸런서가 어떤 서버로 요청을 보내더라도 동일한 세션 ID를 Redis에서 조회할 수 있다. 또한 TTL을 설정하여 세션 만료를 관리할 수 있다.

## 4. AWS에서의 인증/인가

AWS 환경에서는 여러 인증/인가 서비스가 존재한다.

- **AWS IAM**: AWS 리소스에 대한 인증 및 인가 제어
- **Amazon Cognito**: 사용자 풀, 소셜 로그인, OIDC/OAuth 2.0 기반 사용자 인증
- **Application Load Balancer Authentication**: ALB에서 OIDC 또는 Cognito 기반 인증 연동 가능
- **API Gateway Authorizer**: Lambda Authorizer 또는 JWT Authorizer로 API 접근 제어 가능

예시:

```text
Client -> API Gateway -> Lambda Authorizer -> Backend Lambda
```

Lambda Authorizer는 요청의 토큰을 검증하고, 허용/거부 정책을 반환하여 API 접근을 제어할 수 있다.

---

## 5. GCP에서의 인증/인가

GCP에서는 다음과 같은 인증/인가 구성을 사용할 수 있다.

- **Google Cloud IAM**: GCP 리소스 권한 제어
- **Identity-Aware Proxy, IAP**: 애플리케이션 앞단에서 사용자 인증 및 접근 제어
- **Firebase Authentication**: 웹/모바일 앱 사용자 인증
- **Google OAuth 2.0 / OpenID Connect**: Google 계정 기반 로그인 및 API 접근 위임

IAP는 애플리케이션 코드를 크게 수정하지 않고도 HTTP 애플리케이션 앞에서 접근 제어를 수행할 수 있다.

## 클라우드 연결

## 1. Docker와 인증 정보 관리

Docker 컨테이너 환경에서는 인증 관련 비밀값을 이미지에 포함하지 않는 것이 중요하다. JWT 서명 키, OAuth Client Secret, 세션 암호화 키 등을 Dockerfile이나 Git 저장소에 하드코딩하면 안 된다.

나쁜 예:

```dockerfile
ENV JWT_SECRET=my-secret-key
```

더 나은 방식:

- Docker Secret 사용
- 환경 변수 주입
- 클라우드 Secret Manager 사용
- Kubernetes Secret 사용
- HashiCorp Vault 같은 외부 비밀 관리 도구 사용

컨테이너는 쉽게 재배포되고 복제되므로 인증 키 관리와 회전 전략이 필수다.

---

## 2. Kubernetes와 인증/인가

Kubernetes 자체도 강력한 인증/인가 모델을 가진다.

- 인증: 클라이언트 인증서, Bearer Token, OIDC 등
- 인가: RBAC, ABAC, Node Authorization, Webhook 등
- 서비스 계정: Pod가 Kubernetes API에 접근할 때 사용

애플리케이션 인증 관점에서는 다음 구성이 자주 사용된다.

```text
Client -> Ingress Controller -> Auth Proxy -> Service
```

예를 들어 Ingress 앞단에서 OAuth2 Proxy를 사용하면, 백엔드 애플리케이션이 직접 로그인 로직을 구현하지 않아도 OIDC 기반 인증을 적용할 수 있다.

```text
+--------+      +----------+      +-------------+      +---------+
| Client | ---> | Ingress  | ---> | OAuth2 Proxy| ---> | Service |
+--------+      +----------+      +-------------+      +---------+
```

## 3. Kubernetes Secret과 JWT 키

JWT를 RS256 같은 비대칭 키 방식으로 서명하는 경우 개인키와 공개키를 관리해야 한다. 개인키는 안전하게 보관되어야 하며, Resource Server는 공개키 또는 JWKS 엔드포인트를 통해 서명을 검증할 수 있다.

```text
Auth Server:
  - Private Key로 JWT 서명

Resource Server:
  - Public Key 또는 JWKS로 JWT 검증
```

Kubernetes에서는 개인키를 Secret으로 저장할 수 있지만, Secret은 기본적으로 Base64 인코딩된 데이터 형태이므로 암호화 저장 여부와 접근 권한을 별도로 고려해야 한다. 운영 환경에서는 etcd 암호화, RBAC 제한, 외부 Secret Manager 연동을 함께 고려하는 것이 좋다.

## 4. AWS Cognito 기반 OAuth/OIDC

AWS Cognito User Pool은 사용자 가입, 로그인, MFA, 소셜 로그인, OAuth 2.0, OIDC 기반 토큰 발급을 지원한다. 일반적인 구조는 다음과 같다.

```text
User -> Cognito Hosted UI -> Cognito User Pool
                         -> Access Token / ID Token / Refresh Token
Client -> API Gateway -> JWT Authorizer -> Backend
```

API Gateway의 JWT Authorizer는 Cognito가 발급한 JWT의 issuer, audience, signature, expiration 등을 검증하여 API 접근을 제어할 수 있다.

## 5. 마이크로서비스와 중앙 인증

마이크로서비스 환경에서는 각 서비스가 독립적으로 인증 로직을 구현하면 중복과 보안 불일치가 발생하기 쉽다. 따라서 보통 다음 중 하나를 사용한다.

1. API Gateway에서 인증 처리
2. Service Mesh에서 mTLS 및 인증/인가 정책 적용
3. 중앙 Auth Server에서 토큰 발급
4. 각 서비스는 JWT 검증 및 세부 인가 수행

```text
Client -> API Gateway -> Service A
                    -> Service B
                    -> Service C
```

일반적으로 Gateway는 “토큰이 유효한가?”를 검증하고, 각 서비스는 “이 사용자가 이 도메인 리소스에 접근할 권한이 있는가?”를 판단하는 식으로 책임을 나눈다.

## 보안 연결

## 1. 세션/쿠키 보안 이슈

### 세션 하이재킹

공격자가 세션 ID를 탈취하면 사용자인 척 요청할 수 있다. 이를 방지하려면 다음이 필요하다.

- HTTPS 사용
- `Secure` 쿠키 설정
- `HttpOnly` 설정
- 로그인 후 세션 ID 재발급
- 세션 만료 시간 설정
- 비정상 위치/기기 탐지

### 세션 고정 공격

공격자가 미리 알고 있는 세션 ID로 사용자가 로그인하게 만든 뒤 해당 세션을 탈취하는 공격이다. 로그인 성공 후 반드시 새로운 세션 ID를 발급해야 한다.

### CSRF

쿠키는 브라우저가 자동으로 요청에 포함하기 때문에 CSRF에 취약할 수 있다. 방어 방법은 다음과 같다.

- `SameSite=Lax` 또는 `SameSite=Strict`
- CSRF Token 사용
- 중요 요청에 재인증 요구
- Origin/Referer 검증

---

## 2. JWT 보안 이슈

### Payload 민감 정보 노출

JWT Payload는 쉽게 디코딩할 수 있으므로 민감 정보를 넣으면 안 된다.

```json
{
  "sub": "123",
  "role": "USER"
}
```

위와 같은 최소 정보만 포함하는 것이 바람직하다.

### 토큰 탈취

Access Token이 탈취되면 만료 전까지 악용될 수 있다. 따라서 다음 전략이 필요하다.

- Access Token 짧은 만료 시간
- Refresh Token 안전 저장
- Refresh Token Rotation
- 재사용 탐지
- 로그아웃 시 Refresh Token 폐기
- HTTPS 필수

### 알고리즘 혼동 공격

JWT 검증 시 허용 알고리즘을 명시적으로 제한해야 한다. 과거에는 `alg=none` 또는 알고리즘 혼동과 관련된 취약한 구현이 문제가 된 사례가 있었다. 검증 라이브러리를 사용할 때는 신뢰할 수 있는 알고리즘만 허용해야 한다.

### 토큰 폐기 문제

JWT는 서버가 상태를 저장하지 않는 방식으로 사용할 수 있지만, 그만큼 발급된 토큰을 즉시 무효화하기 어렵다. 로그아웃, 계정 정지, 권한 변경을 즉시 반영해야 한다면 다음 방법을 고려한다.

- 짧은 Access Token 만료 시간
- Refresh Token 서버 저장 및 폐기
- Token Blocklist 사용
- 토큰 버전 claim 사용
- 중앙 introspection 엔드포인트 사용

---

## 3. OAuth 2.0 보안 이슈

### Redirect URI 검증

Authorization Code를 공격자 도메인으로 보내지 않도록 Authorization Server는 사전에 등록된 Redirect URI와 요청 URI를 엄격히 비교해야 한다.

### PKCE 사용

Public Client, 예를 들어 SPA나 모바일 앱은 Client Secret을 안전하게 보관하기 어렵다. 이 경우 Authorization Code 탈취를 완화하기 위해 PKCE를 사용하는 것이 권장된다.

### Scope 최소화

OAuth 토큰에는 필요한 최소 권한만 부여해야 한다.

```text
좋지 않은 예:
scope=read write admin

더 나은 예:
scope=orders:read
```

### State 파라미터

OAuth 흐름에서 `state` 파라미터는 CSRF 방어와 요청-응답 매칭에 사용된다. 클라이언트는 요청 시 생성한 `state`와 콜백에서 받은 `state`가 일치하는지 검증해야 한다.

## 4. SSO 보안 이슈

SSO는 사용자 경험과 운영 효율을 높이지만, 중앙 인증 계정이 탈취되면 여러 서비스가 동시에 위험해질 수 있다.

보안 모범 사례:

- MFA 적용
- 조건부 접근 정책
- 기기 신뢰도 평가
- 짧은 세션 만료
- 중앙 로그아웃 처리
- 감사 로그 수집
- 관리자 계정 별도 보호
- IdP 장애 대비 전략

SSO 환경에서는 IdP가 단일 장애 지점이 될 수 있으므로, 고가용성 구성과 장애 대응 절차도 중요하다.

---

## 5. 인증과 인가의 책임 분리

인증만으로는 보안이 충분하지 않다. “로그인한 사용자”와 “이 리소스에 접근 가능한 사용자”는 다르다.

예를 들어 `/users/100/orders` API에서 사용자가 로그인했더라도, 해당 사용자가 `userId=100`의 주문을 볼 권한이 있는지 반드시 서버에서 확인해야 한다.

```text
나쁜 예:
GET /users/100/orders
Authorization: Bearer valid-token
=> 토큰만 유효하면 허용

좋은 예:
1. 토큰 검증
2. 요청 사용자 ID 확인
3. userId=100 리소스 소유자 여부 확인
4. 관리자 권한 여부 확인
5. 허용 또는 거부
```

이를 흔히 Broken Access Control 문제라고 하며, 웹 애플리케이션에서 매우 중요한 보안 리스크다.

## 면접 질문

**Q1. 인증과 인가의 차이는 무엇인가요?**  
> 핵심 답변: 인증은 사용자가 누구인지 확인하는 과정이고, 인가는 인증된 사용자가 특정 리소스나 기능에 접근할 권한이 있는지 판단하는 과정이다. 로그인은 인증이고, 관리자 페이지 접근 가능 여부 판단은 인가다. 두 개념은 반드시 분리해서 설계해야 한다.

**Q2. 세션 기반 인증과 JWT 기반 인증의 차이는 무엇인가요?**  
> 핵심 답변: 세션 기반 인증은 서버가 로그인 상태를 세션 저장소에 저장하고 클라이언트는 세션 ID를 쿠키로 전달한다. JWT 기반 인증은 서버가 서명된 토큰을 발급하고 클라이언트가 토큰을 요청마다 전달한다. 세션은 서버 상태 관리가 필요하지만 즉시 폐기가 쉽고, JWT는 분산 환경에서 검증이 쉽지만 토큰 폐기와 탈취 대응이 더 까다롭다.

**Q3. Access Token과 Refresh Token을 분리하는 이유는 무엇인가요?**  
> 핵심 답변: Access Token은 API 접근에 사용되며 짧은 만료 시간을 갖게 하여 탈취 피해를 줄인다. Refresh Token은 Access Token 재발급에 사용되며 더 민감하게 보호한다. 이를 통해 사용자 경험을 유지하면서도 Access Token 노출 위험을 줄일 수 있다. Refresh Token은 서버 저장, 회전, 재사용 탐지 전략과 함께 사용하는 것이 좋다.

**Q4. OAuth 2.0과 OpenID Connect의 차이는 무엇인가요?**  
> 핵심 답변: OAuth 2.0은 인가 위임 프레임워크로, 제3자 애플리케이션이 사용자의 리소스에 제한된 접근 권한을 얻도록 한다. OpenID Connect는 OAuth 2.0 위에 만들어진 인증 계층으로, ID Token을 통해 사용자의 신원을 표준화된 방식으로 전달한다. “소셜 로그인”에는 보통 OIDC가 함께 사용된다.

**Q5. SSO를 도입할 때 고려해야 할 장단점은 무엇인가요?**  
> 핵심 답변: 장점은 한 번의 로그인으로 여러 서비스에 접근할 수 있어 사용자 경험이 좋아지고, 중앙에서 인증 정책과 MFA를 관리할 수 있다는 점이다. 단점은 IdP가 단일 장애 지점이 될 수 있고, 중앙 계정 탈취 시 여러 서비스가 동시에 위험해질 수 있다는 점이다. 따라서 MFA, 감사 로그, 조건부 접근, 고가용성 구성이 중요하다.

## 관련 개념

- [[Authentication]] - 사용자의 신원을 확인하는 인증 개념의 기본 토대
- [[Authorization]] - 인증된 사용자의 리소스 접근 권한을 판단하는 핵심 개념
- [[Session]] - 서버가 사용자 로그인 상태를 유지하는 대표적인 방식
- [[Cookie]] - 브라우저가 인증 식별자나 상태 정보를 저장하고 전송하는 메커니즘
- [[JWT]] - 서명된 토큰 기반 인증/인가에 사용되는 표준 토큰 형식
- [[Access Token]] - 보호된 API 리소스 접근에 사용되는 단기 토큰
- [[Refresh Token]] - Access Token을 재발급받기 위한 장기 토큰
- [[OAuth 2.0]] - 제3자 애플리케이션에 제한된 권한을 위임하는 인가 프레임워크
- [[OpenID Connect]] - OAuth 2.0 위에서 사용자 인증 정보를 제공하는 인증 계층
- [[SSO]] - 한 번의 로그인으로 여러 서비스에 접근하는 통합 인증 방식
- [[SAML]] - 기업 SSO에서 널리 사용되는 XML 기반 인증/인가 프로토콜
- [[CSRF]] - 쿠키 기반 인증에서 특히 주의해야 하는 요청 위조 공격
- [[XSS]] - 토큰이나 세션 정보를 탈취하는 데 악용될 수 있는 클라이언트 측 공격
- [[RBAC]] - 역할 기반 접근 제어 모델로 인가 설계에 자주 사용됨
- [[ABAC]] - 속성 기반 접근 제어 모델로 세밀한 인가 정책 구현에 사용됨
