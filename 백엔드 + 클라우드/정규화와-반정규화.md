# 정규화와 반정규화 - 제1정규형 ~ BCNF, 성능을 위한 반정규화 트레이드오프

## 핵심 개념

정규화(Normalization)는 관계형 데이터베이스에서 데이터 중복을 줄이고 삽입·수정·삭제 이상 현상을 방지하기 위해 테이블을 구조적으로 분해하는 설계 기법이다. 핵심 기준은 함수 종속성(Functional Dependency)이며, 어떤 속성 값이 다른 속성 값을 결정하는 관계를 분석해 테이블을 더 안정적인 형태로 만든다. 제1정규형(1NF)은 컬럼 값이 원자값이어야 함을 요구하고, 제2정규형(2NF)은 부분 함수 종속 제거, 제3정규형(3NF)은 이행 함수 종속 제거, BCNF는 모든 결정자가 후보키가 되도록 더 엄격하게 제약한다.

정규화의 목적은 데이터 무결성 유지, 중복 최소화, 이상 현상 방지, 명확한 데이터 모델링이다. 예를 들어 주문 테이블에 고객명, 고객주소를 반복 저장하면 고객 주소 변경 시 여러 행을 모두 수정해야 하며 일부만 수정되면 데이터 불일치가 발생한다. 정규화를 적용하면 고객 정보와 주문 정보를 분리하여 이런 문제를 줄일 수 있다.

반정규화(Denormalization)는 정규화된 구조를 일부러 합치거나 중복 데이터를 저장하여 조회 성능을 높이는 설계 전략이다. 조인이 많아지는 OLTP 시스템, 읽기 비중이 높은 서비스, 리포팅·분석용 테이블에서 자주 사용된다. 하지만 반정규화는 중복 데이터 증가, 갱신 비용 증가, 데이터 불일치 가능성이라는 트레이드오프를 동반한다. 따라서 정규화는 기본 설계 원칙으로 삼고, 반정규화는 실제 쿼리 패턴과 성능 병목을 확인한 뒤 제한적으로 적용하는 것이 바람직하다.

## 내부 동작 원리

정규화는 테이블의 속성 간 관계를 함수 종속성으로 분석한 뒤, 이상 현상이 발생하지 않도록 테이블을 분해하는 과정이다.

예를 들어 다음과 같은 테이블이 있다고 하자.

```text
주문_원본
------------------------------------------------
주문ID | 고객ID | 고객명 | 고객주소 | 상품ID | 상품명 | 수량
------------------------------------------------
1     | C01   | Kim   | Seoul   | P01   | Keyboard | 2
2     | C01   | Kim   | Seoul   | P02   | Mouse    | 1
3     | C02   | Lee   | Busan   | P01   | Keyboard | 1
```

이 테이블에는 다음과 같은 함수 종속성이 존재할 수 있다.

```text
고객ID -> 고객명, 고객주소
상품ID -> 상품명
주문ID -> 고객ID
주문ID, 상품ID -> 수량
```

이 상태에서 고객주소를 수정하려면 같은 고객ID를 가진 모든 행을 수정해야 한다. 상품명이 바뀌어도 여러 행을 수정해야 한다. 이러한 문제가 수정 이상(Update Anomaly)이다. 또한 주문이 아직 없는 고객을 저장하기 어렵다면 삽입 이상(Insert Anomaly), 특정 주문을 삭제했더니 상품 정보까지 사라진다면 삭제 이상(Delete Anomaly)이 발생한다.

정규화 과정은 보통 다음과 같이 진행된다.

```text
[비정규 테이블]
      |
      v
[1NF: 반복 그룹 제거, 원자값 보장]
      |
      v
[2NF: 부분 함수 종속 제거]
      |
      v
[3NF: 이행 함수 종속 제거]
      |
      v
[BCNF: 모든 결정자가 후보키인지 확인]
```

### 제1정규형, 1NF

1NF는 각 컬럼이 원자값을 가져야 한다는 조건이다. 하나의 컬럼에 여러 값을 리스트처럼 저장하면 관계형 연산이 어려워지고 검색, 인덱싱, 제약조건 적용이 복잡해진다.

나쁜 예:

```text
고객ID | 고객명 | 전화번호
--------------------------
C01   | Kim   | 010-1111, 010-2222
```

1NF 적용 후:

```text
고객전화
--------------------
고객ID | 전화번호
--------------------
C01   | 010-1111
C01   | 010-2222
```

### 제2정규형, 2NF

2NF는 1NF를 만족하면서, 기본키의 일부에만 종속되는 속성을 제거해야 한다. 주로 복합키를 사용하는 테이블에서 중요하다.

예를 들어 주문상세 테이블의 기본키가 `(주문ID, 상품ID)`라고 하자.

```text
주문ID, 상품ID -> 수량
상품ID -> 상품명
```

여기서 `상품명`은 전체 키 `(주문ID, 상품ID)`가 아니라 `상품ID`에만 종속된다. 이는 부분 함수 종속이다.

분해 후:

```text
주문상세
-------------------------
주문ID | 상품ID | 수량

상품
-------------------------
상품ID | 상품명
```

### 제3정규형, 3NF

3NF는 2NF를 만족하면서, 키가 아닌 속성이 다른 키가 아닌 속성을 결정하는 이행 함수 종속을 제거한다.

예:

```text
고객ID -> 우편번호
우편번호 -> 지역명
```

이 경우 `고객ID -> 우편번호 -> 지역명` 구조가 된다. `지역명`은 고객ID에 직접 종속되는 것이 아니라 우편번호를 통해 이행적으로 종속된다.

분해 후:

```text
고객
--------------------
고객ID | 우편번호

우편번호지역
--------------------
우편번호 | 지역명
```

### BCNF

BCNF, Boyce-Codd Normal Form은 3NF보다 더 엄격한 정규형이다. 모든 함수 종속 `X -> Y`에 대해 `X`가 슈퍼키여야 한다. 즉, 어떤 속성이 다른 속성을 결정한다면 그 결정자는 반드시 테이블의 행을 유일하게 식별할 수 있어야 한다.

3NF에서는 일부 예외적으로 후보키의 일부인 속성, 즉 프라임 속성에 대한 종속을 허용할 수 있지만, BCNF는 결정자가 슈퍼키가 아니면 허용하지 않는다.

개념적 예:

```text
수강
-------------------------
학생ID | 강의ID | 교수ID
```

가정:

```text
학생ID, 강의ID -> 교수ID
교수ID -> 강의ID
```

교수 한 명이 하나의 강의만 담당한다고 하면 `교수ID -> 강의ID`가 성립한다. 하지만 `교수ID`만으로는 학생ID를 알 수 없으므로 전체 행을 유일하게 식별하지 못한다. 따라서 `교수ID`는 슈퍼키가 아니며 BCNF 위반이다.

분해 예:

```text
교수강의
--------------------
교수ID | 강의ID

수강교수
--------------------
학생ID | 교수ID
```

### 무손실 분해와 종속성 보존

정규화에서 중요한 조건은 무손실 분해(Lossless Decomposition)다. 테이블을 나눈 뒤 다시 조인했을 때 원래 정보를 잃거나 가짜 행이 생기면 안 된다.

```text
원본 R(A, B, C)
분해 R1(A, B), R2(A, C)

R1 ⋈ R2 결과가 원본 R과 동일해야 무손실 분해
```

또 다른 고려사항은 종속성 보존(Dependency Preservation)이다. 테이블을 분해한 뒤에도 기존 함수 종속성을 각 테이블의 제약조건만으로 검증할 수 있으면 좋다. BCNF 분해는 무손실 분해를 보장하도록 수행할 수 있지만, 항상 모든 종속성을 보존한다고 단정할 수는 없다. 따라서 실무에서는 3NF와 BCNF 사이에서 무결성, 제약조건 관리, 쿼리 복잡도를 함께 고려한다.

### 반정규화 내부 동작

반정규화는 정규화된 테이블 간 조인을 줄이기 위해 데이터를 중복 저장하거나 미리 계산된 값을 저장하는 방식으로 동작한다.

예를 들어 정규화된 구조는 다음과 같다.

```text
주문
--------------------
주문ID | 고객ID | 주문일

고객
--------------------
고객ID | 고객명 | 등급
```

주문 목록에서 항상 고객명을 함께 보여줘야 한다면 매번 조인이 발생한다.

```sql
SELECT o.주문ID, o.주문일, c.고객명
FROM 주문 o
JOIN 고객 c ON o.고객ID = c.고객ID;
```

반정규화 후:

```text
주문
-------------------------------
주문ID | 고객ID | 고객명 | 주문일
```

이 경우 조회는 빨라질 수 있지만 고객명이 변경되면 고객 테이블뿐 아니라 주문 테이블의 중복 고객명도 갱신해야 한다. 즉, 읽기 성능과 쓰기 일관성 사이의 트레이드오프가 발생한다.

반정규화의 대표 방식은 다음과 같다.

```text
1. 테이블 병합
2. 중복 컬럼 추가
3. 집계 컬럼 추가
4. 캐시 테이블 또는 요약 테이블 생성
5. Materialized View 사용
6. 읽기 전용 검색 인덱스에 데이터 복제
```

## 실제 시스템 연결

실제 백엔드 시스템에서는 정규화와 반정규화가 모두 사용된다. 일반적인 주문·결제·회원 시스템 같은 OLTP 데이터베이스에서는 정규화가 매우 중요하다. 회원, 주문, 주문상세, 상품, 결제, 배송 같은 엔티티를 분리하면 데이터 중복을 줄이고 무결성을 유지하기 쉽다.

예를 들어 전자상거래 시스템에서 다음과 같이 설계할 수 있다.

```text
회원
--------------------
회원ID | 이름 | 이메일

상품
--------------------
상품ID | 상품명 | 가격

주문
--------------------
주문ID | 회원ID | 주문일시

주문상세
--------------------
주문ID | 상품ID | 수량 | 주문당시가격
```

여기서 `주문당시가격`은 반정규화에 가까운 설계다. 상품 테이블에 현재 가격이 있더라도 주문 당시의 가격은 결제 기록과 회계상 중요한 정보이기 때문에 주문상세에 별도로 저장한다. 이는 단순 성능 목적뿐 아니라 이력 보존 목적의 중복 저장이다.

Linux 서버에서 MySQL, PostgreSQL 같은 RDBMS를 운영할 때 정규화는 테이블 구조와 제약조건 설계에 직접 반영된다. 기본키, 외래키, UNIQUE 제약조건, NOT NULL 제약조건을 통해 정규화된 모델의 무결성을 강제할 수 있다. 예를 들어 주문 테이블의 `회원ID`는 회원 테이블의 기본키를 참조하는 외래키가 될 수 있다.

```sql
CREATE TABLE member (
  member_id BIGINT PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  name VARCHAR(100) NOT NULL
);

CREATE TABLE orders (
  order_id BIGINT PRIMARY KEY,
  member_id BIGINT NOT NULL,
  ordered_at TIMESTAMP NOT NULL,
  FOREIGN KEY (member_id) REFERENCES member(member_id)
);
```

반면, 대규모 조회 트래픽을 처리하는 서비스에서는 반정규화가 자주 사용된다. 예를 들어 게시글 목록 화면에서 작성자 닉네임, 댓글 수, 좋아요 수를 매번 여러 테이블과 조인하거나 집계하면 부하가 커질 수 있다. 이때 게시글 테이블에 `작성자닉네임`, `댓글수`, `좋아요수` 같은 값을 중복 저장하거나 별도의 통계 테이블을 둘 수 있다.

```text
게시글
-------------------------------------
게시글ID | 작성자ID | 작성자닉네임 | 제목 | 댓글수 | 좋아요수
```

Nginx 같은 웹 서버나 리버스 프록시는 직접적으로 정규화를 수행하지는 않지만, 백엔드 API 서버와 데이터베이스 사이의 트래픽 패턴에 영향을 준다. 캐시 가능한 API 응답을 Nginx 또는 애플리케이션 계층에서 캐싱하면 데이터베이스 반정규화 필요성이 줄어들 수 있다. 즉, 성능 문제를 반드시 테이블 구조 변경으로만 해결하지 않고, 캐시, 인덱스, 쿼리 최적화, 읽기 복제본 등을 함께 검토해야 한다.

검색 시스템에서는 반정규화가 더 적극적으로 사용된다. Elasticsearch나 OpenSearch 같은 검색 엔진에 문서 단위로 데이터를 저장할 때는 관계형 모델처럼 조인을 중심으로 설계하기보다 검색 화면에 필요한 데이터를 한 문서에 포함시키는 경우가 많다. 예를 들어 상품 검색 문서에 상품명, 카테고리명, 브랜드명, 가격, 평점, 리뷰 수 등을 함께 저장한다. 이는 검색 성능과 응답 구조 단순화를 위한 반정규화의 전형적인 사례다.

## 클라우드 연결

클라우드 환경에서도 정규화와 반정규화는 데이터 모델링의 핵심이다. AWS RDS, Amazon Aurora, Google Cloud SQL, Azure Database for PostgreSQL 같은 관리형 관계형 데이터베이스를 사용할 때도 테이블 설계 원칙은 동일하다. 기본적으로 OLTP 워크로드에서는 정규화된 스키마를 통해 데이터 무결성을 확보하고, 필요한 경우 인덱스·읽기 복제본·캐시·반정규화를 조합해 성능을 개선한다.

AWS 환경의 예를 들면 다음과 같은 구조가 가능하다.

```text
[Client]
   |
[ALB]
   |
[ECS 또는 EKS의 Backend API]
   |
[RDS/Aurora - 정규화된 OLTP DB]
   |
[읽기 복제본 또는 ElastiCache 또는 OpenSearch]
```

이 구조에서 RDS나 Aurora에는 정규화된 원본 데이터를 저장하고, 조회 성능이 중요한 데이터는 ElastiCache Redis, OpenSearch, 별도 조회용 테이블에 반정규화하여 저장할 수 있다. 예를 들어 상품 상세 페이지에 필요한 상품 기본 정보, 브랜드명, 카테고리명, 리뷰 통계, 재고 상태를 매번 여러 테이블에서 조회하지 않고 Redis 캐시나 검색 인덱스에 미리 구성해 둘 수 있다.

Docker 환경에서는 데이터베이스 자체를 컨테이너로 실행할 수 있지만, 정규화와 반정규화는 컨테이너 기술과 독립적인 논리적 설계 개념이다. 다만 개발·테스트 환경에서 Docker Compose를 사용해 애플리케이션과 PostgreSQL, MySQL, Redis 등을 함께 띄우면 정규화된 원본 DB와 반정규화된 캐시 구조를 쉽게 실험할 수 있다.

```yaml
services:
  app:
    image: backend-app
  db:
    image: postgres
  redis:
    image: redis
```

Kubernetes 환경에서는 데이터베이스를 직접 StatefulSet으로 운영할 수도 있지만, 운영 복잡도를 줄이기 위해 관리형 데이터베이스를 사용하는 경우가 많다. 애플리케이션 Pod는 정규화된 원본 DB에 쓰기 작업을 수행하고, 읽기 최적화가 필요한 경우 캐시나 검색 서비스에 반정규화된 데이터를 조회한다.

```text
[Backend Pod]
   | 쓰기
   v
[Managed RDBMS]

[Backend Pod]
   | 읽기
   v
[Redis Cache / Search Index / Read Model]
```

이벤트 기반 아키텍처에서도 반정규화가 자주 등장한다. 예를 들어 주문이 생성되면 메시지 큐나 스트리밍 시스템을 통해 `OrderCreated` 이벤트를 발행하고, 별도의 컨슈머가 조회 전용 테이블이나 검색 인덱스를 갱신할 수 있다.

```text
[Order Service]
   |
   v
[Event Bus / Message Queue]
   |
   v
[Read Model Updater]
   |
   v
[Denormalized Read DB]
```

이 방식은 CQRS(Command Query Responsibility Segregation)와도 연결된다. 쓰기 모델은 정규화하여 무결성을 유지하고, 읽기 모델은 화면이나 API 응답에 맞게 반정규화하여 빠르게 조회하는 구조다. 다만 이벤트 전달 지연으로 인해 원본 DB와 조회 모델 사이에 일시적 불일치가 발생할 수 있으므로, 서비스 요구사항에 맞는 일관성 모델을 명확히 정해야 한다.

## 보안 연결

정규화와 반정규화는 보안과도 연결된다. 정규화된 설계는 민감 정보를 한곳에 모아 관리하기 쉽게 만든다. 예를 들어 사용자 개인정보를 여러 테이블에 중복 저장하면 접근 제어, 암호화, 마스킹, 삭제 요청 처리, 감사 로그 관리가 어려워진다. 반대로 회원 개인정보를 별도 테이블로 분리하고 필요한 서비스 테이블에는 식별자만 저장하면 보안 통제 범위를 줄일 수 있다.

예를 들어 다음과 같이 분리할 수 있다.

```text
회원
--------------------
회원ID | 상태 | 가입일

회원개인정보
--------------------
회원ID | 이름 | 전화번호 | 주소
```

이 구조에서는 개인정보 테이블에 더 강한 접근 권한, 암호화, 감사 로깅을 적용할 수 있다. 애플리케이션에서도 일반 조회 API는 회원 기본 정보만 접근하고, 개인정보가 필요한 제한된 기능만 개인정보 테이블에 접근하도록 설계할 수 있다.

반정규화는 보안 위험을 증가시킬 수 있다. 민감 정보가 여러 테이블, 캐시, 검색 인덱스, 로그성 테이블에 복제되면 유출 지점이 늘어난다. 예를 들어 사용자의 이메일이나 전화번호를 주문 테이블, 배송 테이블, 검색 인덱스, 분석 테이블에 중복 저장하면 어느 한 곳의 접근 제어가 약해져도 개인정보가 노출될 수 있다.

보안 관점의 주요 이슈는 다음과 같다.

```text
1. 민감 정보 중복 저장으로 인한 노출 범위 증가
2. 캐시나 검색 인덱스에 개인정보가 남는 문제
3. 삭제 요청 또는 보존 기간 만료 시 모든 복제본 삭제 누락
4. 권한이 낮은 서비스가 반정규화 테이블을 통해 민감 정보에 접근
5. 데이터 마스킹·암호화 정책의 일관성 부족
```

모범 사례는 다음과 같다.

- 민감 정보는 가능한 한 별도 테이블 또는 별도 저장소로 분리한다.
- 반정규화 테이블에는 필요한 최소 정보만 저장한다.
- 개인정보를 캐시하거나 검색 인덱스에 넣을 때는 보존 기간과 삭제 정책을 명확히 한다.
- 원본 DB, 캐시, 검색 인덱스, 데이터 웨어하우스에 동일한 접근 제어 원칙을 적용한다.
- 데이터베이스 계정은 최소 권한 원칙에 따라 분리한다.
- 반정규화된 데이터도 암호화, 마스킹, 감사 로그 대상에 포함한다.
- 애플리케이션 로그에 반정규화된 민감 데이터가 출력되지 않도록 주의한다.
- 데이터 삭제 또는 익명화 기능은 원본 테이블뿐 아니라 복제·반정규화 저장소까지 포함해야 한다.

정규화가 SQL Injection을 직접 방어하는 기술은 아니다. SQL Injection 방어에는 Prepared Statement, 파라미터 바인딩, ORM의 안전한 쿼리 생성, 입력 검증, 최소 권한 DB 계정 사용이 필요하다. 다만 잘 정규화된 스키마와 명확한 권한 분리는 공격자가 한 번의 취약점으로 과도한 데이터를 조회하는 위험을 줄이는 데 도움이 될 수 있다.

## 면접 질문

**Q1. 정규화의 목적은 무엇인가요?**  
> 핵심 답변: 데이터 중복을 줄이고 삽입·수정·삭제 이상 현상을 방지하여 데이터 무결성을 높이는 것이다. 함수 종속성을 분석해 테이블을 적절히 분해하며, 일반적으로 1NF, 2NF, 3NF, BCNF 순서로 더 엄격한 조건을 적용한다.

**Q2. 1NF, 2NF, 3NF의 차이를 설명해주세요.**  
> 핵심 답변: 1NF는 컬럼 값이 원자값이어야 한다. 2NF는 1NF를 만족하면서 복합키의 일부에만 종속되는 부분 함수 종속을 제거한다. 3NF는 2NF를 만족하면서 키가 아닌 속성이 다른 키가 아닌 속성을 결정하는 이행 함수 종속을 제거한다.

**Q3. BCNF는 3NF와 어떻게 다른가요?**  
> 핵심 답변: BCNF는 모든 함수 종속 `X -> Y`에서 결정자 `X`가 반드시 슈퍼키여야 한다. 3NF는 일부 경우 프라임 속성에 대한 종속을 허용할 수 있지만, BCNF는 결정자가 슈퍼키가 아니면 허용하지 않는 더 엄격한 정규형이다.

**Q4. 반정규화를 적용해야 하는 상황과 주의할 점은 무엇인가요?**  
> 핵심 답변: 조인이 과도하거나 집계 비용이 커서 읽기 성능 병목이 명확할 때 적용할 수 있다. 중복 컬럼, 요약 테이블, Materialized View, 캐시, 검색 인덱스 등이 방법이다. 단, 갱신 비용 증가, 데이터 불일치, 저장 공간 증가, 보안 위험 증가를 고려해야 한다.

**Q5. 정규화된 OLTP DB와 반정규화된 조회 모델을 함께 사용하는 이유는 무엇인가요?**  
> 핵심 답변: 쓰기 모델은 정규화하여 무결성과 일관성을 유지하고, 읽기 모델은 화면이나 API 응답에 맞게 반정규화하여 조회 성능을 높이기 위해서다. CQRS나 이벤트 기반 아키텍처에서 자주 사용되며, 원본과 조회 모델 사이의 일시적 불일치를 관리해야 한다.

## 관련 개념

- [[함수 종속성]] - 정규화 판단의 핵심 기준이며 속성 간 결정 관계를 표현한다.
- [[후보키]] - 테이블의 행을 유일하게 식별할 수 있는 최소 속성 집합으로 BCNF 판단에 중요하다.
- [[슈퍼키]] - 행을 유일하게 식별할 수 있는 속성 집합이며 BCNF에서 모든 결정자가 슈퍼키인지 확인한다.
- [[무손실 분해]] - 테이블 분해 후 조인했을 때 원래 데이터를 정확히 복원할 수 있는 성질이다.
- [[종속성 보존]] - 분해 후에도 기존 함수 종속성을 개별 테이블 제약으로 검증할 수 있는지와 관련된다.
- [[삽입 이상]] - 잘못된 테이블 설계로 인해 특정 데이터를 자연스럽게 삽입하기 어려운 문제다.
- [[수정 이상]] - 중복 데이터 일부만 수정되어 데이터 불일치가 발생하는 문제다.
- [[삭제 이상]] - 특정 행 삭제로 인해 보존해야 할 정보까지 함께 사라지는 문제다.
- [[인덱스]] - 반정규화 전에 검토해야 할 대표적인 조회 성능 최적화 수단이다.
- [[CQRS]] - 쓰기 모델과 읽기 모델을 분리하며, 읽기 모델에서 반정규화를 자주 활용한다.
- [[Materialized View]] - 미리 계산된 조회 결과를 저장해 조인과 집계 비용을 줄이는 반정규화 기법과 관련된다.
- [[데이터 무결성]] - 정규화의 주요 목표이며 기본키, 외래키, UNIQUE, NOT NULL 제약조건과 연결된다.
