# 캐싱 전략 - Look-aside, Write-through, Write-behind, Redis 영속성(RDB, AOF)

## 핵심 개념

## 캐싱 전략: Look-aside, Write-through, Write-behind, Redis 영속성

캐싱 전략은 애플리케이션과 데이터베이스 사이에 빠른 저장소를 두고, 읽기 성능 향상과 데이터베이스 부하 감소를 달성하기 위한 설계 방식이다. 일반적으로 캐시는 Redis, Memcached 같은 인메모리 저장소를 사용하며, 원본 데이터는 RDBMS나 NoSQL 데이터베이스에 저장된다. 캐싱 전략이 중요한 이유는 단순히 “빠르게 읽기”만을 위한 것이 아니라, 데이터 정합성, 장애 복구, 쓰기 지연, 캐시 무효화, 트래픽 폭증 대응 등 백엔드 시스템의 안정성과 직결되기 때문이다.

대표적인 전략에는 **Look-aside Cache**, **Write-through Cache**, **Write-behind Cache**가 있다. Look-aside는 애플리케이션이 캐시를 먼저 조회하고, 없으면 DB에서 읽어 캐시에 채우는 방식이다. Write-through는 데이터를 쓸 때 캐시와 DB에 함께 반영하여 읽기 시 최신 데이터를 얻기 쉽게 만든다. Write-behind는 캐시에 먼저 쓰고 DB 반영은 비동기로 지연 처리하여 쓰기 성능을 높인다.

Redis는 인메모리 저장소이지만, 장애나 재시작 후 데이터를 복구하기 위해 **RDB 스냅샷**과 **AOF(Append Only File)**라는 영속성 기능을 제공한다. RDB는 특정 시점의 메모리 상태를 파일로 저장하는 방식이고, AOF는 쓰기 명령을 로그처럼 기록하는 방식이다. 캐싱 시스템에서 Redis 영속성은 “캐시 데이터도 복구할 것인가”, “장애 시 어느 정도 데이터 유실을 허용할 것인가”, “성능과 안정성 중 무엇을 우선할 것인가”를 결정하는 중요한 설계 요소다.

## 내부 동작 원리

## 1. Look-aside Cache

Look-aside Cache는 **Cache-aside**라고도 부르며, 가장 널리 사용되는 캐싱 패턴 중 하나다. 애플리케이션이 캐시와 DB 접근을 직접 제어한다.

### 읽기 흐름

```text
Client
  |
  v
Application
  |
  | 1. Cache 조회
  v
Redis Cache
  |
  |-- Cache Hit --> Application --> Client
  |
  |-- Cache Miss
          |
          v
       Database 조회
          |
          v
       Redis에 저장
          |
          v
       Client에 응답
```

### 동작 과정

1. 클라이언트가 데이터를 요청한다.
2. 애플리케이션은 먼저 Redis 같은 캐시를 조회한다.
3. 캐시에 값이 있으면 바로 반환한다. 이를 **Cache Hit**라고 한다.
4. 캐시에 값이 없으면 DB에서 데이터를 조회한다. 이를 **Cache Miss**라고 한다.
5. DB에서 가져온 값을 캐시에 저장한다.
6. 이후 같은 요청은 캐시에서 빠르게 응답한다.

### 장점

- 구현이 비교적 단순하다.
- 자주 조회되는 데이터만 자연스럽게 캐시에 적재된다.
- 장애 시 캐시가 비어 있어도 DB에서 데이터를 읽어 복구 가능하다.

### 단점

- 최초 요청은 Cache Miss로 인해 느릴 수 있다.
- 캐시와 DB 간 데이터 불일치가 발생할 수 있다.
- 특정 키가 만료된 직후 대량 요청이 몰리면 **Cache Stampede**가 발생할 수 있다.

---

## 2. Write-through Cache

Write-through는 쓰기 요청이 들어올 때 **캐시와 DB를 함께 갱신**하는 전략이다. 일반적으로 쓰기 성공 응답은 캐시와 DB 반영이 완료된 뒤 반환된다.

### 쓰기 흐름

```text
Client
  |
  v
Application
  |
  | 1. 데이터 쓰기 요청
  v
Cache 갱신
  |
  v
Database 갱신
  |
  v
Client에 성공 응답
```

또는 구현에 따라 다음과 같이 캐시 계층이 DB 쓰기를 담당할 수도 있다.

```text
Application
  |
  v
Cache Layer
  |
  v
Database
```

### 동작 과정

1. 사용자가 데이터를 생성하거나 수정한다.
2. 애플리케이션은 캐시에 먼저 데이터를 반영한다.
3. 이어서 DB에도 같은 데이터를 반영한다.
4. 두 저장소 모두 성공적으로 반영되면 클라이언트에 성공 응답을 보낸다.

### 장점

- 캐시에 최신 데이터가 유지될 가능성이 높다.
- 읽기 요청이 많은 시스템에서 Cache Hit 비율을 안정적으로 유지할 수 있다.
- DB와 캐시 간 불일치를 줄일 수 있다.

### 단점

- 쓰기 지연 시간이 증가한다.
- 캐시 또는 DB 중 하나가 실패할 경우 트랜잭션 처리와 롤백 전략이 필요하다.
- 자주 읽히지 않는 데이터도 캐시에 저장될 수 있어 메모리 낭비가 발생할 수 있다.

---

## 3. Write-behind Cache

Write-behind는 **Write-back Cache**라고도 부르며, 쓰기 요청을 캐시에 먼저 반영하고 DB 반영은 비동기로 처리하는 방식이다.

### 쓰기 흐름

```text
Client
  |
  v
Application
  |
  | 1. Cache에 쓰기
  v
Redis Cache
  |
  | 2. 즉시 성공 응답
  v
Client

비동기 작업자
  |
  | 3. 일정 시간 후 또는 큐 기반으로 DB 반영
  v
Database
```

### 동작 과정

1. 클라이언트가 쓰기 요청을 보낸다.
2. 애플리케이션은 캐시에 데이터를 저장한다.
3. 클라이언트에는 빠르게 성공 응답을 보낸다.
4. 별도의 비동기 워커나 메시지 큐가 변경 내용을 DB에 반영한다.
5. DB 반영 실패 시 재시도, 보상 트랜잭션, Dead Letter Queue 같은 장애 처리 전략이 필요하다.

### 장점

- 쓰기 응답 속도가 빠르다.
- 짧은 시간에 많은 쓰기가 몰리는 환경에서 DB 부하를 줄일 수 있다.
- 여러 번의 쓰기를 병합하여 DB에 반영할 수 있다.

### 단점

- 캐시 장애 시 아직 DB에 반영되지 않은 데이터가 유실될 수 있다.
- DB와 캐시 간 일시적 불일치가 발생한다.
- 구현 복잡도가 높고, 재시도 및 순서 보장 문제가 중요하다.

---

## 4. Redis RDB 영속성

RDB는 Redis 메모리 데이터를 특정 시점에 스냅샷 파일로 저장하는 방식이다. Redis는 백그라운드 저장 시 일반적으로 `fork()`를 사용해 자식 프로세스를 만들고, 자식 프로세스가 RDB 파일을 생성한다. 운영체제의 Copy-on-Write 특성 때문에 스냅샷 생성 중 변경된 메모리 페이지는 복사될 수 있다.

### RDB 동작 개념

```text
Redis Memory
  |
  | 특정 조건 또는 명령에 의해 스냅샷 생성
  v
Background Process
  |
  v
dump.rdb 파일 생성
```

### 특징

- 복구 속도가 비교적 빠른 편이다.
- 파일 크기가 AOF보다 작을 수 있다.
- 스냅샷 간격 사이에 장애가 발생하면 최근 변경 데이터는 유실될 수 있다.
- 대용량 데이터에서 `fork()` 비용과 디스크 I/O 영향을 고려해야 한다.

---

## 5. Redis AOF 영속성

AOF는 Redis에 들어온 쓰기 명령을 Append-only 로그 파일에 기록하는 방식이다. Redis 재시작 시 AOF 파일의 명령을 다시 실행하여 데이터를 복구한다.

### AOF 동작 개념

```text
Client Write Command
  |
  v
Redis Memory 반영
  |
  v
AOF Buffer
  |
  v
appendonly.aof 기록
  |
  v
장애 후 재시작 시 명령 재실행
```

### fsync 정책

Redis AOF는 디스크 동기화 정책을 설정할 수 있다.

- `always`: 매 쓰기마다 디스크 동기화. 안정성은 높지만 성능 부담이 크다.
- `everysec`: 일반적으로 1초 단위로 동기화. 성능과 안정성의 균형을 목표로 한다.
- `no`: 운영체제의 디스크 동기화 정책에 맡긴다. 성능은 좋을 수 있으나 장애 시 유실 가능성이 커진다.

### AOF Rewrite

AOF는 시간이 지날수록 파일이 커질 수 있으므로 Redis는 AOF rewrite를 통해 현재 데이터 상태를 재구성하는 최소 명령 집합으로 파일을 다시 작성한다.

```text
기존 AOF:
SET user:1 nameA
SET user:1 nameB
SET user:1 nameC

Rewrite 후:
SET user:1 nameC
```

### RDB와 AOF 비교

| 항목 | RDB | AOF |
|---|---|---|
| 저장 방식 | 특정 시점 스냅샷 | 쓰기 명령 로그 |
| 복구 방식 | 스냅샷 로드 | 명령 재실행 |
| 데이터 유실 가능성 | 스냅샷 이후 변경분 유실 가능 | fsync 정책에 따라 다름 |
| 파일 크기 | 상대적으로 작을 수 있음 | 커질 수 있음 |
| 성능 영향 | 스냅샷 시점에 영향 | 쓰기마다 로그 기록 영향 |
| 적합한 용도 | 빠른 백업, 복구 | 더 높은 내구성 요구 |

Redis에서는 RDB와 AOF를 함께 사용할 수도 있다. 이 경우 장애 복구 시 더 최신 데이터를 제공할 가능성이 있는 AOF가 활용될 수 있다.

## 실제 시스템 연결

## 실제 시스템에서의 연결

### 1. Linux와 Redis 영속성

Redis는 Linux 환경에서 많이 운영된다. RDB 생성 시 `fork()`가 사용될 수 있으며, 이는 Linux의 프로세스 생성과 Copy-on-Write 메모리 관리 방식과 관련된다. 대규모 Redis 인스턴스에서 RDB 또는 AOF rewrite가 발생하면 CPU, 메모리, 디스크 I/O에 영향을 줄 수 있다.

운영 시 확인할 주요 지표는 다음과 같다.

```text
CPU 사용률
메모리 사용률
디스크 I/O 대기
Redis used_memory
Redis evicted_keys
Redis keyspace_hits / keyspace_misses
AOF rewrite 상태
RDB save 상태
```

Linux의 `vm.overcommit_memory` 설정은 Redis 운영 문서에서 자주 언급되는 항목이다. Redis가 백그라운드 저장을 위해 `fork()`를 수행할 때 메모리 할당 정책이 영향을 줄 수 있기 때문이다.

---

### 2. AWS ElastiCache for Redis

AWS에서는 Redis 호환 캐시 서비스로 **Amazon ElastiCache for Redis** 또는 **Amazon ElastiCache Serverless**를 사용할 수 있다. Look-aside Cache는 애플리케이션이 ElastiCache를 먼저 조회하고, Cache Miss 시 Amazon RDS, Aurora, DynamoDB 등을 조회하는 구조로 자주 사용된다.

```text
Application
  |
  v
ElastiCache Redis
  |
  | Miss
  v
Amazon RDS / Aurora / DynamoDB
```

실제 예시는 다음과 같다.

- 상품 상세 정보 캐싱
- 로그인 세션 저장
- API 응답 캐싱
- 랭킹 데이터 저장
- Rate Limiting 카운터 저장

ElastiCache Redis에서는 장애 조치, 복제, 백업 설정 등을 통해 가용성을 높일 수 있다. 다만 캐시는 원본 DB가 아니므로, 어떤 데이터까지 캐시에 의존할지 신중히 설계해야 한다.

---

### 3. GCP Memorystore for Redis

GCP에서는 **Memorystore for Redis**를 통해 관리형 Redis 서비스를 제공한다. Cloud SQL, Spanner, Firestore와 함께 캐시 계층으로 사용할 수 있다.

```text
Cloud Run / GKE / Compute Engine
  |
  v
Memorystore for Redis
  |
  v
Cloud SQL / Spanner / Firestore
```

예를 들어 Cloud Run 기반 백엔드에서 Redis를 Look-aside Cache로 사용하면 DB 조회 횟수를 줄일 수 있다. GKE에서는 Redis를 직접 배포할 수도 있지만, 운영 복잡도를 줄이기 위해 Memorystore 같은 관리형 서비스를 선택하는 경우가 많다.

---

### 4. Nginx와 캐싱

Nginx는 HTTP 응답 캐싱을 지원한다. Redis 캐싱이 주로 애플리케이션 데이터 객체 단위라면, Nginx 캐싱은 HTTP 응답 단위 캐싱에 가깝다.

```text
Client
  |
  v
Nginx Cache
  |
  | Miss
  v
Backend Application
  |
  v
Database / Redis
```

Nginx 캐시는 정적 파일, API 응답, 프록시 응답을 캐싱하는 데 사용할 수 있다. 단, 사용자별로 달라지는 응답을 잘못 캐싱하면 개인정보 노출 문제가 발생할 수 있다.

---

### 5. 실제 서비스 설계 예시

#### 상품 조회 서비스

```text
1. 사용자가 상품 상세 페이지 요청
2. Application이 Redis에서 product:{id} 조회
3. Hit이면 Redis 데이터 반환
4. Miss이면 DB에서 상품 조회
5. Redis에 TTL과 함께 저장
6. 사용자에게 응답
```

이 경우 Look-aside Cache가 적합하다. 상품 정보는 읽기 요청이 많고, 변경 빈도는 상대적으로 낮은 경우가 많기 때문이다.

#### 주문 처리 서비스

주문, 결제, 재고 차감처럼 강한 정합성이 필요한 영역에서는 단순 Write-behind를 신중하게 사용해야 한다. DB 반영 전에 캐시 장애가 발생하면 중요한 데이터가 유실될 수 있기 때문이다. 이런 경우에는 DB를 먼저 갱신하고 캐시를 무효화하거나 갱신하는 방식이 더 안전한 경우가 많다.

## 클라우드 연결

## 클라우드 및 컨테이너 환경과의 연결

### 1. Docker에서 Redis 사용

개발 환경에서는 Docker로 Redis를 쉽게 실행할 수 있다.

```bash
docker run --name redis -p 6379:6379 redis
```

영속성을 테스트하려면 볼륨 마운트를 사용해 RDB 또는 AOF 파일을 컨테이너 외부에 보존해야 한다.

```bash
docker run --name redis \
  -p 6379:6379 \
  -v redis-data:/data \
  redis redis-server --appendonly yes
```

컨테이너는 삭제될 수 있는 실행 단위이므로, Redis 데이터를 보존하려면 Docker Volume 또는 외부 스토리지를 사용해야 한다.

---

### 2. Kubernetes에서 Redis 운영

Kubernetes에서 Redis를 직접 운영할 경우 다음 요소를 고려해야 한다.

- `StatefulSet`: Redis처럼 상태를 가진 워크로드에 적합
- `PersistentVolume`: RDB, AOF 파일 보존
- `Service`: 애플리케이션에서 Redis 접근
- `ConfigMap`: Redis 설정 관리
- `Secret`: 인증 정보 관리
- `PodDisruptionBudget`: 의도치 않은 중단 최소화
- `livenessProbe`, `readinessProbe`: 상태 확인

구조 예시는 다음과 같다.

```text
Application Pods
  |
  v
Redis Service
  |
  v
Redis StatefulSet
  |
  v
PersistentVolume
```

Redis를 캐시로만 사용할 경우 영속성을 끌 수도 있지만, 세션 저장소나 Write-behind 버퍼처럼 데이터 유실이 문제가 되는 경우에는 영속성 설정과 복제 구성이 중요하다.

---

### 3. AWS 아키텍처 예시

AWS에서 Look-aside Cache 구조는 다음과 같이 설계할 수 있다.

```text
Client
  |
  v
ALB
  |
  v
ECS / EKS / EC2 Application
  |
  v
ElastiCache Redis
  |
  v
RDS / Aurora
```

서비스별 역할은 다음과 같다.

- **ALB**: HTTP 트래픽 분산
- **ECS/EKS/EC2**: 애플리케이션 실행
- **ElastiCache Redis**: 캐시 계층
- **RDS/Aurora**: 원본 데이터 저장소
- **CloudWatch**: 지표와 로그 모니터링
- **Secrets Manager**: Redis 인증 정보, DB 비밀번호 관리

캐시 장애 시 애플리케이션이 DB로 직접 fallback할 수 있도록 설계하면 가용성을 높일 수 있다. 다만 대규모 트래픽에서 Redis 장애가 곧바로 DB 폭주로 이어질 수 있으므로 Circuit Breaker, Rate Limiting, Graceful Degradation을 함께 고려해야 한다.

---

### 4. 메시지 큐와 Write-behind

Write-behind를 클라우드에서 구현할 때는 메시지 큐를 함께 사용하는 경우가 많다.

```text
Application
  |
  v
Redis Cache
  |
  v
Message Queue
  |
  v
Worker
  |
  v
Database
```

AWS에서는 SQS, MSK, Kinesis 등을 사용할 수 있고, GCP에서는 Pub/Sub, Cloud Tasks 등을 사용할 수 있다. 큐를 사용하면 DB 반영 실패 시 재시도, 순서 제어, 처리량 조절이 더 쉬워진다.

단, 메시지 큐를 사용해도 정확히 한 번 처리 보장은 구현과 서비스 특성에 따라 달라진다. 일반적으로는 멱등성 키, 중복 처리 방지, 재시도 정책을 함께 설계해야 한다.

---

### 5. Redis 영속성과 클라우드 스토리지

관리형 Redis 서비스에서는 백업, 스냅샷, 복제, 장애 조치 기능을 제공하는 경우가 많다. 직접 Redis를 운영한다면 RDB/AOF 파일을 주기적으로 오브젝트 스토리지에 백업할 수 있다.

```text
Redis RDB/AOF
  |
  v
Persistent Volume
  |
  v
Backup Job
  |
  v
S3 / GCS / Object Storage
```

백업만으로는 완전한 고가용성을 보장하지 않는다. 복구 시간 목표인 RTO와 복구 시점 목표인 RPO를 기준으로 백업 주기, AOF 정책, 복제 구성을 함께 결정해야 한다.

## 보안 연결

## 보안 이슈와 모범 사례

### 1. 캐시 데이터 노출

Redis에는 세션 토큰, 사용자 프로필, 권한 정보, API 응답 등 민감한 데이터가 저장될 수 있다. 캐시라고 해서 보안 중요도가 낮아지는 것은 아니다. 캐시 데이터가 유출되면 DB 유출과 유사한 피해가 발생할 수 있다.

모범 사례:

- 민감 데이터는 가능한 최소한만 캐싱한다.
- 토큰, 개인정보는 암호화 또는 해싱 후 저장을 검토한다.
- TTL을 설정해 불필요하게 오래 남지 않도록 한다.
- 사용자별 데이터와 공용 데이터를 명확히 분리한다.

---

### 2. Redis 접근 제어

Redis를 인터넷에 직접 노출하는 것은 위험하다. Redis는 일반적으로 신뢰된 내부 네트워크에서 접근하도록 구성한다.

모범 사례:

```text
Application Subnet
  |
  v
Private Redis Endpoint
```

- Redis를 Public IP로 노출하지 않는다.
- Security Group, Firewall, VPC, Subnet으로 접근을 제한한다.
- Redis AUTH 또는 ACL을 사용한다.
- TLS를 지원하는 환경에서는 전송 구간 암호화를 활성화한다.
- 기본 포트 접근을 제한하고, 운영망과 관리망을 분리한다.

---

### 3. 캐시 무효화 실패와 권한 문제

권한 정보나 사용자 상태를 캐싱할 때 캐시 무효화가 제대로 되지 않으면 보안 문제가 발생할 수 있다.

예시:

```text
1. 사용자의 관리자 권한 제거
2. DB에는 권한 제거 반영
3. Redis에는 기존 권한 데이터가 남아 있음
4. 사용자는 TTL 만료 전까지 관리자 권한처럼 동작 가능
```

대응 방법:

- 권한 관련 캐시는 TTL을 짧게 설정한다.
- 권한 변경 시 캐시를 즉시 삭제하거나 갱신한다.
- 중요한 권한 검사는 DB 또는 권한 서버에서 재검증한다.
- 캐시 키에 권한 버전 또는 사용자 상태 버전을 포함한다.

---

### 4. Cache Poisoning

Cache Poisoning은 공격자가 잘못된 데이터를 캐시에 저장하게 만들어 다른 사용자에게 오염된 응답을 제공하게 하는 공격이다. HTTP 캐시, CDN, 애플리케이션 캐시 모두에서 발생할 수 있다.

대응 방법:

- 캐시 키 생성 기준을 명확히 한다.
- 사용자 입력값이 캐시 키나 캐시 값에 영향을 줄 경우 검증한다.
- 인증 사용자 응답과 비인증 사용자 응답을 분리한다.
- `Authorization`, `Cookie`, `Accept-Language` 등 응답 차이에 영향을 주는 헤더를 고려한다.
- 사용자별 응답을 공용 캐시에 저장하지 않는다.

---

### 5. Cache Stampede와 서비스 거부

인기 키가 동시에 만료되면 다수 요청이 한꺼번에 DB로 몰릴 수 있다. 이는 장애 상황에서 서비스 거부와 유사한 결과를 만들 수 있다.

대응 방법:

- TTL에 랜덤 지터를 추가한다.
- Mutex Lock 또는 Single Flight 패턴을 사용한다.
- Soft TTL과 Hard TTL을 분리한다.
- 백그라운드 캐시 갱신을 사용한다.
- 인기 데이터를 사전에 warming한다.
- DB fallback 요청에 Rate Limit을 적용한다.

---

### 6. Redis 명령어 오남용

운영 Redis에서 `KEYS *`, 큰 범위의 `LRANGE`, 대량 삭제 등은 성능에 큰 영향을 줄 수 있다. 특히 단일 스레드 이벤트 루프 기반으로 명령을 처리하는 Redis 특성상 오래 걸리는 명령은 다른 요청의 지연을 유발할 수 있다.

모범 사례:

- 운영 환경에서 `KEYS` 대신 `SCAN` 사용
- 큰 키, Hot Key 모니터링
- 키별 TTL 정책 적용
- 메모리 상한과 eviction 정책 설정
- 관리자 명령 접근 제한

## 면접 질문

**Q1. Look-aside Cache는 어떻게 동작하나요?**  
> 핵심 답변: 애플리케이션이 먼저 캐시를 조회하고, Cache Hit이면 바로 반환한다. Cache Miss이면 DB에서 데이터를 읽은 뒤 캐시에 저장하고 응답한다. 구현이 단순하고 자주 읽히는 데이터만 캐시에 올라간다는 장점이 있지만, 최초 요청 지연과 캐시-DB 불일치 문제가 있다.

**Q2. Write-through와 Write-behind의 차이는 무엇인가요?**  
> 핵심 답변: Write-through는 쓰기 시 캐시와 DB에 동기적으로 반영한 뒤 응답한다. 정합성은 높지만 쓰기 지연이 증가한다. Write-behind는 캐시에 먼저 쓰고 DB 반영은 비동기로 처리한다. 쓰기 성능은 좋지만 장애 시 데이터 유실과 일시적 불일치 위험이 있다.

**Q3. Redis RDB와 AOF의 차이를 설명해주세요.**  
> 핵심 답변: RDB는 특정 시점의 메모리 상태를 스냅샷 파일로 저장한다. 복구가 빠르고 파일이 작을 수 있지만 스냅샷 이후 데이터는 유실될 수 있다. AOF는 쓰기 명령을 로그로 남겨 재시작 시 재실행한다. 내구성을 더 높일 수 있지만 파일 크기와 쓰기 성능 부담이 있다.

**Q4. Cache Stampede는 무엇이고 어떻게 방지하나요?**  
> 핵심 답변: 인기 캐시 키가 만료된 순간 다수 요청이 동시에 DB로 몰리는 현상이다. TTL 랜덤화, 분산 락, Single Flight, 백그라운드 갱신, Soft TTL, 사전 캐시 warming, Rate Limiting 등으로 완화할 수 있다.

**Q5. 캐시를 사용할 때 보안상 주의할 점은 무엇인가요?**  
> 핵심 답변: 민감 데이터를 무분별하게 캐싱하지 않아야 하며, Redis를 외부에 직접 노출하지 않아야 한다. 인증, ACL, TLS, 네트워크 접근 제어를 적용하고, 사용자별 응답과 공용 응답을 분리해야 한다. 권한 정보 캐싱 시 무효화 실패로 권한 상승 문제가 발생할 수 있으므로 TTL과 즉시 무효화 전략이 필요하다.

## 관련 개념

- [[Redis]] - 인메모리 캐시와 데이터 구조 저장소로 캐싱 전략의 대표 구현체다.
- [[Cache Aside Pattern]] - Look-aside Cache의 다른 이름으로, 애플리케이션이 캐시 적재를 직접 제어한다.
- [[Cache Invalidation]] - 캐시와 원본 DB 간 정합성을 유지하기 위해 반드시 필요한 개념이다.
- [[TTL]] - 캐시 데이터의 만료 시간을 설정해 오래된 데이터 사용을 제한한다.
- [[Cache Stampede]] - 캐시 만료 시 대량 요청이 DB로 몰리는 장애 패턴이다.
- [[Write Through Cache]] - 쓰기 시 캐시와 DB를 함께 갱신하는 전략이다.
- [[Write Behind Cache]] - 쓰기 성능 향상을 위해 DB 반영을 비동기로 지연하는 전략이다.
- [[RDB Snapshot]] - Redis의 특정 시점 데이터 스냅샷 영속성 방식이다.
- [[Append Only File]] - Redis 쓰기 명령을 로그로 저장하는 AOF 영속성 방식이다.
- [[Eventual Consistency]] - Write-behind와 분산 캐시 환경에서 자주 등장하는 최종적 일관성 개념이다.
- [[Distributed Lock]] - Cache Stampede 방지나 중복 갱신 제어에 사용된다.
- [[Message Queue]] - Write-behind에서 DB 반영 작업을 안정적으로 비동기 처리하는 데 사용된다.
- [[RTO RPO]] - Redis 영속성 및 백업 전략을 결정할 때 필요한 장애 복구 지표다.
