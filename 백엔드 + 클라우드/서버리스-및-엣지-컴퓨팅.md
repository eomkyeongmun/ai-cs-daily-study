# 서버리스 및 엣지 컴퓨팅 - AWS Lambda 서버리스 아키텍처, CDN 작동 원리

## 핵심 개념

## 서버리스 및 엣지 컴퓨팅 핵심 개념

서버리스(Serverless)는 개발자가 서버 프로비저닝, 운영체제 패치, 런타임 관리, 오토스케일링 같은 인프라 운영을 직접 관리하지 않고, 이벤트 기반으로 코드를 실행하는 컴퓨팅 모델이다. 대표적인 서비스가 **AWS Lambda**이며, 사용자는 함수 코드를 작성하고 트리거를 연결하면 된다. 서버리스라는 이름은 서버가 없다는 뜻이 아니라, 서버 관리 책임이 클라우드 제공자에게 추상화된다는 의미이다.

AWS Lambda는 HTTP 요청, S3 이벤트, DynamoDB Streams, SQS 메시지, EventBridge 이벤트 등 다양한 이벤트를 받아 짧은 단위의 함수를 실행한다. 요청이 없을 때는 비용이 거의 발생하지 않고, 요청이 증가하면 플랫폼이 실행 환경을 자동으로 늘린다. 따라서 트래픽 변동이 크거나 이벤트 기반 처리가 많은 백엔드 시스템에서 유용하다.

엣지 컴퓨팅(Edge Computing)은 사용자와 가까운 네트워크 지점에서 연산, 캐싱, 보안 처리를 수행하는 방식이다. CDN(Content Delivery Network)은 엣지 컴퓨팅의 대표적인 형태로, 정적 파일이나 일부 동적 응답을 사용자와 가까운 엣지 서버에 캐싱해 지연 시간을 줄이고 원본 서버 부하를 낮춘다. AWS에서는 CloudFront가 CDN 역할을 하며, Lambda@Edge 또는 CloudFront Functions를 통해 엣지 위치에서 요청/응답을 조작할 수 있다.

서버리스와 CDN은 현대 백엔드 인프라에서 중요한 조합이다. 서버리스는 백엔드 로직의 운영 부담을 줄이고, CDN은 글로벌 사용자에게 빠른 응답을 제공한다. 함께 사용하면 API, 이미지, 정적 웹사이트, 인증 전처리, 캐시 최적화, 트래픽 흡수 등을 효율적으로 처리할 수 있다.

## 내부 동작 원리

## 내부 동작 원리

### 1. AWS Lambda 서버리스 아키텍처 동작 과정

AWS Lambda는 이벤트 소스에서 발생한 이벤트를 함수 실행 단위로 처리한다.

```text
[Client / Event Source]
        |
        v
[API Gateway / S3 / SQS / EventBridge / DynamoDB Streams]
        |
        v
[AWS Lambda Service]
        |
        v
[Execution Environment]
  - Runtime: Node.js, Python, Java 등
  - Handler 실행
  - 환경 변수 로딩
  - IAM Role 기반 권한 사용
        |
        v
[외부 서비스 호출]
  - DynamoDB
  - RDS
  - S3
  - 외부 API
```

Lambda 함수는 크게 다음 단계로 실행된다.

1. **이벤트 발생**
   - 예: 사용자가 API Gateway 엔드포인트 호출
   - 예: S3 버킷에 객체 업로드
   - 예: SQS 큐에 메시지 적재

2. **이벤트 전달**
   - 이벤트 소스가 Lambda에 이벤트 페이로드를 전달한다.
   - 호출 방식은 동기 호출, 비동기 호출, 스트림/큐 기반 폴링 등으로 나뉜다.

3. **실행 환경 준비**
   - Lambda는 함수 코드와 설정에 맞는 실행 환경을 준비한다.
   - 이미 재사용 가능한 환경이 있으면 기존 환경을 재사용한다.
   - 새 환경이 필요하면 런타임을 초기화하고 코드를 로드한다.

4. **핸들러 실행**
   - 개발자가 정의한 handler 함수가 이벤트와 컨텍스트를 입력으로 받아 실행된다.

5. **결과 반환 또는 후속 처리**
   - 동기 호출은 호출자에게 결과를 반환한다.
   - 비동기 호출은 내부 큐에 이벤트를 저장한 뒤 처리하며, 실패 시 재시도 또는 DLQ/대상 설정을 사용할 수 있다.
   - SQS 같은 큐 기반 이벤트는 메시지 처리 성공 시 삭제된다.

### 2. 콜드 스타트와 웜 스타트

Lambda 실행 환경은 요청이 없으면 제거될 수 있고, 새 요청이 들어왔을 때 새 환경을 만들어야 할 수 있다. 이를 **콜드 스타트(Cold Start)**라고 한다.

```text
Cold Start:
[요청] -> [컨테이너/환경 생성] -> [런타임 초기화] -> [코드 로드] -> [핸들러 실행]

Warm Start:
[요청] -> [기존 실행 환경 재사용] -> [핸들러 실행]
```

콜드 스타트는 런타임, 패키지 크기, VPC 연결 여부, 초기화 코드 등에 영향을 받을 수 있다. 성능이 중요한 서비스에서는 불필요한 초기화 작업을 줄이고, 함수 패키지를 가볍게 유지하며, 필요한 경우 Provisioned Concurrency를 사용할 수 있다.

### 3. CDN 작동 원리

CDN은 전 세계 여러 지역에 배치된 엣지 서버를 통해 콘텐츠를 캐싱하고 전달한다. 사용자는 원본 서버가 아니라 지리적·네트워크적으로 가까운 엣지 서버에 접속한다.

```text
[User Browser]
      |
      v
[DNS Resolution]
      |
      v
[Nearest CDN Edge Location]
      |
      |-- Cache HIT --> [Cached Response 반환]
      |
      |-- Cache MISS --> [Origin Server 요청]
                              |
                              v
                     [S3 / ALB / Nginx / API Server]
                              |
                              v
                     [CDN Edge에 저장 후 사용자에게 반환]
```

CDN의 핵심 동작은 다음과 같다.

1. **DNS 라우팅**
   - 사용자가 `example.com`에 접근하면 DNS 또는 CDN 라우팅 메커니즘을 통해 가까운 엣지 위치로 연결된다.

2. **캐시 키 생성**
   - CDN은 URL, HTTP 메서드, Host 헤더, 쿼리스트링, 특정 헤더, 쿠키 등을 기준으로 캐시 키를 만든다.
   - 캐시 키가 달라지면 같은 리소스처럼 보여도 다른 캐시 객체로 취급될 수 있다.

3. **캐시 조회**
   - 엣지 서버에 해당 객체가 있으면 Cache Hit가 발생한다.
   - 없거나 만료되었으면 Cache Miss가 발생한다.

4. **원본 서버 요청**
   - Cache Miss 시 CDN은 Origin으로 요청을 전달한다.
   - Origin은 S3, EC2, ALB, Nginx, API 서버 등이 될 수 있다.

5. **응답 캐싱**
   - CDN은 `Cache-Control`, `Expires`, `ETag`, `Last-Modified` 같은 HTTP 캐싱 헤더를 참고해 응답을 저장한다.
   - 이후 동일한 요청은 원본까지 가지 않고 엣지에서 응답된다.

6. **TTL 만료 및 재검증**
   - TTL이 만료되면 CDN은 Origin에 재검증 요청을 보낼 수 있다.
   - `ETag` 또는 `Last-Modified` 기반으로 변경 여부를 확인할 수 있다.

### 4. 서버리스와 CDN 결합 구조

```text
[Browser]
   |
   v
[CloudFront CDN]
   |              \
   |               \-- [S3 정적 파일]
   |
   v
[API Gateway]
   |
   v
[AWS Lambda]
   |
   v
[DynamoDB / RDS / SQS / S3]
```

이 구조에서 CloudFront는 정적 리소스를 캐싱하고, API 요청은 API Gateway를 통해 Lambda로 전달한다. 이미지, JavaScript, CSS, HTML 같은 정적 파일은 S3와 CloudFront 조합으로 제공하고, 비즈니스 로직은 Lambda에서 수행하는 방식이 일반적이다.

## 실제 시스템 연결

## 실제 시스템 연결

### 1. AWS Lambda 실제 사용 사례

AWS Lambda는 다음과 같은 백엔드 작업에 자주 사용된다.

- API Gateway와 연결한 REST API 또는 HTTP API 백엔드
- S3 업로드 이벤트 기반 이미지 리사이징
- DynamoDB Streams 기반 변경 이벤트 처리
- SQS 메시지 소비자
- EventBridge 기반 배치성 이벤트 처리
- CloudWatch Logs 구독을 통한 로그 처리
- Cognito 사용자 인증 흐름의 트리거 처리

예를 들어 이미지 업로드 시스템은 다음처럼 구성할 수 있다.

```text
[사용자 이미지 업로드]
        |
        v
[S3 원본 버킷]
        |
        v
[S3 ObjectCreated 이벤트]
        |
        v
[Lambda 이미지 리사이징]
        |
        v
[S3 썸네일 버킷]
        |
        v
[CloudFront로 배포]
```

이 구조에서는 사용자가 이미지를 올리면 S3 이벤트가 Lambda를 실행하고, Lambda가 썸네일을 만든 뒤 다른 S3 경로에 저장한다. CloudFront는 생성된 이미지를 캐싱해 빠르게 전달한다.

### 2. CDN 실제 동작 사례: Nginx + CDN

전통적인 백엔드에서는 Nginx가 정적 파일 서빙, 리버스 프록시, gzip 압축, TLS 종료 등을 담당한다. 여기에 CDN을 붙이면 다음과 같은 구조가 된다.

```text
[Client]
   |
   v
[CDN Edge]
   |
   v
[Nginx Reverse Proxy]
   |
   v
[Application Server]
```

CDN은 반복 요청되는 정적 파일을 엣지에서 처리하고, Nginx는 원본 서버 앞에서 요청을 프록시한다. CDN 캐시가 잘 동작하면 Nginx와 애플리케이션 서버로 들어오는 요청 수가 줄어든다.

### 3. Linux 관점

Lambda는 개발자에게 운영체제 관리를 숨기지만, 내부적으로는 격리된 실행 환경에서 프로세스가 실행된다. 개발자는 직접 `systemd`, 커널 튜닝, 패키지 업데이트를 관리하지 않는다. 반면 EC2나 온프레미스 Linux 서버에서는 다음을 직접 운영해야 한다.

- OS 보안 패치
- 프로세스 관리
- 로그 로테이션
- 디스크 용량 관리
- 네트워크 방화벽 설정
- 런타임 설치 및 업그레이드

서버리스는 이러한 운영 부담을 줄이는 대신 실행 시간 제한, 상태 저장 제약, 콜드 스타트, 벤더 종속성 같은 고려사항을 가진다.

### 4. CloudFront 실제 사용

AWS CloudFront는 S3, ALB, API Gateway, EC2, 외부 HTTP 서버 등을 Origin으로 사용할 수 있다. 일반적인 정적 웹 호스팅 구성은 다음과 같다.

```text
[Browser]
   |
   v
[CloudFront Distribution]
   |
   v
[S3 Bucket]
```

S3 버킷은 직접 공개하지 않고, CloudFront를 통해서만 접근하도록 구성하는 것이 보안상 일반적이다. 이를 위해 Origin Access Control 또는 Origin Access Identity 같은 접근 제어 방식을 사용할 수 있다.

## 클라우드 연결

## 클라우드 연결

### 1. Docker와 서버리스

Lambda는 일반적인 VM 서버처럼 사용자가 컨테이너 오케스트레이션을 직접 관리하는 구조는 아니지만, 컨테이너 이미지를 Lambda 배포 패키지 형태로 사용할 수 있다. 즉, 애플리케이션을 컨테이너 이미지로 패키징해 Lambda에 배포할 수 있다. 다만 Lambda에서 실행되는 컨테이너 이미지는 장기 실행 서버가 아니라 Lambda 호출 모델에 따라 실행된다.

Docker 기반 배포의 장점은 다음과 같다.

- 로컬 개발 환경과 배포 환경의 차이 감소
- 대형 의존성 포함 가능
- 기존 컨테이너 빌드 파이프라인 활용
- 언어 런타임과 라이브러리 명시적 관리

### 2. Kubernetes와 서버리스 비교

Kubernetes는 컨테이너 오케스트레이션 플랫폼으로, 장기 실행 서비스와 복잡한 마이크로서비스 운영에 적합하다. 반면 Lambda는 이벤트 기반 단기 실행 작업에 적합하다.

| 구분 | AWS Lambda | Kubernetes |
|---|---|---|
| 운영 단위 | 함수 | Pod/Deployment |
| 확장 방식 | 이벤트 기반 자동 확장 | HPA, Cluster Autoscaler 등 |
| 서버 관리 | 추상화됨 | 클러스터 운영 필요 |
| 실행 모델 | 요청/이벤트 단위 | 장기 실행 프로세스 |
| 적합한 작업 | 이벤트 처리, API, 배치성 작업 | 복잡한 서비스 mesh, 장기 실행 워크로드 |

둘은 대체 관계만은 아니다. 예를 들어 핵심 API는 Kubernetes에서 운영하고, 이미지 처리나 이벤트 후처리는 Lambda로 분리할 수 있다.

### 3. AWS 서비스와의 연관성

서버리스 아키텍처는 보통 여러 AWS 관리형 서비스와 함께 구성된다.

```text
[CloudFront]
   |
   v
[API Gateway]
   |
   v
[Lambda]
   |
   +--> [DynamoDB]
   +--> [S3]
   +--> [SQS]
   +--> [SNS]
   +--> [EventBridge]
   +--> [Step Functions]
   +--> [Secrets Manager]
   +--> [CloudWatch Logs]
```

주요 연결은 다음과 같다.

- **API Gateway**: HTTP 요청을 Lambda로 전달
- **S3**: 객체 저장 및 이벤트 트리거
- **DynamoDB**: 서버리스 NoSQL 데이터베이스
- **SQS**: 비동기 메시지 큐
- **SNS**: Pub/Sub 알림
- **EventBridge**: 이벤트 버스 및 스케줄링
- **Step Functions**: 여러 Lambda 함수를 워크플로로 연결
- **CloudWatch**: 로그, 메트릭, 알람
- **IAM**: Lambda 실행 권한 제어
- **VPC**: 사설 네트워크 리소스 접근

### 4. 엣지 컴퓨팅과 AWS

AWS에서 CDN과 엣지 컴퓨팅 관련 서비스는 다음과 연결된다.

- **CloudFront**: 글로벌 CDN
- **Lambda@Edge**: CloudFront 이벤트에 연결해 엣지에서 코드 실행
- **CloudFront Functions**: 경량 요청 처리용 엣지 함수
- **AWS WAF**: CloudFront 앞단에서 웹 공격 차단
- **Shield**: DDoS 보호
- **S3 Transfer Acceleration**: 엣지 네트워크를 활용한 S3 업로드 가속

CloudFront는 캐시뿐 아니라 TLS 종료, HTTP/2 및 HTTP/3 지원, WAF 연동, Origin 장애 완화, 지리적 접근 제어 등 다양한 기능과 연결된다.

## 보안 연결

## 보안 연결

### 1. Lambda 보안 이슈

AWS Lambda는 인프라 관리 부담을 줄이지만, 애플리케이션 보안 책임이 사라지는 것은 아니다. 주요 보안 이슈는 다음과 같다.

#### IAM 권한 과다 부여

Lambda 함수는 실행 역할 IAM Role을 통해 AWS 리소스에 접근한다. 너무 넓은 권한을 부여하면 함수 코드 취약점이 곧 AWS 계정 권한 탈취로 이어질 수 있다.

**모범 사례**

- 최소 권한 원칙 적용
- 함수별 IAM Role 분리
- `s3:*`, `dynamodb:*`, `*:*` 같은 과도한 권한 지양
- 리소스 ARN 범위 제한
- CloudTrail로 API 호출 감사

#### 환경 변수에 민감정보 저장

Lambda 환경 변수에 DB 비밀번호, API 키 등을 평문으로 넣으면 유출 위험이 있다.

**모범 사례**

- AWS Secrets Manager 또는 SSM Parameter Store 사용
- KMS 암호화 적용
- 로그에 환경 변수 출력 금지
- 민감정보는 코드 저장소에 커밋하지 않기

#### 의존성 취약점

서버리스 함수도 외부 라이브러리를 사용하므로, npm, pip, Maven 패키지 취약점이 문제가 될 수 있다.

**모범 사례**

- 의존성 스캔 도구 사용
- 불필요한 패키지 제거
- 런타임 버전 업데이트
- 배포 패키지 최소화

#### 이벤트 입력 검증 부족

API Gateway, SQS, S3 이벤트 등 외부 입력을 신뢰하면 인젝션, 권한 우회, 데이터 오염 문제가 발생할 수 있다.

**모범 사례**

- 입력 스키마 검증
- SQL/NoSQL 인젝션 방어
- 파일 업로드 MIME 타입 및 확장자 검증
- 사용자 인증·인가를 Lambda 내부에서도 확인

### 2. CDN 보안 이슈

#### 캐시 포이즈닝

캐시 포이즈닝(Cache Poisoning)은 공격자가 조작된 응답을 CDN 캐시에 저장시켜 다른 사용자에게 전달되게 만드는 공격이다.

**모범 사례**

- 캐시 키에 포함할 헤더, 쿠키, 쿼리스트링을 명확히 제한
- 사용자별 응답은 캐싱하지 않기
- `Cache-Control: private`, `no-store` 적절히 사용
- Origin에서 신뢰할 수 없는 헤더 기반으로 응답을 바꾸지 않기

#### 민감정보 캐싱

인증된 사용자 응답이나 개인정보가 포함된 응답을 CDN이 캐싱하면 다른 사용자에게 노출될 수 있다.

**모범 사례**

- 로그인 사용자 응답에 `Cache-Control: private` 또는 `no-store` 사용
- Authorization 헤더가 있는 요청의 캐싱 정책 주의
- Set-Cookie 포함 응답 캐싱 여부 검토
- API 응답 캐싱 시 사용자 식별 요소를 캐시 키에 반영하거나 캐싱 금지

#### Origin 직접 접근

CDN을 앞단에 두더라도 Origin 서버가 공개되어 있으면 공격자가 CDN을 우회해 직접 공격할 수 있다.

**모범 사례**

- S3는 CloudFront Origin Access Control 사용
- ALB/EC2는 보안 그룹에서 CloudFront IP 대역만 허용 검토
- Origin에 인증 헤더 또는 mTLS 등 추가 보호 적용
- WAF를 CloudFront에 연결

#### DDoS와 트래픽 폭주

CDN은 대규모 정적 콘텐츠 요청을 흡수할 수 있지만, 동적 API나 캐시 미스가 많으면 Origin에 부하가 전달된다.

**모범 사례**

- 캐시 TTL 최적화
- Rate Limiting 적용
- AWS WAF 규칙 사용
- API Gateway Throttling 설정
- Lambda 예약 동시성으로 폭주 제한
- SQS를 이용한 비동기 완충

### 3. Lambda와 VPC 보안

Lambda가 RDS 같은 사설 리소스에 접근해야 하면 VPC에 연결할 수 있다. 이때 보안 그룹, 서브넷, NAT Gateway, VPC Endpoint 설계가 중요하다.

**모범 사례**

- RDS는 퍼블릭 노출 지양
- Lambda 보안 그룹에서 필요한 포트만 허용
- AWS 서비스 접근은 가능하면 VPC Endpoint 사용
- NAT Gateway를 통한 외부 접근 비용과 보안 정책 검토
- DB 커넥션 폭주 방지를 위해 RDS Proxy 고려

## 면접 질문

## 면접 질문 5개

**Q1. 서버리스는 서버가 없다는 뜻인가요? AWS Lambda 관점에서 설명해주세요.**  
> 핵심 답변: 서버가 없는 것이 아니라 서버 운영이 클라우드 제공자에게 추상화된 것이다. 개발자는 함수 코드와 이벤트 트리거를 관리하고, AWS가 실행 환경 생성, 확장, 런타임 운영 일부를 담당한다. 요청 기반 과금과 자동 확장이 장점이지만 콜드 스타트, 실행 시간 제한, 상태 저장 제약이 있다.

**Q2. Lambda의 콜드 스타트와 웜 스타트 차이는 무엇인가요?**  
> 핵심 답변: 콜드 스타트는 새 실행 환경을 준비해야 해서 런타임 초기화, 코드 로딩, 초기화 코드 실행이 필요하다. 웜 스타트는 기존 실행 환경을 재사용하므로 상대적으로 빠르다. 패키지 크기, 런타임, 초기화 로직, VPC 설정 등이 콜드 스타트에 영향을 줄 수 있다.

**Q3. CDN에서 Cache Hit와 Cache Miss는 무엇인가요?**  
> 핵심 답변: Cache Hit는 CDN 엣지 서버에 요청한 객체가 있어 Origin까지 가지 않고 응답하는 경우이다. Cache Miss는 엣지에 객체가 없거나 만료되어 Origin 서버에 요청한 뒤 응답을 받아오는 경우이다. Cache Hit 비율이 높을수록 지연 시간과 Origin 부하가 줄어든다.

**Q4. CDN 캐시 키는 왜 중요한가요?**  
> 핵심 답변: 캐시 키는 CDN이 어떤 요청을 같은 캐시 객체로 볼지 결정하는 기준이다. URL, 쿼리스트링, 헤더, 쿠키 등이 포함될 수 있다. 캐시 키 설계가 잘못되면 캐시 효율이 떨어지거나, 사용자별 응답이 다른 사용자에게 노출되는 보안 문제가 생길 수 있다.

**Q5. Lambda와 API Gateway로 API를 만들 때 보안상 주의할 점은 무엇인가요?**  
> 핵심 답변: IAM 최소 권한, 입력 검증, 인증·인가 적용, 민감정보를 Secrets Manager 등에 저장, CloudWatch 로그에 비밀값 출력 금지, API Gateway Throttling 및 WAF 적용, 의존성 취약점 관리가 중요하다. 또한 외부 이벤트를 신뢰하지 않고 Lambda 내부에서도 권한 검사를 수행해야 한다.

## 관련 개념

- [[AWS Lambda]] - 이벤트 기반 서버리스 함수 실행 서비스로 서버리스 아키텍처의 핵심 구성 요소이다.
- [[API Gateway]] - HTTP 요청을 Lambda로 연결하고 인증, 라우팅, 제한 정책을 적용할 수 있다.
- [[CloudFront]] - AWS의 CDN 서비스로 엣지 캐싱과 글로벌 콘텐츠 전송을 담당한다.
- [[CDN Cache Key]] - CDN이 요청을 캐시 객체로 식별하는 기준이며 성능과 보안에 직접 영향을 준다.
- [[Cold Start]] - 서버리스 함수의 새 실행 환경 초기화로 인해 발생하는 지연 현상이다.
- [[Edge Computing]] - 사용자와 가까운 위치에서 연산과 캐싱을 수행해 지연 시간을 줄이는 개념이다.
- [[IAM Role]] - Lambda가 AWS 리소스에 접근할 때 사용하는 권한 모델이다.
- [[S3]] - 정적 파일 저장소 및 이벤트 소스로 Lambda, CloudFront와 자주 연결된다.
- [[SQS]] - Lambda와 함께 비동기 메시지 처리 및 트래픽 완충에 사용된다.
- [[AWS WAF]] - CloudFront나 API Gateway 앞단에서 웹 공격을 필터링하는 보안 서비스이다.
- [[Cache-Control]] - 브라우저와 CDN의 캐싱 동작을 제어하는 HTTP 헤더이다.
- [[Origin Server]] - CDN이 캐시 미스 시 콘텐츠를 가져오는 원본 서버이다.
